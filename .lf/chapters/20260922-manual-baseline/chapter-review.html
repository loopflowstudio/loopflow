Technical history

From remote lfd requests to execution on the owning Home

No formal summer snapshot survives. This reconstruction starts with the service-shaped runtime documented on 30 June and ends with the checked architecture on 22 September. It excludes the planning redesign except where durable Work hands an objective to execution.

The topological change

Before Client → HTTP → lfd → runtime

The Mac app reached remote lfd over HTTPS. A large client/service API carried lifecycle reads and actions, encouraging the daemon's representation to stand in for execution truth.

After Client → lf ssh → target Home's lf

The target executes the same complete command against its own files, store, credentials, processes, and providers. SSH is transport. lfd remains a local keeper, not the universal runtime API.

The enabling boundary

The topology only works if durable Work is distinct from the process acting on it. Wave, Project, or Task Work preserves purpose, input, status, and a controller playhead. A controller reconstructs one boundary, executes it, records one transition, and can disappear. A Run records one provider launch on the Home that launched it; attribution explains why it ran but grants no Work, Git, credential, or signal authority.

This boundary emerged through a reversal. On 18 July the system deleted duplicate Project and Task Session controllers and made Run the single execution path. That ended a split brain. Dogfooding then showed Run still carried too much meaning. By September, Work owned purpose, the provider owned conversation continuity, the direct spawner owned its child, the OS supplied current liveness, and Run had narrowed to immutable evidence and causality.

Early summerThe runtime was held together by its container

Service connection, tmux, environment, worktree names, controller Sessions, and ledger rows overlapped. They could each appear to answer what persisted, what was live, what was controllable, and what happened. Recovery and presentation repeatedly chose the wrong one.

18–23 JulyOne execution substrate replaced duplicate controller stacks

Session controllers collapsed into Run; cross-provider recovery followed. Immediate dogfood exposed missing-flow retry storms, containment presented as progress, synthetic Runs used for controller facts, and empty execution slots treated as retry permission.

20–30 AugustThe distributed topology was made explicit

Recorded history was separated from current liveness. Trace contention stopped killing healthy Work. Recovery began depending on direct process truth rather than telemetry completeness. Main agents moved into worktrees. Session returned with the narrower meaning of provider-native continuity or a human boundary. Mac reads moved from the lfd API to shared lf --json projections.

22 SeptemberAuthority is clearer than observation

The current architecture enumerates its owners and projections, but users still cannot reconstruct every execution. Settled records lack context, replay contracts, token or cost evidence; cross-source state can disagree; and no unattended replay cohort exists. The runtime boundaries moved faster than tracing.

What “getting it right” required

Once each Home executes locally, guarantees previously hidden inside one service have to be explicit. Identity cannot be recovered from a path or inherited environment. Placement cannot imply liveness. An old event cannot be shown as current state. Monitoring cannot gate the work it observes. A visible PID cannot manufacture control authority. Remote scope cannot remain ambient.

Read this way, most later runtime work was not a collection of unrelated lifecycle defects. It was the work of making the command-on-the-owning-Home model survive restart, concurrency, missing telemetry, provider replacement, remote placement, and partial failure.

Where the work actually happened

The topology is an Infrastructure story, but the recorded implementation was mostly Product work. That was not simply misplaced development: failures in real product use correctly drove the redesign and clarified which mechanics should remain durable Infrastructure responsibilities. Product's loopflow-api Tasks built Session-to-Run convergence, cross-provider recovery, capability boundaries, explicit execution context, nonfatal tracing, watched landing, and human checkpoints. Product memory also records the Mac HTTP-client deletion. The Wave spent much of August building the runtime beneath the surface. Its Sessions and fleet-loading Tasks remain open; one Mac Surface KR holds because the app avoided a second authority, while the other six fail or remain unknown.

Infrastructure supplied Home identity and placement, start/wake behavior, worktree isolation, architecture checking, promotion, credentials, cron, and release hardening. Its roster also contains trace and ledger work—lineage, capture survival, usage parsing, continuity—that fits Intelligence's stated mandate. The Wave map lagged the architecture that emerged.

What the evidence layer still lacks

Intelligence adapted the contracts late but not the operating evidence. Its immutable launch-contract and replay work matches the new authority model, but every Trace KR is false, real-ledger capture audits reported 1,767 decode failures, scheduled telemetry failed, and the activity projection has no delivery receipts for several Linear-complete Trace Tasks.

The technical map points toward monitoring rebuilt as a non-authoritative join across the design that now exists: Work boundary → owning Home and runtime artifact → Run launch contract → provider attempt and native Session → owned or merely observed process → events and terminal proof → resulting Work transition → delivery outcome. Whether that becomes a separate chapter KR remains a planning decision.

Each edge needs its source owner, stable identifier, time, freshness, and explicit missingness. A fleet index may aggregate across Homes, but it must be rebuildable and must never become the fact that decides whether a process is alive or Work may advance.

Judgment

The decentralization thesis holds when stated as a topology: Loopflow moved from clients calling a lifecycle-shaped daemon API to complete lf execution on the Home that owns the processes and evidence. The Work/execution split defined what could safely cross that boundary. The achievement was not removing centers; it was replacing one general execution center with narrow authorities whose claims do not silently transfer to one another.

What changed for users

An interpretation of the product experience, built from the objective Project evidence below. Historical chapter coverage remains incomplete.

Infrastructure

Infrastructure was meant to make Loopflow disappear beneath ordinary work: a maintainer should be able to start, resume, verify, and land changes without repairing the system that coordinates them. One part of that experience improved. Nineteen consecutive first-parent landings remained legible against the architecture model. But the larger promise is not dependable: expired Linear credentials blocked planning, all 35 observed scheduled telemetry runs failed, and the main build occupied 18.4 GiB against a 12 GiB budget. The architecture became easier to reason about; daily operation did not yet become boring.

Intelligence

Intelligence was meant to help users understand why an agent acted as it did, what context shaped the run, and whether the work could be reproduced. The strongest advance is concrete: a twenty-launch audit reconstructed ordered provider context, source identities, hashes, roles, and token totals every time. That makes individual launches more explainable. The experience still breaks at the level users need during failure or investigation. Settled records lack context, launch contracts, token counts, or cost; no unattended replay cohort exists. Loopflow remembers more, but users cannot yet treat the record as a complete explanation.

Product

Product was meant to make goal-authored work understandable and steerable from the surface a user already occupies. It preserved an important foundation: Mac, CLI, and Discord continued to share authority rather than creating separate companies inside each interface. The visible experience remains fragmented. Mac lacks Project-management edits and recovery controls; a terminated provider can appear live; there is no iOS path; and PM, Git, Work, status, and presentation state disagree in real cases. Users see more of the system, but the surfaces expose unresolved contradictions instead of resolving them.

Across the three Waves, Loopflow became more explicit about authority, context, and state, but not proportionally easier to trust. That imbalance begins in planning: many Project definitions describe the mechanism, while their KRs measure internal invariants without saying why those invariants prove a better user experience. The next chapter should name the beneficiary and experienced change first, explain the causal link from each KR to that change, and preserve an objective evidence packet beneath a short Project synthesis.
