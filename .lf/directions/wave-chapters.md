Expose Waves and Tasks in ordinary planning and execution. Resolve the one current
chapter internally; never choose a Project by name or creation time.

Chapter rotation is a deterministic, resumable operation. Preserve started work,
expire untouched backlog, keep dated history, and preserve uncertain evidence.
Task claims and retirement share the SQLite authority; first execution remains a
Task event after Flow resets. Generic Run history lives in Home Run records,
not a SQL `runs` table.

The Wave owns the enduring objective and reusable metric instruments. Its one
current Project owns Tasks, KRs, and metric targets, all shown through the Wave
UI. Rotation replaces the chapter plan without changing the Wave objective.
Preserve each closed chapter's targets and dated evaluations; do not inherit
targets implicitly or give the Project a separate objective.

Freeze predecessor metric readings and their evaluation date in the chapter
transition receipt. After activation, resuming Task transfers consumes that
receipt; changing or removing an instrument must not strand the transition.
Untargeted readings retain measured values without a success/failure verdict.
Missing current provider content is unavailable, never the original creation
plan. Missing instruments produce unresolved historical target evidence; they
must not prevent a later chapter from dropping those targets and rotating.

Desktop source selection uses a complete successful status read, including an
absent chapter. Fall back to cached authored content only when the status read
fails, with a visible stale warning. Chapter history remains reachable even
when the current plan is unavailable.

Status and roadmap project Tasks directly from chapter planning and durable
Task identity. Share that join, including stranded Tasks when provider content
is missing or malformed. Do not rebuild a Project operator tree just to flatten
it. Runtime Task DTOs need no duplicate Project/routing-parent fields; historical
Project provenance remains in the chapter sources and durable records.

Before chapter cutover, reconcile provider Task lists with durable predecessor
membership. Recover omitted Tasks through their stable issue identities;
unavailable evidence must stop cutover. Historical chapter Tasks remain outside
later rotations, and activated retries retain their frozen boundary.
Recover an omitted current Project through the durable chapter binding before
listing its Tasks. Read its provider content afresh and apply the same ownership
validation and naming rules as listed Projects. Never scan all historical local
Projects or substitute a cached plan for unavailable provider evidence.
Retire recorded predecessors by identity. Portfolio absence does not prove an
archive succeeded; use the provider's archived state to settle retries.
After cutover, refreshed Task membership must still belong to a recorded
predecessor or successor. External reassignment is unresolved in preview and
application; never reclaim or cancel it as lost-response recovery. Keep its
frozen boundary facts so the same receipt resumes after reconciliation.
Before activation, preview and application share fresh boundary enumeration,
including newly filed Tasks and edited predecessor plans. Replace saved plans
and Task evidence together only after the full read succeeds. Preview never
writes the receipt; activated retries never rebuild the frozen boundary.
Preview and application share lost-response reconciliation as well as fresh
classification. A successful cancellation still pending acknowledgment is
abandonment recovery, not unrelated historical work. Fresh completion and
conflicting evidence keep their existing precedence.
