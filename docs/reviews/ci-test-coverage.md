## Limits, review and open measurements

- This is a stratified sample, not exhaustive coverage analysis. Assertions were read for the matrix representatives and named hotspots; no mutation testing, coverage instrumentation or real-provider calls were performed. Absence of proof in this sample is not proof that no test exists elsewhere.
- CI logs measure one detailed successful run plus seven successful job summaries. Dated memory provides incident evidence, not a representative failure/retry sample. Fixture timestamp errors, reconnect protocol errors and registry throttling are different causes; none justifies calling the suite generally flaky.
- No linked private/native traces were copied into this report. Repository source, aggregate CI results and dated memory support the findings. Current deployed website content, installed behavior and external service schemas were not queried.
- Missing measurements: Cargo rebuild invalidation reasons and lock intervals; fixture setup versus waits; aggregate billed runner time by OS; cache/artifact transfer; failed/cancelled attempts; queue admission and push-to-merge. Ten consecutive runs remain the parent Task's acceptance. No dollar or percentage saving is asserted.
- Review question: can the CLI artifact be supplied through one test-owned path while retaining custom target directories, migration frontier and provenance? Nextest process-local build caching makes this a better first experiment than simply raising worker count.
- Review question: which cadence assertions truly need wall time, and which can be reduced without weakening public reconnect behavior? Do not add production timer knobs solely to make fixtures fast.
- Review question: which native-provider/version checks already exist outside ordinary CI, and who owns running them after transport changes? The ignored live one-turn smoke cannot substitute for resume/failover acceptance.
- Simulated code review found two immediate truthfulness issues: unexpected errors accepted as resolution success, and browser strings treated as proof of usable commands. It also rejected a tempting shortcut: collapsing development/published installation builds or removing macOS discovery would erase distinct proof.

Validation: read-only source/assertion/CI-log review completed; only this report added; no product changes or tests run.

## Eight decision-useful findings

1. **Do less build work first:** installation alone shows about 396s in five explicit serial build invocations; Rust library fixtures also enter Cargo through process-local caching.
2. **Three jobs independently exceed five minutes:** Rust, disposable installation and Swift all need attention; a Rust-only fix cannot meet the objective.
3. **The 121.6s resolution matrix can pass unexpected failures.** Strengthening its oracle is both a confidence improvement and a candidate for cheaper proof.
4. **The 156.2s reconnect and 134.3s no-poll tests protect valuable behavior.** Separate timed policy from integration instead of deleting them.
5. **Swift's 2:36 discovery step is mostly compilation.** Preserve its macOS process-safety assertion while reducing or relocating compatible build work.
6. **Website/docs drift is concrete:** mandatory Linear/PR wording contradicts local-Task tests; HTML/YAML command examples bypass the Markdown checker, including `graph pursue`.
7. **Green fixtures are not installed/provider/Desktop acceptance.** Existing tests often prove strong, narrow boundaries; copy and job labels should say exactly that.
8. **Cheap deletions will not buy fifteen minutes.** Prose checks and two duplicate migration executions are cleanup candidates; build reuse and fixture design should precede costed sharding or hardware selection.
