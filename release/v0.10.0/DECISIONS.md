# Decisions

## 2026-06-30 — A chord is a wave with children; family terms replace "members"

**Context:** The `goals` redesign revisited the wave/chord data model. Chords once had their own `chords` + `chord_members` tables (migration 011), which were dropped (migration 028) and folded into the `waves` table via `parent_wave_id`, `wave_type`, and `position`. The structure was already self-referential, but the vocabulary still carried "member" from the abandoned table, and the chord concept read as a separate type rather than a kind of wave.

**Decision:** A **chord is just a wave with children** — `wave_type = chord`, children pointing back via `parent_wave_id`. No separate chord entity, no `chord_members`. The relationship vocabulary is **parent / child / sibling**, not "member." The wave-structure domain drops "member" entirely. (The VSM/govern "member" — `s2-scan` member backlogs, `s5-scan` member configs — is a different domain; rename later only if it bleeds into the wave structure.)

**Implications:** One self-referential `waves` table expresses both waves and chords. Code, docs, and APIs in the wave-structure domain say parent/child/sibling. This simplifies queries (a chord's contents = children where `parent_wave_id = id`) and removes the two-concepts (wave vs chord) split in favor of one type with a `wave_type` discriminator.

## 2026-06-30 — RLM is removed; goals are the subagent-running framework

**Context:** RLM (Recursive Language Model) was a map-reduce framework — split an oversized input into chunks, fan out cheap sub-agents, aggregate — shipped as a ~150-line `RLM.md` injected unconditionally into *every* prompt's system section, plus config knobs (`rlm_agent`, `rlm_max_parallel`, `rlm_max_depth`) and depth-guard env machinery (`RLM_DEPTH` auto-increment, `propagate_rlm_env`, `seed_rlm_env`). The `goals` redesign makes the looping Wave the orchestrator that dispatches flows as inner work — its own, narrower model for running sub-agents. RLM's always-on prompt tax and its capacity-oriented framing no longer earn their place. (Supersedes the 2026-06-24 line "`RLM` becomes the unconditional system section.")

**Decision:** Delete RLM entirely — the doc, the const, the `<lf:rlm>` system-section injection, the config fields, and the depth-guard env machinery. The goals operating prompt (the universal "you are a looping orchestrator, delegate don't implement" contract carried in the launch system layer) is the new home for subagent-running guidance. The runaway stop-condition becomes goals' own blocks→human, not `RLM_MAX_DEPTH`.

**Implications:** Every prompt drops ~150 lines of always-on map-reduce playbook. The map-reduce *technique* (chunk a huge input) is no longer documented in-prompt; if it's wanted back, it returns as an invokable skill (`.lf/skills/`), not an unconditional injection. No recursion depth guard ships until the goals framework provides one — acceptable because the autonomous loop's stop-condition is human escalation by design.

## 2026-06-30 — Goals: a looping prompt primitive that supersedes direction

**Context:** `direction` was removed as machinery on 2026-06-19 (wave model is `area × flow`; direction text redistributed into skill-skills and AGENTS.md). The `goals` redesign introduces a persistent **Looping Agent** per wave that runs a **Goal** — a prompt run in a loop — steered by a live Asana roadmap, reusing existing skills/flows as inner work.

**Decision:** Add **goal** as a third prompt primitive alongside skill (run once) and flow (skills composed). A goal is "a skill that loops." It is the conceptual reincarnation of direction in its *looping, measurable* form, and the product developer's primary authoring surface ("I just want loopflow to be a good way to run my agents"). The bar: builtin skills/flows must be expressive enough to build **the clients and the servers** (mobile client, CLI client, server) from goals with **zero skill authoring**. Backend priority follows the 2026-06-19 vendor-handoff thesis: codex/claude cloud sessions **first** (adapt to the developer's workflow), hosted lfd + Ghostty **second** (ours to own). Self-extension (goals authoring skills) is the rare, mostly-internal path — no permission cage.

**Implications:** New `goal/` primitive with the standard `.lf/` override model. The loop ticker (cold stateless runs) is replaced by a persistent Looping Agent reading the goal prompt each iteration. `pm.rs` inverts from down-mirror to live Asana read + write-back. Concerto surfaces per-repo looping sessions (launcher+link for cloud, dashboard for hosted lfd). Vocabulary gaps to close: greenfield scaffold, run-the-artifact, client↔server integration, platform-specific build/test. Tracked in `wave/goals/`.

## 2026-06-30 — A wave's authored surface collapses to one `goal.md`; YAMLs, local roadmap, and area retire

**Context:** A wave was configured across three on-disk artifacts: `wave/<name>/<name>.yaml` (the `WaveConfig` seed — flow, goal, mode, area, direction, plus machinery), `wave/<name>/*.md` (a local roadmap mirror), and `.lf/goals/<name>.md` (the goal prompt). That is three files expressing one intent, and it splits the human's authoring surface. Separately, `area` (~300 refs) exists to scope an agent to relevant code — a crutch from when agents flailed without a file pointer. In practice the maintainer does not use it; agents self-scope well enough, and the context that matters (goal, metrics, roadmap) is not a file glob.

**Decision:** The human-authored surface for a wave is **one `goal.md`** — the loop prompt as body, metrics (and remaining intent) as frontmatter. The `wave/<name>/<name>.yaml` config retires; genuine machinery (crons, triggers, workers, pm) either moves to frontmatter or a thin config, decided when `goal.md`'s shape lands. The **roadmap moves to Asana** — the local `wave/<name>/*.md` mirror is retired and the goal agent reads (and writes) Asana directly. **`area` is deprecated**: left dormant, not removed in a rush, and nothing new is built on it; a dedicated later PR strips the plumbing.

**Implications:** One file to author, read, and diff per wave. `goal.md` becomes the contract the goal-authoring agent and the Concerto launch button both depend on, so its shape is sequenced first. Metrics enter the model for the first time (open fork: prose success-criteria the agent judges, vs. structured fields the loop measures). Waves without an Asana backlog lose their roadmap source — acceptable, since the redesign targets Asana-backed waves. `area` stops being a first-class wave dimension; existing plumbing is inert until removed.

## 2026-06-30 — The looping agent captures to the roadmap, then dispatches — it never solves inline

**Context:** The goals operating prompt told the Looping Agent to "delegate, don't implement," but left the mechanics vague ("when interactive subagent sessions are available"). The maintainer wants a stronger, concrete discipline: the agent must not directly solve a subproject it identifies, and every unit of work must stay externally visible and steerable — not buried in the orchestrator's own transcript.

**Decision:** The operating contract is **capture, then dispatch**. When the goal agent picks a substantial next move, it first writes it to the roadmap as an **Asana task**, then launches a flow **against that task** (`lf <flow>: <task>`), which runs as a **steerable subagent session** the human can monitor and redirect. Only atomic fixes dispatch directly. Fan-out is a gated escalation: when budget allows and the roadmap holds well-scoped independent tasks, launch **parallel** subagents (one flow per task); spawn a **child wave** when a task is itself a looping unit. The operating prompt states the full contract from turn one even though parts (budget primitive, Asana write-back, Concerto monitor/steer) are not yet wired — deliberately, so the prompt pulls the runtime forward rather than trailing it.

**Implications:** The roadmap (Asana) becomes the single source of truth for what is being worked — no work exists that isn't a task. Every subagent is observable and interruptible by construction. Four runtime capabilities are now owed by the prompt: a budget primitive (`wave/goals/2-wave-budget.md`), Asana write-back (`2-asana-roadmap.md`), flow-bound-to-Asana-task dispatch, and Concerto monitor/steer of looping sessions (`3-concerto-looping-sessions.md`). Until they land, the corresponding prompt clauses are aspirational.

## 2026-06-30 — Repo holds authored intent; lfd holds runtime state. A Wave *is* a goal agent.

**Context:** Designing the `goal.md` collapse surfaced a boundary the old `wave/<name>/<name>.yaml` violated: it seeded lfd runtime wiring (crons, triggers) *from the repo*, fusing two things that belong at different layers. It also framed a wave as a config row that *has* a goal, rather than as the looping agent itself.

**Decision:** A **Wave is a goal agent** — the looping orchestrator itself, not a container that holds a goal loop. The authored surface is one file, `wave/<name>/goal.md` (frontmatter = intent: prompt, `metrics`, `roadmap`, `agent`, `workers`, `primary_flow`; body = the loop prompt). **Repo = authored intent; lfd = runtime state.** Crons and triggers are a *lower* primitive than the goal agent — flow-level reflexes ("on signal X, fire flow Y"), no agent reasoning in the loop. They have two origins: **authored** reflexes a human records in `.lf/crons`/`.lf/triggers` to make them portable/installable (deliberate, like `.lf/skills`), and **wave-spawned** reflexes the goal agent creates while operating (lfd-only state, never written to disk). Neither lives in `goal.md`. The runtime does not auto-dump every reflex a wave creates to the repo.

**Implications:** Killing the wave YAML separates repo-authored intent from lfd-managed runtime, rather than just merging files. Wave creation sources only intent fields from `goal.md`; crons/triggers lose their repo seed path and become lfd-only (with an optional, deliberate `.lf/crons`/`.lf/triggers` authoring path for portability, a later milestone). Metrics enter as a frontmatter list of prose criteria the loop self-judges — no measurement engine until a specific loop needs a hard exit. Build order: **M1** `goal.md` as the authored surface (retire the YAML incl. its crons/triggers seed path) *plus the ruthless collapse below*; **M2** live Asana `roadmap:` read + write-back; **M3** `.lf/crons`/`.lf/triggers` portable reflex definitions; later Concerto author/spawn/steer and the budget primitive.

## 2026-06-30 — Ruthless collapse: keep the loop handles, cut the old `area × flow × direction` model

**Context:** Reflecting on the cumulative goal-primitive changes, the wave model still encoded a superseded design — a wave as `area × flow × direction`, woken by a cold ticker, configured by a repo YAML. We want the model focused on what a wave is *now*: a goal agent. A usage map (read-only) sized each candidate and caught two traps a blind delete would have hit.

**Decision:** Keep only the **loop handles** the operating contract names — *flow* (`primary_flow`, first-class on the record), *roadmap* (Asana), *metrics* — plus the *goal* prompt. Cut, as part of M1: `area` (its context-scoping use), wave-level `direction` (distinct from and not touching the `.lf/directions/` doc system), `skill_agents`, `serialized`, the `WaveConfig` all-`Optional`/`Default` YAML-mirror shape, and the serde-enforcement tests (`*_is_required` — they test serde, not the product; the type already carries the requirement). Collapse the `Wave`/`WaveConfig` duplication: `WaveConfig` = the parsed `goal.md` (required fields), `Wave` = a running instance wrapping it, no duplicated config fields. **Two corrections from the map:** (1) `WaveMode::Manual` is *not* cut — it is load-bearing (`list_loopable_waves` filters `mode='loop'`; Manual exempts cron + inline/goal waves from the ticker and gates branch advancement); it is an old-activation-model artifact that dies with the activation redesign (M2+), not now. (2) `area` scoping does *not* simply vanish: repo-trigger path scoping moves onto the trigger itself (an explicit path-pattern field — a reflex should own what it watches), and `ops/release.rs`'s `config.area` is a *different* concept (release-target manifest/PR scope) that stays.

**Implications:** The wave model shrinks to goal + handles + runtime state. `area` as a wave dimension is deleted (not dormant); the area-gated wave summary is dropped; trigger scoping becomes explicit per-trigger patterns. Test philosophy sharpens: stop writing tests that assert the type system's own guarantees. The activation model (ticker, `mode`, crons/triggers) is explicitly *not* redesigned in M1 — that's M2+, and `mode`/Manual survives until then.

## 2026-07-02 — lfd runtime ontology is Wave, Run, Session

**Context:** The goal-agent runtime cleanup exposed four overlapping lifecycle nouns: `WaveRun` for Wave-scoped execution and PR lineage, `AgentRun` for backend process state, `TerminalSession` for tmux/Ghostty attachability, and `Session` for transcript/input/usage events. Launch APIs added a fifth noun, `AgentLaunch`, as an envelope around the thing callers actually needed. This duplicated Codex/opencode's simpler shape, where "session" is the live conversation/control surface and "agent" is the performer or mode, not a durable record.

**Decision:** The lfd product model has three core nouns: **Wave**, **Run**, and **Session**. `Wave` is durable goal/memory/orchestration identity. `Run` is one agent invocation's execution/result lineage and absorbs old `WaveRun` + `AgentRun`. `Session` is the attachable live conversation/control surface and absorbs old `Session` + `TerminalSession`. Launching a Wave agent or worker returns a `Session`; `AgentLaunch` is deleted.

**Implications:** Public/core Rust types, HTTP DTOs/routes, Python/lfq models, Swift/Concerto models, and fixture names move to `Run`, `Session`, `run_id`, and `session_id`. `/v0/wave_runs` and `/v0/terminal-sessions` collapse into `/v0/runs` and `/v0/sessions`. Transport-specific UI code may still say tmux, Ghostty, or terminal when it is actually dealing with that transport; product/API code does not. Backwards compatibility aliases are not preserved for this branch.
