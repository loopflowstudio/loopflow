- #889 W2-141: Now + Available work views — research, design, and the liveness fix it proved (+26 -2, 2 files)
  - Closes W2-141 (research + product design). The design doc lived in `scratch/` and is cleared at submit per the repo rule, so the durable findings are recorded here and in the three follow-on Linear tasks.  ## The code change  `Liveness::probe` called `command_exists("tmux")`, which runs `tmux --version`. tmux only accepts `-V` and exits 1 on the long flag, so the probe reported tmux as **absent on every machine** — pinning liveness to `Unknowable`, short-circuiting `is_gone()` to false, and making the attention rule *"process is gone but the Session still records 'running'"* dead code that had never fired anywhere.  Meanwhile `process_alive` was correct all along — it's computed by `tmux_session_exists()` via `has-session`. Two liveness paths in one snapshot disagreed: one could see the process, the other believed tmux wasn't installed.  Now it asks PATH. `command_exists` is untouched — its five other callers probe `gh`, which does accept `--version`.  **Dogfooded before/after:** `product-performance` held a Project Session recording `running` with `process_alive: false` and raised no attention. It now reads `process is gone but the Session still records 'running'`. Across both waves the registry claimed 5 active sessions; only 2 tmux processes existed.  ## The design (research → decisions)  **`lf status <wave> --json` already returns the whole join** — Wave → Projects (KRs + Project Session runtime) → Tasks (PM item + Task Session runtime + worktree + branch + PR + next-move owner), plus `attention` and `runs` in `Evidence` wrappers. The PM↔Session join is already done by id (`waves.rs:643-646`). So this was never a "what data do we need" problem.  **Availability is the absence of a Session, not a PM property.** Any surface computing it from the planning store alone must reconcile against runs afterward — by *title matching*, per the docstring on the unused `RegistryQuery.backlog()`. That's the join that rots. The predicate is `!completed && runtime == None`, and both halves come from one read.  **One query, two shapes.** A lens may change the *shape*, not just filter one outline: - **Now** — flat, cross-wave, grouped by attention (Ready for review / Needs input / Working / Stopped / Failed). This is where Claude Code's agent view landed, and Conductor — the healthiest worktree manager — uses a status-grouped list, not lanes. - **Roadmap** — the `Wave → Project → Task` tree from the PM snapshot. Complete, and renderable with **zero processes running**.  **The row carries three orthogonal facts, never collapsed into one word:** PM completion × Session status × process liveness. Against real Product data the cross-product lands in six cells, and three are only legible as a pair — notably `done × none` (3 real rows: W2-87, W2-126, W2-114), which is "closed outside Loopflow", neither an error nor identical to a merged Session.  **A dead process is not a dead task.** Ghost sessions aren't an error state to clean up; they're `Stopped` rows that stay attachable and resumable and say why they stopped.  **No second store.** Now/Available stay client-side predicates. Obsidian Bases states the thesis: *"There is no `from` or `source`… the filters section narrows the dataset"* — the view holds the question, the store holds the answer. Dataview is the counter-case: a second index buys speed, constrains the query language, then goes stale.  **No kanban.** The board metaphor is losing empirically (Vibe Kanban sunsetting, Crystal deprecated, Terragon shut down), and Vibe Kanban's own docs admit dragging a card *"won't trigger any functionality"* — a board that isn't a control surface is a lie.  **Zero new verbs.** `run` / `attach` / `steer` / `resume` / `diff` / `abandon` all exist. Launch is offered exactly where `session == none` — the same predicate that defines Available. Launch and availability are the same fact.  ## Follow-on tasks filed  - **loopflow-api** — `lf work --json`: the one machine-wide read (envelope over the existing per-wave snapshot) + a derived status category, so CLI/Mac/iOS don't each re-implement a nine-arm match. Linear, Jira and Shortcut all converged independently on splitting status *name* from a fixed status *category*. - **loopflow-api** — `task_sessions.issue_id` is `UNIQUE`, so **one Task gets one Session, ever**. A merged or abandoned Task can never be re-run. That's the W2-140 bootstrap deadlock one level down, and it means the roadmap will render terminal rows with no legal action. - **mac-surface-ux** — the Now and Roadmap surfaces over `lf work`; retires the per-wave `pm show` fan-out (one spawn, not N) and deletes the unused `backlog()` / `BacklogItem`.  Plus the two that already existed: **W2-139** (truthful liveness — the Now lens is only as honest as this) and **W2-131** (all-Wave roadmap, launch/attach).  ## Open question, not decided here  **Backlog decay.** 18 of 26 Product tasks are filed-and-unstarted, and this design makes the pile *more* visible. Linear manages backlogs by decay (auto-archive); Basecamp deletes the concept; Height automated the pruning and shut down. That's a wave-level judgment about how Product carries intent, not a view predicate — picking one silently inside a rendering task would be the wrong place. Design assumes: render everything filed, no hidden staleness filter.  ## Verification  - `cargo test -p loopflow --lib engine::process` — 4 passed, including a new test pinning the probe to agree with whether tmux actually runs.   - ## Usage  ```bash lf thread follow          # watch a wave's live turns grow, delta by delta ```  The stream reconstructs each open turn from a whole-`turn` frame plus a run of small `turn-delta` increments, so the wave's speech renders token-by-token without a whole turn crossing the wire per token.  ## Summary  The live-turn wire re-broadcast the entire accumulated `ChatTurn` on every content delta — O(prose²) bytes over a turn.
