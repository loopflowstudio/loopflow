---
requires: scratch/vsm-s3.md plus member wave backlogs, open PRs, and area overlap analysis
produces: scratch/vsm-s2.md, scratch/vsm-batch.md
---
Coordinate the member waves so the next batch can run without tripping over itself.

## Goal

s2 turns s3's capacity decision into a parallel-safe batch. Resolve interference,
reorder work where dependencies changed, and only launch items that can coexist.

## Workflow

1. **Read s3.** Treat `scratch/vsm-s3.md` as the control constraint, especially
   its batch-size recommendation.

2. **Read current backlogs and PRs.** For each member wave, inspect:
   - remaining roadmap items
   - in-flight branches and open PRs
   - touched areas and likely file overlap
   - trigger relationships and dependency ordering

3. **Simulate the member perspectives.** Ask, wave by wave:
   - what does this wave believe it should do next?
   - which other wave could interfere with that work?
   - what ordering or trigger change would remove that interference?

4. **Resolve coordination issues.** Adjust backlogs or dependencies when needed
   to avoid:
   - overlapping file ownership
   - duplicate work
   - dependency inversions
   - trigger loops or oscillation

5. **Compose the batch.** Choose up to the s3 batch size worth of items that are
   safe to run in parallel. If fewer than N items are truly safe, choose fewer.

6. **Route.** After assessment, decide:
   - **continue** — coordination is clean enough; write the batch and move to s1
   - **implement** — active interference must be fixed now, then write the batch and move to s1

## Implement now when

Implement at s2 only for live coordination failures:
- conflicting PRs or overlapping branches that need immediate reordering
- duplicate work already happening in two waves
- trigger loops or dependency mistakes that would poison the next batch

Always finish by writing a clean `scratch/vsm-batch.md` for s1.

## Output

Write `scratch/vsm-s2.md`:

```markdown
# VSM S2 — <date>

## Summary
<main coordination picture and the biggest source of interference>

## Conflicts and Dependencies
| Waves | Issue | Resolution |
|-------|-------|------------|
| chord-model / agent-embedding | same files | defer item X |

## Wave Plan Updates
- <wave>: <backlog reorder, dependency change, or trigger change>

## Decision
**Route**: continue | implement
**Why**: <why this was enough or urgent>

## Actions Taken
<coordination fixes applied now, or "none">
```

Write `scratch/vsm-batch.md`:

```markdown
# VSM Batch — <date>

## Batch size
N items (determined by s3 resource assessment)

## Items
| Wave | Item | Why now |
|------|------|---------|
| chord-model | 03-wave-discovery | Unblocks disk-based wave creation |

## Parallel safety
<s2's reasoning about why these items don't conflict>
```

## What to avoid

**Optimistic concurrency.** If two items might interfere, assume they will until
you have a concrete reason they will not.

**Batch padding.** Don't fill the batch just to hit N.

**Coordination theater.** s2 must change backlogs or dependencies when conflicts
are real, not just describe the conflict and pass it downstream.
