Control the system: assess capacity, health, and the size of the next batch.

## Goal

Turn policy and environmental context into concrete control decisions. s3 judges
whether member waves are performing well enough to take on more work, where
mechanical blocks exist, and how many items the next batch can safely carry.

## Workflow

1. **Read s5 and s4.** Carry forward structural and environmental constraints.

2. **Read live state.** For each member wave, inspect:
   - `lfq show <wave> --json`
   - recent algedonic history or failure signals
   - open PR count, queue state, active run state, and recent progress
   - signs of stalls, repeated CI failures, or blocked reviews

3. **Assess control health.** For each wave, judge:
   - delivery rate and finish-line crossing
   - error rate, retry churn, and CI stability
   - whether current resource allocation matches the wave's leverage
   - whether the wave is overfed, starved, or blocked

4. **Choose batch size.** Recommend how many items the next s1 batch should run
   in parallel. Let actual capacity decide the number. Fewer is better when
   review queues, CI, or coordination are tight.

5. **Update wave plans.** Reprioritize or rebalance work where capacity or
   performance says the current ordering is wrong.

6. **Route.** After assessment, decide:
   - **continue** — write the assessment and batch recommendation, then move to s2
   - **implement** — a mechanical control issue is urgent enough to fix now, then move to s2

## Implement now when

Implement at s3 only for mechanical issues that directly prevent execution:
- failing CI that blocks active work
- a stalled run that needs cleanup or restart
- broken config, auth, or queue settings
- obvious resource misallocation that can be corrected immediately

## Output

Write `scratch/vsm-s3.md`:

```markdown

## Summary
<overall control health and the main capacity constraint>

## Member Waves
| Wave | Throughput | Error rate | Control state | Pressure |
|------|------------|------------|---------------|----------|
| chord-model | high | low | balanced | waiting on review |

## Resource Allocation
<which waves should get more, less, or no work in the next batch>

## Batch Size
**Recommendation**: <N>
**Why**: <reasoning tied to real capacity>

## Wave Plan Updates
- <wave>: <reprioritization or allocation change>

## Decision
**Route**: continue | implement
**Why**: <why this was enough or urgent>

## Actions Taken
<mechanical fixes applied now, or "none">
```

## What to avoid

**Fake precision.** Don't invent metrics you don't have. Use the live signals that exist.

**Activity bias.** Runs and PRs are not progress unless they move items across a finish line.

**Aggressive batching.** The right batch size is the amount the system can absorb,
not the amount that sounds ambitious.
