Read the environment above the system and decide what changed.

## Goal

Surface external changes that matter to this chord before they arrive as breakage
or surprise. s4 turns the outside world into concrete implications for member
waves.

## Workflow

1. **Read s5.** Start from `scratch/vsm-s5.md` so environmental scanning stays
   grounded in the current identity and boundary.

2. **Scan the environment.** Look for changes since the last cycle in:
   - dependencies, lockfiles, package registries, and release notes
   - external APIs, SDKs, auth providers, and service contracts
   - upstream code this repo tracks closely
   - security advisories, deprecations, and sunset notices
   - likely near-future changes that will affect roadmap sequencing

3. **Assess impact.** For each relevant change, decide:
   - which member wave owns the response
   - how urgent it is
   - whether the change alters roadmap ordering, scope, or feasibility
   - whether the chord's current phase still fits the environment

4. **Update wave plans.** Add or adjust roadmap items only when the environment
   materially changes what member waves should do next.

5. **Route.** After assessment, decide:
   - **continue** — record the implications and move to s3
   - **implement** — an urgent environmental change must be fixed now, then move to s3

## Implement now when

Implement at s4 only when delay is itself risky:
- a breaking dependency or API change is already landing
- a security advisory needs immediate remediation
- a service sunset or credential change will break active work

Prefer mechanical, urgent fixes. Deeper redesign belongs in later cycles unless
waiting would cause damage.

## Output

Write `scratch/vsm-s4.md`:

```markdown
# VSM S4 — <date>

## Summary
<what changed outside the chord, and why it matters>

## External Changes
| Change | Source | Urgency | Owning wave | Impact |
|--------|--------|---------|-------------|--------|
| API sunset | ... | high | agent-embedding | ... |

## Forecast
<what is likely coming next that should affect roadmap sequencing>

## Wave Plan Updates
- <wave>: <new item, reorder, or no-op>

## Decision
**Route**: continue | implement
**Why**: <why this was enough or urgent>

## Actions Taken
<urgent changes applied now, or "none">
```

## What to avoid

**Noise.** Ignore environmental changes that do not alter decisions for this chord.

**Wishlist scanning.** s4 is not trend-spotting for its own sake. Every item
must have a concrete implication.

**Unsourced claims.** Tie each environmental claim to a real dependency,
release note, advisory, contract, or upstream change.
