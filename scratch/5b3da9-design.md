# 5b3da9: Desktop live updates without lf processes, and a cheap `lf monitor work`

Jack Heart's direction, October 28, 2026: Desktop reads Loopflow through the Rust library inside the app, with an equivalent `lf` command for every call. `lf monitor work --watch` must also become efficient in its own right. Both parts are in this Task. Full brief: `lf task status 5b3da9`.

## Done when

**`lf monitor work` is efficient on its own**
- An idle store costs a reader under 2% of one core on average over 5 minutes. With several agents active, it stays under a stated budget (proposed: 15% of one core). Measured on an installed build and recorded here.
- Writes that aren't Work state, such as Process rows for read-only commands and build output in checkouts, don't trigger a Work reading.
- A reading touches only what a revision could have changed, not the whole snapshot (about 5.7 MB of Session rows today). Coordinate with LOO-670 on Session paging.
- A reader exits within a few seconds of its parent exiting or crashing, even when a descendant still holds its stdin. No `lf monitor work` with parent PID 1 survives an app quit, crash or relaunch.

**Desktop starts no `lf` processes for reads or live updates**
- The Work observation, task diff, task file and the other `RegistryQuery` reads run in-process through the Rust library. Opening Desktop and leaving it idle starts no `lf` processes and writes no Process rows.
- The replaced Swift process code is deleted in the same diff (`WorkObservation.swift` `--watch` launches, `TaskFileDocument.swift` polling, `RegistryQuery` process reads).
- One WAL watcher in the app serves every view, with the same change semantics as `lf monitor work --watch`. A Task becoming started, a new Task, or a Session change reaches Desktop within about a second, including the sidebar's Working Tasks list.
- The library runs inside the Desktop process: no resident process, `lfd`, socket or hosted service.
- Library reads stay off the main thread and release their pinned read snapshot promptly. No snapshot is held open across a wait, so WAL checkpoints keep running and the WAL doesn't grow while Desktop is open.
- A Rust panic at the library boundary becomes an error in the app, not a crash.

**Every app operation has an `lf` equivalent**
- Each operation is one Rust function returning one DTO, called by both the `lf` command and the app binding.
- A test fails when an app operation has no `lf` equivalent or the two outputs differ.

## Concept review with Jack Heart (October 29, 2026), accepted

Jack Heart's rule (comment 628f4502, refined October 29): a Process records a change a person would call work, such as adding, completing or renaming a Task. Linear sync is follow-through on an earlier write, so whether it records doesn't matter.

Accepted (Jack Heart, October 29, 2026, answers 1a and, by default, 2a) and implemented as `Commands::changes_work`: the classification asks "is this a Work change?" Work means Tasks, Waves, Projects, Sessions, Graphs, PRs and planning. UI actions and arrangement metadata record no Process and don't wake Work readers; arrangement writes still persist. In Desktop, navigation, panes, Dashboard query/pin/layout and Dashboard renames record nothing; Task renames, `send`, `send-key`, `run`, `close`, `reopen` and `do` record. `send`/`send-key`/`run` stay recorded because an agent driving a terminal is doing work.

## Decisions

- October 28, 2026 (implement pass): `lf history --watch` re-reads on the 5-minute planning clock, not the 2 s activity clock. It shows committed facts only; the clock just ages the window.
- October 28, 2026 (implement pass): a watch reads its parent's PID before starting any thread, so a parent that exits during startup is still noticed. Covered by `watch::a_watch_ends_with_its_parent_while_stdin_stays_open`.
- October 28, 2026, Jack Heart (comment d946b2bc): the library boundary has Ghostty's shape. The library never hands frames to Swift from its own threads. `watch::Reader::step` is the one reading function: the CLI's `--watch` (`Transport::Stdio`) steps it and streams to stdout; `Transport::Pull` returns a `Subscription` whose waker thread only calls a data-free wakeup when the result may have changed (a store change, a request, the read's clock), and `Subscription::pull` steps the reader on the caller's thread and returns the latest changed frame or nothing, so bursts coalesce. The reading's snapshot is dropped before `pull` returns.
- October 28, 2026, Jack Heart (comment 628f4502), replacing the implement pass's choice to keep read-only Process rows as Work state: only `lf` commands that change state record Process rows, including small edits such as renaming a Task. Reads (status, list, show, diff, file, `--watch` readers) record none, so they never wake Work readers or appear in a Task's work. `Commands::changes_work` (`lf/mod.rs`, with `MonitorCommand` and `HistoryCommand` beside their definitions) classifies every command in exhaustive matches; `lf` marks a read effect-free right after parsing. Unsure cases record (Desktop UI actions, bare `lf pr`, `release notes`). `--version` and parser errors still append evidence through early observation. A read still prepares the store it reads (`journal::mark_read` opens, creating or migrating it), so reads work on a fresh Machine; commands that touch no store keep `mark_effect_free_read`. A Graph step records its Process whatever it runs, since the Graph reads the step's result from it: the runner sets `LF_GRAPH_STEP` on its direct child, which clears it so the step's own children are not steps.
- October 28, 2026, Jack Heart (comment d6bdd719): the library boundary is a C ABI passing the existing JSON DTOs, not uniffi. `rust/loopflow-ffi` (`include/loopflow.h`): `lf_read(read, error)` and `lf_subscribe(read, wakeup, context, error)` take the same `Read` JSON; then `lf_request`, `lf_pull` / `lf_frame_free`, `lf_ended`, `lf_unsubscribe` (no wakeup after it returns), `lf_string_free`. Every entry point catches panics; a panicking or failing watch arrives as a last `unavailable` frame.
