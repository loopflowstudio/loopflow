Separate account management; decide on proxying independently.

Built from docs/subscriptions.md, docs/config.md, Rust account/auth/subscription/agent/session modules, and CLIProxyAPI 43806c8. Source review only; no live compatibility test.

CLIProxyAPI could replace much of the credential routing machinery, but equal behavior requires integration and some policy we would still own. Extracting our account subsystem is a separate, feasible option that retains native harness behavior.

Where the choice happens

Existing Loopflow
skill / Graph → lf chooses harness + model
                    ↓
              account selection → install native login
                    ↓
              native CLI → provider
              lf observes limits and resumes work

With CLIProxyAPI (proposed integration)
skill / Graph → lf chooses harness + model
                    ↓
              CLI using custom API endpoint
                    ↓
              CLIProxyAPI → chosen upstream credential → provider
                    ↓
              account / request events → lf attribution

The proxy adds a dependency on the inference path. It can switch credentials for an API request without changing the CLI's native home. Our current Claude switch affects every running Claude using that home; Codex processes retain their login until restarted. These are different concurrency semantics.

Request token counts, subscription percentages, and dollars charged are three different measurements. Neither project's token ledger alone establishes the remaining subscription allocation or actual overage charges. The proxy's example disables usage aggregation and retains its management queue for only 60 seconds by default; reliable reporting needs an intentional sink.

2. Overlap and intended use

The account layer overlaps substantially; the work orchestration layer does not. CLIProxyAPI owns provider authentication, credential pools, API translation, refresh, scheduling and request observations. Loopflow additionally owns skills, Graphs, native Sessions, worktrees, Tasks, Waves, PR operations and process ownership. Its API-client design makes it usable underneath an orchestrator like lf, but it does not replace that orchestrator.

Our meaningful difference is native provider behavior. Proxying can improve per-request credential selection and independent concurrent account use, while requiring validation of native tools, streaming, model capabilities, conversation IDs, cache behavior and usage attribution through a custom endpoint. Two autonomous selectors would make failures harder to explain: choose one owner for the account pool.

3. A separate subsystem

Proposed: a harness-independent local account service owns the catalog, secrets, refresh, browser bindings, identity checks, quota observations, cooldowns, ranking and native-home activation. It accepts provider/model/pool/preferences and returns the chosen account, eligibility and retry time. It accepts observed failures and usage, and emits account-change events.

lf: skills · Graphs · Sessions · continuation · Tasks · PRs
               │ choose / activate / observe / status
               ▼
account service: identities · login · quota · selection · native activation
               │
               └─ ordinary native CLI → provider

Optional, independent API path:
client → CLIProxyAPI → provider

Keep repository/Wave/skill interpretation in lf: send a resolved pool to the service. Keep native resume, process restart and cross-harness transcript conversion in lf. Account events carry actual identities and timestamps; lf joins them to its work. Shared-home activation remains machine-wide, so extraction alone does not create simultaneous per-process Claude account isolation.

The code has useful seams in provider_account, provider_auth and subscription. It is not a drop-in extraction: engine/account.rs calls CLI handlers, account data shares the lf database, routing resolves lf context, and activation interacts with sessions and Codex daemons. Separate the library and typed operations before choosing a process or repository split.

Packaging can separate maintenance and product association; it cannot change how a provider regards the behavior. A native account service keeps lf out of inference traffic. CLIProxyAPI adds protocol translation and configurable client cloaking, so replacing our native routing with it does not inherently address provider sensitivity. This is an architectural inference, not a claim about provider approval.

Decisions to resolve

  1. Is the desired outcome (a) reducing our maintenance, (b) independent account selection for concurrent sessions, or (c) making account management optional and separately distributed?
  2. For evaluation, must a prototype retain (a) native subscription login and resume, (b) our quota-before-reset ranking, and (c) saved browser profiles? Each needs an explicit parity check.
  3. Should the first architectural change be a library extraction while keeping today's behavior? This is the smallest way to make the later native-service versus API-proxy choice independent of lf's workflow.
