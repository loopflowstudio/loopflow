What Anthropic has published on graphs and loops, and what Loopflow should take from it

pstack skill review session · 2026-11-05 · gathered by a research agent from public sources; checked against rust/loopflow/src/builtins and .lf/graphs. Most pages came through a summarizing fetcher, so treat wording as paraphrase unless quoted.

Decision needed

Pick which of the candidates below to build here, and answer the three questions at the end. The strongest single move is putting the existing qa skill into pursue: verification is the most consistent theme in the sources, and qa is in no Graph today.

The themes

  • Verification is the lever. Shihipar reports verification skills had the largest measured impact. Carlini says the verifier must be nearly perfect. Getting started with loops: "Loops that write code need loops that check it."
  • Harnesses decay. Rajasekaran: "every component in a harness encodes an assumption". Martin asks what the harness can stop doing. This backs the compression Task.
  • Prompt edits regress silently. The April postmortem found one verbosity line cost 3%, and Anthropic now ablates prompt changes line by line.
  • Loops need stop conditions. Phillips: "Reactive loops are a behavioral problem". Outcomes defaults to 3 iterations with a maximum of 20.
  • Reviewers need proof. Clinton reports that requiring proof of a finding took substantive PR comments from 16% to 54%. Best practices warn a reviewer "will always find something".
  • Simple first. From Building effective agents to Shihipar and Bidasaria: most coding work needs no reviewer panel.

Candidates, ranked

1. Put qa into pursue

No new skill. Add two prompt edits: each finding needs a proof, and style is skipped. One reviewer, not a panel. Headless steps are separate processes, so it should already act as a fresh reviewer; the agent did not trace runner.rs to confirm that.

- graph: refresh
- loop: implement
- qa
- loop: implement
- concept-review

2. drive skill

Records how to run and drive this repository in .lf/skills/drive.md, so demo, verify, qa and gate share one recipe. It overlaps pstack's create-verification-skill. Sources: Shihipar, /run-skill-generator, Young's init.sh.

3. skill-eval skill

Builds tasks from real Session failures, then runs with and without a skill from a clean tree. Grades deterministically first, then with blind pairwise judging, and reports pass^k, tokens and time. It gives reflect and compression a way to catch regressions. Sources: skill-creator, Demystifying evals.

# tune-skill (subroutine)
- skill-eval
- graph: optimize

4. fix subroutine with a reproduce skill

Commits a failing test before any fix. We have incident but no ordinary bug Graph. Sources: Claxton, best practices.

# fix (subroutine)
- reproduce
- step: {name: implement, id: repair}
- loop: repair
- graph: refresh

5. goal subroutine

A Graph form of /goal: work until a stated condition holds. No new skill, though implement expects a design, so a bare goal may need a prompt change.

- step: {name: implement, id: work}
- loop: work

6. Widen reflect across Sessions

Read corrections across many Sessions and write Gotchas into skills. Dreams write a reviewable copy and never edit the input store, which differs from the direct edits Jack chose.

7. sweep skill

Fan out per item, verify each, and stop after two rounds with nothing new. It would use the harness's Workflow tool, which ties a builtin to one harness and hides sub-agents from the Process ledger. Weakest fit.

8. investigate

A ledger of proved, refuted and open claims, from math-proof/siege. Low priority, but "unverified is not refuted" belongs in research regardless.

Already covered: PR babysitting, routines, spec interviews, per-step model choice, initializer agents.
