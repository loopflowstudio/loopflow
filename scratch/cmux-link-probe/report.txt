# cmux custom-link probe — October 18, 2026

Jack Heart requested native investigation for LOO-426. Research skill used;
cmux studied through installed behavior only. No cmux source, tests, help,
skills or configuration inspected or copied.

## Result

**cmux's shell opener forwards an arbitrary registered custom scheme to macOS,
but these observations do not prove a rendered custom-link click preserves its
workspace context.** Direct commands in a cmux pane have exact workspace/surface
context. A persistent OS receiver's environment cannot identify the source of
each later URL: the probe received cmux URLs while still carrying Herdr's pane
identity from its launch.

Installed baseline: cmux **0.65.0 (108)**, macOS **26.0.1 (25A362)**.
`TERM_PROGRAM` inside its owned test shell was `ghostty`, with version
`1.3.2-HEAD-+324c027`; therefore checking that value alone misses cmux.

Representative received URL:

```text
lf426cmuxprobe://loopflow/task/LOO-426?probe=cmux-host-open-warm&encoded=a%2Fb#frag
```

The recorded Apple event's payload was the URL. Sender PID was available, but
`NSRunningApplication` returned no sender bundle or executable; short-lived
opener processes cannot be assumed to remain queryable. No pane/workspace
metadata appeared in the event description. This probe did not enumerate every
possible Apple-event attribute or test another OS API for recovering ancestry.

## Reproduction and evidence

Created one plain `zsh -f` workspace (no provider Session/Flow) via the installed
cmux CLI. Captured only explicit host-context environment keys. Registered an
owned Cocoa receiver for unique scheme `lf426cmuxprobe`, emitted an OSC 8 link,
and dispatched marked URLs from the shell through each opener.

Registration from `/tmp` claimed the scheme but `open` returned
`kLSApplicationNotFoundErr (-10814)`. Moving the owned app temporarily to
`~/Applications/LOO426 Link Probe.app` made generic scheme dispatch work. An
explicit `open -a` control also received events before that move. These setup
failures are retained in the investigation; they are not cmux failures.

The receiver was then rebuilt to record the bounded environment on **every**
URL event. Herdr's investigator cold-launched it from `w1:p2`, opened it from
`w1:p1`, and released the still-running receiver for cmux's two warm opens.
All subsequent receipts retained `w1:p2`. The earlier cold cmux startup had
correctly inherited its own workspace and surface IDs. That contrast separates
fresh launch inheritance from reliable per-click context.

Retained evidence:

- [events.jsonl](cmux-link-probe/events.jsonl): exact URL receipts, sender PID,
  startup and per-event allowlisted environments, including cross-host controls.
- [shell-context.txt](cmux-link-probe/shell-context.txt): owned cmux shell context
  and resolved `open` executable.
- [receiver.swift](cmux-link-probe/receiver.swift): independent probe receiver,
  so its observation limits can be reviewed.

## Implications and remaining proof

Use explicit current shell context for `lf open`; do not infer cmux solely from
`TERM_PROGRAM`. Keep public Work links free of host identity. OS registration can
receive the URL, but a long-running handler must not route by its inherited
CMUX/HERDR environment. Source evidence must accompany each activation or come
from a reliable host integration. Missing context should follow the documented
fallback, not reuse stale pane identity.

The remaining cmux test is a physical click on an actual rendered OSC 8 custom
link, with the receiver already running from another host. That will establish
whether the clicked path contributes any usable per-event origin information.
No native click success or context loss is inferred from the shell tests.
