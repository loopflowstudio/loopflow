# Orca: source-level competitor research

Observed 2026-11-07. Product: **Stably AI’s Orca**, [stablyai/orca](https://github.com/stablyai/orca), [onorca.dev](https://www.onorca.dev/), not the unrelated autonomous agents also called Orca. Source inspected from a shallow clone at **`e799cb419e89e1aa52f49feec0e273f8f613d737`**, retained in `/tmp/competitor-orca-research`. This is a code/doc investigation, not a hands-on device reliability test. All code links below pin that revision. Loopflow comparison uses the supplied checkout’s architecture plus LOO-593’s current `server/README.md`, `server/wire.rs` and documented terminal bridge behavior; LOO-593 is still local, not a shipped remote/mobile implementation.

## What matters most

Orca’s strongest distinction is a broad, cross-platform **workspace IDE around agent sessions**, with a real phone companion and remote runtime. Its particularly useful engineering is bounded, resumable terminal delivery and host-owned structured-chat history. Loopflow’s distinctive center remains durable work, graph execution, process/session identity, and delivery lifecycle. Both have real host/process ownership concepts; treating Orca as merely a terminal wrapper misses its current structured-session system.

The major correction to its marketing: **“chat or terminal, same conversation” is not one universal operation.** Terminal-backed chat can view the same PTY. A native structured chat has no PTY underneath; its current “Continue with Terminal Agent” action forks/copies the conversation. The current source explicitly says the earlier terminal handoff was removed. That distinction matters directly to any Loopflow chat/terminal design.

## 1. Architecture and codebase strengths

### Structure and difference from Loopflow

Orca’s desktop is Electron/React/TypeScript, mobile is React Native/Expo, and the host runs a Node runtime. Its main runtime offers shared RPC for workspace, terminal, agent, file, browser, source-control and orchestration operations. It can run in the desktop or as `orca serve`/`orcad`; the remote machine owns repositories, workspaces, tabs, provider credentials, processes and sessions while clients display/control them. Separate terminal-host machinery preserves PTYs independently of renderer lifetimes. [Manifest](https://github.com/stablyai/orca/blob/e799cb419e89e1aa52f49feec0e273f8f613d737/package.json), [mobile implementation guide](https://github.com/stablyai/orca/blob/e799cb419e89e1aa52f49feec0e273f8f613d737/mobile/README.md), [remote runtime docs](https://www.onorca.dev/docs/remote-servers).

Loopflow’s Rust kernel composes direct skills into Graphs and attaches execution evidence, ownership and delivery to Tasks; Swift presents those shared models. A Wave/Project/Task graph is a different center of gravity from Orca’s project/workspace/tab/pane/session model. Orca has orchestration, schedules and issue integrations, so this is a difference in architectural emphasis, not a claim that it lacks automation. Conversely, worktree isolation, multiple providers, native session IDs and remote execution are not unique to Orca.

Orca now has substantial durable session machinery. `AgentSessionRecord` separates execution location, provider/account, provider-handle history, conversation name and a process lease; lease fields include a monotonic fence, spawn token, owner identity, claim status and exit evidence. Structured chat uses SQLite `journal_rows(session_id, epoch, seq, ts, row_json)` plus session/record tables. This is closer to Loopflow’s separation of LfSession, AgentSession and AgentProcess than the landing page suggests. [Record model](https://github.com/stablyai/orca/blob/e799cb419e89e1aa52f49feec0e273f8f613d737/src/shared/agent-session/lifecycle/agent-session-record.ts), [journal schema](https://github.com/stablyai/orca/blob/e799cb419e89e1aa52f49feec0e273f8f613d737/src/main/native-chat/agent-session-journal/database/journal-database-schema.ts).

### Best concrete code choices

1. **One subprocess implementation across surfaces.** `@orca/process-host` has no runtime dependencies, Electron imports or native addons, and owns spawning, bounded output, cancellation, process-tree termination and Windows argument handling for desktop, server, CLI, SSH relay and daemon. This is a useful boundary: platform behavior can improve once without different host modes drifting. [Package contract](https://github.com/stablyai/orca/blob/e799cb419e89e1aa52f49feec0e273f8f613d737/src/packages/process-host/README.md).
2. **Terminal recovery cares about what the client actually rendered.** A stream ledger translates acknowledged UTF-16 display units back to host output sequence. A retained ring also records coverage epoch and terminal dimensions. Resume is allowed only when the retained output truly continues the client’s screen; otherwise it sends a fresh snapshot. This enables quick phone tab switches and reconnects without pretending that arbitrary byte offsets are interchangeable. [Ledger](https://github.com/stablyai/orca/blob/e799cb419e89e1aa52f49feec0e273f8f613d737/src/main/runtime/rpc/methods/terminal/terminal-stream-resume-ledger.ts), [ring](https://github.com/stablyai/orca/blob/e799cb419e89e1aa52f49feec0e273f8f613d737/src/main/runtime/terminal/output/terminal-published-output-ring.ts).
3. **Structured history has explicit reset semantics.** Cursors include epoch and sequence; epoch mismatch, cursor ahead of storage, compacted cursor and unreadable schema produce reset conditions rather than partial timelines. Subscribers receive snapshot, batch or reset; a large catch-up can jump to a bounded tail snapshot and leave older history pageable. This enables readable chat on phones without loading a full conversation on every reconnect. [Cursor logic](https://github.com/stablyai/orca/blob/e799cb419e89e1aa52f49feec0e273f8f613d737/src/main/native-chat/agent-session-journal/replay/journal-cursor.ts), [catch-up delivery](https://github.com/stablyai/orca/blob/e799cb419e89e1aa52f49feec0e273f8f613d737/src/main/native-chat/agent-session-wire/publication/subscribers/agent-session-subscriber-catch-up.ts).
4. **Readers do not start agents.** `agentSession.subscribe` explicitly treats subscription as reading, not keepalive or execution admission. A phone opening a conversation does not implicitly launch another writer. [Subscription method](https://github.com/stablyai/orca/blob/e799cb419e89e1aa52f49feec0e273f8f613d737/src/main/runtime/rpc/methods/structured-sessions/subscriptions/structured-agent-session-subscribe-method.ts).

These boundaries are useful examples, not a blanket cleanliness endorsement. The current tree is very large and contains substantial compatibility/legacy machinery. The source is more nuanced than several docs: even `mobile/README.md` says version floors currently never block, while actual protocol constants are runtime/mobile version 3 with minimum 2. Prefer code for exact behavior. [Actual protocol constants](https://github.com/stablyai/orca/blob/e799cb419e89e1aa52f49feec0e273f8f613d737/src/shared/protocol-version.ts).

## 2. Mobile ↔ desktop synchronization

### Ownership and transport

The phone is a remote client of a running host, not an offline replica of the repository or provider. Pairing establishes a phone credential and host key. The host owns agents, worktrees, conversation history and shared mutations; device-specific preferences such as terminal zoom remain local. The app can aggregate multiple hosts. Direct connections use WebSocket RPC (default 6768) over LAN/Tailscale; Relay allows outbound connections from both host and phone. The host must remain available, or a headless remote host must own the work. [Mobile docs](https://www.onorca.dev/docs/mobile), [mobile source guide](https://github.com/stablyai/orca/blob/e799cb419e89e1aa52f49feec0e273f8f613d737/mobile/README.md).

The relay is public source: a director assigns hosts to relay cells and cells splice frames between outbound sockets. It is transport, not the authority for the agent conversation. E2EE v2 binds client/desktop keys and nonces, direct-vs-relay context, selected framing and payload kinds into the transcript; HKDF-SHA256 derives direction-specific keys and a session ID. Encrypted frames authenticate session, direction, text/binary kind and an expected counter, rejecting wrong-order/replayed frames. This is application-level end-to-end encryption across the relay. [Relay overview](https://github.com/stablyai/orca/blob/e799cb419e89e1aa52f49feec0e273f8f613d737/cloud/README.md), [handshake contract](https://github.com/stablyai/orca/blob/e799cb419e89e1aa52f49feec0e273f8f613d737/src/shared/remote-runtime/e2ee/mobile-e2ee-v2-contract.ts), [key schedule](https://github.com/stablyai/orca/blob/e799cb419e89e1aa52f49feec0e273f8f613d737/src/shared/remote-runtime/e2ee/node/mobile-e2ee-v2-node-key-schedule.ts), [framing](https://github.com/stablyai/orca/blob/e799cb419e89e1aa52f49feec0e273f8f613d737/src/shared/remote-runtime/e2ee/mobile-e2ee-v2-framing.ts).

### Reconnect, ordering and backpressure

- **Terminal resume:** each stream gets a random token scoped to the paired device. It is retained for two minutes after stream end, at most eight retained streams per device, and consumed once even if resume fails. Tokens avoid late ACKs crediting a successor stream when a relay renumbers stream IDs. The output ring is bounded to 64 Ki UTF-16 code units; different coverage epoch, grid size, missing span or unsafe transformed-chunk split falls back to snapshot. [Tokens](https://github.com/stablyai/orca/blob/e799cb419e89e1aa52f49feec0e273f8f613d737/src/main/runtime/rpc/methods/terminal/terminal-stream-tokens.ts), [resume tests](https://github.com/stablyai/orca/blob/e799cb419e89e1aa52f49feec0e273f8f613d737/src/main/runtime/rpc/terminal-subscribe-resume.test.ts).
- **Slow phones:** output credit limits unparsed text to a 512 Ki-unit window. The held-output budget is currently 256 KiB; overflow recovers to a current-screen snapshot after the link drains rather than endlessly replaying obsolete output. Snapshot/sequence trimming avoids duplicating output, and special terminal query handling preserves required replies. On PTY exit, held final output is flushed because no later recovery is possible. [Credit implementation](https://github.com/stablyai/orca/blob/e799cb419e89e1aa52f49feec0e273f8f613d737/src/main/runtime/rpc/methods/terminal/terminal-output-credit.ts), [current limits](https://github.com/stablyai/orca/blob/e799cb419e89e1aa52f49feec0e273f8f613d737/src/shared/terminal/stream/terminal-multiplex-flow-control.ts), [behavior tests](https://github.com/stablyai/orca/blob/e799cb419e89e1aa52f49feec0e273f8f613d737/src/main/runtime/rpc/terminal-subscribe-output-credit.test.ts).
- **Chat:** durable cursor-based catch-up is separate from terminal replay. Phone frames receive explicit size bounds; oversized side lists are split and editable queue cards are kept whole rather than silently truncating text that might later be saved. [Bounded frame projection](https://github.com/stablyai/orca/blob/e799cb419e89e1aa52f49feec0e273f8f613d737/src/main/native-chat/agent-session-wire/publication/history/agent-session-bounded-frames.ts), [queue bounds](https://github.com/stablyai/orca/blob/e799cb419e89e1aa52f49feec0e273f8f613d737/src/main/native-chat/agent-session-wire/publication/subscribers/agent-session-bounded-queue.ts).
- **Input versus geometry:** passive remote desktop attachment records dimensions without taking control; explicit activity/claim changes who controls resize. Terminal-backed phone chat has a lease-only subscription for input acknowledgment, without duplicate output or a viewport that resizes the PTY. [Viewport handling](https://github.com/stablyai/orca/blob/e799cb419e89e1aa52f49feec0e273f8f613d737/src/main/runtime/rpc/methods/terminal/terminal-viewport-update.ts), [lease-only subscription](https://github.com/stablyai/orca/blob/e799cb419e89e1aa52f49feec0e273f8f613d737/src/main/runtime/rpc/methods/terminal/terminal-subscribe-json-and-lease.ts).

Mobile notifications use a separate APNs/FCM gateway; the host registers each paired device and requests pushes. The notification socket handles dismissal/reconciliation rather than generating OS banners. Android’s offline collapse behavior means not every pending alert is guaranteed. This is distinct from keeping the foreground RPC stream synchronized. [Push architecture](https://github.com/stablyai/orca/blob/e799cb419e89e1aa52f49feec0e273f8f613d737/cloud/README.md).

## 3. What users like, with evidence quality

The defensible pattern is **managing several projects and agents without losing their context**, with fast access to terminals and remote work. Evidence is individual accounts, not a representative satisfaction survey.

- **One place for parallel projects.** Takayuki’s firsthand account describes switching from Zed as editor-window switching became cumbersome with more projects, then monitoring and steering multiple projects in Orca. It highlights worktrees, per-worktree browser, Quick Commands and a floating terminal. This is stronger evidence for the multi-project experience than star counts. [Firsthand account, October 2026](https://note.com/gadgettakayuki/n/n49e9874d175c?hl=en).
- **Floating workspace and keyboard flow.** GitHub user `edwin-anderson` calls the floating workspace something they “otherwise love,” within a concrete focus bug report. The report shows why it is valuable and how easily the benefit breaks if typing goes into a hidden terminal. The issue was closed through a fix on November 1. [Issue #36351](https://github.com/stablyai/orca/issues/36351).
- **Multi-agent orchestration, with cost concerns.** `khaiminh0401` appreciates the orchestration concept but reports unexpectedly high coordinator token consumption with version 1.4.237. This is positive evidence for the concept, not evidence that overhead is solved. [Issue #35557](https://github.com/stablyai/orca/issues/35557).
- **Mobile use is real, but “universally loved” is unsupported.** A mobile bug participant describes trying to steer agents between gym sets. That is evidence of an actual mobile workflow, accompanied by broken link interactions, not a satisfaction rating. [Issue #19585](https://github.com/stablyai/orca/issues/19585).

Do not flatten the experience into universal preference for chat. JanPlessow reported sticking with the Codex CLI because Chat UI lacked their needed status-line/timestamp experience in September. An October report described terminal-backed chat ordering problems while finding structured chat more reliable, alongside orchestration limitations at that time. Those dated reports should not be presented as confirmed current defects. [CLI preference](https://github.com/stablyai/orca/issues/19926), [October workflow report](https://github.com/stablyai/orca/issues/24447).

Diff annotations sent back to agents, design-mode element selection, source control, splits, previews, account usage and mobile approvals are documented product strengths. The source sample does not establish which of these are most-loved across users. Keep that distinction explicit.

## 4. Terminal versus chat: exact current answer

| Path | Same live process? | Same provider conversation? | Mechanism |
|---|---|---|---|
| Terminal-backed chat ↔ raw TUI | Yes, where the view toggle is available | Yes | Alternative transcript/composer presentation over the PTY. |
| Existing CLI → structured chat | No: stop/exit or writer-readiness check, then native runtime | Can resume the original provider ID | Native launch uses `resumeFrom.providerSessionId`; an active source must no longer compete as writer. |
| Structured chat → terminal | No | **No: fork/copy** | Claude `--fork-session`; Codex `fork`; other providers use their fork/copy path. |
| Desktop structured chat ↔ phone structured chat | Same host-owned agent | Yes | Two clients subscribe/control the same host session. |

The tab code explicitly says only terminal-backed tabs can toggle view because structured chats have no terminal underneath. Its current menu also preserves returning to terminal while switching terminals into terminal-backed chat can be disabled. Therefore, avoid promising a universally available bidirectional toggle even for all PTY-backed agents. [Tab menu](https://github.com/stablyai/orca/blob/e799cb419e89e1aa52f49feec0e273f8f613d737/src/renderer/src/components/tab-bar/SortableTabContextMenu.tsx).

For CLI→structured chat, the launch passes the original provider session ID. If closing is required, it installs exit waits, closes the source terminal and waits for proven exit before releasing native creation; an uncertain close does not silently start another writer. [Resume flow](https://github.com/stablyai/orca/blob/e799cb419e89e1aa52f49feec0e273f8f613d737/src/renderer/src/components/tab-bar/cli-chat-resume-run.ts), [exit verification](https://github.com/stablyai/orca/blob/e799cb419e89e1aa52f49feec0e273f8f613d737/src/renderer/src/components/tab-bar/cli-chat-resume-close-terminal.ts).

For structured→CLI, both the header button and history action use fork preparation. `getAgentForkArgv` explicitly documents that a new conversation ID prevents chat and terminal writing the same one: Claude `claude --resume ID --fork-session`, Codex `codex fork ID`, Grok `--fork-session`, Pi `--fork PATH`. OpenCode/OpenCode2/OMP use a chat-protocol copy and resume that copy. The original chat survives. You can have both, but their subsequent history diverges. [Button](https://github.com/stablyai/orca/blob/e799cb419e89e1aa52f49feec0e273f8f613d737/src/renderer/src/components/native-chat/pane/actions/NativeChatResumeInCliButton.tsx), [fork runner](https://github.com/stablyai/orca/blob/e799cb419e89e1aa52f49feec0e273f8f613d737/src/renderer/src/components/tab-bar/native-chat-cli-fork-run.ts), [provider fork argv](https://github.com/stablyai/orca/blob/e799cb419e89e1aa52f49feec0e273f8f613d737/src/shared/agent-launch/startup/agent-resume-argv.ts), [host preparation](https://github.com/stablyai/orca/blob/e799cb419e89e1aa52f49feec0e273f8f613d737/src/main/ai-vault/structured-chat-cli-fork.ts).

The model itself documents that terminal handoff was removed and the old `tui` owner kind is mapped away on decode; native structured sessions now have only `runtimeKind: 'native'`. The public native-chat docs still say live switching in one paragraph and describe CLI forks in another. **The source is the stronger evidence for current main; released binaries may lag main.** [Owner-kind definition](https://github.com/stablyai/orca/blob/e799cb419e89e1aa52f49feec0e273f8f613d737/src/shared/agent-session/lifecycle/agent-session-record.ts), [conflicting/broader documentation](https://www.onorca.dev/docs/agents/native-chat).

## Concrete lessons for LOO-593

LOO-593 already separates full-reading subscriptions from one-use terminal bridge tickets, keeps terminal bytes off the control connection, reconnects to the exact owner, and leaves input/geometry ownership with the terminal owner. Orca is evidence for preserving those boundaries, not for replacing them with its much larger system.

### Applicable now

1. **Make same-session continuity a tested semantic claim.** A terminal view, a provider resume and a provider fork are different operations. Keep those names/distinctions in any future chat RPC and UI. Orca’s docs/source mismatch illustrates the user-visible failure of collapsing them. A new view should subscribe to the existing owner; resuming a different native transport must not imply that it is the same live process. This is particularly relevant to 593’s current owner-specific attach.
2. **Test snapshot/live boundaries with terminal dimensions and incarnation changes.** Orca rejects resume after resize, coverage reset or reused token. 593 already has Resume/fresh-screen recovery; add these cases to its acceptance matrix if not already covered rather than copying another replay layer. Include output arriving during snapshot generation and late ACK from a previous attachment. [Behavior cases](https://github.com/stablyai/orca/blob/e799cb419e89e1aa52f49feec0e273f8f613d737/src/main/runtime/rpc/terminal-subscribe-resume.test.ts).
3. **Keep passive attach passive and separate chat input presence from terminal geometry.** 593’s free claims should preserve newer viewers’ ownership. A future transcript-only subscriber should not resize a PTY to phone dimensions or answer terminal queries as a second emulator. Orca has explicit lease-only subscription and passive viewport observation; these are useful concrete scenarios for 593 tests.
4. **Bound memory per slow client and make recovery explicit.** Orca’s 512 Ki-unit credit window, bounded pending queue and snapshot replacement are concrete examples. The requirement is not these exact constants; it is that stalled clients cannot make memory grow forever, output flooding cannot delay control, and the final terminal tail is not silently lost on exit. 593’s separate terminal connections already address control head-of-line blocking.

### Future remote/mobile work, not scope to add to 593

5. **Add incremental history only when it has a real durable cursor.** Current full-reading reconnect in 593 is a valid simple contract. If chat history size later justifies deltas, use epoch+sequence with explicit reset/snapshot fallback and history pagination; do not repurpose request IDs, server incarnation or a generic store revision as replay authority.
6. **Mobile needs protocol ranges plus feature negotiation.** Orca tolerates app-version drift with protocol min/max and capability flags because App Store updates lag host releases. 593 already exposes a revision range and schema. Preserve that foundation; defer per-feature capability complexity until deployed client skew requires it.
7. **Remote pairing is separate from transport and process ownership.** Orca’s direct/relay E2EE contract binds endpoint identity and direction/counters, while the host still owns execution. Keep future relay routing from becoming session authority. APNs/FCM delivery is a separate product channel from foreground WebSocket sync.

## Limits and remaining questions

No builds, tests, pairing or live UI actions were run; cited tests were inspected. Source establishes intended implemented behavior and failure handling, not real-world latency or reliability. Current main and current docs visibly disagree on session switching and some protocol-version details. Before a product-level comparison claims exact released behavior, verify the chosen Orca desktop/mobile release pair. Independent user sentiment is a small, biased public sample; do not infer “people love” from GitHub stars, promotional posts or feature lists.
