# Protocol lessons for LOO-593

Research date: 2026-11-07. This is source inspection, not a load test or an implementation request. Baseline: LOO-593 checkout at `5ea4f4e16794417b006e6380c5f6f997a366d08d` plus its live working changes, including revision-2 `server/{README,wire,service}.rs`, `lf/commands/subscribe.rs`, `transport/{wire,stream,connection}.rs`, and Swift `ServerClient.swift`. Its current protocol is local-only; remote admission remains a separate concern.

## 1. Bound retained work, not only the outbound queue

The most immediate finding is in `server/service.rs`. `session()` admits an unbounded number of distinct request/subscription IDs into its `JoinSet` and `inflight` map. The outgoing channel holds 64 messages, but each completed `request()` can retain its entire result while awaiting `outgoing.send()`, outside those 64 slots. Messages remain `serde_json::Value` until `send()` serializes them; the 32 MiB message limit is checked there. The five-second socket timeout and 64-connection limit are useful, but they do not bound all response memory or admitted computation. This is a code-derived resource-bound gap; no memory exhaustion was reproduced.

[T3's LiveStreamBudget](https://github.com/pingdotgg/t3code/blob/71c2d3a302092b94511eb7e6ab4e6844a66dbf22/apps/server/src/orchestration-v2/LiveStreamBudget.ts) counts retained items **and serialized bytes**, including items delivered but not acknowledged. Its reference limits are 1,000 items and 8 MiB. The transferable idea is end-to-end accounting across queue boundaries, not those constants or the Effect implementation.

For 593, consider per-connection admitted-request/subscription limits plus a retained-byte budget that includes pending producers. Reserve admission before dispatch; never describe an already-dispatched write as safely unexecuted merely because delivery overflowed. Preserve `outcome_unknown` for lost mutation outcomes. Bound at the retained-result boundary, not after constructing an arbitrarily large queue of values. Any aggregate process budget must also account for the number of connections.

The existing pulled subscription already reads the newest changed state; `Notify` coalesces wakes. If further outbound coalescing is useful, replace only complete state readings for the same subscription. Preserve checkpoint answers, unavailable/error frames, and the final reading-before-`ended` ordering. A checkpoint here requests a fresh reading; it is **not** an acknowledgment of applied events.

## 2. Keep the three recovery contracts separate

593 has complete Work readings and a separate terminal continuation protocol. That is a good fit for its current scope. Do not add a universal event log because competitors have one.

- **Work inventory:** reopening a subscription gives a complete current reading. Existing `select` reduces payload and suppresses irrelevant updates. If mobile measurement later justifies deltas, [Paseo's VersionedCollection](https://github.com/getpaseo/paseo/blob/71439e51a555bfca21dc21e74bcfb39f1eb5e760/packages/server/src/server/directory-sync/internal/versioned-collection.ts) is a smaller model than event sourcing: latest value per entity, monotonic sequence, bounded deletion tombstones, and explicit snapshot fallback when a cursor expires. [Its directory service](https://github.com/getpaseo/paseo/blob/71439e51a555bfca21dc21e74bcfb39f1eb5e760/packages/server/src/server/directory-sync/index.ts) separates daemon generation from entity sequence.
- **Structured conversation:** if introduced, durable history, transient token deltas and pending approval state need explicit reconciliation. [Paradev's journal](https://github.com/ParadevAI/Paradev/blob/61645f4852d3f7ecca7f58a6f6d68d7bc9dc460c/packages/chat-runtime/src/journal/journal/journal.ts) and [replay](https://github.com/ParadevAI/Paradev/blob/61645f4852d3f7ecca7f58a6f6d68d7bc9dc460c/packages/chat-runtime/src/replay/replay.ts) distinguish durable epoch/sequence from ephemeral streaming. A stored cursor must correspond to the state actually applied, not merely bytes received.
- **Terminal:** retain exact-owner continuation and fresh-screen recovery; never replay uncertain input. Terminal display recovery is not permission to start or resume a provider.

For future delta subscriptions, T3's [LiveStreamBudget](https://github.com/pingdotgg/t3code/blob/71c2d3a302092b94511eb7e6ab4e6844a66dbf22/apps/server/src/orchestration-v2/LiveStreamBudget.ts#L365) subscribes before obtaining the replay boundary and discards overlap; [ThreadStream](https://github.com/pingdotgg/t3code/blob/71c2d3a302092b94511eb7e6ab4e6844a66dbf22/apps/server/src/orchestration-v2/ThreadStream.ts) bounds replay by count and bytes; the [wire handler](https://github.com/pingdotgg/t3code/blob/71c2d3a302092b94511eb7e6ab4e6844a66dbf22/apps/server/src/ws.ts#L1010) resnapshots when history is unavailable or pruned. [Paseo's DirectoryTransactionOwner](https://github.com/getpaseo/paseo/blob/71439e51a555bfca21dc21e74bcfb39f1eb5e760/packages/app/src/runtime/directory-sync/transaction.ts) rejects stale bootstrap completion by client generation and connection epoch. These are future delta-protocol invariants, not missing requirements for today's fresh full readings.

## 3. Preserve owner authority when adding mobile transport

593 already separates a control connection from each terminal bridge, resolves a Session to an existing owner, offers an exact-owner condition, and leaves input/geometry authority with that owner. Its viewer recovery uses a bounded spool and a fresh-screen fallback. Preserve these distinctions: a slow terminal must not block Work control, a connection loss must not prove process death, and a reconnect must not steal newer claims.

Competitor geometry choices differ. Paradev uses the smallest **visible** viewer and treats resize as a byte-replay boundary; background viewers do not shrink the PTY. [Terminal implementation](https://github.com/ParadevAI/Paradev/blob/61645f4852d3f7ecca7f58a6f6d68d7bc9dc460c/packages/host-service/src/terminal/terminal.ts). Paseo has explicit `claim` versus `update` for geometry; only the current claimant's updates resize it. [Size ownership](https://github.com/getpaseo/paseo/blob/71439e51a555bfca21dc21e74bcfb39f1eb5e760/packages/server/src/terminal/terminal-size-ownership.ts). These are alternatives; Loopflow need not replace its explicit owner with smallest-screen arbitration.

Useful acceptance cases: phone sleeps while Desktop resizes/types; phone returns after replay retention expires; old owner ends and Session gets a new owner; one viewer stops draining while another remains healthy; an old socket completes after a replacement connected. Verify existing coverage before adding tests. Assert both visible recovery and absence of unintended input/geometry transfer.

## 4. Lost writes need receipts or reconciliation, not automatic retries

593's cancellation/disconnect semantics are deliberately honest: admitted mutations finish; losing an answer gives an unknown outcome. Keep this until a particular operation has a durable retry contract.

Paradev's [CommandDedupe](https://github.com/ParadevAI/Paradev/blob/61645f4852d3f7ecca7f58a6f6d68d7bc9dc460c/packages/chat-runtime/src/commands/commandDedupe/commandDedupe.ts) stores 500 results in memory, so it cannot establish deduplication across restart. Its mobile [retry link](https://github.com/ParadevAI/Paradev/blob/61645f4852d3f7ecca7f58a6f6d68d7bc9dc460c/apps/mobile/lib/errors/transport-retry.ts) explicitly retries queries only because replaying workspace creation can produce another workspace.

Paseo's [CreationService](https://github.com/getpaseo/paseo/blob/71439e51a555bfca21dc21e74bcfb39f1eb5e760/packages/server/src/server/creation/index.ts) offers a more relevant reference for a future reconnect-safe Task/Session creation operation: persist request identity and fingerprint before provisioning, reuse resource IDs, expose milestones, reject reuse with different content, and preserve an unknown outcome after interrupted external effects. Even this does not manufacture exactly-once execution across arbitrary provider side effects. This should be operation-specific; it is not a reason to introduce a second generic execution owner into Loopflow.

## 5. Name fork, native resume and live attachment separately

The competitors expose a concrete terminology trap. Paradev docs claim a same-session CLI/chat toggle, but current [SurfaceModeMenu](https://github.com/ParadevAI/Paradev/blob/61645f4852d3f7ecca7f58a6f6d68d7bc9dc460c/apps/desktop/src/renderer/routes/_authenticated/_dashboard/v2-workspace/%24workspaceId/hooks/usePaneRegistry/components/SurfaceModeMenu/SurfaceModeMenu.tsx) and [useSurfaceFork](https://github.com/ParadevAI/Paradev/blob/61645f4852d3f7ecca7f58a6f6d68d7bc9dc460c/apps/desktop/src/renderer/routes/_authenticated/_dashboard/v2-workspace/%24workspaceId/hooks/usePaneRegistry/hooks/useSurfaceFork/useSurfaceFork.ts) create a fork beside the still-running original. Orca's structured-chat-to-CLI argv likewise uses provider fork operations, while its terminal-backed chat view is a different presentation of one PTY. [Orca launch arguments](https://github.com/stablyai/orca/blob/e799cb419e89e1aa52f49feec0e273f8f613d737/src/shared/agent-launch/startup/agent-resume-argv.ts).

Keep Loopflow's existing LfSession, provider AgentSession, AgentProcess and viewer authority distinct. If a structured chat surface is added, its operation/result should explicitly establish whether the provider conversation was retained, resumed in a replacement process, or branched. A chat view that can read a transcript does not thereby gain permission to drive it.

## 6. Remote admission is its own boundary

Do not expose revision 2's same-user Unix socket through a generic relay. It includes local account/configuration authority. A future remote boundary needs deliberate identity, authorization and pairing semantics, while dispatching allowed work through the same engine.

Paseo's [secure channel](https://github.com/getpaseo/paseo/blob/71439e51a555bfca21dc21e74bcfb39f1eb5e760/packages/relay/src/secure-channel.ts) illustrates the distinction between an encrypted tunnel and replay-resistant endpoint authentication: protected Noise handshakes, authenticated records, and a minimum security mode pinned to daemon identity. It also retains a legacy mode without replay protection when permitted; the useful lesson is the invariant and explicit failure behavior, not copying its compatibility layer or cryptography implementation. [Security construction and limits](https://github.com/getpaseo/paseo/blob/71439e51a555bfca21dc21e74bcfb39f1eb5e760/docs/relay-endpoint-security.md).

The immediate candidate for 593 is retained-work budgeting. The remaining findings support existing boundaries or inform later mobile/structured-chat work; they do not require broadening this Task into a new remote architecture.
