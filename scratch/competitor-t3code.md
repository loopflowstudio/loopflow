## 1. Architecture versus Loopflow; strongest implementation choices

T3 is a server-owned agent workspace with multiple interchangeable client surfaces: React web, Electron desktop, and Expo/React Native iOS/Android. A server environment owns projects, threads, providers, files, Git, PTYs and durable state. Even the local desktop renderer uses authenticated RPC to that environment. Shared `packages/client-runtime` owns connections, reconnect policy, subscriptions, caches and domain state; platform apps supply storage, credential and lifecycle services plus rendering. This makes mobile a full client of the same execution system, not a separate companion database. [Architecture](https://github.com/pingdotgg/t3code/blob/71c2d3a302092b94511eb7e6ab4e6844a66dbf22/docs/internals/overview.md), [mobile dependencies](https://github.com/pingdotgg/t3code/blob/71c2d3a302092b94511eb7e6ab4e6844a66dbf22/apps/mobile/package.json).

Loopflow's current architecture grows from direct Skills, reusable Graphs, durable Sessions, actual Processes, Task worktrees/PR delivery and Wave/Project planning. Its Rust domain core and Swift Mac presentation are different from T3's TypeScript/Effect application server and shared TypeScript client runtime. The LOO-593 branch narrows the surface difference by making Desktop a client of the same Rust server; that is already moving toward the same ownership boundary. Its revision-2 transport is explicitly local, with existing terminal owners behind tickets, whereas T3 is already a remote, mobile, independently versioned client/server product. This comparison is against the inspected Loopflow checkout and 593 branch, not an assertion about a future Loopflow release. [Loopflow model](/Users/jack/src/loopflow.agent/docs/architecture/reference-models.md), [593 protocol](/Users/jack/src/loopflow.loo-593-decide-the-desktop/rust/loopflow/src/server/README.md).

Their central abstractions differ. T3's app Thread persists across provider selection; Runs, ExecutionNodes, ProviderThreads and ProviderSessions describe normalized agent activity. Native provider conversation handles remain separate from app history. It supports its own dynamic subagent orchestration and MCP access, so describing it as merely a GUI wrapper understates current functionality. Loopflow's Task/Graph delivery and planning model is a different layer of product intent; T3's execution graph is not equivalent to a reusable Loopflow Skill Graph. [T3 model](https://github.com/pingdotgg/t3code/blob/71c2d3a302092b94511eb7e6ab4e6844a66dbf22/docs/orchestration-v2/core-graph-and-data-model.md), [MCP orchestration](https://github.com/pingdotgg/t3code/blob/71c2d3a302092b94511eb7e6ab4e6844a66dbf22/docs/orchestration-v2/orchestrator-mcp-server.md).

The most useful codebase aspects are concrete boundaries rather than the framework choice:

- **Shared connection and synchronization implementation.** Mobile and desktop do not independently invent reconnect or data freshness. There is one environment-scoped connection owner, one retry supervisor, and platform lifecycle signals. That directly enables phone/desktop continuity and multiple host environments without divergent recovery behavior. [Connection runtime](https://github.com/pingdotgg/t3code/blob/71c2d3a302092b94511eb7e6ab4e6844a66dbf22/docs/internals/connection-runtime.md), [supervisor implementation](https://github.com/pingdotgg/t3code/blob/71c2d3a302092b94511eb7e6ab4e6844a66dbf22/packages/client-runtime/src/connection/supervisor.ts).
- **Atomic durable intent plus explicit side effects.** `EventSink.commitCommand` reserves a command receipt, appends events, applies projections, enqueues side effects and saves the resulting receipt in one transaction. Commit/publication ordering is serialized; publication occurs after commit even if the writer is canceled. The effect worker then performs provider/filesystem work. A successful acknowledgment therefore means committed intent, not completed execution. Duplicate command IDs deduplicate. This is a stronger network retry story than a request ID used only for response correlation. [EventSink, lines 285 onward and 665 onward](https://github.com/pingdotgg/t3code/blob/71c2d3a302092b94511eb7e6ab4e6844a66dbf22/apps/server/src/orchestration-v2/EventSink.ts#L285), [EffectWorker](https://github.com/pingdotgg/t3code/blob/71c2d3a302092b94511eb7e6ab4e6844a66dbf22/apps/server/src/orchestration-v2/EffectWorker.ts).
- **An app conversation can survive provider changes.** `ProviderSessionTransitionPolicy` distinguishes reuse, in-session model switch, restart-and-resume, and new provider conversation with handoff. `ContextHandoffService` selects actual historical messages within a budget and records coverage/omissions; the current implementation does not ask a model to summarize every switch. Native context is resumed when compatible, while portable context fills in off-provider history. This enables one visible discussion to use multiple providers without pretending their hidden native states are identical. [Transition policy](https://github.com/pingdotgg/t3code/blob/71c2d3a302092b94511eb7e6ab4e6844a66dbf22/apps/server/src/orchestration-v2/ProviderSessionTransitionPolicy.ts), [handoff implementation](https://github.com/pingdotgg/t3code/blob/71c2d3a302092b94511eb7e6ab4e6844a66dbf22/apps/server/src/orchestration-v2/ContextHandoffService.ts#L500), [current user contract](https://github.com/pingdotgg/t3code/blob/71c2d3a302092b94511eb7e6ab4e6844a66dbf22/docs/user/portable-handoffs.md).
- **Transport cost is designed into the model.** A lightweight shell/sidebar stream is separate from subscribed thread detail, older history is paged, full-entity streaming updates are coalesced, and replay has both event-count and byte limits. A client viewing one thread need not download every thread's transcript. This materially enables mobile and high-latency remote use. [ThreadStream](https://github.com/pingdotgg/t3code/blob/71c2d3a302092b94511eb7e6ab4e6844a66dbf22/apps/server/src/orchestration-v2/ThreadStream.ts), [wire subscriber](https://github.com/pingdotgg/t3code/blob/71c2d3a302092b94511eb7e6ab4e6844a66dbf22/apps/server/src/ws.ts#L882).

Important nuance: this is not an indefinitely replayable event-sourced database. Maintenance prunes old event history, while persisted projections remain authoritative; projections cannot be rebuilt from the retained log alone. Command receipts remain for idempotency. Also, some older orchestration design prose still says “summary”; current handoff code and user docs establish the actual message-selection behavior. [Pruning contract](https://github.com/pingdotgg/t3code/blob/71c2d3a302092b94511eb7e6ab4e6844a66dbf22/docs/internals/overview.md#durable-intent-and-side-effects).

## 2. Mobile ↔ desktop sync, precisely

**They connect to one authoritative environment; they do not synchronize two running agents or two workspace copies.** The phone controls agents and terminals running on the host. Host must stay awake/running/reachable. Server credentials, files and provider processes stay there. Clients may cache projections for offline reading, but reconnect loads/replays authoritative server state. Preferences and connection catalogs can remain client-local; “All environments” settings is an explicit bulk edit, not a magic offline global setting. [Remote architecture](https://github.com/pingdotgg/t3code/blob/71c2d3a302092b94511eb7e6ab4e6844a66dbf22/docs/internals/remote.md), [settings ownership](https://github.com/pingdotgg/t3code/blob/71c2d3a302092b94511eb7e6ab4e6844a66dbf22/docs/internals/overview.md#settings-ownership).

Connectivity options share that execution model:

- T3 Connect links a cloud account to the environment and provisions a Cloudflare tunnel. Clerk handles cloud identity. A trusted relay brokers one-time DPoP-bound bootstrap credentials; the client exchanges these with the environment for its own session. Application HTTP/WebSocket traffic then uses the tunnel hostname; the relay Worker is not the general application traffic proxy. Do not label this end-to-end encrypted on that evidence: it is a Cloudflare tunnel architecture, and the relay has explicit signing authority.
- LAN/private network pairing, Tailscale HTTPS and desktop-managed SSH are alternative routes. A stable environment ID is distinct from the endpoint. A saved environment can hold ordered routes; clients discover LAN/tailnet routes, try reachable ones, and move back to a preferred route when it becomes usable. A public descriptor check avoids sending credentials to an old LAN address now occupied by another machine.
- Desktop-managed SSH can start a host server and forward a port. Cleanup stops a server only when that launcher owns it. Hosted `app.t3.codes` is a client; serving the UI over HTTPS does not make an inaccessible/plain-HTTP backend reachable.

[Connect trust boundary](https://github.com/pingdotgg/t3code/blob/71c2d3a302092b94511eb7e6ab4e6844a66dbf22/docs/internals/t3-connect.md), [route implementation and ownership](https://github.com/pingdotgg/t3code/blob/71c2d3a302092b94511eb7e6ab4e6844a66dbf22/docs/internals/remote.md), [setup](https://github.com/pingdotgg/t3code/blob/71c2d3a302092b94511eb7e6ab4e6844a66dbf22/docs/user/remote-access.md).

The synchronization mechanics are unusually worth studying:

1. Snapshots have a committed `snapshotSequence`; subsequent events have monotonic server sequences. Reconnect sends the last applied cursor. Up to 128 events and 1 MiB raw/encoded replay can be used; larger gaps return a current bounded snapshot. A cursor behind pruned history also requires a snapshot. The server checks the prune frontier again after reading replay because pruning can race the read. [ThreadStream](https://github.com/pingdotgg/t3code/blob/71c2d3a302092b94511eb7e6ab4e6844a66dbf22/apps/server/src/orchestration-v2/ThreadStream.ts), [replay path](https://github.com/pingdotgg/t3code/blob/71c2d3a302092b94511eb7e6ab4e6844a66dbf22/apps/server/src/ws.ts#L1010).
2. A subscription starts draining live publication before reading the high-water/replay range, then removes overlapping sequences. It cannot leave an unbounded subscriber parked while replay is slow. Live budget accounts for both queued and delivered-but-unacknowledged objects. [LiveStreamBudget](https://github.com/pingdotgg/t3code/blob/71c2d3a302092b94511eb7e6ab4e6844a66dbf22/apps/server/src/orchestration-v2/LiveStreamBudget.ts#L365).
3. A `synchronized` marker says catch-up finished. Socket readiness and thread freshness are different states. The client retains state plus cursor only after the update applies, and an old canceled subscription scope cannot overwrite its successor's cache. [Client thread state](https://github.com/pingdotgg/t3code/blob/71c2d3a302092b94511eb7e6ab4e6844a66dbf22/packages/client-runtime/src/state/threads.ts#L250).
4. The supervisor probes on foreground/network change because a suspended mobile socket may die without a close event. It uses route-sensitive deadlines and separate fresh-HTTP evidence before replacing a suspect socket. Transport retries use jittered exponential backoff; authentication failures wait for a relevant wakeup. HTTP token renewal does not needlessly replace a healthy WebSocket. [Supervisor contract](https://github.com/pingdotgg/t3code/blob/71c2d3a302092b94511eb7e6ab4e6844a66dbf22/docs/internals/connection-runtime.md).

These are server/client continuity mechanisms. They do not establish cross-machine workspace replication or seamless migration of the running provider process to another host.

## 4. Terminal versus chat; what “same session” actually means

**Both chat and terminal are available. On desktop/web the terminal drawer is part of the chat workspace; mobile has a native terminal surface. But the terminal is a separate shell PTY, not a second rendering of the structured agent chat.** Running `claude`/`codex` yourself in that shell does not automatically make its transcript the T3 app thread. The chat providers use protocol adapters—Claude Agent SDK queries and Codex app-server requests—not the shell drawer as their chat transport. [Chat terminal composition](https://github.com/pingdotgg/t3code/blob/71c2d3a302092b94511eb7e6ab4e6844a66dbf22/apps/web/src/components/ChatView.tsx#L3976), [Claude adapter](https://github.com/pingdotgg/t3code/blob/71c2d3a302092b94511eb7e6ab4e6844a66dbf22/apps/server/src/orchestration-v2/Adapters/ClaudeAdapterV2.ts), [Codex adapter](https://github.com/pingdotgg/t3code/blob/71c2d3a302092b94511eb7e6ab4e6844a66dbf22/apps/server/src/orchestration-v2/Adapters/CodexAdapterV2.ts).

| Meaning of switching | Finding |
|---|---|
| Chat ↔ integrated shell in a thread workspace | Yes. Both surfaces exist; they share host/workspace association, not agent conversation transport. |
| Desktop chat ↔ phone chat | Yes: clients operate the same server-owned T3 Thread. |
| Desktop terminal ↔ phone terminal | Yes: attach to the same host PTY. Server-owned history plus snapshot/live streams restore the view. |
| Native CLI conversation → T3 chat | Best-effort import through the welcome/import flow, with native session references for continuation. It is not a continuous mirror. |
| Freely toggle native agent TUI ↔ structured chat on the same live provider process | No first-class path found in current source/docs. Do not claim support from the presence of an integrated terminal. |

Current import discovers Claude/Codex/Pi conversations active in the last 30 days and keeps the first prompt plus newest visible user/assistant messages, up to 200 total; tool activity and attachments are omitted. Current source calls `agentSessionsImport` from `WelcomeWizard`; `AgentSessionImporter` records strong native references and avoids importing an already owned native thread. ACP providers that advertise session listing/import have a separate native-session UI. That is materially different from a universal bidirectional live CLI/chat handoff. [Welcome import limitations](https://github.com/pingdotgg/t3code/blob/71c2d3a302092b94511eb7e6ab4e6844a66dbf22/docs/user/welcome-wizard.md#L76), [importer](https://github.com/pingdotgg/t3code/blob/71c2d3a302092b94511eb7e6ab4e6844a66dbf22/apps/server/src/project/AgentSessionImporter.ts#L180), [ACP imports](https://github.com/pingdotgg/t3code/blob/71c2d3a302092b94511eb7e6ab4e6844a66dbf22/docs/user/providers-acp.md#L94).

Users explicitly requested native CLI/T3 interoperability in [discussion 6994](https://github.com/pingdotgg/t3code/discussions/6994) and per-session continuation in [issue 15234](https://github.com/pingdotgg/t3code/issues/15234). The October issue establishes the prior gap and identifies Claude import continuation trouble then; it is not sufficient evidence that the old bug remains today. Current code now has more resume-state checks, so this report does not repeat that historical defect as a current verified failure. An [external t3-codex-bridge project](https://github.com/sadhiappan/t3-codex-bridge) pursues CLI/phone continuity, but that is not evidence of upstream T3 support.

Terminal implementation details matter for device switching. Each attached viewer reports geometry; the server uses the minimum columns and rows across attached viewers, so a phone can shrink the grid also rendered on desktop. Snapshot/live publication suppresses events already represented in the snapshot. Retained server history is bounded by lines and bytes; clients use incremental output and separate bounded buffers. Native iOS uses GhosttyKit, Android uses libghostty-vt, and current web also uses libghostty-vt via WASM; older xterm-only descriptions would be stale. [PTY ownership and geometry](https://github.com/pingdotgg/t3code/blob/71c2d3a302092b94511eb7e6ab4e6844a66dbf22/apps/server/src/terminal/Manager.ts#L1700), [terminal runtime](https://github.com/pingdotgg/t3code/blob/71c2d3a302092b94511eb7e6ab4e6844a66dbf22/docs/internals/terminal-runtime.md), [mobile native module](https://github.com/pingdotgg/t3code/blob/71c2d3a302092b94511eb7e6ab4e6844a66dbf22/apps/mobile/modules/t3-terminal/README.md).

## Concrete lessons for LOO-593

Read the actual branch at `/Users/jack/src/loopflow.loo-593-decide-the-desktop`, particularly `server/README.md`, `wire.rs`, and `service.rs`. Revision 2 deliberately serves complete readings over a local same-user socket; remote admission, event replay, and creating new PTYs are outside its contract. T3's mechanisms should be separated into immediately relevant resource/lifetime improvements and future remote-protocol work.

### Applicable to 593 now

1. **A count-bounded queue does not bound retained memory or work.** `service.rs:442` creates a 64-message channel, but every independently spawned request can finish and wait in `outgoing.send(message)` with another full result outside that channel (`request`, lines 696–711). `inflight`/`JoinSet` admission is uncapped (`session`, lines 538–546). The 32 MiB wire limit is checked only when serializing/sending (`send`, lines 886–891). This is a concrete resource-bound gap, not a claim that ordinary use currently OOMs. Bound admitted work and retained bytes, including replies waiting to enqueue and the frame currently being sent. T3's `LiveStreamBudget` explicitly charges queued plus delivered-but-unacknowledged items (1000 items / 8 MiB), releases on acknowledgment, and fails slow streams with an explicit resume instruction. [Implementation](https://github.com/pingdotgg/t3code/blob/71c2d3a302092b94511eb7e6ab4e6844a66dbf22/apps/server/src/orchestration-v2/LiveStreamBudget.ts).
2. **Latest-state coalescing can fit complete readings, but checkpoint barriers must survive.** T3 only coalesces whole-entity replacements, keeps survivors in original sequence order, and flushes at lifecycle/synchronization boundaries. Loopflow can consider latest-per-subscription readings for slow clients without adopting deltas, but must preserve `answers` checkpoints, unavailable readings and `ended`; silently replacing those would violate the existing protocol. [Coalescer](https://github.com/pingdotgg/t3code/blob/71c2d3a302092b94511eb7e6ab4e6844a66dbf22/apps/server/src/orchestration-v2/ThreadLiveEventCoalescer.ts#L17).
3. **Keep reconnect separate from creation and mutation replay.** Loopflow's exact owner ticket and refusal to recreate a provider are stronger guarantees than T3 terminal attach. T3 avoids recreating known-closed IDs within a server lifetime, but its close markers are in memory and unknown IDs after restart can create a shell. Preserve Loopflow's existing owner/input/geometry discipline; do not copy that behavior while borrowing T3's view recovery. [T3 attach behavior](https://github.com/pingdotgg/t3code/blob/71c2d3a302092b94511eb7e6ab4e6844a66dbf22/apps/server/src/terminal/Manager.ts#L2979).
4. **Test cancellation against the data it protects.** T3 caches projection and cursor only after completed application and uses an owner generation to stop canceled scopes overwriting successors. Loopflow's full-reading protocol has no replay cursor, but old subscription results must likewise not update a replacement subscription or reused request ID. This is a test target, not a verified Loopflow bug. [Client cache fencing](https://github.com/pingdotgg/t3code/blob/71c2d3a302092b94511eb7e6ab4e6844a66dbf22/packages/client-runtime/src/state/threads.ts#L279).

### For a later mobile/remote protocol

- Snapshot + sequence + catch-up completion + explicit snapshot fallback. Bound replay by count and raw/encoded bytes, handle history pruning during reads, and deduplicate overlap. This is useful only if Loopflow adopts incremental/replay delivery; full replacement readings already avoid many delta correctness obligations.
- One connection supervisor shared by client surfaces; transport health distinct from synchronized data. Mobile foreground probing must handle silently dead sockets; logical environment/Machine identity must survive endpoint changes.
- If mutations become transparently retryable, persistent idempotency receipts and side-effect intent are required. Until then preserve 593's `outcome_unknown` and inspect-before-retry semantics. Do not retrofit the entire T3 Run/ExecutionNode/outbox domain just to get remote transport.
- High-latency terminal output should avoid one round trip per chunk. T3's `OutputProtocol` allows an 8-chunk/64 KiB acknowledgment window. Separately, an 8 MiB pending output budget unsubscribes and obtains a fresh terminal snapshot on overflow rather than blocking the host PTY forever. Geometry policy remains a product choice: T3's smallest-viewer grid trades desktop width for phone visibility, while Loopflow has explicit geometry ownership. [Output window and overflow](https://github.com/pingdotgg/t3code/blob/71c2d3a302092b94511eb7e6ab4e6844a66dbf22/apps/server/src/terminal/OutputProtocol.ts).

## Remaining evidence limits

- No hands-on app, live multi-device test, performance benchmark or provider-login test was performed. Behavior above is source/docs backed, with user reports separately labeled.
- HN reports are a handful of self-selected users. “Users love” should be phrased as “these users specifically praise.”
- Current source has a first-class import mechanism, but no first-class universal live native-TUI/chat toggle was found. Absence from the inspected entry points/docs is narrower than proof that no undocumented workaround exists.
- T3's main is moving quickly; pinned links make this a dated snapshot. Some architecture design documents are older proposals, so implementation and current user contracts won when they differed.
