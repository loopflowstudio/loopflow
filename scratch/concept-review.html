Biggest mismatch left: off is two promises

Existing

stands_in:        auto == on  → stand in
waiting_to_land:  auto == off → wait at the merging step
                  never set   → land

lf task auto off X
lf task run X        # you take ship-review yourself
#   Waiting at pr land: auto is off (Maya).
#   `lf task auto on X` lands it.

"Auto on" is the way to land a Task you reviewed yourself, with no step left to stand in at.

Proposed, its own Task

each interactive step records who took it:
  a person | a stand-in

landing waits only when auto is off
and the last interactive step was stood in for

lf task auto off X
lf task run X        # you take ship-review yourself
#   lands

Off then means one thing: you take the interactive steps. An off said after a stood-in review still stops the merge, because that review was not yours.

Tested against. Normal: off, own review, run: lands. Failure: off said while a stood-in run is past review: last interactive step was a stand-in, so it waits, as now. Recovery: the person runs the Task again; it needs somewhere to put their review, so the Task goes back to ship-review, not to auto on. Counterexample kept: a Graph with no interactive step and auto off has no step to go back to; it must keep waiting for auto on, so the off-at-land read cannot be deleted outright.

Not in this work: it changes what Graph steps record and where an off puts a Task, and the present rule is documented and safe (an off never lets a merge through).

Larger than this work

  • A config default is read once. Removing auto: on from a Wave leaves its taken-up Tasks on, attributed to "wave config". Resolving at read costs a config read in every projection that shows auto.
  • auto::running_graph polls up to 30 s so TaskRunStart::Live can name a Graph run. If Live named the carrier the wait would go; it changes the TaskRun answer.
  • outlook on the run snapshot has no reader. Either a surface uses it in place of reason's wording, or it leaves the wire.
  • Upgrade reads a released withdrawal as off. A ship that ended on a failure under 0.16.0 arrives as auto: off by the row's person, though nobody said off, and that Task's next run waits at land. It is the safe reading of an ended approval; under the new rule a failure would have left auto on.
  • LOO-971 drops task_ship_events, tasks.shipped_at, task_summaries.ship_events; Task d3af77 removes the graph: auto fold.

Questions

  1. Off at the landing step, when you took ship-review yourself.
    1. Keep: it waits until lf task auto on (as built).
    2. Your own run past review lands; only a stood-in review waits. Its own Task.
  2. A config default that is later removed:
    1. Tasks already taken up stay on (as built).
    2. Resolve it at read, so they follow the config. Its own Task.
  3. TaskExecutionSnapshot.outlook:
    1. Leave it for a surface to pick up.
    2. Drop it from the wire until one does.
  4. A released withdrawal after upgrade:
    1. Off (as built).
    2. No mark: the Task takes its config default again.
