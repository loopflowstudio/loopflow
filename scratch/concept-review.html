Ship is shorthand for Auto-Ship

LOO-968 concept review, 2026-11-18, before implementation. The area: everything that decides whether a Task's run stands in for people and merges — lf ship, lf -b task run, stop/hold, the shipping state and Autonomous section, recovery, and the records behind them. The plan was read against LOO-959's head 89943efba2, which this branch stacks on.

"i feel like ship is supposed to be a small short hand that maybe updates the proposed graph to be auto mode, and has grown into this sprawling concept. lets reduce its impact on the overall system and protocol" — Jack

The kickoff plan already gets the large move right: one carrier, one recovery, the landing as a Graph step. This review found three places where the plan's own model was still bigger than the concept, and changed the plan for all three. proposed marks what the review changed.

The biggest mismatch: a stored approval nobody reads

The kickoff plan kept Approval::Route: a run with no interactive step ahead writes Auto-Ship on, and so does reaching end. Walk what reads that write under the new model:

  • The runner reads on only at an interactive step. A run with no interactive step ahead never reaches one.
  • Landing reads only stopped (stopped_landing, graph.rs:843). on doesn't gate it.
  • At end, today's ship carrier already returns ShipStep::Finished without merging (ship.rs:543); after this Task there is no carrier at all.
  • The only reader left is the label: shipping versus moving.

So the write is a stored copy of something the Graph answers, plus an "unless stopped" rule to keep the copy from overriding a person. Deleting it deletes the Approval enum, the conditional, and the only writer of Auto-Ship that isn't a person's command.

Before (kickoff plan)

  → task_graphs.auto_on_at = now
       (unless auto_off_at)
  → state shipping · Autonomous

After proposed

What changes on purpose: that run shows in Working, not Autonomous. Nobody turned Auto-Ship on, and the board says so. What survives: it still merges, lf task hold still stops it at the landing, the ships: line still warns. "Approval never granted without a person's lf ship or -b" becomes literally true.

Counterexample checked: a routed path reaching end on a graph that also had interactive steps (the task_work.rs:619 comment). Today that write hands the Task to a ship carrier that finishes at end without merging. Nothing is lost.

One interaction, with failure and recovery

Maya's Task waits at human-review on code.

  1. lf ship LOO-1 writes on, by Maya and runs lf task run LOO-1. One Graph process; state shipping.
  2. The run stands in at human-review, runs deliver (land --wait-and-fix).
  3. The Machine sleeps; the run dies. restart_runs relaunches lf task run LOO-1 — the same rule as any run. It reads on at verify and stands in.
  4. Instead: Maya runs lf ship --stop mid-implement. stopped, by Maya. The run finishes implement, reaches human-review, blocks; state active. lf -b task run stands in by its mode but waits at land: "not approved to merge (Maya stopped shipping). lf ship lands it."

One gap the walk exposed, left as question 5: ship_settle_merge today completes a Task whose PR someone merged by hand even on a graph with no land step (build, pursue, deep-clean, queue end at pr-publish or gate). The plan's answer "the land step sees it" holds only for graphs that have one.

  • Three names for stop: lf ship --stop, lf task hold, Stop Auto-Ship. With stop as one write, hold could become the only command, or --stop could.
