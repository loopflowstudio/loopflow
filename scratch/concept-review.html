Where a flag can sit on an lf command line

Area taken: the whole promise "a flag works on either side of the command", and what a person is told when they get one wrong. The Task names one failure in reorder_args; the review covers every place lf decides which token is a flag's value. Nothing is built yet; this reviews the plan. Blue marks what is proposed; everything else exists today.

One interaction, walked

Someone means to open a repository and stops typing one word early.

Today 
$ lf open --repo
Error: resolve repository
  /Users/jack/src/open

$ lf open --agent
# agent is "open"; no command
# is left; the default agent starts

The message is about a repository called open. Recovery means guessing that lf rewrote the line to lf --repo open. With --agent there is nothing to recover from: an agent is already running.

Proposed 
$ lf open --repo
error: a value is required for
  '--repo <NAME_OR_PATH>' but none
  was supplied

$ lf open --agent
error: a value is required for
  '--agent <AGENT>' but none was
  supplied

Exit 2, nothing started. The fix is the one the message names. Same text whether the flag came before the command, after it, after a skill name, or beside the wrong command on the path.

The biggest mismatch

"This flag's value" has no single owner in lf.rs. The kickoff plan fixed the visible symptom in push_flag and scheduled the other two readings for the last slice. They are the same defect. lf task --wave --title x create shows it: selected_command_path skips --title as --wave's value, meets x, finds no such subcommand and never reaches create, so the flag's owner is never on the path and it is treated as the root --wave. The nested case in the Task cannot be fixed while the path scanner reads values differently from the mover.
Proposed. One function answers the question for every caller, using Clap's rule. 
enum Takes     { Nothing, OptionalValue, Value }   // per flag, from the Clap tree
enum FlagValue { None, Inline, Next, Missing }     // per flag at a position
Missing: the flag needs a value and the next token is absent, --, or starts with - (a lone - is a value). push_flag and both index + 1 < len checks are deleted. FlagTables becomes one map of Takes.

Changed in the plan

  • The value function moved from the last slice to the first: it is the mechanism, and the nested case depends on it.
  • Three slices became two.
  • FlagTables becomes one Takes map instead of gaining a third "requires a value" set.
  • The returned argv is the shortest one, not "everything written before the flag".
  • Three things are named as separate outcomes: prose scanned for flags, attached short values (-acodex), and the three scanners.

Questions

  1. When a moved flag is missing its value, what does Clap get to see?
    1. Chosen: only the flag at its owner (lf --repo). One rule, same error from every position.
    2. Everything written before the flag, then the flag. An earlier error on the line is reported first; the rule depends on what was already moved.
  2. Should prose after skill: be scanned for root flags?
    1. Chosen for this Task: leave it. -c after a prompt keeps working; a stray --repo in a sentence is still read as a flag.
    2. Lift only flags at the very end of the line.
    3. Lift nothing after skill:; flags go before the prompt.
  3. Three argv passes before Clap, two flag tables. Worth its own Task?
    1. Chosen: not here. This Task leaves lf.rs with one reading and navigation.rs with its own.
    2. One pass that resolves path, owner and placement, replacing CommandArgTables.
    3. Clap global = true for root flags, keeping a small lift for skills only. Needs the commit -m collisions settled first.
