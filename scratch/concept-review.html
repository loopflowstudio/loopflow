Biggest mismatch: ship_control is the old concept, still on every row

The Task asks to delete "the wire fields that only restate auto mode". One is left. Every Task row in every list carries ship_control (12 DTO fixtures, the server schema, Swift RoadmapTask.shipControl, WorkCache's key list). It has one reader, the Auto toggle, and it is built from three reasons:

Existing (commands/waves.rs) 
ship_control.unavailable =
    run_control.unavailable        // the row already has it
 or "auto is already on"           // the row has state:auto;
                                   // the toggle never reads this:
                                   // when on, it shows "off" instead
 or "Task is at the end of its graph"
                                   // `lf ship` there is not refused:
                                   // it answers "ended", exit 0

Toggle (off): disabled by ship_control.unavailable
Run button:   disabled by run_control.unavailable
Proposed 
(no ship_control)

Toggle (off): disabled by run_control.unavailable
Run button:   disabled by run_control.unavailable

A Task at `end` that is not yet done:
  the toggle sends task.ship, the answer is
  {"state":"ended"}, auto stays unset and the
  toggle reads off again, as `lf ship` prints.

Ship is the run, asked for auto, so what makes it unavailable is what makes the run unavailable. That was already true in the CLI and the server after the second pass; this makes the row say it. One predicate, one field, and the last ship word leaves the row DTOs.

Tested against:

  • Normal. Idle Task, auto unset: toggle enabled, as today. Auto on: the toggle never read ship_control.
  • Failure. Missing worktree, abandoned Task, launch refused: run_control carries the sentence, as it did through ship_control.
  • Counterexample kept. A Task at end whose completion is pending shows an enabled toggle that does nothing. A done Task hides the toggle, so this is the window between reaching end and completing. The CLI's answer there is the same "ended"; if the toggle must be disabled in that window, the row's step is the fact to read, not a second control.
  • Must survive. Desktop never offers auto on a done or abandoned Task; run_control is unchanged.

Passed over: renaming it auto_control and dropping the dead reason. That keeps a second control whose only difference from the first is a case the server does not refuse.

Same pass

  • --reason goes where reasons are read. lf ship --reason becomes the run's own --reason (TaskProcessOptions.reason, "Direction for this run, published to the Task"), since it is the same operation. lf task auto off --reason is saved as a Task comment. AutoAsk::Person loses its note, set_task_auto loses its note parameter, and the progress row says only "auto on: Maya". Help says what happens. Passed over: a note on the mark that lf task status prints (a column and a wire field for one sentence), and deleting both flags (a person's why at an off is worth one line).
  • The developer reference tells the one-carrier story. docs/dev/reference-models.md drops "ship event" from the records that own a process and "lf ship" from the spawners.
  • The task.ship answer fixture is named task_shipping.json, beside task_running.json with the same shape. Rename it task_ship_answer.json, as task_auto_off_answer.json is named.

Larger than this work

  • "latest Graph: Graph code finished; nothing further is launched" on a Task that waits at an interactive step. The sentence is the base's, and it is wrong about the common case: the Graph run finished, the Task has not, and lf ship or lf task run launches more. It needs the execution snapshot to know the Task's position, not only its latest Graph process.
  • Auto before a first Graph. The setting reads as the Task's and lives on its Graph row, so lf task auto off on a never-run Task answers "auto was not on" and saves nothing; a later lf -b task run turns auto on. A released hold on such a Task is lost in the upgrade the same way. Storing auto on the Task closes both.
  • The 30 s wait. A ship that meets a carrier whose Graph has not registered polls so its answer can name a Graph process. If the answer named the carrier, the wait and its fallback sentence would go. Not driven in QA.
  • task.shipped, the subscription event, means "the PR merged". With ship now meaning "run with auto", that is one word for two ideas on the wire. Released Desktop reads it.
  • The auto Graph's name.
