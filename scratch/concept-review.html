Do the tracker's concepts line up?

LOO-925 at 2a2b47cc93, PR #1957. I reviewed the whole path a person's plan takes to and from a tracker, not only the diff: connecting one, seeing whether a change arrived, losing a conflict, a coworker's edit coming in, and forcing a sync. That's where the new words (tracker, action, event) have to hold up.

One interaction, start to finish

You rename a Task while offline, a coworker renames it in Linear, then you reconnect.

lf task edit LOO-12 --title A→action field · queued→drain sends · sent, reply lost→looked for · Linear holds B, newer→conflicted, A kept

What do you check, and what does it say?

lf repo plan --json

"transport": "linear",
"actions": [{ "owner": "LOO-12",
  "change": "title",
  "phase": "sent",
  "provider": "linear",
  "error": "Reply lost" }]

Phases are the new words, but the doc comment on phase still says "pending, or attempted". The tracker is named twice, as transport and provider. Once the action is conflicted it drops out of this list, because it only shows unconfirmed actions.

lf task show LOO-12 --json | jq .sync (what Desktop shows)

"changes": [{ "field": "task_title",
  "state": "adopted_linear",
  "local_value": "A",
  "linear_value": "B" }]
Adopted planning provider change · task_title
 · saved: "A" · provider: "B"

The same action under a second vocabulary: pending · uncertain · adopted_linear, linear_value (even on Asana), "planning provider". This is the surface the Demo and Desktop read.

Do the same on a Git-planned repository and there's a third answer: the losing value is in lf repo plan journal. lf task sync LOO-12 answers "Task repository has no remote planning provider", even though the glossary just made Git a tracker.

The biggest mismatch

"Where does my change stand" has three answers. The queue is one table with one set of phases. A person sees it through two projections written in two vocabularies, plus a third place for Git's losing values. The rename went as far as the store; the surface people and Desktop read still says adopted_linear.

Existing

lf repo plan   → actions[]: QueuedAction
                 phase: queued|sent
                 transport + provider
lf task show   → sync.changes[]: PlanningSyncChange
                 state: pending|uncertain|adopted_linear
                 local_value, linear_value
lf repo plan journal → Git losing values
Swift: PlanningSync.swift mirrors PlanningSyncChange
Proposed 
one TrackerActionView, two filters
  seq, owner, change, subject,
  phase: queued|sent|conflicted
  tracker, error,
  local_value, tracker_value  (when conflicted)
lf repo plan   → tracker, actions[]          (all owners)
lf task show   → sync.actions[]              (this Task's)
Git: losing values from the journal show here
     as phase "conflicted", same shape

Behavior stays the same. PlanningSyncChange, PlanningSyncState, the hand-written lines() labels and linear_value are deleted; the Task view becomes a WHERE owner = task over the same read lf repo plan already does. Conflicted actions stay visible until a person edits the field again; today they also stay, under adopted_linear. What it costs: a wire change to task.sync (Rust, PlanningSync.swift, planning_sync.json, Desktop's headless test), the same kind of change as LOO-942.

Counterexample checked. Doesn't a creation need its own state? No: it's already a create action with phase sent while its reply is lost. Doesn't Git need a queue to fit the shape? Not for the view. Git's journal already keeps the losing value; only how it's presented changes, not how it's exchanged. Whether Git sends through the queue is a separate, much larger question (3c).

Smaller things on lines this PR added

  • QueuedAction.phase doc comment: "pending, or attempted" → queued, or sent (rust/loopflow/src/lf/commands/plan.rs:155).
  • PlanStatus.transport and QueuedAction.provider both name the tracker → tracker (plan.rs:132,158).
  • lf task sync says "no remote planning provider" (ops/task.rs:2333): wrong word, and it refuses Git.
  • tracker::configured() is documented as "none under Git planning". If Git is a tracker, the function should say what it actually returns: whether there's a queue (queued_tracker(), or return Tracker::Git).

Larger than this work

  • Connecting Asana and Linear the same way. Make lf wave plan connect handle Asana's team the way it handles Linear's --team-key, so setup is one command for either. It would take an Asana arm in connect_wave and dropping the hand-edited planning.team from the docs.
  • acquisition → the tracker's copy. task.acquisition {state: available|removed|absent|invalid|unavailable} describes the tracker's copy of the Task. Under the glossary it reads as tracker: {state, read_at}. Wire change, so it fits LOO-955 or LOO-942.

    3. Something else.

    3. All the way: Git peer exchange becomes a tracker on the queue (LOO-938's peer half; much larger).
  4. lf task sync --retry-updates:
    1. Drop the flag: an explicit sync always looks now and resends what the tracker lacks.
    2. Keep it.
