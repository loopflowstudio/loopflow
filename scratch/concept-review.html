2. The core mismatch this branch resolved (Base vs. HEAD)

On base 41023c8e55, four places treated which Task a conversation belongs to as the same thing as which directory it runs in: binding overwrote agent_sessions.cwd to task.worktree, workspace admission moved non-bound primaries on idle reopen, recovery required cwd == task.worktree, and re-selecting a primary failed if another Task owned its directory. On HEAD (c36ad9b9b7), ownership and directory are independent everywhere.

3. Failure, recovery & counterexamples checked

Normal path

Live agy chat in unowned Y binds to Task T (checkout X). Bind prints both paths and keeps cwd = Y. lf resume -a claude:fable in Y switches harness in Y; lf resume T from anywhere attaches to it in Y.

Crash, reboot & deleted dir

Provider dies or server restarts → T is open, claimed, and has a local task_checkouts row → server restarts primary in Y and status shows starting again → running. If Y was removed on disk, leave_gone_directory falls back to main.

Task not checked out or closed

No local task_checkouts row → stays down with “its Task is not checked out here.” When T is completed or abandoned, recovery stops and retirement removes only X, never touching Y.

Counterexamples checked against HEAD
  1. lf task create --run setup race: Until setup::checkout creates the worktree, task_checkouts has no row, so recovery never races initial setup.
  2. Remote or moved Sessions: Remote rentals live in machine_records, not agent_sessions; moved Sessions set moved_to_machine_id and completed_at, so neither triggers local recovery.
  3. Re-selecting when T has no checkout and S sits in T2's checkout: resolve_checkout clears checkout = None when checkout_task != target, so re-selecting S never steals T2's worktree.
  4. Refused binds & crossed creation: Reassigning S to another Task refuses cleanly before printing any binding announcement (QA scenario 12); lf task create --session with a crossed Session still refuses.
  5. Unstarted primary placeholder: Fresh primaries (captured IS NULL AND bound_at IS NULL) still land in their scope's worktree before first launch (QA scenario 5).

4. Outside this Task (separate outcomes)

  • lf resume in an empty unowned linked worktree: currently refuses and points to lf; starting a conversation there instead is a separate behavioral change.
  • lf task move with a split primary conversation: moves::send_task checkpoints task.worktree (X), so uncommitted edits in Y do not travel with the move; warning or refusing is a separate follow-up.
  • lf resume -a <agent> on a held conversation with no provider history: attaches to the running agent without noting that -a was ignored (pre-existing; observed in QA scenario 10).
  • Retiring agent_sessions.work_source and test-only bind_session_prepared: tracked under LOO-836. (Also minor cleanup: stale comment on transport::selected_directory still mentions bind moving a directory.)

5. Product choices built for review

All four choices below are Built on HEAD and reversible. Reply with e.g. 1b or 3b to flip any of them.

1. When you bind a conversation to a Task that already has a different worktree, where should the conversation run?

Applies whether you started the conversation in another linked worktree (like manabot.academy-test-drive), in main, or in a Wave checkout.

  • 1a. Built Always stay where it started. The conversation, its uncommitted edits, lf resume in that worktree, and crash recovery all stay in one directory. The Task's own worktree stays where Graph workers and PRs run.
  • 1b. Stay in linked worktrees, but move out of main and Wave checkouts. Keeps shared checkouts cleaner after binding, at the cost of a second rule and breaking directory-keyed native resume (like Claude Code) until a new thread starts.
2. When you bind a conversation in directory Y to a Task whose checkout is X, should lf session bind mention both directories?

Matters because Graph workers, lf task changes, and PR delivery act on X while your bound conversation edits Y.

  • 2a. Built Print one factual line only when they differ: “Conversation stays in <Y>; <TASK>'s checkout is <X>.” Silent about directories when they match or when the Task has no checkout.
  • 2b. Say nothing about directories. Print only the Task it bound to.
3. When a bound conversation running outside its Task's checkout crashes or dies on reboot, should Loopflow restart it automatically?

Applies when the Task itself is open and checked out on this Machine, while its primary conversation runs in another directory (another worktree or main).

  • 3a. Built Yes — restart it in the directory it was running in. Matches normal Task conversations, fixes the misleading “its Task is not checked out here” message, and leaves Tasks with no local checkout stopped.
  • 3b. No — auto-restart only conversations inside the Task's own worktree. Leave split-checkout conversations stopped after crashes, and change the status line to say the conversation runs outside the Task's checkout.
4. Should we leave previously moved conversations alone in your local store?

session_94d9963b7fd74dacbe01b65c99f7deb5 already had its recorded directory rewritten to manabot.mtg-388-getting-into-a by the older bind.

  • 4a. Built No automatic repair. Leave existing rows as recorded; lf resume <session> reaches them from anywhere.
  • 4b. Repair that row by hand afterwards so session_94d9963b… points back to manabot.academy-test-drive.
