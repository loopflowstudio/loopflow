How outside code reaches what ships

The area taken: every route by which code nobody here wrote gets into main, the signed dev build and the release. LOO-1120 removes one route, Dependabot. Reviewed as the whole supply path with commit 0586cdf9f4 in it, because the Task's outcome is a claim about that path, not about two YAML files.

What was found

The deletion is right and complete for what it names. Removing instead of taming holds up: the deleted workflow was the repository's only pull_request_target trigger, it merged on user.login == 'dependabot[bot]', and it needed a write-scoped token to enter the merge queue. Nothing else in the tree reads any of it. Live checks today: security-update PRs are off ({"enabled":false}), no open Dependabot PR, five stale dependabot/* branches on origin.

The outcome sentence is not yet true. scratch/plan.md promises that "workflow action versions change only in a PR a person or their agent wrote." They don't, before or after this change. That is the biggest mismatch, below.

One interaction, walked

Normal: someone wants a newer crate

After this change.

a Task→cargo update -p x→third_party.py refresh→PR + CI + queue→main

One owner, one commit, revertable. The notice inventory already has a written update procedure in third_party/README.md, so "by hand" has a home.

Failure: an upstream release is malicious

Three routes, one closed.

crate / wheel / Swift package→lockfile PR→main
action tag moved (@v2)→no PR, no commit→next CI run
new Rust stable, uv, nextest, xcodegen→no PR, no commit→next build

Recovery

A bad lockfile bump is one git revert, and history says exactly which versions were in which build. A bad action tag has nothing to revert: the repository never recorded which commit of the action ran. Only the Actions run log shows it, for as long as the log is kept.

The biggest mismatch

"Automatic dependency updates stop" is true for libraries and false for build steps

The Task removes the updater that opened a PR, ran the full matrix and left a commit. The updater that remains does none of those: when an action's owner (or whoever holds their account) moves v2, the next run on main executes the new code inside the job that builds the release tarballs. That route is faster than the one-week path the brief describes, and it is silent.

Dependabot was also the thing that would have kept SHA pins fresh. With it gone, a SHA pin simply stays where it is until someone moves it, which is the stated outcome.

What survives, what changes on purpose

  • Survives: every lockfile, CI, the merge queue, package and release workflows, vulnerability alerts, release notes that mention Dependabot.
  • Changes on purpose: dependencies go stale until someone bumps them. Weekly ruff bumps end.
  • Counterexample that breaks the outcome as written: a moved action tag. Kept above as the main finding.
  • Counterexample that does not: GitHub opening security PRs with no config. Checked: the setting is off.

Questions

  1. Should build steps be locked the same way libraries are, in this Task? Today, if the owner of one of the eight actions changes what v7 points at, the next build of the dev app and the release runs their new code, and nothing in the repository changes.
    1. Recommended. Lock all eight in this PR. Afterwards an action changes only when a commit here changes it, which is what the Task says it delivers.
    2. Land the Dependabot removal alone and file the lock as its own Task now, before landing clears the note.
    3. Leave build steps floating and narrow the Task's stated outcome to libraries only.
  2. When a dependency bump is done "by hand", does a person read it before it merges? A bump is a Task. With auto on, an agent can update a lockfile, pass CI and merge without anyone looking.
    1. Recommended. No extra rule. Someone chose to start the bump; that is the "hand". Say so in the PR so the word is not read as "reviewed".
    2. Bump Tasks always stop for a person before merging. This needs a way to mark such a Task, which does not exist today.
  3. Should a bump refuse releases younger than some age? The brief names "no cooldown" as part of what went wrong. Most malicious releases are pulled within days, so taking only releases older than, say, two weeks avoids most of them.
    1. Not now. Bumps are rare enough.
    2. Recommended. File a separate Task to give hand bumps an age floor, starting with Python where the tool supports it directly.
  4. The merge key: who revokes it, and is it used anywhere else? The plan leaves revoking the PAT and deleting both stored copies to a person, because it cannot be undone.
    1. Recommended. A person revokes the PAT on GitHub after merge; an agent may then delete the two secrets and the five branches.
    2. An agent does all of it after merge, on a clear yes.
    3. The PAT is shared with something else: keep it, delete only the two DEPENDABOT_MERGE_TOKEN entries.
  5. How far does "nothing updates itself" go? The Rust compiler, uv, the test runner and the CI machine image also move on their own.
    1. Recommended. Stop at libraries and build steps. The compiler and tools keep floating.
    2. Also fix the Rust compiler version in the repository, so a new compiler arrives in a commit. Each new Rust release then needs a bump Task.
