Concept Review: Harness Interface, Parity & Waking Work Sessions

Area reviewed: How Loopflow defines, enforces, and verifies top-level behavior across all five harnesses (Claude, Codex, OpenCode, Pi, Antigravity) — widened from LOO-1098's Antigravity reopen and parity pass to the whole Harness / Launcher interface, SQL wake dispatch, conformance tests, and docs.

Task: LOO-1098 (Decision pass 1, post-build) Built at HEAD: c0b28b7dc6 vs base 80cced1bd4 Status: Built at HEAD vs Proposed next pass in scratch/plan.md

What is built vs. what this review changes

Committed & live-verified at c0b28b7dc6: Reopening a closed Antigravity work session with waiting steers or Task updates starts one turn via agy --conversation <id> -i … and delivers them through PreInvocation (verified on real agy 1.5.16 in scratch/qa.html); nested launches strip ANTIGRAVITY_* parent markers; live held-terminal wake for already-open agy was dropped after PTY probes showed ?2004h cannot distinguish prompts from dialogs/menus and moved to LOO-1099.

Why we iterate before landing: Pass 1 built a declarative parity table (harness/parity.rs + generated harness/README.md) with a first-class Support::Gap opt-out that makes missing behaviors pass tests, left idle-wake dispatch hardcoded in SQL, kept provider env stripping outside Harness, and overloaded ResumeInput. This review replaces that with required interface methods/capabilities and unconditional HarnessKind::ALL assertions.

4. Open questions for review

All remaining items are reversible choices made for the next pass. Reply with a number and letter (e.g. 1b) to reverse any of them.

1. When you reopen a closed Antigravity Task conversation with waiting steers, what should appear as the opening message on screen?

Antigravity needs an opening prompt to trigger the hook that loads waiting steers and Task updates before you type, so that opening prompt shows up as a turn in the terminal.

  • 1a (chosen in current build): Show the short generic line "Read the waiting steers and Task updates for this Session." and let the hook inject the actual steers behind the scenes — nothing is marked delivered until the hook runs, so a failed launch never loses a steer.
  • 1b: Put the actual steer text directly as the opening prompt (so you see the steer words on screen instead of the generic line, at the cost of marking steers read at launch before Antigravity starts, or skipping Task updates that exceed prompt size).
2. Should Loopflow still list known provider-specific limitations (like live idle wake on Antigravity under LOO-1099) in prose inside docs/sessions.md and harness/README.md?

The generated parity table is being removed so code and tests enforce full parity instead of documenting opt-outs.

  • 2a (chosen for next pass): Yes — keep brief, plain sentences in user docs (docs/sessions.md, docs/config.md) and developer notes (harness/README.md) where current behavior actually differs (for example, that an already-open Antigravity conversation reads new steers on its next turn), with no parity table.
  • 2b: Remove provider-caveat prose from harness/README.md too and leave known gaps only in Linear issues (LOO-1097, LOO-1099, Task 48edb9) and user docs.
