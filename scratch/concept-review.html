Where a flag can sit on an lf command line

Area taken: the whole promise "a flag works on either side of the command", and what a person is told when they leave a value off. This is the review of the change as built, against its base 12b66c3e17. Every transcript below was run on the branch binary on 2026-11-21 from /tmp.

The biggest mismatch, and whether it closed

"This flag's value" had no single owner in lf.rs. It has one now. The nested case shows it: on the base, lf task --wave --title x create lost create from the command path because the path scan and the mover read values differently. Built, both call separate_value, the line is rewritten to lf task create --wave, and Clap names --wave <WAVE>.

The file is smaller for it: 196 lines added to lf.rs and 252 removed, with thirteen missing-value cases and six kept-value cases tested through reorder_args and Cli::try_parse_from together.

The last three are one rule seen three times: a word written directly after a value-taking flag is its value, even when it also names a subcommand. That is Clap's reading and every other CLI's, each case exits 2 without running anything, and the base behaved the same. The alternative, "a subcommand name is never a value", would make a Wave called list unreachable without =. Question 4.

Outcome

Nothing to change in this work. The concepts the Task touches line up; the two that do not are separate outcomes, named in scratch/plan.md.

Questions

  1. When a moved flag is missing its value, what does Clap get to see?
    1. Built: only the flag at its owner (lf --repo). One rule, the same error from every position.
    2. Everything written before the flag, then the flag, so an earlier error on the line is reported first.
  2. Should prose after skill: be scanned for root flags?
    1. Built: yes, as before. -c after a prompt keeps working; a stray --repo in a sentence is read as a flag.
    2. Lift only flags at the very end of the line.
    3. Lift nothing after skill:; flags go before the prompt.
  3. Should navigation.rs share the reading in lf.rs?
    1. Built: not here. It would take its own Task: one table from the Clap tree, used by remote routing and by reorder_args.
    2. Go further: Clap global = true for root flags, keeping a small lift for skills only.
  4. A value-taking flag written directly before a subcommand name (lf task --wave create):
    1. Built: the word is the value, as Clap reads it.
    2. A subcommand name wins, and the flag reports a missing value. Names that collide with subcommands then need --wave=list.
