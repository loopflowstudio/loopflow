The interaction

You (or lf, for a Task) run git worktree add ../x main. lf's own add (rust/loopflow-execution/src/git/mod.rs, add_worktree) never passes --no-checkout, so Git's post-checkout hook fires with a null old OID in both cases. The hook clones a sibling's compiled units. Your first cargo build -p loopflow --bin lf compiles 7 units instead of 256 and uses 87 CPU-s instead of 208.

Failure: every sibling is mid-build, or the volume can't clone. You get no seed and today's cold build, and status says seed none. Recovery: nothing to recover. The cold path is the fallback, and the rename never exposes a half seed to Cargo. Doubt: something looks stale. Cargo's fingerprints decide freshness, and every workspace unit is dirty in a new checkout, so the remedy is the usual one: rm -rf target.

Biggest mismatch: what a seed is

Before (plan as written)

clonefile(source/target/debug → debug.seeding)
debug.seeding/
  .fingerprint/   kept
  build/          kept
  deps/           kept
  examples/       kept
  incremental/   rm -rf after clone
  lf, lf.d, *.rlib  rm after clone
  .cargo-lock …   cloned
rename → debug

Correctness depends on the delete list covering every top-level file Cargo uplifts. Deleting incremental/ takes time proportional to its file count.

After PROPOSED

mkdir debug.seeding
for e in .fingerprint build deps:
    clone(source/target/debug/e → debug.seeding/e)
rename → debug

Three clones and no delete step. A stale lf binary can't arrive, because nothing at the top level is copied. A source missing one of the three is skipped. A clone that fails partway removes debug.seeding. Fixture 4 now patches the clone to fail after the first entry, which replaces the plan's "forced cp failure" (the plan doesn't use cp on macOS).

What this review didn't change

The trigger, the lock check, the atomic rename, Cargo-owned freshness and the "never a full copy" rule all survive the counterexamples I tried:

  • A Task worktree made by lf: hook fires.
  • A sibling mid-build: skipped.
  • A sibling reaped by cleanup mid-clone: the clone fails, or a missing output dirties its unit.
  • A different Cargo.lock or toolchain: mismatched units compile.
  • Another volume: EXDEV, no seed.

The remaining ~200 CPU-s of a fresh test build is workspace libraries in the incremental test profile. No seed reaches it, and it stays outside this work (see scratch/questions.md).

Questions

  1. Opting out of seeding:
    1. No knob; rm -rf target after the add.
    2. Keep LOOPFLOW_SEED_TARGET=0 to skip the 2–7 s clone.
  2. What a seed contains:
    1. Exactly .fingerprint, build, deps.
    2. The whole target/debug minus a delete list (the original plan).
  3. Choosing the source:
    1. Newest .fingerprint mtime among quiescent siblings.
    2. Prefer the main checkout.
    3. Prefer the sibling with the closest merge-base.
  4. The hook's stale script copy:
    1. Reinstall once, documented in testing.md.
    2. The hook runs the checkout's own scripts/build_cache.py when present, else its copy.
  5. Test-profile workspace libraries (~200 CPU-s):
    1. Leave to LOO-921's edit-loop decision.
    2. File a Task measuring per-package incremental = false for crates not being edited.
