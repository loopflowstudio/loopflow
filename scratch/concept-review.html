Closed · Navigation

Real stages in Start from…, topology-based loop decisions

Desktop’s Start from… menu uses TaskGraph.startFromSteps (start plus top-level runnable stages, excluding standalone breakpoints). Loop decisions check return_target(body, leaf.index).is_some(), requiring --reason when iterating without a prior verdict. Continued runs print <graph> from <step> instead of from start.

Closed · Reply scope

One-step handoff, one clean comment

GraphProgress.handoff carries non-loop / advance --reason replies to the immediate next step only and clears on settlement without leaking downstream; GraphProgress.direction stays strictly for loop iteration. Replies write one CommentKind::Breakpoint comment (skipped by task_undirected_comments so the primary never receives its own reply back as news).

Closed · Waits

Breakpoint wait separated from PR submission

lf task wait --until breakpoint (TaskWaitUntil::Breakpoint) waits for a parked breakpoint, end, or terminal even when a PR is already open. --until submitted (TaskWaitUntil::Open) stays dedicated to PR submission / terminal.

Choices built for your review

Every choice below is already built and reversible once you try the app and CLI. Reply with numbers (e.g. 2b 3b) to change any of them.

  1. When a worker blocks at a breakpoint, what should Desktop’s main button do?

    1a · Built for review. Hide the plain Continue button and show the blocker reason so you reply in the Task conversation, because continuing without choosing a direction always fails.

    1b. Keep Continue visible and have clicking it focus the Task conversation input instead of trying to run.

  2. What should Desktop’s “Start from…” menu list?

    2a · Built for review. List real work stages (start, explore, plan, build, ship-review, deliver, verify) so picking ship-review runs a fresh review and stops with its results.

    2b. List the breakpoint stops (after-explore, after-ship-review, after-verify) and have picking one start at the step right after that stop.

  3. How should the workflow bar show breakpoints?

    3a · Built for review. Show each breakpoint as its own marked item beside its step (explore · 👤 after-explore · plan · …), matching lf graph show.

    3b. Put the person icon on the step before the breakpoint (explore 👤 · plan · build · ship-review 👤 · deliver · verify 👤) so the bar stays short enough to fit on narrower windows.

  4. When “Sort by status” is off in Desktop’s sidebar, where should a Task waiting at a breakpoint sit?

    4a · Built for review. Keep your manual drag order intact in the sidebar; surface breakpoints first in Now and whenever Sort by status is turned on.

    4b. Temporarily float Tasks waiting at a breakpoint to the top of the sidebar even when Sort by status is off.

  5. When a reviewer recommends another loop pass (iterate), what should a plain Continue (lf task run) do?

    5a · Built for review. Accept the worker’s recommended path (running another pass if it recommended iterate, or moving on if it recommended advance), requiring --decision only when you want to override it.

    5b. Always move forward to the next stage on plain Continue unless you explicitly ask to iterate.
