Does “install from main” install all of Loopflow, or only the CLI?

The branch updates the CLI. Loopflow.app runs its own bundled lf, a release build, against the same ~/.lf. The first migration that merges after this PR can lock Desktop out of the store until the next release, which brings back the release-to-update loop for the window you use most.

One interaction, start to finish

todayA Task adds add_wave_colour.sql and merges. Packages (main) goes green.

todayYou run lf self install --main. It backs up, applies add_wave_colour and switches ~/.local/bin/lf. The terminal works.

todayLoopflow.app reads through Contents/MacOS/lf, a v0.15.0 build. That reader parses ledger versions as release ids, so it rejects the slug row with “incompatible Loopflow database; delete loopflow.db”. Desktop shows Couldn't update until a release ships an app with the new reader.

todayRecovery: cut a release, or restore the backup and stay behind main. The overnight lf install LaunchAgent follows releases, so it never brings you to main either.

After a release that includes this PR, additive slugs are fine, because the new reader admits unknown additive rows. Every breaking slug still locks Desktop out until the following release.

Three ways Desktop can follow main

a · Main packages include the app

Packages (main) also builds, signs and notarizes Loopflow.app. lf self install --main replaces both together, so CLI and app are always the same commit.

Cost: a macOS runner and notarization on every green main, so slower packages and a larger post-merge window. Keeps the rule that the app runs its own bundled lf.

b · The app runs the installed lf

controlLfPath uses the installed entry when it's newer than the bundled helper. One lf per Machine, whichever you installed.

Cost: the app's Swift DTOs and the CLI can come from different commits. DTOs have no defaults, so a renamed or added required field fails to parse in the app. The skew moves from the store to the wire.

c · Desktop stays on releases

Keep the branch as is. Release once before the first slug migration merges, and again before installing any breaking slug.

Cost: “push a release to update my Machine” comes back for every breaking migration, the case Jack wanted gone.

Proposed usage text (option a)

lf self install --main     # newest green main: CLI and Loopflow.app, then migrate ~/.lf
lf self install            # back to the latest release (store must not be ahead of it)
lf self install schedule   # keep following whichever channel you last installed

Proposed only. Two stale docs need fixing whichever option you pick: swift/README.md says schema changes require “a published release installed through lf install”, and store/MIGRATIONS.md says a private LF_HOME shows schema work “on real data”, but it starts empty.

Questions

  1. How should Desktop follow main?
    1. Main packages build the app; install replaces both.
    2. The app runs the installed lf when it's newer.
    3. Desktop stays on releases; release before the first slug migration and before each breaking one.
  2. Should the schedule follow the channel you last installed?
    1. Yes. After install --main, overnight refreshes stay on main.
    2. No. The schedule stays on releases, and main stays a manual command.
  3. Does this PR wait for 1, or ship and leave 1 to a follow-up Task?
    1. Wait: ship this PR and the Desktop answer together.
    2. Ship now, then cut a release right after merge, so Desktop's reader is current before any slug migration lands.
