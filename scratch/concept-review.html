Do the website's concepts and the code's line up?

Area taken: every page a visitor reaches on loopflow.studio (/, studio pages, /docs/*, /architecture/*, /download) and what wraps them: faces, bar, footer, palette, type steps, the install action and the workflow card. The plan named a bar; the thing a visitor meets is the whole page frame, so the review takes the frame. Nothing is built yet; this reviews the plan against main.py, content.yaml and style.css at 07e2fcd6c5.

The interaction

A visitor lands on /, reads, clicks Docs, reads a page, clicks Install. Today: the bar changes shape on the click to Docs (Navbar, sticky, blurred, a "Graphs" link, different type), the footer changes text, and Install from the homepage bar goes to /#start, which nothing carries, so it does nothing. From the docs bar the same word goes to /download. On /studio there is no footer at all. Recovery today is the browser's back button.

proposed The same bar and the same footer frame every page; Install goes to /download from everywhere; only what sits between them changes.

The biggest mismatch: the page frame

The plan unifies the bar and leaves the footer as "its own decision". But the visitor's concept is the page frame, and the code's mismatch is the four builders, not the bar. Fixing only the bar leaves the four builders in place, each choosing a footer, and the next page added picks a fifth arrangement.

Choice made for review: the homepage footer wins ("Loopflow · An open-source software instrument." with Loopflow Studio, Get started ↗, Source ↗). It is already the shared copy in content.yaml, so nothing new is written; the docs footer's "Built by Loopflow Studio" line goes. Studio pages gain a footer. The identical-frame e2e test covers header and footer on four pages, so a page that skips SitePage fails it.

Also folded in: one install block in content.yaml (the dead /#start goes, /download reads the command instead of hardcoding it), and the footer block moves to top level since every page reads it. Both ride in slice 2.

Kept as the plan has it: slice 1 (faces) first, since Old Standard at 390px is the riskiest visual unknown; the workflow card tested against the YAML rather than rendered from it, because the Docker image copies only website/ and cannot read rust/.

Counterexamples tried

  • Docs run 1440 wide, the homepage 1240: the frame's bar and footer sit in their own 1240 wrapper, so the box matches while the docs body stays wide.
  • Docs need docs.js and a robots Meta on architecture pages: they pass through SitePage's content; nothing about the frame changes.
  • Two nav landmarks on docs pages: they keep distinct labels ("Main navigation", "Documentation"), which the accessibility test checks.
