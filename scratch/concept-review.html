Biggest mismatch: reopening an abandoned Task leaves its dead PR and deleted checkout live

Counterexample on current HEAD

LOO-12 is completed with --children abandon. Child LOO-15 had open PR #1981 and checkout /worktrees/loo-15; abandoning closes #1981, marks task_prs.abandoned_at, and deletes the worktree and branch. Now the person clicks Reopen Task in Desktop (or runs lf task reopen LOO-15). Because reopen_task leaves #1981 as historical = 0 and leaves the deleted task_checkouts row behind:

1. Desktop disables Run, Auto-Ship, and Start from… with "Task LOO-15 worktree … is missing; restore that exact path before lf task run LOO-15".
2. lf task status LOO-15 says "PR closed without merge; reopen the same PR or abandon the Task" (recommended: no_action).
3. lf task complete LOO-15 refuses because dead PR #1981 is still its active PR (and on a leaf arms a pending completion that can never settle).
4. lf task run only survived QA via a published-PR-only workaround in restore_task_checkout — an abandoned checkout without a published PR still fails.

Choices made for review

All choices below are reversible in code and written into scratch/plan.md. Reply with a number and letter (e.g. "1b") to change any of them.

  1. After you reopen an abandoned Task (whose PR was closed and branch deleted when it was abandoned), what should its status and next run look like?
    • 1a (chosen, next pass) Fresh start on the same Task. The closed PR moves to history, Desktop's Run button is immediately active, lf task status recommends running it, lf task complete works if no PR is needed, and lf task run creates a new checkout from current main (unless its old checkout or local branch still survived on disk, which is kept).
    • 1b Keep the closed PR front and center. Status continues warning that the old PR was closed without merging until a new PR is opened, and Desktop blocks Run until the old checkout path is manually restored.
  2. When moving children up with --children rehome and the grandparent Task was deleted (while a great-grandparent above it is still open), where should the children land?
    • 2a (chosen, next pass) Top-level Tasks. Deleting the grandparent already detached this parent into a top-level Task in every view, so its children stay top-level rather than jumping under an ancestor nobody saw it attached to. (Closed — done or abandoned — grandparents are still skipped to reach an open great-grandparent.)
    • 2b Under the open great-grandparent. Walk past deleted Tasks just like closed ones (requires sending the destination from Rust to Desktop so the dialog button names the same Task).
  3. When a child is parked idle at ship-review (no Graph running, just its open conversation waiting for you), should --children abandon allow abandoning it?
    • 3a (chosen, built) Allow it and close the idle conversation. Only block when a Graph is actively running, a headless run is live, or the conversation is mid-turn.
    • 3b Block whenever any conversation window is open. You must manually close each child's conversation before --children abandon proceeds.
  4. In Desktop, when every open child already has a merged PR (so nothing would be abandoned), which button should be the default?
    • 4a (chosen, built) Complete & Finish Children first (marks merged children done), with Move Children second. When any child is unmerged, Move Children is default and Abandon Children is destructive.
    • 4b Complete & Move Children is always the default button, even when every open child is already merged.
