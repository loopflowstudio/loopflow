One rule, one place

Built. Cli::names_work is true when the command names its Work (--task, --wave) or is a step of a Task's run. It sets AgentConfig::managed; headless spawns take it as an argument, native launches read SessionCommand::managed. Nothing reads agent_sessions.work_source to decide it; the column is still written.

Cli::names_work ──► AgentConfig::managed ──► require_server + steer capability
                                         └──► ContextDelivery::hook_settings(managed)
                                              OpenCode / Pi: spec.managed

The gap, and what closes it

The first open from a Task workspace goes through the Task:

lf session resume --task LOO-1 --prepare
  open_argv: lf session resume --task LOO-1        # open_through: id spliced out, reselected from cwd

Every later open of the same pane goes through its Session id:

lf session resume 3f2a… --prepare
  open_argv: lf session resume 3f2a…               # bare

Proposed, next implement. One command names both:

lf session resume 3f2a… --task LOO-1 --prepare
  open_argv: lf session resume 3f2a… --task LOO-1  # the id selects, --task makes it managed

SessionTarget::from_selectors accepts an id with --task or --wave. Desktop passes the Task from its Task workspace and from executionLocations. open_through, its splice and its fork exception go, and the terminal stops reselecting the Task from its cwd between prepare and open. A Session link names no Task and stays bare.

Looked at and left alone

A Task-run step knows it is one from LF_GRAPH_STEP=task, which the Graph sets on the child and take_graph_step clears, so the step's own subagents are bare. Passing --task instead would make names_work read only flags, but --task also drives cwd, checkout and Session binding, which steps don't take today. The Graph spawning its step is the command; the mark is its argument.

The plugin observations (Pi polling --moment tool each second, OpenCode never resetting compacted) stay recorded in the working design as seen, not changed here.
