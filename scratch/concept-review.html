Swap the schedules only after the new ones are written

LOO-629 · concept-review (in a Graph, no person) · 2026-10-27

Built from scripts/bootstrap-cron-host.sh, release/CRON_HOST.md, python/tests/test_release_automation.py, scratch/loo-629-local-placement.md

The placement model is right as built. A Wave's Machine default is the one concept, and when it is null the Wave runs on whichever Machine reads it. Implementing that needed no new flag. The mismatch is in the cutover: the script deletes the old launchd jobs before it writes the crontab that replaces them.

Actions → concepts → APIs

Jack runs:   scripts/bootstrap-cron-host.sh infrastructure
Concept:     Wave placement  = lf wave status --json .wave.machine (null → this Machine)
             Installed lf    = ~/.lf-machine/install/gates/1/lf (what lf re-execs to)
             Schedule        = two crontab lines tagged # loopflow:infrastructure:*
             Old schedule    = ~/Library/LaunchAgents/loopflow.cron.infrastructure.*.plist
Verified by: telemetry-daily run in the same minimal env cron uses

Before (current branch)

checks pass → remove launchd plists → write crontab → telemetry run

If crontab - fails, no schedule is left. The Task allows removing launchd jobs "only as part of a verified replacement".

After

checks pass → write crontab → confirm both lines → remove launchd plists → telemetry run

Exactly one schedule exists at every exit. If telemetry goes red, the crontab is still the only schedule, so release never fires twice at 10:00.

Held, not changed

With null placement, two Machines that both bootstrap would both schedule releases. Jack accepted implicit local placement, and pinning elsewhere is lf machine use. The gate path's gates/1 is the pin lf itself uses. ~/.local/bin/lf can move with LF_INSTALL_DIR.
