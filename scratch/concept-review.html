LOO-708 · concept-review · 2026-11-02
Built from the working design, questions.md, and Rust Session commands, human_session.rs, transport.rs, native_exit.rs, journal/mod.rs and transport tests.

Keep the command's result when its waiting process goes away.

Review result: design changed. The next implementation preserves post-return JSON and launcher exit semantics across exec. Jack Heart's accepted requirement to keep resume and exit recording intact supplies this direction. No open product choice or new approval is recorded.

Same actions, fewer retained processes

Open a conversation → Session → lf resume SESSION
Close its pane      → viewer leaves; owner retains execution
Open another pane   → same Session → attach to its live owner
Recover after reboot → saved Session/history → lf resume --all

Before: the viewer and inner connect retained launch state; lf -i waited beside Claude.

viewer → owner → connect → lf -i → Claude

Implemented: connect becomes the launcher, which becomes Claude. The viewer execs into a store-free relay.

viewer ⇄ owner → Claude
          └─ wait, terminal, capture and exit settlement

Session and provider identities survive. Attachment tokens retain exact control authority. NativeExit carries settlement work to the owner; record_process remains the writer. Graph children retain their own waits. No new public lifecycle or database table is needed.

The remaining mismatch

Implemented gap: a successful relay exec cannot return to print_opened. The existing post-return Session JSON disappears. Separately, a provider exit of 7 now becomes launcher exit 7; the returning path previously produced an ordinary command error, exit 1.

Proposed repair: retain the command's continuation without a resident waiter or live store. Interpret provider exit, interruption and attachment loss consistently in both settlement paths. Preserve the capture result as well as the command result.

lf resume SESSION --prepare --json  # existing Desktop preparation
lf resume SESSION --json            # restore existing JSON after successful return

Direct startup errors remain acceptable when they explain the failure and preserve recovery. The deleted history-polling loop need not return just to keep its old wording. LOO-712 still owns encoding; LOO-705 owns the explicit successor needed when an owner ends.

Evidence limits

Existing stand-ins prove the reduced chain and normal settlement. Earlier measurements were owner 20 MB and relay 2.5 MB, before compression; final-tree Desktop and footprint acceptance remain outstanding. This review inspected code and changed scratch documents only. It ran no new lifecycle tests.

Questions for the next proof

  1. Does successful resume --json still return the Session JSON, while the live viewer stays small and opens no store?
  2. Do native exits 7 and 130 produce equivalent command, Process and capture results through the returning and owner-settled paths?
  3. Does takeover leave the new attachment intact, and does reboot recovery preserve history without replaying input?

These are verification obligations, not unanswered product choices. The working design records the direction; loop-or-next owns routing.
