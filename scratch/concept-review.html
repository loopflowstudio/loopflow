Settings and skills as a served reader sees them

LOO-978, reviewed before anything is built. The area taken: how lf server run, Desktop and --subscribe readers get settings and the skill catalog, and observe, the layer that tells them an outside fact changed. The plan adds a third thing to that layer, so the review covers the layer and not only the two values the Task names.

Legend: exists today proposed removed by the plan

Outcome

The plan changed. The mechanism stays: values computed from observed facts, kept with the facts they read. Five things changed in how it is built, and three findings larger than this Task are listed below without being acted on. No code was changed, nothing was built or timed in this step.

One interaction, walked

Desktop shows a Wave with 40 Tasks. Forty agents are writing, so the store revision moves several times a second and each move is a new reading. Someone edits .lf/config.yaml to change agent.

Today, per reading

For each Task: resolve_task_agent
↓
Read 3 to 5 config files cached answers from observe, cheap
↓
Parse each file's YAML again
↓
Validate every leaf of every file: clone the defaults tree, deserialize a whole Config validate_value, settings.rs:219. Twice per Task, once more per named skill per Wave.
↓
Merge, deserialize the result

Three caches already try to blunt this, each for one reading: PersonalSettings waves.rs personal map waves.rs agents memo

Proposed, per reading

For each Task: resolve_task_agent
↓
Ask for Derived::Settings { checkout, wave, outside } unchanged dependencies: return the shared value, one map insert

After the edit: within a second the refresh sees the file differs and bumps its revision. The subscription's dependencies report changed, the next reading finds that checkout's slot stale and resolves once. The frame shows the new agent.

Failure: the edit is invalid. The error is the slot's value, with its own variant, so every reading reports the same thing without resolving again.

Recovery: fix the file; the same path resolves once more.

The biggest mismatch: a cached computation that can read what nothing tracks

A derived value is right only if everything its computation read is either an observed fact or part of its key. Read anything else and the value is wrong until one of its files happens to change, and it is wrong silently: a Desktop row showing the old agent. Today the same mistake heals at the next store revision, a fraction of a second later.

The kickoff plan handled this with a rule in a doc comment and an audit table. The audit is good; it is also the kind that the next change to resolve_layers invalidates without anyone noticing.

Before (kickoff plan)

pub fn derived<K, T>(key: K, compute: impl FnOnce() -> T) -> Arc<T>

// settings key, assembled at the call site:
(repo, wave, lf_home, env_value, sole_harness, remote_env)

// and inside compute, resolve_layers reads them again:
environment()?          // LF_SETTINGS, LF_AGENT, ...
invocation_values()     // --setting, thread-local
default_agent()         // PATH probe
  • The key and the computation each read the outside world. Nothing ties them.
  • What is cached, and by what, is spread over call sites.
  • A hit copies every dependency into the reading. For the catalog that is several hundred facts per ask.
  • The slot keeps an error's message; LoadError::AgentSelection matches at ops/task.rs:2297 and commands/config.rs:268 would stop matching.

After (plan as revised)

pub enum Derived {            // beside `enum Fact`
    Settings { checkout, wave, outside: Outside },
    WaveSetup { checkout, wave, outside: Outside },
    SkillCatalog { repo, home, claude, codex },
}
pub fn derived<T>(key: Derived, compute: impl FnOnce() -> T) -> Arc<T>

pub struct Outside { environment, invocation,
                     sole_harness, home, remote }
fn resolve_with(layers, skill, &Outside)   // reads nothing else
  • Outside is the key and the argument. They cannot drift.
  • Every cached computation and its identity is one list, the way Fact is the list of what is observed.
  • A reading holds a derived value's dependencies by reference. A hit is one insert.
  • LoadError derives Clone (every variant is a String); the slot keeps the error.
  • Three values, not five: the Task agent is a field of the settings value, and placement waits for a sample that shows it.

Considered and passed over

  • Fix the validator and add no cache. validate_value is slow because it deserializes a whole Config per leaf. Fixing that would cut each resolve several-fold with no staleness to reason about. It leaves a parse and a merge per Task per reading and does nothing for the catalog walk, so it does not meet the outcome alone. It is listed below because bare lf commands still pay it.
  • Cache one validated file at a time and merge per call. The cached part would read exactly one file, so no ambient input could reach it, and --setting would need no special case. The merge and final deserialize stay per Task per reading. Safer, slower, and a larger change to a module with pinned semantics.
  • Recompute on every hit in test builds and compare. Tests mostly read without a cache or with a fresh one, so the check would rarely see a hit.

Larger than this Task

FindingWhat it would take
Validity belongs to a file; resolution should be a merge. Today Config.setting_layers keeps raw layers so a resolved value can be resolved again per skill, validating everything each time. A validated-declarations type produced once per layer; resolve_layers splits into validate and merge; ContextBudgets::load and store/placement.rs build validated layers. Then Derived::WaveSetup is unnecessary.
validate_value clones the defaults tree and deserializes all of Config for each leaf. Every bare lf command pays this; nothing here changes it. Validate a value against its own definition's type, or validate a file's leaves in one deserialize and fall back to per-leaf only to name the bad one.
A served read's setting warnings reach only the server's stderr. Warnings become part of the resolved value and of what a reader can show. New behavior.

Questions

  1. What identifies a cached computation?
    1. A closed enum Derived in observe.rs, beside Fact. (chosen)
    2. A generic key per call site, as kickoff had it. observe stays ignorant of settings and skills; the list of what is cached is wherever it is used.
  2. --setting overrides inside a served reading:
    1. Compute inline, never enter a slot. (chosen, kept from kickoff)
    2. Part of the key like the rest of Outside. No special case; an override gets its own slot for 300 s.
  3. Machine placement:
    1. Derive only if the sample after the catalog slice shows it. (chosen)
    2. Derive it now as kickoff planned, a fourth variant.
  4. Validity per file, resolution as a merge:
    1. Its own Task after this one; this Task ships the cache. (chosen)
    2. Do it here instead of Derived::WaveSetup.
    3. Leave it; the cache makes it not matter for served reads.
  5. The per-leaf whole-Config validator:
    1. File it separately; it is the bare CLI's cost now. (chosen, not filed by this review)
    2. Fix it in this Task's first slice and measure before building the rest.
  6. The live sample under 40-agent load needs this branch as the Machine's server. Who runs it, and before or after merge?
