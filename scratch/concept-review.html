Two concrete interactions where HEAD still breaks the model

1. Moving a Task while it is open in Desktop (and starting a new conversation on a remote Task)

A Task is open in Desktop on laptop with its Session pane and Files pane visible. Someone runs lf task move <task> --machine mini (or opens a remote Task and clicks New conversation).

built at HEAD Pane holds a stale client-side location

Task open on laptop: pane.content = .session(id: sid, location: laptop_wt) browser = .browser(taskId, …, location: laptop_wt) workspace.location = laptop_wt; workspace.owner = laptop lf task move <task> --machine mini (Session keeps same sid): plan.list → runtime.owner = mini, reference.workspace = null WorkModel sets workspace.location = nil, workspace.owner = mini → Files follows cleanly: "mini origin.dc5441-…" → Session pane is NOT retired or re-prepared: • openWarmConversations gates on workspace.location != nil • openWarmConversation skips presentSession because pane(forSessionId: sid) != nil (same sid!) • SessionsStore.prepare never updates pane.content.location • reconcileMembership only sees local session.list (sid gone) → _terminal checks surface.workspace == pane.content.location → MISMATCH → renders "Session location unavailable" → strip checks pane.content.location != workspace.location → BOTH Session & Browser strips print stale "repo.dc5441-…" Click "New conversation" on a Task owned by mini: reference.workspace is nil → newTaskSession runs LOCAL `lf task checkout` on the Mac → rogue local checkout + local shell!

Observed live in QA2 (scratch/qa/s5-f5b.png). Files follows the Task; the Session pane, Browser strip, and "New conversation" still behave as if a local checkout location owns them.

One source of truth for Task placement across all four Desktop views. Running shells stay put; everything else follows the owner.

2. Inspecting or opening a remote Session's record from this Machine

A Task runs on mini. Desktop displays the Session's Open here button tooltip (SessionRecord.action.help), or resolves an exact remote Session link through Task-scoped session.list.

built at HEAD Peer's local commands leak through

Write::SessionResume → mini → ssh::prepared_remotely(): • rewrites record.open_argv → `lf open --task … --session … --here` • leaves record.action.help → "View the running conversation here: lf resume b3bc…" (fails on laptop!) • leaves record.outlook.command & status_line → `lf resume …` Read::SessionList { task: Some(issue) } → mini: • returns mini's raw SessionRecords with NO localization: - open_argv has mini's binary path `/home/mini/.local/bin/lf …` - action.help / outlook.command say `lf resume …` - task_ids has mini's local Task UUID (fails Desktop's record.names(task:) on tracker-backed peers with different UUIDs)

proposed One calling-Machine localization boundary

localize_remote_session(record, machine, local_task_id, task): Used by BOTH Write::SessionResume and routed Read::SessionList: • open_argv → [current_exe, "open", "--task" <task> | "--machine" <machine.id>, "--session", <id>, "--here"] • action.help, outlook.command, status_line → replaces peer `lf resume …` with calling Machine's `lf open --task <task>` (primary) or `lf open --task <task> --session <id>` / `lf open --machine <machine.id> --session <id>` • task_ids → includes this Machine's local TaskId when routed for a Task (tracker-backed peers match cleanly)

The biggest mismatch: Desktop panes still guard on a stale client-held location

Slice 3 deleted Desktop's client-side SSH routing and placement guard, and Slice 5 made Files and Shell follow task.runtime.owner. The Session pane, Browser strip, and New conversation action are the last holdouts: Desktop still caches Task/Session location in four places (pane.content.location, workspace.location, preparedTaskWorktrees, and SessionRecord.workspace) and lets them drift when ownership changes. When a Task and its Session move (keeping the same LfSessionId), WorkspacePanesView._terminal compares the new record against the old pane location and prints Session location unavailable beside the stale laptop worktree name — the exact kind of client-opinion failure LOO-1083 set out to end.

Before (HEAD at f28db78cd5)

  • WorkModel updates workspace.owner on move without retiring the old Machine's Session surface or clearing stale preparedTaskWorktrees / Browser location
  • openWarmConversations skips Tasks when workspace.location == nil; openWarmConversation skips updating pane location when pane(forSessionId:) != nil
  • SessionsStore.prepare adopts a prepared SessionRecord without syncing pane.content.location → "Session location unavailable"
  • Browser strip prints stale laptop checkout whenever workspace.location is nil
  • newTaskSession runs local lf task checkout on remote Tasks (creating a stale Mac checkout)
  • Remote SessionRecords keep peer lf resume <id> in action.help / status_line, and routed session.list --task skips localization

proposed After (Slice 6, no wire change)

  • Owner change on a retained Task workspace clears stale preparedTaskWorktrees, retires the old Machine's Session surface, clears stale Session/Browser pane locations, and leaves running ShellTabs on their starting Machine
  • Selected/visible started Tasks (!awaitsStart) warm-open from owner != nil (no list fanout on prefetchConversations)
  • Every Session preparation/adoption syncs pane.content.location via updateSessionLocation (renewing pane incarnation for scripts while preventing mismatch)
  • Task Browser strip omits stale checkout text when Files owns its Machine header
  • newTaskSession on a remote owner runs lf --interactive --task … through entry.newShell (zero local checkout fallback)
  • One localize_remote_session helper rewrites open_argv, action.help, outlook.command, status_line, and local task_ids for both SessionResume and routed SessionList
