The consequential mismatch

Existing failure path

Open → installation readiness fails → Unavailable
Retry → installation readiness again → connect

Work read fails before readiness succeeds
Refresh / reopen watch → installation readiness again

Status::connect keeps its initial flag after preparation fails. ServerLocation.path() caches only a successful result. Both let connection recovery repeat registration.

Proposed correction — not implemented

Open → one installation-readiness attempt
     → connect, or show the failure

Installation / OS enablement repairs availability
Retry / refresh → existing endpoint → same owner / fresh Work

Consume the setup attempt even when it fails. Obtain the endpoint independently of readiness success through the existing authority. Remove installation from the recovery loop; add no persistent retry record or second path resolver.

Counterexample: setup fails before the first connection, then registration becomes possible. Pressing Retry must leave registration unchanged. After installation independently starts the server, that same pane must recover without reopening, replaying input or replacing a newer viewer's claim.

Proposed usage clarification: “Local setup is automatic on first connection. If it fails, use the reported installation or Background Items repair, then Retry. Retry connects; it never installs or re-registers.” Existing usage and skill guidance keep their accepted boundaries.

Keep editing through replacement

  1. Open Desktop. Installation prepares the local server. Desktop connects without a separate setup ritual.
  2. Hold a draft while a Graph runs. Update the installed helper. The server connection drops; the existing execution owners continue.
  3. See “Reconnecting…” in native chrome. The screen stays visible. Copy, Find and scrolling remain available; typing waits for the exact owner's acknowledgement.
  4. Continue on that owner. Automatic recovery preserves a newer viewer's claim. A read-only pane offers Move here for explicit control. Retry repairs connectivity only.

If takeover succeeds but its reply is lost, and another viewer claims control, recovery must leave that newer claim intact. Never replay takeover, typing or an uncertain command.

Earlier signed same-build replacement evidence covers owner, provider, draft and Graph continuity. It predates the namespace cutover. The renamed composition, failed-start recovery, rendered Desktop interaction and Linux replacement still need proof. This review ran no builds or runtime checks.

The server owns admission and delivery. Session owners retain terminal control and lifetime; Graphs retain execution. Drafts, active turns, pending requests and running Graphs already protect their owners.

A paired phone is a client credential. It does not become a worker, move a Task or own its provider. Remote access has separate authentication; turning it off must leave local access and execution intact.

Migration boundary

Local command routes, supervisor entries, Swift names and fixtures now share the server namespace. The old bundled plist remains only to inspect and retire existing registration. The socket address stays stable for live relays. MachineId, machine_id, SSH routing, credentials and owner protocols stay in place.
