The biggest mismatch

"Changes are refused on a copy" is one promise with two keepers. Through the server it is a rule: refused before any command code. Through an lf process on the copy's home (a Desktop pane, a shell tab, a terminal with the copy's env.json) it is an outcome: the command runs until SQLite stops it.

Built

lf task create on the copy, from its log (November 20, 10:36:48Z): resolve_repository, creation_lock, open_store, check_receipt, then file_task ended after 82 ms. No later step was logged and the home holds no tracker request log. An empty creation-locks/ entry stays behind.

So this command did nothing outside the copy before it stopped. That is true of the commands tried (session resume, desktop shell, desktop move, task create, -b default), not of every command by construction.

Not built: one keeper

lf asks copy::sealed_at once at start and refuses a command that changes anything, the way the server does. It needs a list of which CLI commands change things; the server has one (Operation::changes) and the CLI does not.

Passed over for this work: it adds a classification that exists nowhere, to close a door nothing has been seen to walk through. The world's stand-ins and the sealed store are the backstop, and copy_world asserts the pane's sentence.
