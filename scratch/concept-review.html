Do recovery's concepts line up with the code's?

LOO-959, reviewed before any code, 2026-11-17. The area taken: everything that keeps an open Task's work alive on one Machine. That covers the Task conversation (its primary Session), the Task run that moves it (the lf task run / lf ship carrier and the Graph under it), and every existing restarter: the carrier's own retry, restart_ships, limit waits, lazy recover() and start_in_background. It is wider than "add a recovery pass" because the pass would become a fourth owner of "keep the Task going".

Outcome: the plan changed. Three parts of it moved onto concepts the code already has. scratch/plan.md now says what to build.

A person knows four things here: my conversation, my Task is moving, it died and it came back, or here is the one command. The question is whether each of those has exactly one thing behind it in the code.

The biggest mismatch: one action, three owners

"Keep the Task moving after something dies" is one thing to a person. The kickoff plan would have spread it across three places:

Before (kickoff plan)

After (plan as changed)

Why the Auto-Ship predicate goes. The kickoff plan continued a died run only "if continuing cannot approve Auto-Ship", and otherwise offered lf task run. Approval is written in two places only:

  • at run registration, when no interactive step is left. A Task launched that way is already shipping, and restart_ships already carries it.
  • at end (Approval::Route), which a person's lf ship --stop blocks. A continuation reaches end only where the original would have.

A continuation of a run launched with an interactive step ahead still has that step ahead, and stops at it. So the predicate was true in every case but one: an lf -b task run that ran an interactive step headless, then died after it. That continuation approves at launch instead of at end, and -b already hands the Task off. The "offered" branch therefore only appears after giving up. Deleted from the plan: the predicate, graph_processes.continues, "continued once" and the offered state.

Larger than this work

restart_waiting_runs and restart_runs both relaunch a carrier when it is due. They differ only in why: a death with backoff, or a limit that resets. They could be one "run due again at T" record on task_graphs. That would mean moving limit recovery's own table and its readers. It is not needed to make deaths recover, so it is left for later.

Questions

  1. What happens when a moving Task's carrier dies?
    1. It is carried again with lf task run on the ship backoff, and offered after 5 deaths in a row
    2. Kickoff's rule: continue only where Auto-Ship cannot change, otherwise offer
    3. Never continue; always offer lf task run
  2. A continued lf -b task run has interactive steps still ahead. How is it relaunched?
    1. Plain lf task run, which stops for a person at the next interactive step
    2. Remember -b on the run and relaunch headless
  3. Which conversations come back on their own?
    1. Task conversations only
    2. Every managed conversation, Wave and repository ones too
  4. Where do "died / quit / starting again" appear on the wire?
    1. ended and recovery on the Session; Task status names its primary Session
    2. A Task-level conversation object with its own state enum
  5. The shutdown exit-0 risk:
    1. Measure in slice 1; add the holder's "told to stop" marker only if an exit 0 can land
    2. Give the holder a SIGTERM handler now, regardless
