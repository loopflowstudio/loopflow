Do the tracker's concepts line up? Round two

LOO-925 at e5cb52f2f6, PR #1957, reviewed against its base 470da475a1. Same area as round one: how a person's plan travels to and from a tracker. Since then the branch built one action view, Git as a tracker in what people see, lf task sync that always looks, and blocks decided before a request. This page reviews the result as a whole.

What round one fixed

lf repo plan, lf task show .sync and Desktop now read one row type, TrackerActionStatus, with the same phases and a tracker field:

LOO-412  title · queued · Offline
LOO-398  complete · sent, waiting for linear to confirm
LOO-377  title · conflicted · lost: "Offline rename" · linear: "Renamed in Linear"

PlanningSyncChange, adopted_linear, linear_value and --retry-updates are gone. That mismatch is closed.

One interaction: a coworker's rename wins

You rename LOO-377 offline. A coworker renames it in Linear first. You reconnect, the drain sees Linear's newer value, and your action becomes conflicted. Linear's title stands.

You agree with the coworker

Nothing records that. The line stays in lf repo plan and on the Task (Desktop shows it too) until a later save of that same field is confirmed. The only way to clear it is to type their title back: lf task edit LOO-377 --title "Renamed in Linear", which queues and sends a no-op to Linear.

You want yours

lf task edit LOO-377 --title "Offline rename". That works and is what the docs say.

So the common case, where the coworker's edit was fine, leaves a permanent open line per field. Across a repository's history, lf repo plan's "N open actions" stops meaning "N things still on their way". The code agrees: the migration's own comment says conflicted rows "left the queue", but the open read (OPEN in sqlite/planning_sync.rs:18) lists them anyway.

The biggest mismatch: a lost edit is shown as unfinished work

Existing

open = queued | sent | conflicted*
       * until a later save of that field
         is confirmed or conflicted
keep theirs → retype their value, which sends a no-op
put mine back → lf task edit
lf repo plan "N open actions" counts both
Proposed 
open  = queued | sent          (still on its way)
lost  = conflicted, shown on the Task
        until you answer or that field
        changes again
keep theirs → nothing to do; it closes on
              the next change to that field,
              or with one dismiss
put mine back → lf task edit (as now)
lf repo plan: "2 open · 1 lost"

Data stays the same: conflicted rows and conflict_json remain, so the losing value is always there to copy back. What changes is the read and the count. OPEN stops including conflicts, a lost list gets its own section, and a lost row also closes when an event later changes that field (the coworker edits again) or when a person dismisses it. On Desktop that's two buttons on the line: Keep linear's / Use mine.

Counterexamples checked. Could someone miss that they lost an edit? Not on the Task: it stays there until answered. It only stops inflating the queue count. Does Git fit? Yes: a Git loser is the same row with tracker: git, and "Use mine" is the same lf task edit. What does dismiss need in the store? Moving conflicted → retired with error='kept the tracker's value', which is already a phase the table has. No migration.

Smaller things on lines this PR added

  • tracker_actions.provider → tracker in the unmerged migration, and queued_tracker() returns TrackerKind. Provider stays the type for accounts.
  • lf repo plan on Git lists Git's conflicted rows too, the same lines lf task sync prints. Then the docs drop "On Linear and Asana" and the journal copy-back sentence.
  • Header Planning: linear. → Tracker: linear.

Larger than this work

  • lf repo plan doesn't show the plan. It shows the tracker, its queue and Git's destinations. Under the glossary it reads as lf repo tracker (or lf repo sync), with key and journal under it. A CLI rename with docs and Desktop callers; it fits LOO-955.
  • Linear-only words in shared surfaces. lf wave sync says "Refresh … from its provider (Git or Linear)" and "no Linear Initiative", and the docs explain Waves through Initiatives. Asana has neither. LOO-956 (Asana setup) is where those words would change.
  • task.acquisition still names the tracker's copy of a Task in old words. Wire change; LOO-955 or LOO-942.
