Can a Wave’s work still be sent after recovery?

LOO-995 · Decision pass 3 · 23 November 2026 · Branch ca8b46bc20 against 2aa9964894

A Wave and its Project share one lifetime in the plan. A tracker can receive that work later. This review follows a Task from an older chapter through upgrade and reconnect, because those are the moments when the Project saved on the Task and the Project sent to a coworker can diverge.

One Task, two destinations after upgrade

Existing

Before upgrade
billing → November → Task T
        → December
queued create(T, November)

After upgrade
billing → December → Task T
queued create(T, November)
                  ↑ Project deleted

On a temporary Machine initialized by the installed app’s lf, I seeded two started Projects and an unsent Task create under the older one. Running the branch’s complete remove_chapters.sql moved T to December. Its queued action still held November’s ID. The foreign-key check found zero violations.

Proposed

After upgrade
billing → December → Task T
queued create(T, December)

After tracker recovery
December → one issue for T

Translate the destination in the existing request during consolidation. The action keeps its place in the queue, the Task keeps its identity, and the sender can resolve December. An issue already delivered to November gets no move merely because Loopflow upgraded.

Biggest mismatch. The migration updates tasks.project_id, while delivery uses WorkValue::TaskProject inside tracker_actions.value_json. Both providers resolve that saved local ID before sending. Once its Project row is gone, remote_project returns “Project is missing”. Reconnecting cannot repair this reference.

What does “sync this Wave” do?

In a separate private repository bound to Linear, I created billing without a login. Its Project create stayed queued. I cleared only the action’s recorded credential error so a new attempt would be visible, then ran the branch CLI.

$ lf wave sync billing
billing: links no Linear Project; showing local planning (lf wave plan connect billing)
…
Project   billing (local) · started
  create · queued

The command exited 0 and the error stayed empty. The connect receipt directs people to this command for a retry. refresh_status checks the external ID before calling the exchange that could obtain it. In a second fixture with an Asana Team and a seeded, acknowledged Asana link, the same command exited 1 asking for repo.tracker.linear.team.

Existing

Check for a Project ID. If absent, show local status. If present, exchange with the repository’s tracker, then request a Linear inventory for that ID.

Proposed

Use the repository’s selected transport. Exchange once, prioritizing this Wave’s stored Project. Read its link again. Fetch a Linear inventory only for a linked Linear Project. For Asana, use its existing exchange. Show any still-pending create and its recorded reason in the status.

Recovery check. Restore the simulated provider and run the same sync twice. The first call should acknowledge the original create and show the link. The second should show the same remote Project. A busy queue, a still-offline provider and a repository syncing through Git or a hub each exercise a different branch of that promise.

What the previous pass established

Slice 7 set out to make removal release the tracker Project for reuse and keep earlier edits from renaming a newly linked Project. Its simulated-Linear checks recorded one winner from concurrent connects and zero stray Project creates or renames. QA also removed an offline Wave and read its completed Task after its queued work retired. These results cover the earlier recommendation. Successful reconnect against live Linear was outside that QA run.

Counterexamples to keep. A lost reply may mean a tracker already created T under November. Recovery must recognize that same issue before any retry that could duplicate or move it. A pending move to a different, surviving Wave still names its intended destination. On removal, a completed Task that never reached the tracker and whose retired Project has no link stays local. Running sync must respect all three.

Reading every create’s fields at send time would change the meaning of other queued edits and lost replies. That broader queue redesign would require a separate decision about baselines and action order. The two repairs here can use the existing queue and its stored identities.

Questions for review

  2. What should explicit Wave sync do when the Project create is pending?
    1. Attempt it on the configured tracker and show the result (chosen).
    2. Show local status and require another command to send it. This would change the recovery promised by connect.
