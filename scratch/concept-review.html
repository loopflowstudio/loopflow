Area: how a Task goes on without a person: the auto setting, what turns it on and off, what a run does with it, and the review step a person meets before delivery (human-review, to become ship-review). Taken this wide because the Task's claim is about the whole: "ship is shorthand for auto on the Task's Graph". Tan panels are proposed and not built. Everything else exists. The first pass's proposal (auto on is one action) is built and was driven in QA (scratch/qa.html).

Biggest mismatch: ship is a second front door to the run

The Task's sentence is "lf ship turns it on and runs the Graph the way lf task run does". As built, ship_on decides, in the CLI process and before any run exists, most of what the run then decides again: which Graph (and takes it up), who owns the Task, whether a run is live, where to start. Then it hands a --from to the real thing. Each duplicated decision is a place the two can disagree, and the gap between them is real time: a Task that took up a Graph and has no run reads as "starting", so its conversation starts one, and the ship that caused it reports a refusal. QA saw the same gap with two ships at once.

Existing 
lf ship X
  ship_on:            Task open? launchable?
                      take up Graph        ← Task now reads "starting"
                      claim
                      write auto on
                      live run? → report
                      from = waiting step
  carry_task_run:     prepare_task
    start_task_run:   select (refuses a live run)
                      take up (already done)
                      -b: write auto on unless off
                      read auto → through, merges
                      position → Run, carried here
Proposed 
lf ship X  =  lf task run X, asking for auto on
  carry_task_run:     prepare_task
    start_task_run:   live run + auto asked → write on, report it
                      select; auto asked at a waiting
                        interactive step → start at it
                      take up
                      auto asked: write on (lifts off)
                      -b:         write on unless off
                      read auto → through, merges
                      position → Run, carried here

One request type says who is asking for auto (nobody · -b, which an off outranks · a person, which lifts off, with their note), and the run's own take-up writes it. ship_on, ShipStart, graph_for_ship, task_for_auto and live_graph_run go; ship.rs keeps the mark (set, auto_off, starter) and ship_branch_task. "Ship is shorthand" becomes the shape of the code: a run with one field set.

Tested against:

  • Normal. Never-run Task: the run takes up, writes on, runs. Waiting at ship-review: the selection starts at that step instead of after it, because auto was asked for. A bare lf task run there still means "I finished this step".
  • Failure. Two ships at once: the second meets a live run, writes on, reports that run, exits 0. A conversation opening mid-ship sees what it sees for any lf task run.
  • Recovery. Unchanged: a dead run is carried as bare lf task run and reads the mark.
  • Counterexample kept. A ship that fails in prepare_task (no worktree, launch refused) now leaves auto unset, where today it leaves auto on with nothing running. That is the truer result: nothing was turned on that isn't going.
  • Must survive. Done and abandoned Tasks still answer in a sentence; at end nothing is written; off outranks -b; the unowned Task is claimed once, by the run.

Passed over: leaving the two doors and documenting the window (it is rare), and moving only the auto write. The first keeps a refusal QA already hit; the second keeps ship_on's copy of the start choice.

Same pass

  • Stored and wire value stopped → off; AutoState::Stopped → AutoState::Off. One edit in the unmerged migration, the enum, fixtures and Swift.
  • human-review → ship-review, with the goals already written in the plan, and the concept-review skill's "larger than this work" rule tightened.

A separate outcome

  • The auto Graph's name. Renaming it touches graph: auto in people's configs and the catalog.
  • lf task auto off on a Task that never took up a Graph saves nothing, so a later lf -b task run turns auto on. The setting reads as a Task's and lives on its Graph row. Storing it on the Task would close this; nobody has asked to set auto before a first run.

Questions

  2. The stored word: (a) off; (b) keep stopped.
  3. lf -b task run writes auto on: (a) keep; (b) stands in for its own run only.
  4. After auto off, your own lf task run past review: (a) waits at pr land until lf ship, as built; (b) lands, because you ran it.
  5. auto off before a first run: (a) leave, as built; (b) store auto on the Task so it sticks.
  6. The auto Graph's name: (a) leave; (b) file a Task to rename it (to what?).
