The theme choice, built across three surfaces: do the concepts line up?

Area taken: the whole theme choice as PR #2020 now stands against main: the catalogue, the chooser, theme: as one Machine fact read through config.theme {value}, the phone drawing its Machine's theme, and the site generated from Loopflow Light. Round 4's page asked where the choice lives; this page reviews what was built from that answer, with QA round 5 (scratch/qa.html, R5.1–R5.10) in it.

One interaction, walked

Normal. On the Mac, Choose Theme → Fig, Apply. The server writes theme: Fig. The window turns plum; the phone draws Fig the next time it comes forward (R5.4). Works.

Failure: a name nobody ships. theme: Verdigris. Desktop: “No theme named “Verdigris”: keeping Fig Leaf. Fix theme: in …/config.yaml …” and a Choose Theme… button (R5.8). The button fixes it. The phone draws Loopflow's pair (R5.5). Works.

Failure: the server can't answer the question. The Dev app against a 0.16.0 server, which is what #2007 (“Run Loopflow Dev on the live Machine”) makes the normal Dev setup until this ships. Desktop keeps the last good theme and shows config.theme: missing field `path` with the same Choose Theme… button (R5.9). Choosing a theme sends the same request and fails the same way. Nothing on screen says which side to update.

Recovery. Running the branch server: the next file change clears it (R5.9). Nobody would know to do that from the message.

Biggest mismatch: a notice that can't tell a bad choice from a server that didn't answer

This change made the theme a question Desktop asks its server. That added a failure the old file read never had: the server can refuse the question. The store still has one slot for “something is wrong with your theme”, and the banner's one button assumes the person's choice is at fault.

Recommendation (made for review): split the slot by who can fix it. notice keeps what Choose Theme fixes (unknown names, unreadable files). A failed read becomes its own value, shown in the banner without the button. When the server rejects the request's shape, ServerLink names both builds, the mirror of unreadable: “The server (0.16.0) can't read what this Loopflow (0.17.0-dev) asked. Update the older one.” No revision bump and no fallback request shape: the repo carries no old-version support, it says which side to update.

Passed over: bumping the revision (the client sends min_revision 8, so it wouldn't refuse old servers, but nothing would then branch on it without a compat path); quiet fallback to Loopflow's pair on Desktop as on the phone (Desktop would then draw the wrong theme with no word why).
