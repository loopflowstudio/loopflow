The decision

“Use Codex unless this step chooses something else” and “Use Codex everywhere while Claude is exhausted” are different requests. A personal global setting describes where a preference applies; it does not tell us which request it means.

The current rule handles the second request well when a broad DB preference overrides file preferences, but makes the first awkward across sources. A general DB agent: codex defeats even a personal file's step-specific Claude selection. Same-file exceptions already work; this is a cross-source problem.

What other systems do

These are observations from primary documentation, not claims that any tool has Loopflow's complete matrix. The Git examples below were also executed locally.

OpenCode: merge configuration, then use a fallback

Configuration sources merge, preserving distinct keys. A primary agent's explicit model overrides the global model; absent that, it uses the global model. Subagents instead inherit the invoking primary's model when unspecified. Organization defaults, global files and project files participate in config loading. Config, agent model selection.

Implication, inferred from those documented rules: a generic model in a global file and a specific agent model in a project file can coexist. One is the fallback for the other, rather than two competing values for one slot. Its default_agent means the starting persona, such as plan/build; that name is not evidence of a weak-versus-strong harness setting.

VS Code: specificity can outrank source

Language-specific settings beat general settings, including when a user language setting competes with a workspace general setting. Within a language, workspace beats user. Language-specific defaults also sit above general user settings; policy settings have higher authority. Settings precedence.

For LF this suggests skill > general, then source. The counterexample matters: copying the rule literally could make a built-in skill's Claude recommendation defeat Jack's personal Codex default. That consequence must be chosen, not hidden.

NixOS: distinguish the strength of a definition

Normal option definitions outrank mkDefault; mkForce outranks normal definitions. Strength is attached to a definition of the same option, not encoded as a second option name. Merge ordering is a different concept from override priority. Setting priorities.

This is the strongest precedent for Jack's agent versus default_agent idea: say whether a value is a fallback or an override. LF could express that with two agent keys or a general defaults: mechanism. Nix does not settle LF's remaining source/scope/target ordering; it supplies another dimension.

Git: same-key source priority and target matching coexist

Ordinary scalar values use config source order. HTTP settings additionally support URL matching, with longer path matches preferred. Git configuration.

Evidence: config-prior-art-experiments.json. Source order still resolves the same target; a generic key does not erase a specific key. The CLI case warns against assuming “highest source” automatically means “force all targets.” LF's explicit Graph -a must retain its separately accepted force behavior.

OpenSSH: first applicable value, not most specific match

CLI precedes personal config, then system config. For ordinary scalar options, the first obtained value wins. Put specific Host entries before broad defaults; a broad earlier entry can defeat a narrow later one. ssh_config.

This supports source-first control but imposes ordering work on authors. It does not automatically solve “global default plus exception.” Some options accumulate; the scalar rule must not be generalized to every field.

ESLint: authors order the applicable rules

Matching configuration objects merge; later objects win conflicts. A narrow file glob has no inherent authority over an earlier or later broad glob. Cascading configuration objects.

Useful for composing a shared preset and local exceptions. It is an ordered list inside the selected configuration, not a full personal/org authority ladder. Copying this would make ordering another thing LF authors must understand.

GitHub Actions: defaults live outside the step choice

Workflow defaults can be refined at job level, and explicit step settings can override them. The most specific applicable default wins. Workflow defaults.

This makes “all steps use bash except this one uses pwsh” straightforward. It provides a useful graph-authoring model, but does not answer LF's personal versus repository conflict by itself.

Three concrete LF alternatives

All preserve explicit Graph -a across that Graph and conversation-only Session -a. Propagation is separate from precedence. All retain DB > personal file > shared file for competing values at the same source-independent address.

A — current branch. Source > scope > target. Broad preferences can override lower-source exceptions. No distinct weak default.

B — targeted choices with a fallback. Explicit invocation overrides first. Among persisted non-builtin choices, graph occurrence > skill > general; source then scope breaks ties at each target. Builtins are consulted only if no applicable non-builtin choice exists. agent at the root is a fallback, not a blanket override. That explicit builtin boundary is part of this proposal, not VS Code's rule.

C — defaults and choices. Two strengths, with source > scope > target within each. Applicable agent choices beat default_agent values; built-in recommendations are defaults. A personal default_agent: codex can yield to a repository step's agent: claude. A DB agent: codex can temporarily override file choices. This keeps current authority ordering among ordinary choices.

C's generic spelling could be defaults: {agent: codex} instead of a special default_agent field. Do not introduce default_X counterparts for every setting without defining replacement, additive lists and applicability. Both strengths would need equivalent CLI, file and DB inspection/write support where appropriate.

In the table, broad preferences use agent in A/B and default_agent in C. Specific authored choices use agent; the built-in recommendation is weak in C. These are illustrative algorithms, not observed alternative LF behavior.

The fifth row is the hardest tradeoff. “Always use Codex for implement” could mean a usual skill preference that permits per-occurrence exceptions, or a personal override of the project's choices. B picks the former; C can express the latter through authority. Neither wording should be left ambiguous.

Assessment

The evidence favors separating fallback selection from authority. It does not establish one universal precedence ordering. Current LF makes one root agent serve both meanings and the DB's priority makes that ambiguity particularly visible.

B is smaller if personal root agent should always mean a fallback and Graph CLI is enough for forcing. It cannot express an ongoing broad DB force without another mechanism. Jack's temporary Claude exhaustion is evidence that this second use case exists, although automatic recovery in PR2 may reduce it.

C is a credible option if both persistent meanings matter. It preserves the chosen source ordering and makes “default” explicit, at the cost of another concept. Restoring the old default_agent name alone is insufficient: built-in recommendations, skill frontmatter and DB/file values must share the same strength rules, with provenance showing why an ordinary choice beat a default.

Automatic availability routing is separate: neither model should silently rewrite stored preferences when Claude reaches its limit. No per-skill accounts are needed to settle this decision.

Questions for review

  1. Should a personal general Codex preference yield to a repository's explicitly authored Claude step? (a) Yes, it is a default. (b) No, personal authority wins.
  2. Should a personal implement preference yield to a repository's one-occurrence exception? (a) Yes, target specificity wins. (b) Only if marked as a default.
  3. Is a persistent “Codex for everything temporarily” control needed independently of CLI Graph overrides and future limit recovery? (a) Yes. (b) CLI is sufficient.
