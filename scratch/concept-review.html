Pause a Task without giving it up

“i think we need a 'paused' state / action for tasks -- stops the task worker - and ideally e.g. any rust compiling happening becasue of it - , maybe closes the tasks session for now as well, but oesnt unassign”
Existing Committed on base 43e03187 Kickoff Plan Earlier scratch/plan.md at c0cccd63 Revised Plan Updated in scratch/plan.md by this review
Build status: Pre-implementation (no Rust or Swift code written yet). This review audited the kickoff plan against current HEAD, caught five conceptual mismatches, and rewrote scratch/plan.md around one aligned model so implementation starts clean.
Area reviewed: Task execution control & lifecycle — how a person starts, interrupts, pauses, unpauses, auto-runs, moves, and unassigns a Task across CLI, Machine server, Mac, and iPhone, and how that maps to TaskState, TaskSection, TaskActions, recovery loops, Session closure, and OS process teardown.
Why this whole area: pause sits directly across five existing mechanisms (derived state, board sections, interrupt/move teardown, server recovery, and Session departure). Treating it as a standalone table creates contradictions and orphaned builds.

3. Concrete walkthrough: normal path, failure, and recovery

Normal path · Pause one build, keep its neighbor compiling

$ lf task pause INF-123
INF-123 paused (build · implement)
  stopped: Graph run lf_81a, cargo (pid 41202), rustc (pid 41219)
  session: session_a1 closed (thread retained)
  kept:    owner Jack on macbook, worktree, PR #2041

$ lf task list --state paused
INF-123  paused  Jack  build (implement)  #2041  Fix build cache

# Neighbor INF-124 is still compiling untouched.
# Server restarts, wave-operate runs, teammate comments on Linear:
#   → INF-123 stays quiet; Linear comment queues as steer.

# Come back in one command (or two):
$ lf task unpause INF-123 --run
INF-123 unpaused
INF-123 · code from implement running as Graph run lf_94c
  follow: lf task status INF-123

Failure & recovery · Crash mid-pause, draining lf land, unassign

1. Crash between writing hold & killing rustc:
task_pauses.stopping_processes already persisted [(41219, birth)] before the interrupt. Even after the worker exits and reparents rustc to PID 1, status reads “Pausing at build (implement is stopping)”, unpause refuses and names PID 41219, and repeating lf task pause INF-123 finishes stopping it and clears stopping_processes.
2. Pausing during lf land (mutating GitHub):
Operation drains cleanly; no later step starts. Receipt reports draining: pr-land. Workflow bar reads “Pausing at deliver (pr-land is finishing).” Once it exits, Graph exits 130 and carrier settles.
3. Unassigning or moving a paused Task:
lf task unassign INF-123 refuses if processes are still stopping, otherwise clears task_pauses and returns it cleanly to Backlog. lf task move INF-123 --machine mini carries the hold inside MovedTask and writes it before mini’s recovery pass runs.

4. What survives, what changes, and what stays outside this Task

Preserved across pause

  • Task ownership (same person, same Machine)
  • Dirty worktree, branch, commits, and PR (including external GitHub merge state)
  • Graph name and cursor (exact interrupted step)
  • Primary LfSessionId, provider thread ID, history, and queued steers
  • task_auto setting (on / off / unset)
  • Neighbor Tasks, shared sccache daemon, and user shells in the checkout

Stopped / cleared on pause

  • Running Graph, agent step, and attributable descendant build groups (cargo/rustc)
  • Carrier liveness (run_pid/run_died_at) and active agent_limit_recoveries row settled immediately
  • Primary Session’s live provider process (closed via Departure::Paused; terminals receive pause notice)
  • Automatic recovery, steer wakes, and operator runs held until explicit unpause

Outside this Task: Stopping live workers during lf task unassign on a non-paused Task (separate outcome: requires defining whether unassign interrupts in-flight runs).

5. Choices made for review (open questions)

Running headless in a Graph, this review recorded the recommended choices below directly into scratch/plan.md so implementation can proceed. Reply with shorthand like 2b to change any choice.

  1. 1. Should lf task pause only apply to started Tasks, or also unstarted Backlog Tasks?
    1. 1a (Chosen in plan): Started Tasks only (checkout or Graph admitted, including create --run setup). Keeps TaskState::Unstarted withdrawal, awaitsStart, isUnassigned, and Backlog menus clean.
    2. 1b: Allow pausing unstarted Backlog Tasks too (requires separating a stored hold axis from TaskState::Unstarted so Linear withdrawal and Backlog checks don’t break).
  2. 2. How should a person resume a paused Task from the CLI?
    1. 2a (Chosen in plan): Explicit lf task unpause <ID> lifts the hold without running; lf task unpause <ID> --run unpauses and runs in one command. Plain lf task run and lf resume refuse while paused so parent agents, cron operators, and steer wakes can’t accidentally undo a pause.
    2. 2b: Let direct lf task run <ID> and lf resume <ID> automatically lift the pause when invoked directly, relying on operator prompts and recovery checks to respect pause.
  3. 3. What should happen to the Task’s primary Session on pause and unpause?
    1. 3a (Chosen in plan): Close the live provider on pause with Departure::Paused (retaining thread & history); on unpause, let the Machine server bring it back automatically unless the person had already quit it beforehand.
    2. 3b: Close on pause and leave it closed after unpause until the person explicitly runs lf resume or clicks Open.
    3. 3c: Leave the primary interactive Session running during pause and stop only the headless Graph worker and its builds.
  4. 4. Where should paused Tasks live on Mac and iPhone?
    1. 4a (Chosen in plan): Separate TaskSection::Paused outside Working and Backlog, surfaced via TaskList.paused on iPhone and a discoverable Paused filter/section in Mac’s sidebar and Wave board.
    2. 4b: Keep paused Tasks inside Working (dimmed / sorted to the bottom with a Paused badge) so Mac’s sidebar needs no new section.
