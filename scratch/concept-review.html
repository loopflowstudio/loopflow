Who can start an agent, and what it is told about who is reading

Concept review for LOO-1119, "Remove the Discord bridge", at 200d4e486a against base 472bacbd64. Everything the plan lists is built and committed; this page replaces the review written at e577962da2.

The area taken: the bridge was the one place a message from someone other than the Machine's own person started an agent. The review covers that launch path with the whole change in it: the command, the prompt's idea of whether someone is reading, a Wave's own config keys, the secrets lf strips before starting an agent, and the docs that named any of it.

One interaction, before and after

Before: a message in the channel

  1. Someone types in the bound Discord channel.
  2. lf discord serve product polls and sees it.
  3. A headless agent starts for the Wave with permissions skipped.
  4. Its final answer is posted back.

Failure: the someone is any non-bot member. Nothing asked who they were; guild_id was never read. Recovery: none short of stopping the process.

After: no message can do that built

  1. lf discord serve product prints "skill or graph not found: discord" and exits 2 (run today, this checkout's build).
  2. An agent starts only from this Machine's account: a terminal, Desktop, a Task Graph, or an SSH peer that already holds that account.
  3. A checkout that still has a chat: block in its Wave config runs as before, with no warning.

What survives the merge: the bot token. It still works, it is still in Doppler loopflow/dev (checked today, names only), and lf no longer strips it from an agent's environment. Row 9.

Deleting was the smaller and truer fix than an allowlist: lf has no type for who asked, and with every remaining launch coming from the account's own person it needs none. What the removal leaves in view is smaller and inside the code: the yes-or-no "is someone in this conversation" now exists three times.

The biggest mismatch: one yes-or-no, three types

At the base, Surface looked like a different idea from run mode: it had six names, some of them places (Mac, iPhone, IDE). Reduced to what it does, it is run mode. One function shows all three:

How the harness is driven 
// harness/mod.rs:230
enum Mode { Interactive, Headless }
// from LaunchKind::mode()
What the prompt says 
// run.rs:471, 508
let is_interactive =
    mode == Mode::Interactive;
let surface = if is_interactive {
    Surface::HumanPresent
} else { Surface::Headless };
What the Session records 
// run.rs:647, 692
begin_process_runtime(&built,
    "tui", …)      // interactive
begin_process_runtime(&built,
    "headless", …)

No launch sets them differently. The other places that choose a Surface pass the constant Headless (ops/sync_execution.rs) or compare against it (agent/availability.rs, to recognise a worker).

Now built

pub enum Surface {
    HumanPresent,
    #[default]
    Headless,
}
impl FromStr for Surface {
    type Err = Infallible;   // any word parses
}
// lf-prompt --surface headless|human-present

Plus the conversion in run.rs, and a second spelling (human-present) for what every doc calls interactive.

Proposed proposed

pub enum Surface { … }
impl FromStr for Surface { … }
impl Mode {
    pub fn instructions(self) -> &'static str {
        match self {
            Self::Headless => SURFACE_HEADLESS,
            Self::Interactive => SURFACE_HUMAN_PRESENT,
        }
    }
}
// lf-prompt --mode headless|interactive
// Clap rejects any other word

The prompt takes the Mode the launch already has. The two instruction files and their text stay as they are.

Normal path: an interactive launch gets human-present.md, a headless one headless.md, as now; the rendered prompt is byte-identical, so the golden cases do not move. Failure: a misspelt mode on lf-prompt is an error naming the two words, where today it is a headless prompt. Recovery: nothing is stored in this type, so there is nothing to migrate and the change can be reverted whole.

The counterexample that would break it: a launch driven one way and told the other. The nearest candidate is a held terminal nobody is viewing (a work session "independent of its viewer"): it is driven interactively and told "someone is in this conversation", today and after. If that ever wants its own instructions, or the iOS app wants phone-specific ones, a prompt type comes back on that day with a third value, which Mode could not carry. No such launch exists now.

Passed over: keeping Surface as the prompt module's own word, so prompt does not name a harness type. Both live in loopflow-execution and prompt::process already builds harness configuration, so the separation is not real. Also passed over: typing the recorded surface string in this change. It is a stored column read by replay and Session lists; giving it a type is right and is its own outcome separate: a Mode-typed field on SessionCaptureSpec that writes the same two strings, no migration, about thirty literal sites.

Size of the proposal: every file it touches but two is already in this branch's diff (prompt/mod.rs, prompt/process.rs, run.rs, lf-prompt.rs, context_tests.rs, golden_prompt.rs, plus availability.rs and sync_execution.rs), and the two lf-prompt callers change a flag name. Reversible; nothing here ships a format.

Questions

1. Should "is someone in this conversation" be one type or two?

Nothing a person sees changes: an agent is told "someone is here" or "nobody is here", exactly as now. The difference is for whoever reads or extends the code, and for a developer running lf-prompt, who would type --mode interactive and get an error on a wrong word.

  • 1a. Recommended. One, in this change: the prompt uses run mode, and Surface is deleted. The branch already rewrote this type and touches nearly every file involved.
  • 1b. One, as its own Task after this lands, so the PR that removes the bridge stays about the bridge.
  • 1c. Two: keep "surface" as the prompt's word, because a phone or an unwatched terminal is expected to want its own instructions soon.

2. When does the Discord bot's token get revoked?

Unanswered since the first review, and still the one thing here that cannot be undone. Until it happens, a working bot token sits in Doppler loopflow/dev; any agent started under that config can read it, and any older installed lf can still run the bridge with it.

  • 2a. Recommended. Before the merge: revoke the token in Discord, delete the secret from Doppler loopflow/dev, remove the bot from the guild. The PR lists them as done. Nothing still needs the token.
  • 2b. After the merge, as the plan has it: the PR body lists the three steps as still to do.
  • 2c. Keep the bot and its token for some other use. Then lf should go back to stripping the name from agents, and the Task's "no Discord name in the code" no longer holds.
