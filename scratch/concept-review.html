Who can sign as Loopflow

Concept review of the LOO-1117 plan, before anything is built. Branch jack/loo-1117-signing-and-notary-secrets-are-unreachable-from-any-branch-but-main at 238fbcce1c: the plan and its questions are committed, no workflow has changed.

The area taken: every place the Developer ID identity and the notary key live, and every holder that can use them: Doppler loopflow/prd, the cron host that signs releases, and GitHub Actions that signs each green main commit. The plan covers the third. The other two decide what the third is worth, so they are on the page.

exists today proposed by the plan ★ proposed by this review

The verdict in four lines

  • The plan's mechanism is right and small: a signing environment whose branch policy is main, named by the two jobs that sign or ask Apple. Build it.
  • Its outcome sentence, "A branch cannot sign", is true of branches and not of the actors the security review named. Every agent Session and every rental holds an admin token that can widen the policy in one API call, and every local agent can read the p12 straight from Doppler.
  • The dependabot environment is planned for a workflow that open PR #2054 (LOO-1120) deletes, along with its secret. Drop it from this plan.
  • The one check of the real settings, scripts/check_actions_secrets.py, has no caller after ship day. Give it one or do not write it.

One interaction, walked

Normal path proposed

A PR merges. CI goes green on main. Packages (main) starts from workflow_run, so its ref is refs/heads/main. desktop-app names signing; the policy matches; the job reads five secrets, signs, notarizes, uploads Loopflow-dmg. lf install --dev installs it. Nobody sees a difference from today.

Failure: a branch tries proposed

Something with push access pushes a branch with an edited release-loopflow.py, or a new on: push workflow. A job that names signing is refused before a runner starts. A job that names no environment reads empty strings, because the repository holds no secrets.

Failure: Apple rejects the key exists

The morning check goes red and opens "Notarization is failing". The fix is in Doppler, then one copy command, now with --env signing. The next green run closes the issue.

Recovery: rebuild a package by hand proposed

workflow_dispatch leaves main-packages.yml. A failed or expired build comes back with gh run rerun <id>, which reruns the same commit on the same ref. Simpler than today: one fewer trigger and no || github.sha fallbacks.

The counterexample that breaks the walk is in the second box. "Something with push access" is, today, never only push access. That is the biggest mismatch below.

The biggest mismatch: "a branch" is not who signs

The security review named three attackers: "an agent Session under the maintainer's gh, the token copied to a rental in finding 3, a prompt-injected Task". All three hold the same admin token (gh repo view reports ADMIN for it), and two of the three run on the laptop, where AGENTS.md tells every agent to fetch secrets from Doppler.

Before: what the plan says proposed

"A branch cannot sign." Demo: a probe branch is refused. Admin access is one paragraph under "What it does not stop".

After: what this review recommends ★

"Push access is no longer enough to sign; changing who can sign is a settings change, and it is noticed." Same mechanism, plus the settings check gets a daily caller, and LOO-1118 is named as the Task that moves rentals from the middle row to the top one.

Nothing here argues against building the environment. Scoped tokens are worthless while repository secrets exist, so this is the first step whichever order the rest comes in. The change is in what the Task claims and in closing the one loop it leaves open.

This work

  1. Drop the dependabot environment. The plan keeps one environment, five secrets, two jobs. dependabot-auto.yml is untouched here, so the two PRs do not conflict. "gh secret list prints nothing" becomes true when LOO-1120's secret deletion is also done; this Task's own check is that none of the five signing names is a repository secret.
  2. State the outcome by holder, as in the table above, in the plan and in .github/CI.md.
  3. Probe before the merge. The PR branch already carries environment: on notarization-check.yml, and that workflow has workflow_dispatch on main. Once the environment exists, gh workflow run notarization-check.yml --ref <this branch> must be refused. That settles deployment: false with the real thing while the repository secrets are still there to fall back on.
  4. Give the settings check a caller (question 3).

Separate outcomes

  • Agents stop holding admin on the repository. LOO-1118 does it for rentals. Local Sessions would need the same: a token that can push and open PRs and cannot edit settings. Without it the middle row stays amber.
  • The p12 and notary key leave the laptop's reach. They would live where only the cron host and the GitHub environment can read them: a Doppler config the maintainer's everyday login does not open, or no Doppler copy at all once both consumers are loaded. Until then the bottom row stays red, and no GitHub setting changes it.

Questions

1. What should this Task promise?

After it ships, a token that can only push cannot get anything signed. A token with admin, which is what every agent and rental holds today, still can, with one extra step that leaves a log entry.

1a. Recommended. Ship it with that promise, written by holder. Rentals move to "cannot" when LOO-1118 lands; local agents wait for their own Task.

1b. Ship it as "a branch cannot sign" and leave the admin path as a paragraph.

1c. Hold this until agents stop holding admin, and ship both together.

2. Does the Dependabot merge token get its own environment?

PR #2054 removes Dependabot's workflow, and its plan revokes the token.

2a. Recommended. No. This Task covers the five signing secrets; LOO-1120 deletes the sixth. If #2054 stalls, the token stays a repository secret a branch can read until it lands.

2b. Yes, as planned, so the repository is empty of secrets from this Task alone, whatever happens to #2054. Costs an environment, a workflow edit that conflicts with a deletion, and a GitHub behaviour nobody has confirmed.

3. Who notices if the signing settings change later?

The settings are the protection. Someone, or something holding the admin token, could add a branch to the policy or put a secret back at repository level. Today nothing would say so.

3a. Recommended. The daily release on the cron host checks them in its preflight, beside the checks it already runs (gh auth status, the keychain identity). A changed setting stops that day's release with a message naming the difference.

3b. Nothing checks. The commands go in .github/CI.md for the day it is set up, and the script is not written.

3c. As planned: the script exists and a person runs it when they think of it.

4. Rotate the signing identity?

The secrets were readable by anything with push access from 2026-10-30 to today. The one branch run on record is the feature's own (run 41111152406). Runs of branch workflows since deleted were not counted.

4a. Recommended. Rotate the notary API key only. It is a new key in App Store Connect and one Doppler edit; nothing already shipped is affected.

4b. Rotate nothing.

4c. Rotate the certificate too. Check first what revoking the old one does to DMGs people have already downloaded.

5. Delete the two unused environments?

dev holds one webhook secret from February for a service that no longer exists in the repository. pypi is empty.

5a. Recommended. Delete both.

5b. Keep dev; something outside the repository still uses that webhook.

6. Was the old Doppler token revoked?

DOPPLER_TOKEN_PRD is already gone from the repository's secrets, and Doppler lists no service tokens for prd now. Whether the token that secret held was one of those cannot be read back.

6a. It was revoked. Nothing to do.

6b. Not sure. Then Doppler's activity log is the place to look, and that is a person's login.
