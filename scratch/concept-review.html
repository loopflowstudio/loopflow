A Wave is one Project — full review after slices 1–6

LOO-995 concept review of the branch at 43d899d4ee against its base 2656258abf (2026-11-23). Slice 6 fixed the premature createProject on connect, switched Wave lifecycle sync to ActionOwner::Project, renamed the Desktop Project sheet to singular, cleaned up KR/metric docs, and moved named-Project lookup ahead of adding a new Wave.

Area taken: a Wave and its one Project across the whole lifecycle (create, connect to an existing or new tracker Project, rename, Task create and move, remove, re-connect after removal, store upgrade) and every surface that reads or describes it: storage, the outbound tracker queue, inbound tracker ingestion, wire DTOs, CLI, Desktop and docs. Walking the full remove → reconnect and rename → connect lifecycles caught two live mismatches in how projects.external_project_id and queued Project actions behave across link changes and Wave removal.

Two concrete interactions, as built — and where they break

1. Remove a linked Wave, then reconnect its Linear Project (or sync an issue in it)

# Wave "billing" links Linear Project "Billing" (ext-1).
$ lf wave remove billing
# Open Tasks move out; completed Tasks stay in history.
# Linear Project "Billing" stays in Linear untouched — no live Wave links it now.

# Path A — reconnect "Billing" to a new Wave later:
$ lf wave plan connect payments 'Billing'
  1. connect_async finds "Billing" (ext-1) and validates its Team.
  2. connect_async sees "payments" does not exist yet → calls add_local():
     Wave "payments" is registered and .lf/wave/payments is committed on main.
  3. link_wave_project_in → project_accepted_planning checks:
       SELECT id, wave_id FROM projects WHERE external_project_id = 'ext-1'
     It hits the RETIRED "billing" Wave's Project (UNIQUE on external_project_id).
  4. Fails with: "Project ext-1 changed Wave ownership"
     AND leaves the newly added Wave "payments" behind in the store and Git
     (whose own Project create will go out on the next drain).

# Path B — same orphan-Wave failure when "Billing" is linked to a LIVE Wave:
$ lf wave plan connect payments 'Billing'      # while live Wave "billing" holds it
  Same: add_local() registers and commits "payments" BEFORE link_wave_project_in fails.

# Path C — coworker files LOO-99 in "Billing" after "billing" was removed:
  Team delta (tracker_events.rs:219): waves list excludes retired Waves → skips LOO-99.
  lf task sync LOO-99 (linear.rs:777,880 → linear_events.rs:425):
    project_by_tracker_id & ACCEPTED_WAVE_PROJECTS ignore w.retired_at
    → imports LOO-99 into the REMOVED Wave "billing".

2. Rename a Wave before linking it to an existing Linear Project

# Connected repository, offline or logged out.
$ lf wave create billing                 # queues create(name="billing") on proj_<uuid>
$ lf wave rename billing payments        # queues field(project_name="payments") on proj_<uuid>

# Log in and link "payments" to an existing Linear Project "Customer Billing":
$ lf wave plan connect payments 'Customer Billing'
  1. link_wave_project_in (sqlite/linear_events.rs:77-81) retires ONLY kind='create':
       WHERE project_id=?1 AND kind='create' AND phase='queued'
     The queued field(project_name="payments") action stays phase='queued'.
  2. project_accepted_planning → reconcile_in sees the queued project_name action,
     rebases it onto "Customer Billing", and overlays "payments" back over Linear's name.
  3. Next drain sends projectUpdate(name="payments") to Linear:
     connecting to an existing Linear Project silently renames it.
  (Same when relinking an empty Wave from Project A, renamed offline, to Project B.)

Biggest mismatch: projects.external_project_id conflates a live Wave's active tracker link with a removed Wave's history, and link_wave_project_in carries old queued edits onto the newly linked Project.

In the product, removing a Wave stops Loopflow from linking its Linear Project (so new issues stay out and another Wave can link it later), and linking a Wave to an existing Linear Project adopts that Project as-is without leaving a stray Wave on failure. In the code, retired Waves still match project_by_tracker_id and ACCEPTED_WAVE_PROJECTS, block re-linking via the unique column, and link_wave_project_in retires only kind='create' while connect_async runs add_local before checking whether another live Wave already links the target Project.

Recommendation (Slice 7)

Now (existing)

// sqlite/children.rs:1326
SELECT ... FROM projects WHERE external_project_id=?1
// matches retired Waves too!

// sqlite/linear_events.rs:425 (ACCEPTED_WAVE_PROJECTS)
JOIN waves w ON w.id=COALESCE(?4,l.wave_id) AND w.repo=p.repo
// no w.retired_at IS NULL!

// sqlite/linear_events.rs:77 (link_wave_project_in)
UPDATE tracker_actions SET phase='retired', ...
WHERE project_id=?1 AND kind='create' AND phase='queued'
// leaves field(project_name) queued; fails on retired holder!

// ops/linear.rs:646 (connect_async)
validate_project_ownership(&project, &wave, &ctx.team_id)?;
// does not check live Wave holder before add_local()!

After proposed

// sqlite/children.rs
// project_by_tracker_id(): JOIN waves w ... AND w.retired_at IS NULL
// (observed_task() keeps a separate lookup or raw external fallback so a
//  lost task_project=None reply after removal never falsely confirms!)
// tracker_states_in(): skip i.project_id != p.external_project_id
//  when pw.retired_at IS NOT NULL (keeps retired completed Tasks Available).

// sqlite/linear_events.rs
// ACCEPTED_WAVE_PROJECTS, observe_order, attach_in item join:
//   filter w.retired_at IS NULL.
// link_wave_project_in(): when changing link:
//   - refuse if another LIVE Wave holds project.id (naming its slug)
//   - refuse if any action on own is phase='sent' (or create conflicted)
//   - clear external_project_id=NULL on any RETIRED Wave holding project.id
//   - retire ALL phase IN ('queued','conflicted') actions on own.

// ops/linear.rs (connect_async)
// After validate_project_ownership(), before add_local():
//   if a DIFFERENT live Wave already links project.id, return error naming it.

Counterexample tested and kept: What if Task T moves out of Wave billing during lf wave remove billing, its field(task_project = None) action is sent to Linear, the reply is lost (phase='sent'), and Linear never applied the move (still reports project_id = Some(ext-1))? If observed_task() (ops/tracker.rs:386) calls the live-only project_by_tracker_id and maps None to WorkValue::TaskProject(None), it would compare TaskProject(None) == TaskProject(None) and falsely confirm the lost move. Keeping a raw-table lookup (or falling back to Some(external) when unlinked) in observed_task() prevents false confirmation while still matching the pre-removal baseline so the drain resends cleanly.

Second counterexample tested: Reclaiming external_project_id from a retired Wave's Project clears external_project_id on that historical row. Without a guard in tracker_states_in (sqlite/children.rs:1485), historical completed Tasks left in that retired Wave would flip from Available to Invalid because i.project_id IS NOT p.external_project_id. Checking pw.retired_at IS NULL on the membership comparison keeps completed history Available.

Larger than this Task (stated plainly, not built here):

  • Queued create field snapshots: tracker_actions.value_json snapshots a Task's fields at enqueue so retire_wave_in patches task_project via json_set. Reading live fields at send time is a tracker-drain redesign of its own.
  • Desktop's Project sheet vs inline Objective detail: BacklogView's title line already shows WaveHeaderProject and its Objective › disclosure already shows WaveProjectView; the ··· → Project menu opens WaveProjectSheet with the same view (also used by historical Project references). Dropping the sheet once historical Project references are retired is a small Desktop UI pass.
