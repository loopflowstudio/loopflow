Waves, Projects and Tasks without chapters

Area reviewed: how work is grouped — a Wave, its Projects, their Tasks — and everything that stood on "the Wave's current Project": selection, activation, the rollover, KRs, metric targets and live metrics, in the CLI, Desktop, agent context and Linear/Asana sync. Nothing is built yet; this reviews the plan in scratch/plan.md against the code on the branch and one saved store.

One interaction, today and after

Today (main)

$ lf wave create billing
  # makes a Project named "billing", marks it current,
  # records an "activation" owned by this process,
  # sends projectCreate to Linear
$ lf task create --wave billing 'refund flow'
  # asks waves.current_project_id
$ lf task run LOO-12
  # refused unless the Task's Project is the current one
  # and In Progress

Failure: Linear is down during create. The Wave reads "Preparing Project…", then "No Project selected yet"; Tasks cannot be filed in it. Recovery is a retry button in Desktop or lf wave create again, which has to find the unfinished project_transitions row and resume it.

On the store measured, 45 of 62 live Waves have no current Project.

After (plan, as revised by this review)

$ lf wave create billing
  # a Wave row and .lf/wave/billing/. Nothing else.
$ lf task create --wave billing 'refund flow'
  # the Wave has no open Project: one is made, named
  # "billing", in the same transaction
$ lf task run LOO-12
  # runs. No Project check.

Failure: Linear is down. The Task and Project are saved; their creates sit in tracker_actions and go out on a later drain, Project first. Nothing is "preparing" and nothing is retried by a person.

Recovery from the wrong Project: move the Issue in Linear; membership is mirrored back.

The biggest mismatch: where a new Task lands

The plan removes the stored, visible, settable "current Project" and replaces it with a computed rule that no surface shows. A Wave connected to an Initiative holds every Project under it, so anyone starting a Project in Linear can change where lf task create --wave files the next Task, and the command says nothing.

Plan as written

$ lf task create --wave billing 'refund flow'
LOO-12 refund flow

Which Project? Newest started by local created_at. Not printed, not in lf wave status.

Recommended, now in the plan

$ lf task create --wave billing 'refund flow'
LOO-12 refund flow · in Project Refunds Q1

Same rule, one function, and the command names the Project whenever the Wave has more than one open. With one open Project it prints what it prints today.

Why keep the rule and not a stored default: both steers remove "the single current slot on a Wave". Why "newest started": on the store measured it answers the old current Project in 17 of 17 Waves that have one; "oldest started" answers it in 15. 22 Waves have one open Project, 5 have two, 1 has three.

Counterexamples kept: a by-name rule ("the Project named for the Wave") breaks when someone renames it in Linear, and the next Task would make a duplicate. "First in the Wave's order" follows the tracker's rank, which says nothing about new Tasks. Refusing when several are open adds a precondition to the most common command.

What the review changed in the plan

  1. Creation and move name the Project joined when the Wave has several open; the rule is one storage function, new_task_project.
  2. Tracker export of a new Project keeps uncreated and swaps its test from project_transitions to the Project's plan_stamps row. An unstamped Project counts as made here, which also settles the Project the released lf made offline and never exported.
  3. A section on what starts and ends a Project, checked against the second steer: tracker status both ways and abandon stay; nothing on the removal list ends a Project. Acceptance now completes a Project in the stand-in Linear and checks the next Task goes elsewhere.
  4. "Project history" becomes "Projects"; the CLI line drops "current" and "historical".
  5. ops/project.rs also holds wave_graph, WaveGraph and GraphDefault, which stay and move beside scope_graph_default.
  6. The contract's export names projects.krs, since saved Projects hold KR text.

Larger than this work

A Wave without a tracker still costs a Project. The brief's complaint is that "a small group of Tasks costs a Project". After this change the cost is silent, not gone: the first Task in a Wave makes a Project named for the Wave, and with Linear connected that sends a projectCreate. Removing it means a Task can belong to a Wave directly (tasks.wave_id), with Project membership optional; every read that walks Task → Project → Wave changes, and so does what an Issue with no Project under an Initiative means in Linear. The first steer rules this out for this Task.

No command completes a Project without a tracker. True on main too. Without Linear or Asana, the Project made for a Wave stays started for good unless abandoned. If Projects that end are wanted without a tracker, that is one command and its docs.

Questions

  1. A Wave has several open Projects. Where does a new Task go?
    1. The newest started one, and the command names it. (in the plan)
    2. The first started one in the Wave's order.
    3. Add --project to lf task create now and require it when several are open.
  2. A Wave with no tracker gets a Project row on its first Task.
    1. Keep: a Task reaches its Wave through its Project. (in the plan, per the steer)
    2. File a follow-up for Tasks that belong to a Wave directly, Projects only where a person or a tracker made one.
  3. KR text exists in 47 of 64 saved Projects and stops being shown.
    1. Leave it in Linear's content and the leaving column; the contract exports it. (in the plan)
    2. Append each Project's KR text to its description once, so it stays readable in lf.
  4. lf wave edit-project goes with update-project and plan bind, so a Project's name and summary are edited only in the tracker.
    1. Remove all three. (in the plan, as the brief lists them)
    2. Keep edit-project: it names a Project by id and never depended on the current one.
  5. Ending a Project without a tracker.
    1. Not in this Task. (in the plan)
    2. Add one command that completes a Project, in this Task.
    3. File it as its own Task.
