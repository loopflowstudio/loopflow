Pasting into a Session whose view can go away

Area taken: everything between a person's keyboard and a held provider's prompt — typing, pasting, leaving with Ctrl+], a second view, and what happens to a half-sent paste. LOO-912 (PR #1944, merged 2026-11-15) lives here; this reads the area as it stands on origin/main at 891d9a9b92, after #1954 moved it into loopflow-execution and a later change let every view type.

result The paste model holds. Nothing in it needs rebuilding. Four smaller things around it do not line up, and none belongs in the merged PR; they are listed as separate outcomes below.

second pass Reread after QA drove view loss, a second view and a server kill through the installed lf on a private Machine (qa.html). All three closed the paste and the next keys submitted, matching the walk below. The revision and log claims were rechecked against the tree and still hold. QA used a stand-in for the provider, so the last row of the counterexamples stays open: real Codex and Claude parsers were not reached.

Counterexamples tried against it, and what happened:

CounterexampleOutcome
Drop the tracking: always write ESC[201~ when a view leaves.Fails. A shell in cooked mode, or a provider outside a paste, receives a stray sequence on every detach. The tracker is what makes the close exact. It stays.
One tracker at the holder only, since it is the last hop.Fails. The holder cannot see which view wrote, and after it closes a paste the server's unsent tail would arrive as typed keys, with newlines submitting. Each hop that can lose its upstream needs its own count.
Queue cleared on a write error while the tracker keeps counting.Holds. For a held terminal the writer only reports "would block"; the holder closes on loss and the Source restores framing.
Old and new writer connections overlap at the holder (state is per terminal, not per connection).Holds. The server drops the old socket before it connects the new one, so the close precedes the restored start.
Server killed mid-paste while the view stays; the view's terminal never sends the paste end (QA, 2026-11-21).Holds. The surviving view still counts an open paste, so after reconnecting it frames later typing as pasted. Only a driver that omits ESC[201~ does this; a terminal always sends it. The count is doing what the bytes say.
Paste tail sent while no server is up (QA scenario 3).Holds, with a loss that predates this work: the tail is discarded (reconnect_held: "What is typed meanwhile is discarded"). The paste is closed and the next keys submit.
The provider's own parser sticks while lf's count says "closed".Not covered, and cannot be from here. See the biggest mismatch.

The biggest mismatch

The product concept is "my keys stopped landing"; the code has no trace of ever having dealt with it.

The repair closed every path lf could lose a paste end on. It never learned which one lost LOO-904's. If the symptom returns, the first question is whether lf believed a paste was open and closed it, or believed nothing was wrong. Today that cannot be answered: the close is a debug line with no terminal named, written by whichever of two processes happened to do it, and the installed build's log holds none.

Existing

// transport/input.rs
tracing::debug!("closing an interrupted terminal paste");

No terminal, no cause, below the level lf.log keeps. A recurrence starts again from process samples and a hand-sent ESC[201~.

Proposed not built

// at each of the four call sites, which know the cause
info: closed an unfinished paste
  terminal=b30e03b7… cause=view-left
  // or another-view-typed, detached, writer-lost

Paste::finish returns the bytes and stops logging; the caller, which knows the terminal and why, writes the line. It fires only when a paste was cut, so the log stays quiet.

With that line, a stuck Session whose log shows a close is a provider parser problem, and one whose log shows none is a path lf still does not see. Either reading is a new Task with a place to start. Passed over: a "paste open" field on the holder's terminal listing, and a command that sends a paste end by hand. Both are new behavior for a symptom not seen since the merge.
