Do recovery's concepts line up with the code's?

LOO-959 as built, 2026-11-17. This covers slice 1 (commit 24f32b1d8d) and slice 2's uncommitted work in the tree. The live implement pass is still writing slice 2. The earlier version of this page reviewed the plan before any code; this one replaces it.

It also includes the carrier that keeps the Task moving, and LOO-953's liveness columns, which the pass is meant to read. A person knows three things here. My Task has a conversation and it's there. I quit it, and it stays quit. It died, and it came back, or here is the command. The first line above is the surprise: a conversation's first start now runs through "recovery", and counts as recovery attempt 1.

The biggest mismatch: "recovery" is the normal path now

Slice 2 did what the earlier review asked for: one rule decides what should be running, and the first start goes through it. That was the right move, and it makes the old name wrong. To a person there is no recovery. Their Task has a conversation, and it is there unless they quit it. Every name in the code still describes the exception:

As built

server/recovery.rs          watcher: settle + start
RecoverableConversation     includes never-started
recoverable_task_conversations()
record_recovery_start()     first start = attempt 1
agent_sessions
  .recovery_attempts        starts since a turn
  .recovered_at             last start
  .recovery_failure         last start's error
log: "Task conversation started" (attempt 1)

proposed

server/recovery.rs          keeps the name: it settles and restarts
ConversationToStart         a Session that should run and doesn't
conversations_to_start()
record_conversation_start()
agent_sessions
  .starts_since_turn        what it counts
  .last_started_at
  .start_failure            "no PTY left: 511 in use"
Session wire: start {attempts, next_at, gave_up, failure}

Why it's worth doing now: the three column names go into a migration. Once that migration is on origin/main it can't be changed; renaming later means an expand-and-contract migration. Each name would also appear in the DTO fixtures and in Swift in slice 4. Today it is one find-and-replace on an unmerged branch. The wire name follows: the plan's recovery {attempts, next_at, gave_up, failure} becomes start {…}, and it holds for a first start that fails ("claude is not installed") as well as for a restart.

Counterexample to keep: the reset on yielded. The rename doesn't fix it. Before the counter can go back to 0, check whether record_native_turn(yielded=true) fires when a resumed Claude starts, with nobody typing. If it does, reset on a turn that contains a prompt the person submitted (a session_events user turn after last_started_at) and not on the yield. This is the one place where the failure path, not the names, decides whether the feature is safe.

Smaller, already in the plan's reach

Quit reads the row being deleted. Fixed on the stack: when LOO-953's Session columns land, recoverable_task_conversations reads s.agent_exit_code, s.agent_ended_at and s.agent_pid, and drops both processes joins. Until then the query is what 953 has to rewrite, and the plan should say so in slice 1's "left" list, not "reads through the seam".

One counter for carrier restarts. LOO-953 gives task_ship_events and task_graphs each their own carrier pid. Slice 3 could count restarts on whichever row names the carrier, with one reset (ship_progressed's rule) for both. That would replace count_ship_restart rather than sitting beside it.

Questions

  1. Naming the normal path.
    1. Rename now, before the migration merges: starts_since_turn, last_started_at, start_failure, and the wire field start {…}.
    2. Keep "recovery": the first start through the pass is an implementation detail.
  2. What resets the attempt count.
    1. A turn the person submitted after the last start (proposed).
    2. Any yielded, as built, once a check shows a resumed provider doesn't yield at startup.
    3. Never reset: 5 deaths over the conversation's whole life, then lf resume.
  3. Carrier restart counting in slice 3.
    1. One counter on the carrier's own row, for shipping and moving, replacing count_ship_restart.
    2. As planned: add task_graphs.restarts beside ship events.
  4. Reading "quit" before LOO-953 lands.
    1. Leave the processes join, and name it in the plan as the line 953 rewrites.
    2. Wait for 953's Session columns before merging this Task.
