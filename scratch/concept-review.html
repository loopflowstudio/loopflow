Do the plan's concepts and the code's concepts line up?

Area taken: how a repository's plan is shared — between one person's Machines, between teammates, with and without a hub — as LOO-938's stamped-plan design would leave it. Taken whole (the save, the carriers, what a person reads in lf repo tracker, claims, order, repository identity) because the Task replaces all of it. Reviewed 2026-11-18 against scratch/plan.md at dd2c3b49f9 and the branch's hub code; the stamp, the Git carrier and the claim rule are not built yet.

Blue marks what this review proposes. Everything else is the plan or the branch as it stood. The plan has been updated with every proposal; each is a choice made for review.

Answer

The stamp lines up. The carriers did not. The rule "a save stamps each field; the plan is the newest stamp per field" is one idea in the product and one function in the code, and it deletes first contact, pull-before-push and every conflict state. But the plan then gave each carrier its own shape: the hub sends a queue of fields, Git writes a ref of only-my-newest fields, and each reports "not there yet" in its own word. A person sees "my plan, and how far it has got"; the code had three ideas for that.

One interaction, walked

Three people's Machines on etude: laptop L and mini M (one person, M is L's hub), teammate T (Git only). L creates a Task. T retitles it. L, offline, edits the description. M's server stops. Everyone comes back.

Plan as it stood

L save  → stamps → hub_sends rows (per field)
                 → plan_changes → L's ref: all 15 fields
T save  → T's ref: title only
L sees T's title (by Git) → L drops title from L's ref
M sees it by hub → M writes nothing to Git (not M's stamp)

A reader needs L's ref and T's ref to have a Task. Each file is a fragment.

Proposed

L save → stamps → plan_changes
hub:  records past L's cursor → plan.apply
Git:  records past L's cursor → files in L's ref
T, M the same. Every ref is that Machine's whole plan.

Any one ref is a complete plan. A record is the same bytes on the wire and in Git.

What the proposal costs. Every change is re-published by every Machine: one small commit per Machine per change, and each Machine reads a diff of blobs it already has. Identical records are identical blobs, so the remote stores one copy however many refs name it. At five people and ten Machines that is ten small commits per change. It is the wrong shape for a hundred Machines without a tracker; that tier is Linear's in the design.

The biggest mismatch: what a Machine publishes

Before

A ref holds "the fields whose newest stamp is this Machine's". To keep that true a Machine prunes on every arrival, readers merge fragments across refs, a ref can name a record nobody has created yet, and a retired Machine's ref can never be deleted. The hub sends something else again: a queue of single fields.

refs/loopflow/plan/L   tasks/3e/3e1c9a.json  {description}
refs/loopflow/plan/T   tasks/3e/3e1c9a.json  {title}
hub_sends              (3e1c9a, task_description)

After

A Machine publishes its plan. A record file holds every field with the stamp it carries, whoever wrote it. The hub sends the same record. Each carrier keeps one number: how far into plan_changes it has sent.

refs/loopflow/plan/L   tasks/3e/3e1c9a.json  {all fields, each with at + machine}
refs/loopflow/plan/T   tasks/3e/3e1c9a.json  the same blob once T has seen it
plan_carriers          (etude, git, sent_seq) (etude, hub, sent_seq, seen_seq)
Why this one. It is what the design's own phone section already says ("every one of a person's Machines holds the whole plan"). It removes pruning, cross-ref merging, the stalled-tip state, the adoption question, hub_sends and its three triggers, the queued/sent phases and the word "open" for the hub. It adds the echo commits described above. Passed over: newest-own-fields refs (smaller refs, no echo, but the read-only-teammate counterexample breaks it and four pieces of machinery exist only to maintain the fragmenting).

Two smaller changes written into the plan

The ref names the repository. A repository file at the ref's root holds the repository id. A clone that fetches a plan ref takes the lowest id it sees, through the existing bind_repository. Then the hub works in a fresh clone with no command, and lf config repo --bind leaves the "share the plan" docs. Unchecked: whether binding moves rows already saved under the clone's first id. The docs say bind "before anything is saved there". Slice 2 checks; if it does not, the manual step stays for the hub and this is dropped.
"Your order of your claimed Tasks" leaves this Task. It is a new value with a new view rule, and it is designed as one half of a pair whose other half (backlog order written to Linear's manual order) is already excluded. Built here it would be a per-person value riding in a shared plan with no tracker answer. It goes with the tracker Task. Backlog order across Machines is still delivered here: it is task_rank.

Larger than this work

  • lf repo tracker reports where the plan is shared; only one of the three answers is a tracker. Renaming it (lf repo plan) touches the CLI, Desktop and docs.
  • Remote history under refs/loopflow/plan/* only grows. A Machine could replace its ref with one parentless commit now and then; that needs the "never forced" rule relaxed for a Machine's own ref.
  • The tracker Task (your slice of a Linear Project, both orders, own-Machines-by-Git on a tracker repository) is not filed. Scratch is cleared at submit, so it should be filed before then.

Questions

  1. What a Machine's ref holds.
    1. Its whole plan, as proposed: complete refs, echo commits.
    2. Only the fields it holds the newest stamp on, as the design says: small refs, fragments, pruning.
  2. One word for "saved here, not there yet" on Git and the hub.
    1. "unsent" for both, counted in records, as proposed.
    2. Keep "open" with per-field lines for the hub.
  3. A fresh clone and the repository id.
    1. Taken from the plan ref on first fetch, as proposed.
    2. Stay with lf config repo --bind wherever a hub is used.
  4. Your order of your claimed Tasks.
    1. With the tracker Task, as proposed.
    2. In this Task, as slice 4.
  5. First-wins claims (slice 3).
    1. In this Task, last, as planned.
    2. Its own Task; this one ends at Git refs.
