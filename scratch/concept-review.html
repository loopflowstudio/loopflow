Who can sign as Loopflow

Concept review of LOO-1117 with the change built. Branch jack/loo-1117-signing-and-notary-secrets-are-unreachable at e67affb9c0, against its base 2b9088e6d2 (LOO-1120). GitHub's settings were read on 2026-11-26, names only.

The area taken: everything that decides whether a binary gets Loopflow's signature: the two jobs that read the certificate and notary key, the settings that hold them, the rules on main, the check that reads those settings, and the sentences in .github/CI.md that tell a person what is promised. The diff touches the jobs, the check and the sentences; the rules on main decide what the sentences may say, so they are on the page.

built and committed waits for a settings step exists, untouched ★ proposed by this review

The verdict in five lines

  • The mechanism is built as planned and reads well: one environment, two jobs, no hand trigger. Keep it.
  • The docs promise "Push access is not enough to sign." That is not true. main requires a merge queue and one check, tests-result, and no review; anything with push access can open a PR and queue it. What the change buys is different and better stated: nothing is signed without a commit on main.
  • The settings check starts from the workflow files, so it never looks at an environment no workflow names. Environment dev has no branch policy and holds LFD_GITHUB_WEBHOOK_SECRET. A branch can read it today, and once the settings steps are done the check will print nothing.
  • "The next release stops and names the change" is true of a setting left changed. A policy widened, used and put back before 10:00 prints nothing.
  • No settings step has been done: signing does not exist, and the six repository secrets are still there.

Normal path built

A PR lands. CI goes green on main. Packages (main) starts from workflow_run, on refs/heads/main. desktop-app names signing, the policy matches, the DMG is signed and notarized, lf install --dev installs it. Same as today.

Failure: a branch tries built waits

A branch with an edited release-loopflow.py cannot dispatch the packaging workflow, which has no hand trigger. A new on: push workflow that names signing is refused before a runner starts; one that names nothing reads empty strings. Holds once the repository secrets are deleted.

Failure: the same holder opens a PR exists

The same edit goes in a PR. The holder queues it. tests-result passes, the merge queue lands it, Packages (main) signs the result. No person approved anything. This is lf land working as designed, and it is how every agent ships. The difference from last week: the edit is a commit on main, which nobody can delete or force-push (the ruleset has no bypass).

Failure and recovery: a setting changes built

Something with admin adds release/* to the policy. At 10:00 the cron host's release runs its host check before touching anything, and stops:

GitHub's signing settings differ from the workflows (.github/CI.md, "Signing secrets"):

That text goes to .lf/logs/release-run.log on the cron host. The recovery is one API call and tomorrow's release. If the policy was put back before 10:00, nothing is printed.

Questions

1. What does the page in .github/CI.md promise?

Anyone who can push can also land a PR by themselves: main asks for a passing check and the merge queue, not a reviewer.

1a. Recommended. "Nothing is signed as Loopflow without a commit on main", with the three ways in and what each leaves.

1b. Keep "Push access is not enough to sign" and the holder table, with the first row changed to say a holder can still land its own PR.

2. Should a use of the signing secrets leave a record on GitHub?

As built, a run that uses signing leaves nothing but the run. If the branch policy were widened, used from a branch and put back the same morning, the daily check would see clean settings.

2a. Recommended. Leave it, and have the docs say the check sees a change that is still in place. The fix that counts is agents not holding admin.

2b. Remove deployment: false. GitHub then lists every use of signing under the repository's Deployments, with the branch it came from, and the daily check reports any that is not main. You would see a "signing" entry for every main commit and every morning check. An admin could still delete the entry, with more steps. It also removes the one GitHub behaviour the probe exists to confirm.

3. What happens to the dev environment?

It holds one webhook secret from February for lfd, which left the repository in September. Any branch can read that secret today. With item 2 of "This work" the daily release reports it until this is answered, which stops the release.

3a. Recommended. Delete dev and the empty pypi. The secret's value is gone for good.

3b. Keep dev and give it a main-only policy, because something outside the repository still uses that webhook.

4. When the settings are wrong, does the daily release stop?

As built it stops, and the reason is in a log file on the cron host. From the merge until the six repository secrets are deleted, it stops every day. The release itself signs on the host and does not use GitHub's copy.

4a. Recommended. It stops, as built. A missed release is the one signal that already exists, and the host check already stops for a missing credential the same way. Do the secret deletions the day of the merge.

4b. The release goes out and prints the lines as a warning. Nothing is held up, and nothing makes anyone read the log.

5. Rotate the signing identity? (open since the first review)

The secrets were readable by anything with push access from 2026-10-30 until the repository secrets are deleted. The one branch run on record is the feature's own (run 41111152406). Runs of branch workflows since deleted were not counted.

5a. Recommended. Rotate the notary API key only: a new key in App Store Connect and one Doppler edit. Nothing shipped is affected.

5b. Rotate nothing.

5c. Rotate the certificate too, after checking what revoking the old one does to DMGs people already have.

6. Was the old Doppler token revoked? (open since the first review)

DOPPLER_TOKEN_PRD is gone from the repository's secrets, and Doppler lists no service tokens for prd. Whether the token it held was one of those cannot be read back.

6a. It was revoked. Nothing to do.

6b. Not sure. Doppler's activity log answers it, under a person's login.
