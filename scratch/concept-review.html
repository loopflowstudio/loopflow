1. One concrete interaction: built behavior observed on macOS

A person turns mobile access on once, connects from their iPhone, and leaves it enabled while Tailscale runs, signs out, stops, or rotates its local port — expecting zero macOS GUI launches and zero nehelper churn.

1 · Enable
Turn on once

lf server mobile reads LocalAPI once (0.19s in QA), checks MagicDNS + owner, binds the tailnet address, saves mobile.yaml, and returns the QR endpoint.

2 · Idle & Use
Phone connects, Mac stays quiet

Each socket checks /localapi/v0/whois. Every 5s check_owner reads status?peers=false. 125s live idle window logged 0 nehelper events (1 CLI control call logged 3).

3 · Fail (Auth)
Logout, account or DNS change

HostStatus::verify catches owner or DNS drift on the next 5s check, stops the listener, drops connected phones, keeps the local server untouched, and reports the exact reason.

4 · Fail (Daemon)
Tailscale stopped or hung

Listener exits and schedules restoration from completion at 5 → 10 → 20 → 30s. Against a hung socket, --status answers in 0.03s and --off cancels the in-flight request in 0.05s.

5 · Recover
Daemon returns or rotates port

Each retry re-discovers via libproc / ipnport / socket fresh, picks up any new IPNExtension port and proof token, and rebinds the same saved port so phones reconnect without re-scanning.

6 · Disable
Turn off

--off goes straight to the live manager without waiting behind mobile-setup.lock, aborts any in-flight setup or retry, releases the port before replying, and saves enabled: false.

3. The resolved mismatch: CLI subprocess transport vs. LocalAPI client

On main, lf server reached Tailscale by executing the macOS app bundle with TAILSCALE_BE_CLI=1 every 5 seconds — which made nehelper create and remove a temporary NETunnelProviderManager configuration on every poll. Worse, any fallback to the CLI on macOS would have reproduced the exact same nehelper churn whenever Tailscale was quit or stopped.

Before Base main (2656258abf)

5. Outside this work

Two pre-existing or adjacent gaps surfaced during QA and review. Neither makes LOO-1080’s model wrong, and fixing either belongs in its own Task:

1. Forwarding TS_SOCKET into supervised macOS servers Separate Task

installation/server.rs registers macOS servers via SMAppService (fixed bundled plist) or a generated server.plist carrying LF_HOME only. Setting TS_SOCKET in a shell reaches lf server mobile, not the launchd-managed server — making docs/server.md’s custom-socket instruction unreachable on macOS unless the user runs lf server run manually. Fixing it requires either env-forwarding support in installation/server.rs (for custom homes) or storing an optional socket path in Machine config.

2. lf server mobile JSON vs. plain text output Separate Task

lf server mobile and --status print raw JSON without --json, whereas --off prints "Mobile access is off" (same on main). swift/LoopflowMac/Views/MobileSettings.swift parses stdout of lf server mobile --status directly without --json, so normalizing CLI output requires coordinating Rust and Swift together.

6. Open choices for review (all built & reversible)

Everything below is already built and committed on HEAD, internal to server/{mobile,remote}.rs, with no wire, Swift, schema, or mobile.yaml changes. Reply with numbers and letters (for example, 3b) only if you want to change a built choice.

1. Tailscale transport boundary
  • 1a Built LocalAPI only: macOS App Store (libproc), macOS Standalone (/Library/Tailscale/ipnport), Unix sockets, and TS_SOCKET; all CLI subprocess probing deleted so macOS can never launch Tailscale.app even when Tailscale is quit.
  • 1b LocalAPI + Linux-only CLI fallback: Keep macOS strictly LocalAPI-only; retain a throttled PATH CLI fallback only on non-macOS builds.
2. macOS App Store IPNExtension discovery
  • 2a Built Direct libproc: Inspect same-UID IPNExtension open vnodes in-process via PROC_PIDLISTFDS / PROC_PIDFDVNODEPATHINFO (zero subprocesses; proof token never crosses a pipe).
  • 2b Bounded /usr/sbin/lsof: Match upstream safesocket_darwin.go literally with a bounded child process.
3. Behavior of lf server mobile --status (Desktop’s “Refresh”) during backoff
  • 3a Built Strictly read-only: Return the manager’s cached Status immediately without waking the 5 → 10 → 20 → 30s backoff timer (Desktop’s “Set up again” still binds immediately).
  • 3b Non-blocking wake on Refresh: Return cached status immediately, and if enabled and sleeping in backoff (>2s since last attempt), wake the retry timer so the next probe runs right away.
4. Five-second maintenance payload
  • 4a Built Full status at bind, status?peers=false every 5s: Verifies User[user].LoginName at bind while keeping 5-second owner and DNS checks O(1) on large tailnets.
  • 4b Full /localapi/v0/status everywhere: One endpoint and one parser for both bind and 5-second maintenance.
