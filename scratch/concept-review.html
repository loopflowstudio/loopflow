Biggest mismatch: the Task's setting is stored on its Graph

Existing

task_graphs
  task_id  graph  step  …
  auto  auto_at  auto_by      -- NULL ×3: never set

set_task_auto:  UPDATE task_graphs … WHERE task_id
                0 rows → "no mark", nothing kept
take_up_task_graph:
  INSERT OR REPLACE … SELECT old.auto,old.auto_at,old.auto_by
reopen:   UPDATE … SET auto=NULL,…
Move:     graph.auto  (absent before a Graph)
upgrade:  a released hold on a never-run Task is dropped

Proposed

task_auto
  task_id PRIMARY KEY → tasks
  state ('on'|'off')  at  by   -- no row: never set

set_task_auto:  upsert; INSERT OR IGNORE for a config default
take_up_task_graph:
  writes the Graph, nothing else
reopen:   DELETE
Move:     auto, beside graph
upgrade:  every Task's latest approval or stop becomes its row

One row is the mark, and a Task can hold it from the moment it exists. The copy across Graphs, the three NULLs and the "no Graph" answer go. Nothing on the wire changes shape.

lf task auto off INF-9          # INF-9: auto off
lf task status INF-9            # INF-9  unstarted · auto: off by Maya, Nov 19 17:40
lf task run INF-9               # the Wave's auto: on finds a mark and leaves it;
                                # the run stops before its first interactive step

Tested against.

  • Normal. Never-run Task in an auto: on Wave, nobody says anything: take-up inserts the config's row, as today.
  • Failure. Two first runs at once: both INSERT OR IGNORE the config mark, one row. A person's off landing between them wins, because the config write never replaces.
  • Recovery. A Task moved to another Machine before its first run carries its off on the Move record. A reopened Task has no row and takes its config default again, as now.
  • Counterexample kept. An off on a never-run Task in a Wave with no auto: on now leaves a row that changes nothing until a run reaches a merging step, where that run waits. That is what off already means after a first run (question 2).
  • Passed over. Taking a Graph up at auto off so the row exists: an earlier build's mark-only take-up left a Task that owed setup and refused the person's own run. Columns on tasks: a planning table whose update triggers compare every column. A personal auto: off config value: it answers "every Task", not "this one".

Larger than this work

  • Off is two promises. "I take the interactive steps" and "nothing merges". After an off, your own lf task run past ship-review waits at land until you say lf task auto on, which by then has no step left to stand in at. Collapsing it needs the run to know whether a person or a stand-in took the last interactive step, and to put the Task back there on an off; that is a change to what Graph steps record.
  • auto::running_graph polls up to 30 s so TaskRunStart::Live can name a Graph run. If Live named the carrier, the wait would go; it changes the TaskRun answer.
  • A config default is read once. Removing auto: on from a Wave leaves its taken-up Tasks on, attributed to "wave config". Resolving the default at read would make the attribution always true and cost a config read in every projection that shows auto.

Questions

  1. Auto's home. Chosen for review: its own row per Task.
    1. Keep it: task_auto, a row is the mark.
    2. Three columns on tasks instead.
    3. Leave it on task_graphs and document that an off needs a first run.
  2. Off at the landing step, when you took ship-review yourself.
    1. Keep: it waits until lf task auto on.
    2. Your own run past review lands; only a stood-in run waits. Its own Task.
  3. An off on a Task that was never on prints:
    1. "INF-9: auto off" (chosen).
    2. "INF-9: auto off (was not on)".
  4. A config default that is later removed:
    1. Tasks already taken up stay on (as built).
    2. Resolve it at read, so they follow the config. Its own Task.
