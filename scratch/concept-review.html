The mismatch QA found

Before the follow-up: an account-wide hold ending January 1 and a Fable hold ending January 2 could appear as one account-wide hold until January 2. Clearing cooldown then claimed success without naming Fable.

Implemented in the working tree:

lf account next
'fixture@example.com' cooling account-wide until 2100-01-01T00:00:00Z;
for fable until 2100-01-02T00:00:05Z

lf account set fixture@ --clear-cooldown
Cleared Claude login 'fixture@example.com' account-wide cooldown;
still held for fable until 2100-01-02T00:00:05Z

Repeating the clear says “has no active account-wide cooldown” and still names the Fable hold. The observed quota stays intact.

Actions → concepts → APIs

  1. lf account claude refreshes a login's observed capacity → known windows replace matching old observations → reconcile_provider_account_capacity commits only if the revision read before polling is still current.
  2. A fresh or resumed Sonnet conversation asks for Sonnet → account-wide holds apply; Fable holds do not → account_held_until receives the actual launch model.
  3. lf account next explains availability without a model → every active scope participates → account_unavailable_reason uses account_capacity_holds to label each scope and deadline.
  4. --clear-cooldown clears the account cooldown → observed windows remain → clear_account_cooldown reloads state and reports the remaining holds through the same description function.

Normal path, failure, recovery

Fresh Fable room replaces an older Fable rejection. At 100%, Fable stays held while Sonnet can run if account-wide windows permit it. A genuine global rejection still holds every model. A rejection arriving during refresh changes the account revision, so the delayed poll cannot erase it.

Weekly headroom cannot establish Fable recovery, included headroom cannot establish paid-credit recovery, and missing or malformed observations cannot establish recovery. These counterexamples retain their existing conservative handling. No new cache, public DTO or persistence concept is needed.

Review questions, resolved from the design

  1. Should clearing cooldown reset quota? No; it retains observed windows and names the holds that remain.
  2. Should next become model-specific? No; the documented model-unspecified behavior remains. Actual launches and resumes check their model.
  3. Is another implement iteration needed? No. The overlapping-hold regression is recorded as passing in the working design; gate and CI own broader checks.
