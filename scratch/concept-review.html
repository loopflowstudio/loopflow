Resolved in this pass (verified by unit, integration and QA)

1. Open Graphs obey the Git-root rule

Before (7d8cc0c9) 
Nested worktree /repo.a/.claude/worktrees/exp runs `lf graph`:
  graph_processes.task_id = NULL, cwd = nested root
  task_open_graph_pairs: within(g.cwd, c.worktree) → TRUE
  → outer Task A becomes 'moving' and blocks `lf task run A`
  → `lf task show A` lists graphs: [] (contradicts status)
Built (5eca00f2, QA 0be48216) 
task_open_graph_pairs matches taskless runs by root equality:
  rtrim(g.cwd,'/') = rtrim(c.worktree,'/')

- Nested worktree run: outer Task A stays idle and runnable.
- Adopted checkout with running Graph: blocks a second run,
  stays out of Task history.
- Directory cleanup (`checkout_open_work`): keeps `within`
  so removing a checkout never deletes live nested work.

2. One detach command for stacked Tasks and --stack checkouts

Before (7d8cc0c9) 
Stacked Task:    lf sync main → merges main, clears parent_pr_id
--stack checkout: lf sync main → merges main, KEEPS loopflow-base
                  no `lf` command could unstack it
Built (93fbc3de, c5fe7709, QA 0be48216) 
`record_control_task_state` (runs only after sync completes):
  when target is default, origin/<default>, or fork upstream:
    clear Task parent_pr_id (if stacked)
    clear branch.<verified-branch>.loopflow-base

- `--plan`, mid-conflict, and `--abort` keep the base.
- `--continue` clears it on completion.
- Next `lf sync` and `lf pr open` follow the default branch.

Biggest remaining mismatch (outside this Task)

Run liveness across two OS processes LOO-1075

A person asks "is this Task's run alive?" The store answers from two places because lf task run spawns a carrier process (task_graphs.run_pid) which then spawns lf graph (graph_processes.pid). Unifying them requires changing launch so the carrier records itself as the run or runs the Graph in-process — launch work, tracked in LOO-1075.
