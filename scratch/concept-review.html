2. The Redesign Across the Branch — Before vs. After

Before this branch (base d8b2afeb):

Every subsystem kept its own private timer, store open, watcher, runtime, or permanent OS registration. An idle Machine ran three 250 ms polling loops, four transcript watcher threads, a 16-worker Tokio runtime per subscription, thousands of fresh SQLite opens re-parsing 402 triggers, per-key YAML Config deserializations outside any cache, permanent launchd jobs for temporary LF_HOMEs, unguarded SQLite calls on the held-terminal relay thread, and split background plan sync loops that hammered dead or local-only repos.

At HEAD (86624c0f) Built & committed:

One rule governs every layer: work happens on a change or a request, never on an idle timer, and each process owns one of each shared resource (one store pool, one bounded async runtime, one observation cache with one filesystem watcher). The terminal relay thread owns only terminal I/O; background plan sync follows one carrier-first rule across owned and unowned repos; only ~/.lf is an OS-registered service.

4. Counterexamples Verified

1. A CLI lf task sync recovers an unreachable remote while the server is mid-backoff. Because backoff lives in the server's memory, a separate CLI process cannot mutate it directly. Verified in live QA: is_backed_off checks plan_carriers in SQLite; once the CLI clears the carrier error, the server drops its backoff and picks up a steer from another Machine on the next 30 s tick (27 s instead of 118 s).
2. A split-Wave conflict (NotTaken) arrives over a working Git remote. NotTaken means the carrier succeeded but a record conflicted locally. Verified by unit test: Backoffs::run clears backoff on NotTaken instead of throttling every steer on that repo to hourly.
3. A repo defines remotes via [include], extensions.worktreeConfig, legacy .git/remotes, or adds/removes a remote live. Verified in live QA and unit tests: exotic configs fall back to git remote once (cached under Derived::GitRemote); adding or removing a remote in .git/config is picked up on the next tick via inline stat_stamp validation with 0 git remote forks.
4. A client attaches to a held terminal milliseconds after its process exits while SQLite is locked. Verified in live QA and unit tests: the relay loop keeps the terminal ID in settling and answers Waiting on held.sock until held-status finishes writing exit_code, so neither typing in other terminals nor exit-code visibility breaks.

5. Outside This Work

Separate outcomes noted during kickoff and QA — not part of LOO-1110's Machine Runtime scope:

Staged migrations (LOO-965, LOO-938) Reclaiming 271 MB from processes and leaving sync tables; collapsing 402 SQLite triggers. Those tables are already marked leaving; their staged drops reclaim the space after the migration window. With connection pooling, trigger parsing is paid once per process instead of per request.
Separate refactor Moving per-Graph watch_owned_work polling into the server. Pooled connections make each 30 s Graph check cheap; centralizing Graph ownership polling into the server is its own lifecycle change.
Pre-existing plan-sync bug Fresh clone that runs lf task create before its first lf task list. QA observed that creating a Task registers the clone first, so before_first_read skips the initial fetch from other Machines until an explicit sync or background tick. Predates this branch; requires separating "known locally" from "ever fetched from remote" in plan_git.
Minor optimization One cat-file -p verification on the tick immediately after a publish. Each actual publish moves the tip OID, so the next quiet tick verifies it once (then 0 times thereafter). Recording the newly pushed commit OID in VERIFIED_TIP_REPOS at push time would save that single fork per publish.

6. Open Questions (Reversible Product Choices Built for Review)

Resolved during implementation: machine.jobs stays host-local (confirmed by Jack Heart; built in Pass 4). All six choices below are already built and committed using option a, and every one is reversible. Reply with e.g. 1b or 6b if you want any of them changed.

1.Should a custom LF_HOME stay alive in the background without an open client or running agent, or restart after a reboot?Built: 1a
  • 1a (built): Only your main ~/.lf Machine restarts on login and stays up indefinitely. A custom LF_HOME runs as a normal background process and exits automatically when you delete its folder or 10 minutes after its last open client, terminal, and running agent finish — even if it still has a claimed Task waiting. Running any lf command there starts it again.
  • 1b: Keep custom LF_HOME servers running whenever they have a claimed Task (or register them as persistent login services unless flagged temporary), so a secondary custom-home Machine keeps receiving remote steers indefinitely without a client connected.
2.When you delete a custom LF_HOME folder while agents are still running inside it, should Loopflow stop those agents?Built: 2a
  • 2a (built): Yes — once the folder is deleted, no server or view can ever reconnect to those terminals, so the terminal holder closes them (sending hangup to its children) and exits within a second. Live homes are unchanged: agents still survive server restarts and lf install.
  • 2b: Leave those agents running in the background until you stop them manually by PID.
3.How should concurrent Graphs share your Machine's CPU cores during local builds and tests?Built: 3a
  • 3a (built): Automatically divide cores across running Graph steps (floor 2, at lower scheduling priority nice 5, overridable per Machine with machine.jobs), leaving your interactive terminals at normal priority and never pausing an agent mid-turn.
  • 3b: Queue builds in a server-managed slot semaphore so later builds wait until earlier ones finish.
4.Where should live server counters (threads, database opens, spawned commands, watched facts) live?Built: 4a
  • 4a (built): Separate lf server diagnostics --json, keeping lf server status a fast, unversioned readiness check that stays compatible across old and new builds during upgrades.
  • 4b: Fold them into lf server status --json by opening a second versioned connection whenever the server is ready.
5.Should repositories with no active Waves and no unfinished Tasks still sync Git plans every minute?Built: 5a
  • 5a (built): No — only repositories with an unfinished Task or an active Wave on this Machine sync automatically in the background. Quiet repositories still sync the next time you run a command in them.
  • 5b: Sync every existing repository on disk every minute and automatically prune stale repository records instead.
6.When you have a claimed Task in a Git-only repository (no Linear/Asana, with a remote), how often should Loopflow check the remote for new direction while idle?Built: 6a
  • 6a (built, slimmed to 2 forks/check): Every 30 seconds — incoming steers from another Machine or phone arrive within 30 s, and offline remotes back off up to an hour (ending immediately if you run lf task sync).
  • 6b: Match the 60-second unowned cadence (halving idle remote fetches when no turn is running, at the cost of up to 60 s delay for remote steers).
