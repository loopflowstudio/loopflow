Working Task order, sidebar status toggle, and row status

Area reviewed: Working Task ordering, the window-local sidebar Sort by status toggle and open-Task hold, row status & Graph step display, Desktop drag recovery, OSC 7501 done/error handling, and packaged New Task fonts across Desktop, CLI, and iOS — widened to the whole sidebar and Working-order model after the demo pivot from one-shot sort to toggle.

Biggest mismatch: pinning an array index instead of latching status

Mismatch · Built at 14f44821e8 The demo pivot replaced the destructive one-shot sort with a clean window-local toggle and deleted the entire server/CLI/storage sort path. Seven of nine product-to-code pairings now line up cleanly. Two pairings in the new Mac sidebar toggle do not:

  1. Open-Task hold is modeled as an array index (WorkNavigation.selectedSidebarSlot: Int?) instead of a latched status group.
    Splicing the open Task back into a saved integer slot fights every row above it:
    • Switching from a latched Busy Task to the next Available Task inverts status order: setSelection reads the clicked row’s slot while the previous row is still pinned at slot 0, so releasing the old row slides an Idle row into slot 0 above the Available row you just opened (literally asserted in WorkNavigationTests.swift:298–301).
    • An unrelated Task leaving or changing above the open Task pulls Busy above Available: if [0: Blocked, 1: Available (open), 2: Busy] has slot 1 pinned and Blocked completes, sidebarRows removes Available from index 0 and splices it at index 1 → [0: Busy, 1: Available].
    • Turning Sort by status On while a Busy Task is open at slot 0 keeps that Busy Task glued to slot 0 above Blocked and Available rows.
  2. Sort by status is still restricted to sidebarScope == .repository — a leftover from the deleted one-shot task_orders write.
    Both Repository and Wave sidebars list Working Tasks from taskList. Because the toggle is now a local view sort that writes nothing, hiding the button and silently suspending sorting whenever a Wave is selected (while sidebarSortByStatus remains true in memory) forces a distinction with no reason behind it.

Recommendation: latch the open Task’s status bucket across Working scopes

Proposed for next implement pass

  • Replace selectedSidebarSlot: Int? with sidebarStatusLatch: SidebarStatusLatch? (taskID + statusOrder).
    When Sort by status is On, the open Task sorts using its latched statusOrder instead of its live statusOrder until you navigate to a different Task, switch filter, or toggle sorting Off. Sending a prompt (Available → Busy) still keeps the open Task in the Available group instead of dropping it to the bottom; leaving it releases it immediately; every other row stays in strict Blocked → Error → Available → Idle → Busy order, and an unrelated Task completing above never pushes Busy above Available. Re-selecting the already-open Task (e.g. pressing ⌘1 on it) keeps its existing latch.
  • Enable Sort by status for every Working sidebar scope (.repository and .wave), not only .repository.
    One helper (isWorkingSidebarScope) drives sidebarRows, WorkNavigator’s toggle button, and ⌘K’s action. Saved Dashboards (.dashboard) keep their own arrangement order. Drag-to-reorder stays repository-only (when sorting is Off), because dragging mutates the repository’s shared task_orders.

      Failure, recovery & counterexamples checked (with proposal)

      Send a prompt in open Available Task (Sort On)

      Press ⌘1 on the already-open Task after it turned Busy (Sort On)
      setSelection checks whether the resolved Task ID changed before replacing the latch; re-selecting the already-open Task keeps its existing latch instead of dropping it to Busy.
      Click or ⌃Tab from latched Busy Task to Available Task (Sort On)
      Old Task unlatches and drops to Busy (4); newly selected Task latches at its own actual bucket (2). Every row is in strict Blocked → Error → Available → Idle → Busy order.
      A Blocked Task above the open Available Task completes or turns Busy
      Open Task stays at bucket 2 (Available) and smoothly moves up to slot 0. No Idle or Busy row ever jumps above it.
      New Task arrives or cold start restores selection before taskList loads
      applyTaskList updates the reading first, then latches the selected Task’s initial bucket if the latch doesn’t yet match it, so the first turn never drops it.
      Switch sidebar filter (Working ↔ Available ↔ Busy) while Sort is On
      sidebarFilter.didSet clears the latch so a Task latched at Available doesn’t float above earlier Busy rows inside the Busy filter.
      Switch from Repository to a Wave while Sort is On

      Choices recorded for review

      Option a is what this review puts into plan.md for the next pass. All choices are reversible; reply with e.g. 1b to change any one.

      1. While Sort by status is On, how should the open Task stay steady across turns?
        1. Latch the open Task’s status bucket until you switch away (recommended). Sending a prompt (Available → Busy) keeps it in the Available group without ever pulling Idle or Busy rows above Available on navigation or completion.
        2. Keep pinning an integer slot index (selectedSidebarSlot) as built, accepting that Idle/Busy rows can slide above Available rows when another row changes or releases.
        3. Don’t latch at all while Sort by status is On: rows always reflect live status order immediately (since Start-Time Stack is already the default steady mode).
      2. Should Sort by status also work when the sidebar is scoped to a Wave?
        1. Yes — work in both Repository and Wave Working sidebars (recommended). Saved Dashboards keep their own arrangement; drag-to-reorder stays repository-only when sorting is Off.
        2. Keep Sort by status repository-only and hide the button on Wave sidebars (as built).
      3. When you turn Sort by status On while a Busy Task is open at slot 0, should it sort down to Busy right away?
        1. Yes — sort every row cleanly on toggle-on, then latch the open Task at its new bucket (recommended). Clicking “Sort by status” immediately brings Blocked, Error, and Available tasks to slot 0, and keeps the open Task from jumping if its status changes afterward.
        2. Hold the open Busy Task at slot 0 even when first turning Sort by status On.
