Do the concepts line up? Auto, as built

Area: how a Task goes on without a person: the auto setting, the three things that turn it on (lf ship, lf task auto on, lf -b task run), turning it off, what a run does with it at interactive and merging steps, and what the CLI, the wire and Desktop call each of these. Taken this wide because the Task's claim is about the whole: "ship is shorthand for auto on the Task's Graph". Reviewed at 3aaba763d0 against base f5ff6a6c79 (152 files, +2,347 / −3,051).

Tan panels are proposed and not built. Everything else exists.

One interaction, with its failure and recovery

lf task run LOO-12      # runs build, stops: the Task waits at human-review
lf task auto on LOO-12  # LOO-12: auto on            ← nothing starts. status: active · auto: on by Maya
lf task run LOO-12      # goes on to deliver          ← human-review is skipped, not stood in for
                        #   (a bare run at a waiting step means "I finished this step")
lf ship LOO-12          # what was wanted: LOO-12: standing in at human-review … running

lf task create 'x'      # INF-9, never run
lf task auto on INF-9   # error: Task INF-9 has not taken up a Graph, and auto is set on one;
                        #        `lf ship INF-9` turns auto on and runs it

The rest of the walk holds. A killed run is carried again as lf task run and stands in because auto is on. lf task auto off kills nothing; the run waits at its next interactive or merging step. One carrier, one recovery loop, one restart rule, and the run reads the setting when it gets to a step, not at launch.

Biggest mismatch: "auto on" is two actions

The Task set out to make ship a shorthand. As built, ship is the only complete way to turn auto on, and lf task auto on is a narrower thing with the better name: it refuses a Task that hasn't run, and on a waiting Task it sets a mark that nothing reads until a run starts, where the obvious run then skips the step it was meant to cover. The state it creates ("auto on, waiting at an interactive step, nothing running") is the one the plan had to explain twice.

Existing 
lf task auto on X   mark only
                    no Graph → error
                    waiting  → nothing happens
lf ship X           mark + take up + claim + run,
                    stands in at the waiting step
Desktop Auto on     task.ship
lf task auto off X  mark off
Proposed 
lf task auto on X   the Task goes on without you:
lf ship X             same operation, shorter to type
Desktop Auto on       same operation
                    live run → reported, stands in from
                               its next interactive step
                    waiting  → stands in at that step
                    never run → takes up its Graph, runs
lf task auto off X  unchanged

Auto on means nobody is waited for. A Task waiting for someone with auto on is a contradiction the setting can resolve by itself, so turning it on runs the Task. Then "ship is shorthand for auto on" is literally true, the toggle and the command agree, and three things go away: the auto_on operation, the no-Graph refusal and its docs paragraph, and the auto on-then-bare-run trap.

Tested against:

  • Normal. Live run: both commands already only set the mark and report. Unchanged.
  • Failure. A run that failed the same way and stopped keeps auto on; lf task auto on again starts it again, where today it answers "auto on" and nothing moves.
  • Recovery. Unchanged: recovery relaunches lf task run, which reads the mark.
  • Counterexample kept. Someone who wants auto armed on a waiting Task without starting anything can't. Nothing reads such a mark until a run, and they can ship when ready. If arming ahead matters (a Wave marking backlog Tasks), the mark moves to the Task row; that is question 1c.
  • Must survive. Off still stands against -b; only a person's auto on / ship lifts it; the setting still moves with the Task.

Passed over: keeping auto on a pure setting and fixing its holes instead (store it on the Task so it can precede a Graph; make a bare run stand in at the waiting step when auto is on). That keeps two actions and changes what a bare lf task run means at an interactive step, which people rely on to say "I'm done here".

Smaller, same pass

  • ships → merges on TaskRun::Running and TaskRunStart::Run, printed merges: this run may merge the PR; `lf task auto off X` stops it.
  • Run recovery moves out of ops/task/ship.rs to ops/task/run_recovery.rs; ship.rs keeps the setting and lf ship.
  • docs/dev/machines.md: "outside Auto-Ship" → "with auto not on".

Larger than this work

  • The auto Graph shares its name with the setting. Renaming a builtin Graph touches graph: auto in configs, docs and the catalog.
  • Off as "nothing merges" as well as "I take the interactive steps". Splitting them needs a run to know whether it stood in for someone before it reached the merge, across restarts. The three-state mark is the cheaper truth; the page records that the toggle hides one of the three.

Questions

  1. lf task auto on: (a) the same operation as lf ship, as proposed and written into the plan; (b) stays a mark that starts nothing, as built; (c) a mark that starts nothing and lives on the Task, so it can be set before the first run.
  2. ships on the run receipt: (a) rename to merges; (b) keep; (c) drop the line and the field, since the run decides at the merging step.
  3. The auto Graph's name: (a) leave; (b) file a Task to rename it (to what?).
  4. After auto off, your own lf task run past review: (a) waits at pr land until lf ship, as built; (b) lands, because you ran it.
  5. lf -b task run writes auto on: (a) keep; (b) stands in for its own run only.
