A launch that ends before Claude's first turn

LOO-984 · concept review of scratch/plan.md before it is built · 2026-11-19

Area taken: how a conversation decides to resume or start again when you open it, across lf resume, lf session resume, pane opens and the recovery watcher. That covers the record lf writes before Claude starts, lost_thread (#1972), resume_native_session, new_thread and the guards in run_client. Not just the guards the brief names.

The interaction

Today

$ lf -a claude resume       # Ctrl-C twice before typing
$ lf resume
No conversation found with session ID: 3f…

The pane opens Claude with --resume. You're stuck until lf session new. (#1972 catches this on the open path, but openers that go straight to open_waiting_locked don't get that check.)

Proposed

$ lf resume
Claude has no saved copy of this conversation;
starting it again from its first request.
╭─ Claude ─…

The same Session gets a new input with the same first request, and Claude starts with --session-id <new>. A conversation Claude did save still resumes.

Biggest mismatch: a recorded thread is treated as a saved one

lf has to pick the thread id before Claude starts (--session-id), so the record can't wait for Claude without a hook. And the hook fires before Claude saves anything, so it doesn't cover quit-before-typing. The plan accepts that and moves the meaning: the record says which thread, and Claude's transcript file says whether it exists. That's right. Before this review, the plan still left the predicate written out in two places.

Plan as written

resume_native_session:
  input_provider_session(k)
    .filter(|t| !thread_lost(..))
new_thread:
  let threaded = match input_provider_session(k) {
    Some(t) => !thread_lost(..), None => false };

Plan now (changed by this review)

fn saved_thread(store, key, provider)
    -> Result<Option<ProviderSessionRef>>

resume_native_session: saved_thread(..)
new_thread:            saved_thread(..).is_some()

One rule under one name, and the code says what a person means by "has history".

Larger than this work

The label still lies. has_provider_history comes from the store projection. Making it true would mean reading ~/.claude/projects for every listed Session, which the 10,000-Task load rule rules out. The fix that keeps the concepts true is to stop calling a thread recorded until the provider confirms it saved it. For Claude, that means watching for the first transcript write (or the first UserPromptSubmit hook) and recording the thread then. That change would delete thread_lost as an open-time check. It needs its own Task and touches hook delivery.

Outcome

The plan changed: one saved_thread helper serves resume_native_session and new_thread, slice 2 is renamed to match, and the label mismatch is written up as an exclusion with what fixing it would take. The rest of the design stands.

Questions

  1. Restarting from a lost thread: a) a new input via append_input (planned) · b) the same input restarted on the same --session-id, which real Claude accepts.
  2. The "Resume" label on a lost thread: a) leave it (planned) · b) file a Task to record the thread only after Claude saves it · c) check the transcript in resume_explanation only, not the listing.
  3. The diagnostic text: a) "Claude has no saved copy of this conversation; starting it again from its first request." (planned) · b) say nothing, since the first request shows up anyway.
