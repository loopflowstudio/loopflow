Biggest mismatch left: the record ID is named for one tracker

Everything a person reads now says tracker. The largest gap left is one a person never sees: a Task's ID in its tracker is tracker_id on the wire and LinearIssueId in Rust, whichever tracker issued it. One name for two ideas, and the reason Asana's tests still live under ops/linear/.

The walk. A repository on Asana creates a Task. The action is sent, Asana answers with a gid, and the store binds it. lf task show --json prints "tracker_id": "1209…". A person reading the code to find out why a bind failed lands in LinearIssueId::new and LinearBindingError for a record Linear never saw. Recovery (rebinding after a lost action) goes through the same type.

As built

pub struct Task {
    tracker_id: Option<LinearIssueId>,
    tracker_writeback: LinearWritebackState,
}

LinearIssueId: 37 uses in 15 files. LinearWritebackState: 37 uses in 18 files. LinearProjectId beside them.

proposed, not in this plan

pub struct Task {
    tracker_id: Option<TrackerRecordId>,
    tracker_writeback: TrackerWritebackState,
}

A rename with no wire, SQL or stored-receipt change, since the keys are already neutral. It touches every planning signature, so it is its own Task and not an eighth slice of this one. LinearIssueState keeps its name: it is Linear's.

Counterexample checked: does the Linear name guard a Linear-only rule, such as UUID validation? It would have to pass Asana gids and Git Task IDs today, so no. Why it stays out: this change set out to make people and the wire say one vocabulary, and they do; three passes each found a smaller ring of leftovers and this one found none a person can read.

Larger than this work

  • "action" also names what a command would do. TaskPlanningAction and the "action" key in lf --explain --json task … (create, edit, move, save, comment) predate this change. The glossary already sets Desktop's buttons apart from tracker actions; this is a third sense. Renaming it (change? request?) is a choice about the explain surface, not a leftover.
  • The design doc still narrates with the old verbs. docs/dev/planning.md says "acquire" for fetching at lines 196, 321, 418, 479, 570 and 605, and "observed"/"accepted" throughout its Linear sections. Its glossary is right; its prose predates it. A rewrite of that document, not a rename.
  • "Effect:" in the explanation. The label for what a command would do, beside TaskPlanningAction. Same third sense as the first item.
  • Applying an event is still "accept". accept_linear_issue_in, accept_linear_project_in, project_accepted_planning: about 60 call sites. As a verb for what the store does with an event it reads fine; as the retired noun it doesn't appear. Noted in scratch/questions.md for a follow-up.
  • Two sync times on one Task. tracker_state.synced_at and tracker_synced_at may be one fact. Settling it means reading every writer of both.
  • Git has no actions. "action" and "lost" on lf repo tracker describe two of three trackers; Git conflicts are a third thing.
  • Columns provider, planning_provider_revision, observed_at, pm_snapshot_synced_at, pm_writeback_json: each a staged rebuild. LOO-960 could carry them with the contract migration.
