Do Mobile Access’s product concepts and code concepts line up?

Area reviewed: Mobile remote access (lf server mobile, Desktop’s Mobile settings, and the server’s Tailscale boundary in server/mobile.rs & server/remote.rs) — how Loopflow discovers, talks to, monitors, and recovers this Machine’s Tailscale daemon. Widened from “stop the 5-second poll” to the whole lifecycle because the previous plan still kept a macOS CLI fallback and two retry/health regimes.

Existing Current main & kickoff plan Proposed Updated in scratch/plan.md (not yet built) Code changed: none

1. One concrete interaction: normal, failure, and recovery

A person turns mobile access on once, opens Tasks from their iPhone, and expects Loopflow to stay silent on macOS whether Tailscale is running, signed out, or quit.

1 · Enable
Turn on once

Desktop “Enable mobile access” or lf server mobile binds this Machine’s .ts.net address, saves owner + port in mobile.yaml, and shows the QR code.

2 · Idle & Use
Phone connects, Mac stays quiet

Each phone socket is checked by Tailscale whois. While idle for days, lf server spawns zero Tailscale apps and triggers zero nehelper saves.

3 · Fail (Auth)
Logout or account switch

Already-connected phones disconnect within seconds. Local lf server and running Sessions stay untouched. Status says why.

4 · Fail (Daemon)
Tailscale quit or stopped

Listener stops and reports unready. While Tailscale stays off all weekend, lf server must still trigger zero GUI launches and zero nehelper churn.

5 · Recover
Tailscale returns

Opening Tailscale with the approved account binds the same saved port automatically; phone reconnects without re-scanning QR.

6 · Disable
Turn off

Closes the HTTPS listener immediately, cancels any in-flight retry, keeps address/owner in mobile.yaml with enabled: false.

3. The biggest mismatch: two Tailscale transports & “The Weekend Quit Bug”

Counterexample that breaks the kickoff plan’s CLI fallback

Trace what happens on an App Store Mac when mobile access is enabled and the person quits or turns off Tailscale for the weekend:

1. Person quits Tailscale → IPNExtension exits → no live sameuserproof descriptor exists. 2. lf server restoration runs → LocalAPI discovery finds no running daemon. 3. Kickoff plan treats “no LocalAPI” as “direct access unavailable” → falls back to legacy CLI. 4. Spawns TAILSCALE_BE_CLI=1 /Applications/Tailscale.app/Contents/MacOS/Tailscale status --json. 5. macOS nehelper creates a temporary NETunnelProviderManager delegate, commits preferences.plist, broadcasts com.apple.neconfigurationchanged, and removes it 200ms later. 6. CLI still fails (IPNExtension isn’t running!). Repeats every 60s all weekend. (Even a PATH-only fallback hits this: macOS installs symlink /usr/local/bin/tailscale → Tailscale.app.)

Every Tailscale distribution on macOS and Linux exposes the exact same LocalAPI — the tailscale CLI itself has no separate backend; it is just a Go client to these four LocalAPI endpoints. Deleting the CLI transport removes the bug in both steady-state and stopped-daemon states, and collapses two transports, two health intervals, and two backoff state machines into one.

4. Stress-testing the proposal against counterexamples

Scenario / Counterexample What could break a naive design How the proposed model handles it
App Store port/token rotates on daemon restart Reusing a cached loopback port/token after IPNExtension restarts fails forever with connection refused or 401. maintain() fails → listener exits and drops remote sockets → restoration re-runs Tailscale::discover() fresh via libproc, picking up the new port and token and rebinding the same saved port.
Stale /Library/Tailscale/ipnport beside live App Store Stopping on the first discovery file that fails to connect leaves a working App Store daemon unused. Discovery tries each LocalAPI candidate in order; unreachable/stale endpoints (refused, ENOENT, EACCES, 401/403) continue to the next candidate. An authoritative HTTP 200 Running status with wrong owner, tags, or missing MagicDNS stops immediately and never falls through.
Tailscale uninstalled vs. installed-but-quit Without executing the CLI, error messages might lose the distinction between “Install Tailscale” and “Open Tailscale and sign in”. When no LocalAPI candidate responds, a passive check (does /Applications/Tailscale*.app, ~/Applications/Tailscale*.app, or tailscale on PATH exist on disk?) picks the exact wording with zero process launches.
status?peers=false omits User map owner_from_status checks User[user].LoginName; blindly using peers=false at bind fails owner verification. discover() / bind() calls full /localapi/v0/status (verifying User[user].LoginName). Once bound to an approved owner, the 5-second maintain() check calls /localapi/v0/status?peers=false (verifying BackendState, untagged Self, ID, UserID, DNSName, TailscaleIPs) — avoiding O(peers) JSON every 5s on large tailnets.
Slow Let’s Encrypt cert issuance during --status or --off Inline bind().await in manage() stalls lf server mobile --status and --off for up to 60s. Restoration runs as a separate cancellable task inside manage(). Control::Status returns immediately; --off aborts the in-flight bind and cancels its async HTTP request immediately.
Custom Linux tailscaled socket Hardcoding only /var/run/tailscale/tailscaled.sock misses userspace or containerized tailscaled --socket=…. Check TS_SOCKET when set before standard Unix socket paths. Same LocalAPI client, zero CLI code.

5. Choices made for review (recorded in scratch/plan.md)

None of these choices change the wire protocol, mobile.yaml, QR format, or Swift clients; all are reversible before release.

1. LocalAPI only — delete the CLI subprocess fallback Chosen

Passed over
Keeping a legacy CLI fallback (throttled to 60s) alongside LocalAPI.
Why
Every supported Tailscale distribution exposes LocalAPI; any CLI fallback on macOS still spawns Tailscale.app and triggers nehelper churn whenever Tailscale is stopped, while doubling health-check and backoff complexity.

2. Direct libproc lookup on macOS (no lsof child) Chosen

Passed over
Spawning /usr/sbin/lsof -n -a -u <uid> -c IPNExtension -F n.
Why
lsof is not setuid on macOS and calls the exact same libproc APIs already used by os_process/macos.rs. Direct kernel reads spawn zero processes, take <1ms, work in sandboxes, and keep proof tokens strictly in memory.

3. Cancellable async restore + single 5 → 10 → 20 → 30s backoff Chosen

Passed over
Inline blocking bind() in select! and dual 60s-ceiling backoff schedules.
Why
Fixes stalled --status / --off during slow binds. With zero subprocesses and <0.5ms idle checks, a 30s cap is negligible and halves recovery wait when reopening Tailscale.

4. Full /localapi/v0/status at bind; ?peers=false every 5s Chosen

Passed over
Full status (all peers) every 5s, or streaming /localapi/v0/watch-ipn-bus.
Why
Keeps the full User[user].LoginName check at bind, avoids parsing hundreds of peers every 5s on large tailnets, and avoids version-sensitive watch-ipn-bus bitmasks.

6. Questions for review

Reply with numbers and letters (for example, 1a, 3b). Highlighted options are what scratch/plan.md builds unless changed.

1. Tailscale transport boundary
  • 1a LocalAPI only (proposed): Support macOS App Store, macOS Standalone, Unix sockets, and TS_SOCKET; delete all CLI subprocess probing so macOS can never spawn Tailscale.app even when Tailscale is quit.
  • 1b LocalAPI + Linux-only CLI fallback: Never spawn CLI on macOS (#[cfg(not(target_os = "macos"))]), keep throttled PATH CLI fallback on Linux.
  • 1c LocalAPI + full CLI fallback (previous plan): Keep 60s-throttled CLI fallback including macOS .app bundles.
2. macOS App Store IPNExtension discovery
  • 2a Direct libproc (proposed): Inspect same-UID IPNExtension open vnodes in-process via PROC_PIDLISTFDS / PROC_PIDFDVNODEPATHINFO (zero subprocesses, proof token never touches a pipe).
  • 2b Bounded /usr/sbin/lsof: Match upstream safesocket_darwin.go literally with a bounded child process.
3. Behavior of lf server mobile --status (Desktop’s “Refresh”) during backoff
  • 3a Strictly read-only (proposed): Always return cached manager status immediately; rely on the 5 → 10 → 20 → 30s backoff for automatic recovery.
  • 3b Non-blocking wake on Refresh: Return cached status immediately, and if enabled & sleeping in backoff (>2s since last attempt), wake the retry timer so the next check runs right away.
4. Five-second maintenance payload
  • 4a Full status at bind, status?peers=false every 5s (proposed): Verifies User.LoginName at bind while keeping 5-second checks O(1) on large tailnets.
  • 4b Full /localapi/v0/status everywhere: One endpoint and one parser for both bind and maintenance.
