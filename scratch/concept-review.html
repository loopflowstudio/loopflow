Normal path. Usually no code appears here: the repository was approved at its first rental and the stored token is checked and reused. A code appears when GitHub refuses what is stored (the approval was revoked, six months passed, the app was uninstalled, or the check of a renewed token failed). The screen does not say which; the refusal GitHub gave is dropped before the code is shown.

Failure. You are at lunch. At 14:03 code-1's Task finishes and this Machine's server gives it back: Session history copied, sandbox deleted, billing stopped. Its last step is GitHub's: end the token code-1 held. That step first waits for whoever is working on loopflow's token, which is the placement showing your code. It waits as long as the code lives, 15 minutes.

The wait is inside the server's one recovery pass, the same loop that restarts a Task run whose lf died, starts runs that were waiting on a usage limit, collects every rental's history and gives back every other rental. Until 14:15 none of that happens: web-1, whose Task finished at 14:05, stays rented and billed, and a run that died at 14:04 stays dead. The one line that says so, Waiting for another lf to finish with GitHub for loopflowstudio/loopflow; if it shows a code, approve it there, goes to the server's stderr.

Recovery. At 14:15 the code expires, the placement fails, the pass goes on. Nothing is lost, and nothing told you. On an ordinary day this needs a code on screen at the wrong moment, which is rare. The biggest mismatch: an ending is given a step that can wait on a person

Pass 4 made one step, settle, serve placement, sign-in, approval and ending with no flag between them. For the three a person runs, that is right. An ending is different in kind: it is run by lf machine end and also by the server's recovery pass (ops::recovery::settle → rental::recovery::check → mark_ended → settle_unattended), one thread that does everything else the server recovers. Earlier reviews weighed "an ending waits behind a typed code and says so" as a slow lf machine end and left it. What it stalls is the pass.

Ending built

Take the repository's lock, waiting as long as its holder takes: up to 15 minutes when the holder shows a code.

Other rentals of the repository still running: three requests to GitHub about the stored token, then SSH to each rental that is behind.

It was the last: one renewal, so the held token stops.

All of it inside the pass that restarts dead runs and gives other rentals back.

Ending proposed

Try the lock once. Held: log it and go on; whoever holds it is settling this repository now, and the ended rental no longer counts as holding anything.

Free: exactly what is built.

Commands a person runs keep waiting and saying so.

Tested. Normal: the last rental ends, the lock is free, the token is cut, as today. Failure: the lock is held by a placement. If that placement goes through, the new rental shares the same token and a cut would have been wrong anyway; if it ends in a new approval, the old token is superseded. Recovery: a rental that was behind is sent the token by the next placement or sign-in for the repository, as the docs already say. Counterexample kept: the lock is held for a second by lf ondemand login github confirming an approval while the repository's last rental ends. The cut is skipped and that token works until its own 8 hours, on a sandbox that is already deleted. This is the fallback the code already names ("a token left alone stops at its own expiry") and what Pass 3 did before the lock waited.

What changes: one branch in repository_lock for the unattended caller, one sentence in docs/subscriptions.md. What it does not fix: an ending with the lock free still spends up to three GitHub requests and an SSH per behind rental inside the pass, each bounded by its timeout. That work belongs to the separate outcome (this Machine settles each repository by itself), which should not ride the recovery pass either. If the first real run shows a renewed token loses its restriction, the cut goes entirely and this finding goes with it.

This Machine settles each repository by itself. It delivers a missed token and renews one near its end with nobody acting, which is what a rental longer than 8 hours and any headless use need. It takes its own rule for when to renew and its own place to run: after this review, not inside the recovery pass, and it would take over the re-send an ending does today.
