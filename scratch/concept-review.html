The biggest mismatch: a died run and a died conversation answer the same question in two shapes

Now 
Session (conversation)
  outlook: {kind: coming_back, at: 09:18, …}
  status_line: "died 09:16 (exit 1) · starts again 09:18"
  rule: ops::recovery::server_start
  no server → waiting_for_you + command

Task run
  state:  waiting | blocked
  reason: "Run died at implement; it is carried
           again in 2 min (restart 4 of 5)"
  rule: DiedRun::next_at + continuable
  no server → same sentence, still promising
Proposed, with or after LOO-968 
Task run
  died:    {at_step: implement, at}
  outlook: same type, same server_start rule
  status_line:
    "Run died at implement · starts again 09:18"
    "Run died 5 times at implement;
     `lf task run LOO-d` starts it again"

server_start already takes plain facts (here, exit, starts, last start), so the run can hand it its own. The run stops borrowing waiting.

Normal path: a live run has no outlook. Failure: carrier killed → coming_back. Recovery: carried again; a finished step clears the count. Give-up: waiting_for_you with lf task run. Counterexample kept: while ship has its own restart rule a shipping Task needs a third reading of one count; LOO-968 (started, unmerged) removes it. Doing this here adds a wire type to an area about to shrink. Not this work.

  2. The outlook's kind:
    1. Leave as built; clients print status_line.
    2. Split the axes: by: server | you beside what happened (never_ran | died | quit).
  3. The recovery docs' name for it:
    1. Leave: "work session" in prose, "Conversation:" on the line.
    2. Say "Task conversation" through the recovery section, as the line does.
