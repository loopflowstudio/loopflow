Worktree registration should own cache recovery

Based on scripts/build_cache.py, scripts/dev-lf, scripts/testing.md, Cargo.toml and scripts/benchmarks/crate-rebuild/results/loo-921.json.

Existing behavior

Yes, checkout → cache registration → Git hook. A new linked worktree is recorded in the Machine inventory. If the serving pinned client-side daemon lacks its root, registration requests a stop. Cargo starts a replacement on demand. In the two-worktree run, the focused test passed and one library’s cache write was lost.

No, inspect the cache → cache readiness → status. With the checkout hook skipped, a private fixture started with no daemon and no inventory. Checking status wrote the inventory and returned 0. dev-lf also writes the list, leaving a stale daemon in place. These paths carry over from the idle-based design.

Proposed usage after a skipped or failed hook

$ uv run python scripts/build_cache.py status
roots    this checkout is missing; run register
$ uv run python scripts/build_cache.py register
$ uv run python scripts/build_cache.py status
roots    this checkout is listed for the next daemon start
$ cargo test -p loopflow-execution --lib skills::catalog::
  • Inspect → readiness → cache_status. Read the configured list and the daemon’s loaded roots. A stale daemon also points to register. With a caller-owned list, point to that configuration. Reading stats still resets the idle timer.
  • Recover → worktree registration → register. The hook and manual command share the inventory update and conditional stop. A registration error still lets Git finish the checkout. A build can proceed and pay for cache misses.
  • Build → local target and shared cache → Cargo. Remove the passive refresh command and its launcher call. dev-lf --isolated-build still bypasses the cache. The measured incremental test default carries forward.

Implementation checks

  1. With a skipped hook, does status leave the missing inventory alone and does register make the next build ready? Verify both outcomes in a linked-worktree fixture.
  2. Does recovery stop only the eligible stale daemon and leave a caller-owned configuration alone? Verify both configurations.
