Normal → failure → recovery

A claim reads its repository and scope, observes that scope’s preferences, then commits. New-Task creation compares the supplied repository/Project scope; bulk hand-back batches held Tasks and observes each repository once. A changed held set that needs new configuration returns to acquisition. If Project membership, Wave ancestry or the repository address changes during acquisition, reacquire for the new scope before writing. Existing claims remain independent of changed preferences. No SQL mutex spans Git or file reads.

A dead or unknown first Session cannot hide a live available second row at limit=1. Quiet deadlines update list and Task selection without a store write. The implemented short-read → observe → compare approach retains the enclosing Work snapshot without lending a shared connection during observation.

Implemented: disconnected peer imports retain conflicts and routing; repository registration acquires Git/locator facts above SQL. A locator left by a failed import is reused on retry. Proposed Wave preparation: a file failure registers no partial hierarchy; a SQL rollback retains prepared IDs for retry. Authored bytes survive. A stale checkout cannot rename a Wave back or resurrect a retired identity; file authoring uses the requested checkout. Concurrent Dashboard edits retain stale-write checks. Cached debug paths may name a deleted checkout: use the isolated build. An unknown root may miss while another build runs; it cannot restart that build’s daemon.
