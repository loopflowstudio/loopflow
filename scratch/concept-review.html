Complete, through recovery

Proposed shared behavior on Desktop and mobile

Tap Complete → row disappears + next Task opens → save/send → request saved → settlement commits → each covering list/count incorporates the removal.

Held settlement: a refreshed list covers task.completion_requested only. Keep the row projected out: that stage confirms intent, not completed membership.

Partial failure: settlement commits, then planning sync or command output fails. Keep the completed facts and recover the remaining work in place. A definite refusal can restore only effects proved not to have committed; it never changes a later selection.

Restart: restore confirmed cache and remaining effects atomically. A fresh count must not subtract Complete twice while another list is held. Recover the saved operation on its original Machine; uncertainty never authorizes generic replay.

Start uses the same distinction: task.filed binds actual Task/Session identity; Graph admission and native readiness remain their own facts. Failed attachment keeps submitted words and offers Retry opening for the same Session.

No-op/external success: command output alone cannot acknowledge an effect. Require a domain-established result/fence or covering confirmation; filesystem/provider effects need their own confirmation contract.

Admission is built: immutable envelope before Git, deferred canonical identity, recoverable legacy adoption and one atomic CLI/served creation claim. Preserve these paths during the client migration.
