Streams belong in lf release status

Run headless, so no decision is requested. The accepted stream names settle the one change. The review sent it back to implement.

Actions → concepts → APIs

mark a regression     lf task create|edit --regressed-in v0.15.3   Task.regressed_in
daily release run     lf release run                                advance_stable → stable_advance
see where things are  lf release status                             ReleaseStatusResult

The first two hold up. A regression is one Task field. The fix boundary is the Task's completion, which in the work model is "fix shipped". The third action doesn't show any stream.

The mismatch

Existing behavior

$ lf release status
Target: lf
Latest tag: v0.16.2
Workflow: completed / success

"Latest" here means the newest tag, which is preview. Since slice 2, GitHub's Latest marker means stable. Why stable hasn't moved shows up only in the cron host's log.

Proposed (next implement)

$ lf release status
Target: lf
Preview: v0.16.2 (published 2026-10-29)
Stable:  v0.15.4
  v0.16.2 soaks until 2026-11-05
  LOO-12 holds v0.16.0, v0.16.1
Workflow: completed / success

One function builds this view, and advance_stable logs from it, so the log and status can't disagree. latest_tag becomes preview_tag. It is not a wire DTO.

Kept as is

  1. Completion time as the fix boundary. It's conservative when a release lands between merge and completion. A release cut before the fix but published after completion is still the narrow case scratch/questions.md records.
  2. Linear label mapping for regressed_in. Still open, and nothing here depends on it. Git planning exchange carries the mark to the release host once that host's lf has the field.

Questions

  1. Should status also list dev (newest green main build)? a) yes, b) no, because dev belongs to lf install (slice 4).
