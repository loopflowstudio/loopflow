One interaction, walked

Normal: someone wants a newer crate or action

a Task→cargo update -p x or a new SHA→PR + CI + queue→main

One owner, one commit. .github/CI.md now carries the three commands. An action bump is the same SHA replaced on up to 23 lines; one find-and-replace. built

Failure: a version we are on turns out to be vulnerable

advisory published→nobody here is told→stays until someone happens to look

Before, the weekly bot would have moved past it within days, unread. Now nothing moves and nothing announces. The safe direction changed from "takes bad releases fast" to "keeps bad releases long".

Failure: an upstream release is malicious

library→lockfile commit→main
action tag moved→nothing: pinned by commit
new Rust stable, uv, xcodegen, runner image→no commit→next build

The third row is the stated, documented choice.

Recovery

Any bump, library or action, is now one git revert, and history says which commit of which action built which release. This is what the pin pass bought. The pinned workflows themselves have not run yet: see "Not yet exercised".

The biggest mismatch

"Alerts are the prompt for a hand bump", and no alert can be shown to arrive

What was observed today on loopflowstudio/loopflow:

  • The alerts setting is on (/vulnerability-alerts → 204).
  • The repository has 0 alerts in any state, ever: none open, none fixed, none dismissed. That is with 425 Rust packages and a year in which Dependabot merged 91 bumps.
  • GitHub's dependency graph, which alerts are computed from, lists 0 manifests for the repository, and the SBOM endpoint returns 404. The cause was not determined from here; it reads like the graph being off or empty.
  • GitHub's docs: "For GitHub Actions, alerts are only generated for actions that use semantic versioning, not SHA versioning." Pinning by commit, done on this branch, opts the 8 build steps out of alerts.
  • uv.lock is not in GitHub's table of supported files (pip and Poetry are), so Python is probably not covered either. Not confirmed.

So the design has a named signal and, as far as can be seen, no signal. "Dependencies change by hand" then means "dependencies change when someone happens to think of it", including for a published vulnerability.

What survives, what changes on purpose

  • Survives: every lockfile, CI, the merge queue, package and release workflows, release notes that mention Dependabot.
  • Changes on purpose: dependencies and build steps stay where they are until someone moves them.
  • Counterexample that broke the last draft, now closed: a moved action tag.
  • Counterexample that breaks this one: a vulnerability published tomorrow in a crate, a wheel or an action. Nothing here would say so.

Questions

Questions 1 to 3 are new. 4 to 6 were asked in the last draft, are unanswered, and the plan took the recommended option for each.

  1. What should tell you a dependency you are on has a known vulnerability? Right now, as far as can be seen, nothing would: GitHub has never raised an alert on this repository and cannot raise one for the pinned build steps.
    1. Recommended. You look at the repository's security settings once and switch the dependency graph on if it is off. This PR corrects the docs to say what alerts do and do not cover. What stays uncovered becomes its own Task.
    2. Nothing needs to. Bumps happen when someone thinks of it; the docs drop the sentence about alerts.
    3. A scheduled check that files a Task when an advisory matches. New behavior; its own Task, not this PR.
  2. If someone later adds a build step that is not pinned, should GitHub refuse to run it? Today it would run and nobody would notice the rule had lapsed.
    1. Recommended. Yes: turn on the repository setting after this PR merges. A workflow with an unpinned step fails with a message saying why. Can be switched off again.
    2. No: the documented grep is enough.
  3. One of the eight pins is to code published 14 hours earlier. Keep it? It is the step that installs the test runner in CI. The brief named "no cooldown" as part of what went wrong.
    1. Recommended. Move that one pin to a commit at least two weeks old before landing. The test runner is a slightly older version.
    2. Keep it. It is one maintainer's routine release and CI is the only thing it touches.
  4. The merge key: who revokes it, and is it used anywhere else? Revoking cannot be undone, and only you can see what else uses that token.
    1. Recommended, taken. You revoke the token on GitHub after merge; an agent may then delete the two stored copies and the five branches.
    2. An agent does all of it after merge, on a clear yes.
    3. The token is shared with something else: keep it, delete only the two DEPENDABOT_MERGE_TOKEN entries.
  5. When a bump is done "by hand", does a person read it before it merges?
    1. Recommended, taken. No extra rule. Someone chose to start it; the PR says "by hand" does not mean "reviewed".
    2. Bump Tasks always stop for a person. Needs a way to mark such a Task, which does not exist.
  6. Should a new Rust compiler also arrive only in a commit?
    1. Recommended, taken. No. The compiler and tools keep floating, and the docs say so.
    2. Yes. Every Rust release then needs a bump Task.
