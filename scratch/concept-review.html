Recover the connection to the same Session.

Design changed: make a lost Machine connection recoverable without invoking provider resume. Jack Heart's accepted continuity contract settles this direction. Keep the existing deliberate retry policy.

Headless review. No new product approval is inferred. Implementation and proof remain; no code changed in this review.

One interaction

Action: Open a Task → edit its existing Session → the helper restarts → reconnect.

Concepts: Task → recorded primary Session → existing execution owner.

APIs: read(view_plan) → session_owner(session) → attach(owner) → existing binary owner protocol.

The Machine service carries requests and output. The Session owner keeps the provider, draft, input claims and lifetime policy. The Graph keeps its execution. Desktop keeps UI automation and terminal rendering.

The consequential mismatch

Existing implementation

Bridge EOF exits the terminal relay. Desktop enters its ended/elsewhere view path; ordinary preparation uses lf resume --prepare. The restart fixture closes its viewer before restarting the helper, then creates another fixture viewer. It proves owner survival without exercising recovery of the interrupted Desktop relay.

A failed connection does not establish that the provider ended. Recovery must not turn that uncertainty into permission to resume a provider.

Proposed experience · not yet implemented

Machine connection lost.

Reconnect → the same owner → continued output or a fresh screen.

If another viewer controls this Session, show its output. Move here remains a separate deliberate action.

If that owner has ended, report it. Opening provider history remains the existing explicit Open action.

Reconnect refreshes Work and sends no buffered typing or command. A lost rename reply remains “outcome unknown”; read its current name before deciding whether another rename is needed.

Follow recovery through the layers

The client retains the exact owner and, while its relay lives, the existing reconnect token and output position. Reopen the Machine bridge and use the owner's Resume protocol. If its output window expired, obtain a fresh screen from that same owner. A reopened Desktop can also request a fresh screen without saving viewer state on disk.

The owner alone grants input and geometry. Recovery cannot unconditionally repeat control: true and own: take from the initial attachment. It cannot fall through to a new owner or provider launch.

No durable connection record, service-owned viewer registry, scheduler, PTY manager or retention policy is needed. Work subscriptions retain their existing fresh-reading recovery. Migrated operations keep one socket path.

Counterexamples the next proof must survive

  1. Normal recovery: keep the real terminal relay connected during helper replacement. Reconnect through the client and finish an unsubmitted draft with the same owner, provider and running Graph.
  2. Another viewer takes control: reconnect observes the Session without stealing input or geometry. No uncertain keystroke is resent.
  3. The output window expires or the owner ends: refresh the screen from the same live owner, or report unavailability. Never silently substitute provider history or another conversation.

Installed executable replacement, actual Desktop quit/reopen, disabled/version states, slow-client cancellation and unchanged usage totals remain acceptance work. Separate registrar and restart fixtures do not replace those proofs.

Review questions and disposition

  1. Does a connection retry authorize provider resume?
    Resolved: no. Implement recovery of the exact existing owner and preserve separate explicit Open and Move here actions.
  2. May recovery displace a newer controller?
    Resolved: no. The accepted contract already forbids it; use the owner's existing claim rules.
  3. Does this select remote admission, phone takeover or unattended hosting?
    Unresolved later scope: none is needed to settle this local correction, and none is approved here.
