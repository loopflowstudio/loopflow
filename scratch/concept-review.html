Keep Reconnect on the selected Session.

The accepted same-Session recovery contract implies this correction. A failed attachment attempt must not force a trip back through Tasks. Recorded as next implementation direction; code is unchanged.

Jack Heart selected open Tasks → existing Session terminal, Desktop styling, and Paste / New line / keyboard visibility. The current native build is an explicit offline fixture. This review adds no screen, provider conversation, or remote takeover policy.

Proposed usage copy: If opening or reconnecting fails, choose Reconnect on the Session screen. Reconnect restores viewing. In the offline fixture, choose Use keyboard again before typing; inspect the prompt before resubmitting anything whose delivery was uncertain.

Actions → concepts → APIs

Open a Task
Existing Task → selected Session ID → open(task) → attach(sessionID:). Opening observes; it does not grant input or geometry.
Reconnect here
Selected Session survives; attachment is replaced → reconnect(). Failed connection attempts stay retryable in the same screen. No automatic retry loop, launch operation, or second owner resolver.
Type after recovery
Program owns the draft; attachment owns revocable permissions → fresh snapshot → viewing → explicit fixture requestControl() → send(bytes). Resize remains separately gated.
Encounter a missing or ended Session
Retain work identity → explicit unavailable/ended explanation → Tasks navigation. Do not manufacture a replacement Session. Reject a mismatched Session ID before rendering it.

The correction reuses existing UI states. It needs no persisted recovery record, client-side draft, domain DTO, or wire schema. LOO-593 remains the owner of Machine errors, Session lookup, and terminal transport. A future adapter must distinguish authoritative permanent failures from connection failures.

Challenge the recovery contract

Normal path: open → observe → fixture control → type → Return. The reduced key bar and direct Task navigation stay intact.

Failure and recovery: first attach fails, a retry also fails, then attachment succeeds. Reconnect stays visible through both failures, and success restores the identical Session as an observer.

Uncertain input: the peer accepts bytes, then the send operation reports an error. Recovery must show those bytes once from the peer’s snapshot; it must not send them or Return again. The existing drop/reconnect test does not exercise this accepted-then-error boundary.

Counterexample: the returned attachment names another Session, or the owner reports an ended Session. Treating every failure as a retryable disconnection would erase useful evidence. Keep those outcomes explicit and never attach a replacement behind the selected Task.

Scope and next proof

Verify the visible retry action through repeated failure, observer-only recovery, wrong-Session rejection, and an uncertain send. Existing mounted UIKit tests are prior evidence for fixture input; no tests were rerun for this design-only review. No rendering environment was available to inspect this page visually.

Carrier/pairing, remote takeover gesture, and hosting tier remain open for follow-up C. They do not block this fixture correction. Physical keyboard, IME/dictation, VoiceOver, and live Tailscale proof remain outstanding. Contextual approval/Stop controls still require trustworthy provider state and action bindings.

Review questions and disposition

  1. Should a failed attachment require returning to Tasks?
    No. The accepted recovery contract implies an in-place retry; implement the correction.
  2. Does Reconnect restore keyboard control or resend input?
    No. It restores viewing of the same Session; existing control and no-replay rules remain.
  3. Does this review select a remote takeover gesture or hosting tier?
    No. Those remain unresolved follow-up choices, outside this fixture correction.
