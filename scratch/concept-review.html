Signing Machines in, as built

Area: how a Machine (this one, an owned one, a rental) comes to be signed in to Claude, Codex and the services, how a person sees that, and what a launch does when it isn't. Taken whole because the rescope changed Claude's half from a sign-in into a forwarded secret, and that seam is where the concepts now disagree. Reviewed at bf28572dc3 against base 250e266b4a, with the QA run of 2026-11-23 (scratch/qa.html).

One interaction, walked

A person following docs/subscriptions.md runs claude setup-token, doppler secrets set CLAUDE_CODE_OAUTH_TOKEN, lf set --global forward.env '[CLAUDE_CODE_OAUTH_TOKEN]'. Later, in another checkout or a shell without doppler run, they launch on Codex:

$ lf --machine mini -b -a codex : 'say hi'
Error: forward.env names CLAUDE_CODE_OAUTH_TOKEN, which has no value on this Machine: export it, …
$ lf machine logins mini
claude   signed out
codex    signed in   ChatGPT

Codex is signed in on mini and the run never asked for Claude, yet it stops. The logins table says Claude is signed out on mini, which is the target's own reading and not the reason. QA recorded both as the worst rough edge and left them.

The cause is a naming one. To the person, the token is Claude's login on other Machines: the docs, lf machine login claude mini's refusal and the forwarded row all say so. To the code it is one more forward.env entry, a per-run secret, and forward::read treats every named secret as required. A missing login should mean "Claude signed out there": the launch check skips Claude's models and moves to the next provider. A missing required secret means "this config is broken, stop everything".

The recommendation

Before (built)

forward.env: [CLAUDE_CODE_OAUTH_TOKEN]
# token not in this shell
lf --machine mini -a codex …
  Error: forward.env names
  CLAUDE_CODE_OAUTH_TOKEN, which has
  no value on this Machine
lf machine logins mini
  claude  signed out

After (proposed)

forward.env: [CLAUDE_CODE_OAUTH_TOKEN]
# token not in this shell
lf --machine mini -a codex …
  (runs on Codex)
lf --machine mini -a claude …
  mini has no Claude login; give this
  Machine CLAUDE_CODE_OAUTH_TOKEN
  (doppler run, or doppler secrets set)
  → continues on Codex if the order has it
lf machine logins mini
  claude  signed out  CLAUDE_CODE_OAUTH_TOKEN has no value here
Proposed, choice made for review. Claude's token is a login, so it fails like one. forward::read leaves out login::CLAUDE_TOKEN_ENV when it has no value here instead of erroring; every other forward.env name stays required. The target's launch check then reads Claude signed out and does what it already does for Codex: skip, fall back, or stop with advice. The advice for Claude names giving this Machine the value, since forward.env may already name it. logins keeps the target's row and says why in the account column. Rental place reaches its own "no agent login" stop. No new state, no new type; forward.rs gains one exemption and loses a failure mode for every launch path (ssh.rs, write.rs, rental.rs).

Passed over: (a) a forwarded, no value here state in LoginState, which adds a wire value for what the account column can say; (b) forwarding the token whenever it is in this Machine's env with no forward.env entry, which drops the opt-in that keeps a person's token off third-party rentals they didn't choose; (c) making every missing forward.env value optional, which turns main's deliberate rule for real per-run secrets into silent omissions.

Counterexample tested: someone who wants Claude and forgot doppler run. Today they get a stop naming the variable. After, a Claude launch on mini is refused before its agent starts with a line naming the variable, and continues on Codex only if their order includes it, with the fallback line printed. Nothing runs on Claude without a login, and the fixing command is still on screen.

Larger than this work

  • The CredentialInvalidated wording above the advice. ops/release.rs and release_tests.rs match the string, so it is its own change.
  • lf set printing its effect variant (saved; NextLaunch), seen in QA; also on released lf.

Questions

  1. When forward.env names CLAUDE_CODE_OAUTH_TOKEN and this shell lacks it, should launches
    1. treat Claude as signed out there and go on (proposed, in the plan)
    2. keep stopping every launch, as main's rule does
    3. treat every missing forward.env value as optional
  2. Should lf machine logins mini, in that case, show
    1. the target's row with "CLAUDE_CODE_OAUTH_TOKEN has no value here" (proposed)
    2. a new forwarded-without-value state
  3. lf machine logout claude mini runs claude auth logout there, though launches from here use the forwarded token. Keep it, refuse it like login (naming forward.env), or
    1. keep (as built)
    2. refuse like login
  4. Should a usage-limit refusal count for --refused?
    1. yes (as built: any refusal counts)
    2. no, only signed-out or revoked
