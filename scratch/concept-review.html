What a theme is, and where the title bar fits

Area taken: the theme as a whole, as it stands with this Task's plan in it. That is the theme file and its roles, how missing roles are filled in, what the app paints from them, the editor, and the two defaults as a pair. The plan's one model change is a new role for the title bar, so that is where the review goes deepest. Nothing is built yet; no code changed here. Things marked proposed do not exist.

The biggest mismatch: the title bar

The plan's answer holds: make the bar a role, loopflow-titlebar, stated in the file like every other color and derived at import when a file leaves it out. The measurements in the plan rule out the alternative (no single mix gives Dark a burgundy bar and keeps the other eleven readable), and after this work the bar differs from the accent in 17 of 24 themes, so a separate name is the true one.

Three things in the plan do not survive being walked through, and are changed.

1. The fallback must run after the file's own roles

The plan derives a missing bar inside GhosttyThemeMapping.palette(terminal). That function sees only terminal colors; its accent comes from ANSI 4. ThemeFile.parse applies the file's stated roles afterwards. A theme saved by the editor before this change states its accent and has no loopflow-titlebar, so its bar would come from ANSI 4, not from its accent. A green-button custom theme would wake up with a blue-grey bar. The same goes for loopflow-appearance.

// plan as written
var palette = GhosttyThemeMapping.palette(terminal)
// titlebar already fixed here, from ANSI 4
palette.isDark = dark
for role in appRoles { …stated roles… }
// proposed
var palette = GhosttyThemeMapping.palette(terminal)
palette.isDark = dark
for role in appRoles { …stated roles… }
if roles["loopflow-titlebar"] == nil {
    palette.titlebar = GhosttyThemeMapping.titlebar(
        accent: palette.accent,
        background: palette.background, dark: dark)
}

2. One rule for the fallback, and it is the rule behind the five fixes

The plan keeps "today's bar exactly" for files without the role, and separately hand-darkens five light built-ins, and adds a test that the bar's text reaches 4.5:1 "in every built-in and in the five derived fixtures". Those three cannot all be true. Under today's rule the fixture 747474/FFFFFF gets bar #717478, secondary text 3.29:1: the new test fails on the rule the plan promised to keep. Every light import whose accent lands at the mapping's floor has the same unreadable path today.

One rule covers all of it: start from today's color, then darken (same hue) until the 72% text reaches 4.5:1. Measured with the audit's functions:

Loopflow Dark is the one theme the rule does not serve (it would give #4c3237), which is what the stated role is for: loopflow-titlebar = #722f37.

3. The check belongs where the other text checks are

PaletteDefinition.readabilityErrors is the one predicate for "this theme's text can be read"; a built-in that fails it does not load. Title bar text and its 72% level join it, with the 0.72 named once and read by both the check and titlebarSecondaryText. WorkPaletteTests then covers the derived fixtures through the real palette. And one expectation holds the pair together: ThemeDefinition.light and .dark state the same bar. Break "Dark looks like Light's sibling" in your head and today nothing fails; with this, something does.

Outside this work

Each of these is its own outcome; none is needed for the two defaults to be right.

  • A diff role. diff-added and diff-removed tints, separate from chip fills. Takes two roles, a mapping rule, and 24 files.
  • Roles that are formulas. Hover, pressed, button text, and now the bar in 23 of 24 files are a rule's output written down. A theme could state seeds and exceptions only. That changes what a built-in file is, and the "state every role" rule with it.
  • The prototype's second catalogue. design/prototypes/desktop-themes.js restates all 24 themes by hand under different names (keyboard-focus, waiting). This work updates it by hand once more; generating it from Catalogue/ would end that.

Questions

  1. A personal theme that leaves out the title bar:
    1. gets today's color, darkened only if its second text level is unreadable (chosen for review);
    2. gets today's color exactly, readable or not, and the five built-ins are fixed by hand.
  2. In the editor, when a custom theme's "Button" changes:
    1. the bar stays where it is, like hover and pressed (chosen; what the stated role means);
    2. the bar follows until the person has set "Title bar" themselves, which needs the editor to leave unstated roles out of the file.
  3. Loopflow Dark's bar:
    1. #722f37, Light's own, 1.4:1 against the window, separated by hue (chosen);
    2. #8a3a44, Dark's button fill, a little more separation, secondary text 4.78:1, and the pair no longer shares one bar.
  4. The five light built-ins whose bars get darker (Catppuccin Latte, Gruvbox Light, Flexoki Light, Linen, Noctis Lilac):
    1. darken them, as above (chosen);
    2. leave them at 3.35 to 4.35:1, and exempt the title bar's second text level from the 4.5:1 rule.
