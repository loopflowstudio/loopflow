Working Task order, status and sidebar

Area reviewed: Working Task ordering, one-shot status sorting, row status & Graph step display, write recovery, and New Task fonts across Desktop, CLI, and iOS — widened to the whole sidebar and selection model because B1 introduced a shared start-time stack, a status sort, a Graph step wire field, and OSC 7501 done availability on top of PR #2025’s drag-and-drop repair.

Biggest mismatch: “Status” in Sort by status disagrees with “Status” on the row

Built at 1e3b4007ce Two separate precedence rules exist for the same word. On the row, Mac (ProgramStatusState.summaryOrder) and iOS (WorkViewPlan.Content.status) rank Blocked > Error > Busy > Available. In the one-shot sort, Rust (status_bucket) ranks Blocked > Available > Idle > Busy and ignores Error altogether. Clicking Sort by status puts a row whose label says Busy (one working Session, one idle Session) above Idle rows, and drops a red Error row below Available rows.

Proposed Give row status and one-shot sort one vocabulary and one precedence: project OSC 7501 error into SelectionState::Error (also surfacing Error in attention and on iOS), and bucket Blocked → Error → Available → Idle → Busy using the row’s own winner so a dual-state row labeled Busy sorts with Busy while still matching both state:available and state:busy filters.

Two related mismatches found in the same pass:

  • Two Desktop write paths for one Working order: Dragging routes through PendingChanges (retries blips under one requestID, disables offline, protects Notices), while WorkModel.sortWorkingTasksByStatus() bypasses it — failing on a blip, staying enabled while the Machine is away, and letting an in-flight drag replay over a newer sort.
  • Graph step sentinels leak into the sidebar: fill_graph_steps_in returns raw task_graphs.step values "start" and "end" instead of matching TaskGraph::read’s current_step = None; and iOS TaskListView drops graphStep even though the wire already sends it.

      Failure, recovery & counterexamples checked

      Task has one Working Session and one Idle Session
      Both Mac and iOS rows display Busy. Under the proposed bucket rule, Sort by status places it in Busy so the sorted list never shows a Busy row above Idle. Because SelectionState remains a set, the Available and Busy filters both still include it.
      Task has a Blocked question AND a Working sub-process
      Blocked outranks Error, Busy, and Available in both row display and sort bucket (0). The row says Blocked and sorts at the very top.
      Build or provider emits OSC 7501 error, then person types
      Error appears in red on Mac and iOS, joins attention, and sorts right behind Blocked (bucket 1). Typing in the pane clears error via acknowledge_results / ProgramStatusReducer.interaction; the saved order stays put until the next sort or drag.
      Drag Task C above A, Machine blips 1 s, person clicks Sort by status
      Both writes sit in PendingChanges with distinct requestIDs and retry across the blip. Once Sort is queued after the drag, workingOrder stops replaying the pre-sort drag preview over newer readings; a drag made after Sort still previews on top.
      Machine is offline >10 s (Link.away)
      Both the sidebar Sort by status button and ⌘K action respect pendingChanges.acceptsChanges (disabled / away notice), matching every other Work mutation control.
      Task leaves Working (completed/unclaimed) and later re-enters
      Counterexample noted: task_orders prunes departed Tasks on the next drag or sort, not on completion/unassign, and started_at uses first claim (MIN(o.at)) so Machine handoffs keep original start time. Reclaiming a Task before any drag/sort keeps its old slot rather than prepending. Acceptable trade-off vs writing task_orders on every completion/unclaim, documented explicitly.
      Graph parked at start or finished at end
      fill_graph_steps_in returns None when parked at START or END (matching TaskGraph::read). While running (run_start set), it resolves the live cursor step name as today.
      Task blocked by Graph/git condition with no live terminal report
      Boundary noted: TaskCondition::Blocked (e.g. missing worktree or merge conflict) is derived during full roadmap snapshots, not in SQLite selection reads. SelectionState::Blocked reflects program/session reports only. Unifying condition derivation into SQLite selections is separate architectural work outside LOO-1063.

      Choices made for review

      In headless Graph execution, the bold choice in each pair is written into scratch/plan.md for the next implement pass. Reply with e.g. 1b to override any choice.

      1. When a Task has one Busy Session and one Available Session, where should Sort by status place it?
        1. Match the row’s own status word (Busy → bottom bucket). Chosen for review: both Mac and iOS rows print Busy, so sorting it as Busy prevents a Busy row from sitting above Idle. Both Available and Busy filters still include it.
        2. Keep Available ahead of Busy in the sort, and also change Mac/iOS row display so dual-state rows print Available instead of Busy.
      2. How should OSC 7501 error sort in Sort by status?
        1. Project SelectionState::Error and sort Blocked → Error → Available → Idle → Busy. Chosen for review: matches ProgramStatusState.summaryOrder, keeps failures above Available, and brings red Error status to iOS too.
        2. Merge Error into the Blocked bucket without adding a new SelectionState variant (leaves iOS unable to distinguish Error from Idle).
      3. Should Sort by status guess a local preview before the Machine replies?
        1. Route through PendingChanges without a guessed preview, superseding pre-sort drag previews. Chosen for review: ViewContent does not carry started_at, so a client preview would guess within-bucket order and flicker when the Machine answers. Routing through PendingChanges still gives blip retry, offline disable, and race-free reconciliation with drags.
        2. Carry started_at on ViewContent so the client can compute an exact instant preview of Sort by status too.
