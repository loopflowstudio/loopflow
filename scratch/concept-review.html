The command lf open puts in a host pane, as built

LOO-986, second concept review, 2026-11-19, of the branch at 1785859962 against its base 2750c9e0fb. Text in blue is proposed; the rest exists on the branch.

Area taken: one opening, end to end: the command lf open writes into a pane, what that command inherits, which harness it names, and the answer the caller gets back. The whole change sits there, and so do the three things QA found still wrong.

One opening, walked

/bin/sh -c '<wrapper>' lf-open /tmp/…/receipt env -u LF_AGENT_CALLER -u LF_AGENT_OVERRIDE \
  LF_OPEN_RECEIPT=/tmp/…/receipt  /…/lf session resume ses_1
  1. The pane's lf (the viewer) appends the tool directories to its PATH and starts the launcher in a held terminal.
  2. Normal: the launcher spawns the provider; the viewer writes attached; the caller reads status: usable.
  3. Failure: no claude. The launcher's main writes 'claude' is not installed. … to the receipt; the caller reads it as reason; the pane shows the same text and waits for Enter.
  4. Recovery: install it, run the same lf open. The command names no harness, so nothing moved in between.

The command is now a name for a conversation. That part of the first review held up in QA on tmux, Rex and Herdr.

Biggest mismatch: who answers an opening

A person thinks of one opening with one answer. The code has a variable in the environment, and main lets every failing lf that holds it write the answer. First answer stands, so the earliest failure wins, whoever it was.

Counterexample. agent_process::require_server runs lf install server and carries on if the server answers afterwards. That child inherits the variable. If it exits with an error and the server is up anyway, its error is the first answer: the conversation attaches and lf open reports failed. When the launch really fails, the reason is the install child's, not the launcher's "Loopflow server is not running". lf starts itself from about fifty places; the branch already strips the variable at one of them (native_session.rs:571, the provider).

Before (built)

LF_OPEN_RECEIPT in the environment
  viewer        may answer
  launcher      may answer   (inherited)
  lf install…   may answer   (inherited)
  any lf child  may answer   (inherited)
  provider      stripped by hand
+ viewer keeps a 4 KiB tail of relayed output

Four rungs: launcher's error, viewer's error, tail, wrapper's status line. The third is unreachable for its stated purpose.

After (proposed, in the plan)

main takes LF_OPEN_RECEIPT out of the environment
  viewer        answers
  launcher      answers   (handed on by start_held)
  everything else never sees it
no tail

Three rungs: launcher's error, viewer's error, wrapper's status line. Nothing to strip, so the strip at the provider is deleted too.

Choices made for review

  • The tail is deleted, not kept as a net. It could only answer for a launcher that crashed without returning from main; the pane still shows that. Passed over: keeping it. It comes back if usable is ever made to wait until the provider takes input, because then a provider's early exit is a failed opening and its last words are the reason.
  • The receipt is handed on by name. Passed over: stripping it at each place lf starts lf, or leaving it ambient.
  • The bare-PATH fixture returns early on a Machine with claude in a system tool directory. Passed over: a variable that makes lf skip a directory (a knob only tests would set), or a test that fails on such a Machine.
  • Docs: docs/workspaces.md stops promising "the provider's last words".

Larger than this change

  • usable is "spawned". To mean "takes input" the acknowledgement would move from NativeStarted to a signal each harness gives when it is ready; four harnesses, and a timeout story for one that never says so.
  • A failed move is still a move. Recording the harness after it starts, or undoing it when the launch fails, belongs to lf session resume --agent, not to lf open.
  • "Not installed" for nvm, mise, asdf tools. Since #1981 a person's terminal PATH reached the pane; the brief asks for that deleted so an agent's shims stay out. Either carry PATH only when the caller is a person, or run the pane command through the person's login shell.

Questions

  1. The relayed tail:
    1. delete it now (in the plan);
    2. keep it for a crashed launcher;
    3. keep it and move usable to "takes input" in this Task.
  2. Who may answer an opening:
    1. the viewer and its launcher, handed on by name (in the plan);
    2. any lf that inherits the variable (built).
  3. Tools behind shell rc (Pi under nvm reads "not installed"):
    1. accept, add directories as they are missed (built);
    2. carry the caller's PATH when the caller is a person;
    3. run the pane command through the login shell;
    4. keep (a) but say "lf did not find 'pi' on its PATH" instead of "not installed".
  4. A failed lf open -a <harness>:
    1. leaves the conversation moved (built);
    2. records the move only once the harness starts, as its own Task.
