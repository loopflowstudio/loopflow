2. The biggest mismatch: stopping at a loop cap and recovering

Biggest Mismatch A Blocked Graph stop is invisible to lf task status and task-session, and the kickoff plan's recovery path traps the person in wasted sessions.

In the kickoff plan, RunningGraph::run_skill threw away the decider's Iterate verdict on pass 6 and returned SkillOutcome::Blocked. Because the deciding step itself exited 0 while the Graph exited 3, three surfaces broke at once: lf task status said Idle without the reason, task-session woke with "failed · realign: succeeded", and running lf task run (with or without raising max_loop_passes) re-ran a cold-cache realign session from scratch.

Architecture Follows the Concept One owner per job, zero new tables, zero schema migrations
  • Loop transitions & pass bound: transitions::finish_step(steps, index, progress, max_passes) owns all backward-edge rules (repeats, direction, verdict, and max_passes). GraphRunner::tick asks SkillExecutor::loop_pass_limit(&skill) when settling a saved verdict.
  • Wave-aware config resolution: RunningGraph resolves max_loop_passes via load_wave_config(Some(self.cwd), wave) + config::settings::resolve(&config, Some(&skill.skill)), honoring --setting, LF_SETTINGS, personal/repo/Wave, Skill, and Graph-step scopes.
  • Truthful blocked status & updates: ops::task_execution::project_execution checks graph.run.error when latest.run succeeded (marking "Graph is blocked:" and non-GraphHeld errors as TaskExecutionState::Blocked while keeping GraphOutcome::Waiting handoffs Idle); task_updates::RunObservation includes graph.run.error on settled runs.
  • Step commits: ops::commit::commit_step checks git diff --cached --name-only --no-renames -z; when every staged path starts with scratch/, it commits and pushes deterministically (lf <step>: update scratch/…) with 0 LLM calls.
  • Quiet running steps: harness::task_updates::write records only settled runs and ignores TaskGraphPosition::Run { running: true, .. } movement, aligning a Task's own conversation with conducted child notices.

3. Counterexamples tested against the revised model

1. Bare lf task run after cap stop (no cap raise) Because cursor.progress.verdict keeps Some(Iterate, …), GraphRunner::tick re-settles immediately against max_loop_passes = 6 and stops in <10ms with 0 LLM calls and prints exact recovery commands instead of wasting a decider session.
2. Auto-standing-in interactive: ship-review hits cap execute() sees (GraphOutcome::Blocked(_), Some(skill)) with skill.interactive_step() == Some("ship-review") and calls arrive_task_graph, handing the Task cleanly back to the person at At { step: "ship-review" }. Live humans (!standing_in) get loop_pass_limit = None and are never capped.
3. lf pr land handoff (GraphOutcome::Waiting) lf pr land exits 0 and returns Waiting → GraphHeld("Graph stopped before its last step…"). project_execution only promotes "Graph is blocked:" (or non-GraphHeld errors) to TaskExecutionState::Blocked, so healthy landing handoffs stay Idle.
4. Wave-scoped max_loop_passes A Wave like optimize or coverage sets max_loop_passes: 12 in .lf/wave/<name>/config.yaml. Using load_wave_config (resolving Wave from CLI --wave or Task's wave_id) instead of load_config_or_default ensures Wave settings take effect.
5. Nested loops in build.yaml repeats is keyed per loop edge and stays cumulative across outer passes. Inner realign is bounded to 6 total passes across the whole run (never 6 × 6 = 36), and outer concept-review is bounded to 6 passes.
6. Code file renamed into scratch/ Default git diff --cached --name-only -z can report only the destination path on a rename. Passing --no-renames exposes the deleted source path outside scratch/ so real code changes always invoke commit-message.
7. Pre-upgrade task_update_readings & crashed runs While a run is live (running: true), task_updates::write retains old.position and omits unsettled runs, producing 0 spurious wakeups on upgrade. A SIGKILL'd run still yields observed_result().outcome() == Some("unknown") and running: false, waking task-session once.
8. Explicit --from <decider> after steering If a person steers the Task or edits scratch/plan.md and wants the decider to re-evaluate from scratch without raising the cap, lf task run ISSUE --from realign creates a fresh cursor (clearing verdict and repeats) and re-runs realign.

  • External repository custom Graphs (e.g., manabot/.lf/graphs/coverage-working.yaml): Automatically benefit from updated builtin skills (extends: builtin), max_loop_passes, zero-LLM scratch commits, and quiet task-session wakeups; moving heavy reviews into an outer loop is an edit in those repos, guided by the updated docs/orchestration.md.

5. Decisions made for review

None of these choices are irreversible once shipped. The highlighted option in each question is what the revised scratch/plan.md builds; reply with e.g. "1b, 2a" to steer any of them.

  1. 1. Default autonomous loop cap & warning threshold
    • 1a Chosen for review: Default max_loop_passes = 6 (0 or null = unlimited), deep-loop warning from pass 4 onward, final-pass notice on pass max, autonomous deciders only (live human interactive steps uncapped).
    • 1b Tighter default max_loop_passes = 4 (warns at pass 3, stops at 4; requires raising for 5–6 pass Tasks and optimize).
    • 1c Warning-only by default (max_loop_passes: null), opt-in cap per repo/Wave.
  2. 2. Resuming after hitting max_loop_passes
    • 2a Chosen for review: Preserve the decider's Iterate verdict on cursor.progress.verdict and enforce the cap in transitions::finish_step. Raising max_loop_passes continues straight into the loop body with 0 wasted decider sessions; bare lf task run stops immediately in <10ms; --from <next> advances; --from <decider> re-evaluates.
    • 2b Discard the verdict on cap stop so any lf task run re-runs the decider from scratch (simpler cursor, but wastes a cold-cache decider session on every resume or accidental rerun).
  3. 3. task-session wakeups during healthy Graph runs
    • 3a Chosen for review: Silence all intermediate running-step updates for a Task's own conversation (matching conducted children); wake once when a run settles (finished, blocked, failed, crashed, interactive stop), PR merges, Task closes/reopens, or a comment/steer arrives.
    • 3b Keep one wakeup when a Graph starts running, silencing only subsequent step ticks.
  4. 4. scratch/-only automatic step commits
    • 4a Chosen for review: Keep committing and pushing scratch/ checkpoints, but write a deterministic subject (lf <step>: update scratch/…) with 0 LLM calls whenever every staged path (with --no-renames) is under scratch/.
    • 4b Skip committing scratch/-only changes altogether (saves commits too, but loses pushed crash-recovery checkpoints between steps).
