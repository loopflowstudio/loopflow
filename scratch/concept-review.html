Fork 2: how long a conversation lives

LOO-823's demo review, Jack Heart: "with bare lf, noting holds its at all", "with task sessions, i think we can just hold them until the task is closed basically", "wave/repo should behave exactly like open tasks tho", "whatever gets to the cleantest possible world fastest. transition costs ok".

LOO-823's next pass deletes the two-minute idle ending, DetachedLimit, idle_retention and the native-input ledger. On this branch, commit e7198a3b7 gave held terminals "one lifetime watcher", and it runs that same grace (transport/lifetime.rs: end_detached_after, idle_retention). Whichever PR lands second meets the other's code at that point.

Under LOO-823's rule a held terminal has a simple life: it runs until its Task is done or abandoned, or its Wave conversation closes, or its agent exits. Nothing in the holder or the registry has to measure quiet.

ProposedHeld terminals take LOO-823's rule from the start. LOO-824 drops the idle grace for held terminals rather than sharing it, and syncs onto LOO-823 once it lands. LOO-823's deferred piece, suspending conversations past a per-Machine agent limit, was planned to "read the input line off the server's emulator". That emulator is LOO-824's. It becomes a follow-up Task on top of both.

Two smaller joins

Status reading moves to the server

LOO-822 makes "is the agent waiting on you" come from the Session's status reports. Today Desktop reads them from its own Ghostty pane and sends session.status writes, so a Task conversation nobody has open in Desktop reports nothing. A held terminal has the server's emulator reading every byte, viewed or not.

ProposedA follow-up Task, not this one: the server reads status for every held terminal, and Desktop's writes remain only for what isn't held.

One rule for a server of another build

LOO-821's open question is a stale server that passes the launch check and then answers no boundary. LOO-824 has just built the same fix for its own socket: a revision in the first exchange, and a client that finds a different one replaces itself (a view) or records a gap (a launcher). The hook side is the same situation.

ProposedHooks follow the same rule: a revision on session.boundary's first exchange, and a mismatch recorded as a RecordingGap that names lf install. That is LOO-821's call; it is listed here because the two should match.
