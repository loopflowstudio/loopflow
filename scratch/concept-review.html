What a person holds in their head: code-1 can use GitHub until 17:00. What the code holds: the repository has one token; code-1 and code-2 were last sent it. GitHub forces the second shape (a grant has one live token, and a renewal kills the old one), so sharing is not the problem. The problem is that the rental's side of it is not written down anywhere.

Failure. At 14:10 the SSH send to code-2 fails. connect_rental returns on that error before it reaches the loop that re-sends to code-1 (credentials.rs, send(machine, …)? then for other in …). The renewal already happened. code-1 now holds a dead token, nothing printed its name, and nothing recorded that it is behind.

Recovery. The placement is retried. The stored token now outlives the new rental, so token_for reports renewed: false and nobody is re-sent. code-1 stays dead until its agent's push fails and someone reads lf machine logins code-1 and runs lf machine login github code-1. "Who needs the new token" was a fact for the length of one function call.

The biggest mismatch: a rental's GitHub access is not a record

The person's unit is the rental. The code's unit is the repository's token, plus a pointer on each rental saying which repository. Everything about this rental's access is computed in passing: RentalToken.renewed, RentalToken.replaced, RentalGithub.others, the "until" line. When the pass is interrupted the fact is gone. Three behaviors fall out of that one gap: the stranded rental above, the replaced repository's token that nobody retires, and an "until" time that cannot be shown again.

Built

grant per repository+ rental → repository id

Three paths each decide who gets what: token_for (renew, flag renewed), connect_rental (send, then re-send to others when flagged), retire_token (last holder gone). Re-send happens once, in the call that renewed.

Proposed proposed

grant per repository+ rental → repository id and the expiry of the token it was sent

A rental is behind when what it was sent is not the repository's current token. One step, settle a repository: renew when the token does not cover its live rentals, send to every live rental that is behind and record each send that lands, and when no live rental is left, renew once so the last token stops. Placement, lf machine login github, an ending and a replacement all call it for the repositories they touched.

Normal path: the same output as today. Failure: a send that fails leaves that rental recorded as behind and named. Recovery: the next settle of that repository, from any command, sends it; nothing depends on a flag from an earlier call. Survives: the grant table, one approval per repository, the cut at the last ending, the laptop token never leaving. Goes: renewed, replaced, others, retire_token as a separate rule. Counterexample kept: a rental whose provider deleted it still gets an SSH attempt until this Machine notices; the send fails, is logged, and stops when the rental reads ended.

Passed over: sending to the others before the new rental, or ignoring the first send's error. It fixes the walk above and leaves a failed re-send just as unrecorded. The deferred "this Machine renews by itself" then needs this record anyway; with it, that work is one call from the server's rental visit.

Smaller findings

1. Get the token before renting this work

The rental's deadline is known from the template before anything is rented. Asking for "a token for this repository that lasts until then" before rent puts every GitHub failure ahead of the bill: no approval, a refused renewal, a changed gh account, GitHub unreachable, the app uninstalled. After renting, only the SSH send is left. approve_first_rental and its weaker check go; the plan's sentence "placement stops before anything is rented" becomes true for all of them, not only for a missing row.

2. Simultaneous placements wait their turn this work

The lock protects one repository's single-use refresh token. Scope it to the repository and let the second caller wait. Two placements of one repository then show one code, not a code and a refusal; placements of different repositories do not meet. An ending waits a moment and makes its cut. This Machine runs many placements at once; a refusal here is a failed Task launch.

3. Show the install link with the code this work

An approval happens once per repository, and that is exactly when the app may be missing. Print First install the app on loopflowstudio/loopflow: https://github.com/apps/loopflow-studio above the code. The wasted first code becomes rare without any new check. lf cannot see the install beforehand: only a token from this app can ask.

4. One door for "sign this rental in to GitHub" this work

With the settle step taking a repository, prepare and lf machine login github <rental> differ only in where the repository comes from. The branch in prepare and the current-directory read inside connect become one argument.

5. --logins github says what happens this work

lf ondemand add --logins github answers "GitHub and Linear are signed in whenever the repository uses them; --logins takes codex or opencode". Templates already saved with them keep loading and the words are dropped when read.

6. Unproven facts the model rests on needs a person

The four probes, plus two this review adds. GitHub documents, for OAuth apps, a limit of ten tokens per person and app with the oldest revoked past it, and ten new tokens an hour; whether App user tokens share it is unread here. If they do, the eleventh approved repository silently ends the first one's grant, and a rental longer than 8 hours, which renews on every sign-in, can meet the hourly limit. Add to probe 2: approve an eleventh repository, or read the limit.

7. Other outcomes separate

This Machine renews a rental's token by itself. One call to settle from the server's rental visit, once the record above exists. Removes the 8-hour clock while the laptop is awake. Codex and OpenCode outlive the rental. Needs a sign-out in the give-back path and a decision about rentals the provider deletes. Both are in the plan as deferred, neither is a Task yet.

Questions

    2. As built: it is told once, in the output of the command that caused it, when that command gets that far. Otherwise the rental's next push fails and you run lf machine login github <rental>.
  2. Two lf task run --rent at the same moment.
    1. The second waits a few seconds for the first, then proceeds. For a repository's first rental both wait on one code.
    2. As built: the second stops with "another machine login is in progress", sometimes after its rental was created and deleted.
  3. GitHub says no (approval revoked, six months passed, gh switched accounts) on a run with no terminal.
    1. The run stops before renting anything.
    2. As built: it rents, fails to sign in, deletes the rental, then stops.

    1. The install link is printed above the code, every time a code is shown.
