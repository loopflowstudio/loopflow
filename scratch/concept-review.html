No new product decision or design change is needed. Jack Heart selected shared direct writes with request-scoped telemetry. The implementation and corrected guides now agree. Adoption and settings retain that boundary after integration; the remaining obligation is proof on the merged build.

The consequential mismatch is resolved

Before — superseded implementation and guidance:

Desktop write → server → CLI child → mutation
                         └ Process attributed to each write

After — accepted, implemented and documented:

Desktop Write → server request ─┐
CLI command ───────────────────┴→ shared mutation dispatcher → Work

server request → trace + diagnostics + effects in logs/lf.log
CLI execution → actual Process + existing Session / Graph owners
terminal connection → bridge to the exact existing owner

The dispatcher owns routing, selection, defaults, effects and formatting. Each caller supplies a directory and input/output/error streams. A served request uses a scoped worker without changing global cwd, environment or standard streams. It creates no Process row and inherits no launcher Session or Task attribution. The server adds no scheduler or second Work store.

Write remains the existing wire carrier. Reusing its CLI spelling to parse shared options starts no CLI child. A response trace correlates diagnostics; neither that trace nor the request ID is a durable receipt authorizing replay.

Binding selects the Task’s primary conversation and recorded directory. It preserves live attachment and historical attribution; a changed record does not move the running provider. Configuration remains file-backed and available before Work can open. These existing authorities make a second executor, request Process and server-owned execution lifecycle unnecessary.

The interaction stays simple

Open Desktop. Rename the conversation or save an edit. If the reply is lost, inspect the current state before making another deliberate edit. During terminal recovery, keep reading the last screen; wait for acknowledgement before typing. Use Move here only to request control.

Existing guidance, unchanged: Connect clients, the architecture and Swift guides now describe this boundary. Use lf server status to inspect access and lf install to update. No new setup command or recovery skill is needed. The protocol README owns direct dispatch and wire details.

Rename, lose the connection, continue editing

  1. Normal path. Save a Session name. The server runs the shared mutation and returns output, errors, exit status and trace. The native pane reflects the saved name; no provider restarts.
  2. Lost reply. The write may have committed before the connection disappeared. Cancel releases the client’s wait; it does not roll back an admitted mutation. Refresh authoritative state before another deliberate edit. Never automatically resend.
  3. Server replacement. The draft, provider history and unfinished Graph must survive actual supervisor cleanup. Native status shows “Reconnecting…” outside terminal bytes. Input pauses; selection, copy, Find and scrolling stay available.
  4. Recovery. Reconnect the exact owner and wait for acknowledgement. Refresh Work subscriptions. Discard uncertain input. Retry changes connectivity; Move here deliberately requests control. Recovery neither repeats setup nor overrides disabled background items.

Counterexamples to preserve: a rename commits, its reply is lost, and replay overwrites a later edit; or takeover succeeds, its acknowledgement is lost, and recovery steals control from a newer viewer. Both violate the accepted contract. Unknown outcomes and one-shot control transfer are necessary distinctions.

For adoption, a lost reply likewise requires inspecting the conversation’s association before another deliberate action. Neither a transport Retry nor a changed Task directory authorizes starting a replacement provider. A recovery path that did so would invalidate this review’s conclusion.
