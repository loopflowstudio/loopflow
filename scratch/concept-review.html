This ran headless, so it asks for no decision. Accepted decisions already settle both mismatches below, so the review sends them back to implement.

Actions → concepts → APIs

pick a stream          lf install --dev|--preview|--stable   stream: in ~/.lf/config.yaml
stay current           launchd/cron → lf install              published::install(recorded)
app updates itself     Sparkle, appcast-<stream>.xml         AppUpdates.feedURL, can-open veto
app's first launch     lf install adopt                       promote(app → app), relink lf
terminal lf            ~/.local/bin/lf → app's lf, or CLI     public_cli_target

The model holds: there's one recorded stream, one link, and one promotion path. The two problems are both cases where an updater acts on something other than the recorded stream.

Mismatch 1: dev on a Mac with the app

Existing behavior

$ lf install --dev           # lf → ~/.lf/bin/lf-<dev digest>
  … Sparkle (dev → appcast-preview.xml) installs v0.16.2
  … app launches → lf install adopt  # lf → Loopflow.app/…/lf (v0.16.2)
  … launchd → lf install       # dev again: lf → dev digest
  … repeat

Under the accepted decision, Sparkle's feed reads the recorded value. dev has no appcast, so the app shouldn't pick one for it.

Proposed (next implement)

$ lf install --dev           # lf → dev CLI; app runs no updater while dev is recorded
  … Desktop updates again once CI signs dev app builds and appcast-dev.xml exists

Mismatch 2: between Sparkle's install and the next launch

Existing behavior

  (quit app; Sparkle installs v0.16.3, which adds a migration)
$ lf task status
shared store ~/.lf/loopflow.db does not have migration … yet;
install a build that carries it with `lf install --dev`

The link already reaches the new bundle, but nothing has adopted it yet. Following the advice would move a stable Machine onto dev.

Proposed (next implement)

$ lf task status
shared store … does not have migration … yet; run `lf install`
$ lf install
Loopflow.app v0.16.3 is installed but not adopted; adopting it.

Kept as is

  1. On a Mac with the app, the launchd schedule and Sparkle both run daily. When the app is running, the schedule only hands off to Sparkle. When it isn't, the schedule does the work (Jack's "b").
  2. The entry gate. It's refreshed on every promotion with the same build, and scheduled jobs and Graph steps pin it. It's a stable path, not a second version.
