The accepted lifecycle is built and holds. One thing the accepted decisions already settle is still unbuilt: Desktop keeps a second Wave reader, a filesystem scan of .lf/wave/*/GOAL.md, and that reader brings a removed Wave back on removal's own retry path. The next implement direction is one reader.

What you do

Desktop sidebar or Waves window, or the CLI
New Wave… name, optional objective → the row appears selected, its workspace opens.
lf wave add ops --objective "…"
Wave row menu, titlebar crumb, or the CLI
Rename Wave… → same Wave, Tasks and chapters; .lf/wave/ops moves on main.
lf wave rename ops operations
Wave row menu, titlebar crumb, or the CLI
Remove Wave… → a sheet shows what happens, then Remove. Open Tasks move to the parent Wave or the repository; started ones keep worktree, PR and Graph; chapters, completed Tasks and conversations stay in history.
lf wave remove ops --preview · lf wave remove ops · --delete-backlog
After an interruption
Retry in the sheet, or run the same command again. Nothing retires until every open Task has its disposition, so a second run finishes the first.

The one consequential mismatch

Two readers decide which Waves exist. lf reads wave_addresses WHERE retired_at IS NULL. Desktop additionally runs PortfolioDiscovery.authoredWaves, a scan of .lf/wave/*/GOAL.md in every portfolio repository, and both WorkModel.visibleWaves and WavesView.mergedWaves merge the scan in as placeholder rows with isRegistered == false.

They disagree exactly where removal is supposed to be clear:

$ lf wave remove ops            # Linear archive fails
ops has no Tasks or Sessions.
Linear Initiative init_… is still live: …. Run `lf wave remove ops` again to retry.
.lf/wave/ops is not committed: kept until the Linear Initiative is archived.

$ lf wave list --current        # ops is gone
Desktop sidebar                 # ops is back, as a "ready" unregistered row

The receipt says removed; the sidebar says present. The accepted contract says both "Desktop and CLI … reflect the result consistently" and "removed Waves stay removed". The same ghost appears on any main checkout that is behind the planning store (another Machine ran the removal) until it pulls. The design's own deletion list already names this reader; slice 5 kept it because unregistered directories "no longer arise from Desktop creation". They arise from removal's retry path and from clones.

What the placeholder is for, and must survive

A freshly cloned repository whose .lf/wave/ has authored Waves nobody registered on this Machine. Today the scan is the only way Desktop shows them; WorkModelTests.authoredWavesRemainVisible pins that. The only registering paths are lf wave add, lf wave connect, Task creation, lf run and relocation.

Direction proposed, next implement

  • Desktop lists what the store knows. Nothing else.
  • Registering authored directories is lf's job, through ensure_wave's id-first match, which already skips retired ids. So a kept directory of a removed Wave never returns, and a clone's Waves still appear.
  • The trigger is an explicit write, not a plan read (reads record no Work): when a repository joins the Desktop portfolio, and inside lf wave add / connect --all as today.
  • Delete PortfolioDiscovery.authoredWaves, both authoredWavesByRepo copies, authoredPlaceholder, WaveViewModel.isRegistered and every guard on it. The Swift placeholder test becomes a Rust test: registering a clone's directories lists them and skips a retired id.
  • The archive-failure case then needs no Desktop code: the kept directory is invisible to Desktop and only the receipt's leftover line names it.

Looked at, not changed

  • Desktop's Remove sheet has no --delete-backlog control; unstarted Tasks move and the preview says so. A checkbox is ordinary follow-up, not a product choice.
  • lf wave rename also carries --repo (relocation) and --title. Pre-existing, outside this Task.
  • Removal flow, idempotency and the Rust-authored receipt match the accepted design and the five demo steps.
