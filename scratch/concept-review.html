2. Biggest mismatch: split ownership of the clean pushed head

Both HEAD and the first kickoff draft cleared scratch/ before merging upstream changes in prepare_pr. Walking real paths exposes why that split breaks down — and why moving to one clear at the push boundary is smaller and cleaner.

What the kickoff draft missed (caught by walking failure and edge paths):
  1. Real code conflict loses scratch/plan.md: clearing before sync_land deletes scratch/plan.md from disk right before sync-conflicts starts — even though sync-conflicts.md:9 tells the resolver to read scratch/. If the resolver stops or runs lf sync --abort, the failed lf land leaves a "Clear added scratch files" commit and wiped notes on the branch.
  2. SyncStrategy::Noop never pushes: ops/sync.rs:292 hardcodes finish_sync(..., false) for Noop. A persistent worktree or already-integrated stacked child hits Noop in sync_land and skips pushing its clear commit entirely.
  3. lf land --local still pushes: ops/land.rs:406 hardcodes push: true in sync_land even when options.local is set.
  4. Two smaller leaks: non-Task notes-only PRs on resync == false bypass require_task_pr_range_nonempty, and the standalone already-armed shortcut (land.rs:97-113) can return early on a manually armed checkpoint head without clearing notes.

After (Revised Plan)

Single-owner clear at the push boundary

prepare_pr(Required):
  # standalone armed shortcut checks added scratch == empty
  resolve_pr_copy()               # published_pr_copy | generate
  if resync:
    sync_land(push: !local)       # delivery: true; notes stay on disk
      Noop  -> finish_sync(push = options.push && delivery)
      Merge -> if all rerere_remaining are branch-added scratch
               absent from target_sha:
                 git rm -f && continue_merge  # 0 agents!
               else:
                 sync-conflicts reads scratch/plan.md on disk;
                 lf sync --abort leaves 0 clear commits!
      finish_sync:
        verify_integrated_head + 0 unmerged paths
        scratch::clear(repo, target_sha)       # ONE clear
        refuse if HEAD^{tree} == target^{tree} # before push
        push once (skip if remote == HEAD)
        record_control_task_state(target_sha)  # ONE stack write
  else:
    base = merge_base(HEAD, integration_base)
    scratch::clear(repo, base)                 # ONE clear
    refuse if empty (Task or non-Task)
    push_with_upstream_if_needed()

prepare_pr(Completed):

3. Concrete walkthroughs (normal, failure, recovery, edge)

Scenario What a person sees What survives / what changes on purpose
1. Normal code Task
build → ship-review → deliver		 pr-publish opens a checkpoint PR (notes kept, CI deferred during ship-review). After approval, deliver runs reflect then lf land --wait-and-fix: clears notes, pushes 1 clean head, full CI runs, merges. Published PR copy reused if no new local commits; checkpoint history kept in git; scratch/.gitkeep and any existing repo docs under scratch/ survive.
2. Stacked child, parent squash-merged
Parent added scratch/plan.md, child edited it.		 lf land merges origin/main via fork comparison, sees only UD scratch/plan.md in rerere remaining, drops it mechanically (0 agents launched), clears any other child notes in finish_sync, detaches stack, pushes once. Child commits and commit identities survive; parent link clears in store and PR retargets to main; remote head has only scratch/.gitkeep.
3. Real code conflict during lf land
src/foo.rs conflicts with main.		 sync-conflicts launches with scratch/plan.md still on disk. If it resolves src/foo.rs (even if it writes scratch/notes.md), finish_sync clears notes and pushes once. If it aborts (lf sync --abort), branch is untouched. On abort: zero clear commits, all notes intact. On recovery: conflict resolution survives, notes cleared before push, 1 push total.
4. Noop delivery or --local
Already-integrated stack, persistent worktree, or origin-less --local.		 Noop delivery still clears committed notes and pushes the new head (skipping push only if remote already matches). lf land --local clears and merges locally without touching origin. Untracked notes and unstaged edits in a persistent worktree survive untouched (git::scratch::added inspects committed HEAD only).
5. Renamed repo doc in scratch/
git mv research.md scratch/research.md		 git::scratch::added uses --find-renames across the whole tree, so both auto-drop and finish_sync leave the moved file alone. Repository content is never mistaken for a disposable note.

4. Choices made for review (recorded in scratch/plan.md)

Every choice below is reversible; none is irreversible once shipped, so the plan commits to the boldest, simplest option and records what was passed over.

  1. Single-owner delivery clear (no pre-sync clear when resync == true). Keeps scratch/plan.md readable during real code conflicts and avoids mutating the branch on abort, while auto-dropping pure stacked-scratch UD conflicts with zero agent launches. Passed over: clearing before sync in prepare_pr and clearing again in finish_sync.
  2. Delete builtin queue Graph and .lf/graphs/finish-queue.yaml. Without gate, queue is just compress + refresh with no caller outside tests and one doc row. Passed over: keeping an unused two-step Graph.
  3. Delete cached PR copy (scratch/pr-title.txt, pr-body.md, .pr-copy-ref). Nothing writes it anymore; it was gate's handoff. Passed over: leaving dead readers for a separate cleanup.
  4. Drop pursue-auto's outer loop with gate. The outer loop had no step other than the inner loop plus gate + loop-or-next. Passed over: keeping a degenerate outer loop.
  5. Keep lf scratch clear as a standalone command with today's base (task_diff_base else git::scratch::base) so someone can still trigger CI on a manual lf pr publish without arming auto-merge. Passed over: deleting the CLI command.

6. Open questions for review

Answer with a number and letter (for example, 1a 2b). Nothing here blocks building the plan as written.

1. When lf land hits a real merge conflict, should your scratch/ notes stay in the checkout until the conflict is resolved?

  • 1a (Chosen in plan): Yes — notes stay on disk so the conflict resolver can read your plan, and aborting the conflict leaves your branch and notes untouched. Notes clear only when the merge finishes and is about to push.
  • 1b: No — clear notes before attempting the merge, then clear again after conflict resolution. Simpler merge path, but the resolver cannot read scratch/plan.md on disk and an aborted land leaves a "Clear added scratch files" commit behind.

2. Should lf scratch clear stay as a command you can run by hand?

  • 2a (Chosen in plan): Keep it — useful if you want to trigger full CI on a manual lf pr publish without arming auto-merge or submitting.
  • 2b: Remove the command — only lf land, lf arm, and lf pr submit clear working notes.

3. Should the unused queue Graph disappear with gate?

  • 3a (Chosen in plan): Delete queue (and .lf/graphs/finish-queue.yaml) — without gate it is only compress + refresh and nothing invokes it.
  • 3b: Keep queue as compress → refresh.
