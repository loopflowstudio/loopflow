One interaction, walked

A Graph runs a loop-or-next step. Fourteen seconds, one turn.

  1. The Graph sends the step's message. lf writes a captured row in loopflow.db.
  2. The provider starts a turn. lf inserts a row in usage.db, then writes the turn's Task, Wave, skill and step onto it.
  3. While it runs, lf appends about six rows to history.db: what the message was made of, the attempt starting, the provider's state change, the provider's own events.
  4. The turn ends. lf completes the usage.db row in place: end time, status, tokens.
  5. The Graph asks "which turn answered my message?" It reads usage.db to get the turn id, then reads that turn's last message from the provider's transcript, and routes.
  6. The Session list asks "is this turn finished?" It reads usage.db.

The failure

Something holds usage.db for the length of the turn. The turn still completes (about 5 s of waiting per locked file, measured in QA) and lf.log gets a recording gap. But step 5 now has no turn id. The code falls back to "the last turn this provider conversation began since the message was captured", guarded by a check that no later message continued the same conversation. The comment on that fallback says why the guard exists: "that thread's last turn may answer someone else." Step 6 has no recorded end, so the turn reads as running until the transcript moves.

The recovery

At the next unlocked write the gap closes, and the missed turn gets its row written later from the transcript, with model and tokens but without skill or start time. So the row that was meant to answer "time by skill" is missing both for exactly the turns that had trouble.

The biggest mismatch: the turn

The change set out to separate two things: state the product acts on, and a record people read later. It then put the turn, which is both, in a file named for the second. Everything awkward in the walk above comes from that. The guess in step 5, the "running" turn in step 6, and three files that all have to be watched by the main views are one problem.

A turn has two parts with different needs. Whether it ended and which message it answered are tiny facts the product needs at once and must not guess. Its tokens, cost, duration and grouping are a record that can arrive late and can be rebuilt from the transcript.

Before (as built)

  • "Did it end?" and "which turn answered?" are read from usage.db.
  • A missed write means a guess, or a turn shown as running.
  • Session list, Task view and status watch all three files.
  • Deleting usage.db loses trends and also changes what running Graphs and Session lists see.

After proposed

  • The message row in loopflow.db records the turn that answered it and when it ended. lf already writes to loopflow.db at these moments: the message itself, and session_activity each time the agent yields.
  • Graph routing and the Session list read only loopflow.db. No guess.
  • usage.db becomes what its name says: numbers that can arrive late.
  • Only history views watch the other files.
  • Deleting usage.db or history.db changes nothing a running Graph or a Session list sees.

Counterexamples kept

  • It puts a write back on the main lock. The point of the Task was to take per-turn writes off it. This adds one update per turn end, to a row in a table already written per turn. The inventory measured about 0.3 history writes a second against 7 of state. Worth measuring before accepting.
  • Several turns can answer one message in an interactive Session. The message row then holds the latest completed one, which is what routing asks for today (ORDER BY ended_at DESC LIMIT 1).
  • A prompt folded into an earlier turn has no message row of its own. It has no turn row today either, and reads as running until the transcript moves. Unchanged.
  • The failed-step read (interrupted or errored, from history.db) is not covered by this. It would need the turn's status on the message row too, or the Graph to read the transcript as it does for the answer.

Smaller findings

  • History repeats the turn. Attempt and terminal rows could be written only when a turn retries or fails. That would cut history.db to roughly a third for ordinary turns. Not checked against every reader.
  • Two journal files or one. If the turn's state moves to loopflow.db, usage.db and history.db are both pure later-reading, written by the same process at the same moments. One file would halve the worst-case wait QA measured (5 s per locked file). Two files keep usage easy to copy and history safe to delete.
  • kind in session_history can only be 'observed'. Either it names the real kind (transition, manifest, gap) or it goes.

Larger than this work

  • Naming the message. Picking one word among input, capture and receipt, and renaming session_events to match, touches most of the Session code and three clients. Sibling Task 5 ("Name a repository and a person one way everywhere") is the same kind of work.
  • Headless Claude turns have no duration. Without it, "time by skill" is wrong for most Graph steps. The released build has the same hole.
  • A command for the questions. lf usage groups by Wave, Project and Task but not skill, model or step.
  • Process rows named by history and turns. LOO-953.
