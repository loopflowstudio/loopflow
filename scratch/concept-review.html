When an update arrives, may it close your open Desktop?

Recommendation: defer scheduled activation while Desktop is open. An explicit lf install can update now and reopen it. This is a proposal: updates could wait indefinitely if Desktop stays open.

The current branch lets both manual and scheduled installs restart Desktop. It preserves running helpers, but usable conversations and pending input still need proof.

Your action: run lf install, or let the schedule run.

Installation: one complete app + CLI, in the existing location.

Update: recover receipt → choose destination → acquire → promote.

Running work: retain Session identities and images; verify continued interaction.

The mismatch: “process survived” is weaker than “work survived”

Before: the public CLI advanced while Desktop kept an incompatible helper. Branch: the app and CLI update together; Desktop alone is stopped and reopened. That stop escalates to a forced quit after five seconds. Keeping helper PIDs alive does not prove that the visible workspace, a draft, or the next turn survives.

Walk through failure, recovery and the proposed usage text

Normal, proposed: you are typing when the schedule runs. It keeps the whole installed build. A later run updates when Desktop is closed, or you run lf install to update immediately. No separate “staged update” record is needed.

Failure: download or preflight fails; the prior selection stays usable. Recovery: if activation already started, finish its recorded destination before considering a different request or deferring a new update. Never advance only the CLI.

Scheduled updates leave an open Desktop alone and retry on the next run. Run lf install to update now; it may close and reopen Desktop. The app and CLI always update together.

Proposed skill wording: preserve an existing conversation and pending input; verify reconnect, a completed turn and continued interaction after rollout. A surviving PID or reopened window is insufficient.

API consequences: current app_destination resolves location; PromotionArtifacts carries the pair; promote writes SwitchReceipt.activation; recover_switch finishes its pinned paths. Deferral would carry scheduled intent to a decision before a new switch or store advancement. The same promotion and recovery owner remains.

Remaining source finding: Desktop still has a different location rule

Rust follows the public CLI into a custom bundle. Swift's AppUpdates.isInstalled still checks only /Applications or LF_APPLICATIONS_DIR. A custom app launched without that environment skips both updater startup and automatic adoption. This source counterexample remains regardless of the restart choice.

Required direction: use the same installed-location facts in Desktop, while keeping private development builds excluded. Verify a normal custom-location launch; the Rust adoption command alone does not fix the Swift gate before it.

The parent reports the immediate Desktop repair on signed main. That is separate from this branch's installation policy, mini rollout and the existing-session recovery owned by LOO-724.

Decision

  1. When Desktop is open, what should a scheduled update do?

    1a — Update and reopen Desktop. Current branch behavior; prompt updates, with visible interruption. Continuity must be demonstrated.

    1b — Wait for a run when Desktop is closed. Proposed, recommended; avoids unattended interruption, but updates may be delayed. Explicit lf install still updates now.
