Your rule

“Only things that actually change state (which could include editing a task name) should get process rows.” Then: adding or completing Tasks should be tracked, and Linear sync “is just followthrough on a previous write.”

Mismatch

changes_state asks “does this command change anything?” A window focus counts, because Desktop’s terminal state changes. So an agent driving panes, or you dragging a pane, writes Process rows. Each one advances the processes revision and wakes every Work reader. That is the same wake-up cost this Task set out to remove, now coming from UI actions instead of reads.

Proposed

The question becomes “is this a change to Work?” Work means Tasks, Waves, Projects, Sessions, Graphs, PRs and planning. UI actions and arrangement are not Work: they record no Process and wake no Work reader. Arrangement is still saved.

APIs: rename changes_state to changes_work and flip about 20 DesktopCommand arms. No new commands. The equivalence test is unchanged.

Normal path, failure, recovery

Normal: an agent focuses a pane and types into it. The focus records nothing. The send records a Process attached to the Session. The sidebar wakes once, for the send.

Failure: a layout save fails halfway. Today the failed lf process leaves a failed Process row in the Task’s work. Proposed, the save reports its error to Desktop and the Task’s history stays clean. Nothing about Work was lost.

What survives either way: every Task, Session and Graph change and its record, Linear delivery and its retry, and saved layouts.

One follow-on

Under (b) the library never writes, so a pane drag still starts an lf process just to save the layout, even when it records no Process. Arrangement is metadata only Desktop reads. It could be the single kind of write the library owns. You said you weren’t worried about metadata writes, but you chose (b).
