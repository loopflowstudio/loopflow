Do the steering concepts line up?

Area: how a person's steer reaches a managed conversation on each of the four providers, and how a work session is launched to match its worker. The idle-wake diff (git diff 2a3b6d11d8 HEAD) sits in the middle of it; the review covers the area with that diff in it.

One interaction, walked

Someone runs lf steer LOO-974 'use the staging bucket' while the Task's OpenCode work session sits idle in its terminal.

  1. The steer is stored. The Machine server's watcher sees the revision move and finds the Session idle: session_activity.yielded, recorded at the plugin's Stop.
  2. The reach comes from the row: provider = opencode → IdleReach::Extension(agent_inbox).
  3. The server connects to /tmp/lf-wake-*/s, writes {"thread","text"} and waits up to 15s for started. The plugin calls session.synthetic, and the turn runs in the TUI.
  4. Failure: the socket is gone or answers nothing, so the steers stay undelivered and the next boundary carries them as context. Nothing is stamped read.
  5. Recovery: the person quits and reopens. The plugin names a new socket as it loads, record_agent_inbox sees a change, marks the new process idle, and the wake runs before anyone types.

This holds on the normal path, the failure and the recovery. QA on real models showed the same sequence (scratch/qa.html).

The biggest mismatch: one model setting, two outcomes

Before

The OpenCode TUI (2.2.1) has no --model flag: opencode --help lists --standalone --server --auto --continue --session --prompt. The worker passes --model to run; the work session drops the setting. Steering, context and resume are the same in both, but the model is not.

PROPOSED

After

opencode::environment writes "model" into OPENCODE_CONFIG_CONTENT, which both launches already build. run --model is deleted, so the model goes through one place for workers and work sessions alike. A test on environment checks the key; a real TUI run checks that the configured model answers.

Choice made for review: config over a CLI flag. The other option is to wait for OpenCode to add --model to its TUI, which leaves work sessions on the wrong model until it does. Config is the one path the TUI reads today, and it is reversible.

Larger than this work

  • Reopen semantics across providers. Making Claude start a turn on reopen with steers waiting means changing Claude's start hook so it leaves the steers to the wake instead of folding them into context. That touches every Claude work session.
  • An owner for "a new process is idle". This could be one store write at a process's first boundary, used by every provider, with record_agent_inbox back to saving the address. First it needs a check of Codex's reopen and of the opening-prompt race (questions.md 6).

Questions

  1. OpenCode work-session model: (a) through OPENCODE_CONFIG_CONTENT for both launches, as planned; (b) keep run --model for workers and add config only for the TUI; (c) leave it until OpenCode's TUI takes --model.
  2. Reopen with steers waiting: (a) a turn starts, on every provider; (b) the steers become context for the next typed turn, on every provider; (c) leave the providers different.
  3. The "new process is idle" rule: (a) leave it in record_agent_inbox; (b) move it to a process's first boundary for every provider, as its own Task.
  4. agent_inbox holding two shapes: (a) fine, since provider tells them apart; (b) split into a key-file column and a socket column.
