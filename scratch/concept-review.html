Who wakes a Session?

The area: everything that gets text to an existing Session and makes it act on it — lf steer at every scope, the server's wake watcher, session.continue, lf resume, and the Graph correction loop — as it would stand with LOO-958's plan built. Reviewed before implement, against the two direction lines that arrived after kickoff: "the machine server manageds the terminal" and "i mean it WAKES those".

Biggest mismatch. The kickoff plan gave "wake" a second owner. The Machine server's watcher (server/wake.rs) already reads every saved steer and wakes idle held conversations. The plan added a detached lf -b session wake ID started by the steering command, with its own lock file and its own run-again loop, for the stopped case. Same news, same reader's job, two places. And the server already knows how to start a stopped Session in a held terminal: that is session.continue, the phone's Continue.

One interaction

  1. A person quits lf : after saying "remember the word mango". Session S is stopped: interactive, no live AgentProcess.
  2. From another terminal: lf steer S 'what word did I give you?'. The steer is saved; the command returns.
  3. proposed The watcher sees news for a stopped interactive Session it should wake. It runs continuing(S, request = steer id) → Registry::start: lf session resume -- S in a held terminal, in S's directory. run_refusal refuses if S came back meanwhile.
  4. S yields idle. The watcher's existing path (Claude inbox, Codex app-server) delivers the steer. S answers "mango".
  5. lf resume S attaches to that held terminal. The answer is on screen. "resume connects to existing sessions" — and now there is always one to connect to.

Failure. The held start fails (provider won't launch). The server logs it to logs/lf.log; the steer stays undelivered in lf session steers S. It has used its one start, so it doesn't loop.

Recovery. The person runs lf resume S; the resumed conversation reads the steer at its first boundary. Nothing was lost.

Counterexample, kept. Machine restart. The watcher's first reading wakes everything with news. With stopped Sessions in scope, every interactive Session holding an old undelivered steer would start at boot. Hence: each steer starts its Session at most once, recorded on the steer; the migration marks existing undelivered steers as already started.

Before and after

Kickoff plan 
lf steer S  ─ save ─┬─ running: hook at next tool call
                    ├─ idle held: server watcher → inbox
                    └─ stopped: start_lf("-b session wake S")
                                  ├─ own wake lock
                                  ├─ claim, headless turn
                                  └─ loop while unread, recheck
lf steer TASK ─ save ─ wakes nothing stopped

Woken Session runs headless; lf resume S later has nothing to attach to.

Proposed 
lf steer S|TASK ─ save. That's all.

server watcher, on news:
  running          → hook at next boundary
  idle, held       → inbox / app-server   (today)
  stopped, wakes   → session.continue launch, once per steer
                     → yields → inbox / app-server

lf -b steer S ─ save claimed ─ turn here ─ print

Deleted from the plan: hidden session wake, the wake lock, the loop, the steering command's detached start.

What could break it

  • A resumed conversation with no viewer may not yield as idle. Claude in a held terminal at its prompt must report yielded for the inbox wake. Slice 2 checks this first; if not, the held start passes the steer as the first input instead.
  • No server. Nothing starts S until one runs; the steer waits, visible. lf steer says so. Tests already require a MachineServer for managed launches.
  • A person's bare Session becomes held. After a wake, S lives in a server terminal rather than the one it was quit from. That is what "the machine server manageds the terminal" describes; it changes where S runs, on purpose.

Questions

  1. Who starts a stopped Session for a steer?
    1. The Machine server's watcher, in a held terminal (this plan).
    2. The steering command, detached and headless (kickoff).
  2. A Task steer with no Graph step running:
    1. Wakes only the primary conversation (this plan).
    2. Also held for the next step's first boundary, as today.
    3. Also wakes the last finished step.
  3. An old undelivered steer after a Machine restart:
    1. Starts its Session at most once ever; the upgrade marks old ones started (this plan).
    2. Starts it whenever the Session is stopped and the steer unread.
  4. lf -b steer to a running Session:
    1. Saves and returns (this plan).
    2. Waits until the running agent has read it.
