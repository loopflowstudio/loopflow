Does a reopened work session hear its steers the way people expect?

Area reviewed: how a steer reaches a person's managed conversation — the hook's claim at a boundary, the server's wake of an idle conversation, and what "idle" means — with all of LOO-1068 (slices 1–4, against base 7487986a30) in it. Chosen because the Task changes who owns a waiting steer at the moment a provider process starts, which touches all three.

What a person knows

Steerlf steer <task> '…' — direction for the conversation.
WorkingThe conversation hears it at its next tool or prompt.
IdleIt starts a turn on it now, before anyone types.
Reopenedlf resume after quitting: it is idle, so the same as above.

One promise: a steer arrives once, as soon as the conversation can take it. "Reopened" is not a separate concept to a person; it is idle. Before this Task the code disagreed on two of four providers.

Biggest mismatch (fixed in slice 4): Codex's start is reported in Codex's voice

Codex runs its start hook only inside its first turn, so the launch reports the start itself (codex.rs::report_first_boundary). That part is right: the launch is the one place that knows the process opened, its address and whether an opening prompt is coming. What is off is the payload. It is shaped as Codex's own hook, with "source":"resume" hard-coded.

Before slice 4
{"hook_event_name":"SessionStart","session_id":thread,"source":"resume"} on every launch with no opening prompt. A new work session launched with no prompt (saved is None) writes a resume provider transition into its history (with_provider_context → provider_transitions::observe_in) for a conversation that was never resumed.
Now built (first_boundary, test a_launch_reports_its_first_boundary_as_codex_would)
"source" is "resume" when the launch resumed a saved thread and "startup" otherwise — what Codex's own hook would have said. Keep the shape; no wire change. A BoundaryMoment::Open would name it more honestly but is a wire change for one caller (SessionBoundary is deny_unknown_fields), and the history label is what a person can see.

One small fix in this work

Proposed plan
record_first_boundary reads first so later boundaries take no write lock, but the read only asks "does a row for this process with observed_at<>0 exist?". A worker (interactive=0), or a process with no steer capability, answers no until its stream writes a row, and each of its boundaries then runs an INSERT … SELECT that matches nothing — still a write statement on the Machine's one SQLite write lock. Fold eligibility into the read (interactive Session, this process current, capability present), so only a boundary that will write takes the lock. No behaviour change; one query.

Outside this work

The wake has three entry points for two ideas: news arrived (watcher on steer and Task-update revisions) and a conversation became idle (After::TurnEnd → after_turn, and After::Reachable). Making "became idle" a store revision the watcher reads would delete After::Reachable and Codex's synthetic report together. It costs a migration and triggers on session_activity, which changes every turn on every agent, and turns each turn end into a Machine-wide idle_conversations(None) scan instead of today's one-Session read. Not worth it at this Machine's load without measuring; a separate Task if pursued.

Verdict

The concepts line up. The change made the model smaller: "a new process is idle until its first turn" has one owner, and the inbox write went back to saving an address. The one wrong label is fixed. Left: a one-query write-lock fix, one rare edge to know about, and one risk only a real Claude can answer.
