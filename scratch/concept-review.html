The biggest mismatch: what a Task offers

Existing

The page and the iPhone ask TaskActions, which reads the Task's Graph position from its own reading (TaskOverview): Start at the beginning, Run at a step or after a stopped run, nothing while a run carries it.

A Portfolio row holds a RoadmapTask, which has no position. It asks the server's actions.recommended whether to offer the verb and graphHasRun which word to use.

The backlog asks awaitsStart: Start runs Tasks with no checkout and says "Open" for the rest.

Proposed, on the wire, not in this change.

The planning row carries the Task's Graph position. TaskActions is built from the row alone; roadmapTaskAction, RoadmapTaskAction.label, graphHasRun and the backlog's own split are deleted, and the workflow sentence reaches every tile and list row by the same field.

That is the "Workflow position on a list row" entry the plan already had; it now names the action too.

Why not in Swift, now

  • The row lacks the fact. TaskActions needs a reading only an opened Task has. A row-level copy of its rule would be a fourth decider.
  • The blocked Task. Offering Run whenever runControl allows it would contradict the comment the code stands on: the server recommends, the app "never re-derives it from status". The disagreement is between two Rust answers, the recommended action and the position.
  • The backlog's Start (question 53). Moving it to graphHasRun changes one case: a Task with a checkout, no run and no owner. Opening a Task claims it, so it leaves the backlog for Working, which is what the third qa run saw and what the server's sections decide. The case Swift could change needs a release after an open; there the bar says "Open" where a Portfolio row says "Start", and the page it opens offers Start. One click, and it goes with the wire change.

Counterexamples kept

  • Opening a Task still changes it. It reads "Unstarted" before and "Idle" after, and moves from the backlog to Working. Nothing it says about needing someone changes, which is what slice 6 promised. Whether a link should place a checkout at all is the CLI's open, not these screens.
  • "Waiting" over "ready" on a parked Task, every row. The server's reason; the standing-on-the-wire Task replaces it.
  • Not looked at: the activity pane, the jump menu, New Wave, the title bar, menus, hover and drag. The screen was locked on all three qa runs; tests hold their words. These belong to review on a display.

What changed in the plan

  • "Outside this change": the workflow-position entry names the action as well as the sentence, and what it deletes. No new entry.
  • "What the code is today" says the third review found nothing to build.
