Normal path. It reads as the docs promise. The approval, a refused renewal, the wrong account and a missing install all stop the run before "Renting". One step (github::settle) decides the token and who is sent it, for placement, a sign-in by hand, an ending and a rental moved to another repository.

Failure. At 12:30 the renewal ended code-1's token and the SSH send to code-1 failed. Pass 4 gets this right: code-1 is recorded as sent the 17:00 token while the repository's token is the 20:30 one, and the run names it.

Recovery. This is where it thins out. The record is read by one thing: the next settle of that repository, which happens at a placement, a sign-in or an ending of that repository. If none comes, code-1's agent meets a 401 on its next push. A person who looks:

lf ondemand list            code-1  running until 15:00   …   # nothing about GitHub
lf machine logins code-1    github  signed out                # asks the rental and GitHub; no time, no repository

"17:00" and "20:30" were each printed once and cannot be shown again. And when the renewal is caused by an ending that the background rental check makes, the sentence naming code-1 goes to the server's stderr, where nobody is.

The biggest mismatch: the record has one reader

The earlier review found that a rental's GitHub access was not written down. It is now: which repository, and which token it was last sent. But the only reader is the settle step itself. The person's two questions, can code-1 use GitHub? and until when?, are answered once in the scrollback of whatever command signed it in, and after that by an SSH round trip that says "signed in" or "signed out" with no time and no repository. A missed token is known to this Machine and visible nowhere.

Normal path: each running rental shows when its GitHub token stops, including after someone else's placement renewed it. Failure: a send that did not land shows as "not delivered" on that rental, whoever's command or whichever background check caused it. Recovery: unchanged, the next settle or lf machine login github code-1; the person now has a place to see that one is owed. Survives: everything built; this adds one read. Counterexample kept: the record is what this Machine sent, not what GitHub thinks. A token revoked on github.com still lists "until 20:30"; lf machine logins code-1 stays the command that asks.

Passed over: having lf machine logins answer from the record. That row is computed on the rental, which has no copy of this Machine's store, and asking GitHub is the truer answer there. Also passed over: a notification. The other half of this gap is the deferred automatic renewal (separate outcomes, below): until the background rental check settles each repository, "not delivered" is acted on only when something else happens to that repository.

Smaller findings

1. lf ondemand login github asks for a code only when one is needed this work

Built, it is a fifth caller beside the four that go through settle, and it always spends a device code. On a repository that is already approved that is a typed code for nothing, and it replaces a working approval with a new one: the old approval's token is still on the rentals until the send lands, and this Machine has thrown away the only thing that could cut it (whether GitHub ends it at the new approval is the plan's unanswered probe 2). Proposed: when an approval for this account exists, renew it, which proves GitHub still honors it, and say "already approved"; ask for a code only when there is none or GitHub refuses. The command then answers the question a person runs it for before a scheduled run: will a placement with no terminal work?

2. Before renting, ask GitHub, or say less this work

Placement trusts a stored token until its expiry. If the person revoked the approval or uninstalled the app within those 8 hours, the run rents, fails at the send or the clone with an error that does not mention the app, and deletes the rental. Either placement asks GitHub what the stored token reaches before renting (the check grant_from already makes at approval and renewal: three requests), which puts this failure with the others and gives it the install link; or the docs sentence is narrowed to what is asked. Both acts are the person's own and rare.

3. Say it when GitHub stops before the rental this work

Only a template over 7 hours meets this. Placement prints the rental's end and GitHub's end as two unrelated lines. One clause on the second, only in that case: GitHub on code-1 until 07:40, before the rental ends; lf machine login github code-1 renews. The plan asked for it; the build prints the time alone.

4. Commands that wait on someone else's code say so this work

The repository's lock is held while a person types a code, up to its 15 minutes. A second placement waiting there is right: it shares the code. An ending waits too, so lf machine end, lf ondemand list (which ends rentals its provider deleted) and the background rental check can sit silent behind a terminal elsewhere. It happens only when a repository that already has running rentals is approved again; with finding 1 that is GitHub refusing a renewal or a changed gh account. Too rare to build a second lock for. One line when the lock is not free, waiting for the GitHub approval of loopflowstudio/loopflow in another terminal, is enough.

Passed over: an ending that gives up after a short wait and leaves the token to its own expiry. A settle that renews and sends over SSH to several rentals is itself not short, so no bound separates "a person is typing" from "a busy repository".

5. Left as built

A sign-in records the repository before it knows the outcome. lf machine login github code-1 run from another repository's checkout marks code-1 as that repository's first; if the settle then fails, code-1 is recorded for a repository whose token it does not hold. The error is on the safe side (the token it does hold is cut when its repository's other rentals end) and running the command again repairs it. 7 hours counts as new, 10 minutes of margin at admission. Two numbers a person never meets except through finding 3.

6. Unproven facts the model rests on needs a person

Nothing here has met GitHub. The five probes in the plan wait on two acts only a person can do: install the app on one repository, and type one device code (scratch/plan.md, "Needs a person now"). One addition to probe 5: the cut at a repository's last ending is a renewal, so Tasks that run on rentals one after another renew once or twice each. If GitHub's "ten tokens created per hour" covers these tokens, a repository running more than a handful of rentals an hour back to back meets it, well before any rental is long.

7. Other outcomes separate

This Machine settles each repository by itself. One call, settle_unattended, from the background check that already visits every rental. It delivers a missed token within one visit and removes the 8-hour clock while this Machine is awake. It needs its own rule for when to renew: with the 7-hour rule a long rental would be renewed every hour. Codex and OpenCode outlive the rental. A sign-out in the give-back path, and a decision about rentals the provider deletes. Both are in the plan as deferred; neither is a Task.
