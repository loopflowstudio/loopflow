Which lf does a test run?

Second pass, after the build (base origin/main, head edf0aeef5f): the code matches this page; one row and question 4 are new. Area taken: the test-fixture CLI and the holder it spawns, plus the two in-process traps (the with_process OnceLock, Swift warm openings). All four flaky tests come down to a test seeing something it did not start. 1b is the one where the product's concepts are off, so most of the page is about 1b.

The interaction

A developer edits lf.rs and runs cargo test -p loopflow --test session_launch_contract. On main:

cargo links lf (dev features, 03ff…)   → target/debug/lf
fixture starts MachineServer          ← target/debug/lf   (server is 03ff, keys holder place 03ff)
test calls lf_binary()                → cargo build lf (no dev features, aef4…) → target/debug/lf
server spawns current_exe()           ← target/debug/lf   (now aef4: binds holder-aef4.sock)
server polls holder-03ff.sock … 20 s  → "Holder … is not answering: No such file or directory"

Rerun and it passes: the path already holds aef4 before the server starts. The failure names a socket, not the cause.

As built: the integration binary's ctor sets LOOPFLOW_TEST_LF to its own CARGO_BIN_EXE_lf, so line 3 never runs (27/27 on the first run after a link, same hash before and after). With that line removed, the test fails in about two seconds with:

The executable at …/target/debug/lf is now build 7db1716ee77a; this server is build 405a35a6b8f1
and has been replaced since it started. Run `lf install server` to restart it

Recovery, run on a private Machine under launchd: lf install server from the replaced path restarted the server and the next shell was held. A foreground lf server run has no command that restarts it.

Biggest mismatch: a build is spawned by path

Before
The server knows its build (hash at start) and spawns current_exe(), trusting the path still holds that build. When it doesn't, 20 s of polling and a socket error.
Built
Integration tests stop relinking the path (ctor sets LOOPFLOW_TEST_LF = CARGO_BIN_EXE_lf). The holder's ready line carries its build; a mismatch fails at once, naming the path, both builds in the twelve digits the socket is named by, and lf install server.
Proposed, larger than this Task: make the mismatch unspellable. Place carries the executable the holder runs; the server links (or copies) its own executable there at start, checks the hash once, and always spawns that file. Then no relink of target/debug/lf and no lf install can hand a server the wrong holder, and the nested-build gap below disappears for the holder. Costs: a binary per live build under the holder state, cross-volume copy when a hardlink fails, cleanup when the holder exits.

What the first pass changed in the plan (all built)

  • Gap named. Lib test binaries (--lib, incl. tests/work/; loopflow-execution's tests) have no CARGO_BIN_EXE_lf and still nested-build onto the same path. Under bare cargo nextest run without LOOPFLOW_TEST_LF they can still swap it under an integration binary. scripts/test.py, CI, and plain cargo test ordering avoid it. Listed in Exclusions.
  • Slice 2's error names the cause, the replaced server, not only the two hashes. Production reaches it too: installation.rs:753 renames over the entry gate under a live server.
  • Choice made for review: keep slice 2 a named failure and leave the build-owned executable for its own Task. Passed over because it changes what lives in LF_HOME and the install story, and this Task is about tests.

Unchanged and checked

  • 1a and 3 are fixed on main; the with_process cfg is one line that closes the trap for loopflow-execution lib tests. It can't be widened to test-support: the unified lf built during cargo test calls it.
  • Swift: the probe saw the two warm session resume requests; both New Task tests set the existing canPrepare guard.
  • The mismatch is found after the spawn, so a holder of the new build starts with no server and exits by itself within a minute. Hashing the path before spawning would save that process and add a race between the hash and the exec; the ready line says what really started. Left as built.
