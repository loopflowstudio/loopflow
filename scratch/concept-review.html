LOO-926 as built: sending work to another Machine

The area taken: what happens when something you do here belongs to a Task or Session that another of your Machines runs. PR #1956 at 60895c2e30, read against main. Not reviewed: sign-in (LOO-957), the phone's WebSocket, rentals. Dashed green boxes are proposals; grey boxes are what the branch does.

One interaction, followed through

LOO-123 runs on mini. On the laptop: lf task run LOO-123.

  1. Write::remote() reads the Task's route and finds mini. It collects the sender's context with forwarding_environment: five environment variables (LF_REMOTE_PROFILE as JSON, participant name, agent override, LF_SETTINGS, Task source as JSON).
  2. First SSH. forward::deliver writes the per-run secrets to ~/.lf/forward/<uuid> on mini as export NAME='value' lines and returns the file's path.
  3. Second SSH. Connection::open_on(mini) runs lf server connect there. It checks it is mini, starts the server if none is running, and copies bytes to machine.sock.
  4. The laptop sends hello as client kind machine, then one request: machine.write { repository, environment, forwarded, change }.
  5. mini's server rewrites change.directory to its own checkout by round-tripping the write through JSON, reads the secrets file back by parsing the shell lines, deletes it, and runs Write::run_here.
  6. The answer comes back on the pipe; the laptop prints it.

The biggest mismatch

"This request came from another Machine" is a fact about the connection and the request. The branch writes it as a new kind of operation.

As built
hello { client: { kind: "machine" } }
request {
  operation: {
    kind: "machine.write",
    repository: "repo_30…",
    environment: { "LF_REMOTE_PROFILE": "{…}",
                   "LF_USER_NAME": "Ada", … },
    forwarded: ".lf/forward/0f…",
    change: { kind: "task.run",
              directory: "/laptop/repo", … }
  }
}

What follows from the shape, read from server/service.rs::operate:

  • Only writes can be sent. A read or a subscription for mini needs machine.read and machine.subscribe beside it, or a different design.
  • A plain task.run sent through the same pipe is run with Write::run, which uses the laptop's path and may route onward. "Never forwarded again" holds only if the sender picks the wrapper.
  • operate does not look at who sent machine.write. Any client the server admits can send it, with any environment variable names. Not tried from a phone.
Proposed
hello { client: { kind: "machine" } }
request {
  repository: "repo_30…",
  selection: { profile: {…}, participant: "Ada",
               agent: null, source: null },
  secrets: { "NAME": "…" },
  operation: { kind: "task.run", … }
}
  • The server decides from the connection: a machine client's operations run here, in this Machine's checkout of repository, whatever their kind.
  • Reads and subscriptions for mini need nothing new on the wire.
  • MachineOperation, in_checkout's JSON rewrite and the environment map go. With secrets in the request, so do forward::take, exported and the first SSH for environment values. Files named by forward.files are still delivered as files.
  • The plan already has Selection on Request in PR 3. This moves it to PR 1, where the wire shape is first shipped, so machine.write is never released.

Counterexample kept: the constraint "credential bytes travel on SSH stdin, never in arguments, logs, the store or Session records". A request is on SSH stdin, but the server records request telemetry. telemetry() strips named fields from writes today; secrets in the request would need to be a field that telemetry and Debug cannot print. If that cannot be made certain, the file stays.

Smaller things, in this PR's reach

  • A stalled mini hangs the command. The plan lists it as open. Every other failure in the table names its cause; this one says nothing.
  • The demo promises a line PR 1 does not have. The plan's Demo shows lf task status LOO-123 --subscribe answered by mini's server; its Slices put that in PR 2.
  • Hold's reason. Adding reason to Write::TaskHold lets the CLI call Write::run and removes the copy in mutation.rs.

Larger than this work

  • Four places still decide where a command runs. PR 3 owns it.
  • Write in the application crate keeps the execution crate from sending one, which is what ContinueRun and the argv spelling in the engine both work around. Moving the operation types down would remove both.
  • No CI suite has run on this branch; scratch defers the matrix until gate.

Questions

1. Where does "who is asking, for which repository" live?

  • a. On the request, typed, in this PR. machine.write and the environment map are deleted before they ship.
  • b. As built. PR 3 replaces it, as the plan says.

2. What makes the server run an operation here and never send it on?

  • a. The connection: a client that said it is a Machine. Applies to every operation.
  • b. The operation's kind, as built.

3. How do a run's secret values reach mini's server?

  • a. In the request, as a field nothing can log. Files are still delivered as files.
  • b. As built: a separate SSH writes a file and the request names it.

4. A mini that accepts SSH and never answers:

  • a. Bounded in this PR, with a message naming mini.
  • b. Left open, as the plan has it.

5. Reads and --subscribe for a Task on mini:

  • a. In this PR. With 1a and 2a they need no new message.
  • b. PR 2, and the demo loses its second line until then.
