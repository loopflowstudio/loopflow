Do the plan's concepts and the code's concepts line up?

Area taken: how a repository's plan is shared without Linear or Asana — the save, the stamp, the two carriers, when they run, what lf repo tracker says, claims, and what "this repository" means across clones. Taken whole because the branch replaces all of it. Reviewed 2026-11-18 at 3234477ab1 against base e55f40bde0, with all three slices built and QA's run (scratch/qa.html) as the record of what it does. The page this replaces reviewed the plan before anything was built; its three proposals were built and are marked below.

Blue marks what this review proposes. Everything else exists on the branch. The one proposal sent back to implement is in scratch/plan.md as slice 4.

Answer

What the plan is lines up. When it travels does not. A field, its stamp, a whole record, a cursor per carrier: each is one idea a person can say and one thing in the code. But "I saved; it goes out" has no owner. Seventeen call sites outside the carrier modules decide, each for itself, whether to tell the hub, Git, or both, and the person sees the result as rules they have to learn: a save from the CLI reaches the hub in a second and the remote in up to a minute; the same save from Desktop reaches both in two seconds.

One interaction, walked

Laptop L and mini M share origin. No hub. On L: lf task create 'x'.

As built (QA, measured)

L$ lf task create 'x'
     save → stamps → plan_changes
     sync_saved → plan_hub::sync(send_only)   no hub: nothing
L$ lf repo tracker
     Plan: Git origin, 1 unsent.
     … L's server minute …            38 s
     push refs/loopflow/plan/L
     … M's server minute …            97 s
M$ lf task list                       x

The same create sent to L's server socket (Desktop's path): pushed in 1.6 s, by plan_carriers::after_command.

Proposed

L$ lf task create 'x'
     save → stamps → plan_changes
     sync_saved → plan_carriers::send
        hub:  records past its cursor, if a hub
        Git:  records past its cursor → commit → push
L$ lf repo tracker
     Plan: Git origin.
     … M's server minute …            ≤ 60 s
M$ lf task list                       x

A send does not fetch. Reading stays as it is: the hub when a command wants fresh, Git on the minute or when asked.

The biggest mismatch: who sends a save

Before

The first review made both carriers one shape in storage. The scheduling kept the hub's old call sites and added Git's beside them. So the rule a person would have to learn is a table:

                     hub        Git
CLI save             now        server's minute
served save          5 s quiet  5 s quiet
lf task sync         now        now
claim / place        now        now
provider exit        read       —
--subscribe          read       —
no server            now        never

docs/work.md had to be loosened to "within a couple of minutes" after QA; the plan's own "What people see" says a minute.

After

Two verbs in ops/plan_carriers.rs, and nothing outside it names a carrier to send by.

send(repo)   after a save: each carrier takes the
             records past its cursor. No read.
sync(repo)   when asked, before a claim, on the
             minute: read and send, each carrier.

The table becomes one line: a save goes out by every carrier the repository has, whichever door it came through. Reads that nobody asked for still use the hub only, because a hub read is one request and a fetch is not; that distinction has a reason a person can feel.

Why this one. It is the plan's second difference from the design ("one shape for both carriers") carried to the place it stopped. It removes a row of QA's "still wrong" list and lets the docs say what the plan promised. Passed over: a CLI save asking the running server to exchange (a new wire operation, and nothing happens with no server); shortening the minute (a fetch per repository per interval for everyone, to fix a push); leaving it and documenting two minutes.

Checked and left alone

An ownership entry has its own order beside the plan's stamp: two clocks.The entry travels with a move before its comment does and has to sort the same on arrival. order is drawn from the plan clock, so it is one clock read in two places.

Clones keep their own repository id instead of converging.QA showed converging hid every Task saved under the first id. The id is a local name for a checkout now; that is the honest reading, and the mismatch above is what remains.
plan_stamps, plan_changes, plan_carriers, plan_refs: four tables.When a field was written, what changed here last, how far each carrier got, what was read from each ref. None derives from another.

Larger than this work

  • Repository identity. A person means the remote. The code mints an id per clone, then learns the others' from plan refs, and a hub is asked by an id it may not have seen yet: "no checkout" for up to a minute, and an error that tells the person to --bind although the docs say a remote needs none. A second clone of one remote on one Machine shows an empty plan. An identity every clone can compute alone (the repository's root commit, say) would remove locators, the repository file and --bind. It means re-keying tasks.repository_id for every store, which is its own Task.
  • lf repo tracker reports where the plan is shared; only one of its three answers is a tracker.
  • Ref history only grows, and no command deletes a gone Machine's ref.

Questions

  1. A save made by the CLI.
    1. Pushes its own records by Git as it already sends them to the hub, as proposed (slice 4).
    2. Asks the running server to exchange; nothing without a server.
    3. Stays on the server's minute; the docs say two minutes.
  2. lf task run on a Task a teammate holds, seen.
    1. Takes it over and tells their Sessions, as on main and as built.
    2. Refuses and names the holder; lf task claim is how you take it.
  3. lf task sync without a tracker.
    1. As built: needs a Task id, prints <id>: nothing unsent.
    2. Takes no id and prints the lf repo tracker lines.
  4. A teammate's Machine in lf task list.
    1. Its id, as built; names stay private to the Machine that gave them.
    2. Each plan ref carries the name its Machine gives itself, so everyone who can fetch reads "mini".
  5. Repository identity.
    1. Leave it: an id per clone, locators, --bind for a hub with no remote.
    2. File a Task for an identity every clone computes alone.
