Everything opens. The owner rule we deleted still decides one pane.

The three implications of the sixth pass are in the tree: a started Task nobody owns opens like any working Task, an unstarted Task's pane is a Task-start offer, and Tasks and primaries share one placeholder with one Retry. Reading the code again, the owner survives in one predicate: whether a selected Task shows its conversation panes at all. Working Tasks are now covered by their intent and unstarted ones by their Start offer, so that term decides only what a finished Task shows by default. Who owns a finished Task says nothing about whether it has a conversation to show. Marked proposed below; everything else exists in the working tree. These findings come from reading the code, not from running it.

Counterexamples that held

  • A started Task nobody owns opens; the Wave board's "nothing moves an unassigned Task" rule is untouched because the reading pass claims nothing.
  • An unstarted Task never reaches a conversation gate: its slot, tile and pane offer Rust's task run.
  • No primary shows "Conversation not open" except after Close or a failure: a queued primary reads as opening as soon as the Machine is known.
  • A primary on another Machine is refused by the queue's Machine check; its checkout is Rust's persistent one, so only the Machine is compared.
  • A store without a runtime prepares and launches nothing, so headless registries and tests never spawn lf.

Settled here

One implication goes to the next implement iteration, proposed: delete the owner term from showsTerminals, so a Task's panes follow its state and the person's choice. A finished Task then shows its conversation once the selected reveal presents it and its record otherwise. Consequence: Rust's explicit Start after a refused reveal reaches a person only through a chosen terminals view on a finished Task without history, since an unstarted Task's pane never renders it; the accepted design keeps explicit Start as recovery, so it stays. None of the owed native demo cases touches a finished Task, so this can follow the demo if the loop prefers.
