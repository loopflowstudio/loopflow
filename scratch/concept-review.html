What led here

The rest of this page is the reading that prompted the direction: why the input hold never lets go. Its own proposal and questions, further down, are superseded by the above.

One conversation, start to recovery

  1. You type a prompt in a Task's conversation, fix a typo with Backspace, and send it. The agent answers. You close the tab.
  2. docs/sessions.md says what happens next: "An unviewed, settled conversation ends its processes after two minutes of quiet." It doesn't. The Backspace marked the input as uncertain, and the prompt you sent afterwards did not clear that.
  3. You mark the Task done. Cleanup should remove its checkout and shell tabs about fifteen minutes later. It waits on the same hold, indefinitely.
  4. Days later ps shows hundreds of lf processes. lf process rollover --dry-run says "native input holds the conversation".
  5. The troubleshooting page this PR adds says: "Open it with lf resume <ID>, then send or clear what is there; the owner ends on schedule once its input is empty." You resume and send a prompt. Still held. Only quitting the agent releases it.

Proposed. Step 2 goes the way the docs say, because the prompt you sent settled the input. Step 5 works as written: send or clear, and it ends on schedule.

Why it never lets go

lf records the keys that reach the agent and keeps a small state for each conversation. One clean path leads back to empty. Everything else leads to Uncertain, and the only exit from there is the agent process ending.

What you didWhy lf can't account for it
Backspace, at any pointIt isn't a letter or Enter. The recorded text is discarded.
Enter on an empty editor, Ctrl-CSame rule.
Arrow keys, Esc, a pasteEscape sequences that aren't terminal replies.
Any key while the agent is workingA queued message or a permission answer can't be matched to a prompt.
A prompt lf can't match byte for byteThe acknowledged text differs from what was typed.

The rule was written to keep a draft from being lost (PR #1804: "Edits, paste, ambiguous input and missing acknowledgements can retain processes until native exit"). It does that. What it lacks is a way back: the test ambiguous_or_later_input_keeps_the_native_editor pins that draft⌫⏎, acknowledged and finished, still holds.

The docs paragraph, as it would read

Today, docs/sessions.md: "Edited, pasted or unacknowledged native input can retain the owner until the provider exits; saved history and screens cannot restore an editor or request."

Proposed. "Unsent input keeps a conversation running. Send it or clear it and the conversation ends on schedule. lf process list shows which conversations are kept this way and since when."

Earlier questions, superseded

1. What releases a held conversation?

1a
Only quitting the agent, as today. The troubleshooting paragraph in #1877 is corrected to say so.
1b
A sent prompt. One that the provider acknowledges and finishes, with no key since its Enter, empties the input from any state. Claude only until other providers acknowledge.
1c
1b, plus an age: input nobody has viewed for some number of days ends anyway, with its last screen saved. This also ends real drafts that were ever edited, since an edit discards the recorded text. You'd name the age.
1d
Only stop counting navigation keys on an empty editor (the earlier 1b). Backspace, paste and mid-turn typing still hold forever.

3. Does a finished Task's cleanup wait on unsent input?

3a
Yes, as today: the checkout and shells stay until the conversation is released.
3b
