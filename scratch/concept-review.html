2 · A read that cannot happen

You asked "does that diff need to be 1+ MB? woudl it be better if we handled new files seaparately". What was built for a committed new file over 1 MB: read its patch, see it cut, then read the file with lf task file. Both reads stop at the same 1,000,000 bytes, and a new file's patch is its contents plus one byte a line. The second read succeeds only for a file a few kilobytes under the limit. scratch/task-details-research.html, at 1.28 MB, is past both.

Remove the second read. The pane then says one true thing: a new file over 1 MB shows its first 1 MB and "Cut at 1 MB". Today an untracked one that size shows a note and no lines; it reads the way the committed one does, if lf task diff --path answers for an untracked path. Reading past 1 MB is a protocol change and belongs to Task 4556d0.

3 · A failed file stays failed

Normal: files fill in from the top, the title reads "12 changes in 9 files · reading 4 more", then the count settles.

Failure: the server restarts mid-read. Each waiting file reads "Could not be read: …" and leaves the list of files to read. Lines already shown stay.

Recovery today: edit that file, commit, or leave the Diff page and come back. Nothing on screen says so. The note carries Retry, as a failed folder in Files does.

Holds as built

List first, lines after. The file list is whole from the first read, so the sidebar, the hidden counts and the order never wait on a large file. Hidden files are not read until shown.

One reload rule. While the comparison's commits stand, only the files the observation named are read again; a new commit reads all of them, each keeping its old lines until the new ones land.

Two readers of one file. Files' Diff mode reads its file apart from the stream because it compares your unsaved draft. Both draw through ReviewStream.
