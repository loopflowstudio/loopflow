5. Choices built for review

Each choice below is reversible and already implemented on this branch. Reply with the number and letter (for example 1a or 3b) if you want any changed before landing.

1. What happens after a PR merges on code or feature?

Without verify, a Task closes as soon as its PR merges — nothing calls you back to check post-merge CI on main or confirm deployed behavior.

  • 1a (built) Complete immediately on merge, and remove lf verify everywhere. Rely on qa, ship-review, and gate before merge; if main breaks afterwards, reopen the Task, file a new one, or run lf incident. Repos that want a post-merge stop add their own interactive step after deliver.
  • 1b Add an automatic post-merge check inside deliver so an agent checks post-merge CI on main before marking the Task done (adds one unattended agent run after every merge).
  • 1c Remove verify from code and feature, but keep lf verify available as a standalone builtin skill so other repositories that reference or extend it keep working unchanged.

2. When should lf task run warn that a run may merge the PR?

Previously, any run with no human stop ahead (or with Auto turned on) printed this run may merge the PR — even for workflows like pursue that only open a PR and never merge, while custom workflows with a human stop after merging stayed silent.

  • 2a (built) Warn only when the run can actually reach a merging step before stopping (and Auto is not off). pursue and research never warn; code warns after ship-review; custom workflows with a post-merge stop warn when crossing the merge.
  • 2b Keep the previous behavior (warn whenever no human stop lies ahead or Auto is on, regardless of whether the workflow merges) to keep this PR strictly to Graph and skill deletion.

3. Should Desktop’s Start menu switch to the same merge check in this PR or a follow-up?

Desktop’s Start menu shows merges without asking for workflows that merge before any human stop. Today it guesses from command names on the client, so custom workflows using pr arm, pr-land, or conditional branches can be mislabeled.

  • 3a (built) Handle in a follow-up Task after this PR lands, keeping this change free of client/server protocol changes while leaving the shared check ready on the server side.
  • 3b Include it in this PR so Desktop’s Start menu and CLI read the exact same server answer immediately (changes the catalog protocol shape between Desktop and older installed servers).
