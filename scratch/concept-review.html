Signing Machines in, as built: do the concepts line up?

LOO-957 after all four slices, QA and compress (HEAD c8f6d1ca83, against base 2593c489d7). Area taken: everything a person touches to get any Machine signed in to any provider: lf machine login / logout / logins, approvers.<provider>, ondemands.<name>.logins and rental prepare, the launch check, and --refused. The pre-build review (commit e207309a92) settled the verbs and the provider list; this one reads the code they became.

existing is on this branch now; proposed is this review's change.

The interaction, walked once

A rental for a Task, from a template made with lf ondemand add code … (no --logins). This Machine is signed in to Claude, GitHub, Linear and Doppler.

  1. lf --rent code -a claude implement. The rental starts; prepare reads lf machine logins here for the default list: github, claude, linear, doppler.
  2. GitHub transfers, Claude asks for a paste, Linear renews and sends.
  3. Failure: Doppler reaches credentials::connect, which ends in bail!("machine login supports github, opencode and linear"). Prepare stops; the repository is never cloned; the step never runs. The message names neither Claude nor Codex, which just worked.
  4. Recovery: the person has to learn that "every provider signed in here" means "every provider lf can carry to another Machine", and re-make the template with --logins github,claude,linear. Nothing on screen says so.

The same gap shows by hand: lf machine login --help lists all eight providers for [<machine>…], and lf machine login asana mini fails after parsing. No fixture reaches prepare, so no test sees it.

The biggest mismatch: "every provider" is two different lists

As built existing 
// lf/mod.rs: one parser for every target
provider: Provider,      // 8
machines: Vec<String>,

// rental.rs prepare: default
logins(here).filter(SignedIn)   // up to 8

// credentials.rs: the real set
_ => bail!("machine login supports
            github, opencode and linear")
Three places, three answers. The one that is true is a string.
Proposed proposed 
// login.rs: the set, once
pub fn reaches_other_machines(p) -> bool
  // Claude, Codex, GitHub, Linear, OpenCode

lf machine login asana mini
#  Asana signs in on this Machine only;
#  run `lf machine login asana` on mini

// prepare default
logins(here).filter(SignedIn)
            .filter(reaches_other_machines)
One predicate, read by dispatch, prepare's default and the help text. An explicit --logins asana still fails, at lf ondemand add, not at rent.

Why this one: the plan promised "services sign in through the same command", and here they do; what never got a name is that three of them only do it here. Naming the set makes the system smaller (the stale bail! string goes) and turns a rental that dies before cloning into one that starts without Doppler. Passed over: building remote transfers for Asana, Notion and Doppler. That is more behavior, not review; it would take a Credential variant each plus the target's receive and identity check, and is worth a Task only if a rental needs one.

Counterexample checked: a template that lists doppler on purpose. Rejecting it at ondemand add keeps "the list is what prepare signs in" true; skipping it silently would make the list lie.

Smaller, not for this change

  • Prepare with no approver in a headless run fails the whole rental on Claude's paste even when the step runs on Codex. Recorded behavior ("at most one approval per provider, none with command approvers"); a person who rents headless sets a command approver or --logins.
  • Approver in config::placement: rename the home if that file is next touched.

Questions

  1. Providers that sign in here only (Asana, Notion, Doppler):
    1. one predicate; dispatch says "this Machine only", prepare's default skips them, ondemand add --logins rejects them (chosen)
    2. build remote transfers for them (a Task of its own)
    3. leave as built; document the five
  2. Should a usage-limit refusal count for --refused?
    1. yes, as built
    2. no, only signed-out and missing-login refusals
  3. Should --refused include this Machine?
    1. no, as built: lf machine login codex is right there
