Where a saved record lives

In the storage crate, unless a crate that does not depend on storage needs it; only then in loopflow-model. The model is 1,671 lines and the terminal depends on it, so each record added there rebuilds the terminal and everything else on every edit. This places TaskGraphPosition in storage. Normal → failure → recovery

A steer is saved and its marker touched under the write lock; the next hook check sees it. A reconnecting viewer whose recorded PID was reused stays unknown: never dead, never idle, never permission to close. A replaced provider still cannot change its conversation, and a capture from another Session is still refused, when the caller arrives as a value. Add focused regressions for the steer-marker ordering and the replaced-actor refusal before those files move.

Order

  1. Ownership/placement, rental hand-back and Machine declarations: saved scope → observed configuration → SQL command (already specified).
  2. The nine sites above.
  3. Move synchronous storage with its records, its own files, migrations and schema generation in one cut. Before moving, classify every remaining crate:: name under store/sqlite as stays, record moving down, or supplied by caller.
  4. Measure, then choose the next cut.

Questions

None blocks this pass. These would change the direction if answered differently:
