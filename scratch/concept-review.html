The biggest mismatch: who says why a provider refused

The Task's own title puts failure classification on the Harness API. The committed method does that in name. In practice the harness is asked to parse a line that drive::run built from an event the harness's own decoder emitted two steps earlier.

Before exists

// harness/mod.rs
fn classify_failure(&self, line: &str)
    -> Option<AgentFailure>;

// drive.rs, at each Error event
stderr.push_str(&format!("{code}: {message}\n"));
failure = failure.or(AgentFailure::from_code(&code));

// agent/mod.rs, after the run
result.failure = result.failure.or_else(||
    result.stderr.lines()
        .filter_map(|l| harness.classify_failure(l))
        .min_by_key(rank));

Three stations. Codes win over words by arrival order; words are ranked. The retry tests feed stderr strings shaped like lf's own formatting.

After proposed

// harness/mod.rs
fn classify_failure(&self, code: &str, message: &str)
    -> Option<AgentFailure>;

// drive.rs, at each Error event
stderr.push_str(&format!("{code}: {message}\n"));
failure = gravest(failure,
    launch.harness.classify_failure(&code, &message));

// agent/mod.rs, after the run
let Some(failure) = result.failure else { return Ok(result) };

One question, asked where the event is. _classify_agent_failure and the loose from_code call go. stderr is only what a person reads.

What survives: Claude and Codex classify a single failure exactly as now (provider_failure is from_code, then the same phrase lists). Pi and OpenCode still leave transient failures to the provider. A turn the provider finished is still not a failure.

What changes on purpose: when one turn reports two different failures, the gravest wins whichever arrived first. Today a coded one wins over a worded one.

Counterexample tried: a run that dies before any event (the driver cannot start). It returns CoreError today and is never classified by either design. No difference.

Passed over: a typed failure on ConversationEvent::Error itself. That is the truest shape, and it would delete from_code and the string codes. It is also a recorded wire type in loopflow-model, so it is its own change: a new optional field, fixtures in three languages, and every decoder's error sites.

The second one: a hook callback read in two places

Before in the plan

The shell script saves the first conversationId, drops other conversations, matches "invocationNum":0 to choose --moment start | tool | steer, and applies the marker gate. Then lf __context-block --harness antigravity reads the payload again to rename fields and shape the reply.

The plan's own test list puts "a subagent's hook payload gets {}" under harness::antigravity, a Rust test, while its design puts the filter in shell.

After proposed

The script answers one thing: is starting lf worth it. Mid-turn calls (invocationNum 1-9) go through the marker gate; anything it does not recognize starts lf.

Harness::hook_callback answers the rest from the payload: whose conversation (the thread file beside the delivery file, the one resume already uses), which moment, and the normalized callback. Its default is today's Claude and Codex behavior, with the agent_id check moved in from emit_block.

Cost: one lf start at each subagent's first model call.

What did not change

One agy process per turn; the provider names the thread; the launch folder under the cwd; PreInvocation and Stop as the only declared hooks; trust by session setting; step-<n> turn names; the five slices and their order. Slice 1 is still the one that can prove the plan wrong, and it now starts with the classification move, since that is what Antigravity's status: ERROR plugs into.

Outside this work

The word "provider". In the retry loop provider is a harness name; in provider_auth it is an account home that only Claude and Codex have. Antigravity, one sign-in serving Gemini, Claude and GPT models, makes the difference visible. The revoked-login rule compares harness names and is right for it. Renaming is a sweep of its own.

Questions

  1. Where is a failure classified?
    1. At the error event, classify_failure(code, message). Chosen; in the plan.
    2. Keep classify_failure(line) as committed.
    3. Go further now: a typed failure on ConversationEvent::Error, no string codes.
  2. Does -a agy work?
    1. No. The agent is antigravity; the install hint names the command. Chosen.
    2. Yes, as an alias that records as antigravity.
    3. Name the harness agy, the way the other four are named for the command a person types.
  3. An Antigravity step that used subagents shows only the parent's tokens.
    1. Ship it that way; say so in the README. Chosen.
    2. Count them in this change: follow each invoke_subagent result to its own transcript.
    3. Ship it, and mark the number as partial in lf history usage.
  4. Who filters a subagent's hook?
    1. lf, from the payload, at the cost of one process per subagent. Chosen.
    2. The shell script, by ANTIGRAVITY_CONVERSATION_ID, once a live run shows a subagent's hook carries its own id there.
  5. When one turn reports two different failures:
    1. The gravest wins (credential, usage limit, model, transient). Chosen.
    2. Keep today's rule: a coded failure wins over a worded one.
