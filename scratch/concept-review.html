Do a Task's concepts and the store's concepts line up?

LOO-937 at 0ef1ad038a (PR #1973), against its base a0548bfe28 (main through #1977). 2026-11-18. Replaces the page written at a3639aa8f2, whose four questions were answered and applied.

Area taken: everything a person knows about one Task and the record behind each piece: what it is (title, state, rank, Project, branch), which conversations and runs are its work, which conversation is its own, where it sits in a list, and what happens to all of that across a move, a reused path and an upgrade. Wider than the diff on one side: the launch code that decides a Task before the store records it is unchanged by this PR and is part of the same answer.

One interaction, walked

Normal. In the LOO-937 checkout, with no --task: lf implement opens a conversation and lf graph code starts a run. The launch finds the checkout's Task (counted_task) and names it; the store writes agent_sessions.task_id and graph_processes.task_id. Had the launch named none, the store would find it itself (starting_task_in). lf task show and Desktop list both by that column. A tile dragged in Desktop's Working board changes tasks.planning_rank, which Linear and lf task show too.

Failure. The repository moves on disk and a second clone takes the old checkout path. Each Task lists exactly its own Sessions and runs; no read matches a path (work_keeps_its_task_when_its_repository_moves_and_its_path_is_reused).

Recovery. lf install migrates the store while an older lf is still running (a Desktop app not yet updated, a long-lived process). That lf reads primary_scope='task' as "not this Task's conversation": the Task's primary conversation disappears from its Sessions there and cannot be reopened from it, until that process is the new build. Nothing is lost; QA saw it with 0.16.0+7bb879aff on a migrated home.

Biggest mismatch: A, two owners for "which Task is this directory's"

As built
The launch asks counted_task(cwd): load every task_checkouts row (969 on the live store), canonicalize each, compare Git worktree roots. Its comment: "decided by changing this function alone".
The store asks deepest_checkout(cwd): walk the stored path's ancestors against an index. The plan: "One rule, one function".
They agree on order (named, then checkout, then the caller) and on almost every directory, because the launch names the Task and the store only fills in what the launch left empty. They differ in a Git worktree nested inside a checkout: the launch finds no Task, so the agent gets no Task context and no usage rows, and the store then files its Session under the outer Task. And where two Tasks hold one root: the launch refuses, the store picks one.
proposed, not in this PR
One function in storage answers "the Task holding this directory on this Machine", and counted_task calls it with the worktree root it already computes. The scan of every checkout goes; so does the second definition.
Survives: a symlinked or /private path still resolves, because the caller canonicalizes before asking. Changes on purpose: nested worktrees get one answer (the choice is which), and "Multiple Tasks claim this checkout" becomes a fact the store can or cannot hold, decided once. Counterexample to check first: task_checkouts.worktree rows stored uncanonicalized, which the scan tolerates today.

This PR did what it set out to on the reading side, and the move-and-reuse failure is closed. A is older than the PR (counted_task came with #1954) and touches every launch, so it is stated here, corrected in the plan's wording, and not built at gate. LOO-934 ("reduce the store's reads to what the product needs") is where it fits.

Choices made for review

  • Advance to gate without building A or B. Passed over: unifying the two lookups now. It changes what every launch resolves, on a 105-file PR whose suites have not run since two merges.
  • B stays as main wrote it (a run already in an adopted checkout keeps no Task), with the upgrade backfill's opposite answer left in. Passed over: removing the Graph-run backfill clause for ended runs, which would leave pre-upgrade lf graph runs out of their Task's history.
