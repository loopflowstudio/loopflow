Before a Task runs: do the product's concepts and the code's line up?

Task 923677, reviewed before anything is built, against scratch/plan.md as kickoff left it and main at 0fa6a4e2.

The area taken. The Task names two screens: the New Task sheet and the empty or failed states. Both belong to one part of Loopflow for Mac: what a person sees before work is running. That is the sheet, an unstarted Task, the Start menus, a pane with nothing in it, and a pane whose read failed. The review covers that whole part, because the sheet and the prototype's "A Task that has not started" state show the same thing, and the plan built them from different facts.

"The workflow this Task is about to run" is one thing to a person. They meet it in the sheet, on a filed Task, and in every Start menu. The kickoff plan fixes the drawing (one WorkflowLine) and leaves the facts in three places, then adds a fourth sentence built from the least complete of them.

The second sentence is Rust's, word for word, the one the sheet shows. A dashboard tile shows the title and Start on one line.

Why this and not less. The sheet's workflow menu becomes StartFlowItems, so "3 stops" and "You take part at…" sit an inch apart. They have to come from one list.

Why this and not more. A filed Task could carry a whole TaskGraph at start before its first run, and WorkflowLine would need no second way in. Passed over: graph == nil is how the bar, "…" and Rust tell "has not taken up a Graph, may still choose" from "took one up", and that distinction is real. The outline is the part of a TaskGraph that needs no Task.

What changed in the plan

All of it is written into scratch/plan.md, each as a choice made for review.

  1. The outline carries interactive_steps; the sentence names them; a top-level step that contains a stop is marked; a Rust test holds a Graph with a stop inside an XOR path and checks the outline, the menu count and a started Task's reading agree.
  2. TaskStartOffer is the prototype's "not started" state; SessionSlotOffer goes.
  3. An unstarted Task's bar draws the step line from the outline. "Takes up … when it starts", "feature · repository" and "No workflow selected" go.
  4. One phrase for whose default a workflow is.
  5. "Choose workflow" reads "Start with…".
  6. The component is EmptyState, not StateView.
  7. WorkflowCatalogEntry and model.workflowCatalog go, without the "if".
  8. Step names in the plan and tests are Rust's (ship-review).

The first slice is still the wire and the sheet's step line. It now also draws the unstarted Task's bar, since that is the second place one outline has to read well, and it carries the agreement test.

Outside this work

Choosing a workflow for a filed Task without starting it. The app has no such action; the sheet's choice is stored only because filing stores it. It would take a Task-level "set workflow" in Rust and a place for it in the bar. A separate Task if wanted.

"Merges without asking" is still worked out in Swift from op labels that start with "land" (BacklogView.swift:127). It disagrees with nothing this change shows, so it stays. Moving it onto the outline would be one more field.
