One interaction, as it runs on the branch

Normal path

$ lf wave create billing
Added Wave billing; committed .lf/wave/billing
# 0 projects rows, nothing queued for the tracker

$ lf task create --wave billing 'Invoice export'
Invoice export · d11837
# one Project "billing", started, made in the save

$ lf wave status billing
  Project   billing (proj_4bd9…) · started
  d11837  unstarted — Invoice export

With Linear configured the first Task queues two creates, Project then Task. With a second started Project in the Wave the command says where the Task went: Tax lines · 0cf5d8 in Project Billing v2.

Failure and recovery

Failure: the save into an empty Wave aborts. The Project is made in the same transaction, so nothing is left behind (a_failed_save_into_an_empty_wave_makes_no_project).

Failure: the tracker is down. Task and Project are saved; their creates wait in tracker_actions. No "preparing" state, nothing for a person to retry.

Recovery from the wrong Project: move the Issue in Linear. Ending "Billing v2" there sends the next Task back to "billing", and a Task left in the ended Project still runs.

Upgrade: a store with a current Project and a KR keeps its Project; the new Task joins it and the KR text is no longer shown.

The biggest mismatch: a Project that runs

The branch removed the chapter a Wave works through. The chapter's own run loop is still in the code. A Project has an event journal with "started", "iteration completed", "steer", "interrupt" and "failed", from when lf ran a Project as an agent. On the store measured, project_events holds 30,536 rows (29,107 task_observed, 610 started, 458 failed, 352 iteration_completed), the newest written 2026-09-24. This branch marks projects.iteration leaving "since chapters ended" and keeps IterationCompleted { iteration }.

A Project is then a row with a name, a status and Tasks, in the code as in the product. The table and its saved rows stay until the contract; nothing is dropped here.

What must survive: interrupting a Task (lf task interrupt, a Graph's interrupt cursor), steering a Task or a Wave, and WorkRef::Project as an identity in the Work tree (WorkIdentity gives a Task its Project as parent). Counterexample that would break it: a path that launches a Graph bound to a Project, so latest_interrupt_id is asked about one. None was found; implement checks every WorkRef::Project caller before deleting the arm and keeps the arm if one exists.

Choice made for review: the brief says "Look for earlier attempts left behind (unreachable branches, hidden commands) and remove those too", so this goes in the Task. Passed over: leaving it for a separate cleanup, which would ship a branch named "remove chapters" with the chapter's journal API intact.

What the review changed in the plan

  1. Slice 5a: delete the Project run journal's types, API and tests; mark project_events leaving.
  2. Slice 5b: one definition of an open Project, used by the rule and by the name the command prints.
  3. Slice 5c: the two stale architecture lines; project_transitions, project_transition_items and project_events move to the "Leaving the store" row.

Larger than this work

A Task's Project is shown only at the moment it is chosen. Grouping lf wave status by Project (or a Project column) is new presentation over data the wire already carries. On the measured store 6 of 62 Waves hold more than one open Project.

A Wave without a tracker still costs a Project, and no command ends, adds or renames one there. Tasks belonging to a Wave directly would change every read that walks Task → Project → Wave.

The Task title still says "a Project is a Wave's optional tracker link". The steer withdrew that; the PR title and body should say what was built.
