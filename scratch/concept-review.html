LOO-1113 · Concept Review · Pre-Build Plan Review

Trackerless Plan Arrival & Carrier Read-State

Area reviewed: How a repository without Linear or Asana discovers, fetches, and remembers whether it has read its shared plan across carriers (plan_git, plan_hub, plan_carriers, sqlite::plan_carriers) and across plan-reading commands.
Why this whole area: LOO-1113's bug (lf task create suppressing lf task list's first fetch) is one symptom of a wider split: "has this clone read its remote?" is conflated with local checkout registration, wired into only two CLI commands, implemented for Git alone, and missing cross-process failure throttling.

Nothing in rust/ has been edited yet (HEAD 91531a9eb2 holds only scratch/plan.md and scratch/questions.md over origin/main 6c2560bd0f). This review checks whether scratch/plan.md fixes the underlying model or patches one corner of it.

3. The Biggest Mismatch — Before & After

The core mismatch: There is no single concept of "ensure this clone has done its first read from its carriers." Instead, main abuses checkout registration (repository_plans) as a proxy for "fetched", runs it only for Git, wires it into only two CLI commands, and drops failure throttling across CLI invocations. scratch/plan.md fixes the proxy bug cleanly for Git, but leaves the other three halves of the mismatch intact.

4. All Findings, Scope & Design Choices

F1. Track "carrier has read this peer" separately from checkout registration This work (LOO-1113)

scratch/plan.md's core fix is right: replace store.repository_id(repo).is_some() with PlanCarrier::has_read(), and record read completion inside exchange_with when failed.is_none(), before publish (so a refused push or not_taken Wave clash doesn't undo a completed read).

Design choice (internal, reversible): Reuse plan_carriers.seen_seq (setting 0 for Git via plan_read, hidden behind PlanCarrier::has_read()) vs. adding a first_read_at INTEGER column in a new migration. Recommendation: Keep seen_seq = 0 as proposed — it needs no migration, gets select_carrier's peer-change reset for free, preserves LOO-1110's zero-idle-revision trigger, and is completely internal (not on the wire, reversible if a read timestamp is ever needed). Update the field doc and SCHEMA.md so the dual meaning is explicit.

F2. Give every CLI plan-reading command the same first-read gate This work (LOO-1113)

Call plan_carriers::before_first_read(repo) from lf plan list, lf plan board (direct path), lf wave list, lf wave status, and lf wave plan alongside lf task list and lf repo tracker. On an already-read clone, the cost is one primary-key lookup in plan_carriers (~0.1 ms, zero subprocesses — plan_git::remote reads .git/config without forking since LOO-1110).

Passed over: Keeping before_first_read on only two commands. That leaves an arbitrary distinction between lf task list and lf plan list / lf wave list.

F3. Throttle failed first-read retries across CLI processes (60 s cooldown) This work (LOO-1113)

When a first fetch fails, plan_carriers.error is non-null and seen_seq stays NULL. Check planning_scope_checks (key plan-first-read:<repo>, 60 s window) only when held.error.is_some() (and record the attempt timestamp on failure). Happy-path first reads write nothing to planning_scope_checks; offline repeated reads finish in milliseconds; coming back online heals automatically on the next read after 60 s (or immediately on lf task sync).

Passed over: (1) Retrying on every read (up to 5 s stall every offline command); (2) Skipping whenever error IS NOT NULL (strands an empty clone online forever because LOO-1110's exchange_unowned skips empty repos). Both choices are reversible.

F4. Let before_first_read read an unread Hub when the clone has a repository ID This work (LOO-1113)

Move the "has read?" check from Git-only plan_git::first_exchange up into plan_carriers::before_first_read so it handles both carriers symmetrically: if a Hub is configured, store.repository_id(repo) is Some (e.g. after lf config repo --bind <id> or lf wt create), and Hub's carrier row does not satisfy has_read(), run plan_hub::exchange(store, repo, Why::Read(until)) too.

Passed over: Keeping before_first_read Git-only. That breaks the documented hub-only setup (lf config repo --bind <id> → lf task list) and skips the faster hub on a fresh clone. Reversible.

F5. Clean up stale comments & docs that contradict actual carrier behavior This work (LOO-1113)

Fix three false statements uncovered in this area: (1) plan_git.rs:337 and docs/dev/planning.md:284 still say first_exchange "registers the clone for exchange_unowned" (false for empty clones since LOO-1110); (2) plan_carriers.rs:3,165 says send "reads only what was not taken" (false for Hub, whose Why::Save always calls PlanChanges).

F6. Discovering the very first remote Task in a previously-empty clone Separate outcome

If Machine C clones an empty repo and runs lf task list (marking has_read = true), and Machine A creates the repo's first Task later, Machine C's lf server will not poll that repo (active_plan_repository_paths requires an open Task or active Wave) and lf task list will not fetch again.

What it would take: Decide whether empty clones should stay quiet (zero idle Git forks, matching LOO-1110, requiring lf task sync once) or receive a low-frequency/on-read refresh when a clone has 0 Tasks/Waves and hasn't checked recently. Kept separate so LOO-1113 does not regress LOO-1110's idle-server budget.

F7. Repointing origin's URL in place (git remote set-url origin …) Separate outcome

plan_carriers.peer stores the remote name ("origin"), not its URL. Switching a remote's URL under the same name does not reset sent_seq or seen_seq.

What it would take: Include or track the resolved remote URL (or remote identity) alongside the remote name in plan_carriers.peer, updating lf repo tracker display to keep showing the short remote name. Rare in practice; separate unless it comes up.

5. Questions to Decide

All four choices are reversible after shipping. Reply with numbers and letters (for example, 1a 2a 3a 4a).

1. Which commands should fetch the remote plan on your first look in a fresh clone?
Right now, only lf task list and lf repo tracker fetch on first read. If you clone a repo and start with lf plan list, lf wave list, or lf wave status, you see an empty plan.
  • 1a (Recommended) Every plan-reading command — lf task list, lf plan list, lf plan board, lf wave list, lf wave status, and lf repo tracker all do the one-time fetch if this clone has never read its remote yet. Later runs stay instant.
  • 1b Only lf task list and lf repo tracker (as in scratch/plan.md) — other list commands never hit the network; if you run lf wave list first in a fresh clone, you see empty until you run lf task list or lf task sync.
2. If your first lf task list fails offline, what should the next lf task list do?
Suppose you clone a repo and run lf task list with no network (it waits up to 5 s and falls back to the local plan). Then you run lf task list a few more times while still offline, and later reconnect.
  • 2a (Recommended) Retry after a 60-second cooldown — immediate repeat reads while offline are instant (no repeated 5 s hangs); once you're back online, a read a minute later (or lf task sync anytime) automatically fetches the remote plan.
  • 2b Retry on every read (as in scratch/plan.md) — as soon as you're back online, the very next lf task list fetches immediately, but every read while offline stalls up to 5 seconds.
  • 2c Don't auto-retry after a failed first read — offline reads are always instant, but an empty clone won't pull remote Tasks when you reconnect until you run lf task sync.
3. Should a first read also check your Hub when one is configured?
If you use a Hub without a Git remote and run lf config repo --bind <id> (the documented setup), running lf task list right afterward currently shows nothing because first-read only talks to Git. With both Git and a Hub, first-read also skips the faster Hub.
  • 3a (Recommended) Yes, read both carriers on first read — Hub-only clones show their Tasks right after lf config repo --bind, and clones with both carriers read from the Hub as well as Git.
  • 3b Keep first-read Git-only in LOO-1113 (as in scratch/plan.md) — Hub-only clones need lf task sync (or a save) first; file Hub first-read as a separate Task.
4. If a clone first reads an empty remote and a teammate adds the first Task later, should the background server keep polling that empty clone?
To keep idle Machines quiet, LOO-1110 stopped the server from polling repositories that have zero open Tasks and zero active Waves locally. That means a clone whose first read saw nothing will not notice a teammate's later first Task until you run lf task sync (or look up that Task by ID).
  • 4a (Recommended) Keep empty clones quiet on the background server — preserve LOO-1110's idle-server budget, fix the stale docs/comments that promise background polling for empty clones, and only revisit if this comes up in daily use.
  • 4b Poll previously-read empty clones too — file a separate Task to include empty-plan clones in periodic sync (or re-check on read) so a teammate's first Task appears automatically, at the cost of periodic background git fetch on idle repos.
