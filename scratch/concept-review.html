Who can start an agent, and what it is told about who is reading

Concept review for LOO-1119, "Remove the Discord bridge", at fe4ec68314 against base 472bacbd64. Everything the plan lists is built and committed, including the pass that gave the prompt the launch's run mode. This page replaces the review written at 200d4e486a.

The area taken: the bridge was the one place a message from someone other than the Machine's own person started an agent. The review covers that launch path with the whole change in it: the command, how a launch says whether someone is in the conversation (to the harness, to the prompt, and in the Session it records), a Wave's own config keys, the secrets lf strips before starting an agent, and the docs that named any of it.

One interaction, before and after

Before: a message in the channel

  1. Someone types in the bound Discord channel.
  2. lf discord serve product polls and sees it.
  3. A headless agent starts for the Wave with permissions skipped.
  4. Its final answer is posted back.

Failure: the someone is any non-bot member. Nothing asked who they were; guild_id was never read. Recovery: none short of stopping the process.

After: no message can do that built

  1. lf discord serve product prints "skill or graph not found: discord" and exits 2; lf help has no Discord line (both run for this review).
  2. An agent starts only from this Machine's account: a terminal, Desktop, a Task Graph, or an SSH peer that already holds that account.
  3. Talking to a Wave is lf resume --wave billing, from one of those. Away from every Machine there is no way in, on purpose.
  4. A checkout that still has a chat: block in its Wave config runs as before, with no warning.

What survives the merge: the bot token. It is still in Doppler loopflow/dev (names listed for this review: one Discord-named secret in dev, none in stg or prd), and lf no longer strips it from an agent's environment. Row 9.

Deleting was the smaller and truer fix than an allowlist: lf has no type for who asked, and with every remaining launch coming from the account's own person it needs none. Since the last review the launch and the prompt share one type for "is someone in this conversation". What is left is the copy the Session keeps: a free string under the old word.

The biggest mismatch: the Session keeps its own copy, as a word

A launch knows its mode as a type. When it records the Session it turns the type into a word, and readers turn the word back into a yes-or-no, each in its own way:

Written 
// run.rs: run_prompt
if kind.mode() == Mode::Interactive {
    begin_process_runtime(&built,
        "tui", …)
} …
begin_process_runtime(&built,
    "headless", …)
Read as "not headless" 
// session_record/capture.rs:303
interactive:
    manifest.surface != "headless",
// any other word is interactive
Read as "exactly headless" 
// commands/replay.rs:22
ensure!(
    source.surface == "headless",
    "… not a replayable
     headless request")

Twenty-seven sites spell the word by hand (13 "tui", 10 "headless" in Rust, 4 in JSON fixtures). One test (transport.rs, the resume delegation table) writes "interactive", a word no launch writes, and it passes because the first reader accepts anything. So the same yes-or-no has three spellings for yes: Mode::Interactive, "tui" and interactive: true.

Now built

pub struct SessionCaptureSpec {
    pub surface: String,   // "tui" | "headless" | anything
    …
}
// stored: manifest "surface": "tui"
// derived: SessionRecord.interactive

Its own Task separate

pub struct SessionCaptureSpec {
    pub surface: String,
    pub mode: Mode,
    …
}
// stored: the same key and the same two words,
// written and read in one place

The manifest keeps its surface key and both words, so no stored Session changes and nothing migrates.

Normal path: an interactive launch records "tui" and lists as interactive; a headless one records "headless" and can be replayed. Unchanged. Failure: today a typo'd word is an interactive Session that cannot be replayed, with no error anywhere; after, it does not compile. Recovery: a manifest already on disk with some other word must still read. The one reader decides, once, that an unknown word is interactive, as capture.rs does now.

Why not in this change: the bridge never wrote or read this field (its replies were workers, recorded "headless" like any other), the sites are almost all harness test fixtures this branch does not touch, and the PR removes an open door and should not wait on them. Passed over: leaving it. With prompt::Surface gone, this string is the only thing in the launch path still called a surface, and "surface" elsewhere in lf means a place the product shows up (CLI, Desktop) or a terminal pane. No Task exists for it yet; the plan lists it under Deferred findings.

Questions

1. When does the Discord bot's token get revoked?

Unanswered since the first review, and the one thing here that cannot be undone. Until it happens, a working bot token sits in Doppler loopflow/dev; any agent started under that config can read it, and any older installed lf can still run the bridge with it.

  • 1a. Recommended. Before the merge: revoke the token in Discord, delete the secret from Doppler loopflow/dev, remove the bot from the guild. The PR lists them as done. Nothing still needs the token.
  • 1b. After the merge, as the plan has it: the PR body lists the three steps as still to do.
  • 1c. Keep the bot and its token for some other use. Then lf should go back to stripping the name from agents, and the Task's "no Discord name in the code" no longer holds.
