The concepts

Two carry the whole thing; no new record, flag or state was added.

  • Store, the shared ~/.lf registry, with a migration frontier. A newer tail is additive unless a migration declares -- breaks: <reason>.
  • Reader, any lf process holding the store open: a Graph, a step, a status read. Skew is a reader behind a breaking tail, or a diverged history. It is the condition to name, never to hide.

Settled on the first pass, unchanged. The plan had left "a launch path that keeps running unbound under skew" as a possible product decision. Jack's accepted decision already answers it: skew errors exit nonzero and name the fix, and one lf per Mac (LOO-669, LOO-688) makes skew itself the defect. A launch that quietly ran unbound would hide the skew from the one person who can run lf install. So lf launches, lf context, ssh resume, lf ci and metrics publishing all fail with the skew. Recorded as settled in the working design.

Normal path, failure, recovery

  1. Additive install under a running Graph. Step finishes, revalidation passes, Graph continues. frontier_tests::a_running_older_reader_survives_an_additive_upgrade_under_it applies an additive migration under an open reader and keeps writing.
  2. Breaking install under a running Graph. Step row recorded, Graph stops with the skew text. The worktree keeps the step's files. Recovery is lf install then lf task run <ID>, which restarts that run from where it began under the ordinary stopped-Graph contract.
  3. Older Dev.app lf reads status. doctor_tests::status_reads_name_a_newer_store_instead_of_reading_empty runs four status commands against a store with a future migration: nonzero exit, skew and fix on stderr, empty stdout.

Counterexample held, not acted on

A step's own long-lived connection that meets a -- breaks: migration mid-write fails with a raw SQLite error rather than the skew text. Every fresh lf the agent runs inside that step names the skew, and so does the Graph at the step boundary. Wrapping every write in a revalidate would add machinery for a case -- breaks: exists to make rare. Kept in the working design so a later reader does not mistake the gap for an oversight.

The stored-credential lookup at launch (apply_provider_env_to_command, rust/loopflow/src/provider_auth/mod.rs) warns and injects nothing when the store cannot be opened. Under skew it is unreachable for a Work launch: implicit_binding (rust/loopflow/src/lf/commands/run.rs) and the selector path propagate the store error first, so the launch has already exited with the skew. Its other callers are lf auth flows. A second refusal on a path that already refused would be machinery, not clarity.

Private LF_HOME stores still refuse any newer tail, additive or not, because they self-migrate. Running steps live in ~/.lf; a developer pointing two builds at one private store sees the refusal with lf install.
