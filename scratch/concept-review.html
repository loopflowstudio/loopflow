The counterexample that broke it, now closed

A repository with no checked-in .lf/config.yaml, and lf set agent claude saved for it (the personal file beside the main checkout). A Task's worktree is gone, or half-made by git worktree add, at the moment a subscription reads.

files::private_path asks git::worktree_root, which reads .git with std::fs. It fails, so the personal file is looked for under the worktree path and recorded as a missing file there.
↓
The slot's dependencies: three missing files under the worktree, and the global file. Nothing about .git.
↓
The worktree appears. None of those answers change. The Task shows the settings of someone who never ran lf set, for as long as a subscription holds the slot.

As built now: the computation observes the checkout's .git, so the worktree appearing is a changed fact (personal_settings_reach_a_task_whose_worktree_appears_after_a_reading). A Task no longer depends on it at all: resolved_for_task finds the personal file from the Task's repository, which is there before the worktree and after it (personal_settings_reach_a_task_whose_checkout_is_gone). Before this branch the next reading resolved again and was right. It reaches a display only; launches resolve for themselves. A repository that checks in .lf/config.yaml is not affected: that file appearing is the wake-up.

The biggest mismatch, as it was: the key was not what the computation read

The design's one rule, in AGENTS.md and the server README: a computation reads observed facts and its key, nothing else. Outside exists so that settings carry that rule in the code. Three reads went around it; the right-hand column is now the code.

Before (first build)

// config.rs, inside derived(Settings{…})
files::private_path(repo)        // std::fs on .git
// placement.rs
Derived::GlobalSettings { home, outside }   // outside.home too
remote::apply_document(&path, &mut value)
  // reads PROFILE_ENV and lf_home_dir() again

Two are harmless today: in a served request the profile is always absent and both homes are the Machine's. They are still the drift the type was built to make unspellable.

After (built)

// personal_file_layers: .git is a dependency
observe::exists(&repo.join(".git"));
files::private_path(repo)
// one home, and the profile from the key
outside.home = store_home;
Derived::GlobalSettings { outside }
remote::apply_document(outside.remote, &outside.home, …)

A store's home can differ from LF_HOME, so the store's home is the one written into outside. Nothing inside either computation calls incoming() or lf_home_dir().

Normal: edit a settings fileOne resolve, every reading wokenSame
Failure: worktree missing at first reading, no checked-in configStale until another settings file changes or the server restarts.git appearing bumps a revision; resolved again against the main checkout
Recovery: worktree removed againStays on the last valueResolved again. A Task keeps the person's own settings from its repository and loses only the checked-in files, as the installed lf does

What would break the edit: a main checkout whose .git directory exists before and after while a linked worktree's identity changes underneath. exists on the checkout's own .git covers a worktree made, removed or made again at one path; it does not cover a .git file rewritten to name another repository. That is git worktree repair territory and was passed over.

Considered and passed over

  • Resolve the private path before derived and key on it. Correct, and pays a canonicalize and an ancestor walk per Task per reading for a value that changes about never. One observed existence check costs nothing on a hit.
  • Route git::worktree_root through observe. It has callers in launches and mutations that must not see a cached answer inside a bare reading. Wider than this.
  • Tie each variant to its type (a trait with an associated value). Removes the downcast panic and adds a trait per value for four call sites.
