Normal, failure and recovery walkthroughs

Normal

Rename Later to Someday while the sheet is open: In updates to Someday, File lands in the same Wave ID, and the Someday backlog opens with the brief selected even while planning is behind. Start with Use default resolves Someday's default at admission and opens the conversation.

Refusal

Remove Ops and add a new Ops while the sheet is open: Desktop's ID is refused with not_found and leaves zero rows in SQLite. In shows Wave unavailable and disables File and Start until a new destination is chosen. A missing named workflow returns invalid in place so Use default is one edit away.

Recovery

Lose the reply after commit: receipt lookup recovers the exact Task even if the Wave was later removed. Lose the reply before commit, then remove the Wave: replay confirms refusal and absence, parks the draft, and persists Edit draft across app restarts. Editing and resubmitting replaces the journal slot atomically under a new request ID.

Counterexamples verified: same-name replacement Wave has a new ID; Wave retirement mid-transaction rolls back cleanly; CLI provisioning after wave creation converts later errors to outcome_unknown because an effect already occurred; legacy name-only Wave drafts force a new destination in Edit draft; late replies never overwrite newer navigation.

Outside this work & remaining checks

Removed Wave's page draws as an empty repository (pre-existing on main)

Observed in QA round 3, section 5: after removing a Wave whose conversation exists in Session history, clearSelectionIfOutsideScope keeps the Wave selected and BacklogView falls back to the repository's name over an empty list. New Task recovery often returns here because a refused replay commonly follows Wave removal. Fixing this is a separate Wave-lifecycle product decision across sidebar, sessions and backlog: either redirect the window to the repository when a Wave is removed, or label the page explicitly as a removed Wave while keeping its conversation history.

Safe (CreationSubmissions.record rejects reusing the replaced ID), worth tightening only if convenient.
