Work session, worker, chat, batch: does the code say what we say?

LOO-924 as built at 0eeb7092b7, PR #1966, 102 files against main. The area is launching an agent: which of the four kinds a launch is, who decides, and what a person can call it afterwards. I took the whole launch area and not the last pass, because the names changed after most of the code was written. No code changed by this review.

The grid is in the code now, cleanly. Run has four variants and everything that reads it asks is_managed() or mode(). What's left: one of the four names is doing three jobs, and the words people see for the headless column don't agree with each other.

One interaction

lf task run LOO-12, its implement step, a bad answer, and a person looking afterwards.

  1. lf task run itself is classified Run::Worker (delegate_current(input, task_run) in bin/lf.rs). No agent starts here. delegate sees a Worker that is not a Graph step and re-runs the command detached.
  2. The Graph starts the step with LF_GRAPH_STEP=worker. The step is Run::Worker again; this time delegate returns Here, and Worker means "headless, and each turn is reported to the server".
  3. Failure: the answer fails its schema. The Graph runs lf --batch session resume ID --message … with the same env, so that turn is a worker too.
  4. Recovery: a person runs lf resume ID on the step's Session. It is refused: "ID is a Run (LOO-12 · code · implement · finished); `lf resume` takes only Sessions." The glossary calls that same thing a worker, and calls it a Session.

The biggest mismatch: worker means three things

The decided meaning is "WOrker = (Manage & Headless)". Rows two and three are that. Row one is a different fact, "this command leaves its terminal", carried in the same variant, which is why delegate has to ask run == Worker && graph_step() to tell them apart, and why the glossary's "no terminal or viewer" needs a second sentence for Discord.

As built

delegate_current(input, worker: bool)
  worker || worker_step() → Run::Worker
delegate(run, …)
  Worker && graph_step() → Here
  Worker                 → run detached

A launch kind decides whether a non-launch detaches.

Proposed not built

// lf task run: its own line, before any launch
detach_task_run(argv)       // no Run involved
delegate_current(input)
  worker_step() → Run::Worker   // always Here
delegate(run, …)
  only a work session is handed to the holder

Worker is exactly managed and headless. Run is only ever about an agent.

Tested. Normal: lf task run detaches as today, by its own call; steps and Discord answers are workers. Failure: the correction turn inherits the step's env and stays a worker. Recovery: nothing reads the kind afterwards, so nothing changes. Counterexample kept: lf -b task run waits for the Graph today through the same detached call; the split has to keep that. It is a move of about twenty lines in transport.rs and bin/lf.rs, with no behavior change.
