The three biggest mismatches, before and after

These three directly break real workflows on the first day if left as drafted.

1. Steer target: dead Graph worker vs. live Task

Before (kickoff plan) Drops reviews
1. Headless Graph step runs ship-review in worker session_9f1a and calls lf page build.
2. Stamp records "session": "session_9f1a". Worker finishes and exits.
3. Person opens scratch/ship-review.html beside Rex, writes 3 notes, presses ⌘↩.
4. Page sends session.steer(session_9f1a) → server saves steer and returns OK. Page clears the queue. Nothing ever reads session_9f1a again.
After (revised plan) Proposed
1. lf page build stamps "work": {"kind": "task", "issue": "LOO-1109"} (never a finished worker ID).
2. Person opens page beside Rex, writes 3 notes, presses ⌘↩.
3. Page sends task.steer(LOO-1109) → reaches the live Rex agent (or wakes the Task's primary Session, or forwards to a peer Machine).
4. Strip shows the server's exact delivery.sentence (e.g. session_4b2c reads it at its next boundary).

2. Desktop state ownership: split-brain localStorage vs. single owner in Swift

Before (kickoff plan) Resurrects & crashes
1. Person highlights 2 notes on scratch/ship-review.html in Desktop Files. Saved in WebView localStorage and copied to ReviewComments.
2. Person opens loopback.rs to verify a line (TaskHTMLView unmounts), adds 1 code comment, hits Send to conversation ⌘↩.
3. Swift sends all 3 comments and empties ReviewComments. Unmounted WebView never learns the queue is spent.
4. Person clicks back to ship-review.html → localStorage reloads the 2 sent notes and re-posts them into ReviewCommentsStrip. On peer Tasks (about:blank), localStorage throws SecurityError immediately.
After (revised plan) Proposed
1. Under Desktop's bridge, the runtime never touches localStorage. Every edit posts {type: "sync", path, build_id, state, items} to Swift.
2. Person switches to loopback.rs, adds a code comment, presses ⌘↩.
3. ReviewComments.insert sends all 3 on one line and wipes both items and stored page state — even while TaskHTMLView is unmounted.
4. Clicking back sends ready(path, build_id) → Swift replies null (clean). Works identically on peer Machines (about:blank); ReviewRenderedView stays read-only.

3. Direct actions (data-lf) vs. queued reply

Before (kickoff plan) Mixed lifecycles 
<button data-lf='{"kind":"task.create",
  "directory":"/Users/jack/src/...",
  "request_id":"...", "title":null,
  "request":"Retry bind", "wave":null,

Author must spell all 10 strict DTO fields. Clicking runs task.create immediately, then adds "Ran task.create → LOO-1200" to the unsent reply queue — popping Desktop's 1 comment · Send to conversation ⌘↩ bar for something already done.

After (revised plan) Proposed

  "request":"Retry loopback bind"}'>

</button>

lf page build expands and validates the partial JSON into a complete strict wire Operation (runtime fills per-click UUID request_id). Clicking confirms inline, runs, and becomes an in-place receipt Filed LOO-1200. Never enters the unsent queue or Desktop's comments strip; rides along as [already ran: …] only if you also send a steer.

What changed in scratch/plan.md

The plan is updated in place with zero contradictions left from the earlier draft. Pass order stays the same (Pass 1 still proves the riskiest piece: the loopback carrier + answering page).

  • Work-scoped stamp & task.steer first: lf-page stamps work (task / wave / interactive session / repository) plus build_id. Task pages steer with task.steer and display delivery.sentence.
  • data-lf separated and compiled: partial JSON in .page.html expands into validated strict wire JSON at build time; runtime generates per-click request_id; receipts stay in place and never pollute the reply queue or Desktop comments strip.
  • Swift sole owner of Desktop drafts: ready/sync/operation bridge on TaskFileReadingView only; no localStorage in Desktop; ReviewRenderedView stays read-only.
  • Quiet headless lf page open: background Graph steps print the URL without opening a browser window; adds --host auto|desktop|browser and rejects raw .page.html inputs.
  • Leaner loopback carrier: drops unused /<token>/ticket; restricts ServerOperation::PageUrl to local Unix socket connections.
  • lf page build grounded in Loopflow: reuses diff_snapshot / task_diff_base, makes lines optional, adds old-line for deleted lines, and defines <lf-component> strictly as {{attr}} + <slot>.

Questions for review

All choices below are reversible and already recorded in scratch/plan.md and scratch/questions.md so implementation can proceed. Reply with codes like 1b, 2a if you want any of them changed.

  1. 1. When you click an action button like "File Task now" on a review page, should it run immediately or wait for ⌘↩?
    • 1a. Chosen in plan: Finding choices ("Fix here", "File Task", "Drop") stay in the ⌘↩ reply queue; explicit action buttons confirm inline, run immediately, show their result on the button, and stay out of the reply queue.
    • 1b. Queue every action button into the bottom strip so nothing executes until one final ⌘↩ (requires handling partial failure if one of three actions fails mid-batch).
  2. 2. When you press ⌘↩ on a page open in the browser beside Rex, what should happen to your reply?
    • 2a. Chosen in plan: Send it immediately to the Task (waking or steering the agent right away, with a status line saying who reads it).
    • 2b. Type it into your Rex terminal's unsent input box without pressing Enter so you can edit it first, falling back to immediate steer only when no interactive session is open.
  3. 3. Where should a review page open when an interactive agent in Rex presents it?
    • 3a. Chosen in plan: Open in your Mac's default browser beside Rex (and stay silent during background/headless runs, printing only the URL).
    • 3b. Launch or attach a dedicated browser tool (such as agent-browser, if installed) instead of the OS default browser.
  4. 4. Should review pages keep two files in scratch/ (source fragment + compiled page)?
    • 4a. Chosen in plan: Agents write short scratch/<name>.page.html fragments and compile to scratch/<name>.html; Desktop hides .page.html from the page list so you only see the finished page.
    • 4b. Keep compiled output in a hidden cache directory (or compile on the fly when serving) so scratch/ holds only one file per page (trade-off: you lose a double-clickable offline scratch/<name>.html).
