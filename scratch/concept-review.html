No product decision needed; keep the recovery model

The caller gets a result or an uncertain outcome. The work keeps its own Process and Task state. No design revision proposed. The behavior below is implemented on this branch; served-client QA is pending.

Biggest mismatch, before: failure to open the registry once could leave the launch waiting forever, even after the child exited. After: each poll can see recovery; continuously unknown liveness eventually returns outcome_unknown. That reply says nothing about whether the work stopped.

Actions → concepts → APIs

  1. Start a Task in a connected client. A launch starts an independent execution owner. task.run → engine::task::run → launch::start returns the command’s typed report when its Graph registers or it refuses.
  2. Read the reply. A report wins over owner exit or unknown expiry, including a final report read. read_existing_registry → lf_evidence supplies Live, Dead or Unknown; these observations add no Task state.
  3. Inspect before retrying. Existing Task, Graph and Process records carry recovery. outcome_unknown neither cancels the owner nor repeats the launch. No new record, wire type or setting is needed.

A concrete recovery

Start Task → no usable reply; liveness stays unknown
outcome_unknown: … inspect the affected work before retrying

lf task status <ID> --json
lf task runs <ID>

Graph running → leave it running
Reads unavailable → lf doctor, then inspect again when reads recover

For other launches, inspect the operation’s result and lf process list. Existing operating instructions already require inspection and leaving live Graphs alone; no skill changes are needed.

Cases the model must keep

Normal: return the typed report. Failure: an exited owner without a report or continuously unknown liveness returns uncertainty. Recovery: a readable registry can restore observation; a live observation resets the internal five-second grace.

A late success can happen after the error. The affected work must remain discoverable without relaunching it. A known-live owner can wait beyond the grace: this is not a deadline for every command.

Review questions, resolved for this headless step

  1. Does uncertainty need a new work state or automatic retry? No; existing records and inspection provide the intended recovery.
  2. Does the design need to iterate? No. Next, exercise recovery through the served client; polling tests alone do not establish that interaction.
