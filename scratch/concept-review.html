The holder survives an install. Does everything that talks to the server?

The code now keeps agents alive through a server restart, and the test for that passes. But the promise in the docs is about lf install, and an install changes the server's build while four other processes from the old build keep running and keep talking to it. Only two of those conversations are checked. That is the decision this page is about; four smaller ones follow.

Built from scratch/holder.md, docs/sessions.md, docs/troubleshooting.md, rust/loopflow/src/transport/README.md, transport.rs (reconnect_held), holder/wire.rs, server/service.rs and commits 5f040e37f..0afb960f5. Text beside an orange rule is proposed; everything else is built on this branch.

Concepts someone now has to hold: Session, view, holder (seen in ps and lf ps), and which launches go to it. Held terminal and position stay inside. The owner has not gone: skills, -b runs and Desktop Task shells still get one, so docs/sessions.md carries a five-row table of what runs where. "Terminal" also now means two things in the store: the pane you look through (terminal_id) and the PTY the agent lives in (held_terminal_id).

The mismatch: one build used to stand on both sides

An owner and the launcher beside its agent were always the same build, started together. The server now stands where the owner stood, and the server is the one process an install always replaces. After lf install, these are still running on the old build:

The gate test (held_session_survives_server_restart) stops and starts the same binary. So "lf install mid-turn: the turn keeps streaming and views continue" is shown for a restart, and holds for an install only while the viewer frames and control requests happen not to change. On November 4 an install broke live Sessions through exactly this kind of gap. I read the reconnect path and the wire headers, not every handler; a check I missed would change this section.






Proposed: a view replaces itself; a conversation never has to
A view holds nothing that matters: the screen is in your terminal and its place is one number. When a plain-terminal view reconnects and finds a server of another build, it execs the installed lf as a view of the same terminal from the same position. It already draws nothing while waiting, so nothing shows. The server then only ever speaks its own build's viewer frames, and those can keep changing freely.


Proposed: what an old launcher says is best effort
The launcher's reports improve the record; none of them keeps the agent running. A report the new server does not understand is logged once as a recording gap and the conversation carries on. The exit code still arrives from the holder's exit.json.


That leaves one protocol that must be readable across builds, the holder's, which is the one already designed for it.







Smaller things the walk turned up



Desktop Task shells are the last reason the owner exists


When bare launches go direct (LOO-820), skills and -b runs stop needing an owner. Desktop Task shells would be the only thing left on lf session serve, and the reason on file is "they run without a server on headless Linux". A holder already starts any argv and knows nothing about agents.


ProposedA Task shell is a held terminal like any other. The table in docs/sessions.md shrinks to two rows: in the holder, or in your terminal. The owner and its takeover and rollover rules can then be deleted, not kept for one caller.



A stopped server is refused, not started


Built: lf resume --task with the server down prints Loopflow server is not running; run lf server status and starts nothing. Desktop's first connection asks the installation to make the server ready. The docs written in this run disagree with each other about lf task run in that state: troubleshooting says nothing starts, sessions says the Graph runs and only the conversation is skipped.


ProposedA managed launch asks for readiness the way Desktop does and only reports failure when that fails. lf task run starts its Graph either way.



A plain terminal says nothing while the server is away


Built from "(3) i dot know that we want to do any overlay for raw lf": the view "waits, drawing nothing and discarding what is typed". During an install that is a second or two. After a crash it lasts until the OS restarts the server, and the terminal looks hung while keystrokes vanish.


ProposedStill nothing in the screen. The terminal's title, which the relay already sets, reads Reconnecting… until the view continues.



A killed holder


Built: every agent in it ends; each view says the process is gone and offers resume. Nothing lists what was lost. Someone with thirty conversations in one holder finds out pane by pane.



What falls away


For a held conversation, "superseded" has little left to mean. The agent is not an lf build; the holder is small and stable; a view replaces itself. So lf process rollover and resume's takeover of an old owner have nothing to do for held terminals, and the plan's open line "a superseded build in a holder is never moved onto the installed lf" can read as intended. An old holder is retired by its conversations ending.

  • 1a Replaces itself with the installed lf and continues from its position.
  • 1b Closes with a line telling you to run lf resume.
  • 1c The server keeps speaking older viewer frames.


2. Reports from an old-build launcher beside a running agent


  • 2a Best effort: an unreadable one is a logged gap, the conversation carries on.
  • 2b A small frozen set the server always understands, like the holder protocol.


3. Desktop Task shells


  • 3a Held terminals too, in this Task.
  • 3b Held terminals, as a follow-up Task alongside LOO-820.
  • 3c Stay on their own owner process.


4. A Task or Wave launch while the server is not running


  • 4a lf gets the server ready itself, then fails only if that fails.
  • 4b As built: print the message and stop.


5. A plain terminal while the server is away


  • 5a Nothing at all, as built.
  • 5b The title says Reconnecting…; the screen is untouched.


6. After a holder is killed


  • 6a As built: each view says so and offers resume.
  • 6b Also one place that lists the conversations it took.
