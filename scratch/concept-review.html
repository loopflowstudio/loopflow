Mismatch B: ui.yaml double publish, mid-loop sync, and Auto-Ship demo

In code, build ends with pr-publish because interactive: ship-review comes next and needs a PR URL. In ui, nothing stops between compress and deliver (reflect → gate → land), so pr-publish runs an extra skill, pushes a CI run, and lets reflect + gate immediately push again and cancel it. Meanwhile, demo.md has never been a loop decider in a builtin Graph: its headless note ("say the demo didn't happen and finish") clashes with stand_in_message under lf task auto on / Auto-Ship, leaving agents to guess between blocked and blind advance.

Before (kickoff plan)

After (updated plan)
kickoff→ loopsync→implement→qa→☺ demo →compress →deliver (reflect → gate [publishes] → land)

Plus 2 lines in demo.md ## Headless: when standing in as a loop decider, do not invent reactions — inspect scratch/qa.html (screenshots and transcripts), iterate only for visibly broken UI or missing promised behavior, else note that no person tried it and advance.

Mismatch C: verify.md fast-path counterexample

Walking a real merge through code breaks both earlier versions of the fast-path check:

Broken checks 
# 1. Brief: git diff <qa-head> origin/main
#    → fails as soon as another PR lands on main,
#      AND always diffs scratch/* (cleared on land).

# 2. Kickoff plan: git diff <final PR head> <merge SHA>
#    → FALSE PASS when gate/land pushed code fixes
#      or synced main after qa finished!
Fixed check (updated plan)

#  + post-merge CI on <merge SHA> is green
#  + no claim needs post-merge infra/install

4. Choices made for review

All choices below are reversible prose/YAML edits, written into scratch/plan.md so implementation can proceed without blocking. Answer by number and letter (e.g. "1b, 2a") if you want any changed.

  1. 1. Where should Wave memory curation live now that realign drops it?
    1. (Chosen) In the Wave conversation (wave-session) — it already owns editing and publishing MEMORY.md, while wave-operate stays a read/judge/act Task operator with no self-contradiction or duplicate section when build.rs combines them.
    2. In wave-operate (as the Task brief originally wrote) — requires dropping wave-operate's "Wave files are not yours to change" rule and deduplicating wave-session's existing memory section.
  2. 2. Should the ui workflow drop pr-publish before deliver and run sync before implement?
    1. (Chosen) Yes — deliver's gate already publishes the PR once (after reflect), avoiding a wasted LLM step and cancelled CI run; syncing before implement avoids mid-loop conflicts after a long human demo pause and matches build and fix.
    2. Keep pr-publish and implement → sync exactly as the brief drafted, accepting the extra push before reflect/gate.
  3. 3. What should happen when someone turns Auto-Ship on for a ui Task?
    1. (Chosen) Stand in honestly at demo — inspect scratch/qa.html screenshots/transcripts, iterate only if the UI is visibly broken, otherwise note that no person tried it and advance to ship (matching how Auto-Ship works at ship-review in code).
    2. Refuse to pass demo without a person — return blocked headless so a ui Task can never merge without a human seeing it, even with Auto-Ship turned on.
  4. 4. Should fix keep zero human stops (merging as soon as CI passes)?
    1. (Chosen) Zero stops — matches the brief; Desktop's Start menu already labels it merges without asking, and lf task auto off still stops before land.
    2. Add interactive: verify at the end — keeps the build fast and unattended, with one check on main after merge.
