Do a Task's concepts and the store's concepts line up?

LOO-937 at a3639aa8f2, reviewed as it would stand merged onto origin/main after #1974 (Sessions and Graph runs track their own processes; processes is leaving). 2026-11-18.

Area taken: everything a person knows about one Task: what it is (title, state, rank, Project), which conversations and runs are its work, which conversation is its own, and where it sits in a list, plus the records behind each. Not the branch against its old base: #1974 changed what "a Task's work" is made of, so that comparison answers a question nobody will ask again.

One interaction, walked on the merged frontier

Normal. lf task run LOO-937 starts a Graph run; its graph_processes row names task_id at launch (main). Its review step opens a conversation; that Session's row names task_id at creation (this PR). lf resume --task LOO-937 finds the Session marked primary_scope='task' (this PR). The Task page lists both by one indexed read each.

Failure. The repository moves on disk, then a second clone takes the old checkout path. Graph runs and Sessions keep the Task they recorded; nothing is matched by path. On main alone, Sessions still also join any Task whose checkout holds their cwd, so the reused path would pull the second clone's conversations into the old Task. This PR is what closes that.

Recovery. A released lf still running after the upgrade keeps writing processes rows (main bridges them) and task_primary_sessions rows (this PR mirrors them onto the mark). Both are window-only and drop with their contracts.

Biggest mismatch: A, this PR's Process half

Merged naively
processes.task_id (this PR, backfilled hourly)
graph_processes.task_id (main)
agent_sessions.task_id (both)
Three columns answer "whose work is this", and the first sits on a table marked leaving, filled by a maintenance pass for rows released lf writes and main bridges.
proposed
A Task's work is its Sessions and its Graph runs, each naming its Task when it starts. Drop processes.task_id, processes_task, process_task_backfill, the process_task() resolution and its tests; take main's Graph-run membership.
What survives: every Session and Graph run keeps its Task across a move or a reused path. What changes on purpose: an lf command run inside a checkout (lf commit) is no longer listed as the Task's work; main already stopped recording it as a Process. Counterexample not yet checked: a Graph run launched inside a checkout without --task. Main's record_graph takes the Task from its caller, so whether that run is the Task's depends on the launcher; the merge must confirm it or give it the checkout's Task the way Sessions get theirs.

The rest of this PR carries over: Session Task at creation, the primary mark (its agent_sessions rebuild redone on main's 46-column shape), one order, the move rule, dropping wire task_primary, the tracker revision and completion columns.
