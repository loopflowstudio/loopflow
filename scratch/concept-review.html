The command lf open puts in a host pane

LOO-986 concept review, 2026-11-19, against scratch/plan.md at kickoff. Nothing is built yet. Text in blue is proposed; the rest exists.

Area taken: the whole life of one pane command, from lf open writing it (open/conversation.rs Attachment::argv, open.rs resume_argv) to the answer its caller gets back (OpenReceipt), including what the command inherits (PATH), which harness it names, and who reports its failure. All three parts of the plan touch that one command, so the question is what the command is.

One interaction, as it fails today

An agent runs lf open --task LOO-1 --json. Rex, started by launchd, opens a pane running:

/bin/sh -c '<wrapper>' lf-open /tmp/…/receipt env -u LF_AGENT_CALLER -u LF_AGENT_OVERRIDE \
  LF_OPEN_RECEIPT=/tmp/…/receipt  PATH=<the agent's PATH + tool dirs> \
  /…/lf session resume ses_1 --agent codex:gpt-5
  1. The pane's lf (the viewer) asks for a held terminal; inside it the launcher finds no codex and prints codex CLI not found.
  2. The viewer relays that line to the pane and exits with the child's code.
  3. The wrapper writes Conversation exited before attachment (status 1).
  4. The caller gets reason: "…status 1; see the destination for diagnostics and retry the same command".
  5. Retrying the same command, an hour after someone moved the conversation to Claude, moves it back to Codex.

Three faults, one cause: the pane command is a snapshot of the opener's state (its PATH, the harness it read) instead of a name for a conversation. And the answer channel has one writer that knows nothing.

Biggest mismatch: the pane command carries state, so it goes stale

Before

lf session resume ses_1 \
  --agent codex:gpt-5   # read from the store
PATH=<caller's PATH>    # read from the caller

Replay = move. An agent's shims and venv ride into the person's conversation.

After (plan)

lf session resume ses_1
  [--agent X  only if the caller said -a X]
# no PATH: lf's main appends TOOL_DIRS

The command names a conversation. Everything else is read where it runs, at the moment it runs.

The plan already gets this right in parts 1 and 3. This review endorses it and adds nothing to the command.

What the review changed in the plan

Part 2: one rule for the answer — the first one stands

The plan's fail_open replaced the receipt by rename. Walk the failure:

  1. The launcher inherits LF_OPEN_RECEIPT from the viewer (native_session.rs:571 strips it only from the provider), so its main writes 'claude' is not installed. Install it with …
  2. The held terminal ends; the viewer's relay ends unacknowledged, so it writes its 4 KiB tail — the same line wrapped in relayed bytes — over the exact one.

Every writer creates the receipt only if it's absent (hard_link from the temporary). Who answers, in order: the launcher's error → the viewer's own error → the relayed tail (a provider's own pre-ready exit, e.g. "No conversation found") → the wrapper's status line. One rule covers all four, and the wrapper already follows it ([ ! -f "$receipt" ]).

The tail keeps live Tag::Out only, not Tag::Snapshot. Counterexample: an existing conversation's replayed screen arrives first; its provider then exits before ready; the reason would quote last week's screen.

The probe the plan opened with is half answered: a_launch_that_found_no_provider_leaves_nothing_to_resume already asserts the viewer's stdout holds "'claude' is not installed". The remaining probe asserts the receipt file is the launcher's exact error.

Part 1: a known cost, written down

Since #1981 (yesterday), a person's own lf open from a terminal carries their whole PATH into a Rex pane. The brief asks to delete that. After the change a launchd-started Rex pane sees launchd's PATH + TOOL_DIRS: a tool reachable only through shell rc (nvm, mise, asdf) is gone from the conversation. On this Machine: claude, codex → ~/.local/bin; gh → /opt/homebrew/bin; node → ~/.nvm/…, also present in /opt/homebrew/bin. So nothing here breaks; a Machine with nvm-only node would lose npx MCP servers.

Unchanged

Append rather than prepend; main rather than the provider's Command; part 3 as written; slice order (PATH first, because a fixture that relied on a bare PATH hiding a tool shows soonest whether appending in main holds).

Questions

  1. Tools that live only behind shell rc (nvm, mise):
    a) accept the loss, as the brief says — add directories to TOOL_DIRS when one is missed (in the plan);
    b) carry the caller's PATH when the caller is a person (agent_caller() none), drop it for agents;
    c) run the pane command through the person's login shell, as a terminal's own tab does.
  2. The receipt when two lf processes fail:
    a) first answer stands, launcher's exact error wins (in the plan);
    b) last answer stands, the tail wins.
  3. A provider that exits before ready:
    a) its last 4 KiB of live output is the reason (in the plan);
    b) no tail — only lf's own errors and the wrapper's status line; the provider's text stays in the pane.
