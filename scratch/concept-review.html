The phone attaches to a Process. The product promises a Session.

You said the phone's interaction is "an actual terminal on the actual Claude Code session". On the wire, the terminal is reached through an owner Process ID, which ends on lf install, retirement or takeover, and the contract says the client must notice and look the owner up again. The decision needed: does the API attach by Session, with the server resolving the owner, or stay keyed on the exact Process?

One interaction, with recovery

Open the app. The Tasks you are working on are listed. Tap LOO-593. Its Session's terminal fills the screen; you answer the question Claude is waiting on. You put the phone down. On the Mac, lf install replaces the executable; the Session's owner is replaced with it, the conversation keeps its draft and history. You pick the phone up.

Everything below the ticket stays as it is: the owner byte protocol in transport/README.md, claims fencing every attachment, geometry and input owned by the owner, bounded output continuation. The server resolves once and then copies bytes; it never sits between the person and the provider after that.

Why this is the consequential one

Identity. The style guide says a Session's identity, name and history survive takeover and that attachment claims are separate from provider identity. An owner Process is the opposite: by design it ends on upgrade, which is the November 4 incident, and on retirement. Keying the phone's only interaction on the transient half means every client reimplements the same lookup loop, and a client that caches an owner id has a stale handle after every lf install.

It also decides the shape of a design you have not approved yet. If the agent runs in the pane with no owner or relay (scratch/agent-in-terminal.md on jack-heart/icons), there is no owner Process to attach to, and process.attach has nothing to name. session.attach survives that change unchanged.

Counterexamples kept

Handoff A → B → A. A viewer attached to owner A is ended when B takes over; it is never silently moved, and no uncertain input is replayed. The fresh claim token still fences every attachment.

Desktop's exact reconnect. Desktop keeps the {owner} it was answered and can tell when a re-attach resolved to a different one. Exactness becomes something a client checks, not something the API forces on every client.

lf off the byte path. No in-place re-bridge when the owner changes mid-stream. That would put lf back between the keyboard and the provider; instead the bridge ends with a reason.

Draft of the usage doc

Attach a terminal to a Session

  session.attach {session}

The server resolves the Session's current owner and answers a single-use
ticket with the owner it chose. Open a connection of its own, present the
ticket, then speak the owner byte protocol. When the owner ends, the
connection ends with a reason; attach again with the same Session id and
the server resolves the replacement. The server never replays input and
never re-bridges a live terminal.

Questions

  1. Attach by Session?
    1. session.attach {session} replaces process.attach {owner}; session.owner folds into session.get.
    2. Both: session.attach for clients, process.attach kept for Desktop's exact reconnect.
    3. No: stay keyed on the exact Process; clients own the lookup loop.
  2. When the owner ends under a live terminal:
    1. the bridge ends with a reason and the client re-attaches by Session (server resolves the new owner).
    2. the server re-bridges in place and the client sees only a pause.
  3. Where it lands:
    1. LOO-718, which is building the ticketed attach now.
    2. #1813, with 718 rebased onto it.
  4. The same shape for reads (survey C1): one read per noun?
    1. lf task show is the one Task read (task.get) and task status goes; likewise one wave show.
    2. keep task status and wave status as separate reads.
