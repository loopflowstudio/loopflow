Do a Task's concepts and the store's concepts line up?

LOO-937 as built (HEAD fc60387a99 against origin/main), reviewed 2026-11-18. Area taken: everything a person knows about one Task across surfaces — its definition (title, state, rank, URL, branch), which conversations and Processes are its work, and the order Tasks appear in — plus the records behind them (tasks, tracker_items/pm_items, task_checkouts, task_primary_sessions, processes.task_id, agent_sessions.task_id, rank). The kickoff version of this page reviewed the plan; this one reviews the built change.

One interaction, walked

Normal. lf task run LOO-937 starts a Graph. Its Process row is written with task_id=LOO-937 (rule 1: the launch names it). The agent runs lf commit inside the checkout; that Process takes LOO-937 from the deepest checkout (rule 2). A helper "Generate PR title" Session started there records LOO-937 at creation. lf task status LOO-937 lists them by one indexed read.

Failure. The repository is moved on disk, then a second clone takes the old checkout path. Before: membership was a path match minus/plus a frozen-pair table, probed through sqlite_master. Now: nothing is re-matched; every row keeps its task_id, and the second clone's new work takes the new Task (work_keeps_its_task_when_a_checkout_path_is_reused).

Recovery. A released lf on the same Machine inserts Processes with no task_id during the window. They are missing from the Task's list until the server's maintenance pass assigns them by the same rules (cursor process_task_backfill, 5,000 per write). A Task that gains a checkout a taskless Graph is already running in adopts that work once (write_task_checkout_in).

Order. Dragging a Working-board tile above another Task of its Project writes that Task's rank (reorder_task → reorder_in), which reaches Linear as an order action; lf task and Linear show the same order. Dropping it on another Project's Task changes nothing and says why.

Biggest mismatch: A, the primary conversation

Before / now
agent_sessions.primary_scope = 'repository' | 'wave'
task_primary_sessions(task_id PK, session_id UNIQUE)
agent_sessions.task_id (must equal the row's task_id)
Three places answer "is this the primary, and of what". The 3 live disagreements were repaired by the migration; the shape that allowed them stays.
proposed, not this Task
agent_sessions.primary_scope = 'task' | 'repository' | 'wave', with a partial unique index on (task_id) WHERE primary_scope='task'.
"Which Task" has one home (the Session's task_id); "primary" has one representation for every scope; a disagreement is unspellable. Costs a table drop (staged, LOO-877's contract) and moving task_primary_sessions readers. LOO-932 makes the primary exist at filing and is the natural owner.

Why it is not in this work: LOO-874 just created task_primary_sessions as the expand step for tasks.primary_session_id; replacing it now stacks a second expand on an unfinished contract. Nothing in LOO-937 makes it worse.

B, the cross-Project drop

The board is grouped by Project, so dropping a tile among another Project's Tasks reads as "put it there". The code refuses with a reason. Moving it instead would be: set project_id (a Linear project change, already an exchanged fact), then move_in. That is new behavior, so it is scope, not a fix here; the refusal is honest and visible.

Verdict for this Task

Nothing to change. Every fact the brief named has one home or is explained as desired-vs-observed; membership is a column; one order. A, B and C are larger than this work and are written above with what they take.
