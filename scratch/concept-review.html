Does the pane tell you when you can continue?

LOO-1064 reviews Desktop Session opening, resuming and recovery. A Session keeps the conversation. A provider thread can run in a new process. A pane can reconnect to the held terminal while the provider keeps running.

A past resume looks like a live connection state

Before LOO-1064, a provider resume could appear twice after the pane was ready for input. One copy took up a row and the other covered the first terminal line. The strip already named the provider and reported its activity.

On a later reconnect, the stored event can still say “Resumed in a new process” while the relay says “Same process.” The stored event describes when the provider changed. The relay describes what this viewer reattached to. The branch leaves provider changes in lf session history <session> and uses the pane’s connection bar for interruptions and ended viewers.

Open the Task, lose the connection, rejoin

  1. 1. Resume the saved thread

    Last terminal line

    Desktop asks the Session resume API to prepare the existing Session. Before the terminal mounts, the placeholder can show saved output under a quiet spinner. VoiceOver labels it “Opening session.” After mount, the terminal draws in place while the relay waits for native readiness.

  2. 2. Continue typing

    Claude · Available
    The tests are ready.

    Connection and native readiness enable input. Ghostty restores requested focus when the pane still owns it. The terminal keeps its geometry throughout opening.

  3. 3. The bridge stops answering

    Reconnecting… Input paused; last screen may be stale.

    The pane keeps its last screen and pauses input. The relay can reattach to the held terminal with the provider’s draft and buffered output. Keys pressed during the interruption are discarded.

  4. 4. Retry or refresh if it stays paused

    Session unavailable. Last screen is stale. Loopflow server is not running.Retry connection

    Retry connection starts another attempt through a reachable relay. A long reason truncates beside the button and remains available in its tooltip. If the status channel is gone, Refresh session in the strip opens a replacement viewer for the same Session. A retired or replaced terminal reports why the viewer ended.

A saved screen and an “Available” program report can both precede readiness. The mounted terminal can also appear before its first live frame. Connection and native readiness still gate input in all three cases. If the provider transcript is missing, resume can seed a new thread from the request and retain earlier history. A late status disconnect after an orderly close preserves the ended reason.

What happened in use

Dev QA opened a fresh Task, resumed it after the provider exited, and sent input after readiness. History showed the start and resume while the pane kept its terminal area. During a server outage, the full relay reason pushed Retry out of view. The rebuilt pane kept Retry visible and became usable again after the server restarted. The run could not distinguish a click from relay recovery.

Fourteen focused headless tests passed during review. They cover the spinner and its accessibility label, history payload compatibility, input readiness, status loss, Retry delivery, ended reasons, and recovery bar layout. Foreground focus restoration, Refresh in a live pane, and a forked pane were outside the Dev QA run. Gate checks remain in the plan.

Dev QA also observed a stale rendered frame while the window was in the background. Diagnosing that behavior would require a separate Ghostty repaint reproduction across foreground and background windows after reattachment.

Review questions

    1. Built. A spinner over any saved screen before the terminal mounts. The terminal then draws in place while input waits for readiness.
