Biggest mismatch: when Git publishes

Before (existing)

PlanningSync (any non-Linear repo)
 ├─ every 5 s: acquire        → git fetch
 └─ every 1 s: publish        → git fetch, export, maybe push
save → after reply: publish   → git fetch, export, maybe push

About 4,300 fetches an hour from the 1 s loop alone, whether or not anything changed.

Plan as written (slice 2)

every 1 s: if planning revision moved
           or publication pending/unconfirmed:
             publish

planning is one revision for the whole store. Any Linear save, import or tracker acceptance in another repository moves it. On this Machine loopflow is busy all day, so etude's Session still fetches about once a second.

Proposed. Git's own outbox gates publication, and one loop owns retry: 
PlanningSync (only when config is Git; decided once at start)
 └─ every 5 s: if destination has an unrouted owned change
               or publication_state ≠ confirmed:
                 publish      (acquires first, as today)
               else:
                 acquire
save → after reply: publish   (unchanged: the normal path)
That's one loop instead of two, at most one fetch per 5 s per Session, and no global cursor. Saves still go out as soon as the command has answered. A failed one waits at most 5 s instead of 1 s. The check is an EXISTS over unrouted_changes's join; slice 2 runs EXPLAIN QUERY PLAN on it against a 10k-Task store.

Counterexamples tried

  1. A busy Linear repository beside an idle Git one. This breaks slice 2 as written (above). The proposal holds because the gate belongs to the destination.
  2. Git → Linear → Git (manabot's history). The plan keeps a switched repository's journal and seeds when bind first records git, before acquiring. The kept observed heads match what was last exchanged, so the seed's captures name them as parents and the Linear-era values win causally. That's correct. If the journal were pruned (an option in questions.md), the seed would either race the remote's old heads, giving a lost line on every field, or, if seeded after import, have the remote's stale values silently overwrite Linear's. Pruning switched repositories' journals is unsafe while they could switch back. The question is updated to say so.
  3. Slice 3's "or to no record". Journal rows whose record left the live tables are kept on purpose: the routes table comment says routing belongs to "records removed from the live Work tables". A routed orphan is history a peer holds. Only unrouted orphans are safe to delete: nobody else has them, and export never reaches them again.
  4. Tracker recording on every drain. The drain runs on every save and tick. An unconditional UPDATE would add a write under the shared lock each time. It writes only when the value differs (WHERE planning_tracker IS NOT ?), and bind does the same.
  5. Git repository right after upgrade. planning_tracker is NULL, so saves aren't journaled. The first exchange records git and seeds, and capture's idempotence picks the saves up. One risk: those saves carry the seed's clock, not the save's. Only etude is affected, once.

The name

The Task promises "one queue". The plan decides that Git stays a replica, and a person still sees one status view (lf repo plan). The concepts agree. The title describes LOO-925's half. The PR title should say what this half does: journal only Git repositories, and publish only when there's something to publish.

Questions

  1. Publication gate
    1. Git's own outbox plus one 5 s loop (chosen here, written into the plan)
    2. the global planning revision, 1 s loop (plan as written)
    3. keep the 1 s loop, gated by the outbox
  2. A failed Git publication retries within
    1. 5 s (chosen)
    2. 1 s
  3. Switched repositories' journals (manabot 13k, kata, etude-studio)
    1. keep, so a switch back stays correct (chosen)
    2. prune, and accept lost lines or silent overwrite on a switch back
  4. Orphaned journal rows in the cleanup migration
    1. delete only unrouted orphans (chosen)
    2. delete all orphans
    3. delete none
  5. PlanningSync for a non-Git repository
    1. don't start it; config is read once at start (chosen)
    2. start it and read config every tick (today)
