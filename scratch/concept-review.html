One Wave, one Project: does the finished branch say so everywhere?

LOO-995 · Concept review after slices 8–10 · 23 November 2026 · Branch 9b630876ad against 250e266b4a

Area taken: the whole Wave–Project model as it stands with every slice in it, from lf wave create through Task create and move, tracker connect, upgrade of a released store, sync, rename and removal. The last three slices touched upgrade, sync and the index, so those get the closest walk.

Walk: a Wave from creation to removal, with an outage in the middle

lf wave create billing                  # Project billing (local), id = Wave UUID
lf task create --wave billing 'refund'  # Task in billing's Project
# Linear down
lf wave plan connect billing            # create queued; receipt says: lf wave sync billing
lf wave sync billing                    # slice 9: drains this Wave first, shows the queued create and its error
# Linear back
lf wave sync billing                    # Project created with the Wave's UUID; refund follows into it
lf wave rename billing payments         # Project name follows; linked → project_name field action
lf wave remove payments                 # queued actions retire; completed Tasks stay readable

Every step names one Project, and every action has one owner. Upgrade adds one wrinkle: a released store can hold several chapter Projects per Wave. The migration keeps one, translates queued destinations onto it (slice 8), and reads pick the Wave's own record when a released writer adds another (slice 10, held_wave_project_in).

Biggest mismatch, and it is larger than this Task. The model says a Wave's Project is one record whoever holds it, keyed by a UUID every Machine agrees on. The tracker queue still says a Project is created by the Machine that made it. Before this branch that was true by construction; the upgrade's "keep one" makes a Machine depend on another Machine's create, which in a tracker-only repository it never hears about except through an inventory of a link it doesn't have.

Released lf has the same gap for Tasks put in another Machine's Project; the migration widens it to Tasks it moved there. QA run 8 found it on a constructed two-Machine store, not the real one.

Existing

  unless plan_stamps(p, project_wave)
         from another Machine

Asana creates have no client identity, so two Machines sending would make two Asana projects. The stamp rule prevents that.

What it would take proposed, not here

uncreated: any unbound Project of a live Wave
create carries the Project's UUID
duplicate-id reply → look up by UUID, bind

Linear accepts a client id, so a second Machine's create meets the first one's Project. That needs a duplicate-id reply handled as a lost-reply lookup, and Asana needs its footer identity searched before creating. A drain change with its own tests; it belongs beside the queued-create snapshot question.

Recommendation

Nothing in the concept needs to change before gate. The branch's model and the code agree in every place a person meets it; the one disagreement is in multi-Machine tracker delivery and predates the branch. Advance to gate, with the gap written in the PR body and scratch/questions.md.
