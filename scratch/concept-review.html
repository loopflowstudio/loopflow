Biggest mismatch: a breakpoint has no single owner across status, actions, and blocked runs

When a Task parks at a breakpoint, the product has one fact: this Task is waiting for you at breakpoint X (either ready to continue on the worker’s default, or blocked until you choose). The code at HEAD splits that fact across three disconnected owners that contradict each other at after-ship-review, at after-verify, and whenever a worker returns blocked under auto: on.

The other three splits to close in Pass 5

Navigation

Start from real steps, decide any loop breakpoint

Populate Desktop’s Start from… menu with start plus real top-level work steps (explore, plan, build, ship-review, deliver, verify), not synthetic after-* stop markers. In Rust, base loop-decision eligibility on return_target(body, leaf.index).is_some() instead of verdict.is_some() so CLI --from after-ship-review + --decision iterate works. Replace leftover “Auto stands in next at …” with “Auto continues through …”.

Reply scope

Separate one-step handoff from loop iteration

Keep progress.direction strictly for loop iteration (set by finish_step on Iterate, cleared on Advance). Give a non-loop or advance breakpoint reply its own single-step handoff (consumed once by the next step and cleared when that step finishes, surviving crash/retry without leaking into downstream steps) and record the durable Task comment without double-steering the same worker.

Waits

Don’t confuse “PR open” with “stopped for review”

Add --until breakpoint (or stopped: returns when parked at a breakpoint, stopped/blocked without a live run, or terminal) for task-session and operators waiting on the next review, while keeping --until submitted honest for PR submission (or gating its PR check when a Graph is still running toward a breakpoint). Pass 2 of build with an already-open PR will actually wait for ship-review’s breakpoint.

Outside LOO-1096 (left separate on purpose)

  • Claude Esc during a tool call fires no Stop hook — affects every idle wake across Loopflow; predates breakpoints. Requires hook/activity fallback outside this Task.
  • Provider limit retry keeps the agent captured at step start — changing skills.*.agent during a rate-limit wait still requires interrupt + fresh run; belongs to limit recovery, not breakpoints.
  • Builtin build.yaml names qa bare — a repository Graph named qa shadows the builtin qa skill (unlike research.yaml/feature.yaml which now use step:). Separate builtin-Graph hardening.
  • Running-step status prints a process UUID — Step d148293b-… is running explore in task_execution.rs; cosmetic execution status cleanup outside breakpoints.
  • Antigravity immediate idle wake (LOO-1098) and retiring released interactive: YAML/capture compatibility readers (LOO-1100) — already tracked as separate Tasks.

Choices made for Pass 5 review & open product questions

Nothing below is irreversible once shipped, so Pass 5 builds the bold choices directly for you to review in the running app and CLI. Reply with numbers (e.g. 1b 2a 3a) to change any of them.

  1. When a worker blocks at a breakpoint, what should Desktop’s main button do?

    1a · Chosen for Pass 5. Don’t show a plain Continue button — show the blocker reason and let you answer in the Task conversation, because continuing without choosing a direction always fails.

    1b. Keep the Continue button visible and focus the Task conversation input when clicked, instead of sending a run request.

  2. What should Desktop’s “Start from…” menu list?

    2a · Chosen for Pass 5. List real work stages (start, explore, plan, build, ship-review, deliver, verify) so picking ship-review actually runs a fresh review and stops with its results.

    2b. Keep listing the stop markers (after-explore, after-ship-review, after-verify) and make picking one start at the step immediately after that marker.

  3. How should the workflow bar show breakpoints?

    3a · Kept as built for now. Show each breakpoint as its own marked item beside its step (explore · 👤 after-explore · plan · …), matching lf graph show.

    3b. Fold the person badge onto the step before the breakpoint (explore 👤 · plan · build · ship-review 👤 · deliver · verify 👤) so the bar stays short enough to fit without collapsing to text-only on narrower windows.

  4. When “Sort by status” is off in Desktop’s sidebar, where should a Task at a breakpoint sit?

    4a · Kept as built (still open from Pass 4). Keep your manual drag order intact in the sidebar; surface breakpoints first in Now and when Sort by status is turned on.

    4b. Temporarily float Tasks waiting at a breakpoint to the top of the sidebar even when Sort by status is off.
