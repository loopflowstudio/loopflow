Showing an agent a change

Concept review for Task d92894 with the whole change built and run twice, 2026-11-18, against base 3496a8761d at 64d09064af. Anything on a gold edge is proposed; everything else is in the branch. It replaces the page written at 9f5f1fd770, whose proposal (the section in the first turn) is now built.

The area taken. Every place lf puts a change in front of an agent: the commit writer, the PR writer, --diff patch / context: {diff: true}, --diff files, and the Task workspace block. The Task names the two writers; the branch moved the third onto the same type, so the review covers what that type promises and whether each promise holds.

One interaction, walked

lf pr submit on a branch that moves a module

The branch renames old_name.txt (300 lines) to new_name.txt, edits one line of it, and regenerates a 400 KB fixture. The patch is over 15,000 tokens, so the writer gets the list and the command:

Changed since origin/main, 2 files. Read one file's patch with:
  git diff origin/main...HEAD -- '<path>'

  +6000  -0   aaa_generated.txt
     +1  -0   new_name.txt (from old_name.txt)

The list is right: one line changed.

What the command returns

$ git diff --cached -- 'new_name.txt'
diff --git a/new_name.txt b/new_name.txt
new file mode 100644
--- /dev/null
+++ b/new_name.txt
@@ -0,0 +1,301 @@

Failure, run here in a throwaway repository: Git pairs a rename only when both paths are in the pathspec. With one, the writer is handed 301 added lines for a file the list says changed by one. It reads the whole file to find nothing, or describes an addition.

Recovery: the writer has to know to add the old path. git diff --cached --stat -- new_name.txt old_name.txt gives 1 insertion(+).

Renames are what large branches are made of, and large branches are the only ones that take the reading path. The smaller cases (354 KB, 801 files, 3,001 files, Codex, step commits, a path with a space and an apostrophe) all read the right file in qa; none of them held a rename.

The biggest mismatch

The design rests on one sentence: the writer is given every file and a way to read any one. For a rename the way is wrong, and it is wrong in the direction that costs most, a whole file where the list promised a line.

Before (in the branch)

Changed since origin/main, 2 files. Read one
file's patch with:
  git diff origin/main...HEAD -- '<path>'

  +6000  -0   aaa_generated.txt
     +1  -0   new_name.txt (from old_name.txt)

After (proposed)

Changed since origin/main, 2 files. Read one
file's patch with:
  git diff origin/main...HEAD -- '<path>'
A renamed file needs both paths:
  git diff origin/main...HEAD -- '<path>' '<old path>'

  +6000  -0   aaa_generated.txt
     +1  -0   new_name.txt (from old_name.txt)
  • The two extra lines appear only when the change holds a rename, so every section qa read stays byte for byte what it was.
  • Nothing in Change changes shape: renamed_from is already there.
  • The inlined patch is unaffected; Git pairs renames across the whole range.
  • Passed over: dropping rename detection (--no-renames) so list and command agree. The list would then show a moved 3,000-line file as +3000 and -3000, which hides the one-line edit the writer should describe.

Tested against three paths

PathWhat happens
NormalA branch that moves a directory and edits two files in it: the writer reads each with both paths and gets the edit.
FailureThe writer ignores the second line and passes one path. It gets the whole file, as today; the list still says +1 -0 … (from …).
RecoveryNone stored; the next read with both paths is right.
Counterexample keptA pure rename with no edit (+0 -0): both paths return a header and no hunks, which is the truth.
Counterexample keptA copy (-C) is not detected by default, so no line carries a source that is not a rename.

Larger than this work

  • --diff files is a weaker copy of the same list. It reads every changed file's contents and delivers their paths in a listed file, which qa showed agents do not open. --diff both now gives the paths twice. Removing it means dropping the diff_files setting, DocumentSource::Diff, the gather pass and the changes branch in ContextDelivery::prepare; .lf/config.yaml is read by the released lf too, so the key stays readable for a release.
  • The Task workspace block is a second "change as shown to an agent". It would take a fourth ChangeRange (base against worktree, untracked included) and a per-file state. Until then a worker with diff: true is shown a change twice, each up to 15,000 tokens of patch.
  • gather_branch_change treats only a branch named main as the default branch, two lines before asking Git which branch is. Unchanged by this branch.
  • --diff patch on a branch with commits shows committed work only. Documented. The fourth range would close it.
  • lf task diff's 1 MB whole-comparison cap: a person-facing read; its fix is a per-file read in the served API.

Questions

  1. The read command for a renamed file.
    1. A second command line with both paths, shown only when the change holds a rename. Chosen for review.
    2. Leave it; the list's (from old) is enough for a writer to work it out.
    3. List and read without rename detection, so one path always works and a move shows as a delete and an add.
  2. The list has no ceiling: 237 KB at 3,001 files.
    1. Leave it complete, as asked. Chosen.
    2. Collapse a directory of several hundred files to one line with a count.
  3. The PR writer follows yolo; the commit writer always skips permission prompts.
    1. Leave both. Chosen.
    2. Give the PR writer the same floor.
  4. docs/config.md used to say "Point to Git inspection commands rather than inlining a frozen patch". Did that sentence mean:
    1. never put patch text in a Skill's prompt, in which case the block should carry only the list and the command;
    2. don't rely on it staying current, which the read command covers. Assumed.
  5. --diff files.
    1. Its own Task: remove it, --diff becomes on or off. Recommended, not filed.
    2. Keep it as the cheap path-only option.
  6. Untracked files in an uncommitted change are listed with "no patch: read the file".
    1. Keep. Chosen.
    2. Inline small ones as added-file patches.
