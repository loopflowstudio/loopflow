Keep the same Session across a lost connection.

No further design decision is needed for the accepted local slice. Jack Heart's continuity requirement now maps to the recovery implementation. The remaining obligation is acceptance proof, not another execution owner.

Headless review of the implemented change. No new product approval, publication or Auto-Ship approval. Native presentation remains for demo.

Actions → concepts → APIs

Open a Task → recorded primary Session → read(view_plan).

Edit its Session → existing execution owner → session_owner(session), then attach(owner).

Reconnect after interruption → that same owner → fresh terminal attachment or byte-stream Resume, without replacing control.

The Machine service carries Work readings, complete CLI commands and owner traffic. The owner keeps the provider, draft and claims; the Graph keeps execution. Desktop keeps its renderer and app-owned UI automation. No service-side Session registry, scheduler or retention policy is introduced.

The consequential mismatch is repaired

Before: bridge EOF ended the relay and could send Desktop through ordinary Session preparation. The original restart fixture removed its viewer before interruption, proving owner survival without proving viewer recovery.

A failed connection does not establish that the provider ended.

Implemented now: the relay stays alive. It retains the exact owner and output continuation state in memory. The terminal shows:

Machine connection lost.

Ctrl+R to reconnect; Ctrl+] to close. Typing while disconnected is discarded.

After reconnect: the same Session, or a passive view if input remains elsewhere.

A terminal gets a fresh screen because the disconnect prompt changed its display. A byte stream resumes retained output; an expired spool falls back to a fresh attachment. Current claims override replayed notices. An unavailable exact owner ends this recovery path without provider resume.

Work subscriptions separately reopen with complete current readings. If a rename reply is lost, inspect the current name before deciding on another command. Request IDs correlate attempts; they do not promise deduplication.

What would invalidate this design?

  • Reconnect takes input or geometry from a newer viewer. The current recovery requests free claims and becomes passive when input is held.
  • Outage typing reaches the provider, or an ended owner launches again. The current relay discards outage input and refuses replacement-provider recovery.
  • Installing a replacement helper kills the live owner or Graph. Separate registrar and supervisor-restart fixtures do not settle this; composed replacement must prove it.
  • Reconnect creates provider usage again. Existing ownership is preserved in code; unchanged usage totals still require acceptance evidence.

Remaining proof, within the accepted contract

Gate retains installed executable replacement with active Work, bounded-client and cancellation acceptance, command attribution/default equivalence and usage accounting. Demo retains Desktop quit/reopen, disabled-service presentation and the rendered editable draft. This review does not claim those checks passed.

Later proposals, not approved here: remote admission, unattended hosting and phone takeover gestures. They do not block reviewing this local slice. The existing service README already describes the implemented recovery interaction.

Questions for the scheduled proof

These are acceptance questions, not unanswered product choices or a request for input during this headless run.

  1. Does installed helper replacement preserve the exact live provider, owner, unfinished draft and Graph through reconnection?
  2. Does Desktop quit/reopen preserve usable Session access, with honest unavailable and disabled states and no replay of uncertain input?
  3. Do command defaults and attribution match CLI behavior, and do reconnects leave provider-usage totals unchanged?
