Do the recovery concepts line up?

LOO-959 as built, at 74e8218230 against origin/main. PR #1972. Read on 2026-11-18, after slice 7, its compress and its qa. This page changes no code. Blue marks what is proposed; everything else exists.

Area reviewed: work on this Machine that stops without anyone stopping it, and what a person is told about it. That is a Task's conversation, a Task's run, the server's recovery pass that brings both back, the counters behind the pass, and the two lines lf task status and Desktop print. The whole branch, seen new, since the earlier pages each covered one slice.

Result: nothing for this work to change before gate. The conversation side has one owner per idea. What is left is the run side, which says the same thing in a different shape, and four smaller duplications. Each is a wire or behavior choice.

One interaction, with its failure and recovery

The Mac restarts with four Tasks open. These are the lines as the code prints them:

LOO-a  conversation killed, restarted         Conversation: died 09:14 (no exit recorded) · starting again
                                              Conversation: running (started again 09:14, attempt 1)

       five times                             Conversation: died 09:40 (exit 1) · started 5 times; `lf resume --task LOO-b` opens it
LOO-c  claude not on the server's PATH        Conversation: could not start: claude is not installed on this Machine's PATH · tries again 09:15
LOO-d  `lf task run` died at implement        Run died at implement; the server's next pass carries it again

       quit by the person                     Conversation: quit 09:20; `lf resume --task LOO-d` opens it

Every row says what stopped and either that it is coming back or which command continues it. That is the outcome the Task set. Read the two halves side by side, though: the conversation "starts again 09:18", the run "is carried again in 2 min". One gives a clock time, the other a duration. One counts "attempt 1", the other "restart 4 of 5". One names "the server's next pass", a thing the person never otherwise meets.

The biggest mismatch: a died run and a died conversation answer the same question in two shapes

Now 
Session (conversation)
  outlook: {kind: coming_back,
            at: 09:18, reason, command}
  → "died 09:16 (exit 1) · starts again 09:18"
  no server → waiting_for_you + command

Task run
  state:  waiting | blocked
  reason: "Run died at implement; it is carried
           again in 2 min (restart 4 of 5)"
  no server → same sentence, still promising

The run's answer is prose inside a state documented for usage-limit waits. A client cannot tell "died, coming back at 09:18" from "waiting on a limit" without reading the sentence. With no server running, the conversation says so and the run does not.

Proposed 
Task run
  died:    {at_step: implement, at}
  outlook: {kind: coming_back | waiting_for_you,
            at, reason, command}     // same type
  → "Run died at implement · starts again 09:18"
  → "Run died 5 times at implement;
     `lf task run LOO-d` starts it again"

One type, one fold of "does this Machine bring it back" (claimed here, checked out here, a server runs, starts left), used for both. The run stops borrowing waiting. A person's lf task run counts from zero, as a person's resume does.

Normal path: a live run has no outlook. Failure: carrier killed → coming_back, at now. Recovery: carried again; a finished step clears the count. Give-up: waiting_for_you with lf task run. Counterexample kept: while ship has its own restart rule, a shipping Task would need a third reading of the same count, so this is cleanest after LOO-968 makes lf task run the only carrier. Before that it adds a type to an area about to shrink.

Cost: a wire field on the Task's run, its fixtures and Swift decoder, and the shared fold. It is larger than this work and belongs with or after LOO-968.

Smaller findings

  1. "Starting" has no value. A prepared conversation that the server is about to start, and one whose start is in flight, read unknown. The pass already knows both (ConversationToStart.agent is none; a counted start newer than the end). The fold could give them an outlook.
  2. ended.by repeats outlook.kind. ended could be {at, exit_code}.
  3. Two printers. The server could send the sentence, or one fixture of expected lines could hold both printers to it.
  4. One rule, two writers for "the server starts it". A test over the recovery fixtures that the outlook says coming_back exactly when the pass lists the conversation would hold them together without restructuring either.
  5. "The server's next pass" in the run's line. "Run died at implement · starting again" says it in the conversation's words.
  6. "started again … attempt 3" on a conversation whose first two starts failed and which never ran before. It was started, not started again.

Larger than this work

  • Ship's separate restart rule (LOO-968). Until then task_graphs.restarts means two things.
  • Retention of logs, capture folders and Session rows; fixture servers and holders left running. Both are in scratch/questions.md, unfiled.
  • Two checks only a person can run: real Claude's exit code on SIGTERM, and a real reboot with three Tasks.

Questions

  1. The run's "is it coming back":
    1. Give the Task run the conversation's outlook type, with or after LOO-968.
    2. Now, reword the three sentences only (clock time, "starting again", no "pass"); keep them as prose in the run's state.
    3. Leave as built.
  2. A person's lf task run after "died 5 times":
    1. Counts from zero, like a person's resume of a conversation.
    2. Leave: only a finished step resets the count.
  3. Conversation: unknown before the first start and while one is in flight:
    1. The outlook covers it; the line reads "starting".
    2. Leave: it lasts about a second.
  4. ended.by:
    1. Drop it; outlook.kind says quit.
    2. Keep it as the fact beside the exit code.
  5. The conversation sentence:
    1. The server sends it; the CLI and Desktop print it.
    2. Keep two printers, held to one fixture of expected lines.
    3. Leave as built.
  6. "The server starts it", written in the pass and in the fold:
    1. One predicate both call.
    2. A test that they agree on the recovery fixtures.
    3. Leave as built.
