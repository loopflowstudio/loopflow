The biggest mismatch: the next move has three owners

A person, or a conducting agent reading --json, asks one question of a row: what now? Three functions answer it from overlapping facts. next_command reads run_control, which does not know the Graph is at end, so it offers a command that refuses. Slices 4 and 7 gave the finished standing one definition that all three read; every other standing still has three.

Built (and on main for a held Task)

$ lf task status e56b42      # at end, PR open
  action: run (PR is published but settlement
    is not armed; run `lf land`)
$ lf task status e56b42 --json | jq .task
  reason: "…not armed with `lf pr land -c`"
  next:   "lf task run e56b42"
$ lf task run e56b42
Error: Task e56b42 is at the end of graph qa-end

After proposed

$ lf task status e56b42
  action: land (PR is open; `lf land e56b42`)
$ lf task status e56b42 --json | jq .task
  reason: "PR is open; `lf land e56b42`"
  next:   "lf land e56b42"

One function from a Task's facts to (reason, command). The text line, NextMove and TaskRow.next print it. Finished becomes one arm of it.

Why it is not slice 8. This work reaches the standing only through a Graph with no merge step; the builtin Graphs land before end. The same three lines print on main for a held Task. The one-line patch (no lf task run at end) leaves three owners in place, and the real change rewrites next_move_for_task, phase_action and next_command for every standing, with the Desktop reading NextMove.
