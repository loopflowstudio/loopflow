When does a Task take up its workflow?

In New Task on Mac, Start should use the workflow you chose. File to backlog should save your request and leave the workflow choice until first start.

The Task brief reads “ui polish dumping ground.” This review takes the New Task sheet through the backlog, first run, and recovery because the workflow preview exposes a difference between what the sheet offers and what the Machine saves.

Do the concepts line up?

File a request
No NewTaskSheet.file() passes its Start choice through WorkModel.fileTask. The served task.create validates that name even when run is false. The filing operation has no Graph field. An input can stop an action that gains nothing from the input. WorkModel · Task operations
Follow a default or pick a name
No The draft stores an optional name, but the sheet names its source by comparing the displayed name to the reported default. After a Wave change, an explicit sketch can look inherited if that Wave defaults to sketch. NewTaskWorkflow
See where you take part
Yes Rust sends the catalog’s WorkflowOutline. New Task and the unstarted Task draw its steps and participation sentence. Once the Task takes up a Graph, its workflow bar shows the captured Graph and position. Workflow and position types · Task workspace
Start work
Yes New Task uses task.create with run: true. Admission records the selected Graph and primary Session with the Task. Starting a filed Task uses task.run. The first run takes up a Graph, and subsequent runs use its recorded position. Graph outcomes and authority
Recover a submitted request
Yes A creation receipt identifies the submitted action on its Machine. An unread answer can be reconciled with the original request identity and payload. After admission, setup can continue in the Task’s conversation. Creation receipts · Desktop recovery

Let the choice live in the draft until Start

The picker offers Use default and named workflows. The draft’s optional name expresses the choice. When the scope changes, the default can change and an explicit choice stays selected. The Machine supplies the outline and resolves the current default at admission or first run.

File sends run: false and graph: null. Start sends run: true with the name or null for the default. The filed Task keeps its brief and scope. The started Task keeps its captured Graph and position in task_graphs. Creation recovery keeps its submitted payload and identity. This takes the graph argument out of the Mac filing method and gives the choice a single place to take effect.

Try the lifecycle

File today, start tomorrow

File with sketch showing. Open the selected backlog row. If Product has since switched to code, Start offers code. Start with… still allows any available named workflow.

A definition disappears

Remove the sketch definition after opening the sheet. File can still save the brief. Starting with that name still surfaces the Machine’s error. A refused File keeps the draft for correction.

The answer gets lost

Drop the response after the Machine saves the Task. Recovery reads its original receipt and presents the same Task. If Start committed before setup failed, opening that Task recovers its conversation and captured Graph.

Counterexample checked against the design. Moving from Product to a Wave whose default is sketch keeps an explicit sketch choice, even if that Wave later changes its default. Choosing Use default resumes following the Wave.

Questions for review

  1. When should a named workflow take effect?

    1a On Start, as shown here. 1b Save a workflow preference when filing, so it follows the Task when it moves.

  2. What should happen when you change scope in the draft?

    2a Keep an explicit choice until you choose Use default, as shown here. 2b Switch to the new scope’s default immediately.
