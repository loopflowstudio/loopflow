The one consequential mismatch

The design deletes lf wave ensure so that one command, add, is how a Wave comes to exist: files on the main checkout, a first Project, one commit of exactly those paths. The dispatcher for connect still says otherwise, in its own words:

// rust/loopflow/src/lf/commands/ops/mod.rs
// Wave connection is a creation graph: its positional name may select a
// wave not yet registered (it links a wave directory to
// Linear, not a registry row).

connect_async then calls ensure_wave_row(&store, repo, &wave) with the invoking checkout, which seeds .lf/wave/<name>/ there and registers the row. From a Task worktree:

$ lf wave connect ops            # ops does not exist yet
  creating Linear Initiative for wave/ops
  … commit "lf wave connect: ops to Linear" on the Task branch, `git add -A`

Desktop sidebar / lf wave list   # the store knows ops
ops                              # no chapter; its GOAL.md is on a branch main never sees

That is the stranded state the Problem section opens with (“A Task worktree run strands the files on that branch”), produced by the one Wave command the init and split-wave skills tell agents to run right after add. A redesign deletes what it replaces; this half is still standing.

Direction next implement

Now

connect <name>
  ensure_wave_row(repo_root)   # may create
  write Initiative id → repo_root
  commit_workflow { add: true } on repo_root
  refresh inventory

Proposed

connect <name>
  wave_lifecycle::add(name)    # idempotent; main, Project, commit
  write Initiative id → main checkout
  commit_authored(main, [.lf/wave/<name>, .lf/config.yaml])
  refresh inventory
  • Connect never mints a Wave. An explicit unregistered name adds first, because add is idempotent and the Flexibility rule prefers adapting to refusing.
  • Connect's own writes (config.yaml Initiative id, .lf/config.yaml team) and their commit land on the main checkout through the lifecycle's selective commit, not the invoking checkout's whole dirty tree.
  • reteam's ensure_wave_row loop registers existing authored directories through register_authored; refresh_inventory reads its connected Wave with get_wave_at. The “creation graph” comment goes.
  • Proof: a wave_lifecycle test runs lf wave connect ops from a Task worktree with the fake gh and finds .lf/wave/ops/ committed on main with a first Project, listed the same by lf wave list and Desktop's read.

Two smaller consequences, same pass

  • Add's leftovers reach the CLI only. render_added prints .lf/wave/<name> is uncommitted on <main>: <reason>; Desktop decodes WaveIdentity { id } and closes the popover. Rename and Remove keep their sheets open on the same kind of line. WaveAdded gets a summary (fixture wave_added.json, Swift mirror replacing WaveIdentity); the New Wave popover and CreateWaveSheet stay open with it and a Done button.
  • The Remove preview does not name uncommitted edits. remove_authored deletes the directory with remove_dir_all, and the preview says “Git history keeps it”, which is false for edits nobody committed. Jack's main checkout has none today. One sentence in the preview, from git status --porcelain -- .lf/wave/<name>; still no refusal.

Counterexamples checked

  • Normal path: add → use → remove on lf-world wave-lifecycle; the five demo steps hold (wave_lifecycle, 6 tests; CLI steps 4–5 ran).
  • Failure: a Task move fails mid-removal → “2 of 3 open Tasks moved or deleted; LOO-12 could not: … run lf wave remove desktop again”; nothing retired. Desktop shows the error with Retry; the retry resumes from the first unmoved Task.
  • Recovery: a Linear archive failure leaves the Wave retired, the files kept (the Initiative id lives there), and the receipt's leftover line; a second run archives only.
  • Connect from a worktree for a Wave that does exist: unchanged by the direction; only the unregistered name changes path.

Looked at, holding

  • lf wave rename <wave> --repo <path> moves a Wave between repositories under the rename verb, files not following (the receipt says so). Pre-existing relocation surface the design kept; no accepted decision speaks to it, and it is not this Task's to settle. Noted in scratch/questions.md.
  • lf task create --wave <new> adds the Wave (it called project::ensure before this branch), so a mistyped name lands a committed .lf/wave/<typo>/ on main. lf wave remove <typo> is the cleanup the design names for strays.
  • Desktop's Remove sheet exposes no --delete-backlog; unstarted Tasks move and the preview says so.
  • The help text reads as the design intends: add, remove and rename each say what happens to files on main and to Tasks; list says removed Waves stay readable by show.
