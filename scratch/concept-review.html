Installed skills: do the concepts line up?

Area taken: everything behind lf self sync-skills — which Loopflow skills and Graphs show up in each harness's own skill list, where they are written, and what a harness declares about itself. Taken this wide because the plan adds a per-harness declaration, and the declaration's shape decides what a "skill directory" is everywhere else. Reviewed before any code: the plan in scratch/plan.md against the code on this branch.

The biggest mismatch: a folder was given a dialect

The plan's table labels ~/.gemini/config/skills, pi's folder and opencode's folder "Codex". None of them is Codex. The label exists to carry one bit: whether a Graph recipe gets disable-model-invocation: true. And that bit is wrong where it is off. pi's own docs (docs/skills.md:53): "Set disable-model-invocation: true in frontmatter when a skill should be available only through its explicit command." pi reads ~/.agents/skills, where the line is left out, so pi may start the code Graph on its own and Claude may not.

On this Machine: 13 Graph exports in ~/.agents/skills, none carrying the key.

Kept as the plan had it

A generated tree at ~/.gemini/config/skills/ instead of a skills.json entry: agy's docs rank global discovery above builtins and global declared configs below them, and the tree needs no write into a provider's config file. Writing the tree whether or not agy is installed, as the other two are. No "has none, because…" variant. Slice 1 first: it is the one that runs the real binary against ~95 real exports.

Outside this work

Reading hand-written skills from ~/.gemini/config/skills or ~/.pi/agent/skills as Loopflow sources. It would make the catalog's source list and this declaration one list; it takes a dialect for each new folder and a decision on which wins a shared name. Native invocation for agy, pi and opencode, as above.
