One Project per Wave

LOO-995 concept review, 2026-11-22, after “wave is at most 1 project for now”. PR #1997 at 765e0e2df0, read against main, with LOO-996’s plan (../loopflow.subwaves2/scratch/plan.md, said.md) and LOO-980’s brief beside it.

Area taken: what ties a Wave to a tracker Project, from lf wave plan connect through a Task’s filing, a move, a Project ending, and import back from Linear. This is the Task’s title (“a Project is a Wave’s optional tracker link”). The climb rule and tasks.wave_id are already built on the branch. With one Project per Wave, the rest of the area has to change around them.

Where the three plans already stand

  • LOO-980, decided: “A Wave links to a Project on both trackers.” “Teams and Initiatives matter only at creation. A repository names one default Team (optionally an Initiative), used to create a new Wave’s Project”.
  • LOO-996’s plan, 2026-11-22: “connections: at most one tracker item”. It deletes “Project as a stored level between them (tracker_wave_projects, a Wave’s Project list)” and “Team and initiative links”. Locked item 17a: “For now a Wave is not connected to a Linear team or initiative. The tracker connections are a Project and an issue.”
  • This branch: a Wave holds any number of Projects. They reach it through a linked Linear Initiative. A new Task picks “the newest started Project” and prints which one it chose.

“At most 1 project” agrees with the first two and contradicts the third. That contradiction is not in the climb rule. It is in how a Wave gets its Projects at all.

One interaction, as built

A Linear repository. The person connects billing. Linear has three Projects in the Initiative named billing.

$ lf wave plan connect billing                 # links an Initiative
$ lf wave status billing                       # Invoicing (started) · Dunning (started) · Tax (planned)
$ lf task create --wave billing --title "Meter usage events"
Meter usage events · LOO-12 in Project Invoicing   # newest started, by created_at
$ lf task create --wave billing/refunds --title "Refund a mischarged invoice"
Refund a mischarged invoice · LOO-14              # climbs: billing's newest started Project

Failure: a teammate moves Dunning to another Initiative in Linear. Loopflow holds the move “until moved back, because the Initiative determines which Wave owns it” (docs/work.md). Recovery: someone moves it back in Linear. A person who never thinks about Initiatives has to learn about one here.

The same interaction, proposed proposed

$ lf wave plan connect billing linear:project/invoicing    # this Wave's one Project
$ lf task create --wave billing/refunds --title "Refund a mischarged invoice"
Refund a mischarged invoice · LOO-14 in Project Invoicing   # billing/refunds has none; billing's
$ lf wave status billing/refunds
Project: none (Tasks go to billing's Invoicing)

Failure: Invoicing completes in Linear. billing keeps it, shown as ended. New Tasks climb past it to the parent Wave’s Project, else to none. Recovery: lf wave plan connect billing linear:project/invoicing-v2 replaces the link. Invoicing stays a record with its Tasks, which still list under their own Waves. Moving a Project between Initiatives in Linear changes nothing here.

The biggest mismatch: the branch rewrote how a Task reaches a Project, but a Wave still gets its Projects from an Initiative. With one Project per Wave, the Initiative is the wrong thing to link. It is also what makes the Wave hold several, so the “newest started” choice and its message cannot be deleted while it decides.

Recommendation: make the link a Project in this Task. lf wave plan connect <wave> <project> sets projects.wave_id, unique per Wave. Import attributes an issue’s Wave through that link. The Initiative and Team are used only when connect makes a new Project, as LOO-980 decides. Delete tracker_wave_projects (mark it leaving), the tie-break, the chosen-Project message, the Initiative hold on moves, and task_move_project’s separate rule.

Before (branch)

  • Wave ⟵ Initiative ⟶ N Projects, ordered by position
  • New Task: climb, newest started, print the choice
  • Move: keep if below the Project’s Wave
  • Project moved between Initiatives: held
  • No tracker: no way to get a Project

After proposed

  • Wave ⟶ 0 or 1 Project (projects.wave_id unique)
  • New Task, and a moved one: the nearest open Project up the tree, else none
  • Ended Project: kept on the Wave and skipped
  • Initiatives: only for making a Project
  • No tracker: no Projects; Waves and tasks.wave_id carry it

Counterexamples tried

  • An issue moved in Linear to a Project linked to another Wave. The Task follows to that Wave, using the planning writer’s existing “not already within” rule. It holds.
  • An issue moved to a Project linked to no Wave. The Task keeps its Wave, and its project_id is the tracker’s. Loopflow does not move it back. It holds, but only if the writer sends a Project change on a Loopflow move and never on reconciliation.
  • Drop tasks.project_id and derive it from the climb. Passed over: an ended Project could no longer list its own Tasks, and an issue in an unlinked Project would read as being in the climb’s Project.
  • The real store. coverage holds 8 Projects (8 open), infrastructure 7 (4 open), product 6 (3 open), academy 6, experiments 5. Most are chapter leftovers (“Game — Chapter 20260924…”). 1,071 of 1,548 Tasks have a Project. The migration must pick one per Wave, and that choice is hard to take back once other Machines have it (question 2).

Outside this Task

LOO-980 keeps the rest: removing Team claims, ingesting whole Teams, and validate_project_ownership. It also keeps “your slice” and the two orders. Its line “Wave membership is derived from the link, not stored” changes to “a Task records its Wave; the link decides its Project”. LOO-996’s later slices replace Wave and Task with one kind. Nothing here blocks that: the link becomes that kind’s single tracker connection.

Questions

  1. Where the Project link replaces the Initiative link:
    1. in LOO-995 (recommended): connect takes a Project, and the tie-break, message and tracker_wave_projects go. This means another implement round on #1997.
    2. LOO-995 lands as built, with several Projects per Wave, and one per Wave becomes LOO-980’s first slice.
  2. Waves that hold several Projects today (8, 7, 6 above), once migrated:
    1. recommended: keep the one today’s rule picks (newest started open) and unlink the rest. Tasks keep their Wave and Project, and nothing is written to Linear.
    2. keep that one linked and mark the rest ended here, without writing that to Linear.
    3. turn each extra Project into a child Wave linked to it.
  3. When a Wave’s Project ends:
    1. recommended: the Wave keeps it, shown ended. New Tasks climb past it until another Project is connected.
    2. new Tasks still join the ended Project.
    3. an ended Project unlinks itself.
  4. Connecting a Project to a Wave that already has one:
    1. recommended: it replaces the link, and the old Project stays a record with its Tasks.
    2. it says which Project is linked and asks for --replace.
  5. Making a Project:
    1. recommended: lf wave plan connect billing --new makes a Linear Project in the repository’s default Team (and Initiative, if named). Without a tracker there are no Projects.
    2. connect only links existing Projects.
    3. trackerless repositories get local Projects too.
  6. Moving a Task:
    1. recommended: it takes the Project a new Task in that Wave would get.
    2. keep the branch’s rule: the Project stays while the new Wave is below it.

Question 2 is the one that is hard to undo once shipped. The others can change later.
