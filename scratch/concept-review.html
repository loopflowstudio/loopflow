Biggest mismatch: Git is a tracker in the tables and a "peer" in the code

Walk it. Someone on a Git tracker runs lf repo tracker, sees a destination with a fetch failure, and opens the code to find out why.

existing

$ lf repo tracker
Tracker: git. …
  origin  refs/lf/plan/main  fetch failed: …

store      git_tracker_destinations.fetch_error
record     PeerPlanningStatus.acquisition_error
module     sqlite/planning_peers.rs, peer_records.rs
call       planning_sync::peer_status(), acquire_repository()
wire       "acquisition_error": "…"
Desktop    PeerPlanningView, PeerPlanning.swift

Four words for one fact between the table and the screen: fetch, acquisition, peer, destination. The Task's own outcome line retires "acquisition".

proposed

store      git_tracker_destinations.fetch_error
record     GitDestination.fetch_error
           GitDestinationConflict
module     sqlite/git_tracker.rs, store/git_tracker.rs,
           git_tracker.rs (was peer_records.rs)
call       planning_sync::git_destinations(), fetch_repository()
wire       "fetch_error": "…"
Desktop    GitDestinationsView, GitDestination.swift

Two words, each meaning one thing: the Git tracker is the mechanism, a destination is one ref it exchanges with. The glossary gains a "destination" row.

Failure and recovery. A fetch fails: fetch_error is set and shown; the next sync clears it. Nothing about the behavior changes, only that the name in the error path is the name in the table. What must survive: a released lf still writes planning_destinations.acquisition_error; the mirror triggers already translate it, so the rename touches no SQL. Counterexample checked: the plan's Modules section named the Swift files TrackerSync*, but TrackerSync.swift already exists and holds actions. Git destinations are a different thing on screen and keep their own type.

Task JSON: one prefix

existing

"tracker_id": "…",
"tracker_state": {"state":"available","synced_at":…},
"pm_snapshot_synced_at": …,
"pm_writeback": "current"

  PM writeback: current

proposed

"tracker_id": "…",
"tracker_state": {"state":"available","synced_at":…},
"tracker_synced_at": …,
"tracker_writeback": "current"

  tracker writeback: current

Struct fields and JSON keys rename on Task and Project; the SQL column names stay. Swift decodes neither key. Passed over: a serde rename alone, which leaves the Rust field and the wire disagreeing.

Larger than this work

  • Two sync times on one Task. tracker_state.synced_at comes from the issue's last state; pm_snapshot_synced_at comes from the Task row. If they always agree, one of them is a field that could be nothing. Settling it means reading every writer of both; not done here.
  • LinearIssueId holds Asana gids, and LinearWritebackState describes any tracker. A neutral TrackerRecordId touches every planning signature; it is its own Task.
  • Git has no actions. The glossary says so ("Git exchanges the journal instead"), which means "action" and "lost" on lf repo tracker describe two of three trackers, and Git conflicts are a third thing. One model for "a change of mine that has not landed" across all three would be a design, not a rename.
  • Columns provider, planning_provider_revision, observed_at, pm_snapshot_synced_at on hot tables: each is a staged rebuild. LOO-960 could carry them with the contract migration.

What held

  • Mirror triggers: installed and candidate lf exchanged Task edits both ways through old and new table names.
  • tracker: folds to the released planning: layout; a different tracker name replaces the block.
  • lf help wave, lf help repo tracker read in the glossary's words on the candidate build.

Questions

    1. tracker_synced_at and tracker_writeback, as written into the plan;

    1. add the row, as written;
    2. keep it an unglossed CLI word.

    1. file a Task for a neutral type;
    2. leave it.
