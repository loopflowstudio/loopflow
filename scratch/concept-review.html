The short version

The plan's mechanism holds up: a GitHub App user token from a device approval, limited to one repository, with the renewing grant kept on the laptop. The two mechanisms it passed over fail for the reasons it gives. What does not line up is around the mechanism:

  • A person has to learn "GitHub App", "client id" and "grant", and run a command named for signing a Machine in that signs no Machine in.
  • "Signed in" stops meaning "works": the plan's own renew command would answer "already signed in" and send nothing.
  • The token is cut short on two of the three ways a rental ends.

A failure, and the recovery

Rental A (modal-1) is five hours old. A second Task of the same repository is placed on rental B, due in four hours. The stored token has three hours left, so the laptop renews it. GitHub kills the old token at that moment. The laptop sends the new one to B and re-sends to A, and the SSH to A drops.

The biggest mismatch: the person operates the mechanism

The Task's outcome is one sentence a person can hold: a rental reaches one repository and stops reaching it when the rental is over. The plan delivers the sentence and hands over the machinery with it.

Before plan

your GitHub App→ forward.github_app→ login github --rental→ grant per repository→ rental

Five nouns, three of them new to the person. Signed-in rows and the renew command compare names.

After proposed

your GitHub App forward.github_app approve once, at the first rental→ grant per repository→ rental

One Loopflow app whose client id ships in lf. The grant is still a row on the laptop; the person sees an approval and, later, an expiry time.

Recommended. Register one public "Loopflow" GitHub App and compile its client id in. A device-flow client id is public, the app needs no secret, no key, no webhook and no server, so nothing is run by Loopflow. The first placement of a repository asks for the approval in the terminal, the way Codex and OpenCode sign-ins already do at prepare; a run with no terminal stops before renting and names the command to run first.

Passed over. An app per person (the plan): every person learns registration and seven permissions for no gain. The client id from the environment or Doppler, as LINEAR_CLIENT_ID is read: a secret's home for a value that is not secret.

Hard to undo once shipped. The app's name, owner and address appear on every approval page and installation. Adding a permission later asks every installation to approve again; removing one asks nobody. So the app should start with the fewest permissions (question 4).

Findings

1. One Loopflow app, approval at first placement this work

Above. Removes forward.github_app, the first demo line and the registration steps. The grant step keeps the plan's check that the token reads the repository and cannot read a second one, and prints the app's install link when the first half fails.

2. "Signed in" has to mean the token works this work

Three checks compare a login name: remote_has on the sender, installed on the receiver, service_login behind lf machine logins. The plan fixes the receiver. The sender still returns early, so the renew command and the re-send both do nothing on a rental that already has a login. For a rental the sender skips the question and sends; and the rental's GitHub row asks GitHub with the token it holds, so an expired one reads signed out.

3. Cut the token in mark_ended this work

One site instead of two, and it covers the sandbox its provider deleted. The renewal there is a call to GitHub during an ending: it must never fail the ending, only log.

rentals.github_repository stays a stored column. It cannot be derived from the rental's Tasks: a rental made with lf ondemand rent has none, and mark_ended hands the Tasks back before anything could ask.

4. A rental reaches one repository this work, stated

gh keeps one token per account, so a rental has one GitHub login and one repository. The plan excludes a private submodule. The same rule covers a rental made by hand: lf machine login github modal-1 takes the repository from the checkout it is run in, and run from a second repository it replaces the first and says so. Chosen without asking, because nothing today puts two repositories on one rental.

5. Two leftovers of the logins change this work

The error for a rental with no agent says to run lf machine login codex here (rental.rs:697-704). Once an empty logins stops following the laptop, that advice does nothing; it has to name --logins codex on the template. The plan says the message "already says so"; it does not.

github and linear in --logins become words with no effect, since the repository decides both. The docs example --logins codex,github becomes --logins codex.

6. Workflow permission reopens the door the token was meant to close this work, question 4

The plan's app asks for Workflows write. With it, a rental can push a branch carrying a new workflow, and a workflow on a branch reads the repository's Actions secrets. That is finding 2 of the same security review, reached from the rental this Task is narrowing. Without it GitHub refuses any push that adds or edits a file under .github/workflows/.

7. Rentals longer than 8 hours separate

The laptop's server already visits each rental to collect Session history. Renewing a token near its end on that visit would make the 8 h clock disappear while the laptop is awake. It takes the renew path from this work plus a call from that loop. Left out of this Task, as the plan has it.

8. The other logins still outlive the rental separate

After this work GitHub ends with the rental and Linear ends within 24 h. The rest do not: Codex's device login is its own renewing grant written on the rental, and nothing in the rental code signs it out before the sandbox is deleted; OpenCode gets a fresh renewing login or a copied raw key; Claude's setup token is long-lived and reaches the whole account. Signing Codex and OpenCode out during give-back is a small change that helps only when the laptop does the giving back. Claude has no narrower token to offer.

What the plan gets right, and stays

  • User token by device flow over an installation token (needs the laptop every hour and a private key, authors PRs as a bot) and over a fine-grained PAT (cannot be created by a program).
  • The renewing grant never leaves the laptop, as Linear's does not.
  • No fallback to the laptop's token when the grant is missing: placement stops before renting.
  • Owned Machines unchanged.
  • Pass 1 proves the four unknowns against a real app before anything depends on them.
  • The first-contact fixes (-a -x, Daytona's pinned key, userinfo out of errors).

Questions

  1. Who owns the GitHub App?

    Either way an app must be registered on github.com by a person before the first pass can finish.

    1. Recommended. One public "Loopflow" app under the organization. Its id ships in lf. A person clicks Install on a repository once and never sees an id.
    2. Each person registers their own app and pastes its id into a setting (the plan).
  2. Where does the first approval for a repository happen?
    1. Recommended. Inside lf task run --rent, the first time that repository is rented from a terminal. A run with nobody there stops before renting and names the command to run first.
    2. Always a separate command, run before the first rental (the plan).
  3. What is the command for approving ahead of time called?

    Needed for unattended setups under 2a, and for everyone under 2b.

    1. lf machine login github --rental (the plan). Sits with the other sign-ins, though it signs no Machine in.
    2. Recommended. lf ondemand login github. Sits with lf ondemand rent, where rentals are set up.
  4. May a rental push changes to CI workflows?
    1. Recommended. No. A Task that edits .github/workflows/ cannot push from a rental; GitHub refuses with its own message and the Task is finished on your Machine. A rental can then never add a workflow that reads the repository's secrets. Allowing it later means approving the app again.
    2. Yes (the plan). Any Task can run on a rental; a rental can do to this repository's CI what your laptop can.
  5. A rental still running after 8 hours loses GitHub. What should happen?

    Rentals last 4 hours unless asked for longer; the most is 24.

    1. Recommended for this Task. Placement prints the time GitHub stops, and lf machine login github <rental> renews it (the plan).
    2. Also file a Task so the laptop renews on its own while its server runs (finding 7).
  6. A rental is deleted while the laptop is asleep. Its token keeps working until its 8-hour mark, or until the laptop next wakes and notices. Good enough?
    1. Recommended. Yes.
    2. No. The only tighter option GitHub offers is a separate approval per rental: a code typed, or an approver command run, at every placement.
  7. A template with no logins no longer signs the rental in to Codex because the laptop is.
    1. Recommended. Yes (the plan). A rental that should run Codex says --logins codex.
    2. Keep Codex following the laptop, and drop only OpenCode.
  8. File finding 8 (sign Codex and OpenCode out when a rental is given back) as its own Task?
    1. Yes.
    2. No.
