2. Biggest remaining mismatch & the fix (HEAD vs. Proposed)

Biggest mismatch Recovery and status still pretend a Task isn't checked out here whenever its conversation sits in another directory

task_conversation_here_sql was written when binding still overwrote agent_sessions.cwd to task_checkouts.worktree, so it used rtrim(s.cwd,'/') = rtrim(c.worktree,'/') as a proxy for “this Task is checked out on this Machine.” Now that bound conversations honestly stay in their own directories, that proxy breaks crash recovery for every split-checkout Task — directly contradicting this branch's own plan — and makes lf task status and Desktop print a false “its Task is not checked out here” line (observed in QA scenario 7).

Proposed completion Let task_checkouts answer “checked out here” and agent_sessions.cwd answer “where it launches”

Drop rtrim(s.cwd,'/') = rtrim(c.worktree,'/') from task_conversation_here_sql (keeping the task_checkouts join, open-Task check, primary-Session link, and moved_to_machine_id IS NULL), and rename internal in_task_checkout to task_checked_out_here. In parallel, let adoption::bind_session re-select a Session already assigned to the target Task without failing when another Task owns its worktree.

3. Stress-testing the completed model

Normal path

Live agy chat in unowned Y binds to Task T (checkout X). Bind prints both paths and leaves cwd = Y. lf resume -a claude:fable in Y switches provider in Y. lf resume T from anywhere attaches to it in Y.

Crash & recovery

Provider dies without quit (exit_code none or non-0/130) → T is open, claimed, and has a task_checkouts row here → server restarts the primary in Y and lf task status shows starting again. If Y was deleted on disk, leave_gone_directory falls back to main.

Task not checked out here

Task T is checked out on another Machine (or never checked out locally yet, e.g. created from main without a worktree) → no task_checkouts row here → recovery leaves it stopped and lf task status truthfully reports “its Task is not checked out here.”

Counterexamples checked
  1. lf task create --run setup race: Before setup::checkout finishes creating the worktree, task_checkouts has no row yet — so keeping the task_checkouts join in task_conversations_here means recovery never races initial checkout setup.
  2. Collected remote Sessions & moved Sessions: Sessions collected from remote rentals live in machine_records, never agent_sessions. Sessions moved to another Machine set moved_to_machine_id and completed_at, so neither triggers local recovery.
  3. Re-binding when T has no checkout and S sits in T2's checkout: Because bind_session sets checkout = None when checkout_task != target, re-selecting S as T's primary never steals T2's worktree as T's checkout.
  4. lf task create --session with a crossed Session: Creating a new Task (target = None) or passing an explicit --worktree still refuses when the Session and checkout belong to different Tasks.
  5. Split Task moved to another Machine (lf task move): moves::send_task checkpoints task.worktree (X), not Y. Uncommitted edits in Y do not travel with X — kept outside this Task.

1. When you bind a conversation to a Task that already has a different worktree, where should the conversation run?

Applies both when binding from another linked worktree (like manabot.academy-test-drive) and when binding from main or a Wave checkout.

  • 1a. Built Always stay where it started. The conversation, its edits, lf resume in that worktree, and crash recovery all stay in one directory. The Task's own worktree stays where Graph workers and PRs run.
  • 1b. Stay in linked worktrees, but move out of main and Wave checkouts. Keeps shared checkouts cleaner after binding, at the cost of a second rule and breaking Claude Code resume until a new thread starts.
2. When you bind a conversation in directory Y to a Task whose checkout is X, should lf session bind mention both directories?

Matters because Graph workers and lf task changes act on X while your bound conversation edits Y.

  • 2a. Built Print one factual line only when they differ: “Conversation stays in <Y>; <TASK>'s checkout is <X>.” Silent when they match or the Task has no checkout.
  • 2b. Say nothing about directories. Print only the Task it bound to.
3. When a bound conversation running outside its Task's checkout crashes or dies on reboot, should Loopflow restart it automatically?

Applies when the Task itself is open and checked out on this Machine, while its primary conversation runs in another directory (another worktree or main).

  • 3a. Chosen for build Yes — restart it in the directory it was running in. Matches normal Task conversations, fixes the misleading “its Task is not checked out here” message, and leaves Tasks with no checkout on this Machine stopped.
  • 3b. No — auto-restart only conversations inside the Task's own worktree. Leave split-checkout conversations down after crashes, and change the status message to say the conversation is outside the Task's checkout instead of saying the Task isn't checked out here.
