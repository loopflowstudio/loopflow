Counterexamples checked

Failure & recovery pathsHolds

1. Abandon cleanup failed before reopen: if the worktree or local branch still exists on disk (or the PR never closed on GitHub), task_reopen keeps task_checkouts and any still-open PR intact so local commits are never lost.

2. Open Task whose PR was closed externally on GitHub: reopen_task was never called, so the closed PR stays active and status still warns "PR closed without merge; reopen the same PR or abandon the Task".

3. Reopening a Done Task: its merged PR has no abandoned_at and stays visible until a new pass publishes sequence 2.

4. Raced abandon cleanup vs. reopen: both hold retirement::lock; if reopen finishes first, finish_abandon sees the Task is no longer abandoned and exits without deleting the checkout.

Hierarchy & race checksHolds

5. Running grandchild under a merged child: live_abandon_refusal recurses through merged children so a live grandchild still blocks --children abandon and names lf task interrupt.

6. Closed child with an open grandchild: once a child is closed, its open grandchild already appears top-level in lf wave show and Desktop, and is not counted under the grandparent.

7. Child filed between pre-check and commit: complete_task_now refuses inside its IMMEDIATE transaction and answers conflict, writing nothing.

8. Fresh placement finding a remote open PR after reopen: place_task_in allocates the next PR sequence (2) from Task history, avoiding sequence-1 collisions.

Outside this work

Abandoning a parent Task (lf task abandon LOO-12): cancels only LOO-12 and leaves open children linked and open (surfaced top-level). Adding --children to abandon is a separate outcome (would add policy parsing, confirmation dialogs, and live-child guards to the abandon path).

iOS reopen / abandoned Task filter: iOS has no Reopen action or Abandoned list today; adding one is a separate mobile UI Task.

Pre-existing issues noticed during QA (not introduced by this branch): server/recovery.rs read-then-start race that can start a conversation right after immediate abandonment; a killed Graph's failure reason staying on a reopened Task until its next run (Run is still enabled); unplaced lf task status omitting its action: line; PR-less abandon retaining checkout/branch while saying they were removed; iOS single-line NoticeView truncation; and lf task interrupt not stopping a running cmd: step.

Choices made for review

All four choices below are built on 4a4e7d3e and reversible. Reply with a number and letter (e.g. "2b") if you want to change any of them.

  1. After you reopen an abandoned Task (whose old PR was closed and whose branch was deleted), what should you see when you open it?
    • 1a (chosen, built) Ready for a fresh start on the same Task. Desktop's Start and Auto-Ship buttons work right away, the old closed PR moves to history, completing without a new PR works, and running it checks out a fresh branch from current main (unless its old checkout or local branch still survived on disk, in which case that work is kept).
    • 1b Keep the closed PR front and center. Status keeps warning that the old PR was closed without merging until a new PR is opened, and Desktop blocks starting the Task until the old checkout path is manually restored.
  2. When you choose to move a parent's children up and its own parent (the grandparent) was deleted while a great-grandparent above it is still open, where should the children land?
    • 2a (chosen, built) Top-level Tasks. Once the grandparent was deleted, this parent already appeared as a top-level Task everywhere, so its children stay top-level instead of jumping under an ancestor nobody saw it attached to. (Completed or abandoned grandparents are still skipped to reach an open great-grandparent.)
    • 2b Under the open great-grandparent. Skip deleted Tasks the same way as completed ones so children attach to the open great-grandparent above the deleted row.
  3. When a child is sitting idle at a review step (no run in progress, just its conversation waiting for you), should abandoning children with the parent proceed?
    • 3a (chosen, built) Proceed and close the idle conversation. Only refuse when a child actually has work in motion (a running workflow, background run, or an agent mid-turn).
    • 3b Refuse while any child conversation is open. Require closing each idle child conversation first before completing the parent with abandon.
  4. In Desktop, when every open child of a parent already has a merged PR (so nothing would be abandoned), which button should be the default?
    • 4a (chosen, built) Complete & Finish Children first (marks the merged children done alongside the parent), with Move Children second. Whenever any open child is unmerged, Move Children is the default and Abandon Children is destructive.
    • 4b Complete & Move Children is always the default button, even when every open child is already merged.
