One interaction, as it runs on the branch

Normal path

$ lf wave create billing
Added Wave billing; committed .lf/wave/billing
# 0 projects rows, nothing queued for the tracker

$ lf task create --wave billing 'Invoice export'
Invoice export · d11837
# one Project "billing", started, made in the save

$ lf wave status billing
  Project   billing (proj_4bd9…) · started
  d11837  unstarted — Invoice export

With Linear configured the first Task queues two creates, Project then Task. With a second open Project in the Wave the command says where the Task went: Tax lines · 0cf5d8 in Project Billing v2.

Failure and recovery

Failure: the save into an empty Wave aborts. The Project is made in the same transaction, so nothing is left behind (a_failed_save_into_an_empty_wave_makes_no_project).

Failure: the tracker is down. Task and Project are saved; their creates wait in tracker_actions. Nothing for a person to retry.

Recovery from the wrong Project: move the Issue in Linear. Ending "Billing v2" there sends the next Task back to "billing", and a Task left in the ended Project still runs.

Interrupt: lf task interrupt stops the Task's live Graph; the interrupt is recorded against the Task and nothing else (QA pass 2).

Upgrade: a store with a current Project and a KR keeps its Project; the new Task joins it and the KR text is no longer shown.

Larger than this work

A Task's Project is shown only at the moment it is chosen. Grouping lf wave status by Project is new presentation over data the wire already carries. On the measured store 6 of 62 Waves hold more than one open Project.

A Wave without a tracker still costs a Project, and no command ends, adds or renames one there. Tasks belonging to a Wave directly would change every read that walks Task → Project → Wave.

The Task title still says "a Project is a Wave's optional tracker link". The steer withdrew that; the PR title and body should say what was built.
