A Task step on any harness

LOO-974, reviewed before anything is built. The area taken is wider than "admit OpenCode": it is how a Task step gets its agent, what that agent is allowed to do, and what happens when it cannot start. The refusal, the three wasted attempts and the missing tests all sit there.

Outcome: the plan changed. Its center holds: delete the execution boundary instead of teaching OpenCode to satisfy it. Three things moved. The permission rule is now stated as yolo, the word already in the docs, with one owner. A harness that is not installed becomes a recorded move in the place that already moves a step between agents, not a filter in config. The "fail once" rule no longer catches cmd: steps. A parity table in the harness README becomes the way the Task is checked. Idle wake leaves the Task.

Before

A person reading docs/config.md learns four states: attended, the unattended floor, yolo, and "managed execution", with a fifth, "provider-only worktree scope", that no production path reaches.

AgentConfig {

Capabilities { supports_execution_boundary }

Decided in two places: run.rs from the Task input, and agent/session.rs again for batch resume, which sets no skip_permissions.

After

Three states, and one sentence for the third: a headless run in its Task's checkout runs as yolo.

AgentConfig {
  skip_permissions: bool,
  write_scope
  execution_boundary
}
Capabilities { supports_execution_boundary }
confine_checkout_agent
checkout_execution_boundary
one function: is this a headless run in its Task's checkout?

"Execution boundary" keeps one meaning, the one in docs/security.md. "Managed" keeps the glossary's. With no capability to lack, no harness can mismatch.

A step that cannot start

Before, and the first plan

A missing CLI is refused at run.rs:751 with the install hint, then repeated twice by the outer loop.

The first plan filtered the agent order inside Config and stopped the loop "when the failed step started no provider".

Counterexample that broke it: cmd: sync and cmd: land --wait-and-fix are steps of the code Graph and never start a provider. A fetch that fails once would no longer be tried again.

Second counterexample: filtering in Config moves chats too, silently. Today only a Graph step moves, and every move is recorded.

After

Not installed is a reason to move. The Graph step's ladder drops a rung whose CLI is missing and records the move like a limit move. No rung left: the step fails with the first choice's hint. Config never probes the Machine for this.

Attempts are for work. A skill step that failed with no AgentProcess under it was refused by lf; the run stops after one attempt. A cmd: step keeps three. Read from the store and the Graph's step; no new failure type, no stored refusal.

Passed over: writing Failed{resumable:false}. The Task would keep refusing after the CLI is installed.

Questions

The marked option is what the plan now does. A number and a letter is a complete answer.

  1. The execution boundary denies nothing today.
    1. Delete it; a headless run in its Task's checkout runs as yolo. (chosen)
    2. Keep the types and flip OpenCode's capability to true.
    3. Stop this Task and build a real OS sandbox for all four first.
  2. A harness in the agent order is not installed on this Machine.
    1. A Graph step passes it over and records the move; chats and batches fail with the hint as now. (chosen)
    2. Every launch passes it over, chats included.
    3. Nothing passes it over; it fails once with the hint, wherever it sits in the order.
  3. A skill step fails before any provider starts.
    1. One attempt, then stop; cmd: steps keep three. (chosen)
    2. Stop at the second identical error, for every kind of step.
    3. Leave three attempts everywhere.
  4. A worker asks a question with nobody there.
    1. The turn fails with the question as the reason, on every harness. (chosen)
    2. Decline the question so the turn continues.
    3. Leave OpenCode waiting; out of this Task.
  5. Idle steer wake for OpenCode and Pi work sessions.
    1. Out of this Task; its row reads "no". (chosen)
    2. Last slice of this Task.
  6. The parity table in harness/README.md.
    1. Add it, a test or a named gap in every cell, and make it the done-line. (chosen)
    2. Tests only; no table.
  7. Should every headless run be yolo, not only those in a Task checkout?
    1. Not decided here; behavior unchanged. (chosen)
    2. Yes: one rule for every headless run.
    3. No, and say why Task checkouts differ in docs/config.md.
