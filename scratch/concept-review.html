The biggest mismatch: which lf Dev runs

The kickoff plan removed Dev's own lf and handed the choice to the launching shell's PATH. The guarantee the whole Task rests on, "the server is left alone", then depends on PATH order.

Before (kickoff plan)

loopflow-dev.py run
  LF_BIN=$(first lf on PATH)      # 3 candidates here
  open "Loopflow Dev.app"

controlLfPath:
  LF_HOME + LF_BIN → LF_BIN
  bundle helper    → helper
  no helper        → LF_BIN        # second meaning
enriched: keep LF_BIN if no helper

Dev → `$LF_BIN install server`
  sha ≠ running server → replaces it

After proposed

loopflow-dev.py run
  open "Loopflow Dev.app"          # no LF_* at all

one resolver (controlLfPath, enriched, isInstalled):
  LF_HOME + LF_BIN → private Machine
  bundle helper    → release app
  ~/.local/bin/lf  → the Machine's installation
  none             → "Loopflow is not installed…"

Dev → installed lf `install server`
  = what Loopflow.app itself runs

Why this and not a new "connect only" call: the public entry is already what both Rust and Swift mean by installed, so the fix adds no concept and removes the launcher's part entirely. It also closes a case the kickoff wording left open: enriched drops LF_BIN today unless the bundle has a helper, so a helper-less Dev opened on a benchmark's private home would have run the installed lf against it.

Seen on this Machine, 2026-11-20: server instance 5f5bc7b3…, sha aeab8b41…; /Applications/Loopflow.app/Contents/MacOS/lf and ~/.local/bin/lf have that sha; ~/.cargo/bin/lf (Jul 16) is a527444a…; the Dev bundle's lf is 07aa35fc… and is serving ~/.lf-copy for another Task's Dev (pid 35920).

What survives, what changes on purpose

SurvivesThe release app's rule (its own helper, nothing else). Private homes for Swift tests and the benchmark. Dev's bundle id, name and signing identity. copy::snapshot for backups. Data on disk: ~/.lf-copy, world directories, release notes.
Changes on purposeDev can no longer show branch Rust on real data. Dev's panes get the installed lf on PATH. Running Dev from a second checkout closes the first one's window.
Would break itA Machine with no installed Loopflow (a contributor who only builds from source): Dev opens to the "not installed" message. A person who presses Run in Xcode still gets a bundle with a branch helper, which is the release app's build path and behaves as an installation.

Outside this work

The Xcode target always bundles a branch lf (swift/project.yml:74), so Run in Xcode on a developer's Machine is still a second installation that asks to be the server. Making that build helper-less for debug configurations is a separate outcome: it needs the release and CI builds to keep bundling while debug stops, and a check that Swift tests on private homes still find their lf.

Questions

  1. Which lf does a Dev bundle run?
    1. The account's public entry, ~/.local/bin/lf, found by the app. (chosen in the plan)
    2. LF_BIN passed by the launcher from PATH.
    3. Ask the running server for its executable path and run that.
  2. A branch that changes Rust and Swift together, before it lands:
    1. New Swift on the installed server, the changed part saying it can't be read; the new server only on a private home. (chosen)
    2. Keep run --copy for lists only.
    3. Add a real "install this branch on the Machine" command.
  3. Two checkouts both run Dev:
    1. One Dev; the last run quits and replaces the other. (chosen; today's behaviour)
    2. A bundle per checkout, each asking for its own permissions.
  4. Run in Xcode on a developer's Machine:
    1. Leave it bundling a branch lf; file it separately. (chosen)
    2. Make debug builds helper-less in this Task.
  5. The benchmark's one Task and Session, if the real lf with a stand-in claude can't make a resumable Session without seeded rows:
    1. Delete the three benchmark commands and DesktopNativeSessionFixture. (chosen)
    2. Keep a small seeded fixture for the benchmark alone.
