Where the plan lives once there is a hub

Area reviewed: planning across Machines for repositories without Linear or Asana — how a change saved on one Machine reaches the others, what a person sees while it travels, and the records behind it. Taken because LOO-938 replaces the whole of that area (Git peer journal → hub), not one function of it. Reviewed against the kickoff plan at 2ac5bb7187; no code is built yet.

The question

The kickoff plan says the hub is a third tracker. Does a hub that owns the plan line up with what a tracker is in this code?

No. A tracker here is a foreign system reached through a lens. The hub is the same store on another Machine. Treating it as a tracker would have dropped every Wave and half the Task fields on the floor.

One interaction, walked

Laptop, etude, hub = mini. Rename Wave audio to sound, create a Task, retitle it, close the lid on a plane, retitle again, land.

Kickoff plan (tracker lens)

wave_name→enqueue_local→table "waves": return

The Wave rename never queues. enqueue_local only handles tasks, projects, task_comments.

task_title→ActionKind::Field→plan.apply→seq check→Conflicted

The offline retitle comes back lost if mini moved — a rule decide never applies to an unsent value.

task_rank / due / branch / shipped_at→ActionKind::of → None

Proposed (store words)

wave_name→WorkEdit→tracker_actions (hub)→plan.apply→write(Local)

Every value the writer saves is a WorkEdit; every one travels. Waves included.

offline retitle→open→reconnect→applied, sent last wins

Same answer Linear gives and the Git journal's latest clock gives today.

plan.changes(since)→WorkEdit[]→write(Import)

Inbound skips any field with an open local row, so a value on its way isn't overwritten by an older one.

The biggest mismatch

Proposed, written into scratch/plan.md. The hub is the plan's home, spoken in store words — not a tracker.

Before (kickoff)

enum Tracker { Linear, Asana, Hub }
Hub: send / look / changes / fetch_issue
     / removed / issue_ownership   // 4 unreachable
enqueue via ActionKind::of        // lossy
inbound via decide()              // Linear revisions
plan_field_changes(owner, field,
                   seq, action_id)
external_issue_id = own UUID
slices: one field → every kind → delete Git

After

tracker_actions(tracker='hub', kind='field',
                subject=field, value=WorkEdit)
drain: hub sender, one plan.apply / pass
plan.apply  { edits }      → { applied, seq }
plan.changes{ since }      → { edits, seq }
plan_changes(repo, table, owner_id, seq)
inbound: write(Import), skip open fields
slices: hub holds the plan → delete Git

Smaller on every axis: no Tracker variant, no seven-kind mapping, no binding, no second conflict rule, one slice fewer. It also closes a data-loss gap the kickoff plan would have shipped: today's Git journal carries Wave edits and the tracker lens doesn't.

Larger than this work

  • Hub-side conflicts. If "sent last wins" proves wrong for two people on one hub, a per-field check belongs at the hub and would apply to everyone — a product decision for later, not part of replacing Git.
  • The word "tracker". tracker_actions, lf repo tracker and TrackerKind now carry a destination that isn't a tracker. Renaming the queue (e.g. "outbox") is a cross-surface rename; this work keeps the names and fixes the docs' definition.
