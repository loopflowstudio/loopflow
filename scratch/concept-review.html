The biggest mismatch: a Process's Task is computed, not recorded

Walk it. You open LOO-937 in lf task status. Its Processes come from lf_process_ids (task_work.rs:102): every Process whose cwd sits under the checkout, minus pairs frozen when the repository moved, plus those pairs, plus anything that wrote an event, history row, or turn into one of the Task's Sessions, plus agent attachments. Five sources. Move the repo, then reuse the old path for a new clone: the right answer depends on the frozen table and a sqlite_master probe on every read.

Before

Task ← cwd under worktree
     − relocated_task_processes
     + relocated_task_processes
     + session_events.lf_process_id
     + history.session_history
     + history.turns
     + agent attachments

Proposed

at insert, first that answers:
 1 the named Task
 2 caller Session's task_id
 3 parent Process's task_id
 4 deepest checkout holding cwd
read: WHERE task_id = ?

The kickoff plan already adds the column, but resolves it at insert only by path, and is silent on the four Session-derived unions. Path alone would mark a hook lf invoked from outside the checkout as nobody's, so the unions would have to stay and the read stays five-way. Rules 2 and 3 are primary-key probes on columns processes already has (caller_session_id, parent_lf_process_id). With them, task_of_process becomes a row read and lf_process_ids one index probe.

What would break it: a Process reached today only through session_events with no caller_session_id. The plan now says to count those on the /tmp copy before deleting the unions; if any survive the prune, the backfill gets a clause, and the read still never keeps them.

A counterexample that reversed one verdict

The plan sent URL, branch and team to pm_items as "provider facts nobody edits locally". record_task_branch_in (children.rs:154) says otherwise:

/// Git planning carries the Task's branch, so whoever runs it next checks out
/// the same branch and finds the same PR.

lf writes the branch when no provider is connected, and every new checkout reads it (ops/task.rs:1045). On the live store, 4 Tasks hold a branch with no pm_items row. Moving it would send their next checkout to a fresh branch and lose the PR. The rule that falls out is the one the plan already uses for title: tasks holds what people see on any Machine; pm_items holds what the provider last said. Only observation bookkeeping leaves (planning_provider_revision, 421 rows differ; pm_snapshot_synced_at; planning_completed). The "peer-only Machines lose the URL" question disappears with it.

Order: kept as chosen, with its cost shown

task_orders holds 2 rows, 17 Task ids, keyed by repository, not person. The plan makes a Working-board drag write planning_rank through reorder_in. Two places that bites: a drag onto a Task in another Project has no rank meaning and snaps back; and with several people on one deployment, one person's board drag reorders the shared Linear order for everyone. Today's table is wrong for that future too (one order per repository, shared by everyone), so the plan's choice is no worse; it is just visible.
