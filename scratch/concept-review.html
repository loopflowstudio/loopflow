Bare, managed, worker: does the code say what we say?

LOO-924 as built at 74a96d6176, PR #1966, 89 files against main. The area is launching an agent: which harness, which agent, who keeps it running, which Task it belongs to. No code changed by this review. The earlier Session-commands review now lives with LOO-958.

Most of it lines up now. Holder, Place, transport::holder and WorkSource::is_managed are gone; one value, Run, comes back from delegate; belonging to a Task no longer changes how a launch lives. What's left is about names: the code's three states are really two yes-or-no questions, and the type is called something it isn't.

One interaction

lf task run LOO-12, and its implement step.

  1. The Graph starts the step with LF_GRAPH_STEP=worker. In the step's process, delegate_current sees journal::worker_step() and picks Run::Worker.
  2. Launch { run: Worker, harness, admitted, start }; Run::mode() says headless, so drive::run drives it.
  3. Hooks: Run::reports_turns() is true, so each turn boundary is sent to the Machine server, exactly as for a managed conversation.
  4. Failure: the answer fails its schema. The Graph runs lf -b session resume ID --message …; that turn is also a Worker.
  5. Recovery: a person runs lf resume ID on that step's Session. session_run reads the row: not bound, not a primary conversation, so Bare(Interactive), in their terminal. A store that can't be read gives Managed and logs one recording gap.

The biggest mismatch: three names over a two-by-two

Everything that reads Run asks one of two questions:

run.reports_turns()   // !Bare        — hooks, env, thread naming
run.mode()            // Interactive | Headless — which runner, held terminal or not

Where the code matches on it, Managed and Worker sit in the same arm (Run::Managed | Run::Worker => in agent_process.rs and harness/mod.rs). So the four values are a grid:

someone typingheadless
the server is told about each turnManagedWorker
it isn'tBare(Interactive)Bare(Headless)

That is Holder × Mode again under better names. It's fine as code. It's the vocabulary that's off: said earlier, "workers are always headless, so there is basically no point to making them managed", and as built a worker is a managed launch without a terminal. I chose that for this pass because the server records Codex turns and refreshes planning from those turn reports.

As built

Worker = reports turns + headless + runs detached.
Managed = reports turns + interactive + held terminal.

Honest description: two states, bare and managed, and a managed one is either a conversation or a worker.

proposed, if worker should mean something

Worker = headless, runs detached, reports its run and its exit, not each turn. Codex turns are recorded and planning refreshed when the step ends.

Then three states are three behaviors. It needs the server's turn-end work moved to step exit, which is its own change with its own risk.

Tested: normal path is the same either way. Failure: a worker killed mid-step. As built, the server has its turns up to the kill. Proposed, it has nothing after the step's start unless the exit path runs, so LOO-959's recovery would have to read the provider's transcript. That counterexample is why this isn't in the PR.

The name

proposed The comments already call it what it is: "Who keeps the provider running", "Retain the recorded lifetime", "the selected lifetime", "resume lifetime". Rename harness::Run to Lifetime. It reads true (Launch { lifetime }, Delegation::Here { lifetime }) and it leaves Run to LOO-953, where a run is a Graph's execution.

Who picks the state

The rule was "the command alone". As built there are four inputs, all written by lf and none settable by a flag a person passes:

InputGives
LF_GRAPH_STEP=worker, set by a Task's Graph on its steps; or the caller passing workerWorker
Running inside a held terminal the server startedManaged
On reopen, the Session's row: bound, or a primary conversationManaged, else Bare
Anything elseBare, with -b or the terminal choosing interactive or headless

That holds. The one exception is still lf -b resume ID --message, where a flag makes a resume a Worker turn; LOO-958 removes it.

Questions

  1. What is a worker?
    1. As built: a managed launch that is headless and has no terminal. Say that in the docs, and keep three names.
    2. Something of its own: it reports its run and exit, not each turn. A separate Task, after LOO-959 says how a killed worker is recovered.
    3. Drop the third name: bare and managed, where managed is a conversation or a step.
  2. Rename harness::Run:
    1. To Lifetime, in this PR.
    2. Leave it; LOO-953 picks other names.
  3. Showing the state in lf session list and lf ps:
    1. In this PR, derived from the Session row, not stored.
    2. A follow-up Task.
    3. Not needed.
  4. The 45 remaining parse_agent / HarnessKind::parse call sites:
    1. Check each in this PR; keep only those where text comes in.
    2. Good enough.
