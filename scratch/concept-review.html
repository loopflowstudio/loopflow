One consequence of “removed Waves stay removed” is still unbuilt: the default lf wave list keeps showing a removed Wave as abandoned, while Desktop reads the same command with --current and drops it. The one consequential mismatch

The Problem section of the design opens with Jack's own lf wave list showing engbot and list “stuck as abandoned”. The product's own remove now produces exactly that row:

$ lf wave remove desktop
3 open Tasks moved to the repository (1 started keeps its worktree, PR and running Graph).
1 completed Task and 1 chapter stay readable in history.
.lf/wave/desktop removed on the main checkout.

$ lf wave list                       # what docs/work.md, init.md and repo_operate.md tell people and agents to run
WAVE              REPOSITORY                    STATUS    TASKS  MACHINE
desktop           …/loopflow                    abandoned     0  unplaced
product           …/loopflow                    ready        12  unplaced

Desktop sidebar                      # reads `lf wave list --all --current --json`
product

Three readers, two answers, three words for one state. retire_waves writes retired_at and work_state = 'abandoned'; the list prints status.label(); lf wave show prints “retired at …; superseded by -: removed”. The accepted contract says removed Waves stay removed and that Desktop and the CLI reflect the result consistently. An agent in a repository session reading lf wave list --json sees an abandoned Wave it may try to plan around.

Where --current came from

#1615 (2026-10-21, “Trim undesigned CLI surface”) added it as a navigation filter — “exclude abandoned and retired registrations from current navigation” — and the Swift README of the same PR calls the unfiltered list “historical registry visibility”. No decision made the unfiltered list a history view, and nothing in product code abandons a Wave except retire_waves; the abandoned-without-retired rows are legacy strays.

Direction next implement

Now

lf wave list                 # live + removed (as abandoned)
lf wave list --current       # live
lf wave show desktop
  desktop  retired
  history   retired at 1762…; superseded by -: removed

Proposed

lf wave list                 # live; what Desktop shows
                             # (--current deleted)
lf wave show desktop
  desktop  removed
  history   removed at 1762…
  • The default excludes retired_at rows. A legacy abandoned row that was never retired stays listed, in Desktop too, so Remove Wave… can finish it.
  • --current and its callers go: RegistryQuery, read.rs Waves, the s1–s5 skills, the graph/mod.rs test, status_tests, wave_lifecycle, the Swift README and tests.
  • lf wave list's help drops “retained planning identities”; lf wave show says removed at, and superseded by only when a successor exists. The WaveSnapshot wire (status, retired_at) is unchanged.
  • No new listing of removed Waves. lf wave show <name|id> reads one; an inventory is a later ask.
  • Same pass: the Swift README still says authored GOAL.md files “appear before their first registration” — the placeholder scan slice 6 deleted.

Counterexamples checked

  • A clone whose Waves nobody registered: still listed once lf wave add, connect --all or joining the portfolio registers them; unaffected by the default filter.
  • A removal whose Linear archive failed: the row is retired, so the list hides it; the receipt's leftover line is the only place it is named, as the first review decided.
  • Re-adding a removed name: the fresh Wave lists; the old one answers to its id in lf wave show.

Looked at, holding

  • lf wave rename old new after the rename already happened answers with the Wave at new (renamed: false). Desktop renames by id and never takes that path; the CLI answer is the idempotent one.
  • The Remove sheet stays open when other Waves' documents still mention the name. Jack's 2026-10-28 direction lists those for a person to edit; the sheet shows what the CLI prints.
  • The sidebar's New Wave selects the new row after addWave awaited the planning refresh, so the row exists when selected; the Waves window closes its sheet and refreshes.
  • Removal order, idempotency, recursive child removal, memory folding and the Rust-authored receipt match the accepted design and the five demo steps (wave_lifecycle 6 tests).
