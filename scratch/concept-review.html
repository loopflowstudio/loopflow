Waking an idle work session: do the concepts line up?

LOO-1002, reviewed before anything is built, against scratch/plan.md at 8fc8bdf64c. Area taken: how a steer or Task update reaches a work session that has finished its turn, for all five harnesses: the idle recording, the store's wake address, the server's watcher and each provider's reach. That is the whole "hears a steer while idle" row, not only the three new harnesses, because the new reaches reuse the Claude/Codex model and should fit it rather than extend it.

The interaction

You run lf steer LOO-12 'use the new API'. The work session for LOO-12 sits idle in an OpenCode TUI. Within a second a turn starts there showing lf's message, and lf session steers says delivered. If the wake fails (provider refused, socket gone, agy changed its RPC), nothing breaks: the steer waits and the session hears it at its next boundary, as it does today. A person learns one thing — an idle session hears lf — and nothing about sockets, tokens or providers.

Biggest mismatch: who reports the address

The store's wake address has two sources today, and they are honest about it:

The provider makes it → a boundary reports it

Claude creates its inbox key; lf only finds it from a hook (claude_inbox()). The OpenCode/Pi plugin binds its socket inside the provider process and reports it on each boundary. Reporting from inside is the only way lf learns these.

lf makes it → the launch records it

Codex's app-server is spawned by lf; codex.rs calls record_agent_endpoint during open(). No hook involved.

The plan's Antigravity reach is the second kind wearing the first kind's route. lf creates the token, picks the log file and writes the wake file in antigravity.rs open() — then puts the file's path in an env var so agy's hook can read it back and send it to the server as inbox, which the server stores. That's a round trip through the agent's environment to tell the store something the launch already knew.

Before (plan as written) 
antigravity open():  token, --log-file, write wake file
                     set LF_AGY_WAKE=<file> in child env
agy hook (every boundary):
  context.rs: inbox = env(LF_AGY_WAKE)
server boundary.rs:  record_agent_inbox(adapter, inbox)
After proposed 
antigravity open():  token, --log-file, write wake file
                     store.record_agent_inbox(attachment, file)
                     (as codex.rs records agent_endpoint)
agy hook:            unchanged
server boundary.rs:  unchanged for agy

Deletes the env var and the context.rs hook change; the address lives exactly as long as the AgentProcess that owns it (the bind already nulls agent_inbox, processes.rs:579). Counterexamples tried: /resume inside agy — same process, same server, thread follows via hook_callback, address unchanged ✓; lf resume — new AgentProcess, new launch, new file ✓; a released lf launch — no file, no row, next-turn only ✓; a hook that never fires (store down) — the hook route would leave no address, the launch route still has one ✓.

Smaller findings, written into the plan

  1. One concept, one description. agent_inbox is "where the conversation's own process takes a wake"; IdleReach's doc lists the four formats in one place and record_agent_inbox's doc stops saying Claude. agent_endpoint stays Codex's app-server: saved_session_connection and AfterStop read it as one, so Antigravity must not go there.
  2. Pi idle is already recorded through agent_settled → AvailabilityReading. The plan should say so, so the build fixes OpenCode's Stop only and doesn't add a second Pi idle writer.
  3. OpenCode's typed prompt reports moment tool with hook_event_name: "UserPromptSubmit": that pair is what boundary.rs maps to yielded=false.

What stays as planned

The watcher, claim/send/delivered order, one store column read by provider, the plugin wake socket with a real answer, Pi followUp + triggerTurn, OpenCode synthetic/queue, Antigravity over its loopback language server, the slice order (OpenCode end to end first, because the TUI rendering is the risk that could sink the approach).

Questions

  1. Antigravity's wake address: (a) recorded by the launch, as Codex's endpoint is chosen; (b) reported by its hook from an env var, as the kickoff planned.
  2. Antigravity shows lf's message as a typed prompt: (a) accept, the only idle entry agy has chosen; (b) leave Antigravity next-turn-only until it offers a non-user message.
  3. Pi's turn end stop {}: (a) leave it, idle comes from agent_settled chosen; (b) send a named Stop like every other harness and drop Pi's activity reading for yielded.
