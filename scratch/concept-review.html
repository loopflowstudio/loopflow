Biggest mismatch: the sync time has a second name where people ask "why"

Walk it. A Task looks stale. Someone runs lf task show --json, then lf --explain on the same command to see what it resolved.

existing

$ lf task show LOO-1 --json
  "tracker_synced_at": 1794962032,
  "tracker_state": {"state":"available","synced_at":1794962032}

$ lf --explain task …
  Task: LOO-1 (…)
  Planning observed: 1794962032

$ lf --explain --json task …
  "planning_observed_at": 1794962032

Swift  ContextExplanation.planningObservedAt

Same number, same source. "Observed" is the word the glossary retires for incoming changes, and it is printed.

proposed

$ lf --explain task …
  Task: LOO-1 (…)
  Tracker synced: 1794962032

$ lf --explain --json task …
  "tracker_synced_at": 1794962032

Swift  ContextExplanation.trackerSyncedAt
Rust   ContextExplanation.tracker_synced_at

ops::linear::fetch_task
ops::task::fetch_from_tracker

One name from the Task row to the explanation. The two fetch functions follow fetch_issue.

Failure and recovery. A Task never synced, or a Wave with no Task selected: the value is null and the line prints unknown, as today. A later sync fills it. What must survive: the key stays required and nullable on the wire (Swift decode(Int64?.self, forKey:)); nothing stored carries this key, so no released reader is affected. Counterexample checked: if the explanation's time could differ from the Task's (a separate read of the tracker), a second name would be right. It can't: there is one assignment, from the Task row.

Size. One Rust field and its printed line, one Swift property and its test, the key in five DTO fixtures, two function names with 13 references. No schema file change beyond regeneration, no SQL.

Larger than this work

  • "action" also names what a command would do. TaskPlanningAction and the "action" key in lf --explain --json task … (create, edit, move, save, comment) predate this change. The glossary already sets Desktop's buttons apart from tracker actions; this is a third sense. Renaming it (change? request?) is a choice about the explain surface, not a leftover.
  • Applying an event is still "accept". accept_linear_issue_in, accept_linear_project_in, project_accepted_planning: about 60 call sites. As a verb for what the store does with an event it reads fine; as the retired noun it doesn't appear. Noted in scratch/questions.md for a follow-up.
  • Two sync times on one Task. tracker_state.synced_at and tracker_synced_at may be one fact. Settling it means reading every writer of both.
  • LinearIssueId holds Asana gids, LinearWritebackState describes any tracker, and Asana's tests live under ops/linear/. A neutral record ID touches every planning signature.
  • Git has no actions. "action" and "lost" on lf repo tracker describe two of three trackers; Git conflicts are a third thing.
  • Columns provider, planning_provider_revision, observed_at, pm_snapshot_synced_at, pm_writeback_json: each a staged rebuild. LOO-960 could carry them with the contract migration.
