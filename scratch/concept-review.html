LOO-1063 · Built change review

Keep Working Tasks in place

The sidebar, grid and Wave view share an order. Do the product’s concepts and the code’s concepts line up when a conversation changes or two windows move rows?

The drag shows a side the write never sends

Built. You see A, B, C and drop B above A. Another window has already moved A after C. The Machine reads B, C, A, puts B into A’s index, and saves C, A, B. The drop preview puts B before A. A confirmed read puts it after A.

Proposed. Send “B before A” through the write. The Machine uses the latest Working order, removes B and puts it immediately before A. Both the preview and the write give C, B, A against that reading. If either Task has left Working when the Machine resolves the move, the drop is refused and the last confirmed reading returns.

What survives a newer reading

B goes Busy and hands back
Working order and selection hold. The Available and Busy filters recalculate membership in that order. An unknown activity reading can make a filter incomplete.
The target leaves Working
A Machine reading without the target refuses the drop. A failed reread leaves the last confirmed rows and the refusal Notice. A successful reread shows current membership, including an empty list.
A read arrives before the write answer
Applying the same side to an already placed pair leaves the pair in place. A receipt retires the preview independently on each covered reading. A later committed move can change the order again.
The command has only a destination
An older CLI call, a saved Dashboard move or a grid drop with a source missing from that grid’s reading keeps target-slot behavior. In the last case the grid has no immediate preview.
A Task joins after a drag
Saved positions come first. The unsaved tail follows planning rank and Task ID. Repository and Wave plans, the phone list and roadmap use the same order. An authored query or touched Dashboard can compose its own list.
Project order changes
Unsaved Working rows can follow rank edits. Committed drags keep their places. LOO-937 proposes making Working drags edit shared Project rank. That would need a decision on cross-Project drops and treatment of saved Working order.

The next build slice

Start with the real Machine writer. Exercise a drop whose source and target already changed sides in the server reading, both before and after. Assert the committed order and the order in a new reading. Carry the same side through both the served and one-shot command paths. Keep the existing receipt and failed reread regressions.

The first pass removed activity from the sort key and moved previews out of confirmed readings. The private Machine QA recorded steady order during turns, a sidebar drag that survived relaunch, and a refused drop with a successful retry. The concurrent case here comes from running the built Rust move function with B, C, A and inspecting the request fields. The live grid drag and key-window shortcuts still need gate.

Questions for review

  1. What should a drop save if another window reordered first?
    1. Use the side the person chose. The plan applies it to the fresher order.
    2. Use the target’s latest slot, as the destination-only command does.
  2. What starts the Working order before a drag?
    1. Planning rank, with Task ID for ties. This is the built choice. A saved drag takes precedence.
    2. Oldest Task first. Planning rank edits would leave the unsaved Working rows in place.
  3. Who owns the order changed by a Working drag?
    1. The repository’s Working list on this Machine. This is the built choice. A drag can cross Projects.
    2. The Project plan, as proposed in LOO-937. A drag changes the shared rank within a Project.
