Waking an idle work session: do the concepts line up?

LOO-1002, reviewed after the build, against origin/main with the whole branch in it (HEAD b497be0e89). Replaces the pre-build review of 8fc8bdf64c.

Area taken: how a steer or Task update reaches a work session that finished its turn, for all five harnesses: the idle reading, the store's wake address, the server's watcher and each provider's reach. OpenCode and Pi came from main (#1988); this branch adds Antigravity and the minute sweep. Reviewed as one area because the Antigravity reach should fit the model the other four share, not extend it.

The interaction

lf steer LOO-x 'reply with exactly WOKEN'. The agy TUI for LOO-x sits idle. Within a second it shows lf's message as a prompt and answers. If agy was quit and reopened, nothing reports it, so the launch records it idle and the next sweep (at most a minute) sends what waited. If the RPC fails, the steer's claim lapses in 15 s and it arrives at the next boundary; logs/lf.log says why. A person learns one thing: an idle work session hears lf.

Biggest mismatch: the wake address has three homes

Existing

agent_endpoint  Codex app-server   (also read by
                                    saved_session_connection)
agent_inbox     Claude inbox key   | agy wake file
                (by hook)          | (by launch, provider='agy')
agent_socket    OpenCode / Pi socket (by boundary)

Possible, not this Task

agent_wake      one address
agent_wake_kind codex | claude | agy | socket
                written by whoever makes it

Why it stays: agent_endpoint is also Codex's resume connection, so it can't fold in without splitting that reader; agent_socket came from main a day ago; and a merged column is a staged migration (expand, 30 days, contract). The decode lives in one query and one enum, which is where a reader looks. The Antigravity arm sits between Codex and socket in the match; the provider='agy' CASE makes its column distinct, so no row can be misread as a Claude key. Recommendation: leave it; it is a separate outcome if a sixth harness arrives.

Smaller findings

  1. Antigravity claims before it connects. LanguageServer::find reads files only; the network is first touched in send, after claim. The other reaches connect first so an unreachable conversation keeps its news. Cost here: a dead language server holds a 15 s claim, then the steer arrives at the next boundary. A typed prompt in that window gets it at the next tool. Nothing lost; not worth splitting a one-shot POST.
  2. A broken RPC logs once a minute per idle agy conversation with news, now that the sweep retries. Bounded by news (none, no connect) and by the conversation going non-idle. Acceptable noise for an undocumented RPC that would otherwise fail silently.
  3. Launch fails if the wake can't be recorded. prepare_wake's ? matches Codex's record_agent_endpoint, and a managed launch already requires the server. Consistent, so left.

What stays

Launch-recorded wake file (0600, beside the delivery), port read from --log-file at each wake, token only in the environment, the shared opened-idle writer, the sweep as the single clock, chats and batches never woken. Untested: a wake racing a typed prompt on agy (plan, Remaining 1).

Outcome

Nothing to change in this Task. The plan stands.
