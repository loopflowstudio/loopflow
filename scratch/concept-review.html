Biggest mismatch inside this Task: nested worktrees still hijack the outer Task's open-Graph state

Walk the concrete interaction under the Git-root rule (choice c): Task A owns /src/repo.a. Someone — or a harness worktree tool like EnterWorktree — creates a nested Git worktree at /src/repo.a/.claude/worktrees/exp (or /src/repo/wt/exp when /src/repo is a Task checkout) and runs lf graph code inside it.

Existing (7d8cc0c9) 
1. starting_task_in → checkout_owner_in(nested)
   Git root = /src/repo.a/.claude/worktrees/exp ≠ /src/repo.a
   → records graph_processes.task_id = NULL, cwd = nested root

2. task_open_graph_pairs runs for Task A:
   g.task_id = tw.id
   OR (g.task_id IS NULL AND within(g.cwd, c.worktree))
                             ^^^^^^^^^^^^^^^^^^^^^^^^^
                             TRUE for nested worktree!

Result while nested Graph runs:
- task_state_sql(A)       → 'moving'
- graph_execution_facts   → shows nested run under Task A
- task_open_work(A)       → blocks `lf task run A` & retire
- task_graphs(A)          → [] (contradicts status)
Proposed chosen for review 
task_open_graph_pairs matches taskless runs
by checkout root equality, not path prefix:

  g.task_id = tw.id
  OR (g.task_id IS NULL
      AND EXISTS(SELECT 1 FROM task_checkouts c
                 WHERE c.task_id = tw.id
                   AND rtrim(g.cwd,'/') = rtrim(c.worktree,'/')))

Result:
- Nested worktree's run (cwd = nested root):
  outer Task stays idle, runnable, not blocked.
- Adopted checkout's pre-existing run (cwd = adopted root):
  still blocks overlapping runs (`adopting_a_checkout...`).
- `checkout_open_work` keeps `within`: deleting a worktree
  on disk (`lf land`) still protects nested dirs inside it.

Why exact equality holds for adopted checkouts: lf graph (lf.rs → graph::run) always passes the resolved Git worktree root as cwd, matching what task_checkouts.worktree stores.

Second mismatch inside this Task: lf sync main does not unstack --stack

Existing (7d8cc0c9) 
Stacked Task:    lf sync main → merges main, clears parent_pr_id
--stack checkout: lf sync main → merges main, KEEPS loopflow-base
                  next `lf sync` merges the old base back in
                  next `lf pr open` still targets the old base
                  no `lf` command can clear it
Proposed chosen for review 
In `record_control_task_state` (runs only after sync succeeds,
never on `--plan` or an aborted conflict):
  when target_ref is default or origin/<default>:
    clear `branch.<current>.loopflow-base`

Both stacked Tasks and `--stack` checkouts now detach the same
way: `lf sync main`.
