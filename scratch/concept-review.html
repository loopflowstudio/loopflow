Who can start an agent, and what it is told about who is reading

Concept review for LOO-1119, "Remove the Discord bridge", at e577962da2 against base 472bacbd64.

The area taken: the bridge was the one place a message from someone other than the Machine's own person started an agent. So the review covers that launch path and the three things it left in the code: the prompt's idea of who is reading (Surface), a Wave's own config keys, and the secrets lf strips before starting an agent. The docs that named the bridge are in it too.

One interaction, before and after

Before: a message in the channel

  1. Someone types in the bound Discord channel.
  2. lf discord serve product polls and sees it.
  3. A headless agent starts for the Wave with permissions skipped.
  4. Its final answer is posted back.

Failure: the someone is any non-bot member. Nothing asked who they were; guild_id was never read. Recovery: none short of stopping the process.

After: no message can do that

  1. lf discord serve product → "unrecognized subcommand".
  2. An agent starts only from this Machine's account: a terminal, Desktop, a Task Graph, or an SSH peer that already holds that account.

Failure that survives the merge: an old lf already running the bridge keeps answering, and the token stays valid. Both live outside the repository; see rows 9 and 10.

The bridge treated "a message arrived" as "the Machine's person asked". lf has no type for who asked, and with the bridge gone it needs none: every remaining launch comes from someone who already has the account. Deleting was the smaller and truer fix than an allowlist. The concept comes back the day lf accepts any inbound trigger again (a webhook, a self-hosted server), and it has to arrive before the first such trigger, not after.

The biggest mismatch: six surfaces for one yes-or-no

The plan's own outcome reads "The prompt has two surface contracts, headless and human-present." The type should say the same thing. Taking out Chat alone leaves five names for two answers, three of them built by no launcher.

After the plan as written

pub enum Surface {
    Cli,
    /// Retained for recorded app-launch

    Ide,
    Mac,
    Iphone,
    #[default]

    Headless,

Proposed proposed

    HumanPresent,
    #[default]
    Headless,
}

match self {
    Self::Headless => SURFACE_HEADLESS,
    Self::HumanPresent => SURFACE_HUMAN_PRESENT,

One variant per instruction file, named for it. run.rs picks HumanPresent where it picks Cli today. lf-prompt --surface takes headless or human-present; its two callers (tests/e2e/test_smoke.sh, scripts/evals/instruction_levels.py) both pass headless.

Normal path: an interactive launch gets human-present.md, a headless one headless.md, as now. Failure: an unknown string still falls to headless, the safe side, since a headless agent never waits for a reply. What changes on purpose: --surface cli, mac, iphone and ide stop being distinct spellings and read as headless unless kept as aliases. The counterexample that would break it: a stored value that is read back into this enum. None was found: the store's surface column is the other "surface" (row 4). The check is to drop the serde derives and build; if it compiles, nothing reads one. A second counterexample is the iOS app in progress wanting phone-specific instructions. That would be a third instruction file and a third variant on the day it exists, not two unused names kept waiting for it.

Passed over: leaving the five variants (the plan as written). It is correct in every line and keeps a type that says more than the system knows. Reversible either way; nothing here ships a format.

Questions

1. Should the prompt's "who is reading" have two values or five?

Nothing a person sees changes either way: an agent is told "someone is here" or "nobody is here".

  • 1a. Recommended. Two: present and headless, in this change. The names Mac, iPhone and IDE disappear from the code until one of them needs different instructions.
  • 1b. Five: remove only the chat one now, and file the rest as its own Task.
  • 1c. Five, and leave it: the Mac and iPhone names are wanted as placeholders for the apps.

2. When does the Discord bot's token get revoked?

Today lf removes that token from an agent's environment. After this merge it does not know the name, so any doppler run -- lf … launch passes the token to the agent for as long as the token works.

  • 2a. Recommended. Before the merge: revoke the token in Discord, delete LF_DISCORD_TOKEN from Doppler, remove the bot from the guild. The PR then lists them as done. Revoking can't be undone, and nothing still needs the token.
  • 2b. After the merge, as the plan has it. Between the two, agents started under Doppler can read a working bot token.
  • 2c. Keep stripping the name in lf until a follow-up removes it. This keeps a Discord name in the code that the Task says is gone.

3. How should lf treat a Wave config that still has a chat: block?

About 111 worktrees of this repository carry one until they take the merge. The plan already chooses silence over a warning on every command; the open part is only how the code says so.

  • 3a. Recommended. Silent, in a list of its own: retired Wave keys (linear, chat), each naming the Task that deletes it, apart from the one key a Wave really owns (id).
  • 3b. Silent, as planned: chat beside linear in the existing list, with a comment.
  • 3c. Let it warn. Each stale checkout says "skipping chat: unknown setting" until it is updated; no ignored key and no removal Task to carry.
