The biggest mismatch

The branch made one type for showing an agent a change, then delivered it two ways. Where it is put in the prompt, a cheap model read the right file every time. Where it is put in a file, the model never opened it. Same section, same model; the only variable is whether lf showed it.

Before (in the branch)

lf commit            prompt: "## Change" + section
lf pr submit         prompt: "## Change" + section
--diff patch         .lf/prompts/…-changes.md
                     context block: its path
attribution          Diff asset: absent
                     StatOnly decision: recorded

After (proposed)

lf commit            prompt: "## Change" + section
lf pr submit         prompt: "## Change" + section
--diff patch         first turn: section, after the
                     request, beside -c and --docs
attribution          Diff asset: Task channel
--diff files         changes file as on main: paths

Why this and not the alternatives

  • The size is already bounded. The section is the file list plus at most 15,000 tokens of patch. --docs bodies go in the first turn with no bound at all.
  • It is asked for. --diff patch and context: {diff: true} are off by default and no builtin Skill sets them. Someone who turns one on wants the agent to have it.
  • It is no more frozen than today. The file is written once at launch; so is a first turn. The read command in the section is how the agent gets the current state either way.
  • The code gets smaller. ContextDelivery::prepare loses its three-way match and goes back to what it does on main for diff_files; attribution starts telling the truth with no edit; the docs lose the caveat.

Larger than this work

  • The Task workspace block is a second "change as shown to an agent". It would take a fourth ChangeRange (base against worktree, untracked included, which Uncommitted now half does) and a per-file state. Then a worker with diff: true would get one section.
  • gather_branch_change treats only a branch named main as the default branch while asking Git for the default branch two lines later. On a repository whose default is trunk, --diff patch there reads origin/trunk...HEAD and finds nothing, so no harm, but main on such a repository is skipped as a feature branch. Unchanged by this branch.
  • --diff patch on a branch with commits shows committed work only. Uncommitted edits on top are absent. Documented. The fourth range above would close it.
  • lf task diff's 1 MB whole-comparison cap (ops/task/snapshot.rs): a person-facing read; its fix is a per-file read in the served API.

Questions

    1. In the first turn, after the request, as --docs and -c are. Chosen for review.
    2. A listed file, as built. The flag stays cheap and does little.
    3. Take context: {diff: true} back off Change and leave the old stat; ship only the writers.
  2. docs/config.md used to say "Point to Git inspection commands rather than inlining a frozen patch". Did that sentence mean:
    1. never put patch text in a prompt, in which case 1a is wrong and the section should carry only the list and the command for Skills;
    2. don't rely on it staying current, which the read command covers.
  3. The PR writer follows yolo; the commit writer always skips permission prompts.
    1. Leave both. Chosen.
    2. Give the PR writer the same floor.
  4. The size rule: 15,000 tokens for every caller. Chosen before code; the runs gave no reason to move it.
    1. Keep.
    2. 100,000 bytes for the writers only.

    1. Keep. Chosen.
