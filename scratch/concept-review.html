2. The Biggest Mismatch — Before, Kickoff Plan, and Recommended

Biggest mismatch The kickoff plan silences an idle server, but on a working Machine it still re-runs 30 × 15-statement inventory projections twice a second — including for 25+ terminals nobody is looking at.

scratch/plan.md's own measurement on a live working Machine shows sessions advancing ~2 times/second (+20 in 10 s) whenever even a handful of agents are running. Because the plan sweeps every hosted terminal (viewed or not) one by one through output_title → session_summary, normal work still triggers ~60 full SessionSummary reads/sec (~900 SQL statements/sec) — and each local cmux/tmux viewer still opens its own SQLite connection to compute the same title again.

4. Counterexamples & Failure Modes Checked

1. Continuous text streaming delays the 120 s quiet deadline without moving sessions. store_revision_session_activity_update deliberately ignores observed_at bumps while open_tools = 0 and delta < 120 s (0.14.7.001_release.sql:12). If an agent starts streaming at t = 1000 and finishes at t = 1030, TitleReader's initial deadline is 1120. When 1120 fires, 1120 - 1030 = 90 < 120, so the title string does not change — but the new deadline is 1150. Rule: TitleReader must update each terminal's stored next_deadline on every successful read, even when the title text is unchanged.
2. Transient SQLite lock or error during a rename leaves the tab stale forever if look is consumed. If store-observer notifies TitleReader that sessions moved 41 → 42 and the read fails with SQLITE_BUSY, dropping the error and waiting for "the next look" loses the rename if the Machine then goes quiet. Rule: advance seen_revisions only after a sweep succeeds; on error, retry on bounded backoff (1 s → 30 s) without holding any connection open.
3. A fresh terminal starts before its child calls bind_session_terminal. When Hosted::new runs, agent_sessions.held_terminal_id is not yet linked. The first read returns None; moments later bind_session_terminal updates agent_sessions, firing store_revision_agent_sessions_update (OLD.fence_locator IS NOT NULL), which moves sessions and wakes TitleReader to publish the first title.
4. Fresh server with no loopflow.db yet must not spin StoreChanges at 100 ms. When the WAL file doesn't exist, StoreChanges::wait_with_history sleeps 100 ms per loop (changes.rs:123). Keeping TitleReader unsubscribed from store-observer until ≥1 terminal is actually watched avoids waking an empty server 10×/sec (and creating any held terminal already initializes loopflow.db).
5. revision_map() reparses history.history_revision on every wake. sqlite/revisions.rs:110 uses prepare_cached for store_revisions, but line 115 uses uncached conn.query_row for SELECT revision FROM history.history_revision. Switching that one query to prepare_cached removes reparsing from every store-observer, recovery-wake, and viewer revision check.

5. Is the Plan's First Slice the Right One?

First-slice verdict Pass 1 has the right boundary, but four details should change before coding starts.
  • Keep in Pass 1: event-driven TitleReader registry + store-observer wake + quiet availability deadline + host waker + bound now in available_sql + prepare_cached across the title and revision paths + focused tests (including the streaming-deadline and lock-recovery counterexamples).
  • Change in Pass 1: (1) borrow 1 pooled read-only store per sweep instead of pinning a private connection; (2) generalize watch_planning to watch_revisions instead of adding a title-specific list to read_stream; (3) watch viewed terminals only (if Q2a) and batch the slim title read (if Q3a) so busy-Machine sweeps don't stay at 30 × 15 statements; (4) cache history.history_revision in revision_map().
  • Pass 2: viewer titles (either server-pushed Event::Title if Q1a, or inline revision gate on TerminalTitle::refresh if Q1b) plus the held-terminal phase in scripts/benchmarks/server_idle.py covering both idle detached terminals and a busy-write sweep.

7. Open Questions

Every question below can be answered directly (e.g. 1a, 2a, 3a). Nothing here has been built yet; all choices are reversible, except 1a includes a one-time held-terminal protocol revision bump (existing views reconnect automatically after upgrade).

1. When you view a held terminal in cmux or tmux — locally or on a remote Machine — should the server send its tab and workspace titles over the terminal stream instead of each viewer reading the local database?
  • 1a (Recommended): Yes — the server computes the title once and sends it to attached viewers alongside terminal output. Local cmux/tmux tabs stop touching SQLite completely (zero per-tab polling), and remote lf --machine sessions in cmux/tmux gain live tab and workspace renames too. Trade-off: bumps the held-terminal wire protocol version once (4 → 5), so open views re-exec once after installing the new build.
  • 1b (Kickoff plan): Keep local cmux/tmux viewers checking SQLite's revision counter every 500 ms (lightweight when quiet, skips full reads unless something moved), leave remote cmux/tmux renames unsupported for now, and avoid a wire protocol version bump in this PR.
2. When dozens of background conversations are running with no tab or pane open on them, should Loopflow skip refreshing their titles until you open one?
  • 2a (Recommended): Yes — refresh titles only for terminals that currently have at least one viewer attached, and fetch the fresh title immediately when a viewer opens a parked conversation. Active work in one tab never triggers title reads for 25 hidden ones; opening any parked tab still shows its up-to-date title within a fraction of a second.
  • 2b (Kickoff plan): Refresh titles for every hosted terminal on any Session, Task, or Graph change even while no viewer is attached, so the server's retained screen always carries the latest title before a viewer connects.
3. During active work with multiple open tabs, how far should this PR slim down the title database read itself?
  • 3a (Recommended): Add one focused, batched title query that reads only the four fields a title uses (Session name, Task label, availability + quiet deadline, waiting Graph step) across all watched tabs in a single pass — sharing the exact same availability rule so labels never drift, while cutting busy-Machine database work by ~10–50×.
  • 3b (Kickoff plan): Keep calling the existing per-Session full summary reader in a loop with cached SQL statements, measure whether 30 terminals × 2 sweeps/sec stays under 1% CPU, and slow title updates from 500 ms to 1 s if it doesn't.
