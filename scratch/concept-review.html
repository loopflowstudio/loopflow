The mismatch

Under lf, a Process and the OS process that ran it end together. In Desktop, a write's Process ends when the call returns, but Desktop keeps running. The journal still assumes the first case.

Existing behavior. with_runtime admits the Process, runs the write, then finishes it. If the write panics, the unwind skips the finish and the FFI turns the panic into an error. The app shows the error, but:

Left behindWhat you'd see
A started Process with Desktop's PIDIt counts as running until Desktop quits, so it shows up as live work in the Task's checkout
THREAD_CONTEXT on the calling threadLater writes on that thread look nested and record no Process
LF_PROCESS_ID / LF_TRACE_ID in Desktop's environmentThe next in-app Process gets the dead one as its parent

Proposed. When an in-app write unwinds, it ends its Process as Errored with the panic message and clears its context. The record then reads like an lf that panicked. The Process identity lives only in the thread context, never in Desktop's environment, which also removes the setenv race. If a write starts an lf child, the identity goes on that child's command.

Proof: a write that panics leaves an Errored Process, no exported identity, and the next write records its own Process with no parent.

Checked and fine

Desktop's environment already drops inherited Work-process variables at launch (enrichProcessPathForGUILaunch). So in-app reads and writes start from the same environment Desktop's lf children had. That question is closed.
