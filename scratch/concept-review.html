2. The biggest mismatch: two competing remote-workspace architectures

What was wrong in both the code and the first draft of scratch/plan.md: The Loopflow server already routes writes (task.run, task.auto.*, session.resume) and task.status to a Task’s owning Machine over Connection::open_on. The original plan proposed extending that server forwarding (plus terminal ticket bridging) for Mobile, while keeping Desktop on its older client-side RegistryQuery.onMachine stack (which spawns lf --machine CLI subprocesses over SSH and wraps every call in two extra ssh lf task location probes). Keeping both guarantees drift, extra SSH roundtrips, and split-brain failures like MTG-421 (remote Session + local Mac shell).

  • Desktop and Mobile use different transport mechanisms for the exact same Task operations.
  • Every remote file read in Desktop pays 3 SSH roundtrips (location + read + location).
  • A stale local worktree row overrides Task ownership in Desktop’s sidebar and shell launcher.

After · One server-side Task router

Proposed in Plan
Desktop (Mac) ──┐ ├──► Local / Paired Server (Unix / WS) Mobile (iPhone) ┘ │ checks Task owner in SQLite (µs) │ + optional expected_machine pin ▼ pooled Connection::open_on (SSH) Owning Machine Server (Modal) ├─ Read: task.files / file / changes │ task.diff / get / detail / status ├─ Write: task.save / run / auto / resume └─ Term: session.attach / continue / start & Task shell (bridged ticket) CLI (lf open) ├─ Always presents on calling Machine (never remote) ├─ --task X [--session S] ──► routes via Task owner └─ --machine M --session S ──► local tab, attaches on M
  • One router: Desktop and Mobile call the exact same server operations (serve(.taskFiles/File/Changes/Diff), write(.taskSave), terminal tickets).
  • Deletes client-side RegistryQuery.onMachine CLI fanout and double-SSH pinTaskLocation for Task views.
  • Safer moves: RoadmapTask reports actual ownership; server checks optional expected owner in SQLite and returns instant conflict on moves while Desktop preserves unsaved drafts at their original (machine_id, checkout).
  • Honest failures: unreachable owner → unavailable (never local fallback); unstarted Task → explicit “not started”.

3. Three other structural alignments

Wave adoption vs. Wave authoring

Simplified in Plan

Existing connect_async calls wave_lifecycle::add → creates stray local tracker_id: null Project and commits normalized YAML to main.
Original plan Separated adoption from authoring, but introduced a rental-only “carried selection” side channel.

Proposed Cold acquisition is read-only on Git files and binds the sole In Progress Linear Project from a complete Initiative inventory (leaving ambiguous/offline Waves unconfigured with available choices). When a Wave genuinely has multiple In Progress Projects and the source Machine chose one, rental prepare runs the existing public lf wave plan bind command — zero hidden side-channel state. Explicit --replace (compare-and-replace) repairs previously misselected Waves without deleting history.

Atomic handoff & container-ready Linux

Proposed

Ownership: Replace hand_off’s two-step Claim (Mac) + Move (Modal) with one atomic ownership entry naming the target Machine, written only after remote repo bind & server readiness.

Containers: Drop systemd & cron preconditions — installation/server.rs::ensure falls back to detached lf server run under the same lock/socket check when no user bus exists; lf install reports unscheduled updates and returns 0 when crontab is absent; binaries::report_before_promote inspects pre-migration stores without forcing post-migration indexes.

Modal burst sizing, harness fallback & login sync

Proposed

Sizing: Add Modal-only reserved: bool to Hardware (default false: floor 0.125 core / 128 MiB, ceiling --vcpus/2 / --memory-gb*1024). Keep worst-case ceiling for admission/cap/timeout; label uptime-derived cost explicitly as a ceiling estimate in CLI and JSON.

Execution & auth: Resolve skill/Session harness against remote availability + native login (keeping -a exact and established threads intact); make missing executable/login quiescent in ops/recovery.rs. Add lf machine forward <label> [--task <id> | --session <id>] for atomic overwrite + opt-in targeted restart.

4. Concrete walkthrough: normal path, failure & recovery

Tracing the field scenario (manabot, Wave coverage, Project rules, Task MTG-421, with a stale local Mac checkout and binary scratch/._plan.md):

STEP 1 · RENT & PROVISION

lf task run MTG-421 --rent modal

Quotes burst ceiling ($0.95184/h cap), creates Modal sandbox with cpu=(0.125, 4), memory=(128, 16384), transfers caller’s Linux lf build (no remote GitHub auth needed), promotes cleanly over any older store, verifies detached lf server run ready without systemd.

STEP 2 · ADOPT & HAND OFF

Clean main, one ownership entry

Clones repo, binds repo_id, cold-acquires Wave coverage and sole In Progress Project rules (zero local stray Project, zero main commits). Writes one ownership entry naming modal-1. If setup failed earlier, sandbox is deleted and MTG-421 stays unowned.

STEP 3 · RUN & ROTATE LOGIN

Codex selected, ._plan.md skipped

Personal agy is absent on Modal → resolves installed, authed codex before stamping Session; skips binary scratch/._plan.md. Later when Codex auth expires: lf machine forward modal-1 --task MTG-421 atomically refreshes ~/.codex/auth.json and restarts only that Session.

STEP 4 · OPEN ON CLI, DESKTOP, MOBILE

All four views reach modal-1

Stale local Mac checkout exists with different bytes, yet RoadmapTask reports owner modal-1. Desktop & Mobile both query the local/paired server → pooled Connection::open_on to modal-1 serves Files, Changes, Diff, held Shell, and bridged Session. lf open --task MTG-421 --tab attaches cleanly in Rex.

STEP 5 · OWNER MOVES OR DROPS

Honest failures, drafts preserved

If modal-1 disconnects, Files/Changes/Shell/Session report modal-1 unavailable (never an empty diff or local Mac shell). If MTG-421 moves to another Machine, expected-owner checks return conflict, stale panes invalidate, and unsaved drafts stay at their original checkout.

STEP 6 · GIVE BACK

lf machine end modal-1

Because main was never dirtied, normal lf machine end modal-1 (no --force) copies up Session/Process records, terminates the sandbox, returns held Tasks locally, and prints cost labeled as a ceiling estimate.

5. Choices made for review & open questions

None of these choices are irreversible once shipped, so the bold defaults are written into scratch/plan.md and highlighted below. Reply with a number and letter (e.g. 1b, 3a) to change any choice.

1. How should Desktop reach remote Task Files, Changes, Diff, Save, Shell, and Session?
  • 1aChosen in plan Unify Desktop and Mobile through server-side Task routing over pooled Connection::open_on (and delete Desktop’s client-side RegistryQuery.onMachine / double-SSH pinTaskLocation for Task views).
  • 1b Keep Desktop on client-side RegistryQuery.onMachine + SessionsView.swift owner resolution, and build server forwarding only for Mobile (original kickoff plan).
2. How should a fresh rental bind a Wave’s active Linear Project when ambiguous?
  • 2aChosen in plan No rental-only side channel: cold acquisition binds the sole In Progress Linear Project on any fresh clone; when multiple In Progress Projects exist and the source Machine selected one, rental prepare calls the existing public lf wave plan bind command.
  • 2b Add a carried Wave Project selection carried across rental preparation and recovered on fresh clones before checking Linear.
3. What should Modal’s default burst floor be?
  • 3aChosen in plan Modal’s published minimum: 0.125 core and 128 MiB (bursting up to --vcpus / 2 and --memory-gb * 1024; --reserved pins floor = ceiling).
  • 3b Higher idle floor of 0.25 core and 256–512 MiB to leave extra resident headroom for lf server + sshd before bursting.
4. How should lf open treat --machine <label> for a remote-only Session?
  • 4aChosen in plan lf open always presents on the calling Machine: both lf open --machine <label> --session <id> --tab and lf --machine <label> open --session <id> --tab open a local view attached to <label>.
  • 4b Keep root lf --machine <label> strictly “run remotely” and add a distinct subcommand flag (e.g. lf open --session <id> --from <label>) for remote-only Sessions.
5. How should lf machine forward <label> target a stuck Session for restart?
  • 5aChosen in plan Opt-in targeted restart by Task or Session: lf machine forward <label> [--task <id> | --session <id>] overwrites configured forward.files atomically and restarts only the named Session (or that Task’s primary Session) on <label>.
  • 5b Accept only --session <id> (requiring the remote Session ID).
  • 5c Restart every running Session of the rotated provider on <label> automatically after forwarding.
