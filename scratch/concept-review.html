Do the product's concepts and the code's concepts line up?

Task 8b92c6, reviewed before anything is built, against scratch/plan.md at d8802dd4cb and swift/LoopflowMac on main at 0fa6a4e202.

The area taken: every Mac screen where a person looks at a Wave and the Tasks in it. That is the Wave's backlog, the Portfolio's roadmap, Now list and Wave page, and a dashboard. The Task asks for those screens to follow DESIGN.md, and its plan is a styling pass. The review asks what the screens say, since the same type on seven different sentences is still seven sentences. Choose Theme, Settings and the spacing sweep are in the plan and are not reviewed here beyond one row in the table: their concepts are sound.

Outcome: the plan changed. Short version: a Task's row is drawn four ways today, and the plan folds them into TaskRow. But the row is the smaller half. Where a Task stands is said seven ways from six sources, and TaskRow as built cannot say it in the Portfolio at all. The plan now builds that answer once and makes it the first slice.

"Working", "idle", "blocked", "open", "next: user" and "at human-review" all describe one Task at one moment. Each is true in its own vocabulary. A person has to learn that Working is a board section, idle a lifecycle, blocked a condition and open the tracker's state, and none of that learning buys anything: the question was "does this need me".

The failure. The sidebar row, the one built to DESIGN.md, says only "Idle". It prints a second line only when a program reports Blocked. This Task's Graph stopped; no program is running to report. The best row is the one that hides the problem.

The recovery. In the Now list a click opens the Task. On the Wave page a click selects it; an inspector appears under the metric table, possibly off screen, and its "Open Task workspace" button exists only if the Task has a checkout. In the backlog a click selects for the action bar. Three meanings for a click on a Task, two of them in one window.

What the plan did with this. It replaced the three Portfolio rows with TaskRow "fed the way the sidebar feeds it", and said "the Task row's status word carries what three capsules did". It does not. The Portfolio rows hold a RoadmapTask and no Session readings; TaskRow would print "Idle" and drop "Graph stopped at human-review". The Now list is grouped by that reason. It would have become a list of Tasks that all say Idle.

The biggest mismatch: where a Task stands

Existing, and in the plan as written

The plan deleted three rows and the capsules, and kept the sidebar's rule as the only one. That rule knows nothing about condition.

Proposed. TaskStanding, built once

A word, its tone, its tooltip, and an optional line. One function, from a RoadmapTask? and a SessionProgramStatus:

  1. A program that reports: its label. Reported Blocked keeps its own word.
  2. Session readings unavailable: no word, the info mark, as now.
  3. Else a blocked or waiting condition: "Blocked" or "Waiting".
  4. Else the lifecycle. An unknown condition adds no word.

The line is the program's ask, else the condition's reason when it is not clear. That is the rule the Brief already uses.

TaskRow draws it and stops choosing. A screen with no Session readings passes .unknown and still gets rules 3 and 4.

Tested on three paths

  • Normal. A Task is running. Sidebar: "Working" from the program. Portfolio, with no Session reading: the lifecycle word. Same row, less evidence, nothing invented.
  • Failure. The Graph stops and no program is alive. Every row says "Blocked" and why. Today only the Portfolio does, in capsules.
  • Recovery. Click the row, the Task opens, the workflow line says who is needed. One gesture.

Counterexamples kept

  • A program reports Working while the condition is blocked. The word is the program's, the line is the condition's reason. Two sources on one row; they can disagree for a moment. Accepted: both are true and the line is the one that asks for a person.
  • The sidebar gets taller. A blocked or waiting Task gains a line there. DESIGN.md wants a row that needs someone to say so; "waiting" may not always mean a person. Question 1.
  • What the inspector showed. Provider name and checkout path as text are gone from the Wave page. Both are in the workspace the click opens. Question 2.
  • The tracker's own state ("PM open") is no longer on any row. It was a third copy of done or not done; a Task done in the tracker and not in Loopflow is the case it could have shown, and no row called that out before either.
  • Swift decides the order. The repository's rule is that a sentence shown by CLI and Desktop is written in Rust. A program's report never reaches RoadmapTask, so Desktop is the first place the two meet, and the CLI prints no merged row. Question 3.

What changed in the plan

  • New section, "Where a Task stands, said once": TaskStanding, its four rules and its line. Not a component; it is what TaskRow already works out inline.
  • TaskRow gains an initializer from a RoadmapTask. The claim that the Portfolio feeds it "the way the sidebar does" is gone.
  • A click on a Task opens it on every Portfolio screen. WaveWorkInspector is deleted, where the plan had only removed its fill.
  • The backlog's standing leads with the same word; its key results use WaveProjectView.
  • The title bar prints the standing's word, so it agrees with the selected sidebar row.
  • The first slice moved. It was the spacing test on the backlog. It is now the standing and the one row in all five hosts, because that is what can fail: one row in a 240 pt sidebar, a third-width tile and a full-width roadmap, and a blocked Task reading as blocked with no Session behind it. The spacing table is slice 2.
  • Two things are named as outside this change, below.

Outside this change

One page for a Wave. A Wave has two pages that share no header and disclose the objective two ways. One page would mean the Portfolio opening a Wave in its repository window, as it already opens a Task, that view gaining finished Tasks and the metric table, and WaveDetailPane going. It changes what the Portfolio window is for.

Workflow position on a list row. The planning wire would carry TaskGraph.sentence on each RoadmapTask, so the backlog and the roadmap say the sentence the Task's page says. Rust, the DTO fixtures, and BacklogList.standing then goes entirely.

Questions

  1. Should a blocked or waiting Task's reason show on its sidebar row? Chosen: (a).
    1. Yes, the same line everywhere.
    2. Only for blocked; waiting gives the word and no line.
    3. No; keep the reason to the Portfolio and the Brief, and accept that the row differs by screen.
  2. On the Portfolio's Wave page, what does a click on a Task do? Chosen: (a).
    1. Opens the Task; the inspector is deleted.
    2. Selects it and shows the inspector, as today, restyled.
  3. Who decides the order of program report, condition and lifecycle? Chosen: (a).
    1. Swift, in TaskStanding, in this change.
    2. Rust: planning carries one standing, and lf task list prints it. A wire change, its own Task.
  4. "Available" counts Tasks you claimed. Chosen: (a).
    1. Leave it: available to you.
    2. Make it mean unclaimed, so All = Mine + Available + someone else's.
  5. Does a Wave keep two pages? Chosen: (a).
    1. For this change, yes; both get the serif name.
    2. File the one-page Task now, and give only the repository view the display step so the two do not read as one.
  6. Is the backlog's row a second kind of row, or should it be TaskRow with a checkbox? Chosen: (a).
    1. A second kind: ID first, one line, as the prototype draws it.
    2. TaskRow, title first and in full, at the cost of a taller list.
