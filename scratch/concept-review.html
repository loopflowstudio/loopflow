What happens when a cached frame points to a deleted worktree?

Decision needed. B can reuse A’s library and report B’s runtime identity correctly, yet still look for source in A. The probe observed those paths; source-debugger recovery has not been demonstrated.

Before → implemented prototype → proposed experience

Before: shipping edits rebuild one large application crate. Installed sccache 0.19.0 misses on identical Rust code in another root.

Implemented: private model and definition-content libraries; native packages replace registry publishing. An isolated newer-cache probe hits in B, misses on a semantic edit, and keeps runtime checkout identity correct.

Proposed, unbuilt: ordinary fresh-worktree builds reuse the larger stable libraries with automatic root upkeep and a defined source-debugging experience. Whole-build time and CPU savings remain unmeasured.

No new Task/store lifecycle. Keep one shared cache daemon and independent worktree targets. Runtime provenance stays with the application.

Normal path, failure, recovery

A builds; unchanged B hits. Change a model value: B misses. Delete A: B’s cached debug paths can go stale. Mapping every path to B can show the wrong source if B has since changed. Recovery must address the exact compiled bytes, including generated source.

The private probe also proves fresh-target reuse after root refresh. It does not establish shared-daemon integration; LOO-908’s recorded completion supplied none. Unknown roots may compile normally while refresh waits for idle builds.

1. Required debugging experience

  1. Find exact compiled source automatically after the producer checkout is removed. Requires a source mapping/retention design.
  2. Allow documented manual debugger mapping to matching source. Adds a recovery action for developers.

Neither is selected. Answer 1a or 1b. Until resolved, keep automatic reuse experimental; the original Task outcome remains open. Next demonstrate source recovery, then ordinary root upkeep and whole-build measurements.
