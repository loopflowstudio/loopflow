      Failure, recovery & counterexamples checked

      Task has one Working Session and one Idle Session
      Mac and iOS rows both display Busy. Sort by status places it in Busy so no Busy row sorts above Idle. Both state:available and state:busy filters still include it.
      Task has Blocked + Error + Busy reports
      Blocked outranks Error, Busy, and Available in row display and sort bucket (0). If Blocked clears while Error remains, the row reads Error and sorts in bucket (1).
      Build or provider emits OSC 7501 error, then person types
      Error renders red on Mac and iOS, enters attention, and sorts behind Blocked. Typing dismisses error via acknowledge_results / ProgramStatusReducer.interaction; saved order stays put.
      Drag Task C above A, Machine blips 1 s, person clicks Sort by status
      Both writes sit in PendingChanges with distinct requestIDs, serialized in orderWrites so the drag lands before Sort. Once Sort is queued, workingOrder stops replaying the pre-sort drag preview; a drag made after Sort previews immediately.
      Machine is offline >10 s (Link.away)
      Sidebar and ⌘K Sort by status controls disable and return PendingChanges.awayText if invoked. Minor asymmetry noted: sidebar/grid drags are not disabled while away and instead queue in PendingChanges until reconnect (consistent with other non-button drag gestures; no data loss).
      Task leaves Working (completed/unclaimed) and later re-enters
      Counterexample noted: task_orders prunes departed Tasks on the next drag or sort, not on completion/unclaim, and started_at uses first claim (MIN(o.at)) so Machine handoffs keep original start time. Reclaiming a Task before any drag/sort keeps its prior slot rather than prepending.
      Graph parked at start or finished at end
      fill_task_contents_in filters START and END to None (matching TaskGraph::read). While running (run_start set), it resolves the live cursor step name via CapturedGraph::step_name_of.
      Task blocked by Graph/git condition with no live terminal report
      Boundary noted: TaskCondition::Blocked (e.g. missing worktree or merge conflict) is derived during full roadmap snapshots, not in SQLite selection reads. SelectionState::Blocked reflects program/session reports only.

      Choices built for review

      These three product choices were made for review and are built as option a at eca5ec7bef. All are reversible. Reply with e.g. 1b to change any choice.

      1. When a Task has one Busy Session and one Available Session, where should Sort by status place it?
        1. Match the row’s own status word (Busy → bottom bucket). Built: both Mac and iOS rows print Busy, so sorting it as Busy prevents a Busy row from sitting above Idle. Both Available and Busy filters still include it.
        2. Sort Available ahead of Busy, and change Mac/iOS row display so dual-state rows print Available instead of Busy.
      2. How should OSC 7501 error sort in Sort by status?
        1. Project SelectionState::Error and sort Blocked → Error → Available → Idle → Busy. Built: matches ProgramStatusState.summaryOrder, keeps failures above Available, and brings red Error status to iOS too.
        2. Merge Error into the Blocked bucket without adding a new SelectionState variant (leaves iOS unable to distinguish Error from Idle).
      3. Should Sort by status guess a local preview before the Machine replies?
        1. Route through PendingChanges without a guessed preview, superseding pre-sort drag previews. Built: ViewContent does not carry started_at, so a client preview would guess within-bucket order and flicker when the Machine answers. Routing through PendingChanges still gives blip retry, offline disable, and click-ordered reconciliation with drags.
        2. Carry started_at on ViewContent so the client can compute an exact instant preview of Sort by status too.
