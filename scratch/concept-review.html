The two closures

  • Export before a contract. Called with the transaction's connection and the guard list, at the same point in the migration order. The application passes config::migrate::preflight as it is. The exporter already owns a raw connection in lf config migrate.
  • Process evidence. Storage keeps the canonical-ID scan and the Session fence try-locks, and asks for ProcessIdentityEvidence per affected row. journal keeps producing it. Anything but Dead defers with today's message.
  • Both are required arguments. Storage's own tests pass closures; the application's wrapper and open path pass the real ones.
  • Storage holds the guards through commit or rollback. The pure SQL checks stay where they are.

Normal → failure → recovery

A store from before 0.16.0 opens under a new lf. Storage takes the migration lock and the exclusive transaction, reaches settings_authority, and calls the exporter: it reads the old tables, writes settings-cutover.json, then the preference files. The SQL runs and commits. Power fails after the file writes: SQLite rolls back, the journal and files remain. The next open exports the same source, matches the journal, finds each file at its before or after bytes, finishes and commits.

What still refuses, as today: after that interruption an old lf changes a setting before the retry. The probe showed exit 1, migration inputs changed; preserved recovery evidence is at …/settings-cutover.json, with config.yaml still holding the first value. A recovery for it was drafted and is outside this Task.

What must hold

  • The journal source string stays byte-identical, or a cutover interrupted under released 0.16.0 turns into “migration inputs changed”.
  • An in-memory store refuses a non-empty export. Preview skips the cutover.
  • Unknown never becomes Dead. A busy Session fence defers without waiting.
  • Earlier migrations in the same transaction have reshaped the schema before the exporter reads it.
