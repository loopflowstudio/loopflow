Area reviewed: How a repository without Linear or Asana decides whether a clone has read its shared plan, runs its initial carrier exchange (Git and Hub), handles offline failures, and delivers that arrival across every plan-reading and Task-lookup surface — CLI reads, single-Task reads, subscriptions, and served requests (sqlite::plan_carriers, ops::plan_carriers, ops::plan_git, ops::plan_hub, ops::planning_sync, commands/{waves,screens,tracker,desktop}.rs, bin/lf.rs, server/service.rs).
Why this whole area: Pass 2 (b9ab216a14) fixed the dual-carrier regression and moved before_first_read out of lf.rs into the read entry points. Probing all 13 plan and Task read commands live on a brand-new Machine against HEAD confirms the core clone-level gate works — and exposes two remaining mismatches (lf wave show silently returning empty on a brand-new Machine because carried() refuses when loopflow.db does not exist yet, and lf task show <id> still failing on unread clones beside task status and task detail), plus a 1-line cooldown bug when an offline Hub sits beside a healthy Git remote.

3. The Biggest Remaining Mismatch in HEAD — Before & After

The core mismatch in HEAD: plan_carriers::carried() (and exchange_after_command()) treats "does ~/.lf/loopflow.db already exist on disk?" as a gate for whether a clone can fetch its remote plan. On a brand-new Machine, that makes first-read arrival depend accidentally on whether the CLI command passed through journal::admit_process() — so lf plan list works while lf wave show (calling the exact same show_snapshot function!) silently returns empty.
Built in HEAD (plan_carriers.rs:389–396) Built in HEAD
lf wave show → planning_read (skips admit_process)
before_first_read → carried(): !path.exists() → Ok(None)
show_roadmap → store is None → waves: [], tasks: []

The bug is invisible on any developer Machine that already has ~/.lf/loopflow.db from another repo, and only hits a real newcomer cloning their first repo — the exact "zero setup on a second Machine" path docs/work.md leads with.

Proposed: Check for a Carrier, Not an Accidental DB File Recommended
tracker::connected(&repo)? → yes: return Ok(None)
!path.exists() && remote.is_none()? → return Ok(None) (no DB created)
else: open_sqlite(&path) → first_read_at fetches remote plan

Counterexamples checked:
• Local-only repo (no remote) on a brand-new Machine: remote.is_none() → creates no DB, returns empty in 0 ms.
• Linear/Asana repo: tracker::connected is true → creates no DB.
• Git repo with remote on a brand-new Machine: opens DB, fetches remote plan, marks seen_seq = 0 → lf wave show prints remote Waves & Tasks on try #1.
• Hub-only (--bind): binding already created loopflow.db, so path.exists() is already true.

4. All Findings & Scope

F1. Let carried() and exchange_after_command() open the store when a Git remote exists This work (LOO-1113)

In plan_carriers::carried (plan_carriers.rs:389) and exchange_after_command (plan_carriers.rs:462), return early when !path.exists() only if the repository has no Git remote (plan_git::remote(Path::new(&repo)).is_none()). Otherwise open the store and run the first read. This fixes lf wave show on a brand-new Machine and eliminates the accidental dependency on journal::admit_process().

Test to add: In local_planning.rs, run lf wave show --json as the very first command on a brand-new LF_HOME against a clone of a remote holding Wave alpha and Task A; assert both appear.
Passed over: Routing lf wave show through admit_process() (adds process-admission overhead to a read intentionally exempted from it, and leaves served after_command broken). Reversible.

F2. Sync on miss in lf task show <id> (and recheck peer route after sync in task detail) This work (LOO-1113)

lf task status <id> and lf task detail <id> both sync via planning_sync::find_task when a Task is missing locally; lf task show <id> (desktop::read_task_pane) still fails with Task <id> is not registered. Giving read_task_pane the same non-served find_task miss fallback (or sharing one helper with screens::task_detail) closes the gap across all three single-Task reads. For Read::TaskDetail, re-checking peer_route() if a local miss was resolved by sync (or running miss resolution before peer_route) also avoids a local-only first response for Tasks owned by another Machine.

Passed over: Leaving lf task show store-only (forces people to learn an arbitrary difference between lf task detail <id> and lf task show <id>). Reversible.

F3. Gate the 60 s first-read cooldown only when every eligible carrier is in error This work (LOO-1113)

In plan_carriers::first_read_with (plan_carriers.rs:326), change errored from git_errored || hub_errored to (!has_git || git_errored) && (!has_hub || hub_errored). When Git has no error (fresh, or just cleared by a successful lf task create push), an offline Hub's leftover error will neither suppress Git for 60 s nor write an unused row to planning_scope_checks.

Test to add: In plan_hub.rs, stamp plan-first-read:<repo> at t=1000 with Hub errored and Git clean (simulating a recovered Git push while Hub stays offline); call first_read_with at t=1025 and assert Git runs and marks the clone read. Reversible.

F4. Confirm --subscribe on unread clones (store-only vs background first-read) This work (LOO-1113)

HEAD keeps all 5 CLI --subscribe commands and server Start::Subscribe streams store-only (and docs/dev/planning.md:299 now says so plainly). That keeps frame 1 instant and read-only, while an unread clone opened directly via --subscribe stays empty until a one-shot read or lf task sync runs. Open in Question 2.

F5. Discovering a teammate's very first Task in an already-read empty clone Separate outcome

A clone whose first read saw an empty remote marks has_read() == true; LOO-1110's exchange_unowned skips repositories with zero open Tasks and zero active Waves, so a teammate's later first Task arrives only on lf task sync or a lookup by ID. docs/work.md and docs/dev/planning.md document this accurately.

What it would take: A separate Task to poll empty-plan repos at low frequency within LOO-1110's idle-server budget, if automatic discovery is wanted.

F6. Repointing a remote URL in place (git remote set-url origin <new>) Separate outcome

plan_carriers.peer stores the remote's name ("origin"), not its URL, so changing origin's URL in place keeps seen_seq = 0 and does not trigger a new first read.

What it would take: Store or hash the resolved URL beside the remote name in plan_carriers while keeping lf repo tracker printing the short name. Rare today.

1. Should lf wave show on a brand-new Machine and lf task show <id> on an unread clone fetch the remote plan like the other read commands?
In HEAD today, cloning on a brand-new Machine (no Loopflow store yet) and running lf wave show prints an empty list even though lf plan list and lf task list fetch and show the team's plan. Separately, lf task show <id> fails with "not registered" on an unread clone while lf task status <id> and lf task detail <id> both fetch and find it.
  • 1a (Recommended) Yes — fix both (plus the offline-Hub cooldown edge case) in LOO-1113 — every plan overview and single-Task read behaves the same on a fresh clone or brand-new Machine, matching what docs/work.md already promises.
  • 1b Fix lf wave show (and the cooldown edge case) only; leave lf task show <id> store-only — keeps lf task show strictly local as a Desktop pane read, while fixing the broken documented command.
  • 1c Ship HEAD as-is — accepts lf wave show returning empty on a brand-new Machine and lf task show failing on unread clones.
2. If your very first command in a fresh clone is a live stream (lf task list --subscribe), what should it do?
On main, lf task list --subscribe waited up to 5 seconds to fetch from Git before printing its first line, while lf plan list --subscribe and lf repo tracker --subscribe did not. HEAD made all five --subscribe commands read the local store only — instant startup, but an unread clone stays empty until you run a one-shot list or lf task sync.
  • 2a (Recommended) Keep all --subscribe streams store-only (current HEAD) — always instant, never touches the network, consistent across every --subscribe command.
  • 2b Print the local store immediately, then fetch once in the background if unread — first line is still instant, and remote Tasks arrive automatically as the next update a moment later.
  • 2c Wait up to 5 seconds to fetch before printing the first line on lf task list --subscribe — restores main's blocking behavior for that one command.
3. When you are offline on an unread clone, how should repeated reads behave?
The first lf task list tries to reach the remote (waiting up to 5 seconds) and then shows your local Tasks. Because the clone has still never read the remote, Loopflow has to decide what the next lf task list two seconds later should do.
  • 3a (Recommended) Wait 60 seconds after a failed first read before trying again (current HEAD) — repeat offline reads answer immediately, and once you reconnect the first read after a minute (or immediately after any successful push or lf task sync) catches up automatically.
  • 3b Try on every read until one succeeds — catches up the instant you reconnect, at the cost of a 5-second pause on every offline read.
  • 3c Stop retrying on reads after the first failure until you run lf task sync — zero offline pauses after try #1, but reconnecting won't pull the remote plan on a plain lf task list.
4. If you clone a repo before anyone has created any Tasks in it, and a teammate later creates the first Task, should your clone pick it up automatically?
Your first lf task list fetches the empty remote and marks the clone read. To keep idle repositories from generating background Git traffic, the local server only polls repos that already have at least one open Task or Wave.
  • 4a (Recommended) Keep empty clones quiet (current HEAD) — zero background network traffic on repos you aren't using Loopflow in; run lf task sync (or look up a Task by ID) to pull a teammate's first Task.
  • 4b File a separate Task to poll empty clones periodically — teammates' first Tasks appear automatically without running lf task sync, at the cost of periodic background fetches for empty repos.
