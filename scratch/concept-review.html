Keep Working Tasks in place

Do the sidebar, Working Tasks grid and Wave view share the order a person expects through a conversation turn, a drop and a failed read?

The drop now saves the side you chose

Before. You see A, B, C and drop B above A. Another window has already moved A after C. The preview puts B above A, but the request carries only A’s ID. The Machine reads B, C, A, takes A’s index and saves C, A, B.

Built. The request carries “B before A”. The Machine uses the latest Working order, removes B and puts it immediately above A, saving C, B, A. If a Task has left Working when the Machine resolves the drop, the refusal gives its ID and the last confirmed order returns.

What survives a newer reading

B goes Busy and hands back
Working order and selection hold. The Available and Busy filters recalculate membership in that order. An unknown activity reading can make a filter incomplete.
The target leaves Working
A Machine reading without the target refuses the drop and reports the target’s ID. A failed reread leaves the last confirmed rows and the refusal Notice. A successful reread shows current membership, including an empty list. A new drop can use a remaining target.
A read arrives before the write answer
Applying the same side to an already placed pair leaves the pair in place. A receipt retires the preview independently on each covered reading. A later committed move can change the order again.
The command has only a destination
A destination-only CLI call or saved Dashboard move takes the target’s slot. A grid receiving a Task from another window can also see a target without the source. It uses the slot and waits for a confirmed order.
A Task joins after a drag
Saved positions come first. The unsaved tail follows planning rank and Task ID. Repository and Wave plans, the phone list and roadmap use the same order. An authored query or touched Dashboard can compose its own list.
Project order changes
Unsaved Working rows can follow rank edits. Committed drags keep their places. LOO-937 proposes sharing drag order through Project rank. That choice would need rules for cross-Project drops and existing saved positions.

What the second pass checked

The served regression reads back C, B, A after “B before A” and C, A, B after “A after C”. The one-shot CLI repeats both moves. The same regression checks that a missing target returns not_found and a saved Dashboard can move the same Tasks without changing Working order.

On the private Machine, a stale sidebar drag sent “D before A” and kept D above A in the newer order. Desktop model tests cover the chosen side across uneven read revisions and the refusal Notice through a failed read. Live grid drag, key-window filters and shortcuts still need the unlocked Desktop walkthrough at gate.

Questions for review

  1. What should a drop save if another window reordered first?
    1. Use the side the person chose. The current branch applies it to the fresher order.
    2. Proposed alternative. Use the target’s latest slot, as the destination-only command does.
  2. What starts the Working order before a drag?
    1. Planning rank, with Task ID for ties. This is the built choice. A saved drag takes precedence.
    2. Proposed alternative. Oldest Task first. Planning rank edits would leave unsaved Working rows in place.
  3. Who owns the order changed by a Working drag?
    1. The repository’s Working list on this Machine. This is the built choice. A drag can cross Projects.
    2. Proposed in LOO-937. A Working drag changes the shared rank within a Project.
