The few concepts behind them

ConceptMeaning
Entryexisting What a launch runs: the install gate, the Desktop helper, or LF_BIN in a private Home (resolve_lf_binary()).
Supersededproposed An owner whose entry no longer runs its executable. Joins removed and replaced. Judged from files and symlinks; no store read, no version numbers, no probe of the other process.
Ends at idleexisting The lifetime policy: once its Sessions wait for a person, the owner stops its agent and records its exit. lf resume reopens from provider history. Superseded is one more trigger.
Takeoverproposed lf resume never negotiates with an owner on another build; it ends it and reopens. Same build: attach as today.
Followproposed A viewer told a successor reruns its argv through it. Reverses the "replacement viewers are removed" half of LOO-502; pinning and probing stay removed.

The consequential mismatch. The design has one heading, "The one judgement". The code has three. The owner compares paths against the entry's target. lf resume compares content with same_build. follow compares paths again, so a Desktop pane whose bundled lf is byte-identical to the installed CLI still reruns itself through the gate when its owner ends.

One function fixes all three: installation::superseded(executable) = !same_build(executable, entry_target(resolve_lf_binary())), used by the owner and the takeover; the viewer's follow reruns the invocation on the owner's word. This is implied by the accepted design, not a new decision. done Implemented 2026-11-02; entry_target and same_build are private to it.

Walking one interaction through, with recovery

Normal path. Jack has a Session open in a cmux pane on 0.15.1. lf install settles 0.15.2 into the gate. Within two seconds the owner sees entry_target(gate) is no longer its file. The agent is mid-turn, so nothing happens yet. The turn finishes; the owner sends the pane Moved { notice, successor: gate }, stops the agent, records its exit. The pane prints the notice and runs gate session resume <id>. The conversation reopens on 0.15.2 with history intact.

Failure. The install also advanced the store past 0.15.1's reader floor. The owner knows it is superseded (that is a file read) but owner_waits_for_person fails (that is a store read). It logs and judges again next tick, forever. The pane sits on the old lf. existing Staged migrations keep old readers working for about 30 days, so this needs an owner older than that.

Recovery. Jack types lf resume <id> anywhere, or runs lf monitor rollover. Both run on the new lf, which reads the store, so both end the owner and reopen. No PID by hand. The deeper fix, if this class recurs: the owner judges idleness from the harness signals it writes itself rather than reading them back. Recorded in the design as a known limit, not scheduled.

What must survive. The saved provider conversation. It does; everything else is rebuilt from it. What deliberately changes. An unviewed idle owner now ends at install instead of at its 24h limit. Counterexample that would invalidate it. Something that needs the idle owner process itself, not its Session. Checked: steers and comments are stored and read at the next turn's context hook; nothing pushes input to an idle owner. An ended Session and an idle one answer a comment identically. Graph runners are never ended; each step launches through the entry.

Questions for Jack

  1. After lf install, an idle Session nobody is looking at:
    1. ends, and comes back on the next lf resume or when a pane shows it (branch; "at a minimum when necessary"; lf monitor rollover stays as the "move them all now" sweep), or
    2. comes back live on the new lf right away ("perhaps always"); rollover folds into install and stops being a concept, and rollover must also resume Sessions that ended for supersession to beat the owners' own 2s ending.
  2. The below-floor owner that cannot tell it is idle:
    1. leave it as the recorded limit; lf resume and rollover cover it, or
    2. schedule the owner judging idleness from its own harness signals as the next slice of this Task.
