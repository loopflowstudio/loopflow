2. The Biggest Mismatch

Every layer assumed "someone else isn't watching, so I'll poll and open my own resources."

observe polled unheld facts for 5 minutes because it didn't distinguish live subscriptions from one-shot reads. read_stream polled every 1 second because observe didn't wake it on change. Hosted::pass and library commands opened SQLite from scratch because the process didn't hold a shared connection pool (and process_ledger() silently fell back to cold opens inside the server). installation/server.rs registered temp homes as permanent launchd jobs because it had no concept of a disposable home. Two earlier patches (#1868, #1979) added caches beside those assumptions and left the server at 80–104% CPU.

The unifying model Proposed

Work happens on a change or a request, never on an idle timer. Each process holds one of each shared resource (one connection pool, one bounded async runtime, one observation cache with one filesystem watcher). The terminal relay thread owns terminal I/O only and never touches SQLite. Only the default Machine (~/.lf) is an OS-registered service; custom LF_HOME servers and holders live only as long as their home and active work do.

4. Counterexamples Caught Before Implementation

Testing the kickoff plan against failure, recovery, and cross-version upgrade paths turned up seven concrete design flaws. All seven are now resolved in scratch/plan.md before any code is written:

1. Always-on observe::derived() + no unheld background refresh = permanently stale config computed.dependencies.changed() only checks cached entry revisions — which stop updating when unheld facts stop polling. A background loop or CLI test calling load_config(), editing config.yaml, and calling load_config() again would read stale config forever.
Fix in plan: Validate unheld File/Bytes/Directory/Metadata dependencies inline via stat(mtime, size, ino) (~5 µs) before returning a cached derived value.
2. Hidden 1-second idle wake loop in read_stream.rs Even with observe.rs's 250 ms loops gone and StoreChanges filtered, Reader::step() schedules now + CHECK (1 s) and read_stream::observe waits CHECK (1 s) forever.
Fix in plan: observe pushes wakeups directly to followers whose held facts bumped, and the fallback reconcile wait rises from 1 s to 30 s so idle subscriptions truly sleep.
3. Three separate notify FSEvents watcher layers Shrinking transcript/watch.rs (4 → 1) while keeping TaskFilesWatch and adding a third watcher in observe.rs still duplicates FSEvents threads.
Fix in plan: One shared filesystem watcher owned by observe covering the 4 transcript roots plus active held checkouts.
4. Adding metrics directly to wire::Status breaks cross-build upgrades ClientMessage::Status is an unversioned pre-hello probe, and wire::Status uses #[serde(deny_unknown_fields)]. Adding threads/store_opens/spawns/held_facts directly to wire::Status breaks every older binary's lf server status and lf install check!
Fix in plan: Keep wire::Status untouched; expose runtime metrics via a versioned post-hello server.diagnostics operation (lf server diagnostics --json).
5. Connection pooling traps: data-only migrations, per-caller token_key, and subscription hoarding PRAGMA schema_version does not change on data-only migrations; SqliteStore carries per-caller token_key; and Reader currently holds one open read-only connection per subscription forever.
Fix in plan: Revalidate when PRAGMA data_version moves and (schema_version, schema_migrations) differ; pool (Connection, HistoryFile) and attach caller's token_key per checkout; have Reader borrow read-only connections per step().
6. Moving settle(exit) off held-terminals races exit-code reads If a terminal leaves terminals before the held-status worker commits its exit row, an attaching view receives Answered::Ended and misses the exit code.
Fix in plan: Track in-flight exits in a settling set on the relay loop that answers Answered::Waiting until the worker sends Command::Settled.
7. Shared current_thread runtime panics under concurrent block_on; macOS lacks pidfd_open Two threads cannot concurrently block_on a shared current_thread Tokio runtime, and server/linux.rs::retire_server uses Linux-only SO_PEERCRED + SYS_pidfd_open.
Fix in plan: Server installs its own bounded multi-thread Handle for all in-process async work (CLI uses one lazy 2-worker runtime); macOS custom-home replacement uses LOCAL_PEERPID + OsProcess verification.

5. Open Questions (Choices Made for Review)

None of these block implementation or are irreversible once shipped — the plan takes the bold, simpler option for each and flags it here. Reply with e.g. 1a or 2b to change course.

1.Should a custom LF_HOME ever stay registered to come back after a reboot?Chosen: 1a
  • 1a (chosen): Never register custom homes with launchd/systemd. Delete the folder (or leave it idle for 10 min with no work) and its server and holders exit automatically. Only ~/.lf restarts on login.
  • 1b: Keep OS registration for custom homes unless a flag or temp-path rule marks them temporary.
2.When a custom LF_HOME directory is deleted while its agents are still running, should its holder end those agents?Chosen: 2a
  • 2a (chosen): Yes — once the home directory itself is gone, no server can ever adopt those terminals again, so the holder closes its PTYs (sending SIGHUP to its children) and exits. Live homes are unchanged: holders still outlive server restarts and upgrades.
  • 2b: Never end children from a holder; require manual cleanup or fixture teardown for deleted homes.
3.How should concurrent Graphs share CPU cores during local builds and tests?Chosen: 3a
  • 3a (chosen): Soft budget in the environment (cores ÷ running steps, floor 2, at nice 5, overridable via env or machine.jobs). Never blocks or stalls an agent mid-turn, and keeps Desktop/typing responsive.
  • 3b: Hard build-slot queue in lf server that makes extra builds wait until a slot frees up (requires build commands to check in with the server).
4.Where should live server runtime counters (threads, store opens, spawns, held facts) live?Chosen: 4a
  • 4a (chosen): Separate lf server diagnostics --json (backed by a versioned server.diagnostics operation), keeping lf server status a pure readiness probe that never breaks older binaries during upgrades.
  • 4b: Put them directly into lf server status --json by having the CLI make a second versioned request when the server is ready (adds a welcomed connection per status check).
5.Should repositories with no Waves and no unfinished Tasks still sync Git plans every minute?Chosen: 5a
  • 5a (chosen): No — only repositories with an unfinished Task or an active Wave on this Machine sync on the minute timer. A repo with neither still syncs automatically the next time you run a command in it.
  • 5b: Keep syncing every existing repository on disk every minute, and prune deleted/temp rows instead.
