One interaction, walked

Normal path built

A PR lands. CI goes green on the push to main. Packages (main) starts from workflow_run, checks out that run's head_sha, names signing, signs and notarizes the DMG. lf install --dev installs it. Same as today.

Failure: a branch tries built waits

The packaging workflow has no hand trigger. A new on: push workflow on a branch that names signing is refused before a runner starts; one that names nothing reads empty strings. Holds once the repository secrets are deleted and the probe has confirmed deployment: false does not switch the refusal off.

Failure: CI finishes on something that is not main exists

A fork opens a PR from its own branch named main. CI runs and passes. GitHub fires workflow_run for Packages (main): the branches: [main] filter reads the head branch's name and the fork's name matches. The run is main's workflow on ref main, so signing would let it in. It stops at github.event.workflow_run.event == 'push': the fork's run was a pull_request, the packages job is skipped, and desktop-app with it. That clause is the whole defence here. GitHub's documented workflow_run behaviour; not run against this repository.

Failure and recovery: a setting changes built

Something with admin adds release/* to the policy. At 10:00 the cron host's release runs its host check before touching anything, and stops:

GitHub Actions secrets are not main-only (.github/CI.md, "Signing secrets"):
environment signing: branch policy allows release/*; expected main only

That text goes to .lf/logs/release-run.log on the cron host. The recovery is one API call and tomorrow's release. If the policy was put back before 10:00, nothing is printed, and the docs now say so.

The biggest mismatch: the environment guards the secret, and an if guards the commit

"Only main's commits get signed" is two rules. The first is new and well described: a workflow on any ref but main cannot read the signing secrets. The second is older and unnamed: main's own packaging workflow signs only the commit of a successful CI run that was a push to main. workflow_run always runs as main, so for that workflow the environment says yes every time, whatever commit it is about to check out. Delete && github.event.workflow_run.event == 'push', say to package merge-queue runs too, and a fork's branch named main gets its PR head signed and notarized. Every test in this change would still pass, and the settings check would print nothing.

A step in desktop-app that checks head_sha is an ancestor of origin/main. The commit rule enforced where the signing happens, independent of the trigger's filters. A second guard for a case the if already closes, in the same file with the same owner. Naming and testing the if is smaller. Worth it only if the trigger ever has to widen.
Keep the pinned job list in the lint as a tripwire. A new secret-reading job shows up as a test edit in its PR. The workflow diff already shows it, and the list has to be edited by the same PR that adds the job, so it stops only an honest slip that the first assertion also catches.
Run the settings check inside GitHub Actions, opening an issue. The message reaches a person where the notarization message does, and the release is not involved. The job token cannot list secrets. It would need a stored admin-reading token, which is a new secret to guard.
