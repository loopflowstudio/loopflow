Installed skills, as built: do the concepts line up?

Area taken: everything behind lf self sync-skills on this branch against its base (7127b9d0d5) — which Loopflow skills and Graphs a harness shows in its own menu, where they are written, what a harness says about itself, and the neighbouring code that also knows about harness skill folders (the skill catalog, native invocation). Taken this wide because the change added a per-harness declaration, and the question after the build is whether that declaration is now the one place the idea lives. Read as someone seeing it for the first time. Outcome: nothing to change in this work; one mismatch remains next door and is a separate outcome.

yes lines up   no does not   proposed not in the code; everything else on this page exists on the branch

One interaction, walked

Normallf install runs the sync. agy -p "/skills" goes from 7 to 116 names; Claude, Codex, Pi and OpenCode list the same 109. Nobody learns a folder.
Add a skillWrite ~/.lf/skills/x.md, run lf self sync-skills --yes, then /skills reload in agy: "1 added".
Failure~/.gemini/config/skills not writable: io error: /…/.gemini/config/skills: Permission denied. The two earlier folders are written, nothing is pruned, lf install prints it as a warning and finishes.
RecoveryFix the folder, run the sync again; it is idempotent. A hand-written skill under a generated name is kept and counted as skipped. A symlinked folder is left alone.

The person's model is one sentence: my Loopflow skills are in every harness's menu. The folders are a detail they meet only in the confirmation prompt and in an error, and both now name them from the same declaration.

The biggest mismatch: two lists of harness skill folders

A harness's skill folder is one thing to a person. The code now has it twice. Sync asks each harness where to write. The catalog has its own literal list of where to read hand-written skills, and that list still stops at Claude and Codex and still gives .agents/skills the dialect "Codex", the label this change removed from the write side because four harnesses share that folder.

What a person would notice: a skill they wrote in ~/.claude/skills or ~/.agents/skills is a Loopflow skill (lf list skill, usable in a Graph); one they wrote in ~/.gemini/config/skills or ~/.pi/agent/skills is not, though Loopflow now writes into the first of those.

Now

// harness/*.rs, per Launcher
installed_skills: InstalledSkills { global, repository }

// skills/catalog.rs, collect_scope
(".lf/skills",       Loopflow)
(".claude/skills",   Claude)
(".claude/commands", Claude)
(".agents/skills",   Codex)
(".codex/skills",    Codex)
(".codex/prompts",   Codex)

Generated files can't feed back in: the catalog skips loopflow: true.

Separate outcome proposed

// each Launcher says what it reads by hand
// and how a skill found there is invoked;
// the catalog folds those, as sync does.

It takes: a format for each new folder, which source wins a shared name, and an invocation syntax per harness (/name in agy print mode, /skill:name in Pi), which is what native_skills would then mean for all five.

Why it is not this work: the outcome here is that every harness lists Loopflow's skills, and it holds without it (agy 7 → 116; Pi 109 over RPC; OpenCode loaded a synced skill). Folding the lists changes which skill a name resolves to on Machines that already have hand-written agy or Pi skills. That is new behavior with its own failure cases, not a correction to what was built.

Outside this work

  • One list of harness skill folders for reading and writing, with native_skills folded into it (above).
  • Each folder syncing on its own: write every folder that can be written, report the ones that couldn't, prune only the ones that wrote. It takes a per-folder result in SkillSyncReport and a decision on the exit code.
  • The sync as something a person runs. A personal skill added to ~/.lf/skills isn't in any harness menu until they remember the command. It could run where the skill is created (lf skill customize) or at launch; harness sessions started outside lf would still need it.
