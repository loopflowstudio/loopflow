The branch answers that question three different ways, and two of them contradict each other in the same PR. Question 1 picks one. Questions 2 and 3 are smaller and follow from it.

The mismatch

Three rules decide how a conversation relates to the server. Each draws its line in a different place.

docs/dev/server-first.md on this branch now says both things. The managed rule, written in LOO-819:

A launch is managed when it comes through a Task or Wave command or from Desktop. A bare lf typed inside a Task's checkout stays bare and records the Task as its ancestry. One function answers this for every launch path.

And the line this Task added, a few paragraphs away:

A Task or Wave launch starts the server before its agent and fails when none comes up.

The code implements the second by asking the store whether the Session has a Task or Wave (session_has_work), which is true for the middle two rows. The plan's "one function" does not exist yet.

One interaction, with its failure

An agent is working LOO-900 on mini. The server there has stopped. The agent runs lf -b research to get a second opinion.

Built. The subagent's launch finds no server and runs lf install server on mini, registering a systemd unit, and waits for it. If it comes up, the subagent runs. If not, the tool call fails with "Loopflow server is not running, and Task and Wave work needs it". A research subagent that receives no steers and records nothing mid-run has been stopped by lf's own state.

Proposed. The subagent runs. It was not started by a Task command, so it is bare. Its hooks find no server, exit in a third of a second and leave one gap line. Its Session still carries LOO-900, so its cost counts there. lf task run LOO-900 on mini is unchanged: it needs the server and starts it.

What survives either way: steers to the Task's own conversations, turn records for them, and "lf --machine M <skill> works with no server". What the proposal changes on purpose: a bare run in a Task checkout on a Machine with no server gets no launch error, so a steer aimed at it waits silently until a server answers. On a Machine whose server is running, the two behave the same.

What the proposal looks like in the docs

Proposed, replacing the added line in server-first.md and the troubleshooting entry's last paragraph:

lf task run LOO-900          # needs the Machine server; starts it
lf resume --task LOO-900     # same
lf implement                 # no server needed, in a Task's checkout or not

Agents started by a Task or Wave command, or from Desktop, start beside the Machine server. Anything you or an agent start with a plain lf <skill> runs without one, and still counts toward the Task whose checkout it ran in.

Two smaller things

A launch check that a stale server passes

The check asks "does a server say hello?". The thing it protects is "will session.boundary be answered?". QA ran branch hooks beside the installed 0.15.2 server: the launch passed, then every boundary logged "this server has no operation session.boundary". So no server refuses the launch, and a server that can't take boundaries doesn't, though both leave the conversation in the same state. The check uses hello on purpose: lf server status reports "not ready" whenever the server runs another executable, which would refuse every launch from a branch build (resumed_session_completes_turns_after_build_replacement_and_viewer_return).

Steer confirmation's moving parts

"Arrive twice" is built as: an answered batch sits in uncertain until the conversation's next hook lists it in printed, read from a .printed file beside the delivery file; waiting in the answer covers two tools finishing together. Every steer now passes through uncertain for one tool interval, so lf session steers shows that word for a healthy delivery.

The case this exists for is a server that answers after the hook gave up. There is a second way to close it: the hook sends its deadline, and a server that reaches the request too late hands over nothing, so the steer stays pending for the next boundary. That needs no .printed file, no waiting and no in-between state, and never duplicates. Its counterexample: a hook that reads the answer and dies before printing loses that steer until --retry, where confirmation delivers it again.

Questions

  1. Which launches need the Machine server?
    1. Every Session that carries a Task or Wave, including a plain lf <skill> in a Task checkout and subagents (built). server-first.md's managed rule then changes to match.
    2. Launches through Task and Wave commands and Desktop, the managed rule as written. A plain lf <skill> in a Task checkout runs without a server and still counts toward the Task. The plan's one function gets written here and the launch check calls it.
  2. When a launch that needs the server can't get one that answers session.boundary:
    1. Refuse when none comes up; start without a word beside an older one (built).
    2. Refuse in both cases, naming lf install. A branch lf beside the installed server then can't launch Task work until the server is updated.
    3. Start in both cases, after trying lf install server, and print one line at launch: steers and turn records wait for the server, and the command that fixes it. Nothing refuses.
  3. Steer delivery:
    1. Keep confirmation (built), and show the in-between state in lf session steers as sent rather than uncertain.
    2. Replace it with the deadline in the request: no duplicates, fewer parts, and a steer is lost until --retry only when a hook dies between reading and printing.
