The interaction

# File separate work, regardless of the current chat or checkout
lf task create --title "Finish the prototype"

# Keep this exact chat and its existing work
lf task create --session SESSION --title "Finish the prototype"

# Select the conversation for an existing Task
lf session bind SESSION --task TASK
lf open --task TASK

Existing implementation: explicit creation retains the source. Binding keeps an existing Task checkout and requests continuation there. The live client and input stay attached until the supported next connection.

Create with an explicit source → Task + optional Session → task_create
TaskAdoptionOptions resolves the exact Session and/or checkout. The common adoption writer preserves Task identity on retry. Plain creation resolves no source.
Bind an exact Session → assignment + primary choice → human_session::bind
CLI and Desktop share the same atomic adoption writer. Other Task conversations remain associated; conflicting permanent binds fail without partial changes.
Reconnect → pending Session directory → admit_workspace
requested_cwd survives failure and a later primary selection. Matching provider connection confirmation clears it. Files remain in their original checkout.

The consequential mismatch — resolved

Task T: done, no checkout
Session S: unfinished, live in unowned linked checkout B

Reviewed source path:
  bind S to T → prepare placement B
              → “terminal Task cannot allocate a checkout”
              → no binding

Implemented correction:
  bind S to T → T selects S; S permanently belongs to T
              → T remains done, with no checkout
              → S continues in B

Review evidence: Before the repair, adoption::save prepared placement whenever a source checkout existed and the Task had none. place_task_in rejected terminal Tasks before binding committed. A Session in a shared main checkout avoided placement. Checkpoint fd5fb9cf76 checks terminal state before preparation and again inside the binding transaction.

Optional checkout adoption now respects terminal Task state in the atomic operation. Ordinary checkout allocation rules remain unchanged. No new command, flag, assignment-only mode or lifecycle was added.

Normal path, failure, recovery

An open, unplaced Task still adopts the selected unowned linked checkout. A Task with checkout A still keeps A, even when done: binding Session S in B records A as its next destination. The live client continues in B until it exits.

If A is missing or the provider rejects the move, retain the request. Restore A or repair the provider failure and reconnect the same Session. Selecting another primary does not cancel S’s pending move. Existing lifecycle fixtures cover those recovery paths; configured binding proof is still pending.

Counterexample to an overbroad repair: skipping every directory effect for done Tasks would lose the accepted continuation into a done Task’s existing checkout. Only the absent-checkout case stays in place.

Updated guidance

Existing usage docs: Done Tasks can still select an unfinished conversation. If the Task has no checkout, the conversation stays in place and no checkout is adopted.

Existing work skill: Bind to a done Task without reopening it. With no Task checkout, retain the Session’s directory; do not allocate a checkout merely to bind the conversation.

Review questions — resolved by the accepted contract

  1. Should a done Task’s missing checkout prevent binding? No. Bind and select the unfinished Session in place without allocating a checkout.
  2. Should the correction remove continuation into an existing Task checkout? No. Preserve its pending directory and provider confirmation.
  3. Is another product choice or implementation direction open? No. The repair follows the working design; remaining demonstrations are proof obligations.
