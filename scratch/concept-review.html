Decision needed: may a read Desktop serves inside the app write the store?

Jack decided (comment 628f4502) that a read is a command whose changes_state() is false. A read records no Process and never wakes Work readers. Desktop now serves its reads in-process. Five of them write anyway, so the app has become a store writer without that being decided. The design still lists that as open: the app and CLI lf both writing, with migrations and version skew.

The mismatch. Two of the done-whens conflict here. "Idle Desktop starts no lf and writes no Process rows" keeps the planning exchange inside the app. "Reads first" keeps the app out of writing. Migration is the sharpest case. A Desktop build whose catalog is newer than the installed lf migrates the store, and that installed lf also reads it.

Settled without you (next implement step)

Proposed One read concept. Operation (watched) and Query (one-shot) are the same thing: an lf read command, with or without --watch. History and PlanningStatus already appear in both. "Operation" also collides with "every app operation has an lf equivalent", which covers writes too.

Product behavior stays the same. This leaves one equivalence test and one JSON shape on both C entry points.
