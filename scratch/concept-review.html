How soon should hourly cleanup make unfinished work rebuild?

Open product choice. The branch uses four idle hours normally, one hour below 64 GiB free, and fifteen minutes below 32 GiB. Jack Heart requested adaptive reclamation; the 24-hour cutoff authorized the earlier one-time sweep. It did not select these recurring windows.

Below 32 GiB, a twenty-minute pause could mean a full rebuild on return. The preservation tests do not establish whether that cost is acceptable.

Keep the interaction small

Before · checkout activity kept output alive

The prior shell cleaner retained an entire checkout's output when any process held the checkout. A model ran ahead of scheduled cleanup; the directory lock could outlive its owner.

hourly cron → skill/model → shell cleanup
any held checkout → retain all generated output
stale directory lock → inspect and remove manually

Existing branch · one operation, three concepts

Preview → measured candidate → scripts/disk-cleanup.sh --dry-run
Reclaim → same operation → scripts/disk-cleanup.sh
Schedule → launchd job → scripts/disk-cleanup.sh install
Explain → run observation → timestamped JSON receipt + logs

Candidate carries paths and checkout ownership. _inventory and _reason derive eligibility; Cleaner.run rechecks before removal. _schedule keeps one job pointing at the main checkout. There is no durable deletion queue.

Task completion still controls native worktree/source pruning. Idle generated output can be reclaimed in unfinished work. Open output, builders, source, history and unknown inspection remain protected at every pressure tier.

Walk through one run

Normal: 50 GiB free; a debug profile is idle for two hours. The draft policy can reclaim it while a held release binary and unpublished source survive. At 64 GiB free, later eligibility checks return to four hours.

Failure: a native child times out after generated-output reclamation. Its process group is killed, failure produces nonzero status, and the receipt retains the measured outcome. Unknown activity stops deletion.

Recovery: the kernel releases the lock when the process dies. The next scheduled run inventories again, including any partially removed root. It does not replay a saved removal plan. Schedule installation leaves an active job alone and attempts to restore the previous job after bootstrap failure.

Counterexample: repeated twenty-minute pauses and rebuilds could regenerate pressure faster than cleanup removes it. A blanket 24-hour recurring window could instead keep almost every daily build. Neither tradeoff is resolved by the one-time sweep.

Proposed reporting clarification

Use existing receipt fields; add no state model or command.

Cleanup completed; free space remains below target.
Report target_shortfall_bytes separately from failures.
Check dry_run and timestamps before attributing the receipt to this run.

A preview overwrites the latest JSON receipt. A skipped run does not. A failed receipt write can leave an older result in place. The skill should report current exit/log evidence when the receipt is missing or stale.
