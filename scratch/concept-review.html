The decision: the branch made a steer one row and a receipt one row per (Session, steer). The commands still describe steering from the reader's side only. You can ask what one Session has read. You cannot ask who has read a steer, and the save tells you nothing about who it will reach. Should the write side get the same treatment the read side just got?

Grey bar is what the branch does today. Green bar is proposed and unbuilt.

The mismatch

A steer is addressed four ways across two command groups, a root flag and a missing argument. lf session steer 'skip the vendored code' with the ID forgotten is a valid command: it steers every Session in the repository. The name says "session" and the effect is the widest one available.

The receipt has the opposite problem. It is keyed by Session and steer, with an index on the steer, and only the Session half has a command. The person who wrote a Task steer holds a steer ID and a question about several Sessions.

What follows underneath

If the save works out its audience once, three things use the same answer: the line it prints, the markers it touches, and lf steer show. The gate in every tool hook then compares two files, and LF_STEER_TASK and steers/latest go away.

Counterexamples kept:

  • A Session that joins the Task after the save was not in the audience. A new Session reads applicable steers at launch, which is built. A running Session bound to the Task later needs the bind to touch its marker, or a bare one misses the steer until something else wakes it.
  • "Reaches 2 Sessions" is a reading at save time. A Session started a minute later skips a steer another Session on the Task already read; that rule is built and lf steer show would have to say so, or the list looks incomplete.
  • A Wave or repository steer touches one marker per live Session it reaches. On this Machine that was 319 lf processes at the last reading.
  • Dropping retry loses "make this one pending again for this one Session". A second steer reaches the whole audience, including Sessions that followed the first.

Questions

  1. After a save, who answers "did they get it"?
    1. lf does: the save prints who it reaches and lf steer show STEER lists each Session's receipt.
    2. Only the save prints its audience; receipts stay per Session.
    3. Leave it per Session.
  2. How is a steer addressed?
    1. One verb, lf steer TARGET 'msg', where the target is a Session or Task ID, --wave or --repo. lf session steer and lf task steer go.
    2. Keep the two commands; a repository steer needs --repo, so a forgotten ID is an error.
    3. Leave it.
  3. Does retry stay?
    1. No. To say it again, steer again.
    2. Yes, per Session, as built.
  4. Task updates, carried over from the last round:
    1. Stay a derived observation beside steers, interactive conversations only, as built.
    2. Become steers lf writes, so one block arrives and one receipt covers both.

Idle bare conversations hearing a steer at their next prompt is not asked here; that was answered earlier in this conversation.
