Keep the work and choose its Task conversation.

No new decision needed. Jack Heart's accepted design survives this review of the merged change. No implementation revision or unresolved product choice is proposed.

The interaction

Existing branch implementation; runtime acceptance still pending. From a shell in a prototype checkout, select the existing Loopflow Session explicitly:

lf session list --json
lf task create --session SESSION --title "Finish the prototype"
lf task status TASK --json
lf open --task TASK --link
lf resume --task TASK

An unfinished interactive Session can select itself when issuing creation. For an existing Task, use lf task promote TASK --session SESSION. Desktop offers Create Task from this Session or Make primary Task conversation; ordinary Assign to Task remains a separate action.

The mismatch, before and after

Before this change: creation filed planning work without adopting the checkout. The superseded selection proposal also inferred the desired conversation from recency.

Accepted and implemented: adopt existing work; select a conversation by its identity. With two Sessions in one checkout, the newer one may belong to another Task. A shell selecting only the checkout binds neither conversation. An explicit selection or the eligible invoking Session supplies the permanent assignment.

Shared checkout: selecting a repository or Wave primary transfers that conversation and frees its former primary scope. The checkout remains shared. A later Task checkout does not move the conversation. Ordinary Wave assignments and permanent Task bindings remain intact.

Failure and recovery

A reservation failure or conflicting permanent bind leaves the local promotion uncommitted. Correct the source or reservation condition, then repeat. If commit succeeded but the reply was lost, the selected Session or adopted checkout identifies the same Task on retry. No turn is replayed.

Remote promotion selects work already on the addressed Machine. Headless Runs do not implicitly become primary; completed Sessions remain assignable through ordinary binding. These boundaries preserve existing work identities.

Review questions, resolved from accepted decisions

  1. Which Session becomes primary? The explicit selection or eligible invoking Session. Never the most recent one.
  2. Does promotion relocate or restart work? No. It changes association and primary selection; the ordinary idle policy still applies afterward.
  3. What remains to prove? Installed and configured-provider create/promote → status/open → continue, including draft or pending-input retention across idle deadlines and Task progress updates. Gate owns the affected suites. Existing fixture evidence is not rendered or configured-provider acceptance.
