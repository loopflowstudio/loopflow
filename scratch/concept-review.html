Do the launch concepts line up?

LOO-924, PR #1966, reviewed against origin/main with the whole change in (56 files, +4571/−3524). The area is launching an agent: everything between a person typing lf, lf -b, lf session resume or lf task run and a provider process starting, plus what lf records about it.

The headline: the per-harness type landed and mostly reads true. HarnessKind::harness() is the one dispatch, Launch requires an Admitted, and the second interactive Claude path is gone. Two product ideas still lack one owner in the code: whether a launch is managed, and which agent was chosen.

One interaction, start to finish

Normal path. In a Task checkout, lf -a codex:gpt-5 implement at a terminal.

  1. LaunchInput::mode() → Mode::Interactive (there's a tty).
  2. transport::delegate computes works(named_work=false, None) → false, so place() → None, so Delegation::Here { mode }. The launch runs in this terminal.
  3. run.rs binds Work from the checkout, then calls transport::holder(false, Some(Checkout)) → Holder::Caller.
  4. native_session::admit creates the capture; Launch { harness: Codex, holder: Caller, admitted, start: New }; Codex.open(&launch) returns codex with the prompt in argv.

Failure. The Codex CLI isn't installed. open fails with the harness's install_hint. Nothing is held, and the capture is admitted but empty. Fine.

Recovery. lf session resume goes through delegate_session → native_session.rs:177, which derives the holder a third way: holder(store.is_work(named_work, session)?, None). That is the same question as step 2's works(), but this one propagates a store error, while works() treats an unreadable store as Work.

Step 2 decides where the launch runs. Step 3 decides who reports its turns. Each reads Work separately, and the readings can disagree.

The biggest mismatch: "managed" has two owners

A person knows one thing: a launch is bare (mine, in my terminal, nobody else records turns) or managed (the Machine server holds it, records it, delivers steers). The server README spells this out under "which launches are managed".

The code answers it twice:

// transport.rs — decides where it runs
let work = works(named_work, session);          // unreadable store ⇒ Work
place(batch, relayed, work, terminal, graph_step)

// run.rs ×3, native_session.rs ×1 — decides who reports
transport::holder(named_work_or_false, work_source)   // Declared ⇒ Server

The brief asked for mode and holder "resolved once, at transport::delegate". Mode is. Holder isn't. The LF_AS=task:<id> lf <prompt> case recorded during implement is what the split produces: place says "run here, bare", while holder says Server. The launch runs in your terminal while its hooks report to a server that isn't holding it. Implement kept that as-is to avoid changing behavior, which was a reasonable call for this pass. The question underneath it is about the concept, not the code.

existing

enum Delegation {
  Delegated,
  Here { mode: Mode },
}
// later, after Work binding, ×4:
let holder = transport::holder(w, src);
Launch { holder, .. }

Three inputs decide "Work": named_work, the store's is_work, the binding's WorkSource. Store failure handling differs between them.

proposed

enum Delegation {
  Delegated,
  Here { mode: Mode, holder: Holder },
}
// delegate reads Work once — named, Session,
// or declared (LF_AS) — then:
//   holder = Holder::of(work)
//   place  = place(batch, relayed, work, ..)
Launch { holder: here.holder, .. }

Delete transport::holder and its four call sites. Holder and place now come from the same reading, so they can't disagree. A store that can't be read means Work in both, as works() already does.

Tested against:

  • Normal (Task checkout, terminal): both say bare, same as today.
  • Failure (store locked at resume): today native_session.rs:177 fails the reopen with ?. Proposed: Work wins and the launch is held, matching works() and the "store failure is a recording gap" rule.
  • Counterexample: implicit checkout binding happens after delegate in run.rs. That's fine today because a Checkout source isn't managed, so it never changes the answer. If a checkout binding ever became managed, delegate would have to read it first. That's cheap: it's the cwd plus LF_AS.
  • What changes on purpose: only the LF_AS-outside-a-checkout cell, and only in whichever direction question 2 picks.

Second: the agent choice is a string

existing

struct AgentConfig {
  agent: Option<String>,       // "claude:opus"
  claude_model: Option<String>,
  codex_service_tier: Option<..>,
  ..
}
// 44× parse_agent(..), 36× HarnessKind::parse(..)

proposed

struct Agent { harness: HarnessKind, model: Option<String> }
struct AgentConfig { agent: Agent, .. }
// parsed once where config resolves;
// Launch.harness = config.agent.harness.harness()

This is larger than the PR. It touches config resolution, the fallback ladder, replay and Session moves. With it, "HarnessKind is the only place a harness name is compared" holds structurally, and an unsupported harness becomes a config error instead of a launch error. Without it, the brief's sentence is true for comparisons but not for parsing.

Questions

Answer by number and letter, for example "1a, 2c, 3b, 4b".

  1. Should bare-or-managed be decided once?
    1. Yes, in this PR: Delegation::Here { mode, holder }, delete transport::holder and its four callers.
    2. Yes, as a follow-up Task stacked after #1966.
    3. No: keep two derivations and say in transport/README.md why they differ.
  2. What is LF_AS=task:<id> lf <prompt> run outside a Task checkout?
    1. Bare, as the server and transport READMEs say of every launch they don't list.
    2. Managed and held, because LF_AS is lf's own declaration for workers it starts (pr_landing.rs:354).
    3. Split the two: lf's workers carry their own marker and are managed; a person's LF_AS is bare.
  3. The agent choice as a parsed Agent { harness, model }:
    1. In this PR.
    2. A follow-up Task.
    3. Leave it a string.
  4. Transcript methods on Harness:
    1. Split them into a per-harness Transcripts impl in the same file.
    2. Leave one trait. One file per provider is what matters.
  5. Admitted names the step that produced it, not the thing it holds (the store, the Session and its attachment that this launch records under). Asked in review: "what is an 'Admitted' harnesse".
    1. Rename it after what it holds, for example Recording (Launch.recording).
    2. Keep Admitted, and give its doc comment one plain sentence.
