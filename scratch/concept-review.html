7. Questions for Review

Answer with a number and letter (e.g. “1a, 2a”). Implementation proceeds with option (a) on each.

1. When an automated CI repair starts, should it load the full Gate test-planning guide up front or only read it if a local Rust/Mac reproduction hits a trap?
  1. On demand (chosen): The repair prompt carries the repo's CI check-to-command table and names the exact Mac error messages that point into scripts/testing.md. Saves ~4K tokens on every repair turn (including simple syncs, lint fixes, and Swift fixes).
  2. Always attached: Attach the slimmed scripts/testing.md (~16 KB) to every repair turn so Mac traps and subsystem test lists are already in context before the first command runs.
2. Before publishing a PR, when should gate run the local Desktop DTO test and iPhone test suite?
  1. Whenever the branch touches any wire/protocol or shared Swift path that CI's macOS classifier maps to iOS, plus loopflow-model (chosen): Catches missed DTO fixtures on server/wire edits and shared Swift breaks on iPhone before waiting on macOS CI runners.
  2. Only when loopflow-model or tests/fixtures/dto/ changed: Narrower and skips local iOS runs on server-only edits, at the cost of missing server wire edits where the fixture was forgotten.
3. Should required-integration stay in this repository's ci-fix overlay for now, or move into Loopflow's builtin ci-fix skill?
  1. Overlay now, builtin as a separate Task (chosen): Keeps LOO-1105 prose-only with no prompt-snapshot churn while immediately fixing Loopflow's own landing repairs.
  2. Move into builtin ci-fix inside LOO-1105: Fixes it for every Loopflow repository at once, adding a Rust prompt-snapshot update to this PR.
