2. The Biggest Remaining Mismatch

Background plan sync still has two halves that disagree — and one of them reads .git/config only to throw it away and fork git.

Passes 1–4 unified observation, pooling, terminal relay, runtime threads, custom-home lifetimes, build budgets, and file retention — but left background Git plan sync split between plan_git::exchange_unowned (60 s, active-work scoped, is_dir() guarded, backed off) and plan_carriers::poll_owned (30 s, writes planning_scope_checks to SQLite even for local-only repos with no hub and no remote, no is_dir() guard, no backoff). Meanwhile plan_git::remote reads .git/config via observe for invalidation, discards the file text, and forks git remote on every active repo at minute 1 — failing the branch's own 60 s acceptance check (12 spawns vs. budget 0).

Pass 5 unification Proposed in scratch/plan.md

One rule for every background plan sync: no carrier (no remote, no hub, or missing directory) means zero SQLite writes and zero subprocess forks; remote discovery reads the .git/config already in memory (forking git remote only for [include] or legacy .git/remotes/branches); owned and unowned Git exchanges share exponential backoff on failure; and quiet Git polls skip redundant for-each-ref and cat-file calls.

4. Counterexamples Tested Against Pass 5

1. What if a repository defines a remote via [include]/[includeIf] or legacy .git/remotes/? Pure .git/config parsing would miss it.
Handling: If .git/config contains an [include header or common_dir/{remotes,branches} exists, fall back to git remote (still cached under Derived::GitRemote). Also ignore empty [remote "x"] stanzas with no keys, matching Git's behavior.
2. What if a claimed local-only repo later gets a remote (git remote add origin …) or a hub (lf machine hub mini)? Because poll_owned skips writing planning_scope_checks, it must still notice the new carrier automatically.
Handling: plan_git::remote and plan_hub::hub both go through observe::derived, which validates .git/config and ~/.lf/config.yaml inline via stat_stamp (~5 µs). The very next 30 s tick detects the new carrier and begins syncing immediately.
3. What if a repo has both a hub and an offline Git remote? Sharing backoff across the whole poll_owned call would starve the reachable hub when Git is down.
Handling: Backoff lives inside plan_git (per repository, for background exchanges only), never gating plan_hub::exchange or explicit user commands (sync, send, before_claim).
4. Could caching (oid, repository_id) in publish() hide a repo-id mismatch? Git commit OIDs are content-addressed and immutable: once commit oid is verified to contain repository == repository_id, that pair can never change. Any new commit has a new OID and is checked once.

5. Open Questions (Choices Built or Proposed for Review)

Resolved since the pre-implementation review: machine.jobs stays host-local (confirmed by Jack Heart; implemented in Pass 4). The remaining choices below are all reversible and have been implemented (or scoped for Pass 5) using the simpler option. Reply with e.g. 2b or 6b to change course.

1.Should a custom LF_HOME ever stay registered to restart after a reboot?Built: 1a
  • 1a (built): Only your main ~/.lf Machine restarts on login. A custom LF_HOME runs as a normal detached process and exits automatically when you delete its folder or leave it idle for 10 minutes with no clients, terminals, or unfinished work.
  • 1b: Keep OS background-service registration for custom LF_HOMEs unless explicitly flagged temporary.
2.When you delete a custom LF_HOME folder while agents are still running inside it, should its terminal holder stop those agents?Built: 2a
  • 2a (built): Yes — once the folder is deleted, no server can ever reconnect to those terminals, so the holder closes them (sending hangup to its children) and exits within a second. Live homes are unchanged: agents still survive server restarts and lf install.
  • 2b: Leave agents running until stopped manually by PID.
3.How should concurrent Graphs share your Machine's CPU cores during local builds and tests?Built: 3a
  • 3a (built): Automatically divide cores across running Graph steps (floor 2, at lower scheduling priority nice 5, overridable per Machine with machine.jobs), leaving interactive terminals unthrottled and never stalling an agent mid-turn.
  • 3b: Make builds wait in a server-managed slot queue until an earlier build finishes.
4.Where should live server counters (threads, database opens, spawned commands, watched facts) live?Built: 4a
  • 4a (built): Separate lf server diagnostics --json, keeping lf server status a pure readiness check that stays compatible across old and new builds during upgrades.
  • 4b: Combine them into lf server status --json by opening a second versioned session whenever the server is ready.
5.Should repositories with no active Waves and no unfinished Tasks still sync Git plans every minute?Built: 5a
  • 5a (built): No — only repositories with an unfinished Task or an active Wave on this Machine sync in the background. Quiet repositories still sync automatically the next time you run a command in them.
  • 5b: Sync every existing repository on disk every minute and prune stale repository records instead.
6.When you have a claimed Task in a Git-only repository (no Linear/Asana, with a remote), how often should Loopflow check the remote for new direction while idle?Pass 5 keeps 6a
  • 6a (kept, slimmed to 2 forks/check in Pass 5): Every 30 seconds — incoming steers from another Machine or phone arrive within 30 s, and offline remotes back off up to an hour.
  • 6b: Match the 60-second unowned cadence (halving idle remote fetches when no turn is running, at the cost of up to 60 s delay for remote steers).
