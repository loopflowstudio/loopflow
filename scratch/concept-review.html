Decision needed: new things reach a conversation in two ways. A steer comes back in a session.boundary answer and is confirmed. A Task update comes from a resident lf watcher that starts a turn. Should they become one inbox, and which items get to wake an idle conversation? PR #1889 finished the steer half for Pi and OpenCode. The memory is in the watcher.

Proposed

Proposed. One concept: the Session inbox. Comments and settled run progress go into it. Every session.boundary answer drains it, with the confirmation steers already have (can arrive twice, never lost). A comment is one item, so it can't be delivered twice.

Wake becomes a property of an item, not a second channel. Only items that need the agent wake an idle conversation: a person's comment, a run stopping, the Task reaching an interactive step, a PR being published. Step progress waits for the next boundary. Someone checking in gets it then.

Waking still needs something waiting for Claude, since only a running hook can inject a message. That can be a /bin/sh blocked on a file the server writes, built the way the Pi bash guard is, instead of a 20–76 MB lf process. No server slot is held.

Checked against

Normal path: a Graph runs for 40 minutes and the Task session stays idle. With the proposal it wakes twice (PR published, at demo) instead of 25 times. When someone asks "where is it", the next turn's boundary drains the step history.

Failure: a run fails at gate while the conversation is idle. That item wakes it, so it's no worse than today.

Server down: nothing drains. Items wait in the store and the waiter sees no file, which matches how steers behave today. One gap line.

Counterexample to keep: someone may actually want every step streamed, for example while watching a first run of a new Graph. That points toward wake rules per Session rather than one fixed list. Question 1c.

Unchanged by these questions

Built. Pi and OpenCode open machine.sock for each boundary (hello, one session.boundary, close). They render the block at start and after compaction. The Pi bash guard is a /bin/sh script. QA ran real Pi 1.3.0 and OpenCode 2.2.1, and neither started an lf process during a turn.

Questions

  1. Which items wake an idle conversation?
    1. Every settled step, as today.
    2. Only items that need the agent: a comment, a run stopping or failing, an interactive step, a PR published. Step progress waits for the next boundary.
    3. (b) by default, with a Session able to choose "stream every step".
    4. Nothing wakes. Everything waits for the next turn.
  2. Steers and Task updates:
    1. Merge them into one Session inbox drained by session.boundary. A comment is one item.
    2. Keep two channels and have the watcher skip comments a steer already delivered.
  3. Where it's built:
    1. Ship #1889 as is and steer the inbox into LOO-826 ("Observers become server registrations"), which already deletes the watcher.
    2. LOO-835 takes it on before merge.
  4. Pi with a frozen server: each report waits the full 2 s, one after another (QA: a 4 s tool step took 8–10 s).
    1. Keep it ("same rules as hooks").
    2. While a gap is open, report only tool-start and fold the rest into the next answered boundary.
