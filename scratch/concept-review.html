Now: the file has no loopflow-titlebar, so GhosttyThemeMapping.titlebar darkens the accent until the second text level reads, and readabilityErrors holds both text levels on the bar at 4.5:1.

Recovery. They want a different bar. The editor has a Title bar row under "Actions and focus". Saving writes loopflow-titlebar; from then on "Button" no longer moves the bar, like hover and pressed.

Old saved theme. A custom theme saved before this change states its accent and no bar. ThemeFile.parse runs the rule after the stated roles and loopflow-appearance, so the bar comes from that accent: today's color where it reads, a darker one where it does not.

Biggest mismatch, before and after

Before: the most visible color in the window had no name in the theme. After: it is a role like every other, with one fallback rule, one check, one editor row, and the two defaults share it by test. That was the mismatch this Task set out to fix, and the code matches it.

What remains on this page as no (diff lines sharing chip fills, selection fill as surface) is catalogue-wide, one rule repeated in 22 files, and already listed in the plan as its own outcome. Taking it here would grow the Task.

proposed The small one: name "white or black on this color" once and have titlebarColorScheme and the rule read it:

// today
titlebarColorScheme { definition.titlebar.prefersLightText ? .dark : .light }
titlebarText        { ThemeRGB(titlebar.prefersLightText ? 0xFFFFFF : 0) }
titlebar(accent:…)  { let text = ThemeRGB(lightText ? 0xFFFFFF : 0) … }
// proposed
extension ThemeRGB { var readableText: ThemeRGB }   // white or black
titlebarText        { titlebar.readableText }
titlebarColorScheme { definition.titlebarText == .white ? .dark : .light }

Cleanup, not a model change; left to compress or gate.
