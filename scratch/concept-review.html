A stacked Task's parent: one record, one verb

Area taken: stacking as a whole — how a Task comes to build on another, every command that reads or moves that fact (lf checkout --stack-on, lf sync, lf pr publish, lf task status, Desktop), and the PR base on GitHub. Not only the publish path, because LOO-959 went wrong before publish ever ran.

What happened, in one interaction

LOO-959 was created unstacked. A steer said "you can stack onto 953 i guess", then "Stay stacked on 953: when they land on its branch, sync onto it". The agent did what those words say with the tools at hand:

# what the agent ran
git merge jack/loo-953-…          # Git now depends on LOO-953; record says main
gh pr edit 1972 --base jack/loo-953-…
lf pr publish                     # record wins: base back to main, silently
lf sync                           # record wins: "Synced onto main."
lf sync jack/loo-953-…            # merges; record untouched

Four places said something about the stack — Git history, the GitHub base, task_checkouts.parent_pr_id, and the person's head — and only one of them is what lf reads. The command that changes it, lf checkout LOO-959 --stack-on LOO-953, exists. Nobody reached for it because "checkout" is not the word for "build on that Task now", and its own message said the PR was unchanged.

The biggest mismatch: the verb

Merging another Task's unmerged branch makes the child depend on it. That is true in Git whatever anyone intended. The kickoff plan kept lf sync <branch> as a plain merge plus a hint naming lf checkout … --stack-on — so the person still has to learn a second command to make lf agree with what Git already says.

kickoff plan

lf sync jack/loo-953-…
Merging origin/jack/loo-953-…
LOO-959 is not stacked on LOO-953, so its PR
still targets main. Stack it:
  lf task checkout LOO-959 --stack-on LOO-953
lf task checkout LOO-959 --stack-on LOO-953
PR #1972 now targets jack/loo-953-…

Two commands; between them, Git and the record disagree. Stacked Tasks still refuse lf sync Q.

proposed

lf sync LOO-953
LOO-959 stacks on LOO-953 (jack/loo-953-…).
PR #1972 now targets jack/loo-953-….
Merging origin/jack/loo-953-…
Synced onto jack/loo-953-….
lf sync main        # undo: detach, PR back to main

lf sync <open Task> = lf checkout self --stack-on Task + lf sync. One composition, existing pieces.

proposed Choice made for review. lf sync becomes the stack verb: no target follows the record, the default branch detaches, another open Task (by ID or branch) stacks onto it. The refusal on stacked Tasks goes — a precondition removed, not added. Plain refs and merged Tasks merge as today. Passed over: hint-only (leaves LOO-959's state reachable), and restacking by raw merge (would carry the old parent's commits; going through stack_existing_task recomputes the fork).

Tested against three paths

NormalUnstacked child, lf sync INF-123: parent file present, status stacked on INF-123, pr edit --base parent. Two publishes later the base is still the parent; neither sends --base.
FailureMerge conflicts the resolver can't finish: the record already names the parent and base_commit stays the old fork — the same state --stack-on leaves today before its sync. The next lf sync retries onto the parent. No gh login: record written, error names gh pr edit N --base …; publish later reports the disagreement instead of fixing it silently.
Recovery"I only wanted to borrow a fix": lf sync main detaches using the recorded fork. Counterexample kept open: someone who wants the sibling's commits to ship inside their own PR. That is rare and the PR would be lying about its diff; question 1 covers it.

Publish, with the verb in place

With a stack always recorded by lf's own verbs, publish disagreements only come from outside: a hand gh pr edit or an unrecorded git merge. Publish keeps the PR's base and prints both, naming lf sync LOO-953 to record and gh pr edit 1972 --base main to follow the record. Unchanged from the plan apart from that command.
