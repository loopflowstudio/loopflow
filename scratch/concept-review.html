The command lf open puts in a host pane, as built

LOO-986, third concept review, 2026-11-19, of the branch at aa8b883529 against its base 2750c9e0fb. Everything on this page exists on the branch unless it is in blue; blue is not built and not in this change.

Outcome of this pass: nothing to change. The second review's two proposals (the receipt handed on by name, the relayed tail deleted) are built at c8779a386c, and QA reran the failed and usable openings on tmux and Rex at 815013de83.

Area taken: one opening, end to end: the command lf open writes into a pane, what that command inherits, which harness it names, and the answer the caller gets back. The whole change sits there, and so do the three things QA found still wrong, which are larger than this change.

One opening, walked

/bin/sh -c '<wrapper>' lf-open /tmp/…/receipt env -u LF_AGENT_CALLER -u LF_AGENT_OVERRIDE \
  LF_OPEN_RECEIPT=/tmp/…/receipt  /…/lf session resume ses_1
  1. The pane's lf (the viewer) appends the tool directories to its PATH and starts the launcher in a held terminal.
  2. Normal: the launcher spawns the provider; the viewer writes attached; the caller reads status: usable.
  3. Failure: no claude. The launcher's main writes 'claude' is not installed. … to the receipt; the caller reads it as reason; the pane shows the same text and waits for Enter.
  4. Recovery: install it, run the same lf open. The command names no harness, so nothing moved in between.

The command is now a name for a conversation. That part of the first review held up in QA on tmux, Rex and Herdr.

Biggest mismatch left: usable

A person reads status: usable as "it's open, I can type". The code writes it when the provider process is spawned. QA saw it: a provider that starts and exits at once is usable, and its pane shows the error. Everything this change built answers for failures before that point; after it, the caller is back to reading the pane.

Built

launcher spawns provider   -> viewer answers "attached"
provider exits 1 at once   -> usable; pane shows why
launcher fails first       -> failed, launcher's error
viewer fails first         -> failed, viewer's error
neither answers            -> failed, "(status N)"

Not built, its own Task

provider takes input       -> "attached"
provider exits before that -> failed, its last words
                              (this is where a relayed
                               tail belongs)

Needs a readiness signal from each of four harnesses and an answer for one that never gives it.

The pane's lf is the entry gatecarry_across_exec hands the receipt to the installed lf. Unit-tested only: an end-to-end run needs a published build (in the plan's "Remaining").

One thing left as found. The launcher keeps its receipt for as long as the conversation runs. When the provider later exits non-zero, end_open writes "conversation opened by lf open failed before attaching" to logs/lf.log, an hour after it attached. The receipt is unaffected (it is already written, or its directory is gone). The base did the same through the inherited variable. A fix would log only while the receipt's directory exists and the receipt does not, the test the pane's shell wrapper already uses.

Larger than this change

  • usable is "spawned". To mean "takes input" the acknowledgement would move from NativeStarted to a signal each harness gives when it is ready; four harnesses, and a timeout story for one that never says so.
  • A failed move is still a move. Recording the harness after it starts, or undoing it when the launch fails, belongs to lf session resume --agent, not to lf open.
  • "Not installed" for nvm, mise, asdf tools. Since #1981 a person's terminal PATH reached the pane; the brief asks for that deleted so an agent's shims stay out. Either carry PATH only when the caller is a person, or run the pane command through the person's login shell.

Questions

  1. usable:
    1. stays "the provider was started" (built);
    2. becomes "the provider takes input", with the provider's last words as the reason, as its own Task.
  2. Tools behind shell rc (Pi under nvm reads "not installed"):
    1. accept, add directories as they are missed (built);
    2. carry the caller's PATH when the caller is a person;
    3. run the pane command through the login shell;
    4. keep (a) but say "lf did not find 'pi' on its PATH" instead of "not installed".
  3. A failed lf open -a <harness>:
    1. leaves the conversation moved (built);
    2. records the move only once the harness starts, as its own Task.
  4. The launcher's late "failed before attaching" log line:
    1. leave it (built, and as on the base);
    2. log only while the opening is unanswered.
