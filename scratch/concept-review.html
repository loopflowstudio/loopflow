LOO-936, PR #1965, reviewed at 5e98f52d69 on 2026-11-17, against origin/main. Read from the branch's code, the plan and a read-only look at the live store. The run's own review of f326e99cbb is in git history at 89d27f36fb.

Area taken: what lf records about a Session's work and where it keeps it, as it stands with the five answers built: the message, the turn that answers it, the history a person reads later, and the two files that hold them. Wider than the last pass (the turn's state), because the change now states one rule for the whole store and the question is whether the code keeps it.

proposed marks anything that does not exist yet. Everything else is as built.

The rule the change states

From the top of history.rs: "Nothing the product acts on lives here: deleting the file loses history and usage, not state." loopflow.db is what the product acts on now. history.db is what a person reads later.

One interaction, walked: it holds

A Graph runs a loop-or-next step, one turn.

  1. The Graph sends the message. lf writes the message row in loopflow.db.
  2. The turn starts. lf inserts a row in history.turns with its Task, Wave, skill and step.
  3. The turn ends. lf writes the turn id, end time and status onto the message row, then completes the turn row with its numbers.
  4. The Graph asks which turn answered. input_answered_turn reads the message row and nothing else, and requires turn_status='completed'. The text comes from the provider's transcript.
  5. The Session list asks whether the turn ended. recorded_turn_end reads the message row.

Failure: something holds history.db for the whole turn. Steps 4 and 5 are exact, because they never open it. Only the numbers are late, with one gap in lf.log. The guess is gone from the code.

Recovery: the transcript pass fills the turn row later. A failed turn keeps the stream error unless a later turn completes.

This was the biggest mismatch last time. It is fixed.

A second interaction: it does not hold

The Task list shows LOO-936 as moving. Where does "moving" come from?

  1. task_state_sql asks whether the Task has an unfinished Graph Process.
  2. To decide which Processes belong to the Task it calls task_open_process_ids, which joins Processes to Sessions five ways. Two of the five read history.session_history and history.turns.
  3. The Task list subscribes as Watch::State, so it does not wake when history.db changes.

So a Task's state is computed partly from the file that "nothing the product acts on" lives in, by a view that is not told when that file changes.

Measured on the live store, last 7 days: 8,038 Process-and-Session pairs are named by rows that move to history. The message row names 7,643 of them and the current attachment 66 more. 329 are known only from history rows, and 0 of those are unfinished Processes. For the open-Process read the two history arms found nothing.

The biggest mismatch: the rule is stated but nothing holds the code to it

The change moved the turn's state and declared the file clean. Five other reads were carried across with a new history. prefix, because on main they read the same rows from session_events. Each one is small. Together they mean the sentence at the top of history.rs is false, and the next read someone adds can break it again without anyone noticing.

As built

  • Every store connection attaches history.db, so any query can name it.
  • Task state and the Session list read it while subscribed as Watch::State.
  • A moved conversation's destination and a fork's lineage pass through it between live processes.

After proposed

  • The open-Process read drops its two history arms. Task state reads loopflow.db only.
  • The Session list drops the legacy_review_feedback read and the ready_summary field with it.
  • One test runs every Watch::State projection twice, with history.db present and deleted, and expects the same answer. That is the rule, checked.
  • Departure and lineage: see question 2.

Counterexamples kept

  • The sample is 7 days on one Machine. An unfinished Process that neither captured a message nor holds an attachment, but did write a turn, would lose its Task membership. None appeared; a turn's Process is the attachment's, so it should not exist while the Process is open.
  • The finished-Process reads (process_session, task_of_process, Task work history) do need history: 4% of pairs. They are a person reading later, except ci-fix finding the Session to continue. Removing those arms here would lose data; LOO-953 replaces the join.
  • A "same answer with the file deleted" test fails today on the Session list until the legacy read goes. That is the point of it.

Smaller findings

  • A history row's kind. history.db does not exist on any Machine yet and its schema only adds once it does. A kind column holding the real kind (manifest, terminal, transition, gap, attempt, lineage) costs nothing now and replaces two partial indexes and three ways of spelling it.
  • turns is the only table that grows without limit. Estimate from the inventory: about 1,760 turns a day at about 0.7 KB is 0.45 GB a year, and final_message at about 1 KB for about 1,200 of them adds roughly the same again.
  • input_events is read only by tests. The plan lists it as a follow-up; it can go now.

Larger than this work

  • Process rows and every join through them: LOO-953. It also decides whether lf process prune survives.
  • One name for the message, and session_events renamed for what it holds: LOO-937.
  • Headless Claude turn duration; lf usage grouping by skill, model and step.
  • Sessions still running the released lf after install leave the message row's turn state empty, so a new Graph finds no answer for them. The fallback that used to cover this was the guess, and it is deleted. Settled as detect-and-name.
