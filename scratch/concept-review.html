Biggest mismatch: the PR's attachment

Walk it: PR #566 opens, its Task's issue gets an attachment (confirmed, remote_id = att-…). The PR merges and a second Link action is queued.

existingEvery state change links again 
LinkAttachment(issue, url)  → 200 + error
  "This URL has already been linked with LOO-966."
Sent::Unknown → phase stays 'sent'
every lf command: resend (no window)
~26 LinkAttachment in 11 s → 429
429 takes the hourly reset → every write paused
The attachment id sits in the store, unread. The action can never confirm.
proposedThe PR keeps its attachment 
recorded = latest confirmed link's remote_id
UpdateAttachment(recorded, state)  → 200
update comment                     → 200
Acknowledged { remote_id: recorded }
LinkAttachment goes out only for a first link. If Linear answers "already linked" (a lost first reply, as with seq 722), read IssueAttachments and take the one with this URL. Not on the issue: retire with Linear's message.

On the live store (2026-11-22) 14 of the 15 sent links have a confirmed predecessor with an attachment id, so all 14 confirm on the first pass after install. The fifteenth goes through the recovery path. With this change, a later link 429 can only hold first links, and §1 makes sure it holds nothing else.

Plan before: recover from the "already linked" error by looking up the issue's attachments, on every state change. That costs a refused request on the limited endpoint plus a read each time, and it treats the store's own record as missing. After: the recorded id is the attachment's identity, as comment_id is the comment's; the lookup is only for recovery.
