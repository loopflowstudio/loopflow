LOO-1084: where a Task runs, and where a steer went

Concept review of the kickoff plan before implement (base fc1b574420). Nothing is built yet; every proposal below is a plan change, already written into scratch/plan.md.

Area taken: how one Machine sees and steers a Task another Machine runs — Task ownership as people read it (status, lists, Desktop board), Task steers and their receipts, and how inbound tracker comments reach the owner. Not the server supervisor on containers (LOO-1081/1083) and not remote viewers (LOO-1083).

One interaction, as it fails today

An agent on modal-2 watches four sibling sandboxes. It has no SSH route to any of them.

modal-2$ lf task status MTG-419 --json | jq .task.reason,.task.next "No Task Graph has run; independent Sessions may still be active" "lf task run MTG-419" modal-2$ lf task list MTG-419 · Jack Heart · Runs on modal-3 since Nov 23 14:02 · Fix deck import ← text knows; --json does not modal-2$ lf steer MTG-419 "stop refactoring foo" Saved steer_8f1… ← sits in Linear; modal-3 never polls

The plan fixes all three. The review's question is whether the names and records it adds match what the agent is trying to learn: who runs this, could I see it, and will my direction reach it?

Biggest mismatch: "where it runs" is a sentence, not a fact

The product already has the concept, worded well: Runs on mini since Nov 12 10:42. But it exists only inside two text printers (waves.rs:918, bin/lf.rs:1205), each recomputing it from ownership. Every JSON reader — agents, Desktop, iOS — is blind to it, which is how modal-2 got told to lf task run a Task running next door. The kickoff plan patches TaskDetail and leaves lists and the board wrong.

Tested against

PathHolds?
Normal: laptop → reachable mini, live workerreached: owner, owner authors the reader sentence; reading: owner. Same as kickoff, fewer fields.
Failure: modal-2 → unregistered modal-3; Linear offline at sendreached: here (was local_only); the existing pending-export drain sends it later. Lists and status both say "Runs on modal-3", next: null.
Recovery: modal-3 restarts with no server, Graph step mid-runRunningGraph::spawn polls; watermark in linear_team_checks; 30 s lookback + idempotent ingest ⇒ no drop, no duplicate.
Counterexample: caller wants to know a steer reached a finished worker that nothing readsStill reached: owner; the sentence says "nothing reads it until its Graph continues it". If a caller ever needs to branch on that, a reader enum can be added; today none does. Kept as question 2.
Counterexample: six sandboxes share one Linear keyEach polls ~2/min at full budget ⇒ ~720/h. delta_fresh_secs() reads Linear's remaining-budget headers, so they stretch together; the 10% urgent reserve holds. Tiers would not change this much.

What did not change

Direct SSH for reachable owners with pre-admission fallback; inbound sync as the cross-sandbox carrier (no relay, no SSH mesh); the 30 s lookback fix in team_changes; TaskState untouched; no migration; slice order (inbound ingestion first, because it is the part that can fail to hold).

Questions

  1. Field name for where a Task runs: a runs_on (chosen, matches "Runs on mini since …") · b machine · c keep kickoff's owner.
  2. Steer receipt: a reached: owner | tracker | here + sentence (chosen) · b also a typed reader (live | starts | none) for callers that branch on it · c kickoff's four statuses.
  3. Comment thread in the steer receipt: a drop it (chosen; lf task status has it) · b keep it flattened.
  4. Inbound polling: a one rule, owns open Tasks ⇒ every max(30 s, delta_fresh) (chosen) · b kickoff's 30/120 s tiers by live process.
  5. Lists and the Desktop board: a carry runs_on and the "Runs on …" reason now, in this Task (chosen) · b fix lf task status only and file lists separately.
