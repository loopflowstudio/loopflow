The biggest mismatch: "is it coming back?" has no answer on the wire

Now 
SessionRecord
  state:  closed
  ended:  {at, by: died, exit_code: 137}
  start:  {attempts: 1, last_started_at,
           next_at, gave_up: false, failure}

Rust  conversation_line(state, ended, start,
                        now, server_runs) → text
Swift conversationLine(state, ended, start) → other text

Each client re-derives the outlook. The repository already rejects this shape elsewhere: "consumers never reconstruct the condition from process flags" (task_condition_states.json).

Proposed 
SessionRecord
  state:  closed
  ended:  {at, by: died, exit_code: 137}     (unchanged)
  outlook: {kind: coming_back | waiting_for_you
                | quit | could_not_start,
            at,        // when it comes back, if it does
            reason,    // "exit 137", "no PTY left: 511 in use"
            command}   // "lf resume --task LOO-12", or null
  start:  {attempts, last_started_at}       (facts only)

Rust folds once (where server_runs, backoff and give-up are known). lf task status and Desktop print outlook; could_not_start replaces "closed · starting again".

Normal path: running → outlook null. Failure: SIGKILL → coming_back, at now. Recovery: started → running, start.attempts 1. Give-up: waiting_for_you with the command. Counterexample kept: the outlook is only as true as the reader's Machine; a Task checked out elsewhere would read coming_back that no server here will do, so the fold needs "checked out here", which session_ending does not read today.

Cost: one wire field, fixtures, Swift decoder; two text functions shrink to one printer each. Nothing stored changes.

Smaller findings
