The biggest mismatch: the Session list's own membership

Walk it. Task A's checkout lives at ~/src/r.wt. Its conversation runs there. The repository moves; a fresh clone takes ~/src/r.wt and becomes Task C's checkout.

Now 
lf session list --task C
  A's old conversation      ← cwd's Git root is C's checkout
lf session list --task A
  A's old conversation      ← stored task_id
lf task show C
  (none of A's)             ← session_task_ids

Same Session, two Tasks in one surface, one in another. The resolver also prints "Multiple Tasks claim this checkout" where the store answers the lower id.

Proposed plan: next 
lf session list --task C
  (none)
lf session list --task A
  A's old conversation

associate sets task_ids from the stored Task only. The resolver keeps what it is good at: the worktree root to show and the "checkout is unavailable" reasons. Its workspace.task_id follows task_checkout_owner's rule.

This is inside the Task: the plan's outcome says a Task's Sessions stay with it after a move and a path reuse, and its readers section says membership reads task_id only. The previous two pages marked the resolver "fits LOO-934"; with the Git-root rule built it is the last reader that disagrees, and fixing it deletes code.
