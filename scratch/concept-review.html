The biggest mismatch: "reaches one repository" is checked by a question whose answer is unknown, and the planned first run cannot learn it

The task is a repository-scoped token. Everything that hands a token to a rental goes through one check, and that check is the only thing standing between "GitHub ignored the restriction" and a rental holding a token for every repository the app is on. The plan says one run ("install the app on loopflowstudio/loopflow, type one code") answers whether GitHub restricts the token. It does not: with the app on one repository, the list has one entry either way, and the check passes for a restricted token and an unrestricted one alike.

Planned first run in the plan

App on one repository. Approve. The check passes.

Learned: a refresh token is issued. Not learned: whether the token is restricted, and whether the check can see it. The first person to install on a second repository finds out, after typing a code.

Proposed first run proposed

App on two private repositories. Approve for the first.

The check passes, and a read of the second repository with the new token is refused: the restriction holds and the check sees it. Renew once and repeat both: the plan's question 1. Or the check refuses: it has to be replaced before anything else is built on it.

What changes by answer. Restricted and the list shows it: the build stands. Restricted but the list shows the whole installation: the check becomes a read of a second installed repository that must fail, which needs a second repository to exist; with one install there is nothing more to reach and nothing to check. Not restricted at all: there is no repository-scoped user token, and the mechanism is the wrong one. What survives in every case: Pass 1, the approval flow, the record of what each rental was sent. What would go: if a renewed token loses the restriction, the renewal, the re-send, the cut at the last ending and the lock around them, about half of rental/github.rs.

This is why the next step for this work is the run and not a sixth pass. Five passes have refined behavior on top of five unasked questions, and the docs already describe the result in the present tense. The run needs a person twice (install, type a code) and about ten minutes; passed over, a further review of the build before it.

Smaller findings

1. A rental's repository is set once; the renew command renews it this work

Each placement rents a new rental for one Task, and records that Task's repository on it. After that, lf machine login github code-1 should mean "send code-1 a working token for its repository", from any directory. Built, the directory wins over the record. Proposed: the record wins; the directory is read only for a rental that has none yet, which is one made by hand with lf ondemand rent, and its first sign-in sets it. Run for a rental that already has a repository from another repository's checkout, it renews as asked and does not mention the directory.

This deletes a concept: no rental moves, so the "it is now for … only" line, the settle of the repository left behind and its test go, and the earlier review's left-as-built wrinkle (a sign-in records the new repository before it knows the outcome) can no longer strand a running rental. Counterexample kept: someone who rented by hand, signed in for A and now wants B on the same box. They rent another; a rental reaching one repository is already the rule (gh keeps one token per account).

2. A dropped connection during a renewal should not cost the approval this work

A renewal spends the stored refresh token the moment GitHub answers. The new tokens are stored only after three more requests ask what the new token reaches. If any of those fails to connect, the new tokens are dropped and the store is left with a spent one: the approval is gone. With a terminal the next command asks for a code without saying why; with none, such as the background check that ends a repository's last rental, it is lost silently and the next scheduled placement stops at "no approval and no terminal". The case with least reason is that ending: the new token goes to no rental, and it is still checked.

Proposed: store what GitHub issued first, then check; GitHub answering "reaches more" discards it, no answer keeps it for the next settle to check. If the proposed first run shows a renewed token keeps its restriction, the re-check after renewal goes entirely, and with it three requests per renewal and the two beliefs in the table.

3. A token that has ended says so in the list this work

lf ondemand list prints GitHub until 17:00 for a token that ended an hour ago, because the record still matches. The time is already in hand: GitHub ended 17:00 once it has passed. No request, no new record.

4. Left as built

One token per repository shared by its rentals, with everything that follows from it (a renewal ends what other rentals hold, the re-send, "not delivered"): forced by GitHub, and the record makes it legible. The cut at the last ending. Six requests to GitHub per placement. An ending that waits behind a typed code and says so. lf ondemand login github keeping a working approval without renewing it.

5. Other outcomes separate

This Machine settles each repository by itself, from the background check that already visits every rental: it delivers a missed token and removes the 8-hour clock while this Machine is awake. It needs its own rule for when to renew. Codex and OpenCode outlive the rental: nothing signs either out before the sandbox is deleted. Both are in the plan as deferred; neither is a Task.
