Actions → concepts → APIs

Watch a pane → subscription reading → Reader::step scopes retain_reads; inherit_reads carries that scope into its workers. Ask once → request → task.changes reads Git afresh.

{"type":"request","id":"changes","operation":{"kind":"task.changes","issue":"LOO-1","base":"parent","head":null},"select":null}

No new wire field, setting, or database record. The shared in-memory map keeps parallel checkout reads useful; ordinary reads and writes bypass it.

Failure and recovery

A failed read uses the existing error path. Subscription retries and checkout refresh remain in place. Return or panic restores the worker's previous scope, so later one-shot requests stay fresh. Restarting needs no cache recovery; Git remains the source.

Two limits remain intentional: a subscription may reuse an answer, and several Git commands do not form an atomic snapshot of a changing checkout.

Review questions — resolved by the brief

  1. Must clients close a pane or request a cache bypass? No; the ordinary request is fresh.
  2. Should each pane own its cache? No; shared subscription answers are required.
  3. Is an atomic checkout snapshot required? No; this change scopes retention.
