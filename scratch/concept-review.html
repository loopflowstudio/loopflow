Signing Machines in: do the concepts line up?

LOO-957, reviewed before anything is built (plan at 9e3edfaf85). Area taken: everything a person touches to get an agent on any Machine signed in to Claude, Codex and the services: the sign-in command, the approver setting, the per-Machine provider list, the launch check, the view and the retry. It is wider than the plan's first slice because the names chosen there become every later slice's surface.

existing is code on main; proposed is the plan or this review's change to it.

The interaction, walked once

A fresh Mac mini, an agent step headed for it on Codex.

  1. lf --machine mini -a codex implement. On mini the harness asks codex login status: exit 1. The step skips Codex, finds no other provider, stops: mini has no Codex login.
  2. The person runs the sign-in. lf SSHes to mini, starts codex login --device-auth, reads the URL and code, opens them in the Chrome profile approvers.codex names.
  3. The person approves in that browser. Whatever account that profile is signed in to now owns mini's Codex login. Codex writes ~/.codex/auth.json on mini itself.
  4. Failure: the approval page says device code is off for this account. Codex exits non-zero; lf prints Codex's error and where to enable it. Nothing was written.
  5. Recovery: they enable it and run the same command again. The next launch reads the new login from mini; nothing was fixed at an earlier launch.

The mechanism holds up. Every awkward spot in that walk is a name or a setting left over from the model this plan replaced: lf used to copy logins onto Machines, so the brief had words for "share" and "own". Now each provider's client creates the login on the Machine, so for Claude and Codex every login is that Machine's own.

The biggest mismatch: "share" and "own" survived the redesign

Plan as written 
machines:
  mini:  {logins: [claude, codex]}
pools:
  home:  {logins: [claude]}
ondemands:
  code:  {provider: runpod,
          logins: [claude, codex, github]}
# on mini itself
own_logins: [codex]

lf machine connect mini codex
#  mini keeps its own Codex login; skipped
lf machine logins mini
#  codex  own

Five places answer "who signs mini in to Codex?", and the answer that wins is "nobody, though you asked".

Proposed 
ondemands:
  code:  {provider: runpod,
          logins: [claude, codex, github]}
# unset: every provider signed in here

lf machine login codex mini
#  Approve Codex for mini in Chrome (Work)
#    with code ABCD-1234
#  mini: Codex signed in (ChatGPT)
lf machine logins mini
#  codex  signed in  ChatGPT

One list, where its only reader is. An owned Machine is signed in to what someone signed it in to, and the view says so live.

Why it's right: under the copy model, "share with mini" was a standing policy that ran without asking, so it needed a list per Machine and an opt-out. Under the provider-flow model a sign-in is a person (or a rental's prepare) asking for one, so the list belongs to prepare and the opt-out is not running the command. What survives: the default of "every provider signed in here" for rentals, and the services' existing refusal to replace a different account on receive. What it passes over: the brief's direction that "each Machine has its own list" and "a Machine can assert its own logins", which were written for the copy model. This is reversible; if an owned-Machine list earns a reader later (say, lf machine logins marking a wanted provider as missing), it can return on machines.<name> alone.

Questions

  1. Owned Machines and the provider list:
    1. only on-demand templates carry logins (chosen);
    2. owned Machines carry one too, and lf machine logins marks a listed provider that's signed out;
    3. back to the plan: machines, pools and on-demands.
  2. own_logins:
    1. gone; not running the command is the opt-out (chosen);
    2. kept for rental prepare only;
    3. kept as planned.
  3. The verb:
    1. lf machine login / logout / logins (chosen);
    2. lf machine connect / disconnect as planned;
    3. lf machine sign-in.
  4. Argument order:
    1. login <provider> [<machine>…] (chosen);
    2. login [<machine>] <provider> with disambiguation by known names.
  5. Retry set for --refused:
    1. probe signed out, or refused with no run since (chosen);
    2. probe signed out only; usage-limit Machines are named by hand;
    3. record a sign-in time per Machine, as planned.
  6. Should a usage-limit refusal count as "refused" at all, given that signing in again only helps if the approving browser now holds a different account?
    1. yes, that's the point of the retry;
    2. no, only signed-out logins.
