Why: a crate below execution gives every other edit back only its own compile time, and loopflow_harness compiles in 0.8 to 0.9 s against execution's 24 to 26 s. The short loop reaches a PR only while it stays in format files, which was 6 of 215.

What moves the typical edit proposed, its own Task

model ┬ storage ┬ execution ─ ops ─ application
      └ harness ┘

Code placed above the rest saves its own edits everything beneath it. ops is in 110 of 184 grouped execution PRs, 34 alone; the plan's estimate is about 20 s off an ops edit. It takes removing 42 references to ops from 17 lower modules, and it lengthens the chain, which the Task said it would rather not.

Choice made for review: ship the crate. It is the representative extraction and measurement the Task asks for, its boundary is honest (no store, no process table, checked by cargo tree), and the measurement is what picks the next cut. Passed over: dropping the branch and filing ops with nothing merged, which keeps the workspace one crate smaller and loses the decoder loop and the two benchmark cases that will measure the next extraction. Merging a crate can be undone by moving the files back.

What is larger than this work

Loopflow's own tags have a writer and a reader with nothing between them

<lf:skill:NAME>, <lf:message> and <lf:suggest_actions> are a format Loopflow owns. A single owner would be one module in loopflow-model with the tag names, the writer and the parser, used by execution's prompt and by the crate's readers. That is a move of Launch and lf_tag down one crate and a change to prompt assembly; it also frees the name Launch.

Three things are still called Provider

The credentialed service, the rental host and, in prose and the glossary, the AI client. Unchanged by this branch, which took the code's word, harness.
