2. Biggest mismatch: collected sandbox analytics siloed outside lf session usage & search

What is wrong at HEAD (afdf8d0b45): Collection (rental/recovery.rs → machine_records) already captures every Session, event, history row, turn, provider transcript, and capture file from Modal while it runs and before give-back. Yet lf session usage --task/--wave/--days/--weekly, lf session history search, and Desktop’s TelemetryDashboardView / TaskHistoryView read local tables only — so all Modal work disappears from analytics unless you look up each Session UUID individually via a mutually-exclusive lf session usage --session <id> flag with a bespoke JSON schema.

Before · Split local analytics vs. single-Session copy flag

Built at HEAD
machine_records (Modal copies: Session, History, Turn, Transcript, Captures) ├─ lf session list (text) ──► shown (from modal-1) ├─ lf session history show <id> ──► shown ├─ lf session usage --session <id> ──► bespoke JSON, conflicts w/ --task/--wave/--days ├─ lf session usage --task/--wave ──► 0 rows (local session_history only!) ├─ lf session history search <q> ──► 0 hits (local provider files only!) └─ Desktop Telemetry / TaskHistory ──► 0 rows (reads [SessionHistory] local only!)
  • Running 5 Modal Tasks (200 Sessions) leaves lf session usage --wave coverage and --days 7 blind to Modal.
  • lf session usage has two incompatible JSON contracts under one command name.
  • Collected transcripts sitting in SQLite cannot be found by lf session history search.

After · One SessionHistory & search surface with origin

Proposed in Plan §4.1
agent_sessions + history.turns (local) ──┐ ├──► conversation_history() machine_records (Modal copies) ──────────┘ │ SessionHistory { ..., origin: Option<SessionOrigin> } ├─ lf session usage --days/--task/--wave/--project ├─ lf session usage --session <id> (same turns/origin) └─ Desktop TelemetryDashboard & TaskHistoryView local provider files ────────────────────┐ ├──► lf session history search <q> machine_records (kind='transcript') ─────┘ └─ hits tagged with origin (from modal-1)
  • One analytics model: explicit nullable origin: Option<SessionOrigin> on SessionHistory (Rust + Swift + DTO fixtures) distinguishes local work (null) from collected rental work ({machine_id, label}).
  • Zero double-counting: import_records forbids local origin; moved Sessions keep remote turns in machine_records and local turns in history.turns.
  • Abrupt-loss safe: projects directly from RecordKind::Session + RecordKind::Turn even if a capture manifest never settled before termination.

3. Two other splits to unify in §4

Session readiness across all server starts

Plan §4.2

HEAD Only server/recovery.rs (for TaskConversation) calls launch_failure and records start_failure. server/wake.rs::start_stopped and ops/human_session.rs::restart_provider spawn doomed PTYs silently, and session_ending hides start_failure for non-Task Sessions.

Proposed Generalize launch_failure to any &LfSession. Call it in server/recovery.rs, server/wake.rs::start_stopped, and ops/human_session.rs::restart_provider; record/clear agent_sessions.start_failure consistently and render could not start: ... for every Session that has one.

Ended-rental settlement & live Machine list

Plan §4.3

HEAD commands/rental.rs::end skips refresh(), so an already-dead sandbox fails SSH and demands --force. commands/machine.rs::listings prints dead modal-1..N SSH routes in lf machine list. OndemandCommand::Add leaves Modal burst modal_sizing: None in JSON.

Proposed Run refresh() first in lf machine end (matching reconcile) so already-gone sandboxes settle cleanly without --force. Omit ended rentals from default lf machine list and lf machine status while keeping SQLite rows for from <label> attribution, explicit <label> queries, and lf ondemand list. Store modal_sizing: Some(Burst) on Modal OnDemand add.

4. Concrete walkthrough of the failure & recovery paths (§4)

PATH 1 · ABRUPT SANDBOX LOSS

Modal terminates modal-1 mid-Task

Periodic SSH collection already imported turns and transcript into machine_records. Person runs lf machine end modal-1 → refresh() sees sandbox.gone → settles ended, returns Tasks locally, prints ceiling estimate (no --force). lf machine list no longer shows dead modal-1. lf session usage --task MTG-421 and lf session history search both show the Modal turns tagged from modal-1.

PATH 2 · STEER WITH NO LOGIN

lf --machine modal-1 steer <id> "..."

Stopped repository Session uses codex with no login. server/wake.rs::start_stopped runs launch_failure → records Waiting for a harness: codex has no usable login… on agent_sessions.start_failure without spawning a doomed PTY. lf session list shows could not start: codex has no usable login… instead of silent unknown. After lf machine forward modal-1 delivers valid auth and a new steer wakes it, start_failure clears.

PATH 3 · BAD LOGIN REFRESH

lf machine forward modal-1 --task MTG-421

Files replace atomically over SSH stdin. On modal-1, restart_provider checks launch_failure before stopping the provider: if the refreshed file is still invalid or for the wrong harness, it records start_failure and returns the exact login error instead of printing “Resuming …” and dying silently in a PTY. With valid auth, it restarts the thread and clears start_failure.

5. Choices made for review & open questions

None of these choices are irreversible once shipped, so the bold defaults are written into scratch/plan.md §4 for the next implement pass. Reply with a number and letter (e.g. 1b, 2a) to override any choice.

1. How should collected rental usage and transcripts appear in analytics commands?
  • 1aChosen in plan §4.1 Unify into SessionHistory, work-scoped lf session usage, and lf session history search with an explicit nullable origin: Option<SessionOrigin> (Rust + Swift + DTO fixtures), while keeping lf session usage --session <id> as single-Session drill-down.
  • 1b Keep work-scoped lf session usage and lf session history search strictly local-only and require lf session usage --session <id> per Session UUID (current HEAD).
2. How should lf machine list treat ended rentals whose SQLite rows remain for history attribution?
  • 2aChosen in plan §4.3 Omit ended rentals from default lf machine list (and unlabeled lf machine status) while keeping the rows in SQLite for from <label> attribution, explicit <label> queries, and lf ondemand list rental history.
  • 2b Keep listing ended rentals in lf machine list with an explicit (ended) badge instead of omitting them.
3. Should lf machine forward --task/--session fail fast if the refreshed login is still unusable for that Session’s harness?
  • 3aChosen in plan §4.2 Yes — check launch_failure after file delivery before stopping/restarting: record start_failure and return an error if the harness still has no usable login, instead of printing “Resuming …” and exiting silently inside the held PTY.
  • 3b Always stop and respawn the provider blindly after file delivery, letting the held PTY report any auth error asynchronously.
