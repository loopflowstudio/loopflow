One interaction, as built — and where it breaks

# Repository already has repo.tracker.linear.team in .lf/config.yaml.
# A Linear Project "Billing" already exists with issues.
$ lf wave plan connect billing 'Billing'

What happens today (ops/linear.rs:628 → ops/wave_lifecycle.rs:85):
  1. connect_async sees Wave "billing" is not in the store yet.
  2. It calls wave_lifecycle::add(repo, "billing", None).
  3. add() creates the Wave + local Project, AND immediately calls sync_after_save().
  4. sync_after_save() drains uncreated() → sends createProject("billing") to Linear.
     Linear now has a brand-new empty Project named "billing".
  5. connect_async resumes, finds existing Project "Billing", unlinks the brand-new
     "billing" Project, and links "Billing".
     Result: an empty orphan Project "billing" is left behind in Linear.

Failure / served race (Desktop / Machine server):
  In a served request, add()'s sync_after_save() runs on a background thread via
  after_reply while connect_async is looking up "Billing". If createProject is in
  phase='sent' when link_wave_project_in runs, connect fails with:
    "Wave …'s Project is being created in the tracker; link it once that lands"

Recovery on the proposed path: connect_async registers the Wave locally without triggering a tracker drain; link_wave_project_in binds the existing Linear Project directly (zero createProject requests, zero race). If linking fails (unknown Project name, offline), the Wave stays registered with a local Project and a retry of lf wave plan connect billing 'Billing' succeeds cleanly.

Biggest mismatch: lf wave plan connect <new-wave> <existing-project> creates a duplicate Project in Linear first.

In the product, connecting a Wave to an existing Linear Project links that Project and creates nothing. In the code, connect_async delegates Wave creation to wave_lifecycle::add, which eagerly drains the tracker queue before connect_async runs link_wave_project_in. Alongside it, wave_lifecycle still passes the Initiative-era ActionOwner::Wave to sync_after_save instead of the Wave's ActionOwner::Project.

Larger than this Task (stated plainly, not built here):

  • Queued create field snapshots: tracker_actions.value_json snapshots a Task's fields at enqueue so retire_wave_in has to patch task_project on removal. Reading live fields at send time is a tracker-drain redesign of its own.
  • Desktop's Project sheet vs inline Objective detail: BacklogView's title line already shows WaveHeaderProject and its Objective › disclosure already shows WaveProjectView; the ··· → Project menu opens a 500×420 sheet with the same two lines (also used by openHistoricalReference). Dropping the sheet once historical Project links are retired is a small Desktop UI pass.
