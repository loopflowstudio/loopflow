How things reach a Machine

The area taken: every way one part of Loopflow reaches another, on one Machine and between Machines. LOO-926 changes one of those ways, and the question "is this the phone's protocol, without SSH?" can only be answered against all of them.

Nothing here changes code or the plan. Solid boxes exist today (the branch counts as today where marked). Dashed blue boxes are proposed.

One interaction, three clients

A Task lives on mini. From somewhere else, put it on hold, then open its conversation.

From the laptop's terminal, on main
lf task hold T→ Clap, then re-spelled as a command line→ ssh: version probe→ ssh: credential delivery (launches only)→ ssh: env preamble + lf task hold T→ mini's lf parses again, writes its store
The conversation: lf --machine mini resume S → ssh → a relay on mini → mini's server at held.sock → holder → PTY. This half needs mini's server; the hold does not.
From the laptop's terminal, on the LOO-926 branch
lf task hold T→ ssh: env preamble + lf server stdio→ hello, {"kind":"task.hold"} on stdin→ mini runs the operation, answers, exits
Same typed message the phone sends. One request per SSH connection; subscribe, session.start and attach are refused, "naming the resident server". The conversation still takes the relay path above.
From Desktop on the laptop
Desktop→ laptop's server, machine.sock→ command line prefixed --machine mini --repo-id R→ a local lf→ the terminal path above
RegistryQuery.onMachine builds the prefix. It carries a guard that throws "Live Task observation is unavailable on this transport"; whether Desktop's remote path hits it today was not checked.
From the phone
phone→ WebSocket to mini's server, /v1/machine→ hello, {"kind":"task.hold"}→ mini's server runs it
One lasting connection. Live subscriptions work. The conversation opens on a ticketed connection at /v1/ticket. Admission is Tailscale: mini asks tailscale whois and admits its owner's other devices. Needs mini's server, and carries no credentials.

When it goes wrong

  • mini's server is down. The phone can do nothing. The laptop can still hold the Task, but cannot open the conversation ("Loopflow server is not running").
  • mini runs an older lf. Phone: incompatible. Branch: "mini runs lf 0.16.0…; update it with ssh -- 'mini' 'lf install'". Main: the probe's "lf versions differ" line.
  • mini's lf dies mid-write. All paths end at "outcome unknown; inspect the affected work before retrying". No path can retry safely.
  • Recovery of a view is the one thing that works the same everywhere: the holder keeps a ring of output and a view reconnects at the byte it had reached.

The biggest mismatch

"Reach a Machine" is one idea with two complete implementations that cannot do the same things.

Phone's way (WebSocket)Laptop's way (SSH)
What travelstyped Operationa command line plus environment (the branch: typed, for writes)
Who is let inthe owner's Tailscale devicesanyone with the SSH login
Needs a server thereyesonly for conversations
Live updatesyesno
Carries your loginsnoyes
Works on a rental or a Machine with nothing installednoyes

So the WebSocket cannot replace SSH. A rental is not on the tailnet, lf install has to get there somehow, and a login has to arrive before an agent can start. What can change is what SSH is: today it is a second API; it could be a third way to carry the first one.

Today

  • Protocol A, revision 5: machine.sock, WebSocket.
  • Protocol B: command lines and environment over SSH, assembled in several places.
  • Branch: one request of Protocol A, inside Protocol B's launch.

Proposed not built

  • One protocol. A client opens a connection to a Machine and sends operations.
  • Three carriers for that connection: the local socket, the tailnet WebSocket, SSH stdio.
  • One thing outside it: getting lf onto a Machine (install), which is a plain SSH command by nature.
The same interaction, proposed not built
terminal, Desktop or phone→ a connection to mini (socket, WebSocket or ssh stdio)→ hello: who is asking, which Machine they expect→ task.hold · subscribe · session.attach
Over SSH, lf server stdio hands the connection to mini's resident server when one is running, so subscriptions and conversations work, and answers reads and writes itself when none is. The SSH login is the same user, so this is not the forwarded-socket case server.md:113 forbids for the phone; the view relay over SSH already does it for held.sock.

Tested against the hard cases

  • Normal: lf task hold T is one SSH connection and one parse. Desktop's remote Tasks update live because the laptop's server can keep a connection to mini open.
  • mini's server is down: reads and writes still answer, as the docs promise today. Conversations say the server is not running, as today. Nothing gets worse.
  • Recovery: views keep the holder's byte-offset reconnect. Writes keep "outcome unknown". A lasting connection that drops is reopened by the client, as the phone does now.
  • Counterexample, credentials: a lasting server must not hold secrets handed to it by a connection. So forwarding stays with the SSH carrier, sent once when the connection opens, and a Machine reached by WebSocket uses its own logins. The proposal survives, but "three equal carriers" is not quite true: SSH is the one that can bring logins.
  • Counterexample, commands with no operation: lf --machine mini install server cannot be an Operation; there may be no lf there to receive one. The command-line launch over SSH survives for that. It shrinks to bootstrap; it does not disappear.
  • Counterexample, interactive agent commands: lf --machine mini --wave product wave-operate is a session.start plus a view, both already in the protocol, so it fits once stdio can reach the resident server. Until then it needs the command-line launch too.

What this says about LOO-926

  • PR #1956 points the right way. It is the first time SSH carries the protocol instead of a command line.
  • It stops one step short of the idea. lf server stdio is documented as "answers requests, nothing more". As a carrier it would be a connection, and the single SSH launch the Task promises would be "open a connection to a Machine", with credential delivery inside it.
  • The environment preamble is the leftover. The brief already says selection should be "a field of the request, not environment". The preamble is the same problem on the SSH side.
  • Recorded on 2026-11-16, in scratch/questions.md: "This was supposed to also do credential forwarding".

Larger than this Task

  • Live remote Tasks in Desktop: the laptop's server keeps a connection to each of your Machines. Takes stdio reaching the resident server, and subscribe over it.
  • One way into a conversation: every view redeems a session.attach ticket; held.sock and the SSH relay path go. Takes care: relays from older builds recover through held.sock today.
  • Mac to Mac over the tailnet WebSocket. mini's admission already lets in its owner's other devices, so this is mostly a client. It adds a carrier; it removes nothing.

Questions

  1. What is SSH, in this product?
    1. A carrier for the one protocol, plus plain commands for install. Recommended.
    2. What it is on the branch: a one-request typed call for writes, command lines for the rest.
    3. Only the way to install lf; all Machine-to-Machine work moves to the WebSocket. Rentals would need Tailscale and a running server before their first Task.
  2. When mini's server is running, may lf server stdio hand its connection to it?
    1. Yes: the laptop gets subscriptions and conversations over SSH, the same as the phone gets over WebSocket. Recommended.
    2. No: stdio stays one request, one answer, and live remote work waits for a Mac WebSocket client.
  3. Should work on another Machine require its server?
    1. No for reads, writes and headless runs; yes for conversations, as today, and say so in one place. Recommended.
    2. Yes for everything except install. Simpler to explain; a stopped server then blocks lf task hold on that Machine.
  4. Where do forwarded logins travel?
    1. With the SSH carrier only, once per connection. A Machine reached by WebSocket uses its own logins. Recommended.
    2. As an operation any carrier can send, which means the resident server receives secrets.
  5. How much of this belongs in LOO-926?
    1. Reshape PR 1 only as far as naming: one "open a connection to a Machine" that delivers credentials, with stdio still answering one request. Everything under "Larger than this Task" becomes its own Task. Recommended.
    2. Land #1956 as built after the LOO-913 merge, and take the carrier idea up afterwards.
    3. Stop the stack here and redesign around the carrier first.

The next question

  1. When mini's server is running, what does lf server stdio do with an ordinary read or write?
    1. Runs it itself, always. Only what needs the server (subscriptions, conversations, tickets) is passed to it. A write behaves the same whether mini's server is up or down, and forwarded environment stays in the process SSH started. Recommended, and what the redesign assumes.
    2. Pipes the whole connection to the server when one is up, and runs requests itself only when none is. Anything the protocol grows works over SSH for free. A write then has two behaviors, the request needs a "do not forward again" mark and its repository as a field, and forwarded environment has to be handed to the server.

The mismatch, and a simpler shape

There are only three ways a login can come to be on a Machine, and they are the same three for every service. Today the code has them, but only names them for some services.

How the login got thereShared with the laptop?Exists today for
Its own: someone signed in on that MachinenoClaude, Codex (by hand over ssh)
Issued for it: the laptop asks the service for a separate grant and installs thatnoLinear (access token), OpenCode (device grant). claude setup-token looks like this kind for Claude; not confirmed against Anthropic's terms
Copied: the laptop's own credential, duplicatedyesGitHub token, OpenCode API key, ~/.codex/auth.json, ~/.claude/.credentials.json

Today

  • machine connect: three services, typed, checked.
  • forward: everything else, unchecked, including the two agent logins.
  • No view of what a Machine is signed in to.

Proposed not built

  • One action: lf machine connect mini claude and … codex join the other three. For a Machine you own it runs the service's own sign-in on that Machine, in your terminal. lf copies nothing and stores nothing.
  • One view: each Machine lists its five services: signed in or not, as whom, and which of the three ways.
  • One check: before any remote launch, not only a rental's: "mini has no Claude login; lf machine connect mini claude".
  • forward keeps one job: per-run secrets. A login named there still works, and the launch says it is a copy.

Tested against the hard cases

  • A rental nobody is watching. No one is there to sign in, so "its own" is impossible. It needs "issued for it" (a Claude setup token) or "copied" (the Codex file). This is where forward's login path has to survive, or where lf would have to hold a token to install, which LOO-913 just removed. The proposal does not make this case simpler; it only names it.
  • Reopen after the agent quit. With its own login on the Machine the problem is gone. With a forwarded variable it remains, unless a reopen that starts an agent counts as a launch (PR 2 can do that).
  • Does lf become an account manager again? Not for owned Machines: connect only runs the native sign-in, and the view only reads whether a login exists. Reading as whom for Claude and Codex means reading their files, which LOO-913 chose to stop doing ("Loopflow does not choose a login, interpret those files or refresh them").
  • Transport. machine credentials receive is already a typed message on SSH stdin. On the carrier it becomes an ordinary request the stdio process runs itself, and credentials::remote_command goes. Sent over WebSocket it would reach the resident server, so it stays an SSH-carrier request (answer 4a).
  • Legal. Not judged here. What the design can do is keep the three ways distinct and visible, so a copy is never made silently.

Questions on logins

  1. Should Claude and Codex join lf machine connect?
    1. Yes, as "sign in on that Machine": lf opens the service's own sign-in there and copies nothing. Recommended.
    2. Yes, and it may also install a token you give it (a Claude setup token), stored on that Machine by lf. Covers unattended Machines; lf holds an agent credential again.
    3. No. Native login and forward stay the whole story.
  2. Should lf check for an agent login before every remote launch?
    1. Yes: existence only, with the command that fixes it. Recommended.
    2. Rentals only, as today.
  3. A copied login file (~/.codex/auth.json): what should lf do when forward.files names one?
    1. Carry it and say it is a copy that shares the laptop's refresh grant. Recommended.
    2. Carry it silently, as today.
    3. Refuse it; only issued tokens and native logins are supported.
  4. Does a reopened conversation that has to start a new agent carry forward values?
    1. Yes: it is a launch. Recommended.
    2. No: only a first launch forwards.
  5. Where does this land?
    1. Its own Task, after PR 1. PR 1 only makes sure forward and machine credentials receive both travel on the one SSH open. Recommended.
    2. Inside LOO-926, as a fifth PR.
    3. First, before any transport PR.

What the providers document for sandboxes

Added 2026-11-17, after: "using an agent inside a sandbox is an extremely common use case. i am confident the providers are ok with that. we should figure out how people are doing this with companies like daytona and do the normal thing + make it as convenient and automatic as we can without claerly crossing some sort of TOS line", and "its ok if it works differently on a per-provider basis". Read from the providers' pages on 2026-11-17. This is a reading of public docs, not legal advice.

Claude

  • Hosting Claude Code in a sandbox is expressly allowed. The legal page has a section "Can customers offer Claude Code in their products?" covering "hosted sandboxes or other agent infrastructure". Conditions: the binary is unmodified, no sign-in method is removed, and "Each end user must authenticate with their own Anthropic API key, Claude subscription plan credentials, or 3P inference provider credential". legal-and-compliance
  • The line. "Anthropic does not permit third-party developers to offer Claude.ai login into their own applications, or to route requests through Free, Pro, Max, or Ultra plan credentials on behalf of their users. Moreover, developers may not collect, store, or intermediate Claude.ai credentials or session tokens — sign-in to a Claude account must complete through Anthropic's own flow." And: "Nor does it prevent an end user from signing in to the unmodified Claude Code binary with their own Claude subscription, including where a platform hosts Claude Code".
  • The documented unattended path. "For CI pipelines, scripts, or other environments where interactive browser login isn't available, generate a one-year OAuth token with claude setup-token"; "It does not save the token anywhere; copy it and set it as the CLAUDE_CODE_OAUTH_TOKEN environment variable wherever you want to authenticate". It "can only make model requests": no Remote Control, no claude.ai connectors. Bare mode does not read it. authentication
  • The documented attended path. claude auth login in a shell; with no browser it prints a URL and takes a pasted code. Daytona's guide does exactly this over SSH. Daytona guide
  • What the sandbox vendors show. Daytona's SDK examples and E2B pass ANTHROPIC_API_KEY. Docker's cloud sandboxes say "For Claude Code, use an Anthropic API key", injected by a proxy so the sandbox holds a placeholder. None of them documents carrying a subscription login file. E2B · Docker
  • Unconfirmed: community issue reports of 401s from setup tokens in containers; "Advertised usage limits … assume ordinary, individual usage" and how many parallel sandboxes that covers.

Codex

  • Preferred for headless: "prefer device code authentication (beta)": codex login --device-auth, after enabling device code login in ChatGPT security settings. auth
  • Documented fallback: "copy your cached credentials to the headless machine", with SSH and Docker commands. "Treat ~/.codex/auth.json like a password".
  • The rule for copies. The CI guide: "Do not share the same file across concurrent jobs or multiple machines." One file per runner. An ephemeral runner restores the file, runs, then writes the updated file back. Reseed when "another machine or concurrent job rotated the token first". It calls itself "an advanced workflow for enterprise and other trusted private automation" and says "API keys are still the recommended default for automation." ci-cd-auth
  • Access tokens: "intended for trusted scripts, schedulers, and private CI runners", given with codex login --with-access-token. Who can mint one, and how long it lasts, was not found.
  • Docker offers Codex "OpenAI OAuth at account scope" beside API keys, held in its secret store.

Where lf stands against that

What lf does todayAgainst the documented way
Forwards CLAUDE_CODE_OAUTH_TOKEN from your environment or Doppler into a remote launchThis is the documented unattended path.
Lists ~/.claude/.credentials.json as an agent login a rental may carry (AGENT_LOGIN_FILES)That file is the interactive session's tokens. No provider or vendor page documents copying it, and the legal page's wording on session tokens points away from it.
Copies the laptop's own ~/.codex/auth.json to a Machine while the laptop keeps using itCopying is documented; sharing one file across machines is the thing the guide says not to do. This is the sign-out the docs warn about.
Never writes a rental's refreshed auth.json backThe ephemeral-runner recipe requires the write-back.
Has no lf machine connect mini claude or … codexThe attended paths exist in both clients; lf leaves them to "ssh there and do it by hand".
Strips ANTHROPIC_API_KEY, OPENAI_API_KEY, CODEX_API_KEY from launchesMatches Claude's precedence order, where a key outranks the subscription token.

lf's position is simpler than a hosting product's: one person, their own subscription, their own Machines, and nothing Loopflow operates ever sees a credential. The lines that keep it that way: sign-in always completes in the provider's own flow; the binary is unmodified; no credential reaches a Loopflow-run service; no login is shared between people.

Proposed, per provider not built

Claude

  • A Machine you own: lf machine connect mini claude runs claude auth login there in your terminal. You approve in the browser. Its own login, refreshed by Claude.
  • Rentals and anything unattended: one setup token. lf account connect claude runs claude setup-token here, in Anthropic's flow, and you keep the token in your own secret store (Doppler today). Every remote launch that finds no login on the Machine sets CLAUDE_CODE_OAUTH_TOKEN from it. No forward.env line to write.
  • Dropped: ~/.claude/.credentials.json as something lf will carry.

Codex

  • A Machine you own: lf machine connect mini codex runs codex login --device-auth there. You enter one code. Its own login.
  • A rental while you are there: the same, at rent time: lf shows the code, you approve once.
  • A rental nobody is watching: a login kept only for rentals (CODEX_HOME=… codex login, separate from the laptop's), restored to one rental at a time and written back when the rental is given back, as the CI guide describes.
  • Dropped: copying the laptop's live ~/.codex/auth.json.
  • Counterexample, five rentals at once. Claude's one token serves all of them. Codex's rule is one file per machine, so five unattended rentals need five rental logins, or an API key, or an access token if those turn out to be obtainable.
  • Counterexample, lf holding the Claude token. If lf itself stored the setup token it would be "collect, store" in the page's words, even on your own Machine. Keeping it in your secret store, read at launch, is the same posture as an API key "in a development environment, secrets manager, or machine image", which the page allows by name for keys. The page does not say the same sentence about setup tokens.

Questions on provider logins

These replace question 7.

  1. Claude on rentals: where does the setup token live?
    1. In your secret store (Doppler), found by name without a forward.env line. lf runs claude setup-token for you and tells you the one command that saves it. Recommended.
    2. In lf's own encrypted store, like the Linear grant. One step fewer; lf stores a Claude credential.

  2. Codex on unattended rentals?

    2. Device code at rent time only; unattended rentals do not run Codex on a subscription.

  3. Should lf stop carrying ~/.claude/.credentials.json?
    1. Yes. A launch that names it says to use a setup token. Recommended.
    2. No, carry whatever is named.
