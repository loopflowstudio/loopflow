Creating a Task: do the concepts line up?

The area is creating a Task: from clicking Start to typing in its conversation, on Desktop, the phone and the Machine. That covers the request ID and its receipt, the order in which the Task, conversation, checkout and Graph come into being, the ready checkout, setup reporting into the conversation, and how a failure shows up. Reviewed at 477c4ac505 (PR #1964) against main. No code was changed.

One Start, walked through

Normal path built

  1. Start is clicked. The sheet closes into StartingTaskView, keyed by the request ID made at the click.
  2. task.create records the Task, the claim, the Graph taken up at start, the primary Session and the receipt at admitted, all in one transaction.
  3. The server holds lf session resume <id> and answers with the receipt, the SessionRecord, the TaskOverview and the row.
  4. The pane shows the typed words, then Checkout ready 0.2 s and Graph code started. The provider then takes typing.

Failure and recovery built

  1. Checkout fails, for example a branch-name collision or a locked ready checkout. The pane prints Checkout failed: …, and session resume exits before the provider starts.
  2. The navigator row still says Working · "Starting code". The Task's Graph is taken up but has no run, and nothing records that setup stopped.
  3. Recovery means reopening the conversation. The receipt is still admitted, so setup runs again. Only someone who read the pane knows to do that.
  4. If the receipt is gone (the brief says request IDs are remembered "for a day"), reopening goes through the ordinary admit_workspace. The Graph is then never started.

The biggest mismatch: setup is owed by the receipt, not the Task

Whether a conversation runs setup is decided by creation_receipts.milestone = 'admitted', matched on the Session (human_session.rs:1018). Setup's last act is to move that row to started (record_setup_launch). That gives the receipt two jobs: it is the record that makes a repeated Start give the same answer, and it is the Task's to-do list. The two want different lifetimes. A repeat only needs to be answered for about a day. The to-do list has to last until setup succeeds, which is why the plan says "nothing prunes creation_receipts; whatever later expires request IDs must keep admitted rows."

Everything setup needs is already on the Task: whether it has a checkout (task.worktree), whether its Graph is taken up (task_graph_row), and whether that Graph has ever run (its GraphProcess history).

Before built

  1. session resume looks up an admitted receipt for this Session.
  2. Found: run setup (checkout from local refs, take the ready checkout, start the Graph), then mark the receipt started.
  3. Not found: admit_workspace (the ordinary checkout, with fetch).
  4. Setup fails: the pane shows it, the row says "Starting code", and nothing else knows.

After proposed

  1. Opening a Task's conversation asks the Task: does it have no checkout, or a Graph that was taken up and has never run?
  2. Then run setup. Checkout always comes from local refs (the ready checkout first), and the Graph starts through lf task run, which already refuses to start a second one.
  3. The receipt answers repeats and nothing else, so it can expire after a day as the brief says. admitted is its last milestone on this path, and started and record_setup_launch go.
  4. A failed step is recorded on the Session as an observation. The Task's position reads "Setup stopped: checkout failed", and reopening the conversation runs it again.
  5. Spans keep their request ID because the held argv carries it, not because of the receipt row.

Checked against three cases. Normal path: same lines, same timing, and one database read fewer. A backlog Task started with lf task run, whose conversation opens mid-launch: setup sees a Graph with no run yet and launches lf task run a second time. This is safe only if task run dedupes a launch that is still in flight, not just a registered run. That is question 2. A Task adopted with --worktree: it has a checkout, so setup only starts the Graph, which is what creation with run means. Something that has to keep working: a released filed+run receipt still answers outcome_unknown, and -b keeps run_requested.

What it costs: one predicate on the Task in place of a receipt lookup, and one Session observation for a failed step. What it removes: admitted_task_creation, record_setup_launch, the started milestone on the conversation path, and the rule that receipts can never be pruned.

Smaller findings

  1. Three shapes of one Task in the answer. Desktop reads overview (to fill taskWork) and row (for the navigator). receipt.task is the storage row the CLI prints. If row can produce what taskWork needs, the answer becomes receipt + session + row, and TaskCreated/TaskCreateAnswer become one type built where the row is read.
  2. No revisions on the answer. The brief's shared model drops the pending row at a reading at or past the answer's revisions. Today it is replaced when the Task first appears in a listing. This is shared by all four sibling Tasks, so it probably belongs with whichever one builds pending changes, not here.
  3. Setup lines are terminal-only. They work on both clients because both show the terminal. They also disappear with the terminal's scrollback. If the observation in the proposal is built, the lines can be printed from it.

Questions

1. Who owes setup?
  • 1a: The Task (proposed). Setup runs when a conversation opens on a Task with no checkout or a Graph that has never run, and receipts can expire.
  • 1b: The receipt, as built. Receipts are never pruned, and the brief's "remembers it for a day" changes to "forever".
  • 1c: Keep it as built in this PR and file the move as its own Task.
2. If 1a: can lf task run start a second Graph when two launches race?
  • 2a: Check it, and if it can, make task run claim the launch inside the transaction that takes up the Graph.
  • 2b: Only setup launches for a Task created with run, and other entry points leave that Task alone.
3. A setup step that failed: where does a person see it?
  • 3a: In the pane, and also as the Task's position ("Setup stopped: checkout failed"), from a Session observation.
  • 3b: In the pane only, as built.
4. The answer's Task.
  • 4a: Receipt + session + row, one type, with overview dropped if Desktop can fill taskWork from the row.
  • 4b: Keep all three. Each client reads the shape it already uses.
5. Revisions on the answer.
  • 5a: This Task adds them to task.create's answer and drops the row by revision.
  • 5b: Leave it to the sibling Task that builds pending changes.
