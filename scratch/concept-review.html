Nobody issued a command for engbot. The tracker gets a Project because Desktop drew the Wave. Offline, every tick for an unbound Wave fails before its repository exchange, and the failure is swallowed (catch { succeeded = false }); Desktop's Project row shows nothing about the unbound state at all, because the "not in Linear yet" line is computed in the CLI printer from repository config, not carried on the wire.

Biggest mismatch: sync makes tracker Projects, and Desktop syncs on a clock

lf wave sync = make an unbound Project in the tracker, then exchange and read. Desktop calls the same served write every five minutes and when a Wave opens. Opening Desktop on an upgraded store makes a Linear Project for every live Wave it shows. The unbound hint is CLI-only.

Sync refreshes; connect makes. refresh_wave drops its create_wave_project call: sync reads and delivers queued saves, on any surface, on any clock. The command whose job is tying a Wave to its tracker Project, lf wave plan connect <wave>, is the retry verb: the create error, the status line, the upgrade note and docs name it. The drain still makes an unbound Project before sending a Task into it (a person filed that Task).

The sentence goes on the wire. ProjectSummary.unbound: Option<String> (required, nullable), written in Rust — "not in Linear yet; `lf wave plan connect ledger` makes it" — for a live Wave's untracked Project in a connected repository. The CLI prints it; Desktop's WaveProjectView prints it. The printer's own config read goes.

Passed over: keeping sync as the creator and giving Desktop's clock a separate non-creating refresh (a new served op or flag for one distinction the verbs can already carry); keeping it as is (background tracker writes for Waves nobody touched — outward-facing and not cleanly undone). Kept from slice 13: binding queues the local order, whichever caller binds.

Smaller as a result: one fewer caller of create_wave_project; the printer stops reading repository config; wave_sync_makes_only_its_own_project and the two a_wave_sync_binds_…_lost_create_reply_left tests become connect tests (connect already runs the same create and its lost-reply recovery).

What stays

  • Tracker down at lf wave create: the Wave is recorded unbound and the command fails, naming the retry.
  • Asana footer search as the synchronous create's lost-reply recovery.
  • Served tracker failures append "inspect the affected work before retrying" (generic engine::Error::written; not this Task).
