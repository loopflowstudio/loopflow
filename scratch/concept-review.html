Bare conversations already hear Task progress at their next turn. Say so.

Built from scratch/loo-826.md, scratch/questions.md, docs/sessions.md, server/boundary.rs, server/wake.rs, harness/task_updates.rs, harness/context.rs, store/sqlite/task_work.rs

The last open question asked whether bare conversations should get next-boundary updates. The code already gives them: an interactive bare launch keeps its turn hooks, the server answers its prompt boundary with an update, and the Task is found from its checkout. The docs and the notes said "nothing". The change is to the words and one test, not the behavior.

"Deliver at the next boundary only for bare or unreachable conversations." (Jack Heart, Task comment 164b4dd8)

Why the code does this

Built. native_args(…, managed=false) keeps Claude's Stop and prompt hooks, without crossSessionInbound. boundary.rs answers every non-stop moment with task_updates::claim, which has no managed filter. session_task_ids joins on session_membership: task_id or the Session's cwd being the Task checkout. idle_conversations keeps only WorkSource::is_managed, so no wake.

Next implement

Proposed. docs/sessions.md:

A conversation you start with a bare `lf <skill>` in a terminal is never
woken; it hears its Task's progress when you next type.

A server::boundary test pins it: interactive bare Session in a Task checkout, step settles, prompt boundary answer carries the update, wake_idle sends nothing.

What would break it

Interactive bare hooks leave with the owner (LOO-821: "dont really care about intermediate states as long as we remove the owner eventually"). When they do, bare conversations lose next-turn updates. That Task's design has to choose; this one doesn't.

Questions

None open. Steers waking (1) and bare conversations (2) are settled by the design and reversible; both are written in scratch/questions.md.
