Ending & Reopening Parent Tasks

Area reviewed: ending and reopening a Task when it has open children — covering complete, pending completion at Graph end, live-work guards, reopen of abandoned Tasks, and how CLI, Desktop, and iOS present and execute them. Widened beyond the --children flag because parent completion currently shares one state machine with Graph-end completion and one blocker check with checkout deletion.

Biggest mismatch: parent completion inside the pending request lifecycle

Counterexample that breaks the kickoff plan

LOO-12 has open child LOO-15 running a Graph. Someone runs lf task complete LOO-12 --children abandon. Under the kickoff plan, request_family_completion writes FamilyCompletionRequested into tasks.completion_request before the live guard runs, then records the blocker in completion_error. The person sees the error and leaves LOO-15 alone to finish. Later, LOO-15 parks at ship-review and background reconciliation runs on LOO-12 — settling the armed request and silently abandoning LOO-15. The same trap hits when LOO-12's own PR is unmerged and a brand-new child is filed before merge.

Before (HEAD + kickoff plan) Superseded
lf task complete LOO-12 --children abandon
1. Writes tasks.completion_request = FamilyCompletionRequested (or new RehomingCompletionRequested)
2. settle_completion hits live guard or unmerged PR → writes completion_error, leaves request armed
3. Later reconcile_delivered_task sees armed request → silently abandons or rehomes children nobody asked to touch again
After (revised plan) Proposed
lf task complete LOO-12 --children abandon
1. Check state, PR merge, open children, and live work (unresolved_work minus idle held conversations) — zero writes on refusal
2. Single IMMEDIATE transaction: complete_task_now re-checks invariants, marks LOO-12 done, settles or rehomes children, clears any stale Graph-end request
3. tasks.completion_request stays leaf / Graph-end only — zero new event kinds, zero version skew with released lf

Choices made for review

All choices below are written into scratch/plan.md and reversible in code. Reply with a number and letter (e.g. "2b") to change any of them.

  1. If completing a parent fails (unmerged PR or a running child), should Loopflow remember the request and finish later, or refuse cleanly with nothing saved?
    • 1a (chosen) Refuse cleanly, save nothing. You fix the blocker or re-run when ready; a child can never be abandoned in the background after you got an error.
    • 1b Save the request and auto-settle later. Once the parent's PR merges or the child stops running, Loopflow completes the parent and applies your earlier choice automatically.
  2. When a child is parked idle at ship-review (no Graph running, just its open conversation waiting for you), should --children abandon allow abandoning it?
    • 2a (chosen) Allow it and close the idle conversation. Only block when a Graph is actively running, a headless run is live, or the conversation is mid-turn.
    • 2b Block whenever any conversation window is open. You must manually close each child's conversation before --children abandon will proceed.
  3. In Desktop, when every open child already has a merged PR (so nothing would be abandoned), which button should be the default?
    • 3a (chosen) Complete & Finish Children first (marks the merged children done), with Move Children second. When any child is unmerged, Move Children is default and Abandon Children is destructive.
    • 3b Complete & Move Children is always the default button, even when every open child is already merged.
  4. When moving children up with --children rehome and the grandparent Task is already done, abandoned, or deleted, where should the children land?
    • 4a (chosen) Nearest open ancestor, else top-level. Open children never get moved under an already-closed parent.
    • 4b Direct grandparent as stored, even if closed. Keeps the exact link chain regardless of whether the grandparent is still open.
