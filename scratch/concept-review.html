LOO-1084: where a Task runs, and where a steer went

Post-build concept review of HEAD (8092a8ef19) against base 250e266b4a. Core delivery, runs_on, reading, and TaskSteerReceipt are built; four conceptual mismatches remain in the built code and are proposed in scratch/plan.md (Slice 4) for one clean pass before gate.

Area taken: how one Machine sees and steers a Task another Machine runs — Task ownership as surfaces read it (lf task status, lf task list, lf wave show, selection states, Desktop rows), peer resolution (TaskPeer), Task steers and their receipts (lf steer, task.steer), and how inbound tracker/hub/Git direction reaches the owning Machine (watch_owned_work, planning_scope_checks). Excludes container lf server supervision (LOO-1081/1083), remote file/shell/session viewers (LOO-1083), and Desktop Swift badge UI.

One interaction on HEAD: what works, and where the model still lies

First, the sibling-sandbox path that motivated LOO-1084 works end to end built: modal-3 polls Linear/Asana/hub/Git every 30 s while it holds open claims and delivers incoming steers to live workers and stopped primary Sessions once. laptop reaches registered mini directly over SSH and never replays a lost reply.

Biggest mismatch: TaskPeer turns a placement preference into a running owner

Loopflow's boundary contract (docs/dev/machines.md) is explicit: placement selects where Work belongs, not whether it is currently running. When a Task is unowned, nothing runs anywhere — it is in Backlog. Because TaskPeer::resolve falls back to task_execution_route for unowned Tasks, it creates a synthetic peer with since: None. Every downstream caller then has to cope with a peer that has no claim, and three of them produce false output.

On HEAD (work_route.rs:18-64) current 
struct TaskPeer {
  machine: MachineRef,
  since: Option<i64>,       // None for unowned Tasks!
  registered: Option<Machine>,
}
// resolve():
//   ownership.runs_on(&local) => Some(claim)
//   ownership.owner.is_some() => None (owned here)
//   None => task_execution_route()  // Wave pref!
//
// Consequence:
// - status prints "Runs on mini; read from its server."
// - status JSON: reading=owner, runs_on=null
// - steer offline: waits 15s, lies "mini reads it
//   when it next syncs" with runs_on=null
Proposed (Slice 4) in plan 
struct TaskPeer {
  runs_on: TaskRunsOn,       // always a real claim
  registered: Option<Machine>,
}
// resolve():
//   let runs_on = ownership.runs_on(&local)?;
//   if move_awaiting_arrival() { return None; }
//   ...
//
// Consequence:
// - unowned Tasks read & steer locally, instantly
// - TaskReading::Owner ALWAYS has runs_on: Some(...)
// - print_remote_detail drops its None branch
// - steer fallback only fires for a real remote owner
# After Slice 4 (Wave has `set machine mini`, MTG-500 is unowned, mini is offline): laptop$ lf task status MTG-500 --json | jq '{reading, runs_on: .task.runs_on, state: .task.state}' {"reading":{"kind":"here"},"runs_on":null,"state":"unstarted"} laptop$ lf steer MTG-500 "use 15s timeout" Saved steer_4a…; nothing reads it until MTG-500 runs ← instant, saved here + synced, no false promise
