A Wave is one Project — as built

LOO-995 concept review, pass after slices 1 and 2, 2026-11-23. Branch at 1e1e114989, read against origin/main (7487986a30). Replaces the 2026-11-22 page, which reviewed the plan before it was built.

Area taken: a Wave and its one Project across a Wave's whole life — create, rename, connect to a tracker, a Task joining and moving, removal — locally and in a Linear repository. That is what the branch now builds; the earlier page took only the tracker link.

One interaction, as built

$ lf wave create scratchpad
$ lf wave status scratchpad        # Project   scratchpad (local) · started
$ lf task create --wave scratchpad 'x'
$ lf wave rename scratchpad sandbox
$ lf wave status sandbox           # Project   scratchpad (local) · started   ← stale (QA 2026-11-23)
$ lf repo tracker ... connect Linear
                                   # the Project's create goes out named "scratchpad"

Failure two, read from code: in a connected repository lf wave add queues the Project's create at once. lf wave remove before the drain sends leaves that action queued, so Linear gets a Project for a Wave that no longer exists. uncreated (tracker_actions.rs:970) skips retired Waves when queuing, but nothing retires what is already queued.

Both failures are new with this branch: on main a Wave's Projects came from chapters or the Initiative; here every Wave makes one from its own name.

Biggest mismatch: a local Project's name is a second copy of the Wave's name.

Until a Project is linked, its name has no source but the Wave. Once linked, Linear owns it and the import mirrors it. So "whose name is it" has one answer at each moment, and the code should hold that answer, not a copy.

Recommendation proposed

Before

Wave create copies the name into the Project. Rename edits waves and the authored files. The Project keeps the old name forever; the queued create sends it.

Remove retires the Wave; a queued create still sends.

After

lf wave rename renames the Wave's Project too while it is unlinked (external_project_id IS NULL): name and slug follow, the queued create reads the new name. A linked Project keeps Linear's name; renaming in Loopflow does not write to Linear (no new tracker action).

lf wave remove retires the unsent tracker actions of the retiring Waves' unlinked Projects, so nothing is created for a removed Wave.

Made for review: rename follows only while unlinked. Passed over: always pushing a rename to a linked Linear Project (a new tracker update action — scope, not a fix), and dropping the local Project's name column (released lf reads projects.name). Both are reversible.

Normal path: rename scratchpad→sandbox, status says Project sandbox (local). Failure: rename after linking — status keeps the Linear name, which is right because that is where the person sees it. Recovery: none needed; the next import still mirrors Linear's name. Counterexample tried: a rename arriving from another Machine over Git — if the Project edit is an ordinary ProjectName plan edit with its stamp, it crosses with the Wave's rename; implement checks this (not run).
