Concept review after slice 12

Area: a Wave's one Project and how it becomes a tracker Project — lf wave create, lf wave plan connect, lf wave sync, the drain, and every edit that waits for a tracker binding. Taken because slice 12 moved Project creation out of the queue and into commands; everything that assumed "unbound means a create is queued" is in question.

One interaction, with its failure

$ lf wave create billing            # Linear unreachable
error: wave/billing has no tracker Project yet: …. Run `lf wave create billing` again to make it.
$ lf task create --wave billing a ; lf task create --wave billing b
$ lf task edit b --rank 1           # b above a, locally
$ lf wave status billing
Project   billing (local) · started
          not in Linear yet; `lf wave sync billing` makes it
$ lf wave sync billing              # Linear back
Made wave/billing's Project in Linear.
                                    # a, b created in Linear in creation order: a, b
                                    # next inventory read: order a, b — the rank edit is gone

Two things a person notices: the failure names one retry (lf wave create) and the status names another (lf wave sync) for the same state; and the reorder made while unbound is silently lost (plan Remains 0).

Before (slice 12 as built)

"Unbound" was designed as "a create is queued; everything else waits behind it." Slice 12 removed the queued create but kept the waiting rule in owner_tracker. Fields the create carries survive by accident; order, which the create does not carry, is dropped.

Proposed (slice 13)

Binding sends the order. When a Wave's unbound Project gets its tracker id (accept_linear_project_in, any caller), queue one Order action with the Project's current local order if it holds two or more Tasks. It waits behind their creates as order edits already do. owner_tracker's queued-create fallback for Project owners goes: a Project's tracker is its binding, nothing else.

Passed over: holding order edits on unbound Projects in a connected repository (storage would need the repository's tracker config, which it doesn't read), and accepting the loss (a reorder a person made disappears without a word). Asana has no order form and retires the action, as today.

Also: the create failure names lf wave sync <wave>, the verb status already prints; the drain comment names the upgrade as its case.

What stays

  • Tracker down at lf wave create records the Wave unbound and fails the command (questions.md). Rolling back store rows, seeded files and their commit is larger than the state it avoids, which upgrade already produces.
  • A Task send into an unbound Project creates the Project first. Without it, upgraded Waves error on every pass until someone syncs.
  • Asana footer search as the synchronous create's lost-reply recovery (Remains 3).

Questions

  1. Order made while a Project is unbound: (a) binding queues the local order once — chosen; (b) hold order edits until bound; (c) accept the tracker's creation order.
  2. Retry verb for an unbound Project: (a) lf wave sync <wave> everywhere — chosen; (b) keep lf wave create in the create error.
  3. Tracker down at lf wave create: (a) Wave recorded unbound, command fails — as built; (b) Wave recorded, command succeeds with a warning; (c) record nothing.
