Biggest mismatch. SQL currently calls a history projector that validates a prepared launch request. Moving that request into storage would bring settings and launch construction with it. Erasing the request to arbitrary JSON would accept malformed manifests that currently count as evidence gaps.

No open product choice. The proposed cut keeps commands, stored bytes and history output unchanged. Green rules below mark unbuilt behavior.

Proposed ownership

PendingHistory / PendingInput → SqliteStore::read_history_input → HistoryInput { capture, artifact key, scoped events, names } → application project_input_history → SessionHistory.

Storage keeps selector resolution, names, truncation and scoped event reads. The application keeps the complete SessionCaptureManifest, AgentProcessRequest and their existing deserialization. One selected-input reader replaces SQL decode_history; one application projector serves full, recent, single-input and activity reads.

Normal → failure → recovery

An input recorded under Task A remains attributed to A after the Session binds to B. A malformed exec request makes its manifest invalid, retaining today's gap count and current-input fallback rules. A later valid observation is read through the existing projector; inspection writes no repair and launches no provider. Missing manifests and orphaned native turns retain uncertainty.

The counterexample that shapes the API

An old input has invalid metadata. Activity already has enough newer entries to stop. Today it never reads that input. Eagerly loading every selected input's events would add work and could fail an otherwise readable page. Keep settled before the per-input evidence reader.

Recent history still retains every unfinished input. Exact drills remain complete. Selection releases its savepoint before events are read, as today; this cut adds no page-wide snapshot or longer SQL lock.
