The biggest mismatch: one Task run, three liveness owners

A person thinks of one thing: LOO-953 is running code from realign. lf task run prints one id for it (8a132276, the Graph run). The code holds up to three OS processes, each with its own pid on its own record:

  • Task carrier, task_graphs.run_pid: the lf task run loop. It spans Graphs and the handoff to shipping. Task state "moving" and retirement read this (durable.rs:353, task_retirement.rs:70), and so does the double-run refusal (carrier_evidence).
  • Graph run, graph_processes.pid: the child the carrier spawns. lf graph list --runs, lf task status's run lines and the docs' "what runs" read this.
  • Ship carrier, task_ship_events.pid: the same lf as the Task carrier after handoff, written on a second record.

Nobody can see the carrier. It has no id they're shown and no command that lists it, yet it decides whether the Task is "moving" and whether a second lf task run is refused.

Counterexamples to test (reasoned from the code, not run):

  • The carrier is killed and its Graph child lives. Status lines say the run is current while the Task reads idle. The child's carrier check (graph.rs:79–101) should stop it at its next step, so the window is one step long. Inside that window, does a new lf task run start a second Graph?
  • The Graph child dies and the carrier lives, e.g. between Graphs or at the handoff. The Task reads moving with no run in lf graph list. This is correct behaviour, but there's nothing to show the person.

The Task run already exists in the data as the task_graphs cursor plus its carrier. What it would take: name the record, print its id from lf task run, hold the pid there only, and give Graph runs inside a Task run a result and no pid of their own. That rewrites the carrier/handoff code and a wire DTO, so it is its own Task.

Recommendation

For this PR: the model is right. Every owner record answers its own liveness, there is one rule behind it, and a crash now reads as stopped. Keep it. The one change that belongs here is finishing 4b's own goal: change "running as Graph process" in engine/task.rs:58 and session_move.rs:132 to "Graph run", along with the two user docs and task_operate.md. The JSON key moves with the GraphProcess* → GraphRun* follow-up, since it's a wire field.

Larger than this work: the Task run as one record (above), and showing ExecutionResult instead of the three-state projection. Neither is needed for LOO-953 to land.
