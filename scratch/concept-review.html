The biggest mismatch: "sibling" that sits in the chain

The Task asks for "siblings consumed by orchestration over a longer downstream chain". The kickoff plan called the new crate "beside storage" and then had it name loopflow_storage types and open test stores, which puts it after storage. The cause is the transcript module holding two ideas.

Bars are a sketch of which crates compile, not measured widths. The only measured numbers are LOO-650's: application edit 27.4 s, execution edit 57.5 s, storage edit 65.5 s.

The rule that keeps it true as the work meets surprises: a function that takes a SqliteStore, an OsProcess or observe::Cache stays in execution and calls down. The crate never gains a dependency to keep a file whole.

What is larger than this work

This extraction cannot move the typical edit much, by the plan's own arithmetic

A crate placed below execution saves every other edit only its own compile share: for 7k of 115k lines, a second or two of 57.5 s. The kickoff plan predicted "a few seconds" for 15k. Code placed above the rest saves its own edits everything beneath it. ops is in 110 of 184 grouped execution PRs and 34 alone; as the crate above the rest it would spare an ops edit about 20 s of 57.5 s.

It was passed over because the Task prefers siblings to a longer chain, and because 17 lower modules reference ops (42 references; engine and machine another 78). Untangling those is its own Task. The plan now says so plainly and names ops as what follows if this crate's measured drop is inside noise.

Three things are called Provider

Credentialed service, rental host, and (in prose) the AI client. Renaming is outside this Task. It would take a rename of rental::Provider and a decision on whether the glossary keeps "provider" as a synonym for harness.
