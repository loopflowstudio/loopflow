What must follow a login switch?

Historical review · superseded by two-item repair direction. Fresh Claude follows the selected login. A legacy Keychain item can retain the previous one. The current iteration retains USER plus one legacy item after every switch; see live-recovery.md.

Before / proposed after

Observed: A → B updates both items. B → A updates USER; legacy stays B. Plain Claude sends A. The third item can also remain stale.

Proposed, pending choice: keep the same switch command and define its compatibility promise. No new account concept, table or lifecycle. A Keychain item is a storage address, not another provider login.

Draft usage: “Switch once with lf account use claude=work@. Plain Claude uses that login; running Claude picks it up on its next request.” Running-client behavior remains unverified here.

Recovery must keep the conversation

Save rotated credentials before switching. Keep Session identity, history and input working. A limit may change the login; explicit models stay fixed and completed Graph steps stay done.

Still unobserved: old Codex refresh overwriting the new login; a no-model spent line contradicted by a usage poll; live resume/move/reload; and Claude refresh invalidating a rental token. Native fixtures do not settle these. Disposable or idle real logins are still needed.

Decision for the next step

  1. Which items must agree after every A → B → A switch?

    1a. Current Claude’s native item. Older items may differ; narrows the original expectation.

    1b. USER and the supported legacy item. Keeps the two-item expectation; identify that legacy item when several exist.

    1c. Every existing item in the service. Expands scope; needs enumeration and update behavior.
