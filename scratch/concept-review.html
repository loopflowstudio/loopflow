Where does a remote Task's workspace live?

LOO-1083 concept review, 2026-11-23, at 20fa14b217 (kickoff design only; no code built yet). Area taken: opening a Task's workspace (Files, Changes, Save, Shell, Session) when another Machine owns it, across CLI, Desktop and Mobile, plus how the server, wire and stores decide which Machine answers. That whole area is what the plan rebuilds, so the review covers all of it rather than one slice.

proposed marks what the revised plan builds. Everything else describes code on this branch today or the kickoff plan. The plan in scratch/plan.md has already been rewritten to the proposal; nothing is implemented.

One interaction, with its failure

A Task runs on modal-1. The laptop still has a checkout of it from before it moved. Jack opens the Task in Desktop and clicks the Session.

Today

Desktop reads plan.list → reference.workspace = laptop checkout (stale row, stamped local) Desktop pins location = laptop Files → laptop bytes (wrong) Shell → laptop $SHELL (wrong) Session→ session.resume answers modal-1 → guard: location ≠ record.workspace → "The conversation belongs to a different Machine or checkout; nothing was opened."

Two routers disagree: Desktop's location and Rust's ownership. The guard is the referee and refuses.

Kickoff plan

Desktop reads runtime.owner = modal-1 every request carries expected_owner = modal-1 server checks route == expected_owner Files/Shell/Session → routed to modal-1 (right) Task moves to modal-2: every open pane → conflict{actual_owner} panes invalidate, drafts parked at (modal-1, /work/checkout) "moved" notice → Reopen

Fixes the routing, keeps two routers. A move becomes an error on every pane, and a draft is filed under a Machine nobody can save to.

proposed The Task is the address

Desktop sends Task id only server resolves ownership → modal-1 (pooled ssh peer) Files/Changes/Save/Shell/Session → modal-1 Task moves to modal-2: task.get subscription re-routes (same id); next reading names modal-2 Files/Changes reload; header says modal-2 draft saves to modal-2 if base revision still matches, else the existing save conflict keeps it Shell on modal-1 keeps running, labelled modal-1; reopening it on modal-2 → ended → New shell modal-2 unreachable → unavailable{machine: modal-2} → "modal-2 is unreachable · Retry"

The biggest mismatch: two routers for one fact

The person knows one fact, "this Task is on modal-1". The code keeps it in two places: Rust's ownership log and Desktop's pinned location. Every bug in MTG-421 is the two disagreeing. The kickoff plan fixed which one wins by having the client send its opinion on every request and the server refuse when they differ. That keeps both routers and adds a referee.

Before (kickoff)

  • expected_owner on task.status/get/detail/changes/diff/file/files/runs/files.watch/save, task.shell.*, session.attach/continue/start
  • conflict {expected_owner, actual_owner} error and its row on every surface
  • Desktop resolves the owner itself, threads ownerMachineId through every call
  • Placement guard at SessionsView.swift:716 kept
  • Drafts parked at (machine_id, checkout)
  • "Task moved" notice + Reopen on Desktop, Refresh on Mobile

proposed After

  • Requests name the Task; the local server alone resolves and routes
  • Subscriptions re-route when task_ownership advances, same id; task.files.watch sends one whole-tree invalidation
  • Panes read their Machine from the answer (reference.workspace.machine_id, attach answer)
  • Placement guard and SessionsWorkspace.location deleted with the rest of the location stack
  • Drafts keyed by (Task, path, base revision); task.save's revision check decides
  • Running terminals stay on their Machine; a stale shell_id on the new owner answers ended → New shell

Questions

  1. When a Task moves, a Shell already running on the old Machine:
    1. keeps running, labelled with its Machine, until the person closes it built into the plan
    2. is closed by the move, like the agent Session
    3. stays but its pane is detached and shows "on modal-1 · reattach"
  2. An unsaved draft after a move:
    1. saves to the new owner when the base revision matches, else the save conflict built into the plan
    2. always asks before saving to a different Machine than it was opened on
  3. The Desktop shell table and operation are named desktop_shells / lf desktop shell while Mobile uses them too:
    1. leave the names; the wire says task.shell.* built into the plan
    2. rename to Task shell everywhere in this Task (adds a migration)
    3. file the rename as its own Task
  4. lf open with a remote-only Session:
    1. accept both lf open --machine X and lf --machine X open, one field built into the plan
    2. only lf open --machine X; root --machine keeps meaning "run there"
