Do a Task's Wave, Project and tracker issue line up?

Area reviewed: how a Task belongs to a Wave and reaches a tracker, with the whole LOO-995 branch in (chapters gone, no first Project, tasks.wave_id, the placement rule). Picked because slice 1 changed the one thing every tracker path leans on: whether a Task has a Project.

One interaction, walked

A repository connected to Linear. Someone runs:

lf wave create billing ; lf wave create billing/refunds
lf wave plan connect billing                  # links billing to a Linear Initiative
lf task create --wave billing/refunds 'Refund a mischarged invoice'

Base (main)

lf wave create made a first Project; the Task joined it; the Project and the issue both went to Linear. A coworker sees the issue.

This branch

Nothing makes a Project, and connect links an Initiative, not a Project. The Task has no Project, so Task::goes_to_tracker is false and no create is queued. Linear never sees it. QA step 5 shows this as intended ("a tracker queue that leaves plan-only Tasks out").

Recovery today: someone makes a Linear Project inside the Initiative by hand, runs lf wave sync, and from then on new Tasks join it. Tasks filed before that never go: tracker_actions::uncreated skips them for good. A Task with no Wave in the same repository does go, as a team issue.

The biggest mismatch: a Wave makes a Task private to Loopflow

The plan line was "A Task with no Project sends nothing to a tracker." It came from the pipeline, not from the direction quoted in the plan, which asked "how we tell with a tracker that a task in a certain wave": a Task in a Wave is expected to show up there. The plan also already answers where the Wave lives: "in Loopflow's plan, carried by Git and the hub". That holds for a Task in an ancestor's Project. It holds just as well for a Task in no Project.

A Task goes to the repository's tracker whether or not it has a Project. No Project means an issue in no Project: a Linear team issue, an Asana task in the repository's team project. Standalone Tasks already take this path (linear/actions.rs sets projectId only from a task_project; Asana always adds the repository project), so nothing new is built.

Deleted: Task::goes_to_tracker, its two callers (task_create.rs:115, ops/task.rs:2922), and the (t.project_id IS NOT NULL OR t.wave_id IS NULL) clause in tracker_actions::uncreated. The local_planning test that checks no create is queued flips to expect one. docs/work.md loses "stays out of the tracker". The fix removes a precondition.

Passed over: making connect create one Linear Project per Wave. That brings back "a Project made for the Wave", which this Task exists to remove.

Before

Filed in a Wave + no Project above → plan only, forever. Filed in no Wave → tracker.

After

Every Task in a connected repository → tracker; its Project there is its Project, or none.

Counterexample kept: someone wants a Wave's Tasks off Linear. Nothing asked for that, and a repository opts out of the tracker as a whole today. If it's wanted it is a Wave setting, not a side effect of having no Project.

Larger than this work

An lf process from before an install that inserts a Task writes project_id and no wave_id; that Task lists in no Wave. The planning writer's fallback covers plan records, not a direct row insert. Closing it would take an insert trigger filling wave_id from the Project, or nothing if the upgrade-skew window is accepted.
