The mismatch

Claude's /clear fires SessionStart, and lf selects the new conversation. In Codex, /new now gets past lf (the relay used to refuse it), but lf goes on recording the first thread. When the person comes back, lf resume opens the conversation they left. A transparent session manager shouldn't do that.

Evidence: Codex already reports the switch

client b: thread/resume t1, nothing else
client a: thread/start          → b gets thread/started {id: t2, parentThreadId: null}
client a: thread/fork t1        → b gets thread/started {id: t3, forkedFromId: t1, parentThreadId: null}

On a Session's private app-server, lf opens its own threads before the observer subscribes. So every top-level start the observer sees after that point comes from the person's client.

Still open (a fact to check, not a product choice)

A thread the TUI starts uses the TUI's own config, not lf's prepared instructions and hooks. If codex --remote accepts -c overrides for its thread/start, lf context reaches the new thread. If not, that limit is Codex's, and the design says so.

Questions

    a. Yes, both change the selection (implied by the model; this is what goes forward)
    b. Only /new; a fork stays in Codex's history and lf doesn't record it
  2. If Codex can't carry lf's context onto a thread the TUI starts:
    a. Follow anyway, with no lf context on the new thread (proposed)
    b. Follow it and also inject context as an observer interjection on its first idle moment
