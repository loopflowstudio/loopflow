3. The Biggest Mismatch in HEAD — Before & After

The core mismatch in HEAD: first_read_with treats "has this clone read its plan?" as "has every configured carrier individually recorded has_read()?" Because a fresh Git clone has no repository_id before read #1, Git runs on read #1 (creating a brand-new local ID), and then Hub suddenly becomes eligible on read #2 — firing an SSH call the Hub cannot recognize, writing a permanent carrier error, and stalling offline-Hub laptops for 5 s every 60 s forever.
Built in HEAD (plan_carriers.rs:279–381) Built in HEAD
Read #1 → repo_id is None → hub_needed = false → Git fetches, mints repo_91c2
Read #2 → git_needed = false, hub_needed = true! → SSH to Hub with unknown repo_91c2
Hub error recorded → 60 s cooldown → Retries every 60 s forever

Requires ~90 lines of tangled per-carrier flags (git_needed, hub_needed, git_errored, hub_errored, do_git, do_hub, stamped) multiplexing two independent carrier gates through one shared cooldown key.

Proposed: One Clone-Level First-Read Gate Recommended
git_read || hub_read → true? return Ok(false) (0 ms)
neither has read → if any errored, check 60 s cooldown
run eligible carriers → Git (if remote) + Hub (if repo_id)
either succeeds → clone is read; all later reads 0 ms

One rule, ~40 lines, zero per-carrier cooldown multiplexing:
• Git-only or Git+Hub (unbound): read #1 fetches Git → read #2+ instant.
• Hub-only (--bind): read #1 reads Hub → read #2+ instant.
• Git+Hub (bound): read #1 runs both concurrently; if Hub is off, Git marks the clone read → read #2+ instant.
• Remote name changed (Git-only): git_row.peer != peer → git_read is false → reads the new remote once.

4. All Findings & Scope

F1. Make first-read a clone-level "any current carrier has read" gate, not "every carrier must succeed" This work (LOO-1113)

In plan_carriers::first_read_with, if either the current Git remote row or the current Hub row already has has_read() == true, return Ok(false) immediately. Only when neither current carrier has read yet does before_first_read check the 60 s error cooldown and run whichever carriers are eligible (Git if a remote exists; Hub if configured and store.repository_id(repo).is_some()).

Test to add: A fresh clone with both a bare Git origin and a configured Hub (lf machine hub): read #1 fetches Git and sees the remote Task; read #2 runs neither Git nor Hub (0 spawns, 0 Hub calls, no Hub error recorded). Also test an unreachable Hub + reachable Git on a bound clone: read #1 succeeds via Git and read #2 does not retry the offline Hub.
Passed over: Keeping per-carrier AND semantics (causes the read-#2 unknown-repo SSH failure and recurring 5 s offline-Hub stalls). Reversible.

F2. Give plan-reading one owner instead of 7 before_first_read calls in bin/lf.rs (and fix lf task detail) This work (LOO-1113)

Currently bin/lf.rs sprinkles before_first_read / before_first_read_cwd across 7 dispatch branches while commands/tracker.rs has an 8th, and lf task detail <id> was missed (it fails with Task <id> is not registered on a fresh clone instead of syncing on miss like lf task status <id>).

Recommendation: Move the CLI first-read call into the non-subscribing CLI entry points (waves::ls, waves::status, waves::show, waves::list_tasks, waves::list_closed_tasks, screens::print for PlanBoard, tracker::run_async) — or into a single CLI read gate — keeping served requests non-blocking (!journal::request::active()). Route screens::task_detail's lookup through planning_sync::find_task on miss so lf task detail <id> behaves like lf task status <id>. Reversible.

F3. Clarify --subscribe on unread clones (store-only vs background first-read) This work (LOO-1113)

HEAD changed lf task list --subscribe to skip before_first_read so all 5 CLI --subscribe commands and server Start::Subscribe streams read the store alone. That keeps frame 1 instant and read-only, at the cost that a fresh clone opened directly via --subscribe (or Desktop subscribing before any one-shot Request) stays empty until another command runs.

Recommendation: Keep CLI --subscribe store-only (matches lf repo tracker --subscribe's read-only contract and current HEAD), unless opening a fresh clone directly in Desktop via subscription alone is a common path — in which case firing a non-blocking background first-read on unread clones (option 2b) gives instant frame 1 and automatic frame 2 arrival. Update docs/dev/planning.md:296 to note that served requests (not subscriptions) trigger after_command. Reversible.

F4. Discovering a teammate's very first Task in an already-read empty clone Separate outcome

A clone whose first read saw an empty remote marks has_read() == true; LOO-1110's exchange_unowned skips repositories with zero local open Tasks and zero active Waves. So a teammate's later first Task arrives only on lf task sync or a lookup by ID. docs/work.md and docs/dev/planning.md in HEAD now document this honestly.

What it would take: If empty clones should discover new remote plans automatically, a separate Task would need to add low-frequency polling (or periodic re-read) for empty-plan repos while staying within LOO-1110's idle-server budget.

F5. Changing a remote's URL in place (git remote set-url origin <new>) Separate outcome

plan_carriers.peer stores the remote name ("origin"), not its URL, so repointing origin in place keeps seen_seq = 0 and does not trigger a new first read.

What it would take: Store or hash the resolved remote URL beside the remote name in plan_carriers while keeping lf repo tracker displaying the short name. Rare today; separate unless it comes up.

5. Questions to Decide

Every choice below is reversible after shipping. Reply with numbers and letters (for example, 1a 2a 3a 4a).

1. On a Machine that uses a Hub, what should happen on the second lf task list in a fresh Git clone (or when the Hub is offline)?
In HEAD today, the first lf task list fetches from Git and shows the whole plan, but the second lf task list tries to SSH to your Hub with the clone's brand-new random ID (failing with "hub has no checkout" and repeating every 60 seconds). If your Hub is turned off, every read also stalls up to 5 seconds once a minute forever even though Git already read the plan.
  • 1a (Recommended) Once the clone has read from either Git or the Hub, later reads stay instant and local — fixes the second-read Hub failure and offline-Hub stalls. Hub-only clones (with no Git remote) still pull from the Hub on their first list; Git+Hub clones read once and let the Hub join normally on saves and syncs.
  • 1b Keep requiring both Git and the Hub to each succeed once (current HEAD) — accepts the second-read SSH failure and 5-second stalls every minute whenever a Hub is unreachable or doesn't yet know a fresh Git clone.
2. If your very first command in a fresh clone is a live stream (lf task list --subscribe), what should it do?
On main, lf task list --subscribe waited up to 5 seconds to fetch from Git before printing its first line, while lf plan list --subscribe and lf repo tracker --subscribe did not. HEAD made all five --subscribe commands read the local store only — instant startup, but an unread clone stays empty until you run a one-shot list or lf task sync.
  • 2a (Recommended) Keep all --subscribe streams store-only (current HEAD) — always instant, never touches the network, consistent across every --subscribe command.
  • 2b Print the local store immediately, then fetch once in the background if unread — first line is still instant, and remote Tasks arrive automatically as the next update a moment later.
  • 2c Wait up to 5 seconds to fetch before printing the first line on lf task list --subscribe — restores main's blocking behavior for that one command.
3. Confirm the offline first-read cooldown already built in HEAD: when a fresh clone's first list fails offline, when should reads try again?
Adopted headless in HEAD. If you clone a repo and run lf task list with no network, it waits up to 5 seconds and falls back to the local store.
  • 3a (Recommended) Wait 60 seconds before retrying automatically (current HEAD) — repeated lists while offline are instant; once back online, a list a minute later (or lf task sync anytime) fetches the remote plan.
  • 3b Retry on every read — fetches immediately as soon as you reconnect, at the cost of stalling up to 5 seconds on every read while offline.
4. Confirm empty-clone background behavior already built in HEAD: if a clone's first read sees zero Tasks and a teammate adds the first Task later, should the background server keep polling that empty clone?
Adopted headless in HEAD to preserve LOO-1110's idle-server budget (no background git fetch on repositories with zero local Tasks and zero Waves).
  • 4a (Recommended) Keep empty clones quiet (current HEAD) — zero idle background fetches; a teammate's very first Task arrives via lf task sync or looking it up by ID. Once the clone has any open Task or Wave, background sync runs every minute.
  • 4b Poll previously-read empty clones too — file a separate Task so a teammate's first Task appears automatically in an empty clone, accepting periodic background git fetch on idle repos.
