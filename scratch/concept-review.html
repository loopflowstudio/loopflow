One interaction, walked

Someone has the Session list open. An agent stops calling tools and says nothing for 120 seconds; its Session becomes available without anything being written. Another agent's process is killed; its Session stops reading as running. A third finished yesterday and reads Dead forever.

To draw that list, a read collects what SQL cannot know (SessionProjectionInputs), asks the OS, checks nothing moved (pin), then projects. Today the collecting step reads 20,732 activity rows and 772 Sessions to end up asking the OS about 37 processes and registering one wakeup.

The biggest mismatch: an ended agent is asked about anyway

The inputs exist to hold what SQL cannot answer. An ended agent is something SQL has already answered. Carrying it through the observation step is what makes the read proportional to history instead of to what is running, and it is why the kickoff plan needed a special case in read_summary for the list while the single read kept the old route.

Today, and in the kickoff plan's single read

  1. SQL returns every started agent with completed_at (really agent_ended_at).
  2. Reading::acquire builds RecordedProcess { ended }.
  3. evidence_by returns Dead before looking at the OS.
  4. The map carries Dead back to read_summary.

Proposed, for every read

  1. SQL returns agents that have not ended. Those are the ones to observe.
  2. Reading::acquire asks the OS about each.
  3. read_summary reads agent_ended_at IS NOT NULL from the row: Dead. Otherwise the map; missing means Unknown.
  4. SessionProcessIdentity.completed_at is deleted.

The same idea settles the other two lists. Deadlines come only from the activity row that available_sql would read: an open Session, its current agent, not ended. That guard is written once and used by both, so a change to who can be available moves the wakeup with it.

proposed
SELECT DISTINCT act.observed_at + ?1 FROM agent_sessions s
JOIN session_activity act ON <the guard available_sql opens with>
WHERE <s.id=?3 | s.agent_process_id IS NOT NULL>
  AND act.observed_at > ?2 - ?1 ORDER BY 1

Graph runs for the list are every unended run. For one Session they stay that Session's run, so a single read never asks the OS about every Graph on the Machine.

What the plan now says

Changed by this review: identities are the unended agents in both reads and completed_at leaves SessionProcessIdentity; the deadline statement shares its guard with available_sql; a test shows an ended agent's fresh activity registers no deadline. Kept from the kickoff plan: no index on observed_at, every unended Graph run for the list, pin unchanged, session_activity joins the plan-checked tables, and deadlines first as the slice that shows whether the plan check widens the change.

Larger than this change

The 120-second rule lives in available_sql, the deadline statement and a literal in store_revision_session_activity_update. Making it one thing takes a migration that rebuilds the trigger. The second read in pin goes away only if every identity write advances the sessions revision, which is also a trigger change. Neither is needed at 50 µs a read.
