LOO-626: the sync fence covers a network fetch

Task LOO-626 · concept-review step (headless) · 2026-10-26

Built from: scratch/questions.md, rust/loopflow/src/ops/sync.rs, rust/loopflow/src/ops/git_operation.rs, Jack Heart's steer of 2026-10-26

Outcome: the design changed, so this goes back to implement. There's no open product choice. Jack's accepted rule ("clear the lock when we realize sync is stuck or errored or whatever") already settles this.

Actions → concepts → APIs

Person / agent action        Concept            API
─────────────────────        ───────            ───
open a Session, run ci-fix → write the checkout → no gate (CheckoutBusy deleted)
lf sync                    → history rewrite   → SyncOperation fence (flock)
sync stops on conflicts    → resolver          → fence released; --continue adopts
remove a checkout          → removal safety    → require_idle / cleanup_* (kept)

The mismatch

The fence is supposed to exclude other writers only while history is actually being rewritten. Today it is taken before the fetch:

begin_sync_operation(repo)      // flock held
fetch_target(repo, onto)        // unbounded network
plan_sync(...); pin_target(...); merge(...)

If the fetch stalls, prepare_agent_process refuses every agent launch in the checkout. That is the "stuck" case Jack ruled out. The fetch rewrites nothing. sync_with_plan already fetches before taking the fence.

fetch_target(repo, onto); plan_sync(...)   // no fence
begin_sync_operation(repo)                 // fence from here
pin_target; revalidate_start; merge; finish_sync

Also

The SyncOperation doc comment says the fence is held "only while Git's merge, abort or commit steps run". It also covers the force-push and the Task PR range writes. The comment should say what the code does.

A hung push still holds the fence until the process dies. The fence has to stay across the push, because the range record lands after lock_task_pr_mutation drops. This is a known limit, not a question.
