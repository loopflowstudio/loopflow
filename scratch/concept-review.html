Opening work: do the concepts line up?

LOO-935 at 6e82d34aba, reviewed against main (470da475). Nothing here changes code.

Area taken: how a person gets to their work, meaning lf open (now absorbing lf workspace), overviews in Rex, Herdr and cmux, Desktop's saved arrangements, and lf resume. That's the user-facing half of this PR. The store reduction underneath it has no product concept of its own, so the only part of it reviewed here is that Desktop now owns its layouts.

One interaction, start to finish

Monday morning, you want to work through the Product Wave.

lf open --wave product --workspace→ Rex: new session, one tab per started Task + a Workspace follower tab→ each tab shows Task & workflow (lf task view), not the conversation→ to reply in LOO-935 you leave the tab and run lf open --task LOO-935 --tab→ a second tab appears for the same Task

The failure: the conversation is already open in Desktop. --tab reports where it is and opens nothing. That leaves you with a brief in Rex and the conversation on the other screen.

The recovery: lf resume <session> moves input here, or you go to Desktop. Both work. But by then you've needed three commands and two ideas of a "Task tab" to get where you were going.

The biggest mismatch: an overview you can't talk in

A person opens a Wave to work its Tasks. But each overview tab shows a brief, and the conversation is one command away in a different tab. There was a reason: an overview of twelve Tasks must not launch twelve agents or take input from views already open. That rule holds. What doesn't hold is giving the brief the same name as the conversation and then sending the person out of the tab to reach it.

Now

Rex session "product"
├─ Workspace   (follower)
├─ LOO-935     lf task view LOO-935
├─ LOO-937     lf task view LOO-937
└─ …
# to reply:
$ lf open --task LOO-935 --tab   # another tab

Proposed

Rex session "product"
├─ Workspace   (follower)
├─ LOO-935     Task & workflow · ⏎ enter conversation
├─ LOO-937     Task & workflow · ⏎ enter conversation
└─ …
# ⏎ in the tab: the same view becomes the
# conversation, by lf open's rules; open
# elsewhere → says where, offers lf resume

Under this proposal there's one "Task tab". It starts as the brief and becomes the conversation where it already sits. Nothing launches until you press Enter. Task & workflow already takes n, p and l; Enter would hand the terminal to the same path lf open --task --here takes, so it adds no new owner.

What breaks it: a Task whose conversation is on another Machine. --here already routes there, so the tab would attach remotely, which is the same as typing lf open --task X --here in it. A Task in the backlog has no Session yet. Enter gives it its first one, the same as lf open does today. Both cases go through the existing path.

Smaller findings

Proposed The follower gets its own hidden command. The six hidden flags move to an internal subcommand that Rex's Workspace tab runs, so lf open --help and OpenArgs hold only what people type. This is smaller and more direct: one public shape, and one internal one.

Proposed Dashboard slots are one command. lf desktop dashboard slots query:<id> reads the slots with no stdin and writes them with stdin, and lf desktop layout is deleted. After this PR, nothing called "layout" exists in lf.

Open question: --diff in an overview. Either it means Changes for every Task, which is costly and hit the walkthrough bug, or it goes away and Changes is one more key in Task & workflow, like Enter above.
