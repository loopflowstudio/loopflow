Which lf runs a release?

LOO-691 · step: demo · 2026-10-30 · from rust/loopflow/src/ops/release.rs, release/README.md, scratch/questions.md, PR #1780

Updated after Jack proposed a separate release home. The fetch fix is settled. The open question is who carries it: the daily release is performed by the host's installed lf, so a fix to release itself only helps the release after the one that ships it. Decide whether that lag is the contract (question 1).

The fetch-on-miss shape holds up: the remote is the truth, the local repo is a cache, and every consumer of a sha passes through one of two chokepoints. No change proposed there.

The mismatch: the fix doesn't reach the run it fixes

The release host runs its installed build on its stream. PR #1780 lands on main, then ships in the next release — which the host performs with the old build. So the very next daily release can still stop at unknown revision and need one manual fetch and rerun. Only once the host installs that release does the fix take effect.

That lag is general: every fix to lf release run is one release late on the host. Today's README records it as accepted:

The release host runs its installed `lf` on any stream; it need not follow
`dev`. To release with a fix the installed build lacks, `lf install --dev`
first: a main build refuses a store missing main's migrations.

Alternative wording if the host follows dev (1b):

The release host follows `dev` (`lf install --dev`), so each release runs
main's release code, including fixes not yet shipped.

The counterexample for 1b is that last recovery row: once the host follows dev, it can't step back down to stable until stable catches up. Under 1a the only cost is one manual step per release-code fix.

Jack's proposal: a release home that follows dev

A dedicated release lf with its own LF_HOME and store, on dev. It runs main's release code. Your main home, its Sessions and its stream don't move.

# release host
LF_HOME=~/.lf-release lf install --dev
LF_HOME=~/.lf-release lf release run patch   # the release-run job

This removes 1b's counterexample: when main is bad, you reinstall the release home and your main store is never touched.

Before a release home is safe, regressions need a source it can read.

Decided

2b: after #1780 lands, the host installs a dev build so the next release uses the fix. With 1c, that install goes in the release home.

Questions

  1. Where does the release home read regressions from?
    1. Linear: a regression is a Linear label plus a version, which any home can read.
    2. GitHub: a regressed-in:v0.15.3 label on the bug's issue or PR, read the same way the release already reads PRs.
    3. Your main home's store, read-only, from the release home. A dev build reading a stable store couples the two stores' schema versions again.
    4. Split the run: the release home cuts and publishes, and your main lf moves stable.
