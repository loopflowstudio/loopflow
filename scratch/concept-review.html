Showing an agent a change

Concept review for Task d92894, written before any code, 2026-11-18. Nothing here is built. Anything on a gold edge is proposed; everything else exists today.

The area taken. The Task is about two writers, the ones behind lf commit and PR descriptions. Both are instances of something wider: lf putting a change in front of an agent. The review covers every place lf does that, because the plan as written would have added a new way to do it beside the ones already there.

One interaction, walked

A Graph step finishes on a branch that touched 44 files, 1.8 MB of patch. lf stages everything and asks the commit-message Skill for a message.

Today

The writer receives the first 20,000 characters of git diff --cached, in path order, then [diff truncated]. It describes rust/ and half a scratch note. The Swift that is the change never reaches it, and nothing tells it which files it missed.

Failure: none visible. The message is confidently about the wrong files.

Recovery: someone notices in git log and amends by hand.

Planned

The writer receives every changed file with its line counts, and the exact command that prints one file's patch. The patch itself is there whole when it is small, and absent when it is not. The writer picks what to read.

Failure: the writer reads nothing, or runs out its 300 seconds. It still wrote from a complete list, or the commit falls back to lf implement: checkpoint as it does today.

Recovery: nothing to recover; no state was added.

That interaction is right, and it is the one the Task comment asks for. The review found no reason to change it. What it found is in the code underneath.

The biggest mismatch

A person has one idea: the agent can see the change. The code has that idea three times, with three size rules, and the plan from kickoff would have made it four.

AGENTS.md says it directly: "If three building blocks exist for one job and none works, the change removes all three. It does not add a fourth."

After (proposed)

prompt/change.rs
  PATCH_INLINE_TOKENS = 15_000     // the one rule
  enum ChangeRange { Staged, Since(base), Uncommitted }
  Change::read(repo, range)
  Change::prompt_section()

ops/commit.rs   Change::read(Staged)
ops/pr.rs       Change::read(Since)
prompt/mod.rs   Change::read(Since | Uncommitted)
ops/task/       reads PATCH_INLINE_TOKENS;
  snapshot.rs   its own comparison stays

What the recommendation changes in the plan

  1. Change lives in prompt/, not ops/, so the Skill context path can use it. It is "a change as shown to an agent", which is what prompt/ is for.
  2. No new number. The patch goes in whole under 15,000 tokens, the rule lf already applies twice, instead of a new 100,000-byte rule. More mid-sized PRs take the reading path; that path is the design, so this costs a tool turn, never a wrong message.
  3. context: {diff: true} moves onto Change in the same Task. Its 20-file and 800-line limits, its --stat and its shortstat parsing go. A Skill handed a large branch now gets full paths, line counts and the read command.
  4. The builtin Skill texts are not edited. "Read the diff" is true in both shapes and when the Skill is run by hand with no section at all. The section lf builds carries the instructions.
  5. The working-note mark belongs to the range. Any branch-against-base change has added scratch notes that leave when it lands, so Change::read marks them for Since, and the Skill context path gets the mark too. Wording follows the code: scratch is cleared at land (ops/land.rs:171), not at publish.

Tested against three paths

PathWhat happens
NormalA two-file step commit: stat plus whole patch, one turn, as today. A 44-file branch: stat and read command; the writer reads the Swift.
FailureThe writer runs git diff --cached with no path on a 4.6 MB change and overflows. The commit gets checkpoint; the PR writer errors as it does today for any failed reply. The section names the per-file command and the patch size to steer away from this. A fixture cannot show whether a cheap model obeys; the demo run does.
RecoveryNothing is stored, so there is nothing to repair. Run again.
Counterexample keptOne generated file is itself 200 KB. Its line count is in the stat, so the writer can leave it. lf does not cut it and does not hide it.
Counterexample keptA vendor configuration denies git diff to the PR writer (it does not skip prompts). It writes from the stat. Worse than a read, better than a prefix.

Larger than this work

  • The Task workspace block could become a Change too. It compares base, index, worktree and untracked files at once and reports a state per file; Change would need a fourth range and those states, and untracked files have no numstat. In this Task it only shares the number.
  • lf task diff caps a whole comparison at 1 MB (ops/task/snapshot.rs:584), a per-file limit reused for the patch. That is a person-facing read with a DTO behind it and Desktop working around it in LOO-515. Its fix is a per-file read, the same shape as here, in the served API.
  • Release notes (ops/release.rs) bound a different thing, a list of PRs and commits, and already report what they left out. Not the same concept; no action.

Questions

  1. The size rule for putting the patch in whole.
    1. 15,000 tokens, the rule lf already has. Chosen.
    2. 100,000 bytes for everyone, as kickoff measured for PRs (24 of the last 40 fit); doubles what --diff patch Skills can receive.
    3. Never whole: always the list and the command, one shape, an extra turn on every step commit.
  2. context: {diff: true} in this Task.
    1. Moved onto Change now, as the last slice. Chosen.
    2. Left as is, with its own Task. The writers ship sooner; three rules stay.
  3. Scratch notes in a branch change.
    1. Listed and marked as leaving at land. Chosen.
    2. Left out of the list entirely.
  4. The PR writer follows yolo while the commit writer always skips permission prompts.
    1. Leave both as they are. Chosen; not this Task's to change.
    2. Give the PR writer the same floor, now that it has to run a command. lf land already refuses if the writer changed the worktree.
  5. The importance-ordered fallback for a writer that cannot run commands.
    1. Not built; no launch lf makes fits it. Chosen.
    2. Built anyway.
