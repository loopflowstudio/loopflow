Concept review: links in Loopflow Sessions and Desktop

Task LOO-1126 Stage: post-Pass 1 review (before Pass 2 & Pass 3) Base: 6deb3b0450 · HEAD: 1279b6cc78

Area reviewed: links across Loopflow Sessions and Desktop — from a program inside a held terminal emitting a link (web URL, file path, loopflow:// Work address, or custom scheme), through held-terminal identity (transport/registry.rs), into Ghostty's hover/cursor/open actions (GhosttyManager, GhosttyTerminalView), TerminalLink classification, and Desktop's pane, Files, and Work routers (WorkspacePanesView, SessionsWorkspace, TaskFilesStore, WorkLinkRouter). Reviewing the whole area against base 6deb3b0450 after Pass 1 shows where the committed pane routing clashes with how Desktop actually owns checkouts, Work links, and pane notices.

What is built vs. what waits

  • Built and committed (a12082957b, 62471317a7, 1279b6cc78): Ghostty handles OPEN_URL (always returning true so Ghostty's fallback never runs), MOUSE_SHAPE, and MOUSE_OVER_LINK with link-previews = true; paused-Session ⌘-hover works via flagsChanged; GhosttyTerminalMount renders the bottom-corner linkFeedback overlay; TerminalLink classifies targets and checks local files via localDocument(); SessionPaneView opens http/https/mailto, confirms custom schemes in TerminalExternalLinkSheet, and opens local non-checkout files; docs/surfaces.md and swift/README.md describe the planned end state.
  • Still unbuilt (Passes 2 & 3): .work and checkout .file clicks currently return placeholder notices ("Work links are unavailable in this pane." / "Checkout links are unavailable in this pane."), and transport/registry.rs still inherits TERM_PROGRAM instead of setting ghostty.
  • Still awaiting a decision: the earlier headless review's three product choices (Files pane vs. default app, unconditional TERM_PROGRAM=ghostty, direct in-app Work links) plus two new ones surfaced by Pass 1 (panes without a matching Files checkout, and remote file:// hostnames).

Biggest mismatch: "the pane's checkout" is not what Files reads

Pass 1's openTerminalLink and docs/surfaces.md assume every terminal pane has a matching Files pane for its location.worktree. In the codebase, TaskFilesStore is not a generic (machine, checkout) viewer: it is keyed by a Task's issue, reads through the server's task.file on the Task's current owning Machine, exists only when workspace.key.kind == .task, and rejects directories.

Look at the three places in Desktop and Rust that contradict the "any pane's location.worktree → Files" model:

Put those together and four real cases break if Pass 2 routes from location.worktree alone:

  1. A Task moves from laptop to mini while the old laptop shell stays open (the exact scenario in RemoteTaskWorkspaceTests): tab.location still names the laptop's checkout, while filesPlace and task.file now read mini. Sending the old shell's relative path to TaskFilesStore silently opens mini's file instead of the laptop's.
  2. Repository and Wave Sessions have workspace.key.kind != .task and no browser pane (MultiplexerStore.init(taskId: nil)). Pass 1 already dead-ends local repo files in those panes with "Checkout links are unavailable in this pane." instead of letting them open safely as local documents on this Mac.
  3. An unstarted shell tab is created with worktree: "" (SessionsView.swift:219), so file.checkoutPath(in: location.worktree) returns nil even after the checkout appears and filesPlace.cwd fills in.
  4. Directory links and local symlinked roots: ls --hyperlink emits links for directories as well as files. checkoutPath(in:) returns "." for the checkout root and "scripts" for a subfolder; passing either to TaskFilesStore.openPresentation hits !absolute.is_file() in task_file and opens an error tab. On macOS, lexical prefix matching also misses /tmp/… when Rust canonicalized worktree to /private/tmp/….

Current Pass 1 + Pass 2 sketch (route from location.worktree alone)

  1. Check location.machineId == localMachineId && file.isLocal() first — rejects every remote file://mini.local/… click before checkout routing runs.
  2. Match file.checkoutPath(in: location.worktree) on any pane, even Repo/Wave Sessions (no Files pane) and old pre-move shells (wrong Machine).
  3. Feed that relative path — including "." or a folder — to TaskFilesStore.openPresentation, which reads the Task's current Machine via task.file and errors on directories.
  4. Dead-end Repo/Wave local checkout files with "Checkout links are unavailable in this pane."

Recommended (route against the Task's active filesPlace, fall back honestly)

  1. Compute the active Files destination from the workspace when workspace.key.kind == .task: filesPlace gives (activeMachine, activeCwd) (the Task's current owner and checkout).
  2. The terminal matches the active Files pane iff location.machineId == activeMachine and !activeCwd.isEmpty and (location.worktree.isEmpty || normalizedEqual(location.worktree, activeCwd)).
  3. When it matches active Files:
    • On a local pane, still require file.isLocal(), normalize symlinks on the local root so /tmp matches /private/tmp, and check whether the resolved target is a directory (open in Finder via localDocument(), or reveal in Files tree — never pass a directory to task.file).
    • On a remote pane, match lexically against activeCwd without touching this Mac's disk, accepting the remote Machine's file://<host> authority (Q3), and exclude ".".
    • Open matching files in Files via openPresentation at #L<n>.
  4. When there is no matching Files pane (Repo/Wave Session, old pre-move shell, or path outside the checkout):
    • If location.machineId == localMachineId && file.isLocal(): run file.localDocument() → default app (blocking apps/scripts/executables).
    • Otherwise: refuse in linkFeedback ("File is on another Machine." or "This shell is on the Task's previous Machine."). Never read this Mac's disk or the wrong Machine's checkout.

Counterexamples tested

  • Task moves laptop → mini, click in old laptop shell: tab.location.machineId (laptop) ≠ filesPlace.machine (mini), so it never opens mini's same-named file. Because the old shell is on this Mac and file.isLocal(), safe local documents open from the laptop's real path in the default app; scripts remain blocked.
  • Task moves mini → laptop, click in old mini shell: tab.location.machineId (mini) ≠ filesPlace.machine (laptop) and ≠ localMachineId → refused cleanly as another Machine. Neither the laptop's checkout nor this Mac's disk is touched.
  • Click file://other-host.local/Users/jack/repo/README.md in a local pane: file.isLocal() is false, so it is refused even though the path string matches this Mac's checkout.
  • Click file://mini.local/home/jack/wt/scripts/test.py#L42 in a remote Task pane: pane is on mini, matches active filesPlace, path is lexically inside activeCwd → opens read-only in Files at line 42 via task.file (which talks only to mini over Loopflow's server, never resolves mini.local over the network, and never runs the script).
  • Click a directory from ls --hyperlink (file:///…/repo/ or file:///…/repo/scripts): never sends "." or a local directory to task.file; local directories open in Finder via localDocument(). On remote panes, "." is skipped from file reading and if task.file refuses a remote subdirectory, Files shows the tree or a clear notice instead of a broken file tab.
  • Click loopflow://loopflow/task/LOO-99999 or loopflow://foo/bar/baz: tightening TerminalLink to the WorkUrl grammar refuses loopflow://foo/bar/baz synchronously in linkFeedback; async resolution errors for unknown Tasks report back into linkFeedback instead of opening the separate open-work window.
  • Click a confirmed slack://… link when Slack is not installed: notice shows "No app could open the link." in linkFeedback, not "Could not change pane: No app could open the link." in the top notice bar.

Second mismatch: two loopflow:// parsers and split link error reporting

Pass 1 checks loopflow:// with a four-host blocklist instead of the real WorkUrl grammar (rust/loopflow-execution/src/work/link.rs:68-96), and WorkspacePanesView routes a failed external-scheme sheet click through paneFailed (which prefixes "Could not change pane: ").

Matching WorkUrl's path shape (empty, /task/<id>, or /wave/<name>) and allowed query keys (repository, session, machine) in TerminalLink refuses bogus loopflow:// paths immediately and allows a repo named open when it carries /task/… or /wave/…. Adding one async showLinkNotice(_:) hook on GhosttyMetalView (or passing a notice callback to onOpenLink) lets synchronous refusals, failed custom-scheme opens, and async query.workLink(url) failures all land in the same bottom-corner overlay — reusing sessions.query.workLink + model.openRepository without popping the open-work error window.

Third mismatch: hover preview vs. click validation, and unbuilt Pass 3

In GhosttyManager.swift, OPEN_URL checks percent-decoded characters and URL credentials via TerminalLink, while MOUSE_OVER_LINK only runs hasUnsafeCharacters on the raw string. Checking the decoded string (or sanitizing through the same helper) keeps hover honest when an OSC 8 target hides bidi overrides as %E2%80%AE.

Separately, Pass 3 is still untouched in rust/loopflow-execution/src/transport/registry.rs: until held terminals set TERM_PROGRAM=ghostty and clear TERM_PROGRAM_VERSION, Sessions started by the server or Desktop still inherit no TERM_PROGRAM and emit no OSC 8 hyperlinks at all.

Questions

1. When you ⌘-click a local file inside a Repository Session, a Wave Session, or an old shell tab left on this Mac after a Task moved to another Machine (none of which have a matching Files pane), what should happen?

Falling back to macOS's default app lets you open Markdown, source, and text files immediately while still blocking scripts and executables. Refusing them leaves those panes with a "checkout links unavailable" notice until Repo and Wave workspaces gain their own Files pane.

2. When you ⌘-click a file inside the Task's active checkout (for example scripts/test.py#L42, on this Mac or a remote Machine), where should it open?

Opening in Desktop's Files pane jumps to the exact line, lets you read executable scripts safely, and works on remote Machines. Opening in the macOS default app matches Rex for ordinary local files, but drops line numbers, must block scripts/executables, and cannot open remote files.

3. On a remote Machine, tools like ls --hyperlink and rg emit links with that Machine's hostname (for example file://mini.local/home/jack/wt/src/lib.rs), which does not match this Mac. Should those open in Files when the path is inside the remote Task's checkout?

Files reads only from the Task's owning Machine over Loopflow's server and never contacts the hostname in the URL. Local panes would still require this Mac's hostname.

4. When a Session starts from another terminal (Apple Terminal, tmux, Rex) or from the server, should every held terminal tell the agent it is running in ghostty?

Always setting TERM_PROGRAM=ghostty makes clickable links work consistently no matter where the Session started, and existing Rex host detection reads REX_SESSION/REX_BLOCK rather than TERM_PROGRAM. Setting it only when unset keeps rex when started from Rex, but leaves Apple Terminal and tmux starters without clickable links.

5. When an agent or lf open --link prints a read-only Loopflow Work link (Repository, Task, or Wave) and you ⌘-click it in a Session, should Desktop jump straight there in this window?

App-control routes like loopflow://update or loopflow://open?repo=…&view=… remain refused. Without direct in-app routing, clicking Loopflow's own links prompts for confirmation and can wake another installed copy of Loopflow via macOS.
