Biggest mismatch: two subtle guards in compress.md that break on normal runs

The overall shape of the built change is right — whole-branch scope, in-run audit of branch additions, check-then-commit per cut, and deferral of behavior/data/metric changes all line up with build.yaml, commit_step, and ship-review. Two concrete clauses added or carried into compress.md undermine it on the most common paths:

  1. Gating scratch/questions.md on "if it exists" drops open questions in normal headless build runs. In code, feature, and pursue, kickoff creates scratch/plan.md, while scratch/questions.md is only created on demand when an earlier step happens to ask a question. On any clean Task where compress is the first step with a question for a person, scratch/questions.md does not exist yet — so compress.md:51-53 sends the question to the headless reply (logged, not displayed) instead of creating scratch/questions.md for ship-review. The signal that scratch/ is active on the branch is scratch/plan.md, not whether a prior step already had a question.
  2. Gating per-cut checks on "when behavior changed" lets refactor cuts commit unchecked. compress's whole job is behavior-preserving simplification: lines 6 and 48 explicitly forbid changing behavior people rely on. Telling a behavior-preserving step to run checks only "when behavior changed" is a direct loophole (prompt.md:66) that lets a multi-file reshape or parameter deletion skip compilation and focused tests. The real line — already written in AGENTS.md:457 and implement.md:79 — is when a cut changes code versus prose-only edits and unchanged reruns.

Contradicts lines 6 and 48: compress preserves behavior, so "when behavior changed" gives a refactor cut licence to skip its build/focused test before committing. scratch/questions.md is never pre-created in a Task. If no earlier step wrote a question, headless compress writes its question to the unprinted log reply and ship-review never sees it. Existing rule draws the right boundary for implement and compress: changed code vs prose-only edits.

Walking normal, failure, and recovery paths

  • Normal path (clean code / feature Task with no earlier questions): kickoff creates scratch/plan.md; implement, concept-review, and realign run cleanly without creating scratch/questions.md. Headless compress spots an unused-looking config option and wants to ask whether anyone relies on it. At HEAD, scratch/questions.md does not exist, so compress prints the question to its headless log and ship-review misses it. With the fix, scratch/plan.md exists, so compress creates scratch/questions.md, commit_step commits and pushes it, and ship-review surfaces the question.
  • Failure path 1 (a multi-file reshape breaks a caller or test): At HEAD, a literal agent reading "when behavior changed" can skip checking a pure refactor and commit broken code before qa catches it. With "when a cut changes code", the focused check fails before the cut is committed, so the agent fixes or drops it cleanly; if a subtle regression escapes the focused check, qa catches it or a reviewer reverts that one commit alone.
  • Failure path 2 (standalone lf compress on a branch with no scratch/plan.md): The person runs lf compress directly on an ordinary branch without a Task plan. Because scratch/plan.md is absent, compress does not manufacture scratch/plan.md or scratch/questions.md; it prints any deferred cuts and questions directly in the interactive reply (while still appending to scratch/questions.md if the branch already uses one).
  • Failure path 3 (ship-review loops back to build): The person requests another pass. realign.md:67 preserves ## Deferred findings when replacing settled review notes, compress.md makes no claim that nothing follows it, and the next compress pass stops cleanly on already-simplified code.
  • Failure path 4 (optimize metric regression after compress): compress.md:48-49 guards against hot-path regressions up front. If one still slips through, optimize.yaml runs measure (final) after refresh and reverts to the last kept commit, losing all compress cuts and refresh together. Keeping that as a separate outcome in scratch/plan.md:259-267 is still the right boundary.
