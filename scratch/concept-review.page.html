The four mismatches, before and after

1. Interactive plain-terminal sessions misclassified as headless

Walking the interaction: a person starts an interactive lf explore in Ghostty or iTerm2. The agent compiles scratch/explore.page.html and runs lf page open scratch/explore.html. Because viewed_placement() only recognizes multiplexer IDs (desktop:, rex:, cmux:, herdr:, tmux:), it returns None and route_for prints a URL without opening the browser — even though SQLite already knows session.interactive == true.

Only checks multiplexer viewed_placement(), ignoring session.interactive in SQLite. Plain-terminal interactive sessions hit None here and silently fall into PrintQuiet.

decide_open_route checks only viewed_placement(). Any interactive agent outside Desktop/Rex/cmux/herdr/tmux returns None → PrintQuiet, breaking "Browser beside Rex or any terminal" in docs/surfaces.md.

Look up caller.session_id in SQLite (the same pattern page/build.rs:248 uses): if session.interactive == false → PrintQuiet; if session.interactive == true → Desktop when viewed in Desktop (or LF_DESKTOP set), else Browser. If the session row is absent (test fixtures), fall back to viewed_placement() so unknown callers stay quiet.

2. data-label doing two jobs breaks scratch/ship-review.html

On this branch's own compiled scratch/ship-review.html, Question 1 has both a short data-label (for the steer line) and a fuller <p> question. Because base.css unconditionally renders ::before { content: attr(data-label) }, the page prints 1. twice, lays out <p> inside a flex row without flex-basis: 100%, and makes the ::before text unselectable for highlight-to-comment.

Always draws data-label via ::before, even when the author wrote a selectable <p> prompt inside the control. data-label is the concise reply key; the <p> on line 140 is the visible question — currently both render stacked.

Bare controls (<div data-choice="q1" data-label="1. Keep?"><button>Yes</button></div>) work, but rich controls with a <p> prompt double-render the heading and break flex wrapping.

Render ::before only when the control has no direct prose/heading child (:not(:has(> p, > label, > h3, > h4, > legend))), and give direct <p> children flex-basis: 100%. Short bare controls still render data-label automatically; rich questions show only their selectable <p> while keeping data-label concise in the steer reply.

3. Hardcoded protocol revision and silent loopback handshake failure

Walking failure and recovery: when wire::REVISION bumps from 10 to 11 (or a person reloads a stale loopback tab after lf server restarts or stops), the WebSocket closes before welcome. Today runtime.js hardcodes 10, drops un-ID'd error frames, and hides the banner unless welcomed was already true — so the page silently falls back to clipboard copy with no explanation.

Hardcoded magic revision instead of wire::REVISION / wire::MIN_REVISION stamped by lf page build. Un-ID'd server error on hello (such as incompatible revision) is silently ignored. If handshake fails before welcome, no banner appears; if server stopped, banner inaccurately says "restarted".

Protocol bump breaks every browser review page silently; stale loopback URLs and stopped servers on reload show no banner; live disconnect says "restarted" even when the server is stopped.

lf page build stamps protocol: { revision, min_revision } from crate::server::wire. runtime.js sends those values, records any un-ID'd handshake error message, and on close for any loopback URL shows either that error or Loopflow server disconnected — run lf page open <path> while switching the button to Copy reply ⌘↩.

4. Browser Clear discards unreported data-lf receipts

Walking recovery: a reviewer clicks File Task now (Filed LOO-1200), adds a note, hits Clear to rewrite the note, and then presses ⌘↩. Because Clear shares clearDrafts() with submitReply(), it flips reported: true on the receipt even though nothing was sent — so [already ran: task.create → LOO-1200] disappears from the steer.

Marks every receipt reported even when invoked from the strip's Clear button rather than a successful send.

clearDrafts() always marks receipts reported: true, conflating "sent to agent" with "discarded unsent draft".

clearDrafts({ markReported }) marks receipts reported only on actual send (submitReply success and Desktop __lfDesktopApplyState(null)); clicking Clear drops unsent notes/choices while keeping unreported receipts ready for the next reply.
