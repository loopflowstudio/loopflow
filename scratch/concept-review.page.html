Biggest mismatch: GraphOutput contradicts realign's new loop rule

Walk a concrete build run when concept-review finds a single 3-line code mismatch:

  1. Pass 1: implement finishes the planned slice and returns advance. concept-review writes scratch/concept-review.html with one "No" row (a leftover helper or misnamed flag).
  2. realign runs as the outer loop's decider. realign.md tells it to write that fix into scratch/plan.md as Pass 2 and return iterate, however small the change.
  3. Then the runner appends DECISION_CRITERIA at the bottom of the prompt (rust/loopflow-execution/src/graph/output.rs:11-19):

Failure mode: Because DECISION_CRITERIA lands last in the prompt, an agent obeying it sees a 3-line review fix and hits a direct contradiction — iterate asks for a "substantial next pass", while blocked triggers when "passes shrink into small increments." Under headless execution, that pushes the decider either to return blocked on a valid small review fix (stalling the Task) or to rationalize advance (dropping the fix).

Notice that Loopflow's native chat checklist renderer already has the right model — it only injects generic loop-or-next rules when the skill is loop-or-next, and otherwise defers to the skill's own criteria:

Before (plan alone)

realign.md says: iterate on any in-scope code fix, however small.

output.rs unconditionally appends after it: iterate only on a "substantial next pass"; block when "passes shrink into small increments."

Result: Two competing authorities in the same prompt, with the generic rule getting the last word.

After (one decision authority)

DECISION_CRITERIA in output.rs states upfront that skill-specific loop rules take precedence (and reserves blocked for passes that repeat without converging, not legitimate small review-fix passes).

Result: Skills without a ## Deciding a loop section still get safe defaults; realign (and implement) decide cleanly by their own stated rules without fighting the runner suffix.

Recovery check: What if a genuine non-converging spin happens (Pass 2, 3, 4 keep reopening the same finding)? graph.rs:1366 still injects Decision pass N, and DECISION_CRITERIA still tells any decider to return blocked when passes repeat without progress or fail to converge. What changes is only that a single targeted review-fix pass is no longer misclassified as "shrinking into small increments."

Meanwhile, scripts/evals/instruction_levels.py already defines realign's action boundary without a separate docs permission:

There are two clean ways to resolve this, and neither leaves the rule vague:

  • Option A (strictest, smallest system): realign edits only scratch/ (and Wave memory when asked). Even doc mismatches go into scratch/plan.md and iterate through implement → concept-review. Zero path-classification judgment calls, 100% current concept-review.html, and 1:1 match with instruction_levels.py. Cost: a docs-only review finding in build pays one extra 4-step pass.
  • Option B (keep Q2 b, draw a crisp boundary): realign may edit only user-facing documentation files (docs/, README.md) — never builtin skills, goldens, AGENTS.md, .lf/qa/, or code comments — and realign.md notes plainly that inline doc fixes stay resolved in scratch/plan.md beside the existing review page. Cost: concept-review.html can still show a stale "No" row for a fixed doc mismatch, and agents must still classify which Markdown files count as user docs.

Findings

This work. rust/loopflow-execution/src/graph/output.rs:11-19 appends generic loop criteria ("substantial next pass", block when "passes shrink into small increments") after every deciding step's skill prompt — directly contradicting realign's new rule to iterate on any in-scope code fix, however small.

Recommendation: Update DECISION_CRITERIA (2–3 lines in output.rs) so skill-defined loop rules take precedence and blocked applies to passes that repeat without converging, not a targeted review-fix pass. Passed over: hardcoding skill names in output.rs (brittle for custom skills) or leaving the contradiction and hoping models ignore the suffix.

This work. realign.md:28-31 tells realign to perform its own shape review and write simplifications into the plan. After concept-review passes all rows on Pass 2, that instruction can inject new code work and trigger an unwanted Pass 3 right before compress.

Recommendation: Scope the "read the work once as a reviewer" paragraph in realign.md to runs without a fresh concept-review (standalone realign, refresh, or post-slice without review). When reconciling a concept-review, triage its findings only. Passed over: deleting the paragraph altogether (loses the quick shape check for standalone/refresh runs).

This work (design choice). "Docs by file path" is ambiguous in repos where Markdown carries executable behavior (skills, goldens, AGENTS.md, .lf/qa/), diverges from instruction_levels.py, and still leaves stale "No" rows on scratch/concept-review.html when realign fixes a doc inline.

Recommendation: Make realign strictly scratch/ + Wave memory (zero repo-file exceptions), or keep Q2 b narrowed explicitly to user-facing docs (docs/, README.md) and never skills/goldens/agent guides/comments. Reversible (prompt text only).

This work. AGENTS.md:453 says realign: reconcile the plan; test only a repair or a real doubt. Update alongside lines 285 and 410 so the guide doesn't imply realign still repairs code.

Separate outcome (if ever needed). optimize.yaml ends compress → graph: refresh → measure. With plan-only realign, any non-conflict upstream drift found during refresh stays in scratch/plan.md without an implement step to build it. Fixing it would mean changing optimize.yaml (or adding a conditional branch after refresh), which is outside LOO-1125 and unnecessary unless optimize runs actually hit post-sync drift.
