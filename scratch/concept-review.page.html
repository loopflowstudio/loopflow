Concept review: links in Loopflow Sessions and Desktop

Task LOO-1126 Stage: pre-implementation (reviewing scratch/plan.md) Base: 6deb3b0450

Area reviewed: links across Loopflow Sessions and Desktop — from a program inside a held terminal emitting a link (web URL, file path, or loopflow:// Work address), through held-terminal identity and VT relay, into Desktop's embedded Ghostty panes and existing Work/Files routers. Widening from Ghostty's OPEN_URL callback to this whole path exposes where treating Desktop like an external terminal clashes with what Desktop already owns.

Biggest mismatch: Desktop acting as a dumb external terminal

GhosttyManager.action_cb sits at the bottom of the stack with no reference to the workspace, checkout, Machine, or WorkLinkRouter. Because plan.md handles clicks right there with NSWorkspace.shared.open as its only opener, Loopflow Desktop treats its own Work links as foreign schemes and kicks its own checkout files out to macOS — throwing away line numbers, refusing executable repo scripts, and failing on remote Sessions.

Desktop already owns both destinations. LoopflowApp.handleDeepLink resolves loopflow:// Work addresses inside this running app, and DesktopActions already opens any checkout path (local or remote Machine) at a line range inside the Files pane:

Meanwhile, Loopflow's own CLI and prompts actively emit loopflow:// OSC 8 and Markdown links inside Sessions (rust/loopflow/src/lf/commands/open.rs:1490), so a person will hit that warning dialog on Loopflow's own links on day one.

Plan as written (generic terminal opener in GhosttyManager)

  1. GhosttyManager.action_cb parses bytes into TerminalLink.
  2. http/https/mailto → NSWorkspace.shared.open.
  3. file://…#L42 → drop #L42, check local disk, refuse scripts/executables, call NSWorkspace.shared.open. Remote checkout file → refused as missing.
  4. loopflow://loopflow/task/LOO-1127 → unknown-scheme alert → Launch Services (can wake the wrong Desktop bundle).
  5. Refusal text → crammed into copyConfirmation in the top strip (invisible on solo shell panes).

Recommended (classify in Ghostty, route in the pane)

  1. TerminalLink stays pure: parses raw bytes, rejects control/bidi characters, and classifies into .web(URL), .work(URL), .file(path, host, line), .externalScheme(URL), or .refused(reason).
  2. GhosttyManager.action_cb copies the bytes, forwards to view.onOpenLink, and always returns true for OSC 8 so Ghostty's fallback never runs.
  3. The pane routes with its real context (machineId, checkout path, WorkLinkRouter, showBrowser(.files)):
    • Work address (loopflow://<repo>[/task/<id>|/wave/<name>] only) → opens directly in this app via WorkLinkRouter, no alert.
    • Checkout file (local or remote Machine) → opens read-only in Desktop's Files pane at #L<n>; safe for scripts/*.py and *.sh.
    • Local file outside checkout (local Machine only) → existing Launch Services safety gate (resolve symlinks, refuse apps/scripts/executables).
    • Web / mail → default app. Other schemes → confirm before dispatch.
  4. Hover preview and transient refusal notices share one bottom-corner overlay on GhosttyTerminalMount, visible whether or not the top strip is shown.

Counterexamples that test this design

  • Malicious internal loopflow:// action in terminal output (e.g. loopflow://update or loopflow://open?repo=/tmp&view=…): auto-routing every loopflow:// URL would let terminal output trigger app commands. Restricting in-app auto-routing strictly to parsed read-only Work addresses (loopflow://<repo>[/task/<id>|/wave/<name>], matching WorkUrl) closes that hole; control hosts like update or open stay refused or prompted.
  • Remote Session clicking file:///tmp/notes.txt (outside checkout): if Desktop checks local disk without checking terminal.machineId == localMachineId, a click in a remote Session silently opens this Mac's /tmp/notes.txt. Routing by the pane's Machine opens remote checkout paths via Files (which reads from that Machine) and refuses non-checkout remote paths explicitly as "File is on another Machine."
  • file://<hostname>/Users/… from OSC 8 tools: RFC 8089 and tools like ls --hyperlink / rg --hyperlink-format emit the host's own hostname in the authority (e.g. file://Jacks-MacBook.local/Users/…). Local host matching must accept empty host, localhost, and ProcessInfo.processInfo.hostName (case-insensitive), not just empty/localhost.
  • Symlink inside checkout pointing to an app or outside the repo: opening checkout paths in Desktop's Files pane goes through the server's read-only checkout reader (which never executes files and enforces checkout containment); local outside-checkout fallback still resolves symlinks before checking bundles, scripts, and the executable bit.
  • Session started in Apple Terminal or tmux, then viewed in Desktop: inheriting non-empty TERM_PROGRAM leaves Apple_Terminal or tmux in place, so Claude still emits no OSC 8 links. Setting TERM_PROGRAM=ghostty unconditionally in registry.rs (and clearing stale TERM_PROGRAM_VERSION) matches the real PTY emulator (libghostty-vt) and fixes links no matter where the Session started.
  • Clicking a link while a Session is reconnecting or ended: GhosttyMetalView.flagsChanged currently drops modifier events when !connectionAcceptsInput, breaking ⌘-hover affordance on a retained screen. Letting modifier flags update Ghostty's local state (without sending bytes to a paused PTY) keeps link inspection consistent with selection, copy, and Find.

Second mismatch: held terminal identity in registry.rs

registry.rs already strips the caller's relay and viewer variables because "a pane's relay variables describe that pane's viewer… neither is this child's." Yet lines 548–554 only default missing TERM and COLORTERM, and plan.md extends that pattern to TERM_PROGRAM=ghostty.

A held terminal is always libghostty-vt — a viewer in Rex, Desktop, iPhone, or Apple Terminal attaches to it later. Inheriting TERM_PROGRAM=Apple_Terminal or tmux disables hyperlinks permanently for that Session; inheriting TERM_PROGRAM=iTerm.app or WarpTerminal invites terminal-specific escapes that libghostty-vt is not, and defaulting TERM_PROGRAM without clearing TERM_PROGRAM_VERSION pairs ghostty with another terminal's version string. Setting TERM_PROGRAM=ghostty unconditionally on held terminals and removing TERM_PROGRAM_VERSION makes the environment describe the real terminal the program talks to.

Checking one counterexample: does anything inside a held terminal depend on TERM_PROGRAM=rex? Loopflow's own host detection (terminal_host.rs) checks REX_SESSION/REX_BLOCK, not TERM_PROGRAM, and held terminals already isolate the child from its viewer's terminal identity. Existing registry_tests.rs covers custom TERM/COLORTERM (such as TERM=dumb), which can stay caller-overridable while TERM_PROGRAM reflects the held VT engine.

Third mismatch: pane notices and paused input

Two small seams in the existing view will bite Pass 1 if left as-is: a solo shell pane has showsStrip == false, so routing link refusals through copyConfirmation hides them there; and blocking flagsChanged when !connectionAcceptsInput stalls ⌘-hover feedback on reconnecting or ended screens.

Questions

1. When you ⌘-click a file inside the Session's checkout (for example scripts/test.py#L42 or a source file in a remote Session), where should it open?

Opening in Desktop's Files pane jumps to the exact line, lets you read executable scripts safely, and works on remote Machines. Opening in the macOS default app matches Rex for ordinary text files, but drops line numbers, must block scripts/executables for safety, and cannot open files on remote Machines.

2. When a Session is started from another terminal (like Apple Terminal, tmux, or Rex), should Loopflow tell the agent its terminal is ghostty (Loopflow's held terminal engine) or keep the starter's terminal name?

Always setting ghostty means links work consistently in Desktop no matter where the Session was started. Keeping the starter's name preserves rex when started from Rex, but leaves Sessions started from Apple Terminal or tmux without clickable links.

3. When an agent prints a Loopflow link (such as a Task or Wave link from lf open --link) and you ⌘-click it in Desktop, should it jump straight to that Task/Wave in this window?

Only read-only Task, Wave, and Repository links would open directly; app-control links like loopflow://update would still be blocked or confirmed. Without this, clicking Loopflow's own links prompts for confirmation and can open a different installed copy of Loopflow.
