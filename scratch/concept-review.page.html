Biggest mismatch: Graph position and scratch ownership baked into a reusable Skill

Two closely tied problems turn a clean improvement to compress into a brittle stage of build.yaml:

  1. It explains its ambition through build.yaml's schedule instead of the job itself. The Task brief says "now that it only runs once per task rather than once per slice" — that is why raising the bar pays off, not a fact the Skill can assert. ship-review loops back into build (running compress again with more work built on top), optimize runs compress before refresh/realign, and people run lf compress directly mid-branch.
  2. It quietly becomes a second writer to ## Deferred findings in scratch/plan.md while mixing in open questions that belong in scratch/questions.md, leaving ship-review.md contradicting it and leaving standalone runs with no scratch/plan.md unspecified.

Planned draft (in scratch/plan.md)

  • requires: the finished change against its base, and the plan
  • "This runs once, after the design has settled and before anyone uses the change. Nothing will be built on top of it later, so take the cut that moves several files as readily as the one that renames a variable."
  • Step 6 commits each cut; step 7 checks afterward.
  • Writes both behavior/data cuts and open questions into ## Deferred findings in scratch/plan.md, while ship-review.md still says "written by realign".
  • Closes with a deep-clean-style report of kept items and before/after line counts that nobody reads in headless build.

Recommended shape

  • requires: branch changes against the base, and the plan if one exists
  • "Treat the branch as one change against its base, not a sequence of edits. Take a reshape that moves several files as readily as one that renames a variable." (True in build, optimize, loop-backs, and standalone lf compress.)
  • One check-then-commit step: verify each substantial cut with the narrowest changed target or focused test, then commit it with what it removed and why.
  • Split untaken cuts cleanly: behavior/data/metric cuts go under ## Deferred findings when scratch/plan.md exists (and ship-review.md:14 drops "written by realign"); questions only a person can answer go in scratch/questions.md; standalone runs report both in the reply.
  • Drop the unconsumed kept-list and line-count report; commit messages and code comments carry the rationale.

Walking normal, failure, and recovery paths

  • Normal path (build → ship-review): implement finishes passes; concept-review + realign settle design; compress reads the whole diff against base, audits every branch addition, checks and commits each substantial cut on its own, and leaves leftovers for commit_step to push. qa runs the real thing; ship-review reads git log (seeing each cut's commit), ## Deferred findings (from both realign and compress), and scratch/questions.md.
  • Failure path 1 (a bold cut breaks behavior): With check-before-commit, the focused test fails before the cut is committed; the agent fixes or drops the cut cleanly. If a subtle regression escapes the focused check, qa catches it on the real thing or a reviewer reverts that single commit via git revert without losing the other cuts.
  • Failure path 2 (ship-review iterates back to build): The person requests another pass. Because compress didn't assume nothing will ever be built on top, and because realign.md:67 keeps ## Deferred findings intact when refreshing review notes, earlier deferred cuts survive and the second compress run stays idempotent on already-clean code.
  • Failure path 3 (standalone lf compress with no scratch/plan.md): With the plan guard, compress simplifies the branch without manufacturing an empty scratch/plan.md; any cut it held back appears in its direct reply (and in scratch/questions.md if scratch/ is in use).
  • Failure path 4 (optimize regression after compress): If a cut slows down the measured workload, measure (final) compares against the last kept commit (measure.md:41) and reverts the tree — discarding all compress cuts and refresh together. Keeping the metric clause in compress.md guards against obvious hot-path regressions; finer recovery belongs to a separate optimize Task if this actually bites in practice.
