Forward preferences before building settings sync

LOO-714 · Research for Jack Heart · November 3, 2026

Recommendation for review, not accepted implementation direction. Built from settings-catalog.md, machine-config-prior-art.md and primary sources below. No live config, machine, account or execution state was changed.

Decision recorded November 3: Jack Heart accepted origin personal preferences for forwarded launches and saved remote preferences for work initiated directly there. The executor supplies its environment. Retention and independent remote edits remain separate from launch authority; persistence mechanisms below remain proposals. The current design is in settings-catalog.md.

Decision

Start with forwarding portable preferences and retaining them remotely. Refresh the retained copy automatically while it remains unchanged; preserve independently edited remote config and report that persistence needs reconciliation. Defer automatic merging of independent edits across machines.

The earlier merge recommendation assumed a requirement Jack has not stated: all machines are equal writers whose edits should eventually reach every other machine. The stated requirements are laptop preferences governing remote work and remote retention for later work, including mobile use while the laptop is unavailable.

Proposed behavior

A laptop request carries authored portable declarations, preserving source, scope, targets and agent/default_agent strength. Invocation choices remain separate. The destination can retain the declarations in ordinary personal config files: ~/.lf/config.yaml and the accepted ./lf.config.local.yaml. Preserve machine-local bindings; credentials and local machine identity never travel as preferences.

Existing differing remote preferences require an explicit adoption choice rather than replacement merely because a client connected. After adoption, refresh only when retained portable content still matches what was last applied, or already matches the incoming content. Remote deletions count as edits too. Compare each coherent portable configuration document/projection initially, without merging leaf values. This can flag non-overlapping edits but keeps the policy understandable.

An independent remote edit through a text editor or lf set takes effect there. On a conflicting delivery, preserve that file and expose the incoming version for comparison. Keep the remote version, explicitly replace it, or bring changes back to the source. Do not silently introduce two personal profiles as precedence layers.

Forwarding and saving have separate outcomes: the request still uses its carried personal declarations, even when saving them would overwrite remote edits. Inspection reports “used laptop preferences for this launch; remote defaults retained.” Subsequent direct remote/mobile commands use the actual saved settings. Do not block work or silently use a different profile because retention conflicted.

Refresh at remote request boundaries. Offline use cannot promise changes that have not arrived. Running commands are not reconfigured by delivery.

This still needs ordered delivery and atomic compare-and-write: older revisions cannot replace newer ones from the same origin, and another client cannot silently become the new source. Last-applied content/origin/version is operational metadata, appropriate for the DB. It is not another editable preference layer. Any evidence or backup copy is not read as a second authority.

Why merging is a larger commitment

These are deductions from LF's model, not claims about the cited products:

  • Account lists are ordered. Combining two edits can invent an unintended order.
  • Deleting an override reveals a lower layer; deletion is different from empty.
  • Changing agent to default_agent changes strength. A merge of different keys can accidentally preserve an explicit choice that defeats the new fallback.
  • Planning-provider records and machine aliases have related fields/references.
  • Different host settings can be intentional rather than changes to synchronize.

Catalogue portability rules help distribution, but do not define merge semantics. The recommendation adds no internal Git repository, CRDT or background sync daemon. It borrows a one-way safety boundary, not Mutagen's exact behavior: in particular, LF should preserve remote deletions rather than resurrect them automatically.

Decision for review

This proposal is insufficient if Jack routinely edits permanent preferences on a phone connected directly to a remote and expects those edits to update the laptop automatically. Two laptops frequently editing the same profile offline also justify genuine synchronization. Using preferences on mobile does not itself require this.

1. Which workflow must the first release support?

1a. Primarily edit on the laptop; remote/mobile use retained preferences, and occasional remote edits survive until explicit reconciliation. Recommended.

1b. Edit permanent preferences anywhere and have changes flow back automatically. Choose a write authority or design peer synchronization before implementation.

Validation: primary documentation reviewed; no external software executed and no sync implementation or live migration performed. Mutagen operates on files, not YAML-setting semantics. VS Code's remote docs do not establish LF-style retention for standalone commands. Rex's host directory is narrower than general config.
