Database-driven UI

Jack Heart selected database-driven dependent UI without caller-managed refreshes, retaining Rust/lf as the only internal-schema reader. October 14 source inspection; no implementation or runtime measurements in this report. The concurrent rendering pursuit remains separate.

Existing foundation

store/sqlite/revisions.rs exposes five trigger-maintained transaction-local domain counters. store/changes.rs observes filesystem changes. lf/commands/work_watch.rs wakes, checks counters, projects selected parts and fingerprints output. Swift WorkModel.apply retains last good values and avoids equal-value assignments. This already supports writes from other processes; replacing it with an in-process SQLite hook alone would lose that property.

Concrete gaps

  • WorkModel.performTaskAction, setWorkflow and saveWorkflow explicitly refresh after commands. refresh sends a global request, raises planning/sessions/task floors and waits for planning. work_watch Request::Refresh forces every part, including unchanged output. Mutation visibility and broad reloading are coupled.
  • Part::changed broadly depends on every non-usage revision for most parts. This is automatic but coarse, not query-specific dependency tracking. Part clocks reread Sessions/Task/WorkActivity every two seconds; liveness legitimately changes without database commits.
  • Reader.project composes multiple reads. Revisions are sampled before projections, and individual parts are emitted independently. A revision tag is not by itself evidence of one SQLite snapshot across joined output. Establish snapshot boundaries before using these tags as read-your-write acknowledgments.
  • Definition catalogues are files: rereadDefinitions and force loads are explicit. Files, Git, process liveness and remote availability need their own invalidation adapters; database-only observation cannot represent them.

Implementation direction

  1. Make affected query subscriptions, rather than UI actions, own reload decisions. Keep typed Rust projections and existing stream transport.
  2. Separate command acknowledgment/read-your-write waiting from global Refresh. Where UX requires confirmation, await an observed committed version or authoritative result; do not clear drafts merely because an unrelated frame arrived.
  3. Declare dependencies beside projections and validate against actual SQL/table reads. Narrow only with tests proving relevant writes are never missed.
  4. Publish database-derived projections from defined consistent snapshots. Attach external observations separately rather than imply transactional process/filesystem facts.
  5. Retain explicit user Retry, reconnect recovery and external-change adapters. Delete ordinary post-write refresh orchestration once subscription tests prove coverage.

Proof needed

Second-process writes update visible affected projections without a Refresh request; unrelated writes do not reproject unrelated data; joined reads never expose half a transaction; reconnect delivers the latest state; failed reads preserve last-good content; local action completion cannot erase newer drafts; liveness/files/definitions still update without SQLite writes. Initial static trace is not proof these scenarios pass or fail.
