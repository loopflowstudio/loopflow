1 · Where content lives

Four places, four kinds of content. The test for each is who writes it and how long it stays true.

PlaceKind of contentWritten byTrue for
Repo .lf/what the project is and how its work is donecontributors, reviewedeveryone who clones, every machine
Personal config ~/.lf/config.yamlwhat one person wants, stated oncethe person, by hand or lf setthat person, on this machine, across repos
Env varwhat is true for this one command and its childrenthe invoking commandone process tree, then gone
Store (sqlite)what lf observed and what lf didlfthis machine's history, read through lf

Repo

skills, graphs, Wave goals and memory, planning provider and team ids, release targets, context and exclude, the graph new Tasks take up, tier requirements on steps. Never an identity, credential, machine path or taste.

Personal config

harness, allowed accounts by login, tier-to-model map, machine preference, theme, terminal, yolo. The same keys restated under repos: and waves:. Never anything lf could look up or measure.

Env var

invocation overrides (-a, --task, LF_HOME) and parent-to-child plumbing (capture key, caller). Read by children, persisted by nobody.

Store

Tasks, Sessions, Processes, PRs, machines, account tokens, usage and limit observations, cooldowns, Session Routes. Nobody declares intent here.

Precedence is env, then personal, then repo. The store is not a layer. It is an input to resolution (which account has room), never an override.

Each fact has one home. Account order: config. Account limits: store. Machine preference: config. Machine registration: store. Task graph: store. Task harness: does not exist.

Today the personal layer is split three ways: a file with a repos: section, a scope_settings table doing the same job at a different rank, and routing tables. Precedence runs by specificity instead of ownership, so lf set agent in a repo beats the committed file while lf set --global agent loses to it. The strongest input, LF_AGENT_OVERRIDE, is invisible and gets saved onto every Task a conversation creates.

2 · Three choices, three owners

Every launch needs a harness, a model and an account. They are not one setting with three parts.

ChoiceWhat it isWho choosesDeclared in
Harnessthe program that runs: claude, codex, …the person: their tools and subscriptions; the repo may suggestpersonal file, repo file
Modelthe quality and cost tier of the workthe step: routing is cheap, implementation is deep; the person may cap or raisestep frontmatter as a tier; personal map from tier to model
Accountwhich login pays right nownobody by hand: whichever allowed login has roompersonal file lists allowed logins; the store observes room

Today agent: claude:sonnet bundles harness and model into one string, read from six places. Splitting them lets a step's choice survive a harness switch and lets the account change without anyone editing anything.

What the work needs

# builtins/ops/skill/xor-route.md
tier: fast

# a graph step
- implement:
    tier: deep

Tiers: fast, standard, deep. No tier means standard. A step may pin an exact model: when it needs one; rare and said so.

What the person has

# ~/.lf/config.yaml
harness: claude                      # or [claude, codex]: fallback order
accounts:
  claude: [jack@loopflow.studio, jackstah@gmail.com]   # allowed, preferred first
models:                              # optional; lf ships a default map per harness
  claude: {fast: sonnet, standard: opus, deep: fable}
repos:
  /Users/jack/src/manabot:
    models:
      claude: {deep: opus}           # cheaper deep work in this repo

Your "Claude only" rule is harness: claude here, enforced by resolution instead of remembered.

What has room

The store keeps what it keeps now: per account, per usage bucket (weekly and Fable are separate), used percent, resets_at, cooldown. Every process that sees a limit records it; lf account refreshes it by polling. Today both Claude accounts sit at 94% and 99% weekly while the Fable bucket is untouched on both.

3 · Resolution: one function, one explanation

A Route is (harness, model, account). One resolver produces it for every launch, headless or interactive:

  1. Harness: invocation -a → personal harness → repo harness → error "no harness configured". No first-installed guess.
  2. Model: invocation -a claude:opus → step model: → step tier through the person's map for that harness → the harness's standard.
  3. Account: the allowed accounts for that harness in preference order, the first whose bucket for that model has room. None → next model in the tier's ladder (deep: [fable, opus]) → next harness in the person's list → wait until the earliest resets_at.

lf route prints the Route for the current context and why. lf route --graph code prints one line per step. That is the proof for part (b).

How a Route reaches the process

  • Model: --model on the harness command line.
  • Account: CLAUDE_CONFIG_DIR / CODEX_HOME point at the account home. Account homes share projects/ with ~/.claude, one more linked name beside skills and settings, so native history is in one place and --resume works on any account.
  • The Route is recorded on the Session. A Session has one current Route; re-routing replaces it and keeps history. The invariant at session_record.rs:1914 ("retry must retain its thread unless the account changes") is deleted: the thread is always retained.

4 · Limits: the same resolver, called again

Headless step

The step's process reports the limit, as today. The runner resolves a new Route and relaunches the same conversation with --resume. Account or model change keeps native history; harness change imports it (Resume::Import exists). If the resolver says wait, the Graph process sleeps until resets_at and Task status reads "waiting for jack@loopflow.studio weekly reset at 06:00Z". No retry budget: a limit is not a failure.

Interactive Session

lf cannot act inside a TUI and does not need to see the limit from inside. The Session's Route names an account, and the store knows when that account's bucket is exhausted. Every Session whose Route is exhausted is limited. lf route --apply, or a Desktop banner "3 Sessions limited, continue on jackstah@gmail.com", re-resolves each and relaunches it with --resume. One action for all of them. Nothing moves while you are typing in one.

Today: headless steps fail over to another account but drop the thread and start a fresh conversation with "re-read the workspace", bounded by a fixed retry schedule, and never wait. Interactive Sessions get nothing after launch.

5 · What goes away

  • default_agent: and agent: in skill frontmatter, skill_agents, config.agent, the first-installed fallback
  • LF_AGENT_OVERRIDE inheritance into Tasks a conversation creates, and the saved Task agent
  • scope_settings and provider_routes tables; lf set edits the personal file
  • LIMIT_FAILOVER_PROMPT, CREDENTIAL_FAILOVER_PROMPT and the fresh-conversation failover path; the thread invariant at session_record.rs:1914
  • lf account route (becomes lf route); supported_harnesses in the personal file

6 · Open

  • Tier names, and the default per-harness map: which Claude model is standard today.
  • Wait: the Graph process sleeps, or exits "waiting until T" and lf task run continues after reset.
  • Desktop learns of a personal-file change by a watcher, or lf set bumps a store revision after writing.
  • machine: and the "copied to your other Machines" promise once the table is gone.
  • repos: keyed by path is machine-specific; keying by remote lets the file travel.
  • Scope: LOO-714 carries the config unification, or a separate Task does and LOO-714 depends on it.
