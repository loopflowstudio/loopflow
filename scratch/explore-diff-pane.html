Six ways the
diff pane could read.

Only the diff pane this round. The same change appears in every panel, drawn at the width the pane really has beside a conversation, about 540 points. That width is the constraint most of these answer: side by side falls back to unified under 640.

The decision: which of these reads better than the stream you have, alone or mixed. If none does, question 1 asks what is wrong with it.

Built today exists: one stream for the whole comparison, unified or side by side, word emphasis, collapsed moves, ]/[ across files, Focus file, select → Ask, live with the anchor kept. Everything below is proposed and simulated.

1Result first proposed

You read the file as it is now, as code, top to bottom. What changed is a mark in the gutter; what it replaced unfolds in place when you ask.

Demo
Open a changed file: no red anywhere, real line numbers, the whole function in view. Green and blue bars in the gutter. Click a bar, or press space on a stop, and the old lines open above it; again and they close. ] still walks the bars.
Cost
Swift only. Files' Read already loads the file; the hunks from lf task diff map onto its new line numbers. It becomes a third layout beside Unified and Side by side, on the same rows and stepper.
Risk
A pure deletion is a small red tick between two lines and easy to walk past. A deleted file has no result to read.

2Flip in place proposed

One column, full width, and a key that swaps before for after without anything moving. Your eye stays on the line and the difference shows as motion.

Demo
Stop on a change and hold space: the lines become what they were; release and they are back. Changed words stay tinted in both states. A tap toggles instead of holding.
Cost
Swift only, and small: side by side already pairs old rows with new ones; this draws one side at a time in the same slots.
Risk
You compare from memory, which works for a line and fails for thirty. When before and after differ in length, the slots need padding or the text below jumps.

3Quiet diff proposed

The pane tells an edit from a shuffle. Renames, reordered imports, whitespace and moves fold to one line each, counted and one click from open, so what is left is what changed behaviour.

Demo
A 7-hunk file opens as 2 changes to read and 4 quiet rows: renamed changesAnchor → changesPlace · 3 places, imports reordered. Click a quiet row to see it. One toggle shows everything as today. ] skips quiet rows; ⇧] does not.
Cost
Token heuristics in ReviewDiff, next to the move detection already there: whitespace-only, same-set reorder, one substitution repeated across hunks. No parser. Swift, with tests per class.
Risk
A folded line that mattered. A rename that also changed a call's meaning must not fold; the rule has to be "identical but for this one token" and the count always in view.

4By symbol radical success

The unit is the function, not the line range. The pane lists what was added, changed, moved and removed by name, shows a changed signature as a signature, and always gives you the whole body.

Demo
Changes opens on a list: step(_:) changed · openNeighbour(_:) added · restore(_:) moved · changesAnchor renamed. Pick one and read the complete function with its edits inside. ] goes symbol to symbol across files.
Cost
The largest here. A syntax parse per language (Swift, Rust, Python at least) on the Rust side, a symbol list on the lf task diff DTO, and a reader that groups rows by it. New dependency: tree-sitter grammars.
Risk
Code caught mid-edit does not parse; files in other languages have no symbols. Both need the line stream as the fallback, so this adds a mode and never replaces one.

5Map of the change proposed

The whole comparison is visible at once as a strip down the side: every file, every change, coloured by kind, with a frame for where you are. You know how much is left without counting.

Demo
Open a 27-hunk PR: the strip shows it is mostly one file and a tail of tests. Scroll and the frame travels; click a tick and the stream goes there. Ticks you have passed fade.
Cost
Swift only. The stepper already holds every stop in order; the strip draws them in proportion and reads the scroll offset. The cheapest of the six.
Risk
46 points taken from a pane that is short of them, and on a five-hunk change it is decoration. It may want to appear only past some size.

6Reading order proposed

The stream runs in the order that explains the change. The type before the code that uses it, each test beside what it tests, generated files last.

Demo
Switch from By path to To understand: the new enum comes first, then the store that keys on it, then the view, with the test for each directly under it. The change you were on stays selected through the reorder.
Cost
An ordering pass over the hunks: which hunk defines a name another hunk uses (a token match over added lines, no parser), and test files paired to sources by name. Swift, in ReviewDiff.
Risk
The design forbids a second file list that disagrees with lf task diff --files; this is the same list in another order, and it has to say so. An order that shifts as the agent writes would move your place.
