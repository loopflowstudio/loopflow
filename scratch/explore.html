The decision: what you see when you switch to a Task whose conversation isn't on screen. All three visions drop the Open click, land you at the bottom, and handle takeover the same way (at the end). They differ in what runs in the background and in what memory pays for.

Click Tasks in each switcher. The meter shows what's running.

you select a Task, see "Not running here", and click Open. After a reboot you do that for each Task. 82 Claude processes were using 24.3 GB, and Desktop was at 2.5 GB with about 15 terminals.

A · Bounded live terminals

Every Task is a real terminal. The recent ones are instant, and older ones come back in a few seconds.

This is the draft plan. Desktop keeps the 8 most recently selected terminals. Rust lets 8 more idle conversations keep running with no terminal. Everything else ends quietly and resumes from Claude's history when you select it, with "Resuming…" shown over the last screen. After a reboot, lf resume --all brings back only what was within those limits.

terminal + agentagent onlyended, resumes from history
AppealNothing new to learn: every conversation looks the same as it does today. The work is small: Swift selection, a pane cap, and a count on the existing 24-hour idle limit.
Cost and riskA Task outside the 16 shows "Resuming…" for 2–5 s. Memory is up to 16 agents (about 8 GB worst case). Text you typed but didn't send in an ended conversation is lost.

B · Read now, live when you type

Every conversation opens instantly as readable history. An agent runs only while it's working or you're typing to it.

Rust already reads every harness's native transcript (transcript/, used today by -a handoff). Switching to a Task shows that history at the bottom immediately, rendered natively and live-updating while a turn runs. Clicking into the composer or typing resumes the agent behind it, and the view becomes the terminal. When you leave, the terminal goes away after a short grace, and the agent ends once it's idle. A reboot costs nothing, because nothing needs resuming until you type.

agent working or being typed tohistory only (no process)
AppealMemory scales with what's active (a few agents), not with how many Tasks are open. Twenty or a hundred Tasks cost the same. Switching is always instant, and reboot recovery disappears as a problem.
Cost and riskIt adds a second rendering: a native transcript view next to the terminal. Your first keystroke waits 2–5 s on a resume unless the composer drafts while it starts. Terminal-only UI (permission prompts, menus) appears only once the conversation is live.

C · Never see "Resuming"

Desktop keeps live whatever you're likely to open next, so every switch is instant and stays a real terminal.

Desktop keeps the Tasks you're likely to need running: ones waiting on you, ones with a turn in progress, and the recent ones. When you hover or arrow onto a Task, it starts warming (resume without a turn) before you commit. After a reboot, every open Task resumes in the background, one at a time in order of recency, until the budget is full. Anything past the budget falls back to A's "Resuming…".

terminal + agentwarmed agentended
AppealThe one that feels like magic: real terminals everywhere, and the wait happens before you click. Notifications ("waiting on you") warm up their Task automatically.
Cost and riskIt uses the most memory (a budget of about 12 warm agents) plus prediction logic to tune. Hover-warming spends a Claude start on Tasks you only glanced at. The reboot catch-up is a burst of CPU. It also stretches the brief's "prefetch prepares nothing" rule: no turn starts, but processes do.

The same in every vision: takeover

Another terminal runs lf resume LOO-672, so LOO-618's default takeover moves the conversation there. The Desktop pane keeps its last screen, dimmed, and explains itself. Desktop never takes it back without a click.

the pane is replaced by "Active in another terminal" and a Move here button. A viewer that gets replaced inside the same session process is dropped silently, with no notice at all.

In B the dimmed screen can keep updating, because the other client is still writing the same history. So you can watch it work from Desktop without taking it back.
