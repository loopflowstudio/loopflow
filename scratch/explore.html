What we built: hold direct chats in lf holder run and split session endings

Whenever lf server is running, interactive lf, lf -a agy, and lf <skill> launches now run inside lf holder run instead of directly in Rex's PTY. Opening the same conversation in Desktop or another Rex tab attaches as a second viewer instead of killing and restarting the provider. Standalone chats idle with zero viewers for 15 minutes retire cleanly without auto-committing worktree edits.

Key design fork: what should the HTML be allowed to trigger?

Both options use the exact same loopback server route (bound strictly to 127.0.0.1, capability token per session, zero CORS, same-origin check). They differ on whether the page only steers the agent or also invokes lf commands directly.

Option A: Steer-only (smallest surface, agent acts in the Rex left pane)

How it works: Submitting the page does exactly one thing: calls lf steer (or delivers input to the active Session) with your clicked choices, free-form direction, and anchored highlight comments. The live agent sitting in your Rex left pane receives that message immediately and executes whatever you asked (fixing F1, calling lf task create for F2, answering your highlighted questions, or advancing).

Appeal: Tiny server endpoint (one route: POST /p/:token/steer). Zero command-execution policy to maintain, zero risk of an HTML artifact silently running mutations, and every decision stays visible in the Session transcript.
Trade-off: Simple mechanical actions (like "File Task for F2" or "Move on to delivery") still cost one LLM turn in the left pane instead of firing instantly.

Option B: Steer + narrow allowlisted lf actions

How it works: Submit always previews the exact actions before sending. Choices and highlight comments go to lf steer; explicit structured button intents (strictly allowlisted in Rust: task.create, task.advance, task.land, steer) can also execute directly in lf server with zero LLM latency. Arbitrary shell commands are never accepted.

Appeal: Clicking File Task on F2 + Move on executes deterministically in milliseconds, even if no interactive agent is currently attached to the Task.
Trade-off: Larger server contract (typed action schema + preview UI + error handling when an action fails mid-batch).
