Three goals, and the four choices that move them

Any holder removes the per-Session owner process. After that, four choices are left. Two of them help all three goals at once. One, where the terminal emulator lives, sets "least duplicative with Rex" against "best Desktop experience", and a short probe measures how far apart they really are.

Built from scratch/holder.md, docs/dev/server-first.md, rust/loopflow/src/transport/README.md, transport.rs, transport/terminal.rs, research/server-protocols.md and a ps sample of this Machine at 18:29.

An owner is a whole lf process: 36 MB at the median, 76 MB at most. Thirty of the 126 were using 1% of a core or more while their conversations sat idle. All of that goes with any cut below, replaced by one holder per build and some state inside the server that already runs.

So on the first goal, the holder is worth about a quarter of today's memory, and it is not the largest piece. The choices below decide how the remaining cost grows with the number of Sessions, and what the result is like to use.

1. Give the held terminal its own model

  • 1a Move today's owner loop into the server: one thread and one private socket per terminal.
  • 1b A terminal registry in the server, one event loop, views dispatched straight to terminal state.
LoadWith 1a every byte takes view → server bridge → Session socket → loop → holder, and each terminal keeps a thread. With 1b it takes view → server → holder and nothing runs until a file descriptor is ready. Why idle owners burn CPU today has not been traced; if the loop's own timers are the cause, 1a carries them into the server 126 times over.
Responsibilities1b says what is true: a Session has a terminal, the terminal sits in a holder, and only real processes appear in the process list. 1a needs adapters that pretend a server thread is an owner process, and the next Task (every view types) deletes them.
DesktopNothing looks different in this Task. 1b is what lets Desktop and lf ps answer "how many Sessions is this Machine holding" from one place.

All three goals point the same way. The cost is more transport extraction now and a changed attach route for managed Sessions.

2. Where the emulator lives

The emulator is the headless Ghostty terminal that paints a view opening late and answers the agent's terminal queries while nobody is watching. Something has to hold one per Session. It is also most of what Rex is.

  • 3a In the server. The holder keeps PTYs and 2 MiB of raw bytes each. Said in LOO-819: "Yea the second".
  • 3b In the holder, beside the PTY. Rex and Paseo do this.
Responsibilities: favors 3aA 3a holder does five things: start, write, resize, read from a byte position, report exit. Rex's block API appears to offer the same five, so a Rex block could stand in for the holder later and the Session would open natively in Rex. A 3b holder is a PTY owner with an emulator, scrollback and a snapshot protocol that must stay readable across builds: a second, smaller Rex that Loopflow maintains.
Desktop: favors 3b, by an amount not yet measuredWith 3b a server restart loses nothing: every pane, including one opened for the first time afterward, is painted from an emulator that never stopped. With 3a the emulator is rebuilt from the ring. Rows are mostly safe: a joining view is painted at most 2,000 rows or 768 KiB today, and the ring holds 2 MiB. What may be wrong is state set before the ring begins: bracketed paste, focus reporting, the Kitty keyboard stack, program colors. The kickoff probe showed Claude and Codex redraw rows and cursor after a size nudge. It could not see modes.
Desktop: also favors 3aThe holder is the one process whose death ends every agent on its build. 3b puts a terminal parser fed by agent output inside it. In the server, the same parser failing costs a reconnect.
Load: roughly evenThe same parsing and the same scrollback (up to 8 MiB per Session, as today) happen in one process or the other. 3b saves the holder → server copy for Sessions nobody is viewing. 3a lets old-build holders stay tiny.

3. Let open panes continue from a PTY position

  • 4a A view's place in the stream is a count of PTY bytes, answered from the holder's ring.
  • 4b As the kickoff plan has it: after a server restart every view refreshes from the rebuilt emulator.

Today a view's resume position counts its own stream and lives in a 1 MiB spool inside the owner. Move the owner into the server and that spool dies with every install, so every open pane repaints. The holder already numbers its bytes. If views use the same numbers, a pane that was open through the restart asks for "everything after byte N" and carries on: no redraw, its own scrollback untouched, whichever emulator choice is made.

DesktopThe common case, an install while panes are open, becomes a pause and nothing else. The emulator question shrinks to panes opened cold after a restart.
LoadNo per-view spool in the server; a slow view rereads from the ring.
ResponsibilitiesOne numbering for output, owned by the holder.

Cost: the snapshot a view starts from has to be tied to a PTY position, which changes the viewer stream. More than 2 MiB of output during the gap falls back to a refresh.

4. Leave the disk journal out

1c writes emulator checkpoints and output to disk so a crashed server can restore the exact screen. It adds continuous writes for every Session, terminal output at rest, retention rules and a format to migrate. It helps only the case 4a does not already cover: a pane opened cold after a server crash. And 3b would cover that case without a disk. None of the three goals moves enough to pay for it.

5. Which launches the holder takes

  • 2a Plain lf resume SESSION of an ended Task or Wave Session starts it managed.
  • 2b It follows where it was typed: bare in a plain terminal, managed from a Task or Wave command or from Desktop.
Responsibilities2b keeps the line where server-first drew it. In Rex the agent is the foreground program and Rex keeps it alive; Loopflow adds nothing Rex already does.
DesktopWith 2a, a Task conversation resumed from any terminal is the same live process Desktop shows. With 2b, Desktop shows that Session as running elsewhere, and opening it there starts a new process from its history.
LoadNo difference worth counting.

Rex behind the same five messages

A sketch, read from rex help text on this Machine. Nothing here has been run against Rex.

With 3a the server never asks a holder for a screen, only for bytes, so a holder is replaceable by anything that keeps a PTY. On a Machine with Rex, managed Sessions could live in Rex blocks and Loopflow's own holder would be what runs where Rex does not. With 3b that door is narrower: the server would depend on a snapshot format only Loopflow's holder speaks. Earlier, on the same idea: "could we make it so that we actually make rex an dependency of loopflow and have rex own the terminal?" and "potentially weird thing there would just be if you then open rex you see all of your loopflow stuff".

One reading

1b and 4a, no journal: they cost work and nothing else. For the emulator, the open fact is whether Claude and Codex set their modes again after a resize. Repeating the kickoff probe through the production Ghostty emulator answers it in an afternoon. If they do, 3a gives up almost nothing a Desktop user would see and keeps the holder something Rex can replace. If they do not, the choice between 3a with a known flaw on cold opens and 3b is a real one, and it is yours.

Questions

1. How does the server model a held terminal?

  • 1a Move the loops.
  • 1b Terminal registry and one event loop.
  • 1c 1b plus the disk journal.

2. Plain lf resume SESSION for an ended Task or Wave Session

  • 2a Managed, because of the Session's Task or Wave.
  • 2b Follows where it was typed.

3. Where does the emulator live?

  • 3a Server, as said in LOO-819.
  • 3b Holder, as Rex and Paseo do.
  • 3c Run the mode probe first, then choose.

4. Open views across a server restart

  • 4a Continue from a PTY position.
  • 4b Refresh from the rebuilt emulator.

Combinations, a different weighting of the three goals, or another round are all answers.
