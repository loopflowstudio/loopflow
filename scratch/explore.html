How far should AgentProcess separate from LfProcess?

The decision: which of three type shapes the implement step builds. All three add AgentProcessId. They differ in what an agent row is. Today, on main:

pub struct LfProcess {
    pub id: LfProcessId,                 // agent rows too
    pub kind: ProcessKind,               // runtime switch, 39 uses in 18 files
    pub agent_session_id: Option<LfSessionId>,   // null on lf rows
    pub via_agent: Option<bool>,                  // null on agent rows
    pub caller_session_id: Option<LfSessionId>,  // null on agent rows
    pub caller_agent_process_id: Option<LfProcessId>,  // names an agent, typed lf
    ...
}

14 fields named agent* are typed LfProcessId (rg 'agent[a-z_]*: *(&|Option<&?)?LfProcessId' rust).

A. Rename the fields, keep the row

Every AgentProcess reference is typed; the inventory row still isn't.

uuid_id!(AgentProcessId);
+ pub caller_agent_process_id: Option<AgentProcessId>,
+ // SessionRecord, AgentCaller, Steer, SessionAttachment: AgentProcessId

// at the one place a row becomes a reference:
let agent = AgentProcessId::from(row.id.as_str());   // kind == Agent checked by hand

Cost: smallest diff, about a day. Risk: the row's id is still an LfProcessId for agent rows, so store.process(&row.id) on an agent row compiles. ProcessKind and its runtime branches stay. The schema shows AgentProcess nowhere; agents remain "an LfProcess with kind=agent". This is the gap the Task names, moved one layer down.

B. The row is a tagged enum (kickoff's plan)

An agent row is an AgentProcess; mixing them up doesn't compile.

#[serde(tag = "kind", rename_all = "snake_case")]
pub enum ProcessEntry { Lf(LfProcess), Agent(AgentProcess) }

pub struct AgentProcess { pub id: AgentProcessId, pub agent_session_id: .., .. }
pub struct LfProcess    { pub id: LfProcessId, pub via_agent: .., pub caller_agent_process_id: Option<AgentProcessId>, .. }
- pub enum ProcessKind { Lf, Agent }

What a reader sees:

$ lf history list --json | jq '.entries[0:2]'
[{"kind":"lf","id":"5e1c…","via_agent":true,"caller_agent_process_id":"a03f…", …},
 {"kind":"agent","id":"a03f…","agent_session_id":"9b2d…", …}]
# same ids, same "kind" values; each row drops only its always-null keys

Cost: 2–3 days; touches ~18 files for ProcessKind plus the 14 reference sites, and Swift's TaskWork.processes becomes [ProcessEntry]. No migration. Risk: conflicts with #1813 in process.rs, id.rs and Swift models, whichever lands second. Released Desktop keeps decoding (dropped keys were optional).

C. Two inventories (radical)

History lists what lf did; agents live under their Session and nowhere else.

$ lf history list --json        # LfProcess only
$ lf session show 9b2d --json | jq .agent_processes
[{"id":"a03f…","pid":4182,"started_at":…,"outcome":"exited"}]

// store: agent_processes table, processes(kind) column dropped
+ migrations/split_agent_processes.sql   -- expand now, contract after STAGING_DAYS

What's true: no mixed-kind reader exists anywhere, so no enum, no cursor over two kinds, no --parent ambiguity. The activity tree in lf top joins Sessions to agents explicitly. Cost: a staged migration (expand, ~30 days, contract), a new Session read API, rewriting top, rollover, task_execution and FORGETTABLE pruning. A week plus the staging window. Risk: the plan lists "a migration" as forbidden for this Task; history loses agent rows that a person reads today when they list everything that ran.

C is the cleaner end state but spends a migration and a new read API on a type-safety Task; it reads better as its own Task if mixed history ever becomes a burden. A leaves the stated gap open.
