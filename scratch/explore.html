LOO-1125 · Route realign fixes back through implement and concept-review

Decision needed: Pick how strictly realign stops editing code, tests, and docs—prompt-only everywhere, split by loop vs standalone, or paired with a mechanical freshness check so scratch/concept-review.html cannot go stale silently.

Visions

Vision A · Plan-only realign everywhere (recommended baseline)

What is true: One single rule across every caller (build, plan, refresh, standalone)—concept-review is read-only, realign edits only scratch/ (and Wave memory when asked), and implement owns code, tests, and docs.

  • Mechanism: Rewrite realign.md so any in-scope mismatch (code, tests, or docs) goes into scratch/plan.md as remaining work and returns iterate when deciding a loop; zero in-scope fixes (all "Yes" or only ## Deferred findings) returns advance immediately. Update tests/goldens/builtin_realign.md, docs/orchestration.md, refresh.yaml description, AGENTS.md, and .lf/qa/skills.md.
  • Demo: Run the build outer-loop fixture (or lf -b -a claude:haiku realign) against a scratch/concept-review.html with one small code mismatch and one separate-outcome finding. git diff shows zero code/doc edits, scratch/plan.md queues the mismatch as the next pass and lists the separate outcome under ## Deferred findings, and the decider returns iterate. Once implement fixes it and concept-review turns all rows to "Yes", realign returns advance without extra passes.
  • Appeal: Smallest, cleanest system. No conditional loopholes for an agent to rationalize around, and matches instruction_levels.json already.
  • Cost & risk: Even a 2-line naming or doc fix surfaced by concept-review pays one extra sync → implement → concept-review → realign pass (~4 steps). Outside a loop (refresh / standalone), mismatches land in scratch/plan.md rather than being patched on the spot. Enforcement is prompt discipline rather than a runtime check.

Vision B · Loop-gated split (plan-only in loops, inline fixes outside)

What is true: Inside a loop (build), realign never edits code/tests/docs and always iterates; outside a loop (refresh, standalone lf realign), it may still patch small, clear mismatches inline.

  • Mechanism: Keep the inline-fix clause scoped explicitly to non-loop invocations, and add an explicit prohibition in ## After a review and ## Deciding a loop so loop runs always write fixes to scratch/plan.md and return iterate.
  • Demo: In build, behaves identically to Vision A (queues small fixes and iterates). In lf graph refresh after a small upstream rename, realign can still patch the 1-line import without needing a separate implement step.
  • Appeal: Keeps refresh and manual lf realign one-shot for tiny upstream drift.
  • Cost & risk: Two conflicting permissions in one prompt invite backsliding—under headless loop pressure, seeing "fix small mismatches yourself" anywhere in realign.md makes models rationalize inline edits during build. Also conflicts with standalone_realign in instruction_levels.json.

Vision C · Radical success: Plan-only realign + mechanical freshness guarantee

What is true: realign is plan-only everywhere (everything in Vision A), and the runtime makes unreviewed code edits after concept-review structurally impossible to miss or silently advance past.

  • Mechanism: Everything in Vision A, plus two small runtime additions:
    1. lf page build records the reviewed HEAD SHA in the compiled page metadata (or concept-review stamps it), so ship-review and humans can immediately see whether scratch/concept-review.html matches the pre-compress code or is stale.
    2. Optional loop guard: if a loop's decider step (realign) modified tracked non-scratch/ files and returns advance, the loop runner either rejects the decision with a correction turn ("non-scratch files changed; iterate or revert") or forces an iteration.
  • Demo: Seed a fixture where a stand-in realign edits src/lib.rs and returns {"decision":"advance",...}; the graph runner refuses to advance past unreviewed edits (or stamps concept-review.html as stale vs HEAD in ship-review).
  • Appeal: Turns a prompt hope into a verified invariant—even a customized realign skill or a stubborn model cannot ship unreviewed post-review edits with a stale concept-review.html.
  • Cost & risk: Expands scope from prompt/docs/goldens into Rust loop-runner and/or page-builder code and tests. A hard guard in the loop runner also needs care so legitimate deciders that do edit code (like implement in build's inner loop or quick) are not affected—meaning the constraint would need to be declared on the step or skill (e.g. a skill/step capability or narrow rule) rather than hardcoded by skill name.
