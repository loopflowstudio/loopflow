Diff v2: where the colors come from, and how Markdown, images and HTML read

The Diff pane LOO-515 built colors only comments, strings, numbers and keywords. It also can't show a Markdown file, an image or a page as what it is. This page offers four ways to get real grammar highlighting, then a working sketch of rendered diffs, which every one of them needs.

The decision: which engine colors the code (question 1). The rendered-diff questions (3–6) are smaller and independent. Answers like “1a, 3a, 5b” are complete.

Today marks what ships now. Proposed marks what this Task would build.

Four engines

All four color both views. They differ in where the grammar runs and in what else that place gives you.

A Native tree-sitter in the app recommended

The Mac app links tree-sitter and its grammars. It parses the old and new files whole, then colors each Diff row by its line number. The same parser recolors the Files editor as you type.

SyntaxColors.swift (230 lines) is replaced by a Grammar that wraps a SwiftTreeSitter parser and its highlights.scm query. Each grammar's capture names (@keyword, @type, @function, @property, @markup.heading …) map to theme inks in one table. While a file's full text loads, a row is colored by parsing its hunk alone. That's the same quality as today, and it upgrades in place when the full parse arrives.

Demo
Open a Task's Diff on a Swift, Rust or TypeScript change and see types, calls and properties in color, in Flexoki Dark and Light. In Files, type /* in a 5,000-line file and see the rest of the file recolor at once.
Needs
The old side's full text, from lf task file <issue> <path> --base <rev>, a new served read. The rendered diffs need it too.
Cost
About 1–1.5k lines of Swift. SPM dependencies: SwiftTreeSitter plus one package per grammar (about 14 for the languages this repository uses). The app grows by an estimated 8–15 MB. A follow-up could move the editor to incremental parsing and drop the 200k-unit limit.
Risk
Grammar packages vary in quality and in which tree-sitter ABI they target, so they need pinning. Upstream highlights.scm files name captures inconsistently, so some languages need a local query. Two parses per file near the view is fine, but it has to stay lazy.
Appeal
One highlighter for the Diff and the editor. No wire change. Works the same on a peer Machine's checkout, because the app colors text it already has. iOS gets it if Grammar lives in the shared Loopflow library.

B lf colors it: spans on the wire

lf task diff --json returns each line with its highlight spans, computed in Rust with tree-sitter-highlight. Desktop, iOS and lf task diff in a terminal all show the same colors.

Demo
lf task diff c9fbcb in a terminal prints grammar colors, and Desktop's Diff matches it token for token.
Cost
Rust grammars are cargo crates, so that half is easy. The wire DTO grows: a new required field, fixtures in tests/fixtures/dto/, and Swift decoding. Payloads get 3–5× larger. The Files editor still needs a native highlighter for typing, so either there are two highlighters or the editor keeps SyntaxColors.
Risk
“One implementation” breaks at the editor. Every theme change is a client concern anyway, so the spans carry capture names, not colors.
Appeal
Follows the rule that state the CLI and Desktop both show is written once in Rust. The terminal diff gets better for free.

C The Diff becomes a web view: Shiki through Pierre

The Diff stream renders in a bundled, offline WKWebView using @pierre/diffs and Shiki, which is how T3 Code does it. Highlighting uses VS Code's TextMate grammars. Rendered Markdown and HTML come almost free.

Demo
Desktop's Diff looks like T3 Code's, with VS Code-grade colors in every language Shiki ships.
Cost
Replaces ReviewStreamView (758 lines) and rebuilds what LOO-515 just made native inside it, bridged through JavaScript messages: keyboard stepping, selection, comments, Viewed, the step menu and the lazy stream. The JS bundle is 2–5 MB with Oniguruma WASM. The Files editor still needs its own highlighter.
Risk
High. It throws away a reviewed native pane, and WebKit crashes in this app have surfaced as silent exit 1 before. Pierre is young and its API may move.
Appeal
The best grammar coverage and the least highlighting code of our own.

D Radical: the Diff understands structure

The tree-sitter parse from A also drives the diff itself. Reindents, reflowed arguments and moved functions stop showing as changes, and a change is marked at the node that changed (difftastic's idea). Every document opens as what it is: prose rendered with redlines, images compared, pages live.

task.rs · structural1 change · 14 lines reindented, hidden
    let runs = store.graph_runs(&task.id, Order::Newest)?;
  ⋯ 14 lines moved into `if let Some(run)` unchanged
Demo
A Task that wraps a block in if let shows as one marked line, not 30 red and green ones.
Cost
Everything in A, plus a structural diff. Difftastic isn't published as a library. Its --display json output is experimental, so it would mean vendoring code or shelling out to an unstable format. Its Dijkstra search also gets slow on large files and falls back to line diffs. Several weeks of work.
Risk
Comments, step menus and line selection all assume lines. Node-level changes need their own anchors.
Appeal
No other agent workbench does this, and agent diffs are full of mechanical reindentation.

Questions

  1. Which engine colors the code?
    1. A: native tree-sitter in the app, for the Diff and the editor
    2. B: lf computes spans and sends them on the wire, and the terminal diff gets colors too
    3. C: the Diff becomes a web view with Shiki and Pierre
    4. D: A plus a structural diff
  2. Where do syntax colors come from in each of the 24 themes?
    1. From the theme's terminal palette (ANSI 1–6), so a custom theme just works
    2. A hand-tuned syntax set per built-in theme, falling back to (a) for custom themes
    3. One set for light themes and one for dark
  3. How does a changed Markdown file open in the Diff?
    1. Rendered, with source one click away
    2. As source, with rendered one click away
    3. Whichever you used last for Markdown
  4. How are Markdown changes marked?
    1. Redline: one rendered document with removed text struck and added text filled
    2. Side by side: base and Task rendered in two columns
    3. Redline by default, with side by side one click away
  5. How does a changed image open?
    1. Side by side
    2. Swipe
    3. Onion skin
    4. Side by side, with swipe, onion skin and difference as modes in the header
  6. How does a changed HTML file open?
    1. Two live pages side by side
    2. One live page, toggled between base and Task
    3. As source, with rendered one click away
  7. Which languages are in the first slice?
    1. This repository's: Swift, Rust, Python, TypeScript/TSX, JavaScript, Markdown, YAML, TOML, JSON, SQL, shell, HTML, CSS
    2. (a) plus Go, C/C++, Ruby, Java and Kotlin, which today's list covers
