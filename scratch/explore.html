How should a Task Session hear its background work?

LOO-711 · explore · 2026-11-02. Four worlds. Pick one, or name the mix.

The decision: when lf task run moves a Task while its Session sits idle, what breaks the silence, and how often. The four worlds below differ by mechanism, not by wording. Kickoff chose the first; its findings hold for all four.

In transcripts, highlighted lines are proposed behaviour. Unhighlighted lines are what happens today. Times are from this Task's own kickoff run.

Today

13:18  you       lf resume --task LOO-711
       session   LOO-711 is moving: the feature Graph is running kickoff.

13:24            (kickoff finishes; the run stops before explore. Nothing happens here.)

13:41  you       what's going on now? did it finish?
       session   Kickoff finished at 13:24. explore is interactive and waits here.

A Session acts only during a turn. Steers and hooks paste text into the next turn; none starts one. The one thing that starts a turn in an idle Claude Code Session is a background command it launched exiting. lf task wait today is a one-second poll whose terminal means done or abandoned, so it never returns for a run that stops, and a timeout exits 0 like success.

1 · The Session listens

Every move of the Task's work is a short turn, spoken by the Session itself.

Before ending a turn with live work, the Session starts lf task wait LOO-711 --until moved --json in the background. The command rides the store's revision stream (the machinery behind --watch), returns on the first change of the Task's position after a 2 s settle, and Claude Code re-invokes the Session when it exits. The Session reads status, says what moved, re-arms.

13:18  you       lf resume --task LOO-711
       session   LOO-711 is moving: the feature Graph is running kickoff.
                 ⟶ lf task wait LOO-711 --until moved --json   (background)

13:24  session   kickoff finished. explore is interactive and waits here: read
                 scratch/loo-711-task-sessions-tell.md and say which approach
                 to build.
                 ⟶ re-armed

14:06  session   pursue started (Process 7e1c…). Nothing for you yet.
                 ⟶ re-armed

15:12  session   pursue failed: cargo test, 2 failures. Log at
                 .lf/logs/graph-01c1…/pursue.log. Reading it.
Cost. One reporting turn per step boundary, about ten per pass of feature; one idle lf process per open Session. Risk. Arming is skill text: a Session that forgets to re-arm is as silent as today. The interactive wake is documented for Claude Code and is being probed in this very Session right now. Codex, OpenCode and Pi have no such wake; for them the result lands on the next prompt. New code. --until moved on the watch loop, exit 2 on timeout, three skill files.

2 · Spoken only when it needs you

Desktop shows the step; the Session speaks when a person matters.

Same wait, same wake, a narrower return: the run stops at an interactive step, a step fails, the PR opens or its checks fail or it merges, the Graph reaches end. A step starting or finishing in the middle of a pass is shown, not spoken: Desktop's Task pane already reads Graph processes and can carry "feature · pursue · 12 min" live, and a terminal user runs lf task status --watch.

13:18  you       lf resume --task LOO-711
       session   LOO-711 is moving: the feature Graph is running kickoff.
                 ⟶ lf task wait LOO-711 --until needs-you --json   (background)

13:24  session   explore waits here. Read scratch/loo-711-task-sessions-tell.md
                 and say which approach to build.

       (Desktop pane, 14:06 → 15:12:  feature · pursue · running · 1h 06m)

15:12  session   pursue failed: cargo test, 2 failures. Log at
                 .lf/logs/graph-01c1…/pursue.log. Reading it.
Cost. Two or three turns per pass instead of ten. "What's it doing right now?" in a terminal still needs a question, or a second pane. Risk. Same wake dependence as 1. The event set is a product judgement baked into a flag; the skill text in 1 can express the same restraint without a second predicate. New code. As 1, plus the Desktop pane line if it is not already there.

3 · The Session narrates live

The Task Session is the Graph's console. Its turn stays open while the Graph works.

The Session runs the watch in the foreground and writes one line per frame as steps start and end, ending its turn only when the run stops at an interactive step, fails or ends. The run itself is detached, so Ctrl-C ends the narration, not the work.

13:18  you       lf resume --task LOO-711
       session   LOO-711 is moving. Following the feature Graph:
                   13:18  kickoff   running
                   13:24  kickoff   succeeded
                   13:24  explore   waits here.
                 Read scratch/loo-711-task-sessions-tell.md and say which
                 approach to build.
                 (turn ends)
Cost. The Session reads busy for the length of a step: an hour of pursue is an hour of "working" in Desktop's Session list, and anything you type queues behind the turn. A Bash call caps at ten minutes, so long steps mean re-arming in a loop. Risk. Kickoff rejected the Stop-hook form of this for exactly the busy cost; the foreground form shares it. New code. Least: today's --watch nearly suffices; the skill does the rest.

4 · Nothing wakes; the next prompt knows

Silence stays, but no question is ever needed: any prompt opens with what moved.

No background command, no wake. The UserPromptSubmit hook that already pastes steers adds a line built from GraphProcess rows: what moved since the Session's last turn. You type anything, and the report comes first.

13:18  you       lf resume --task LOO-711
       session   LOO-711 is moving: the feature Graph is running kickoff.

13:24            (kickoff finishes. Nothing happens here.)

14:02  you       hey
       session   Since 13:18: kickoff finished at 13:24; explore waits here.
                 Read scratch/loo-711-task-sessions-tell.md and say which
                 approach to build.
Cost. You still return to find out. The outcome in the brief says "without asking", and this only changes what you ask. Risk. None on the wake; works on every provider; zero tokens while idle. New code. A context-block line in the hook, keyed by the Session's last turn time. Composes with 1 or 2 as the fallback when a Session forgot to re-arm.

5 · The worker posts

lf posts each move into the Task Session; the Session wakes and reports.

Added during explore, 2026-11-02. The Session arms nothing. At each step boundary lf posts the event, read from GraphProcess rows, to the Task's interactive Sessions. On Claude Code the delivery is the same-machine session bus, probed today: a message from a headless peer woke this idle Session. On every harness it also lands at the next prompt boundary, the way steers do. This is the shape OpenClaw and Amp run: a structured status derived from exits, with an instruction for what to do next. Whether the worker agent may add its own prose is a separate switch.

13:18  you       lf resume --task LOO-711
       session   LOO-711 is moving: the feature Graph is running kickoff.
                 (turn ends; nothing armed)

13:24  ›  Message from lf: LOO-711 kickoff succeeded; explore waits here.
       session   explore is interactive and waits here. Read
                 scratch/loo-711-task-sessions-tell.md and say which approach
                 to build.

15:12  ›  Message from lf: LOO-711 pursue failed (exit 1); log .lf/logs/graph-01c1….log
       session   pursue failed: cargo test, 2 failures. Reading the log.
Cost. lf grows a per-harness deliverer: Claude's session bus now, OpenCode's server API and Codex's app-server later, next-prompt delivery everywhere. Steers today fan out to every member Session, including the worker that caused the event, so the post needs a target. Risk. The bus is undocumented Claude Code behaviour (a socket per session); if it changes, the Claude adapter falls back to world 1's wait. New code. The most: an event poster in the Graph runner, a target for interactive Sessions, one adapter per harness. No skill compliance needed for the wake; the skill only says what to do with a post.

What stays fixed in every world

  • No new store, steer kind, or event table: GraphProcess rows already say what moved.
  • No lf write into a Session's pty. The provider starts turns; lf only returns.
  • Headless Runs never arm anything: they report and exit.
  • lf task wait gets fixed regardless: watch-driven instead of a poll, exit 2 on timeout, status body as output.
