One word for Auto-Ship

LOO-968 · scratch/explore.html

Decision needed: what one idea is called, and whether it is a state at all. The idea: a person lets the Task's Graph take every interactive step on its own and merge.

Existing (PR #1976 as published): four words for one thing. 
lf ship LOO-12                # command: "ship"
lf task status LOO-12         # state: shipping · Auto-Ship: on by Maya, 09:04
lf task hold LOO-12           # "LOO-12 stopped shipping"
Desktop board                 # section: Autonomous   buttons: Auto-Ship / Stop Auto-Ship
store                         # task_graphs.auto_ship = on | stopped
The interrupted build pass had begun vision A (60 files). That diff is saved at refs/wip/loo-968-auto-ship-rename and still sits uncommitted in the checkout.

Jack's words that started the Task: "ship is supposed to be a small short hand that maybe updates the proposed graph to be auto mode … lets reduce its impact on the overall system and protocol".

A · Auto-Ship, everywhere

Keep every concept, rename the words to the one the buttons already use.

lf ship LOO-12                # LOO-12 · code from human-review running … · Auto-Ship on
lf task status LOO-12         # auto-ship · Auto-Ship: on by Maya, 09:04
lf task hold LOO-12           # LOO-12: Auto-Ship stopped
Board                         # Backlog · Working · Auto-Ship · Done

Demo: lf wave show lists an "Auto-Ship" section, and lf task status says auto-ship.

Appeal
Smallest change in meaning, and half built. Desktop copy stays as it is.
Cost / risk
About 60 files, including a wire rename (shipping→auto-ship, autonomous→auto-ship) and DTO fixtures. Three words remain: the command is ship, the stop is hold, and the mode is Auto-Ship. A noun used as a state reads oddly: "LOO-12 is auto-ship".

B · Ship, everywhere

The verb wins. You ship a Task, it is shipping, you stop shipping it.

lf ship LOO-12                # LOO-12 · shipping (code from human-review …)
lf task status LOO-12         # shipping · shipped by Maya, 09:04
lf ship --stop LOO-12         # LOO-12: stopped shipping        (task hold goes)
Board                         # Backlog · Working · Shipping · Done
Desktop                       # Ship · Stop shipping
store                         # task_graphs.ship = on | stopped

Demo: click Ship, and the card moves to Shipping. lf ship --stop moves it back.

Appeal
The command, state, section, button and stop all use one root word, matching the Task's title ("Ship is shorthand"). The shipping state and the ship --stop alias already exist, so the wire state stays.
Cost / risk
"Auto-Ship" leaves about 80 files: docs, operate skills, the Notice and the Desktop buttons. A migration renames the columns (unmerged, so it is edited in place). "Shipping" collides with the deliver steps every Task runs, so a Task with no Auto-Ship that is at pr-land also "ships".

C · A mark, not a state

Auto-Ship is a setting on the Task's Graph. The state says what is happening, and the mark says who takes the interactive steps. There's nothing to name twice because there is only one concept.

lf ship LOO-12                # LOO-12 · code from human-review running … · Auto-Ship on
lf task status LOO-12         # moving · Auto-Ship: on by Maya, 09:04
lf task hold LOO-12           # LOO-12: Auto-Ship stopped
Board                         # Backlog · Working · Done        (Auto-Ship tasks carry a badge)
ExistingProposed
TaskState… Moving, Shipping, Done …… Moving, Done … (Moving = "a Graph runs for it")

Snapshotauto_ship + derived stateauto_ship only; surfaces badge from it
task_state_sqlreads Auto-Ship to choose a labelnever reads Auto-Ship

Demo: lf ship LOO-12. The card stays in Working with an "Auto-Ship" badge and moves to Done when it merges. lf task hold removes the badge.

Appeal
The system gets smaller: an enum variant, a board section and one reader of the mark are deleted. The only remaining reader is the run, at each interactive step. This is the closest of the four to "reduce its impact on the overall system and protocol". The concept review's oddities go away too: an Auto-Ship Task that gave up reads idle, and a killed run no longer reads shipping.
Cost / risk
A wire removal: variants leave TaskState/TaskSection, plus Swift switches, WaveStandupBoard, WorkTone, Wave counts and AGENTS.md's work model. You lose a one-glance list of "what's running without me", which becomes a badge and a filter instead. About the same file count as A, but it deletes rather than renames.

D · Auto per step (radical success)

Every interactive step says who takes it: you, or the run. "Ship" means auto for all of them. You can also hand over only some steps, for example letting the run take human-review while you still verify on main.

lf ship LOO-12                       # auto: human-review, verify          (= every interactive step)
lf task run LOO-12 --auto human-review
                                     # auto: human-review · you: verify
lf task status LOO-12                # moving · code at build → human-review (auto) → deliver → verify (you)
lf task hold LOO-12                  # LOO-12: every step back to you
store                                # task_graphs.auto_steps = ["human-review","verify"] | []

Demo: run lf task run LOO-12 --auto human-review. The PR merges without a review page, and the Task then waits in its conversation at verify. Desktop's step dots mark the auto steps.

Appeal
"Auto mode" becomes a property of the Graph, which is the quote's literal reading ("updates the proposed graph to be auto mode"). It also answers the -b question: -b sets auto for its own run's steps only. It generalizes to Wave graphs that have several interactive steps.
Cost / risk
The biggest of the four. stands_in reads a set per step, the three-way mark becomes a list plus a stopped flag, and the Desktop step dots need an editor. It grows the concept, which runs against "reduce its impact". It could be a follow-up Task built on C, since C's data shape extends into it.
