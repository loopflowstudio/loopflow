Where the plan lives

Four worlds for plan management, each walked through the same four situations: one person on one Machine; one person with a laptop, a mini and a phone (with or without a team's Linear); five people with no Linear and no shared hub; a hundred people whose company runs on Linear.

The decision this page is for: what is the one mechanism that carries the plan between Machines, and separately, how much of a team's Linear Loopflow takes hold of (the last section).

Marks: exists is on main today. proposed is not. LOO-938's run b20a303b is building world A on this branch right now and has already deleted Git plan sync there.

A. One home being built

Each plan lives on exactly one Machine's server. Every other Machine saves locally and sends its changes there.

This is what you chose earlier today ("The hub owns it"). The branch has lf machine hub, plan.changes / plan.apply on the server protocol, and no Git planning ref, journal or field causality. Its conflict rule is the one Linear already has: the change sent last wins.

Laptop + mini + phone

laptop$ lf machine hub mini
laptop$ lf task create 'Cache the board read'      # returns at once
laptop$ lf repo tracker
Plan: hub mini. 1 open.
laptop$ lf repo tracker
Plan: hub mini. 0 open.
mini$   lf task list                               # the Task is there
phone:  asks mini, always the whole plan

Five people, no hub

ana$ lf task create 'Fix signup'
ben$ lf task list
# nothing. ana's plan is on ana's Machines; nothing carries it to ben.

Appeal. Smallest system: one writer of record, no merge, no journal (about 30 MB and 44k rows gone from the live store). The phone has one place to ask. Linear and Asana can be sent from the home alone.

Cost. Mostly paid: slices 1 and 2 are on the branch. What remains is moving etude and proving it against mini.

Risk. A team with no shared Machine cannot share a plan. Either the team runs one hub (a server someone keeps on), or hubs learn to sync with each other, which is peer sync again with fewer peers. Two people editing one title while one is offline lose the earlier edit without a trace.

B. Files in Git proposed

The plan is files on a ref in the repository. Git's own merge is the sync, Git's log is the history, and the store is an index you can rebuild.

Today's Git planning exists keeps a causal journal in SQLite and pushes one merged document. Here the journal tables go and the ref holds one file per Task, one field per line, so two people changing different fields merge like code does.

# refs/loopflow/plan : tasks/7f3a9c1e.md
title: Cache the board read
state: active
owner: jack@mini
wave: infrastructure
rank: 12
---
The board read launches git 120 times...

Just me, one Machine

$ lf task create 'Cache the board read'    # one commit on the local ref
$ git log refs/loopflow/plan --oneline -1
a41c9e2 create 7f3a9c1e Cache the board read
# new laptop: git clone brings the plan with the code

Five people, no hub

ana$ lf task update 7f3a --title 'Cache board reads'
ben$ lf task update 7f3a --rank 3
# both push; the second push is refused, merges, pushes again. Different lines: clean.
cy$  lf task update 7f3a --title 'Board cache'   # same line as ana
7f3a title: yours 'Board cache', ana's 'Cache board reads'. Kept yours; lf task history 7f3a shows both.

Appeal. No server and no hub at any scale; whoever can push code can share the plan. History, blame and review of plan changes come from Git. A person can read and fix the plan with a text editor.

Cost. Rewrite the ref format and the import, and turn the store's planning tables into an index of the ref. A migration for etude's 397 records.

Risk. Every save is a commit, and hundreds of agents pushing one ref race each other; each Machine would push its own branch and merge, which is real work. Nothing tells a Machine that something changed, so the fetch timer comes back (the 4,300 fetches an hour this Task started from). The phone still needs a Machine to ask.

C. Owner writes proposed

Only a Task's owner ever writes it. Each Machine publishes what it owns; the plan is everyone's feeds side by side, and nothing is ever merged.

Two things already point here: Tasks are owned as (person, Machine) with an ownership log exists, and since #1956 a Task's writes run on the Machine that runs it exists. This world makes that the sync rule. A change to a Task you don't own is a request its owner applies. Tasks nobody runs yet belong to the person who filed them, on that person's home Machine.

# one ref per Machine, written only by that Machine
refs/loopflow/plan/jack@laptop     12 Tasks
refs/loopflow/plan/jack@mini       41 Tasks   # and Jack's backlog: mini is his home
refs/loopflow/plan/ana@air          9 Tasks

Laptop + mini + phone

laptop$ lf wave update infrastructure --machine mini   # Wave's default Machine: exists today
laptop$ lf task create 'Cache the board read' -w infrastructure
Filed on mini (infrastructure runs there).
laptop$ lf task run 7f3a --machine laptop              # this one Task, here
7f3a moved mini → laptop.

Five people, no hub

ben$ lf task update 7f3a --title 'Board cache'   # ana runs 7f3a
Asked ana@air. Applies when her Machine next syncs.
ben$ lf task claim 7f3a                           # or take it
7f3a: asked ana@air to hand over.

Appeal. A conflict cannot be written, so there is no conflict rule, no journal and no lost values to show. Matches how work is already routed. Each Machine's ref is a fast-forward, so pushes never race.

Cost. A request queue between Machines, an owner for every record that has none today (Projects, Waves, order within a Project), and a "home Machine" per person for their backlog.

Risk. Waiting. Ben's edit to Ana's Task sits until her laptop opens; your own backlog edit from the laptop sits until mini answers. Taking a Task from a Machine that never comes back needs a rule, and that rule is where conflicts could return.

D. Owned plan, any road proposed

The far version of C: ownership decides who writes, and the feeds travel by whatever road is there. Between your own Machines, live through the server connection. Between people, through the Git remote. To a team, through Linear.

Sync stops being something a repository is configured with. A solo install has one feed and no road. Adding a mini adds a live road. Adding a teammate adds the Git road. Connecting Linear adds a road that carries only your slice. The same save takes every road that exists, and lf repo tracker lists them.

$ lf repo tracker
Plan: 53 Tasks you own, 9 of ana's, 14 of ben's.
  mini      live      0 open
  origin    git       0 open, fetched 40 s ago
  Linear    your slice (23 issues), 1 open

The same day at three sizes

# just me
$ lf task create 'x'                    # saved. No road, nothing sent.

# + mini and phone
laptop$ lf task create 'x' -w infrastructure
Filed on mini.                           # sent over the server connection, no fetch timer
phone:  asks mini; mini answers for laptop's Tasks from its copy of that feed

# + four teammates, no hub
ana$ lf task list --all                 # your feeds arrive with her next fetch of origin

Appeal. One mechanism for all three situations, and each step up adds a road without changing what a save means. Your own Machines are never slower than A; a team never needs a server. Linear becomes one more road and loses its special place.

Cost. The largest build: C's ownership and requests, plus two carriers (the live one is most of A's plan.changes/plan.apply, already on the branch; the Git one is one ref per Machine). The hub-as-home code on the branch would be reshaped, with the Git deletion partly walked back.

Risk. C's waiting, between people. Two carriers that must never disagree about what was delivered. It is the one most likely to take three Tasks, and the middle state has to be worth having.

A team that already lives in Linear

Separate from A–D: you adopt Loopflow first, the team's Projects stay theirs. Today a Wave's plan is one Linear Project and every issue in it becomes a Loopflow Task exists.

L1. Whole Project exists

A Wave takes the team Project whole. Works when the Project is yours. On a shared Project, Loopflow holds teammates' issues as Tasks, rewrites order, and moves states for work it doesn't run.

L2. Your slice proposed

A Wave is linked to a Project (or an Initiative, for several Projects). Loopflow stores only issues assigned to you. Everything else in the Project is read when you look, never kept and never written.

$ lf wave link growth --linear-project 'Onboarding Q1'
$ lf task create 'Shorter signup' -w growth
ENG-412 created in Onboarding Q1, assigned to you.
$ lf task list -w growth --available
ENG-398  Email verification retries      priya   unassigned
ENG-401  Signup page copy                —       unassigned
$ lf task claim ENG-401
ENG-401 assigned to you in Linear; it is a Task now.

Cost: assignment becomes the line between yours and theirs, so unassigning in Linear takes a Task out of Loopflow. Project order and Project state are never written.

L3. A place of your own proposed

Loopflow publishes to its own Project ("Jack: in flight") and links each issue to the team issue it serves. The team's Projects are never touched; people see your work in one place. Cost: two issues for one piece of work, and the team's board doesn't move unless you move it.

A hundred people on Linear

At this size Linear is where people meet. The A–D choice shrinks to what happens between one person's own Machines, and the question that grows is how much of Linear each Machine reads and keeps.

What changes with the number

Reading. Loopflow reads Linear by team: each Machine asks for what changed in every team that has a live Task exists. With L1, a hundred people's edits flow into every Machine and every store holds the whole company's issues. With L2, a Machine keeps the few dozen issues assigned to its person, and reads the rest only when someone looks.

# L1 at 100 people (today's shape)
$ lf repo tracker
Linear: 14 teams, 6,200 issues kept, 1,140 changed today by other people.

# L2 at 100 people
$ lf repo tracker
Linear: your slice, 31 issues kept. 0 open.

Writing twice. A person with a laptop and a mini has two Machines that can both send the same change. A answers with one sender (the home). C and D answer with the owner. B has no answer of its own and leans on Linear's own last-write.

Knowing something changed. Without a reachable server there are no webhooks, so every Machine asks on a timer or at turn boundaries exists. A hub per person (LOO-861 already names it as where webhooks arrive) turns a hundred people's polling into pushes, in any of the four worlds.

Half and half. Fifty people on Loopflow, fifty not ("Lets say literally 50%"). Every shared Project then holds both kinds of issue, so three things follow:

  • No Project is Loopflow's to take whole. L1 is left for a Project one person owns alone. On every shared Project it is L2: your slice, nothing else written.
  • Assignment in Linear is the handoff and the lock. It is the only thing both halves can see and change. A non-user hands you work by assigning it; you hand it back the same way; two Loopflow users can't both grab one issue because Linear holds one assignee.
  • Whatever teammates should know has to read well in Linear. A road beside Linear reaches only half the team. What Linear already shows covers most of it for everyone: assignee, state, the linked PR. What it doesn't show is which Machine and which step.
# priya (no Loopflow) assigns ENG-398 to you in Linear
$ lf task list
ENG-398  Email verification retries     new, from priya
$ lf task run ENG-398                     # Linear: In Progress, then PR linked. Priya sees both.

# ben (Loopflow) looks at your Task
ben$ lf task show ENG-398
jack · In Progress · PR #2011             # what Linear carries
# no Machine, no step: run state stays with jack

What this case says about A–D. None of them is ruled out, because Linear does the work between people. It favors whichever one has a clear single sender per Task (A, C, D) and makes L2 close to required.

Settled since. Run state stays with the person who runs the Task. Between people only the plan travels: title, state, assignee, PR, comments. A Graph never crosses from one person to another; work that does is a new Task.

What that does to A–D. The between-people road carries less in every world, so it can be slow and plain (Git, or Linear). Only your own Machines need the fast, complete one. In C and D, taking a Task from another person never moves a Graph, which removes the hardest handover case.
