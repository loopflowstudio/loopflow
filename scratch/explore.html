A small vocabulary: Conversation, Shell, Files, Changes, Task & workflow. Conversation and Shell use terminals in both hosts. Files and Changes use Swift views in Desktop and configured CLI tools in Rex. Tool names and example templates are proposed.

For first opening: Task’s saved layout → Wave default → builtin fallback. Reopen keeps the existing host arrangement. Editing the Wave default does not rearrange live work. The default-resolution policy is proposed; Wave-owned defaults and configurable host rendering are the requested direction.

Files carries the directory or file to open. Changes carries the exact working-tree, branch or PR diff target. Rex starts a configured program for that purpose; it does not replay the source terminal’s command history. Programs and configuration syntax are still to be chosen.

Task & workflow combines the brief, workflow position and run results. Its Rex renderer could be an LF terminal command over existing Work reads; lf task view is a proposed name, not an existing command. Editor and diff renderers should honor standard editor/pager settings and Git difftool configuration. A file-browser choice still needs a renderer setting. A configured GUI program may open outside the terminal.

What opening actually promises

Conversation faces are passive until deliberately continued or controlled. An ended Session can show retained state without starting its provider. A Task with no checkout gets its brief/start affordance. A destination on another execution Machine is not eligible for these native shells.

The sample Tasks are on this Mac. A real Wave spanning Machines needs a separate Rex session on each execution server, with visible per-Machine results. A failed remote target never falls back to a local shell. Starter layout choices apply on creation, not as an automatic reset on every open.

02 / Move

Bring the workspace here.

Inside Rex, rearrange the real tab and its splits. Between hosts or sessions, move the conversation and representable layout while keeping source-owned tools reachable.

When it is native rearrangementA tab moves within its Rex session, or a Wave session changes position. The same shells, jobs and unfinished commands move with the presentation.

When it crosses a boundaryThe destination gets its own views and optional fresh shells. Input handoff is explicit. Source shells and Files stay put; the source shows what remains.

Edit the source draft before moving. A destination failure leaves source control untouched. A whole-Wave move brings its tabs but hands off only the selected conversation; it does not seize every Task’s input.

What Rex can move today

The installed session.move_window reorders within one session. session.move reorders sessions. session.move_block can rearrange splits between windows in that same session. These methods do not migrate a live tab between sessions or Machines.

“Another Rex session” therefore uses the same honest presentation/handoff flow as Desktop → Rex. The source keeps its live shells. If exact live-tab migration is essential, that is a host capability to establish, not something to fake by restarting processes. This exploration does not change a Task’s actual Wave membership.

03 / Copy

Another workspace. The same Work.

Copy a Task’s split arrangement or a Wave’s set of tabs into “Product · review”. Keep the original open and working.

What is copiedLayout and Work references. The conversation is another view of the same LF Session, initially observing. Each placement can develop its own native layout.

What is deliberately freshAny requested native shells. Variables, jobs and unfinished shell commands are not copied. A separate conversation would be a different action entirely.

The default below copies references and reserves shell space. Select fresh shells to see the difference. Open copy again to reuse it; “another copy” would be a separate intentional operation. Take control only if you want to move the selected conversation’s input here.

A whole Wave without another planning owner

The new Rex session still refers to Product and the same Tasks. It creates no Wave, Project, Task, checkout or provider thread. A destination occurrence is identified separately so intentional copies and accidental repeated opens are distinguishable.

The copy can refer to the existing live selection or a deliberately saved set through the existing selection model. The choice of membership behavior is open. Unsupported Files/Browser content remains in its source host; saved checkout files are shared, but unsaved buffers are not copied.
