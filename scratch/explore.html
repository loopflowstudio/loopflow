Where should the
work disappear?

Choose how far the universal Machine service should go: share readings, maintain a live Work model, or also change who owns the terminal.

All three share one installed service across CLI, Desktop and native integrations. All keep optional configuration errors from stopping a valid Session launch.

Three proposed worlds. None is implemented here. Scenario controls show intended behavior, not a running LF system or benchmark.

EXISTING · THE STARTING POINT

Sharing is already partly here.

The server shares identical subscription readings. Distinct demands still own reader resources, and CLI/native observers have separate paths. The next gain must remove work across those paths.

Installed-build pilot · 16 distinct Task subscriptions ~10 quiet seconds → 59 git status children Server CPU → 80 ms, excluding children

One small pilot on fresh Tasks. It establishes recurring Git work; it is not a complete CPU baseline or a speedup claim. Earlier polling benchmarks describe a different build.

A · PROPOSED

One shared observer

Ask from anywhere. The Machine computes each demanded answer once.

CLI + Desktop + native integration ↓ same demand Machine: one reading + dependency watches ↓ exclusive snapshot lease SQLite → complete answer → independent deliveries Execution: existing LF owner → provider

A Task change invalidates the relevant readings. The service recomputes them with retained database connections. No additional observer process appears when another surface joins.

Appeal: one computation path, with today's authoritative data model.
Cost / risk: routing and observer migration are substantial. A shared dependency can still cause many full projections for different demands.

B · PROPOSED · RADICAL SUCCESS

A live Work graph

A change is computed once, even when people are looking at different views.

SQLite commit → changed entity / membership keys ↓ Machine: bounded Task / Session / Graph indexes ↓ Task view · board · Session progress · CLI answer Execution: existing LF owner → provider

The service maintains derived indexes for demanded scopes. Task facts shared by the board, Task detail and Session progress can update together. SQLite stays authoritative; service restart rebuilds the indexes.

Appeal: recurring work can follow changed entities rather than query shapes.
Cost / risk: a second derived representation must agree with SQL through moves, deletions, missed changes and restart. Memory, cold rebuilds and checkpoint revisions become central design work.

C · PROPOSED · OWNERSHIP CHANGE

Native terminal, shared brain

The terminal hosts the agent directly. LF watches and coordinates beside it.

Rex PTY → provider │ reliable exit + capture receipt (required) ↓ Machine: Session identity + A's shared observations Other hosts need equivalent capabilities, or retain LF's execution owner.

This world removes the LF attach relay from Rex's foreground and may let the host identify the provider directly. The actual program/icon result remains unverified.

Appeal: a direct native terminal experience while orchestration is shared.
Cost / risk: host-specific exit and reconnect contracts. A server cannot recover an unrelated child's exit code from its disappearance. This does not itself eliminate observer CPU.

C changes a different axis: it uses A's computation here and could combine with B. A bounded host experiment must settle feasibility before promising this experience.

A STARTING POSITION

Share first; measure the remaining work.

A is the strongest first candidate from the current findings. B earns its extra model if distinct-demand projections remain a dominant cost. C earns a host experiment if native process visibility belongs in this outcome.

None of these choices permits losing provider identity, blocking tool boundaries on LF health, or replaying a mutation with an unknown outcome. Quiet CPU and delivery latency still need whole-process measurement.
