# Loopflow Arrange — Navigation Redesign Brief

**Date:** 2026-10-16
**Author:** Jack (design conversation with Claude, distilled)
**Audience:** Claude Code sessions picking up the navigation work in `swift/`
**Status:** Design decisions mostly settled; see "Still to explore" for open questions.

This document captures a design conversation about the Swift desktop app's navigation. It is written to be handed to an agent cold. Part 1 is the brief (decisions, principles, tasks). Part 2 is an annotated transcript of the reasoning, kept because the *why* matters as much as the *what*. Part 3 is a short survey of the current code so you can orient quickly.

---

## Part 1 — The brief

### 1.1 The problem

The Swift app (`swift/LoopflowMac`) is now a good single-terminal experience: one task selected, its pane tree in the main area, libghostty surfaces. Navigation between tasks is bad. Specifically:

- There is almost only a "focused view." There is no good way to see several task sessions at once.
- The sidebar is hidden by default and organizes tasks under waves, so open tasks are buried.
- Switching feels like losing a session. (Session retention semantics are a separate task — see 1.5.)
- The top bar is a second header stacked under the macOS title bar and wastes vertical space.
- The baseline experience we want to recover is the one from Semux: a window per repo, a sidebar listing all open tasks in that repo, and the ability to jump to any of them without feeling like you lost your place.

### 1.2 Positioning

Two families of tools exist here:

1. **Generic agent terminals** — Rex, Cmux, Herder. Arbitrary workspaces, everything is a terminal, excellent pane polish, programmable, agent niceties ("is this waiting on you?"). Not agent-*model*-specific.
2. **Loopflow** — organizes the screen around the *work model* (repo → wave → project → task → session), not around terminals, sessions, or PRs.

If Loopflow has the same model as (1), there is no reason to use it. The differentiator is: **a view is `selection → layout`, and the layout is derived from the work model.** Terminals flow into and out of a view as tasks change state. Nobody else can do that because nobody else has the model.

Guiding principle (Jack's wording):

> Don't compete on pane polish; compete on knowing what the panes are. Be at least as good on the API because that's where parity is cheap. Borrow every good UX idea we can, and be relentless about performance, stability, and simplicity of design.

### 1.3 Decisions

**D1. Two layers: selection and arrangement — with a containment invariant.**
- *Selection* (work-centric): which items are shown. Inputs are only work references and queries.
- *Arrangement* (generic): where items go. Operates on the existing content-agnostic `LayoutNode` split tree, but **only on structure, never on membership.**
- **Invariant:** every pane on screen is owned by a work item, and every work item on screen is a member of a selection (a selected work or a query). No pane without an owner; no workspace without a selection. Loopflow being oriented around the work model means it *cannot not* be — so no API is offered whose use would arrange Loopflow around something arbitrary.
- These are two different APIs and two different CLI nouns. "Configure what the items are" ≠ "arrange those items." The full contract is in 1.4a.

**D2. Sidebar content is a function of the selected work type.** Same visual frame, different content:
- **Repo selected:** open tasks first (attention-sorted), then waves.
- **Wave selected:** that wave's open tasks.
- **Task selected:** no sidebar; the task's pane tree gets full width.
- Projects are not shown by default; they can appear as group labels inside a wave's task list, and may later be pinnable or a crumb level (open question).

**D3. Breadcrumbs carry hierarchy.** `repo › wave › (project) › task`, each crumb clickable to navigate up. The sidebar shows the *children of the last crumb* — so breadcrumbs and the sidebar rule are one feature, not two.

**D4. Title bar collapse.** Follow Cmux/Rex: use the macOS title bar as real estate (`titlebarAppearsTransparent` + `fullSizeContentView`). Breadcrumbs on the left after the traffic lights; contextual toolbar actions (task lifecycle, "+" menu) on the right; nothing in the middle. The existing second header row (⌘K title button + actions) goes away. When several workspace panels are open side by side, the window title bar follows the *focused* workspace; non-focused panels keep a slim header showing their tail crumb (that header already exists — it's the one with the ×).

**D5. Wave multi-task view.** Selecting a wave shows its open tasks as a grid of tiles in the main area. This is not a "dashboard"; it's just what a wave looks like when selected. (DESIGN.md's "cockpit, not a dashboard" stays true: derived layouts are in-bounds; hand-arranged monitoring walls are the anti-pattern. Update DESIGN.md to say so.)

**D6. One pane per tile.** A tile shows exactly one pane, and by default it is the task's **primary session** (`TaskSessionGroups.primary`). Not the focused pane — focus moves every time you run `git status`, which would make tiles flicker. The only override is **zoom**: if a pane inside a task is zoomed, the tile honors it until unzoomed. Shells, file browsers, flow logs, and extra sessions are reachable only by entering the task. If you ever want two panes in a tile, that's a signal the item should have been two tasks.

**D7. Auto until touched.** A container's arrangement is auto-tiled until the user (or an agent) moves something. Once touched it's pinned: new matches land in a designated *inbox* region (last leaf or a strip), departures collapse their pane. This rule also keeps agent-driven arrangement predictable.

**D8. Each work item owns exactly one layout.** A task's `SessionsWorkspace`/`MultiplexerStore` is its "selected" view. A container (wave/repo/query) stores a `LayoutNode` whose leaves are `WorkReference`s, not `PaneContent`. Tiles are *projections* of the item's own layout under D6. Two layouts per task never exist, so they can't drift. Entering a task from a tile reuses the same `GhosttySurfacePool` surface — no reattach, no flash.

**D9. Layout memory keyed by work, not by window.** Persist per `WorkWorkspaceKey` (and for containers, per `(container ref, query hash)`), stored with the work (Maestro state or an app-side store indexed by task id) so a task reopened next week on another machine comes back with its splits. Today a hidden workspace survives tab close but not app quit.

**D10. Queries.** A minimal query language seeds views and the palette: `repo:`, `wave:`, `state:` (`open`, `available`, `running`, `blocked`, `pr:open`), and enumerated `task:#412 or task:#418`. A hand-picked set is just a query with an enumerated predicate — do not build a second mechanism for "mix and match." Waves and repos *own* a default query (`wave:X state:open`); tasks *participate* in many; a query *matches* tasks. Pinning a query (Linear "Views") promotes it from palette to sidebar.

**D11. ⌘K stays, the persistent "Find Work" field goes.** ⌘K is the jump mechanism and the only place the query language has to surface in v1. ⌘K should also let you switch repos — but switching repos **opens a new window** (D12).

**D12. One window per repo, windows strongly separated.** Open Repo is the most important action in the current menu/title bar. Repo windows should feel like separate documents the way Ghostty and Cursor windows do: own title, own position in ⌘-` cycling and Mission Control, listed individually in the Window menu, distinct crumbs. `WindowGroup(id: "workspace", for: RepositoryWorkspace.self)` already gives one window per repo; the work is making that separation *felt*.
> Note for implementers: macOS allows one Dock icon per process. Ghostty and Cursor do not actually show a separate Dock icon per window; they show one icon with strongly separated windows (and Ghostty optionally one *process* per window via its `macos-...` config, which is what produces separate icons). Confirm with Jack whether "separate app icon" literally means separate Dock icons (requires a process per repo window, with real costs) or means first-class window separation (cheap, probably what's wanted).

**D13. Everything reachable from both click and CLI through the same model.** Agents must be able to manipulate Loopflow as a UI. Make `lf desktop state --json` the first command written: agents can only reliably drive a UI they can read back, and it doubles as the test oracle.

### 1.4 User experiences to build

- **Repo view:** sidebar of open tasks (attention first), then waves; main area is whatever was last open (one or more workspace panels).
- **Wave view:** sidebar is the wave's open tasks; main area is a grid of one-pane tiles, each the task's primary session, auto-tiled until touched, attention-needing tiles sorted to top-left.
- **Task view:** no sidebar; the task's own pane tree with shells, flow log, files.
- **Breadcrumbs in the title bar:** clickable; toolbar actions on the right; no second header row.
- **⌘K:** jump anywhere, type a query, pin a result to the sidebar, switch repo (new window).
- **Zoom in / out:** click a tile to enter the task; crumb up to leave; same live surface both ways.
- **Open Repo** remains one click away and opens a new, clearly separate window.

### 1.4a The `lf desktop` API contract

**Arrangement API — generic, structure only.** All of these preserve ownership and membership.
- `split --pane <target> --axis v|h` — reshape the tree around existing leaves.
- `move` / `swap` — reorder leaves within their container.
- `resize` — ratios.
- `zoom` / `unzoom` — also sets the tile face (D6).
- `hide` / `restore` — a hidden member stays a member, is listed in `state`, and is restorable. Hide never removes anything from a selection.
- `focus` — direct and spatial (`--left/--right/--up/--down`).
- `state --json` — the whole tree, including hidden members and each leaf's owner. First deliverable; test oracle.

Pane targets are content-addressable: `session:<id>`, `task:#N`, `wave:<name>`, `query:<id>`, with raw pane ids as a fallback for `.shell`/`.files`/`.flowLog` leaves inside a task.

**Selection API — work-centric; the only way membership changes.**
- `view <ref|query>` — replace the focused container's selection.
- `open <ref|query>` — open beside the focused container (today's ⌘-click).
- `query <container> "<query>"` — edit a container's query. "Add task #418 to this view" is `query here "<old> or task:#418"`. There is no `add-pane`.
- `shell` / `files` / `log --task <ref>` — open a scoped subpane inside that task's own layout. cwd is the task's worktree, never a parameter. A generic shell exists only at the repo level and is scoped to the repo root.
- `pin` / `unpin <query>` — promote a query to (or remove it from) the sidebar.
- `rename <ref> "<name>"` — rename the work item itself (task → Linear, wave → Maestro); pane titles and crumbs follow. No pane-local titles.
- `view <ref|query> --plan` — emit the derived tree as data without touching the UI (for task 4).

**Explicitly not offered.** `new-pane` with arbitrary content; `new-workspace` bound to nothing; a shell at an arbitrary cwd; placing a task into a pane (you place it into a *query*); removing a predicate-matched task from a view (hide it, or change the query).

**Nested queries.** A container's leaves are work refs *or* query refs. Dropping a query into a container is a selection op; what it expands to is derived and live. This is how "my wave grid plus a strip of everything blocked in the repo" is expressed, and it is still entirely inside the work model.

**Hide vs. remove.** Hide is arrangement (membership intact, restorable). Remove is selection (edit the query). For an enumerated query, removing `task:#418` from the predicate is the remove; for a predicate query (`wave:X state:open`), the task leaves the view when it stops matching, and until then you can only hide it.

### 1.4b The contract checked against Rex and Cmux

Rex (Superlogical) is the thought leader here; Cmux is the other reference. Both were checked from their public CLI docs on 2026-10-16.

**Rex's model.** server → session → window (a tab, holding a layout of blocks) → block (one application; currently terminals only), plus *client* (a connected viewer such as the app). Two things carry over directly:

1. **Sessions keep running without a connected viewer.** This is task 3's architecture, already decided: the app is a client, the server owns processes. Loopflow analog: Maestro is the server, task sessions are the persistent thing, Arrange is one client among several (the `lf` CLI and the Cmux/Rex skill are the others).
2. **Program Status Protocol — OSC 7501.** A program emits `ESC ] 7501 ; state=…:key=value… ESC \` with `state ∈ {idle, working, done, blocked, error, clear}`, `kind ∈ {permission, question, auth}` for blocked, optional `progress` 0–100, `app`, base64 `msg`/`title`, and child records by `id`. `working`/`blocked` clear on exit or next prompt; `done`/`error` persist. Feature detection via `OSC 7501 ; ? ST`. Rex uses it for session-picker markers and tab spinners; Lua scripts subscribe to `terminal.program_status_changed`. **Loopflow should speak this natively:** consume it from agent sessions so `attention` is reported rather than inferred from idle time, and emit it from `lf` processes so a Loopflow task renders correctly inside Rex. `SessionRecord.programStatus` and VISUAL_DESIGN's "Program Done is not Task completion" are the existing hooks.

**Rex CLI conventions to adopt:**
- Permanent IDs (never reused, short-suffix accepted) + mutable labels + positional targets, resolved in that order; ambiguity exits 3 and changes nothing. For Loopflow: work refs (`task:#412`, `wave:cadenza`) are the labels; session/pane ids are the permanent IDs.
- `--json` on everything; `inspect` at each level (`session inspect`, `block inspect`).
- `send`, `capture`, `wait`, `run --wait` (exit with the program's status).
- Env vars in every terminal (`REX_SESSION`, `REX_BLOCK`, `REX_SERVER`) → Loopflow should set `LF_TASK`, `LF_SESSION`, `LF_REPO` in every pane it spawns.
- A documented exit-status contract (0 ok, 1 fail, 2 bad args, 3 not found/ambiguous, 4 server unreachable, 130 interrupted).
- Scripting: Rex has Lua scripts + an event stream; Cmux is CLI-only. Loopflow's answer is the `lf` CLI plus an event stream (`lf desktop events --json`), not a Lua runtime.

**Cmux's model.** windows → workspaces → panes → surfaces (tabs). Sidebar is a workspace list that agents can write into (`set-status`, `set-progress`, `log`). `notify` posts a macOS notification that focuses the right workspace; `trigger-flash` draws a border on a pane needing input; `read-screen`/`send`/`send-key` for agents; `tree`/`identify`/`surface-health` diagnostics.

**Where the contract holds up.** Neither tool has a selection layer; both begin with "new session/workspace at an arbitrary cwd," which is exactly the op Loopflow declines to offer (1.4a). Rex blocks are terminals only, so Loopflow's scoped `files`/`flowLog` leaves are ahead, not behind. Rex `split` ↔ `lf desktop split`; Rex targeting is what makes content-addressable pane targets natural. Cmux `close-surface` ↔ `hide` (close would break membership). Cmux `move-workspace-to-window` has no analog: a wave belongs to one repo window.

**Where Loopflow should catch up (parity is cheap):** `wait`/`run --wait`, `capture`/`read-screen`, `send`; `notify` and `trigger-flash` driven by `attention`; `set-progress` driven by OSC 7501 `progress`; an event stream.

**The posture:** a minimal, elegant version of Rex and Cmux — the same basic shapes (server/client split, permanent ids + labels, `--json` everywhere, a status protocol, send/capture/wait, an event stream), taking only what the `lf` experience needs. On balance, **take the cheap API wins** — parity on `send`/`capture`/`wait`/`--json`/exit codes/env vars costs little and buys agent trust. Don't add a twin for every command, but the bar is low. The one thing to stay alert for is commands that point *opposite* the Loopflow way: anything that creates a pane, workspace, or shell bound to nothing, moves work across repo windows, or lets a title/label diverge from the work it names. Those stay out no matter how cheap.

**Rename is allowed, and it writes through.** `lf desktop rename <ref> "<name>"` (Rex `rename`, Cmux `rename-workspace`/`rename-tab`) renames the *work item* — a task's name updates in Linear, a wave's name in Maestro — and every pane and crumb showing it follows, because titles are derived. What's not offered is a pane-local title that leaves the work's name unchanged.

**Mapping table.**

| Rex | Cmux | Loopflow |
|---|---|---|
| server | — | Maestro |
| client | window (app) | Arrange window (one per repo) |
| session | workspace | task (persistent; survives client) |
| window (tab) | pane | a task's `LayoutNode` tree |
| block | surface | pane (`PaneContent`) |
| label / id | — | work ref / session id |
| OSC 7501 state | `set-status`, `trigger-flash`, `notify` | `programStatus` → `attention` |
| `rex ls --json`, `inspect` | `tree`, `identify` | `lf desktop state --json` |
| `send`, `capture`, `wait` | `send`, `read-screen` | to add |
| Lua events | — | `lf desktop events --json` (to add) |
| — | — | selection layer: `view`, `open`, `query`, `pin` (Loopflow only) |

### 1.5 Tasks to file

Each task is framed by the outcome it produces, not the components it touches.

**1. Enable the multitask experience.**
*Outcome:* you can see and work several tasks at once without losing your place. Open a repo and the sidebar shows every open task with attention state; open a wave and see all its agents live in one grid; enter a task and come back without anything shifting.
*Scope:* D2–D12 — sidebar-by-selection, breadcrumbs, title bar collapse, wave multi-task view, one-pane-per-tile, layout memory keyed by work, minimal query language, one-window-per-repo separation, title bar/menu action audit (1.8), DESIGN.md update.
*Done when:* the "wild success" loop in 1.10 works end to end by click.

**2. Separate the `lf desktop` API into selection vs. arrangement — and let that reshape the desktop's architecture.**
*Outcome:* an agent (or a script) can drive the same loop by CLI that a human drives by click, through one model. The selection layer answers *which* work is on screen (`open`, `view`, `add`, queries, `--plan`); the arrangement layer answers *where* (`focus/split/move/resize/hide/restore`, now targetable by content — `session:<id>`, `task:#N` — not just pane id). `lf desktop state --json` is the first deliverable and the test oracle.
*Second half of the task:* see what the split implies for the Swift code. Likely: `WorkLayout` leaves become `WorkReference`s with tiles as projections (D8); `MultiplexerStore` stays the arrangement engine; `WorkNavigation` becomes the selection engine; the CLI and the views both call the same two stores. Write up what moves where before moving it.
*Done when:* every UI gesture in task 1 has a CLI equivalent and `state --json` round-trips.

**3. Make switching between tasks seamless.**
*Outcome:* switching to a task is instant and the task you switch back to is exactly as you left it — session still running, scrollback intact, no loading state, no reset. Every spinner or dead session on switch is a bug this task owns.
*Scope:* session retention policy; interrupt vs. restart vs. reset semantics; prefetching and caching task sessions; keeping `lf` processes running when the desktop app that owned them closes (survive window close and app quit; reattach on relaunch); what "open task" means for the sidebar given all of that; surface-count limits in `GhosttySurfacePool` and whether a paused/thumbnail mode is needed for grids.
*Done when:* close the app mid-session, relaunch, and the task is where you left it; cycle through twelve open tasks and never see a load.

**4. Make it possible to arrange your Cmux / Rex / Herder multiplexer around your Loopflow work.**
*Outcome:* a Loopflow user who lives in another multiplexer gets a recognizable version of the work-centric layout there. The loopflow skill, when loaded inside Cmux, Rex or Herder, takes `lf desktop view <ref> --plan` output (a split tree with `(work ref, cwd, command, title, attention)` leaves) and materializes it through the host's pane API; Loopflow `attention` drives the host's waiting/notify/flash signal rather than idle-time heuristics; "enter the task" re-emits a different tree.
*Done when:* `lf desktop view wave:X` inside Cmux produces the same one-pane-per-task grid the desktop app would, with the waiting tasks flagged.

### 1.6 Principles for the tradeoffs

- Organize around the work model, not around terminals. A view is `selection → layout`; the layout is derived.
- One pane per tile. If you want two, it's two tasks.
- Auto until touched. Respect hand arrangement; newcomers land in an inbox; departures collapse.
- Layout memory keyed by work, not window.
- Sidebar is the working set; palette is the long tail; breadcrumbs carry hierarchy so the sidebar doesn't have to.
- Don't compete on pane polish; compete on knowing what the panes are. Be at least as good on the API. Borrow every good UX idea; be relentless about performance, stability, and simplicity.
- Everything reachable from both click and CLI through the same model.

### 1.7 What to borrow

**From Notion:** user-pinned hierarchy in the sidebar (Favorites) rather than data-model hierarchy; clickable breadcrumbs in the title bar; lazy tree expansion that remembers.

**From Figma:** a constant panel *frame* with contextual panel *content* keyed to selection (pages vs. layers vs. components); right-side actions contextual to the selected thing.

**From Linear:** sparse sidebar (Inbox, My Issues, teams); saved filters ("Views") promoted into the sidebar — literally pinned queries.

**From Ableton:** the Session view — a grid where every cell is a live running thing with a visible state (launched / queued / stopped). This is the closest analog to a wave view of live agent sessions. Glanceable state across many parallel things; click to enter one.

**From Photoshop (negative lesson):** fully user-arranged panels are powerful for veterans and hostile to everyone else; Adobe spent years adding "Essentials" presets to paper over it. Don't start there — hence D7.

**From Rex and Cmux:** the title bar as real estate; a complete, scriptable arrangement API with readable state; first-class "waiting on you" signaling; treating agents as users of the UI.

**From Slack / Arc:** sidebar holds pinned/active items with attention state inline; ⌘K for the long tail.

**From Ghostty / Cursor:** windows as strongly separated first-class documents (D12).

### 1.8 Menu / title bar action audit (to do as part of task 1)

Jack asked for a comparison of the actions Rex and Cmux expose in their menu/title bars (and Linear/Asana as non-terminal references) to decide what Loopflow's title bar and app menus should actually contain. What we know so far:

**Cmux** (from its CLI reference, which mirrors the UI): hierarchy is *windows → workspaces → panes → surfaces (tabs)*. Exposed actions: new/close/focus window; new/select/close/rename/reorder workspace, move workspace to window; new pane, focus pane, resize pane; new split, new surface, close surface, move/reorder surface, rename tab; notifications (`notify`, list/clear); sidebar metadata (`set-status`, `set-progress`, `log`); `trigger-flash` (blue border on a pane needing input); `read-screen`/`send` for agents; `tree`/`identify` diagnostics. The sidebar is a vertical list of workspaces; agents can write status rows (e.g. git branch) and progress bars into it. `cmux notify` posts a macOS notification that focuses the right workspace when clicked. No "open repo/folder" concept — a workspace is just a cwd.

**Rex** (from its CLI docs; see 1.4b for the full model): sessions, windows (tabs), blocks; a session picker that marks sessions with done/blocked programs; tab headers showing spinners and blocked symbols for unfocused tabs; a command palette opened through the client; `split`, `send`, `capture`, `wait`, `ls --json`, `inspect`; custom actions, key sequences and key modes; Lua scripts and events. **Still to do:** open the app and inventory the actual menu bar and title bar contents, since the docs describe the CLI rather than the chrome.

**Linear:** title/header shows breadcrumbs (team › project › issue) and a small set of contextual actions; everything else is ⌘K. **Asana:** header is the object's name plus a few contextual actions (assignee, due date, share); navigation is entirely sidebar + search.

**Current Loopflow** top bar: ⌘K title button (shows current Work), task lifecycle actions, "+" menu (shell / Files / Flow processes). App menus include a "Go" menu with "Move to Repo" and "Open Repo…". Separate windows: Portfolio (⌘0), Telemetry (⌘1), Open Work, Appearance, About.

**Proposed Loopflow title bar (D4):**
- Left: `repo › wave › task` crumbs (clicking the last crumb opens ⌘K).
- Right: lifecycle actions for the selected work type; "+" menu; **Open Repo** stays one click away (or lives in ⌘K + the File menu — decide during the audit).
- Middle: empty. Status belongs on tiles and sidebar rows, not in the title bar.

**App menu candidates** (decide during the audit): File › Open Repo…, New Window for Repo…; Go › crumbs as menu items, Back/Forward (⌘[ ⌘]), Find Work (⌘K); View › Toggle Sidebar, Zoom Pane, Split Right/Down; Window › one entry per repo window.

### 1.10 Wild success

You open a repo window and the sidebar already tells you which of twelve running tasks need you. You click a wave and see all of its agents working, live, in one glance, with the ones waiting on you at the top-left. You click one, do the thing, hit the crumb, and you're back in the grid with nothing lost. An agent can do that same loop from the CLI, and someone running Rex gets a recognizable version of it from the skill. Nobody describes Loopflow as a terminal multiplexer; they describe it as the place where you see your work.

### 2.1 On the two approaches and what already exists

[Jack: two approaches — generic terminal workspaces (Rex/Cmux/Herder) vs. organizing around the work model; wants a multi-terminal "dashboard" view; misses the Semux sidebar.]

> Good news first: the pieces you need already exist. `WorkLayout` is an outer split tree whose leaves are workspaces (`WorkWorkspaceKey` = repo / wave / task), and each workspace owns a `MultiplexerStore` whose leaves are `PaneContent` (`.session(id)`, `.shell`, `.flowLog`, `.files`). `GhosttySurfacePool` already keeps one live surface per `TerminalIdentity` across navigation. So the dashboard isn't a new rendering problem — it's a new *kind of workspace* whose panes are derived rather than hand-placed.
>
> That's also the answer to your "two approaches" worry. Rex/Cmux/Herder: the user arranges panes, the panes hold whatever. Loopflow: a view is `query → set of sessions → layout`, and the layout is computed from the work model. Terminals flow into and out of the grid as tasks change state. Nobody else can do that because nobody else has the model. You still get all the pane plumbing (split, zoom, ⌘-click beside) for free underneath.

[Jack: wants mix-and-match of arbitrary task sessions, a query language, waves/repos owning default queries, a sidebar that emphasizes open tasks.]

> **On mix-and-match vs. query.** Don't build two mechanisms. An explicit hand-picked set is just a query with an enumerated predicate (`task:#412 or task:#418`), and "add this task to my view" is appending to that predicate. One saved-query type, with a hand-picked list as a degenerate case.
>
> **On which waves "own/match/participate."** A wave *owns* a default query (`wave:X state:open`), a task *participates* in any number of queries, and a query *matches* tasks. Repos own `repo:Y state:open`. A query view is then a pane container seeded by its owner's default, editable in place. The wave's chat session is just a pinned pane in that container, not a special case.
>
> **Layout for the query view** is the real design work. Options worth prototyping: (a) auto-tiled grid, each cell a live terminal with status chrome, click/⌘⇧Return zooms using your existing zoom; (b) one focused terminal plus a strip of mini terminals; (c) focused terminal plus a list of status rows, terminals only on demand. I'd prototype (a) first because it's the thing that looks like nothing else, then measure whether N live Ghostty surfaces at once is fine or whether the pool needs a "thumbnail/paused" mode. ... DESIGN.md currently says "cockpit, not a dashboard" and lists dashboards as an anti-pattern, so you'll want to update it to say *derived* layouts are fine and *hand-arranged monitoring walls* are the anti-pattern.

### 2.2 On sidebar-by-selection and the two APIs

[Jack: not really dashboards — a multi-task view for waves. Repo sidebar = open tasks then waves; wave sidebar = its open tasks; task = no sidebar. Same visual structure, different content. Agents must be able to manipulate Loopflow as a UI. Two "do whatever you want" levels: configure items vs. arrange layout — maybe two APIs.]

> That sidebar rule is cleaner than queries-everywhere, and it maps directly onto what's already there: `WorkNavigation.selection` is a `WorkReference`, so the sidebar just becomes a function of selection kind. ... The persistent "Find Work" field can go; ⌘K stays as the jump, and it's the only place the query language has to surface for v1.
>
> Your two-API split is right, and I'd name the layers so they don't bleed into each other:
> - **Selection** (work-centric): *which* items. `lf desktop open task:#412`, `lf desktop view wave:cadenza`, `lf desktop add task:#418`.
> - **Arrangement** (generic): *where* items go. This is your existing `lf desktop focus/split/move/resize/hide/restore --pane` set, and it can be exactly as generic as Cmux's, because it's operating on `LayoutNode`, which is already a content-agnostic split tree.
>
> The one thing that would make the arrangement layer better than theirs rather than merely equal: leaves addressable by content, not just pane id. An agent should be able to say "split task 412's primary session right, put 418's session there" without first listing panes to find ids.
>
> "Dashboard = query + arrangement" then falls out, but it has one hard semantic you'll want to decide up front: what happens to a hand-arranged layout when the selection changes under it. ... My suggestion: an arrangement is auto until touched; once touched it's pinned, new matches land in a designated "inbox" region (last leaf, or a strip), departures collapse. That rule is also what makes it safe for agents to arrange things.
>
> Since every operation goes through the same model whether it came from a click or `lf desktop`, make `lf desktop state --json` the first command you write. Agents can only reliably manipulate a UI they can read back, and it doubles as the test oracle for your frame/grid checks.

### 2.3 On breadcrumbs and the title bar

[Jack (voice): bring back breadcrumbs repo → wave → project → task; title bar takes too much space; look at Cmux using the title bar for the repo name; maybe crumbs there.]

> Breadcrumbs actually unify the sidebar rule: the crumb trail is the selection path (repo › wave › project › task), and the sidebar shows the children of the last crumb. ... Clicking a crumb navigates up, which also gives you the back-out gesture the current ⌘[ history only half provides.
>
> Cmux's move is to collapse into the system title bar with `titlebarAppearsTransparent` and `fullSizeContentView`, then draw its own content there. Proposed split: **Left** crumbs, each clickable; clicking the last crumb, or ⌘K, opens the palette; the crumbs *are* the title. **Right:** lifecycle actions and the "+" menu as toolbar items. **Nothing in the middle.** Resist putting status there; status belongs on the panes and the sidebar rows.
>
> One wrinkle: a window can have several workspace panels open side by side. The window title bar can only show one trail, so it should follow the *focused* workspace, and each non-focused panel keeps a slim header with its tail crumb.
>
> The only missing piece is project as a navigable level; it's currently a planning snapshot inside a wave rather than a `WorkDestination` case.

### 2.4 On layout memory

[Jack: how is layout memory associated with the work model? Two views per work item — selected, and as a tile. Don't want to limit the main area to one thing.]

> **Each work item owns exactly one layout.** That's already true: `SessionsWorkspaceRegistry` keeps one `SessionsWorkspace` with its own `MultiplexerStore` per `WorkWorkspaceKey`.
>
> **A container doesn't store panes, it stores references.** A wave/repo/query view's layout is a `LayoutNode` whose leaves are `WorkReference`s, not `PaneContent`. When a task is rendered as a tile inside a container, it shows a *projection* of its own layout under a compact rendering rule. So the tile view is derived, not a second stored layout, and the two can't drift. Zooming from the tile into the task is just selecting it, and because `GhosttySurfacePool` keys surfaces by `TerminalIdentity`, it's the same live surface.
>
> **Persistence keyed by work, not window.** ... Container arrangements get keyed by `(container ref, query hash)` so the auto layout and a hand-touched one for the same wave are distinct records, and a changed query starts fresh rather than inheriting stale pane positions.

[Jack: in a command-center view, maybe only ever show the main pane; click into the item for shells and files.]

> Yes — make that the rule: **a tile is one pane, and by default it's the task's primary session.** Drop "focused" from the fallback: focus moves every time you work in a task, so a tile that follows focus would flip to a shell the moment you ran `git status`. The only override worth keeping is zoom. If you zoom a pane inside a task, you've made an explicit "this is the face of this task" gesture, and the tile honors it until you unzoom. ... If you later find you want two panes per tile, that's a signal the item should have been two tasks.

### 2.5 On the Cmux/Rex skill

[Jack: loopflow.md loaded in Cmux or Rex should use their APIs to simulate the work-centric layout. Separate task.]

> The selection/arrangement split is what makes it tractable. Cmux and Rex both have an arrangement API. What they don't have is the selection layer, and that's the part `lf` can compute without needing the desktop app at all. So: `lf desktop view wave:X --plan` emits the derived layout as data — a split tree whose leaves are `(work ref, cwd, command, title, attention)` — and the loopflow skill, when it detects it's running under Cmux or Rex, translates that plan into their pane calls. The one-pane-per-tile rule makes the translation nearly lossless. ... Worth checking the two APIs for how they expose "needs attention" so the skill can set it from Loopflow's `attention` field rather than letting them infer it from idle time.

### 2.6 On sidebars vs. search dropdowns

> A sidebar gives you *place*. ... Cost: it eats width permanently, it has to pick one hierarchy and commit, and it scales badly past a couple hundred items. A search dropdown (⌘K) gives you *reach*. ... Cost: you have to already know the name of what you want, it shows nothing while closed so you lose ambient awareness, and every trip has the same price. Most mature tools run both, with a specific division of labor: the sidebar holds the *current working set* and the palette handles *everything else*.
>
> Synthesis for Loopflow: the sidebar should be a short working set (Available, open tasks, pinned waves/queries) with attention state inline, structured by the crumb you're standing in, like Figma's panel. ⌘K is for anything not in that set. Breadcrumbs carry the hierarchy so the sidebar doesn't have to. And like Linear, pinning a query is how something graduates from palette to sidebar. The grid of live tiles is your Ableton session view — the differentiated part — and should look like it.

## Proposed architecture

Add Desktop-local `WorkDestination`: repository dashboard, Wave dashboard keyed by Wave, or single `WorkWorkspaceKey`. The registry owns the active destination, one saved repo `WorkLayout` per repository and remembered focus per dashboard. Active layout/visible keys are derived: repo uses saved composition, single Work uses one leaf, Wave uses its retained session beside a Task browser derived from the fixed query. Retained workspaces remain keyed once. WorkNavigation retains visit history and references the selected workspace presentation as today; it stores no second active destination.

Split WorkModel's destination navigation from focus operations. Focusing a wrapper/pane changes the existing Work selection and selected Session without changing destination or composition. Visiting single Work never edits repo composition. Back/Forward records destination and focus, including Wave conversation ↔ dashboard. Keep `WorkLayout` for repo split geometry and `MultiplexerStore` for inner panes. Task/repository canonicalization rewrites saved layouts, focus and history together. Duplicate additions focus the existing key. Only the active destination mounts content; inactive destinations retain references, not view trees. (and its Needs you appearance). Expansion is presentation state, independent of
Work selection. A task-count control could fold a branch without chevrons or
navigation. This proposal is not approved for implementation. The alternative
is Figma's stacked sections: a persistent Wave index above the scoped Task list.
Tradeoff: inline branches consume vertical space; stacked sections separate
Tasks spatially from their Wave. No return to adjacent sidebar columns is proposed.

Repository entry shows Needs you and a single Wave list. A Wave opens its
conversation and replaces that list with Tasks. Repo / Wave breadcrumbs return
to their conversations; selecting a Task keeps its siblings visible. Search hides
nonmatches without navigating. Each Wave retains its Task-list scroll position.

Burgundy fill and cream text mark selected Work, with no edge stripe. Ancestors
are context. Needs you mirrors the same selection; it also recognizes the exact

visible in the three-row queue. These are multiple representations of one
selection, not independent selected values.

Command-click opens Work beside the focused workspace. Ordinary click replaces
the focused slot, or focuses Work already visible. Close hides a workspace while
retaining its panes, surfaces and file drafts. Each inner split stays within its
Work. Narrow outer layouts reflow vertically. Context headers appear only with
multiple workspaces or a collapsed sidebar. Primary single-workspace views have
no middle breadcrumb. Secondary Sessions retain rename/bind actions.

Sidebar collapse belongs to the sidebar; the edge control restores it at its
remembered width. Drag adjusts width within 260–600pt while reserving content
space. Command-[ / ] traverse history without visible Back/Forward buttons.

## Data structures and key functions

`WorkWorkspaceKey` identifies whole Work. `WorkLayout` is a binary split tree
whose leaves hold these keys. `SessionsWorkspaceRegistry.layout` replaces flat
placement; its `openWork` is derived. Existing `selectedWork` and WorkNavigation
remain connected through WorkModel's selection path, not another selection owner.

Each `SessionsWorkspace` retains its `MultiplexerStore`, pane focus, presentation,
documents and pooled surfaces. `SplitDivider` shares only divider geometry and
an update closure; it cannot exchange Work keys and pane IDs.

- `select(reference, besideFocused:)` changes placement and one Work selection.
- `hideWorkspace(key)` removes placement, retains clients, and focuses surviving Work.
- `WorkLayout.replacing/removing/resizing` changes only outer geometry.
- `split(pane, axis:)` remains inside its owning workspace.
- `resizeSidebar(width, availableWidth:)` changes navigation geometry only.
- `isSelected(reference/attention)` reconciles planning/runtime aliases and exact Sessions.

## Current system / Delete — do not maintain

Removed persistent adjacent Wave/Task columns, remembered Wave-click destinations,
`selectWaveContext`, `navigatorWaveID`, `waveDestinations`, and their exclusive
column/restore expectations. Wave clicks now open Wave conversations.

Removed `WorkBreadcrumbBar`, its visible Back/collapse controls, and always-on
ancestor presentation. `WorkSessionToolbar` preserves secondary Session actions;
Task Details, Files, Flow logs, shell creation and zoom restoration belong to the
workspace. Fixed 430pt width is replaced by the resizable sidebar.

The registry's stored flat `openWork` is replaced by `WorkLayout`; terminal pool,
location ownership, retained documents, inspection and exact Session opening
survive. Desktop text inspection distinguishes visible unfocused Work from hidden
Work. No database migration or compatibility path. Review caught and fixed stale inactive Workflow controls, missing selection on attention entries, and prepared-checkout location precedence.

## Constraints / Forbidden outcomes

One Work selection, even when mirrored in the queue. No ancestor highlighting,
duplicate surface mounts, terminal panes shared between Work layouts, draft loss
on hide, navigation launching a Flow, or search changing selection.

The existing Work reader watches Workflow detail for the focused Task. Inactive
workspaces keep live panes and expose a focus action for Workflow controls rather
than presenting stale actions. Task controls can scroll horizontally in narrow
workspaces. Outer layout and sidebar width persist within the window, not across
app launches. Mixed Repo/Wave/Task placement uses the same layout; no extra mode.
