## Concept review — October 17 (proposed, not accepted)

Jack Heart requested concept-review after narrowing the diff to built-in
repo/Wave views. Existing accepted A/B/A, cross-repo Find Work and scope exclusions
remain. The consequential mismatch is visibility versus execution: the current
implementation leaves a running Task's primary Session as a placeholder unless
its workspace/surface has already been opened here. A new window full of running
Tasks can therefore look empty, defeating the see-several-Sessions experience.

Proposed usage: “Open a Wave to see its existing primary Sessions immediately.
Enter a Task to use its full workspace; return to the same grid. Viewing work
never starts an agent. If a Session cannot be viewed, its tile explains why and
offers recovery without changing other tiles. A Task with no Session shows its
brief.” This proposes passive viewing of existing Sessions, not creating or
resuming execution or taking another client's input ownership.

Layer consequence: shared queries own membership; retained Task workspaces own
panes and drafts; lifecycle owns passive attachment and exact terminal identity.
Selecting a Wave requests views of existing Sessions; entering a Task changes
presentation. Starting/resuming remains an explicit execution action. No desktop
CLI API or Dashboard editor is implied. Lost viewing connection retains the tile,
arrangement and drafts; recovery reconnects to the same Session without relaunch.

Unresolved product choice: should a newly opened Wave display all existing primary
Sessions, or only Sessions already opened in this window? Counterexample to the
former: another client owns exclusive input and the transport cannot observe;
the grid must explain that state, never steal the client. Next proof: a fresh
window with several already-running Tasks, an unavailable/remote Session and one
Task with no Session, followed by enter/return and viewer disconnect/reconnect.
No implementation change or execution restart is authorized by this proposal.
