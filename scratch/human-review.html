LOO-986: a pane's conversation starts from anywhere, says why it failed, and stays on its harness

PR #1992, branch at 0063fa68c0, base 2750c9e0fb, 2026-11-19. 28 files, +1026 −210. Written with nobody present; section 6 holds the questions that are still yours.

1. What changes for people

  • A provider starts from wherever lf is started. Desktop, the launchd server, a Rex or tmux pane, an SSH session: every lf appends seven tool directories to its own PATH first thing in main. No entry point carries its own repair any more.
  • A failed lf open says why. The caller's --json reason and the text line hold lf's own error ("'claude' is not installed. …; retry the same command"). No rex capture. The pane still shows the error and waits for Enter.
  • Replaying a pane's command never moves the conversation. The command names a harness only when the caller passed -a.
  • A cost: a pane no longer gets the caller's PATH, so a tool reachable only through shell rc (Pi under nvm on this Machine) reads "not installed" in a launchd-started pane.
  • Also in the diff: lf open --host tmux works on tmux 3.7 (it opened nothing there, on main too), and ~/.opencode/bin is a tool directory.

// rust/loopflow-execution/src/transport.rs
fn answer_open(answer: &str) {
    let Some(path) = OPEN_RECEIPT.lock().expect("open receipt lock poisoned").take() else { return; };
    let temporary = path.with_extension(std::process::id().to_string());
    if std::fs::write(&temporary, answer).is_ok() {
        // Fails when another process answered first.
        let _ = std::fs::hard_link(&temporary, &path);
        let _ = std::fs::remove_file(&temporary);
    }
}

No published build holds this branch, and the installed lf is main's. Build the branch and use it by absolute path, against a private home so the real store is untouched:

cd /Users/jack/src/loopflow.loo-986-a-pane-s
cargo build -p loopflow --bin lf
export LF_HOME=/tmp/lf-986 LF=$PWD/target/debug/lf     # then, inside a tmux pane:

# 1. launchd's PATH starts the provider (USER is needed for Claude's Keychain login)
env -i HOME=$HOME USER=$USER TERM=xterm-256color LF_HOME=$LF_HOME \
  PATH=/usr/bin:/bin:/usr/sbin:/sbin $LF session resume <session>

# 2. a failed open says why (Pi is only under nvm here)
$LF open --task <ID> --tab --host tmux --json -a pi

# 3. the pane command names no harness
$LF open --session <id> --tab --host tmux --json     # then: tmux list-panes -a -F '#{pane_start_command}'

6. Questions, still yours

  1. Tools behind shell rc. Pi under nvm reads "not installed" in a launchd-started pane.
    1. Accept; add directories as they are missed (built).
    2. Carry the caller's PATH when the caller is a person.
    3. Run the pane command through the login shell.
    4. Keep (a) but say "lf did not find 'pi' on its PATH".
  2. usable.
    1. Stays "the provider was started" (built).
    2. Becomes "the provider takes input", with its last words as the reason; its own Task.
  3. A failed lf open -a <harness>.
    1. Leaves the conversation moved (built).
    2. Records the move only once the harness starts; its own Task.
  4. Sole installed harness. With no agent preference and Claude missing, an open started OpenCode from /opt/homebrew/bin and answered usable. The rule is documented; the tool directories now make it apply under every PATH.
    1. Fine (built).
    2. A harness found only in a tool directory should not be picked silently.
  5. Failed panes pile up. Each failed open leaves a pane waiting for Enter; an agent retrying four times left four.
    1. Leave it; the pane is for a person (built).
    2. Close the pane when the caller is an agent and the reason reached the receipt.
  6. Append vs prepend on a remote. remote_path() now appends.
    1. Append everywhere (built).
    2. Keep ~/.cargo/bin first on remotes so a dev lf wins.
