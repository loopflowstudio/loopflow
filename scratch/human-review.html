LOO-979 · PR #1977 · branch at 022a318085 · written 2026-11-18 with nobody present. Rust and docs are unchanged since QA ran at edd8bcb026; the two commits after it touch only scratch/ and .lf/qa/.

1. What changes for the people who use it

Nothing they can read: every Session list, card and Task row says what it said before. What changes is what lf server run spends. The step that runs twice before every Session read went from about 5.5 ms to about 50 µs on this Machine's store (22,643 Sessions, 37 running agents). That step was the largest share of the server's busy time in the 2026-11-18 sample.

The deadline statement, before and after:

-- main
SELECT DISTINCT observed_at + ?1 FROM session_activity
WHERE observed_at + ?1 > ?2 ORDER BY 1

-- branch (all Sessions)
SELECT DISTINCT act.observed_at + ?2
FROM agent_sessions s INDEXED BY agent_sessions_unended_agent
JOIN session_activity act
  ON act.session_id=s.id AND s.completed_at IS NULL
 AND act.agent_process_id IS s.agent_process_id
 AND s.agent_ended_at IS NULL
WHERE ?1 IS NULL AND s.agent_process_id IS NOT NULL
  AND act.observed_at > ?3 - ?2 ORDER BY 1

The ON clause is current_agent_activity("s"), the same text available_sql now opens with:

fn current_agent_activity(session: &str) -> String {
    format!(
        "act.session_id={session}.id AND {session}.completed_at IS NULL
            AND act.agent_process_id IS {session}.agent_process_id
            AND {session}.agent_ended_at IS NULL"
    )
}

And an ended agent is Dead without a trip through the OS evidence map:

// An agent whose end is recorded is dead by its row; the OS is asked about the rest.

2. Product concepts beside code concepts

From scratch/concept-review.html, written against the code as it stands.

What a person knowsWhat the code hasMatch
A Session's agent is running, dead or not known. ProcessIdentityEvidence. Dead from agent_ended_at in read_summary; otherwise the evidence map, which now holds only what the OS was asked. Was no on main: 735 of 772 identities were ended agents carried out of SQL and back, in a field named completed_at that held agent_ended_at. yes
A quiet Session becomes available after two minutes. available_sql and the deadline statement share one guard and AVAILABILITY_QUIET_SECONDS. The revision trigger store_revision_session_activity_update writes 120 as its own literal. no
A Session's Graph is running, finished or failed. graph_runs: every unended run for the list, the Session's own run for one read. yes
The list is correct at the moment it is drawn. pin / is_current: rerun the inputs, compare, restart. Unchanged, now about 50 µs a rerun. yes
Asking about one Session and asking about all give the same answer. session_summary and session_summaries, one route to Dead for both. yes

The biggest mismatch: the two-minute rule lives in two places that can disagree, the Rust constant and a literal in a merged migration's trigger. One source takes a new migration that rebuilds store_revision_session_activity_update; a trigger cannot read a Rust constant, so "one source" would mean a test that compares the trigger's SQL with the constant, or generating the trigger. Not in this PR, which adds no migration.

3. How to try it

The plan, on a backup of your store. sqlite3 only: see the note in section 4 for why no lf command should open the copy.

sqlite3 "file:$HOME/.lf/loopflow.db?mode=ro" ".backup /tmp/lf-copy.db"
sqlite3 /tmp/lf-copy.db "EXPLAIN QUERY PLAN
  SELECT DISTINCT act.observed_at + 120 FROM agent_sessions s INDEXED BY agent_sessions_unended_agent
  JOIN session_activity act ON act.session_id=s.id AND s.completed_at IS NULL
    AND act.agent_process_id IS s.agent_process_id AND s.agent_ended_at IS NULL
  WHERE s.agent_process_id IS NOT NULL AND act.observed_at > strftime('%s','now') - 120 ORDER BY 1"

Expect SEARCH s USING INDEX agent_sessions_unended_agent and SEARCH act USING INDEX sqlite_autoindex_session_activity_1, no SCAN session_activity.

5. Choices made on your behalf

ChosenPassed over
Drive the read from agent_sessions_unended_agent and reach session_activity by primary key. No migration. The Task brief's CREATE INDEX … ON session_activity(observed_at): it serves only the all-Sessions read and is rewritten on every activity reading under the write lock. Moving the bound across without an index left the same scan, 2,578 µs.
Narrow identities and Graph runs too. Fixing only the deadline scan, which was 40% of the time.
The single-Session read drops ended agents as well; SessionProcessIdentity.completed_at is deleted. The kickoff plan's narrower change, which left two routes to Dead.
The all-Sessions read carries every unended Graph run (5 or 6 here). Only runs whose step captured an open Session's input, which meant probing every open Session.
INDEXED BY agent_sessions_unended_agent. If the index is renamed the statement fails to prepare. Letting the planner choose; completed_at IS NULL in the guard lets it pick open_sessions.
The all-read's identities ignore completed_at: a completed Session whose agent has not ended is still asked about. Keeping completed_at IS NULL in one read and not the other.
pin still reruns the inputs. Comparing store_revisions, which needs store_revision_agent_sessions_update to fire on every identity write.
graph_processes stays out of GROWING. Measuring its indexes and auditing every traced Graph statement here.
One plan test for the inputs, the existing one in session_projection.rs. A second trace in store::query_plans::tests::, which the Task brief names; compress deleted it as a duplicate.
The redundant session.completed_at.is_none() in selections.rs stays. Deleting it here; it is outside the diff.
