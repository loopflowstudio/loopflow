# Design Review: jack-heart.remote.20260217_1234

## What was implemented

Three areas of work consolidated into one branch:

1. **Fork execution hardening (Phase 01D).** Fork branches always run all, then synthesize. Removed the `select` modes (first-success, random). Unified fork semantics between `lf flow` (CLI) and `lfd` (daemon). Added scheduler slot guards with RAII cleanup, orphan-fork recovery on daemon restart, and explicit agent timeouts.

2. **Step rename: `plan/review` → `plan/research`, new `interactive/review`.** The old `review` step was autonomous research. The new `interactive/review` walks a human through the diff in a structured conversation (orient → demo → model → simplify → contentious → learnings). All flow YAMLs updated.

3. **Docker executor improvements.** Adapted to bollard 0.19 API. Added Docker-specific CI (nightly e2e workflow, `docker_` test filter). Fork execution is explicitly unsupported in Docker — returns a clear error instead of silently misbehaving. Tracked as `01e-docker-fork-parity.md`.

Supporting changes: build.rs for embedding built-in steps/flows at compile time, wave roadmap updates, ChatState memory block sorting in Swift, and dev script improvements.

## Key choices

**Fork always runs all branches.** The `select` modes (first-success, random) added complexity without clear user value. Removing them simplifies the `FlowItem::Fork` model to a single behavior: run all branches in parallel, then synthesize. The fork manifest captures per-branch exit codes so failures are visible.

**Fork unsupported in Docker.** Rather than building worktree-in-container parallelism now, the branch returns `anyhow!("fork execution is not supported with Docker executor")` and tracks the work in a dedicated wave item (`01e-docker-fork-parity.md`). This avoids a large design surface for a feature that isn't needed until remote dogfooding.

**Scheduler slot guard (RAII).** `SchedulerSlotGuard` auto-releases the semaphore permit on drop, preventing leaked slots across panics and early returns. The guard supports re-entrant acquisition for the same `run_id` (idempotent) with `release_on_drop: false` for the second guard.

**Compile-time step/flow embedding via `build.rs`.** Built-in prompts and flows are now embedded at compile time using `include_str!` generated by `build.rs`, replacing runtime file discovery. This makes the binary self-contained.

**Interactive review arc reordered.** The design doc specifies orient → core model → simplify → contentious → demo → learnings. The shipped prompt reorders to orient → demo → core model → simplify → contentious → learnings, putting demo earlier so the human can poke at the change before discussing the model. Reasonable call.

## How it fits together

```
engine/fork.rs      — pure functions: plan execution, worktree paths, manifest I/O
engine/flow.rs      — FlowItem::Fork parsed, expanded into ConcreteItem::Fork
lf/commands/flow.rs — CLI fork: spawns parallel lf processes, relays logs
lfd/executor/wave/  — daemon fork: spawns via AgentExecutor, manages lifecycle
lfd/scheduler.rs    — slot guards, session tracking
```

The engine layer (`fork.rs`, `flow.rs`) is shared between CLI and daemon. The execution split (CLI spawns processes, daemon uses `AgentExecutor` trait) keeps the daemon's Docker/local abstraction clean.

## Risks and bottlenecks

**`register_session` / `unregister_session` are dead code.** They're `#[allow(dead_code)]` with "reserved for interactive session management." `has_active_session` is used, but the registration pair is not. If interactive sessions never materialize, this is dead weight. Low risk — it's two trivial methods.

**`plan_fork_execution` returns `Result<_, String>`.** Both callers immediately wrap the `String` into `anyhow::Error`. A `CoreError` variant would be more consistent, but the current approach works and the error messages are clear.

**Long `execute` method in `wave/mod.rs`.** The `FlowAction::Complete` match arm is ~100 lines handling PR creation, branch advancement, queue reconciliation, and status updates. It's readable today but will be the first place that buckles under additional post-run logic.

## What's not included

- Docker fork parity (tracked in `01e-docker-fork-parity.md`)
- Phase 05 remote connection (next wave item)
- Fork result diffing or comparison UI
- Interactive session management (the `register_session` stubs exist but aren't wired)
