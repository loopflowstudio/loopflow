# Summary: Wave Area Summaries

## What was implemented

Auto-generated area summaries for waves. When a wave runs, an LLM summarizes the wave's area files before each step, caching the result in the DB. Summaries are injected into step context so agents have a dense overview of the codebase they're working in.

### Components added

1. **`Summary` type** (`lfd/types/summary.rs`) — `id`, `wave_id`, `content`, `source_hash`, `token_budget`, `model`, `created_at`
2. **DB migration** — `summaries` table with unique index on `wave_id` (Postgres `004_summaries.sql`, SQLite inline schema)
3. **Store methods** — `get_summary` / `upsert_summary` on both Postgres and SQLite stores
4. **Source hashing** — `hash_areas()` in `engine/git.rs` using `git ls-tree -r HEAD -- <areas> | SHA-256`
5. **`ensure_summary_fresh()`** — called before each step in `execute()`, compares stored hash to current, regenerates if stale
6. **`run_internal_summarize()`** — launches a headless agent with the builtin `ops/summarize` prompt, reads `.lf/summary.md` back, stores result
7. **Context injection** — `build_step_prompt` accepts optional `(store, wave_id)` and pushes summary into `components.summaries`
8. **Proactive refresh trigger** — `spawn_summary_refresh` listens for `WorktreeUpdated` events, debounces per wave (60s), refreshes summaries for idle waves
9. **Summarize prompt update** — added file-write instruction to `ops/summarize.md`
10. **Tests** — Summary CRUD in store suite, `hash_areas` unit tests

## Key choices

**Summary as internal step, not inline generation.** Summaries are generated by running the same agent machinery as normal steps. This reuses all existing agent infrastructure (streaming, output capture, agent tracking) without building a separate LLM call path. Trade-off: heavier than a direct API call, but simpler and consistent.

**`git ls-tree` for staleness detection.** Fast (reads from git index, no file I/O), deterministic, and tracks exactly what's committed. Uncommitted changes don't trigger re-summarization, which is correct — the summary should match what the agent sees via git.

**Summary injection at `build_step_prompt` level, not `gather_context`.** Keeps `gather_context` pure (filesystem-only), which matters because `lf` CLI uses it without a DB. The executor injects the summary after gathering context.

**One summary per wave, not per area.** Simpler. A wave's areas are summarized together into one document. If a wave has multiple areas, they're concatenated in the prompt.

**Proactive + safety net pattern.** The `WorktreeUpdated` event trigger handles most cases. The `ensure_summary_fresh()` call before each step is the safety net. Both are non-blocking failures — if summarization fails, the step runs without a summary.

## How it fits together

```
execute() loop
  ├── ensure_summary_fresh(wave, run)
  │     ├── hash_areas() → compare to stored hash
  │     └── run_internal_summarize() → agent writes .lf/summary.md → upsert_summary()
  └── run_step()
        └── build_step_prompt(..., summary_source)
              └── store.get_summary() → components.summaries
```

The `spawn_summary_refresh` trigger runs alongside the executor, catching `WorktreeUpdated` events for idle waves.

## Risks and bottlenecks

- **Summarize step latency.** Each summary generation launches a full agent. For the first step of a wave, this adds agent startup + LLM generation time. Mitigated by caching (only runs when hash changes) and the proactive trigger (may pre-warm before the next step).
- **Agent failure leaves no summary.** If the summarize agent fails or doesn't write `.lf/summary.md`, the wave continues without a summary. This is intentional (non-blocking) but means some steps may lack context.
- **No summary for `lf` CLI.** The CLI path (`gather_context`) has no DB access, so summaries are daemon-only. This matches the design but is worth noting.

## What's not included

- **Git post-commit hook installation.** The design doc mentions installing a hook in wave worktrees. This branch uses the existing `WorktreeUpdated` event instead, which serves the same purpose without modifying `.git/hooks`.
- **Summary token counting.** The token budget is passed to the prompt but there's no verification that the agent's output stays within budget. The existing `trim_context_with_breakdown` handles overflow at the context assembly level.
