# W2-129 — Wave Chat is a conversation, not a log

## Problem

The wave thread today renders the runtime's shape, not the human's. Every turn
shows the loop's tool calls (`🔧 Bash`), command cards with exit codes and
durations, file cards, thoughts, and — above each assistant span — a divider
naming the flow step that produced it (`task / task_clarify · completed`). The
model is honest and the journal is truth, but the reading experience is a
build log with prose scattered through it. A human steering a wave has to scan
past the machinery to find what the wave is *saying*.

The fix is a projection, not a new pipeline. Everything needed for a
human-first read is already on the wire (`ChatTurn` + `ConversationItem` +
`BodyProvenance`); the surfaces just render all of it, flat, all the time.

## Shape of the change

**Surface-only.** No wire, journal, runtime, or DTO change — same precedent as
`AttemptFailurePresentation`, which projects failure semantics over existing
provenance. The audit view *is* today's view, so the raw record must keep
arriving; hiding it at the renderer is the only place the change belongs.

Two surfaces, one contract:

| | default (human) | audit |
|---|---|---|
| assistant prose (`turn.text`, `.message` items) | shown | shown |
| tool / command / file items | one coalesced activity row per turn | today's cards |
| thoughts | hidden | shown |
| body boundary (`flow / step` divider) | hidden | shown |
| failed item (status `failed`, or nonzero exit) | shown, always | shown |
| failed turn (`AttemptFailurePresentation`) | shown, always | shown |
| child activity: decision / PR / failed / completed / directed | shown | shown |
| child activity: `state_changed`, `control_applied` | hidden | shown |

The rule the table encodes: **prose, failures, and decisions are the
conversation; everything else is evidence.** Evidence collapses to a count and
stays one disclosure away.

## Swift

New `swift/Loopflow/Models/WaveChatTranscript.swift` — pure, no SwiftUI, unit
tested like `AttemptFailurePresentation`:

```swift
public struct TurnActivity: Equatable, Sendable {
    public let commands: Int
    public let files: Int
    public let tools: Int
    public let isRunning: Bool
    public var label: String   // "Working…" · "4 commands · 2 files" · "6 tool calls"
}

public struct TurnPresentation: Equatable, Sendable {
    public let prose: String                    // turn.text + .message item text
    public let activity: TurnActivity?          // nil when there is nothing to collapse
    public let failures: [ConversationItem]     // actionable, never collapsed
    public let auditItems: [ConversationItem]   // everything, for the disclosure
    public let showsBoundary: Bool              // audit only
}

public func turnPresentation(_ turn: ChatTurn, audit: Bool) -> TurnPresentation
public func isConversational(_ activity: ChildControlActivity) -> Bool
```

`MessageRow` renders `TurnPresentation` instead of filtering
`turn.items` itself; `ConversationItemCard` stays exactly as it is and becomes
the audit-disclosure body. `WaveChatView` gains one `@AppStorage("waveChatAudit")`
toggle in the wave control header (`Audit` / `Conversation`), gates
`bodyBoundary(...)`, and drops non-conversational activity cards.

**Streaming stays smooth by construction.** The prose path is untouched:
`presentation.prose` flows straight into `SelectableAssistantMessageTextView`,
so nothing buffers between the SSE frame and the glyph. The activity row is a
*single* row whose label is derived from counts — items arriving during a turn
change one `Text`, never the row count, so the `LazyVStack` has no rows to
insert and the scroll-follow geometry doesn't move under the reader. That is
the reason the collapse is a count and not a list. (A structural argument, not
a measured one — see "Not claimed".)

## CLI

`lf chat --follow` has the same disease: `turn turn-2 opened`, `  tool Bash →
completed`, `  $ cargo test → completed`, `turn turn-2 completed · 7 items`.

`thread::Renderer` gains an `audit` bit (plumbed from a new `lf chat --audit`;
`--json` is unchanged and stays the raw wire):

- human default: user/attributed turns as today; assistant prose printed as
  plain lines; per-item lines suppressed **except** failures (`! $ cargo test →
  failed`); one consolidated close line only when the turn carried evidence
  (`· 4 commands, 2 files`).
- `--audit`: exactly today's output.

## Verification (done)

The hierarchy is validated against one realistic long-running `task` transcript
— clarify reads the repo and writes a design note, pursue builds and hits a red
`swift test`, mutate opens the PR, and a child project raises a decision — run
through both renderers.

- Swift (`WaveChatTranscriptTests`, 8 tests): five items behind one sentence
  collapse to `1 command · 1 file edited · 2 tool calls`; the red test survives
  the collapse; a nonzero exit is a failure even when the harness marked the
  command `completed`; a silent running turn still reads `Working — …`; audit
  returns every card and the boundary; the visible thread is
  `[human, speech, decision, speech]` — the empty step-boundary span and the
  `state_changed` churn never reach the eye.
- Rust (`a_long_running_task_reads_as_conversation_not_a_build_log`): the same
  transcript renders as four prose lines, one `✗ $ … → exit 1`, and two
  evidence lines; `--audit` over the identical frames restores
  `turn turn-3 opened` / `$ … → completed` / `turn turn-3 completed · 6 items`.
- Suites: `cargo clippy -D warnings`, `cargo test -p loopflow`, `swift test`
  (95), and the LoopflowMac `build-for-testing` all pass.

Still owed: dogfood against the live product wave in both surfaces.

## Not claimed

This change is a projection over turns already in memory; it draws fewer rows,
but **no performance claim is made here**. W2-132 measures the shared base
commit `4fbc980f` — any statement about render cost waits for that baseline.

## Decisions taken (reversible, noted not asked)

- **Audit is a view toggle, not a per-turn expander.** Per-turn disclosure still
  exists (the activity row expands), but the flow-step boundaries are a mode —
  they're structure, not content, and revealing them per-turn would restore the
  log.
- **Status updates are derived, not authored.** "Occasional consolidated status
  updates" comes from coalescing evidence into one row per turn. Teaching the
  loop to *narrate* periodically is a prompt change under a different task.
- **`state_changed` / `control_applied` child activities are hidden by default.**
  They are churn; the decision, PR, completion, and failure kinds are the report.
