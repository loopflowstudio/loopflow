# W2-130 — Project and Task Session supervision recovers safely

Task: `ts_5123f7b72f654d6cbb6ec84d8d364e8e` · Project: Loopflow API · one PR to `main`.

## The five W2-127 failures, located

All five have one root: **a Session's execution context is re-derived in whatever
process happens to touch it, and terminal intent is not durable.** Nothing about
the Session record says which binary owns it, which store it lives in, or that a
human already ended it.

### Failure 9, in detail (observed 2026-07-14, W2-129)

Task Session `ts_c33d8dc7079e42db8135566e22a22bdb` emitted `pull_request_opened`
for **#878** and went `submitted`. The same Session then launched **generation 2**
and returned to `running` at `task_clarify`, `process_alive=true` — re-deriving a
design whose PR was already open for review.

The gate is `is_process_active()` again, and again it is reading a status field
that cannot express what it is being asked. `Submitted` is not terminal
(`task/mod.rs:70` — only `Merged`/`Abandoned` are) and carries no live process, so
to every launch path it is indistinguishable from a Session that stopped and wants
resuming. A supervisor wake therefore did what it always does: started a
generation.

**Delivery is terminal intent for the supervisor, not for the Session.** A
submitted Task's next move belongs to review — merge it, or answer a comment. What
it must never do is quietly begin its own work again from the top. But a human
*does* legitimately resume a submitted Session to answer review, so the bar cannot
be the Session's status alone: it has to distinguish who is asking. Hence
`LaunchIntent`: a supervisor (a project waking on an observation, a queued steer,
an internal retry) is barred; an operator's explicit `lf task resume` is not.

Confirmed non-failures, to be pinned by test rather than changed: `queue_command`
already rejects commands to terminal Sessions (`ops/child.rs:249`); abandon and
stop already perform **zero** git mutation — no worktree removal, no branch delete.

### Failure 6, in detail (observed 2026-07-14)

Two concurrent `task run`/`task start` calls under one Wave. One reservation died
with sqlite `database is locked`. Retrying `task run` handed back a durable Session
still reading *"Linear task reserved before placement"* — no worktree, no process.
Only an explicit `task resume` finished it. Two independent defects:

**6a. Every write transaction is `BEGIN DEFERRED`, so `busy_timeout` cannot save it.**
`conn.transaction()` (`store/sqlite/child_sessions.rs:67` and ~20 sibling call
sites) is rusqlite's *deferred* begin. `reserve_task_session_with_directive` then
*reads* (`validate_task_project_session`, `:68`) before it *writes* (`:70`) — a
read→write lock upgrade. Under WAL, when another process has written since the
read snapshot, SQLite fails that upgrade **immediately**: it cannot wait, because
waiting could deadlock two upgraders. `PRAGMA busy_timeout = 5000`
(`store/sqlite.rs:165`) is never consulted. The in-process `conn.lock()` mutex
serializes writers *within* one `lf`, which is exactly why this only appears when
two `lf` processes race — the common case under a Wave.

Then `ops/task.rs`'s recovery arm conflates the two sqlite errors it can get:
`Err(StoreError::Sqlite(_))` treats a transient `SQLITE_BUSY` the same as a real
`UNIQUE` collision. It re-reads, finds nothing (the winner may not have committed),
and reports *"task reservation collided with another task placement"* — a lie about
a retryable lock.

**6b. `task run` returns a partially-created Session instead of finishing it.**
Creation is: reserve the row (`ops/task.rs:363`, status `Created`) → append event →
`create_from_placement_plan` (git) → `launch_task_process` → `wait_until_running`.
The row is durable at step 1, **before** the worktree exists and before any process.
Any failure in steps 3–5 — including 6a's fallout — leaves a durable `Created` row.
And `task_run`'s early return (`ops/task.rs:261`) hands back *any* existing Session
unconditionally, without asking whether placement or launch ever happened. `run` is
idempotent in the useless sense: it reliably returns a corpse. `resume` was the
undocumented secret handshake that actually finished the job.

### Failure 7, in detail (observed on W2-132)

A Project replacement directive spawned Claude **PID 62870** resuming provider
session `799b65bb`. The Task runner had already spawned **PID 63606** for
`task_pursue` — same provider session, same worktree. Both stayed live: 63606 was
running `cargo bench` while 62870 idled. Two processes writing one worktree and
one vendor conversation.

**Every Claude turn is its own OS process.** `harness/claude.rs:152` spawns
`claude … --resume <provider_session_id>` per `send_input`; `interrupt()` (`:266`)
kills it because there is no per-turn cancel RPC. So "one provider process per turn"
is not an invariant the code holds — it is an invariant the code *assumes*.

Three ways it breaks, in ascending order of importance:

- **`send_input` overwrites `self.child`** (`claude.rs:186`). The `turn_in_progress`
  CAS (`:120`) guards the common path, but the reader clears that flag when the
  *stream* ends (`:257`), which is not the same instant the *process* exits. A
  spawn in that window drops the previous `Child` handle — and unlike codex
  (`codex.rs:603`), the Claude harness sets no `kill_on_drop`, so the old process is
  simply orphaned.
- **`kill()` kills `claude`, not its process group.** `cargo bench` is a grandchild;
  it survives the interrupt and keeps writing the worktree. That is literally what
  W2-132 caught in the act.
- **The real one: two `lf __task` runners existed at all.** `queue_command`
  (`ops/child.rs:357`) launches when `!session.is_process_active()` — a **status
  field**, which failure 5 already proved can lie. The Project's steer found a Task
  whose stored status was not `Running`, so it launched a *new generation*: a second
  tmux, a second runner, a second harness, resuming the same `provider_session_id`
  in the same worktree. Meanwhile the old generation kept going: `begin_generation`
  bumps the counter, but nothing **kills** the prior process. The old runner only
  discovers it is stale at its next boundary (`claim_task_commands_or_stop` rejects
  a stale generation) — and it does not reach a boundary while `cargo bench` runs.
  Bumping a generation orphans the old one instead of ending it.

So failure 7 is failures 4 and 5 collecting their debt: a launch decision made on a
status field that lies, with no lease and no reaping.

### Failure 8, in detail — task-base contamination

All three product Task worktrees were cut from local `main` at **`4fbc980f`**, which
was ahead of `origin/main`. A manual `lf pr open` in W2-132 therefore produced
**PR #877** containing exactly one commit — `lf commit: wave_pursue`, touching
`wave/infrastructure/MEMORY.md` — before any task work existed. A Task PR whose
entire content is another wave's memory file.

Verified now, and worse than reported: `4fbc980f` is reachable from **no** remote
branch except `origin/jack-heart/w2-132`. It is not in `origin/main` and never was.
PR #877 is *how that commit reached the remote at all*. Local `main` has since been
brought back in line, which means the three task branches are now based on a commit
that is orphaned from `main` entirely — including **this** worktree, whose recorded
base is `4fbc980f`.

Two defects meet here:

- **Placement bases on local `main`, not the published tip.** `plan_placement` sets
  `base_ref = get_default_branch(repo)` (`worktrees.rs:629`) and `task_run` resolves
  `base_commit = rev_parse(&main_repo, &default_branch)` (`ops/task.rs:306`).
  `origin/main` is never fetched, never consulted, never compared. Whatever happens to
  be sitting on local `main` becomes the base of every Task — and therefore the content
  of its PR.
- **`ensure_clean_main` checks the wrong three things.** It requires the canonical
  checkout, the default branch, and a clean tree (`ops/project.rs:333-358`) — but never
  that `main` is *published*. A `main` ahead of `origin/main` sails straight through.

And there is a third thing standing behind both, which this design names but does not
fix: **something committed to canonical `main`.** The contaminating commit is titled
`lf commit: wave_pursue` — an agent's wave turn wrote a memory file and committed it to
`main`, in the same codebase whose `ensure_clean_main` error text insists "Wave and
Project turns never edit repository files." Basing on `origin/main` makes the blast
radius zero, which is why it is the fix here. But an agent committing to canonical
`main` is its own defect and belongs in its own task under the Loopflow API project.

## The fix, in seven moves

### 1. The Session record owns its execution context

Add to `project_sessions` and `task_sessions` (edit `001_initial.sql` in place —
one baseline is the convention; a stale DB gets the recreate error by design):

```sql
lf_bin   TEXT NOT NULL,   -- absolute path to the lf that created this Session
db_path  TEXT NOT NULL,   -- absolute path to the store this Session lives in
lf_home  TEXT NOT NULL,   -- absolute LF_HOME for this Session
```

Resolved **once**, at Session creation. `resolve_lf_binary()` gains an absolute
form that refuses to hand back bare `"lf"`: it resolves through PATH and errors
if it cannot produce an absolute, existing path. A Session that cannot name its
own binary is not created.

Every launch (`launch_task_process`, `launch_project_process`) then uses
`session.lf_bin` as `argv[0]` and passes `LF_DB_PATH`/`LF_HOME` **explicitly** in
the child env. `start_lf_session_with_env`'s inherit-if-present list drops
`LF_HOME`/`LF_DB_PATH` for child sessions — they are pinned, not inherited. The
caller's own binary and environment stop mattering: `./target/debug/lf task
resume W2-x` relaunches the child as the *pinned* `lf`, against the *pinned* db.
Kills failures 1 and 3.

### 2. A debug build may not open the live registry by accident

`database_path_from_env()`: when `cfg!(debug_assertions)` and neither `LF_HOME`
nor `LF_DB_PATH` is set, refuse the default `~/.lf/loopflow.db` with an
actionable error — *"dev builds must set `LF_HOME` (e.g. `LF_HOME=~/.lf-dev`) or
`LF_DB_PATH`; refusing to open the live registry."* Release/installed `lf` is
untouched. This makes failure 2 unspellable rather than merely detected, and it
is the separate-dev-lfdb convention the wave has wanted since the migration
collision.

### 3. Terminal intent is durable, and no launch path outruns it

Add `abandon_requested_at INTEGER` + `abandon_reason TEXT` to both Session tables,
written **in the same transaction that creates the Abandon command** — not when
the runner finally consumes it. Then, uniformly:

- `ChildSession::launch()` refuses when abandon intent is set.
- `wake_project_session` refuses when the Project has abandon intent.
- `queue_command` rejects every non-Abandon command once intent is set, with the
  same shape as today's terminal rejection — closing the queue→accept race.
- Liveness reconcile on a dead process with pending abandon finalizes to
  `Abandoned`, not `Failed`. A killed-then-abandoned Session must not read as
  resumable.

**Interrupt never launches a process.** Today bare interrupt on an inactive
Session accepts without launching (`ops/child.rs:341`) but interrupt-*with-replacement*
falls through to the launch at `:357`. Make both accept-without-launch: the
replacement lands as the pending directive, the Session reads `Waiting` with
reason *"interrupted; resume with `lf task resume`"*, and `resume` is the one
explicit verb that starts a process. Interrupt becomes terminal for the turn and
observable: it writes a status + `StatusChanged` event **even when the process
was already dead**, so `lf task show` proves the interrupt landed.

Launch preconditions in `launch_task_process`, each an actionable `Blocked` rather
than a silent respawn: abandon intent set; `session.worktree` missing or no longer
a registered git worktree for `session.branch`; generation count over a fixed cap
(crash-loop guard — no config knob). Kills failure 4.

### 4. Reads tell the truth

- `lf status` / `lf ls`: one batched `tmux list-sessions` snapshot per call (never
  a `has-session` per Session — the wave's own performance rule), so a Session
  whose tmux is gone can never render as `Running`.
- Terminal Sessions render *as terminal* instead of being filtered out of view.
- `lf task show` / `lf project show` surface `lf_bin`, `db_path`, `process_alive`,
  and any abandon intent. The context a Session runs in becomes inspectable, which
  is how failures 1–3 stayed invisible for a week.

### 5. Concurrent creation serializes; `run` finishes what it started

**Write transactions begin `IMMEDIATE`.** Replace `conn.transaction()` with
`conn.transaction_with_behavior(TransactionBehavior::Immediate)` on the write paths
in `store/sqlite/child_sessions.rs` (and the sibling writers in `store/sqlite.rs`).
The write lock is then taken at `BEGIN`, where `busy_timeout` *does* apply, so a
second `lf` process **queues** for up to 5s instead of failing an un-waitable
upgrade. Contention becomes latency, not an error. This is the whole of 6a's
mechanism, and it is a mechanical change — reads keep the deferred begin.

**The recovery arm stops conflating BUSY with UNIQUE.** Match the sqlite extended
code: a unique-constraint violation means another process won the reservation —
re-read and adopt its Session, touching no git. A busy/locked error is retryable —
bounded retry, and if it still fails, say *locked*, not *collided*.

**`run` converges; `resume` restarts.** The two verbs get a crisp division:

> `lf task run` finishes **creation**. `lf task resume` restarts a **stopped process**.

So `task_run`'s existing-Session path stops returning inert state and instead
completes whatever creation left undone, in order:

- terminal status, or abandon intent set → return as-is. Creation never resurrects
  a Session someone ended (move 3 owns that rule; `run` obeys it).
- process already active → return as-is.
- **a process generation exists but none is live** → return, pointing at `resume`.
  `run` does not silently restart a Session that has already run; that is `resume`'s
  job, and blurring them is how W2-127 got its wrong-binary relaunch.
- **no process generation has ever existed** (`latest_process.is_none()`) → this is
  partial creation, and `run` finishes it: create the worktree from the recorded
  plan if it is missing (`branch` + `base_commit` are already on the row), then
  `launch_task_process` + `wait_until_running`.

The last clause is the fix for 6b: the `Created`/"reserved before placement" row is
no longer a dead end but a **resumable creation checkpoint**, which is what a durable
pre-placement reservation was always for. Re-running `lf task run` after any crash
between reserve and launch converges to a running Session.

### 6. One writer per Task: the generation is a lease

The invariant, stated so it can be tested: **a Task Session has at most one live
provider process, and it belongs to the current generation.** The generation counter
stops being a label and becomes a *write lease* on the worktree and the provider
session.

**The launch gate probes, it does not trust.** Every launch path — `queue_command`,
`launch_task_process`, `wake_project_session` — decides on a real liveness probe of
`latest_process` (tmux name, and now the recorded pid), never on `status
.is_process_active()` alone. If the prior process is alive, **adopt it**: deliver the
command to the running runner and spawn nothing. Move 1's pinning makes the probe
meaningful; move 4's honest reads make it correct. A status field must never again be
the sole basis for spawning a process.

**Superseding a generation kills the one it supersedes.** `begin_generation` currently
increments and walks away. It gains a reaping step, ordered *before* the reservation
CAS: terminate the prior generation's tmux session and its process group, confirm it
is gone, then reserve. The reservation CAS stays the single serialization point, so
two would-be launchers still cannot both win — but now the loser of the *previous*
round is dead rather than orphaned.

**A stale runner spawns nothing and exits.** The generation check at
`task/runner.rs:59` already exists at startup; it becomes a precondition of *every*
provider spawn, not just of boot. A runner whose generation is no longer the Session's
current one must not call `send_input` at all.

**The harness holds one process, exclusively.**
- `send_input` refuses to spawn while a `Child` is still live — a live child is
  `TurnAlreadyInProgress`, and `self.child` is never overwritten. The
  `turn_in_progress` flag is a fast path, not the invariant; the `Child` handle is.
- Spawn Claude in its **own process group** and kill the *group* on interrupt/stop,
  so `cargo bench` and every other grandchild dies with the turn.
- Set `kill_on_drop(true)`, matching codex (`codex.rs:603`), as the backstop for
  every path that forgets.

**The flow does not advance until replacement delivery exits.** After an
`interrupt_harness`, the runner can currently reopen the flow body
(`resume_interrupted_flow` → `open_task_flow_body`, `task/runner.rs:~210`) and start a
new step while the replacement body is still pending. A pending replacement becomes a
barrier: no `start_task_flow_turn` until the replacement's body has reached a terminal
event. A directive that replaces the turn must land *in* the turn it replaces, not
race the next one.

### 7. A Task is based on the published tip, and a PR proves it

**Placement bases on `origin/<default>`.** `plan_placement` fetches and sets
`base_ref` to the remote-tracking tip; `task_run` resolves `base_commit` from
`origin/main`, not local `main`. A Task's diff is then, by construction, only the work
the Task did — no local commit can leak in, no matter what state the canonical checkout
is in. This is the structural half: contamination stops being *detected* and starts
being *unspellable*.

**`ensure_clean_main` gains its missing check.** Canonical `main` ahead of
`origin/main` is refused, with an actionable message (push it, or reset to it). Basing
on `origin/main` already makes the Task safe, so this check is not what protects the
PR — it is a **smoke alarm**. A `main` with unpushed commits means something wrote to
canonical `main`, and the maintainer should hear about it at the moment it is cheap to
fix rather than a week later in a PR diff.

**PR opening verifies its own range.** `lf pr open` refuses a PR whose commit range
against `origin/main` contains commits the Task did not author — concretely: the
recorded `base_commit` is not an ancestor of `origin/main`. The remedy is offered in
the same breath (rebase onto `origin/main` and reopen), because that is the only thing
the operator would do anyway. Placement makes contamination impossible for *new* Tasks;
this catches the ones already cut from a poisoned base — which right now is all three.

**Including this one.** This worktree's recorded base is `4fbc980f`. It must be rebased
onto `origin/main` before its PR opens, or W2-130 ships the very bug it is fixing.

## Worktrees and branches

Abandon, interrupt, and stop mutate git **not at all** — that holds today and gets
a regression test. One gap gets closed: `lf wt prune` (`lf/commands/ops/mod.rs:1310`)
prunes by git/PR state alone and will happily delete the worktree of a live Task
Session, which is *how* a relaunch ends up pointing at a missing directory. It
learns to skip worktrees owned by a non-terminal Task Session, and to say so.

## Verification

`rust/loopflow/tests/session_recovery.rs`, against a real temp store. The launch
*decision* and the composed process context are what actually failed in W2-127, and
both are testable without a live provider:

1. Relaunch uses the pinned `lf_bin` even when the calling process's `LF_BIN` points
   somewhere else (the decoy is the whole point).
2. The child command line carries the pinned `LF_DB_PATH`/`LF_HOME` even when the
   caller's environment has neither (assert on `lf_session_shell_command`).
3. Abandon intent blocks launch from *every* path, `wake_project_session` included.
4. Interrupt — bare and with replacement — never launches, and is observable on a
   Session whose process is already dead.
5. Dead tmux + pending abandon reconciles to `Abandoned`, never `Failed`.
6. An abandoned Task keeps its worktree directory, its branch, and its rows.
7. A dead Session never renders `Running` in `lf status`.

The 2026-07-14 race needs *real* concurrency, so it gets its own reproduction —
threads against one temp store file, mirroring two `lf` processes (the per-process
`conn.lock()` mutex means a single-threaded test cannot reproduce it at all):

8. **Reproduce first, on the current code:** N concurrent reservations of the same
   issue against one store file must currently produce a `database is locked`. This
   test is written to fail before the `IMMEDIATE` change and pass after — otherwise
   there is no proof the fix addressed the observed failure.
9. Concurrent `task run` of the same issue: exactly one Session row exists, exactly
   one worktree is created, and **every** caller returns that same Session. No caller
   sees "collided", and none is left holding an error for a lock.
10. Concurrent `task run` of *different* issues under one Wave: all succeed. The
    serialization is on the write lock, not on task creation as a whole.
11. **Partial creation converges:** a Session reserved at "Linear task reserved
    before placement" with no worktree and no process — re-running `task run` creates
    the worktree and launches, ending `Running`. Re-running it again is a no-op.
12. Partial creation with abandon intent set does **not** converge — `run` returns
    terminal state and starts nothing (moves 3 and 5 must not fight).
13. A Session with a dead process generation is *not* restarted by `run`; it says
    `resume`.

W2-132's two-writer race is the one failure that a store-level test cannot see at all
— it is about **OS processes**. So it gets a real end-to-end, driven by a fake
provider: a script standing in for `claude` that announces a provider session id,
writes its own pid to a file, spawns a long-running *grandchild* (the `cargo bench`
stand-in), and sleeps. `LF_BIN` + the agent config point the harness at it, so no
vendor, no network, no tokens.

14. **Process count is the assertion.** Across a steer/replacement delivered while a
    turn is active, the number of live provider processes for the Task Session is
    **never > 1**, sampled throughout — not just at the end, where an orphan hides.
15. **One-writer ownership.** With a runner live on generation N, a second launch
    attempt (the exact `queue_command` path the Project's steer took) spawns **no**
    second runner and **no** second provider process: it adopts the live one. Assert
    against the pid file, not the status column — the status column is what lied.
16. **Superseding reaps.** When a new generation does legitimately start, the prior
    generation's process *and its grandchild* are gone. The fake provider's orphaned
    grandchild is the whole point: kill the group, not the process.
17. **The flow waits for the replacement.** With a replacement pending, no flow step
    starts until the replacement's body reaches a terminal event. Assert on the
    ordering of turns, not on a sleep.
18. A stale-generation runner calls `send_input` zero times before exiting.

Task-base contamination is pure git, so it tests cheaply against a scratch repo with a
real remote (`worktree_tests.rs` already has the machinery):

19. **The reproduction:** local `main` one commit ahead of `origin/main`; place a Task;
    its `base_commit` is `origin/main`'s tip, and the diff of its branch against
    `origin/main` is **empty**. On today's code the unrelated commit is in the range —
    that is the failing assertion that proves the fix.
20. `ensure_clean_main` refuses an unpushed canonical `main`, and names the remedy.
21. `lf pr open` refuses a branch whose `base_commit` is not an ancestor of
    `origin/main`, and names the rebase.
22. Placement still works with no network / no remote-tracking branch — a repo without
    an `origin` must degrade to local `main`, not hard-fail. (The fetch is best-effort;
    a missing remote is not contamination.)

`wave_live_smoke.rs` gains one `#[ignore]`d end-to-end: real tmux, pinned binary,
kill the process, resume, assert the new generation ran the pinned exe against the
pinned db.

## Decisions taken (reversible; noted, not asked)

- **Edit the baseline, don't add a migration.** `store/migrations.rs` has exactly one
  baseline and a recreate path; a numbered migration would fight it.
- **Pin three columns, not one.** `db_path` alone would leave `LF_HOME`-derived
  paths (tokens, endpoint files) drifting.
- **Debug-build guard is a hard error, not a warning.** If it turns out to break
  tests that rely on the default path, it downgrades to a `lf doctor` check — that
  fallback is the only part of this design I expect to have to walk back.
- **Interrupt loses its relaunch.** Anyone depending on `interrupt <text>` to wake a
  dead Session now types `resume`. That is a behavior change, and the honest one:
  it is exactly the path that spawned the wrong binary.
- **`IMMEDIATE` on writes, not a global serializing mutex.** A cross-process lock file
  would also fix the race, but SQLite already has the lock; we were just asking for it
  in the one mode where it cannot be waited on. Let the database serialize the database.
- **`run` finishes creation but never restarts a process.** The alternative — `run`
  meaning "make it be running, whatever it takes" — collapses it into `resume` and
  reopens the class of bug where a supervisor's idempotent-looking retry silently
  starts a process nobody asked for.
- **Adopt the live process; don't kill it and take over.** When a launcher finds a
  live prior generation, the safe move is to deliver into it, not to reap it and
  start fresh. Reaping is reserved for a generation that is *actually* being
  superseded — otherwise a steer would routinely murder a healthy running turn.
- **Probe, don't lock.** A pid/tmux liveness probe plus the existing reservation CAS
  is enough for one-writer; a lease file with a TTL would add a clock to reason about
  and a new way to be wrong. The database already arbitrates who wins.
- **Base on `origin/main`; don't try to keep local `main` clean.** Policing the
  canonical checkout is enforcement, and enforcement gets bypassed. Reading the
  published tip means a dirty local `main` simply cannot reach a Task PR — the
  violation becomes unspellable rather than forbidden.
- **Out of scope, and filed rather than fixed: an agent committed to canonical `main`.**
  `lf commit: wave_pursue` is how `4fbc980f` got there. Move 7 makes it harmless to
  Tasks; it does not stop it happening. That is a separate task under Loopflow API,
  and folding it into this PR would double the blast radius of a recovery change.
