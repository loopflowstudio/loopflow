# W2-132 — Slow token streaming in Wave Chat

Baseline pinned to base commit `4fbc980f`. Worktree clean at that commit; every
streaming-path file (`wave/runtime.rs`, `wave/journal.rs`, `flowloop/wave.rs`,
`harness/codex.rs`) was last touched by `309575f8` (2026-07-13), an ancestor of
base — so the live product journal written on 2026-07-14 is a faithful record of
base-commit code. W2-129 is isolated in another worktree; any coalescing change
it lands is a separate post-change measurement, not this baseline.

## The measured baseline (no optimization applied)

Source: `~/.lf/journal/waves/product/journal.jsonl`, the real accumulated
transcript, restricted to the 17 assistant turns produced after `309575f8`.

| Measure | Value |
| --- | --- |
| Transcript size | 7,420 records / 4.2 MB (product wave) |
| TTFT (`TurnStarted` → first delta journaled) | median **6.01 s** (min 2.75 s, max 10.39 s) |
| Delta rate, in-burst (server side) | median gap **8.0 ms** → **~125 deltas/s** |
| Delta rate, wall-clock over a whole turn | **1.0–4.4 deltas/s** |
| Assistant prose per turn | median 1,070 chars, 3,740 deltas over 18,118 chars |
| SSE bytes actually shipped for that prose | **2,067,580 bytes = 114× the prose** |
| Worst single turn (`turn-626`) | 657 deltas, 3,149 chars, 1.03 MB broadcast — **327× amplification** |

Two facts fall out, and they point in opposite directions:

**The write path is not slow.** Provider delta → `lf_tag` parse → one awaited
HTTP POST → listener → journal append lands in a median of 8 ms per delta. That
already includes the per-delta HTTP round trip. 125 deltas/s reaches the journal.
Whatever renders "a couple of words per second" is not starving there.

**The wire is quadratic.** `WaveRuntime::append_turn_item_locked`
(`rust/loopflow/src/wave/runtime.rs:1202`) clones the entire open `ChatTurn` and
`TurnFrame::share` (`runtime.rs:115`) re-serializes the **whole turn** to JSON on
**every token**, then broadcasts it to every SSE subscriber. Prose of length n
arriving in n deltas ships O(n²) bytes. Measured: 114× amplification across real
turns, 327× on the worst one.

The code says so itself, in two comments that are now false:

- `runtime.rs:1016` — *"No debounce: deltas are item-granular from the vendor
  stream (one per completed item, not per token) … A throttle earns its place
  with the part-grained wire, not before."* The wire **is** part-grained: for
  Codex, `flowloop/wave.rs:864` forwards every `ConversationEvent::TextDelta`
  1:1 as a `ResidentDelta::TurnText`. The condition that comment set for adding a
  throttle is met.
- `runtime.rs:104` — *"the delta-granular wire — sending increments instead of
  whole turns — stays future work."* This task is that future work.

Provider granularity is **not uniform**, and this matters: Codex streams real
per-token deltas; Claude is launched without `--include-partial-messages`
(`engine/agent.rs:501`), so it emits whole assistant messages and the
`text_delta` arm of `claude_mapping.rs:161` is dead for waves. The product wave
runs Codex — hence 3,740 deltas in the journal. Any fix must hold for both.

## Where the reported slowness actually is

The server reaches 125 deltas/s; the reader sees a couple of words per second.
The gap is downstream of `turn_tx.send`. The candidate, pending the Swift
read-path measurement: each SSE frame is a full turn snapshot that grows with the
turn, so the consumer decodes an ever-larger JSON and re-renders the whole
message per token — the same quadratic, paid again in the UI, on a machine that
also has to lay out text.

**Do not optimize before this is measured.** The next act is instrumentation, not
a fix: without a consumer-side number, "fix the batching" is a guess, and the
write-path measurement above already refutes the obvious guess.

## Budgets (proposed, to be enforced by a gate)

Named before optimizing, per the Product Performance KRs:

- **Time-to-first-visible-token**: ≤ 300 ms from the listener journaling the
  first delta to that text being visible in the reader. (Provider thinking time —
  the measured 6 s — is upstream of Loopflow and is measured separately, never
  folded into this budget.)
- **Sustained visible-token rate**: ≥ 30 visible updates/s, and never degrading
  as the open turn grows — the rate at char 3,000 must be within 20% of the rate
  at char 100. Flat, not just fast: that is what kills the quadratic.
- **Wire amplification**: total bytes broadcast for a turn ≤ 3× its final prose
  (today: 114×).

## Plan for pursue

1. **Measure the consumer.** Instrument the SSE→reader stage at base commit:
   replay a recorded provider delta stream (the real `turn-626` sequence, 657
   deltas / 3,149 chars) through resident → listener → SSE, and record per-frame
   arrival time and decode+render cost against accumulated turn length. Two
   consumers: the CLI follower (`lf/commands/thread.rs:68`) and the Mac surface.
   This yields the dominant stage empirically.
2. **Fix the highest-leverage bottleneck.** Almost certainly the delta-granular
   wire the code already names as future work: broadcast the increment, not the
   snapshot, so a frame is O(1) in the delta rather than O(n) in the turn. Keep
   the journal's per-record fold intact (`ChatTurn::absorb_item`,
   `chat/turns.rs:210`, already concatenates stream fragments correctly — the
   replay path needs no change).
3. **Gate it.** A repeatable benchmark asserting the three budgets above, run in
   CI, so a regression fails visibly before release. This is the first evidence
   for the Product Performance KR on enforcement gates.
4. **Verify on the installed Mac surface**, not just the bench.

Out of scope: transcript information architecture (W2's human-first Wave Chat
task owns that). Out of scope: whether Claude should stream partials at all —
worth filing, but it changes provider behavior, not this latency path.

## Assumptions

- Development binaries run against `LF_HOME=~/.lf-dev`, never the live registry.
- The 6 s TTFT is provider thinking time and is reported separately rather than
  optimized here; if the consumer-side measurement shows Loopflow adds materially
  to it, that becomes part of the fix.
