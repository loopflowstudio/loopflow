Bare, managed, detached: how others draw these lines

For LOO-924. The prior art below is from memory of each tool's documented behavior, not re-read today. Everything marked proposed is a sketch, and nothing here has changed the plan or the running implement.

proposed, after those last two One fact: this run belongs to Task X. The checkout, --task and LF_AS are three ways to say it, and they mean exactly the same thing. Belonging gives two things, always together: the run counts toward the Task, and it gets the Task's steers. Belonging never decides who keeps the run alive; only the command does. So WorkSource's variants stop changing behavior, is_managed goes, and LF_AS can stay because it can no longer mean something different from the checkout. This replaces questions 2 and 3 below: --task on a skill is bare and belongs to the Task.

Three things these tools agree on.

  1. Who keeps a process alive is chosen by the command or the kind of thing you create, sometimes by one flag. It is never chosen by an inherited environment variable.
  2. Accounting is separate from supervision. A systemd scope is counted and grouped without being started or restarted by systemd. That is the line "bare runs in a task checkout do count against a task worker": it belongs to the Task without being kept by the server.
  3. Environment variables carry where you are, written by the system for its children. One that a person sets to change what a command means is the GIT_DIR mistake. LF_AS and --as are that kind of knob. LF_CAPTURE_KEY is the TMUX kind.

The names

NamePrecedentFit
bareKubernetes uses exactly this word for "nothing manages it".Keep it. "Foreground" is the usual alternative, but lf -b run as an agent's child is bare and not in anyone's foreground.
managedCommon (Kubernetes, pm2).Fine as the word people read. The code calls the same thing Place::Held and Holder::Server, and the docs say "held terminal". Pick one of managed or held and use it in both places.
detachedtmux and Docker: a thing the server still keeps, with nobody attached.It collides twice. lf already shows "state": "detached" on an interactive Session with no viewer, and in tmux a detached session is still a managed one. For a headless run that nobody will ever attach to, worker (the word used above) or background says it without the clash.

Six combinations of state and mode become four that can be written:

enum Run { Bare(Mode), Managed, Worker }   // replaces Holder × Place × Mode

What that deletes: Holder, Place, transport::holder, WorkSource::is_managed, the named_work parameter threaded through delegate, and, if question 3 says so, LF_AS, --as and WorkSource::Declared.

Where today's code differs from the rule. server/README.md says a launch is managed when it is "lf task run and its Graph's steps, --task, --wave, …". So a Graph step is managed today (Holder::Server: its hooks report each turn to the Machine server), and lf --task X <skill> is managed because of a flag. Making steps workers means deciding what a worker still reports: today the server uses those turn reports to record Codex turns and refresh planning.

Questions

  1. The three names:
    1. bare · managed · worker
    2. bare · managed · background
    3. bare · managed · detached, and rename the Session view state that is called detached today
  2. lf --task X <skill> typed at a terminal:
    1. Bare. It is lf <skill>; the flag only says which Task it counts toward.
    2. Managed, as today.
    3. Remove --task from skill launches. Run it from the Task's checkout, or use lf task run.
  3. LF_AS and --as:
    1. Remove both in this PR. A nested lf finds its Task from the Session it inherited, then the checkout.
    2. Remove them in a follow-up Task.
    3. Keep them, as attribution only.
  4. A worker's turn reports to the Machine server:
    1. None. A worker records its own run and exit, like a bare run.
    2. Keep them. Worker differs from managed only in having no held terminal.
  5. How much of this goes in PR #1966:
    1. All of it: the three-state type replaces Holder and Place here.
    2. #1966 keeps "holder decided once" and "agent parsed once". The three states are a new Task stacked on it.
