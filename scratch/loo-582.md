# LOO-582 — promote existing work

## Accepted design — Jack Heart, 2026-11-03

Upgrade an existing worktree and/or Session into a Task, retaining cwd (including
subdirectories), branch, dirty/untracked files, provider history, live process,
drafts and input attachment. The selected conversation becomes primary without
another agent, replayed turn, implicit Graph or Auto-Ship approval. CLI and
Desktop share the operation. Existing association keeps Task identity; retries
must not duplicate work, and conflicting permanent Task binds remain intact.

Jack Heart resolved Session selection: an unfinished interactive Session may
select itself through `LF_AGENT_CALLER.session_id`, or look up its existing
provider-independent Loopflow ID. A shell must explicitly select `--session`;
`lf session list --json` supplies IDs. The shared resolver also accepts recorded
provider conversation IDs. Never infer permanent assignment from recency,
title or provider. This applies in already-owned checkouts with another primary
and in shared checkouts. Headless Runs retain their lifecycle and never implicitly
take primary. Finished Sessions remain assignable through `session bind`;
promotion does not reopen them. Explicit sources override the invoking Session;
an invoking Session in a different selected checkout is not implicitly promoted.

`task create` adopts an unassociated linked checkout; `--worktree` selects one.
Without an explicit or invoking Session it binds no conversation and chooses no
primary. Repeating creation in an owned checkout returns its Task; `--new` files
independent backlog work. `task promote ISSUE` associates an existing Task.
Record an open GitHub PR on the adopted branch when available through `gh`.

Main, repository and Wave checkouts remain shared. Selecting a shared primary
releases its former primary scope and binds it prospectively to the Task in the
same transaction; the former scope can open another conversation. Its cwd stays
shared even if the Task later gains a separate checkout. Ordinary Wave assignments
and permanent Task bindings remain intact. Remote promotion selects existing
paths and Sessions on the target Machine, without provider launch preparation;
explicit `create --run` still uses launch preparation.

Desktop keeps ordinary assignment distinct from making a conversation primary,
explains permanent assignment and checkout behavior, and retains the terminal
and composer. Already-assigned non-primary Sessions expose primary selection in
the palette and Task menu without creating a Task or offering reassignment.

## Implemented approach — reconciled 2026-11-03

Creation, placement/claim, prospective binding and primary selection share one
SQLite transaction. Checkout admission spans source resolution and commit.
Source resolution reconciles checkout and Session Task IDs before loading their
Task once. Ordinary creation uses the same transaction without placement/binding.
Placement and promotion share branch/PR preparation and store writers; no new
promotion record, ownership model or attachment lifecycle is introduced.

The recency selector, shared-primary refusal, bound-Session cwd relocation and
separate no-source creation path are removed. `checkout_conversation` remains
only for reopening taskless conversations. The single
`task_session_promotion.sql` migration allows shared-primary release while
preserving ordinary Wave assignments, permanent Task binds and captured history.
The unused async `Store::create_task` wrapper is removed; the SQLite constructor
retains creation-recovery semantics. Desktop distinguishes assignment from
primary selection, including an already-assigned conversation.

SSH dispatch and release guidance include promotion. The live LOO-718 mobile
checkout `/Users/jack/src/loopflow.mobile` and its bootstrap patch are outside
this change. No Wave is selected and no Wave memory is changed.

## Upstream integration — 2026-11-03

The branch now includes `ed983ac176` (#1804, idle Session ending) and
`36621da9a0` (#1806, Task progress reports), merged at `77411b5766`.
Promotion still writes only Task placement, prospective binding and primary
selection; it does not replace the provider process, transport attachment or
native-input ledger. Idle ending reads that ledger and current activity, while
progress reporting rereads Session Task membership. Inspection found no need
for a promotion-specific lifecycle or cached-owner repair.

Continuity means promotion itself preserves the live attachment. The ordinary
idle policy still applies afterward; promotion does not grant a permanent
process lease. Configured-provider acceptance therefore includes an unsent
draft or pending request across promotion and the idle deadline, followed by
continuation in the same conversation. Task progress arriving after promotion
must also preserve that draft. These interactions remain unverified; upstream
demonstrations alone do not establish promotion acceptance.

## Concept review — 2026-11-03

Outcome: no design change and no open product choice. The merged implementation
matches Jack Heart's accepted distinction between assigning a Session to a Task,
choosing its primary conversation and running that conversation. Promotion needs
only the existing Task placement, prospective Session binding and primary pointer;
it introduces no provider transfer or promotion lifecycle.

The consequential mismatch was treating the latest conversation in a checkout as
the intended permanent assignment. Exact selection resolves it: the unfinished
interactive caller selects itself, a shell supplies a Session ID, and checkout-only
promotion selects no conversation. Preserve the two-Session counterexample: a
newer conversation may already belong to different work. Likewise, a shared
primary can transfer while its checkout stays shared; a Task's later checkout
does not relocate that bound conversation.

Normal path: create from the prototype checkout and selected Session, inspect
status/open, then continue that same Session. Failure: a reservation or permanent
binding conflict rolls back the local creation, placement and primary changes.
Recovery: correct the source or reservation condition and repeat the command;
the checkout or selected Session identifies the committed Task if the first
command committed before its reply was lost. A shell creating in a shared
checkout with no selected Session has no existing-work identity to recover;
ordinary independent creation remains distinct from promotion.

The usage examples in `docs/work.md`, the builtin work skill, CLI help and Desktop
actions express this model. No further implementation direction is needed from
this review. Next proof remains the configured-provider and installed workflow,
including pending input/drafts across promotion and subsequent idle/progress
activity, plus the already assigned gate checks below. Inspection of code and
fixture assertions does not establish those runtime results. The review screen
is `scratch/concept-review.html`; it proposes no additional behavior.
