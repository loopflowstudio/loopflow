# LOO-582 — promote existing work

## Accepted binding — Jack Heart, 2026-11-03

Jack Heart rejected `task promote TASK`: promotion means turning existing work
INTO a Task, not acting ON a Task. After considering `session bind --primary`,
Jack clarified that binding should always make the Session primary and move its
continuation to the Task's worktree. This supersedes both the published promote
command and the intermediate optional-primary proposal.

The accepted operations are:

- `lf task create --session SESSION --title "Finish the prototype"` creates
  around existing work. Keep explicit adoption and creation defaults unchanged.
- `lf session bind SESSION --task TASK` associates the Session, selects it as
  primary, and requests continuation in the Task's existing worktree. There is
  no `--primary` flag and no public assignment-only binding mode.

Both use the shared adoption transaction. Prospective attribution, permanent
conflicting binds, exact Session lookup, atomic selection, idempotent retries
and pending directory recovery remain required. A Task's other conversations
stay associated; only its default conversation changes. Live provider input
survives until the supported next connection boundary. Files in the old checkout
stay there; creation keeps its source checkout unchanged.

Jack authorized publication to PR #1807 and a stop at demo, with combined gate
after that boundary. Auto-Ship and landing remain unapproved. No command wording
decision remains open. Autonomous observations are in `loo-582-demo.md`.

## Current implementation

CLI `session bind` and Desktop's binding action now share `human_session::bind`,
which selects the exact Session and uses the existing atomic adoption writer.
`task create` still resolves adoption only with explicit `--session` or
`--worktree`; plain creation and `--run` retain their accepted defaults.
An open Task without a checkout can adopt the selected Session's unowned linked
checkout. A done Task without a checkout binds and selects the Session in place,
without allocating a checkout or reopening work. A Task with a checkout keeps it
and records the pending continuation.
Main and Wave checkouts remain shared. Binding a shared primary releases its
old primary scope in the same transaction. Permanent conflicting binds remain.

No schema change accompanies this correction. The branch retains its one
`task_session_promotion.sql` migration. Checkout admission, prospective capture
attribution, atomic placement/claim/binding/primary choice and requested cwd
remain on the same store path. Live provider, input and files stay untouched.
An already-bound nonprimary interactive Session can be selected again.

Closed Sessions are retained history, not eligible Task primaries under the
existing lifecycle. Public binding rejects them before changing either work;
it does not reopen them. Headless Runs are likewise ineligible. This resolves
the design's closed-Session audit without adding a lifecycle. The low-level
store assignment primitive remains for historical imports and fixture seeds;
there is no public command or Desktop assignment-only action.

Source resolution owns explicit adoption: no selected Session or worktree means
an empty source, never a fallback to cwd. Binding passes its already-resolved
Session into checkout resolution. The transaction reads that Session once and
uses the same snapshot for assignment; legacy imports still reject stale captures.
Continuity fixtures share provider-exit setup and Graph settlement waits.

The former `task promote` command, API/Desktop duplication, invoking-Session
fallback and public assignment-only interaction are removed. Creation uses
`TaskAdoptionOptions`; Desktop uses `createTaskFromSession` and `bindSession`.
Worktree-only adoption into an existing Task has no replacement command.
Explicit creation retains checkout-only adoption and retry coverage.

## Accepted experience and boundaries

Jack Heart's November 3 decisions supersede the original implicit-adoption brief:
creation always files separate work unless a source is explicit; no `--new`.
A Session uses its own `LF_AGENT_CALLER.session_id` or exact lookup. Shells
must also supply an ID. No recency/title/provider selection for adoption or bind.
Creation around existing research retains cwd, subdirectories, branch/open PR,
dirty/untracked files, provider history, live drafts and input attachment.
Opening the Task selects that same conversation without provider launch or
replayed input. No implicit Graph or Auto-Ship accompanies either operation.

Binding into an already-placed Task requests its worktree without relocating
files. The current client keeps its cwd until the supported next connection.
Session summaries expose `requested_cwd`; only matching provider confirmation
clears it. A failed move or missing path retains the request, including after
another Session becomes primary. Existing launch locking serializes admission.
OpenCode uses its native move endpoint; Codex/Claude resume with saved identity
and the requested cwd. A database edit alone is never proof of a live move.

Remote commands use the target Machine's paths and Sessions without account
preparation. Explicit create-and-run still prepares launch. The live LOO-718
mobile checkout and bootstrap patch are outside this Task's modification scope.
No Wave is selected and Wave memory remains unchanged.

Directory reporting uses the execution Machine's OS hostname and serialized
terminal transport, respecting complete sequence boundaries and replay. Native
spawn reports once; OpenCode's client reports on spawn and exec handoff reports
on first provider output. Shell integration owns the directory after return.
No terminal-wide preferences change.
