## Build/cache contract

Each worktree keeps its own mutable Cargo target. Ordinary Cargo builds work
without sccache; failed cache service falls back to direct compilation with
`RUSTC_WRAPPER=`. Do not share targets, clean production targets for a cache hit,
run separate servers against one local cache, or restart a shared daemon from a
rustc wrapper.

Installed sccache 0.19.0 missed identical libraries across roots. The verified
experimental binary is upstream
`ca81ec2a2566efc623692741440d99c710268841`, containing Rust basedir normalization
and verbatim environment dependencies. Each absolute root must be listed before
its daemon starts; their parent alone is insufficient. Keep runtime path inputs
`CARGO_MANIFEST_DIR`, `CARGO_MANIFEST_PATH` and `LOOPFLOW_BUILD_SOURCE_ROOT`
verbatim. Runtime checkout identity must remain correct.

Root inventory comes from `git worktree list --porcelain -z` plus the current
canonical root, preserving spaces. One shared daemon applies refreshed config
only while idle; new roots may compile with misses meanwhile. The November 14
LOO-908 read returned done, no PR, closed Sessions: no live root-refresh
integration was delivered. Do not reopen it or invent a hidden scheduler here.

A cross-root hit retains A's absolute source/debug/generated-source paths in B's
rlib; the November 14 model and definition-content probes observed this despite
correct runtime identity. November 15 direction removes that as an extraction
stop. `scripts/dev-lf --isolated-build <lf args>` uses `target/isolated`, disables
both rustc wrappers and sccache, and leaves normal targets/cache intact. Normal
builds honor CARGO_TARGET_DIR and run its executable. No source remap or retention
service is selected. Binaries/tests still compile/link even on library hits.

## Remaining coherent cuts

### Implemented preparation — contracts extraction carries

The Concept, Resumed, Continuation, Shared-connection and Extraction reviews
that produced these are in `b555f1de54:scratch/loo-650.md`.

The synchronous store owns saved facts and atomic SQL effects; the application
owns observed inputs and policy. The `Store` facade under `store/` is application
code; moving it wholesale would recreate the coupling under a new crate name.
Direction: application policy/runtime → synchronous storage → saved values. No
callback from storage into configuration, catch-all core crate or second resolver.

- Reads: SQL returns scope with batched saved evidence from one savepoint; the
  application observes configuration after the mutex releases, once per
  repository, inside the caller's pinned Work snapshot with external revision
  tracking. No per-Task queries.
- Mutations: acquire outside SQL; the command transaction compares the saved
  inputs acquisition used (repository/Project/ancestry/local person, held set,
  candidate rows) and returns stale for reacquisition. Current saved ownership
  still decides; a configuration change never rewrites an existing claim.
  Applies to ownership, placement, Machines, rentals, peer import, Wave bootstrap,
  repository registration, account selection and Dashboard/Task order.
- A general `Store` connection cannot release its mutex inside a savepoint: read
  in a short local savepoint, observe outside, compare the complete ordered batch
  in the final savepoint. No transaction spans OS/file acquisition.
- Session projection filters availability before limit/cursor paging from batched
  observed identities; a quiet deadline that advances time reruns filtering and
  page membership. Task selections use the same projection.
- `process::attachment` coordinates resume/close/settlement; SQL transfer guards
  keep the fence through atomic claim. Splitting that sequence into independent
  calls would let a replacement interleave with takeover.
- Account selection compares candidates, limits and the newest selection at
  commit, rereads preferences on retry, and keeps an unchanged empty choice read-only.
- A locator written before a rolled-back commit is reused; conflicting retained
  identity is refused. A moved Wave is never renamed back, a retired one never
  resurrected; authored files go to the requested checkout, saved Work to the
  canonical address.
- `run_sqlite` stays an attributed application adapter; write transactions stay
  command-owned.

Regressions to keep green across the move: a disconnected planning read keeps
uncertain/conflicting deliveries; a served watch notices ignored-config and timed
projection changes without a store write; historical quota aliases select the
same account (newer observation, stricter limit at equal time, canonical name);
PID reuse or a concurrent resume leaves identity unknown, never absent, closable
or settled; a stale attachment never retires its replacement; native thread,
pending input and once-only claim survive; a limit-one page skips dead/unknown
rows; changed scope during claim, creation or hand-back reacquires; linked
worktrees share private preferences; 10,000-Task/Session plans stay indexed with
constant statements. The Machine candidate query still walks ownership history;
no bounded-history improvement is claimed for it.

Definitions resolution still depends on observed file reads and request-local
environment suppression; split those from transcript/OS observation and settings
resolution before moving graph/catalogue loading. Provider credentials/rotation
and launch continuity follow storage.

### Boundary concept review — November 15 (implemented preparation contracts)

**Design changed; iterate to implement. No open product choice.** No command,
Work record, schema or wire shape changes. Three things the design implied but
had not said, and one correction to the SQL inventory.

**1. Three kinds of thing in `store/sqlite/`, not two.** "No file or OS access in
SQL" is the wrong rule; it fails on the first counterexample below. The rule:

- *Saved facts and atomic SQL effects* stay.
- *Storage's own files beside the database* stay, with their path syntax: the
  retention cursor, Session lock files, admission lease files, and the steer
  marker. `steers.rs` touches the marker inside the write transaction on purpose
  ("a hook that checks after this touch waits for the commit before claiming
  pending steers"). Moving that touch above SQL reopens the race between a hook's
  check and the commit. `steer::{task_marker,session_marker,latest_marker,touch}`
  therefore move down with storage; hooks import the path functions from it.
- *Observation of anything storage does not own* moves above: configuration,
  Git, OS process identity, ambient caller environment, provider state.

**2. External edges in SQL (implemented).** The table of eleven sites and their
rewrites is in `7be8657b77:scratch/loo-650.md`; all are done, the caller last. Keep in each: unknown process
identity is never dead or idle; a replaced provider cannot change its
conversation; a capture from another Session is refused; a steer saved under the
write lock is visible to the next hook check. The marker-order regression exists
(`steers::tests::a_hook_check_after_the_marker_waits_for_the_steer_commit`), and so
does the replaced-actor one
(`processes::tests::replaced_callers_cannot_rename_bind_or_attach_either_title_source`).

Captured Graph, cursor and display Graph: settled in the Relocation review's
address and Graph cut.

**3. Where a saved record lives.** "With or below storage" left the choice open
for about 600 references (`work` 185, `session_record` 88, `session` 83,
`process` 44, `linear` 30, `durable` 26, `graph` 18, and the small ones). Rule:
a saved record and its pure operations live **in the storage crate** unless a
crate that does not depend on storage needs it; only then does it go to
`loopflow-model`. The model is 1,671 lines and the terminal depends on it, so
every record added there rebuilds the terminal and everything else on each
edit. Task, Session, process, planning and Linear records change together with
their SQL (store+ops co-occurred in 28 of 66 PRs); placing them beside the SQL
keeps that edit to storage → application. Application module paths re-export
them, one implementation. `TaskGraphPosition` is neither: `store::task_work`
derives it from the saved row and process liveness, and storage never names it.

**4. What storage extraction can buy, and when to measure.** Line counts at this
workspace (inline tests included): application 331,503; `ops` 62,478; `lf`
60,873; `store` 59,107, of which `store/sqlite` without test files is 35,921;
`harness` 17,661; `server` 12,817. An edit under `ops/task/` still recompiles
`ops`, `lf`, `server` and everything else left in the application. Storage is
at most about a sixth of the lines, and line share is not compile cost. So:

- Run the existing benchmark immediately after the storage crate moves, not
  after every cut. It is the first extraction with real size; its number decides
  whether definitions, providers and runtime are the right next order or whether
  the application itself (`lf` commands against `ops`) is where the cost sits.
- A fresh worktree and an edit are different wins. A fresh worktree takes every
  unchanged extracted crate from the cache; an edit saves only what sits below
  the edited code. Report them separately; do not let the first stand in for the
  second.
