## Build/cache contract

Each worktree keeps its own mutable Cargo target. Ordinary Cargo builds work
without sccache; failed cache service falls back to direct compilation with
`RUSTC_WRAPPER=`. Do not share targets, clean production targets for a cache hit,
run separate servers against one local cache, or restart a shared daemon from a
rustc wrapper.

Installed sccache 0.19.0 missed identical libraries across roots. The verified
experimental binary is upstream
`ca81ec2a2566efc623692741440d99c710268841`, containing Rust basedir normalization
and verbatim environment dependencies. Each absolute root must be listed before
its daemon starts; their parent alone is insufficient. Keep runtime path inputs
`CARGO_MANIFEST_DIR`, `CARGO_MANIFEST_PATH` and `LOOPFLOW_BUILD_SOURCE_ROOT`
verbatim. Runtime checkout identity must remain correct.

Root inventory comes from `git worktree list --porcelain -z` plus the current
canonical root, preserving spaces. One shared daemon applies refreshed config
only while idle; new roots may compile with misses meanwhile. The November 14
LOO-908 read returned done, no PR, closed Sessions: no live root-refresh
integration was delivered. Do not reopen it or invent a hidden scheduler here.

A cross-root hit retains A's absolute source/debug/generated-source paths in B's
rlib; the November 14 model and definition-content probes observed this despite
correct runtime identity. November 15 direction removes that as an extraction
stop. `scripts/dev-lf --isolated-build <lf args>` uses `target/isolated`, disables
both rustc wrappers and sccache, and leaves normal targets/cache intact. Normal
builds honor CARGO_TARGET_DIR and run its executable. No source remap or retention
service is selected. Binaries/tests still compile/link even on library hits.

## Remaining coherent cuts

### Concept review — November 15

Outcome for loop-or-next: **design changed; iterate to implement**. No new
product choice is needed for this direction. The isolated debugging path settles
the old source-retention question; automatic root upkeep remains unfinished
implementation, not a reason to ask that question again.

The experience stays two actions: `scripts/dev-lf <args>` builds and runs this
checkout; `scripts/dev-lf --isolated-build <args>` rebuilds locally for debugging.
Crate names are ownership inside Cargo, not new commands or persisted Work.
The largest mismatch is that shipping, SQL, definition resolution and account
policy still share the application compilation unit. More small leaf moves alone
cannot deliver the intended edit closure.

Next implement direction: finish the synchronous storage boundary with its data
owners, then definition resolution and provider/runtime separation. Besides the
edges below, `store/sqlite.rs` currently owns Claude window canonicalization and
legacy quota reconciliation through application configuration/account policy.
Move that policy to the account owner rather than putting it in shared models
or making storage depend on providers. Preserve historical alias handling:
select the newer observation, then the stricter limit at equal observation time,
and prefer the canonical name on an otherwise equal reading. Callers must receive
the same effective quotas after the move, including old stored rows; moving only
write-time normalization would change recovery. Keep one implementation.

SQL APIs return saved values and delivery receipts from one pinned reading;
the application combines them with observed connection/configuration facts.
Retain batched reads across Tasks and repositories: splitting presentation out
must not turn one reading into per-Task queries or lose external revision and
deadline invalidation. This requires no wire-shape or schema change by itself.

Root inventory belongs to developer build tooling, derived from Git rather than
saved as Work. A coordinated owner for the shared daemon is still to implement;
setting basedirs in a build client's environment alone cannot refresh it.
Unknown roots build with misses until a safe idle refresh. Failure to establish
idle state leaves the daemon alone. Do not add a runtime Session/Task dependency,
rustc-wrapper restart, scheduler or second daemon sharing its local cache.

Counterexamples to carry into implementation: a disconnected planning read still
retains uncertain/conflicting deliveries; a served watch notices ignored-config
changes and timed Session projection changes; historical quota aliases select the
same account; a new worktree building beside another never restarts its cache;
deleting the producer root still permits isolated source debugging. Preserve
native conversation identity, pending input, migration bytes and snapshot format.

`scripts/testing.md` and the benchmark README now point source debugging at
`--isolated-build` and name shared-server root upkeep as the remaining gap for
automatic cross-root reuse.

Next show an application edit rebuilding only its intended downstream closure,
an unchanged fresh-worktree library hit, correct-checkout execution and isolated
debugging recovery. Then compare full time/CPU/RSS, not only cache counters.
The recorded probe receipts do not yet establish that result. Demo and
review remain interactive before merge.

Before relocating the synchronous store, remove these application edges together:


1. `task_comments`, `task_ownership`, `planning_sync` and `planning_peers` read
   `planning_client::connected` inside SQL reads. Connection status is an observed
   configuration fact, not stored state. Command/read callers must acquire it
   before the pinned store reading and compose delivery presentation afterward;
   retain one transaction for each SQL reading and the same external revisions.
   This cannot be replaced by an unobserved file read inside the new crate.
2. `task_comments` and `children` call `linear_observe` for comment direction,
   revisions and rendering. Move shared comment syntax/value operations to the
   comment data owner; keep provider acquisition and outgoing effects above SQL.
3. `graph_inventory`/`task_work` import `ops::graph_process` records;
   `wave_lifecycle` persists `Operation` with file/provider effects in its impl;
   `github_people` persists `ops::people` records. Separate stored values from
   operation methods before moving them. Runtime Graph views remain outside the
   common conversation model.
4. `processes` reads `transport::current()` during insertion; `sessions` uses
   `observe::active/deadline` for dated projection. Command boundaries supply
   runtime inputs, and the served reading still owns deadline invalidation.
5. Async `run_sqlite` stays an attributed application adapter around synchronous
   SQL; replacing it with bare tokio spawning loses request diagnostics and
   observation inheritance. Keep command-owned write transactions.

Definitions resolution likewise still depends on observed file reads and
request-local environment suppression. Split those facts from transcript/OS
observation and settings resolution before moving graph/catalogue loading.
Provider credentials/account rotation and launch continuity follow after storage;
none of these gaps is filled by a catch-all core crate or callback interface.
