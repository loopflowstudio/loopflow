## Problem and demo

Loopflow can report a managed Codex account unavailable and launch with rejected
credentials even while another copy for that account works. Identity equality is
being used as evidence of usable access. Jack needs status and configured launches
to recover without another login, changing account policy, or losing history.

Demo: on Mini, `lf account codex --json` accepts the affected managed account and
reports live limits. A headless configured Codex Session then completes a small
turn; `lf -b session connect <session-id> --message 'Reply with RECOVERED.'` resumes
that same Session and native thread. No home relocation, logout, daemon restart,
or global isolation change occurs. Run the reverse credential scenario in a
fixture: a working native copy stays in place when its stored copy is rejected.
Root's coordinated installation and later cross-Machine continuation remain
separate acceptance, not something a source test establishes.

## Chosen architecture

Keep provider files authoritative for credentials, provider responses authoritative
for current access, and SQLite authoritative for account identity, route intent,
observations, and Session associations. No schema, wire DTO, persistent preferred
credential location, health cache, or second account representation is needed.

Replace identity-only Codex home selection with one bounded resolution operation
shared by status, readiness, activation, and reset preflight. Keep the raw one-home
Codex observation separate from managed selection so there is no recursive
`poll_account`/activation call. Its internal result carries the usable home and
the existing `SubscriptionUsage`; any credential snapshots stay private and
short-lived, never Debug output, errors, argv, or SQLite.

1. Preserve the caller's account and target home. Ordinary status prefers the
   matching native home; shared launches retain their actual command's native
   home; isolated launches retain the account profile. An explicit custom home
   must not accidentally be replaced by the ambient default.
2. Establish that a candidate belongs to the selected account using the existing
   expected-email and per-user-subject validation, before and after the provider
   observation. A same-email/different-subject copy is not a repair source.
3. Observe the preferred home first: account/read with refreshToken false, then
   live limits. Let Codex handle its ordinary refresh. After a definite auth
   rejection, permit one explicit managed refresh and re-observation before
   considering the other same-account copy. Success retains the preferred home;
   do not refresh both copies speculatively.
4. Only a definitive rejection authorizes trying the alternate copy for repair.
   Recognize the observed -32603/HTTP 401 Unauthorized shape as well as existing
   explicit auth markers. Use narrowly defined auth evidence; generic 403, 429,
   5xx, transport failure, malformed response, timeout, or unknown RPC errors
   remain unavailable. Never emit raw provider error text.
5. Observe the alternate through the same one-home path. Both rejected means
   reconnect the selected account. Any unresolved dependency means verification
   unavailable, with a retry diagnostic; it neither proves capacity nor revokes
   the account. A successful response with absent limits remains unknown capacity.

Status returns the successful observation without copying credentials between
homes. Cached status remains provider-free and makes no new account observations.
Readiness consumes the same resolution; token lease requirements for forwarding
still apply to the chosen credential. An explicit reset consumes once on the
resolved connection; no recovery operation retries the mutation.

At launch, retain the existing conversation home and install a verified alternate
only if the target's credential was rejected. This is a repair within existing
activation, not a switch of accounts or isolation mode. Reuse private atomic
installation and preservation; no operator-side credential editing is required.
The shared same-login early return becomes a verified decision for divergent
copies. Identical copies retain the existing cheap activation path: there is no
alternative to recover from, and normal provider authentication still applies.
An isolated route needs the equivalent repair at `launch_as` before its early
return, without changing its recorded home.

Before a replacement, prepare private durable preservation; failure to prepare
aborts installation. Never run the rejected native copy through
`save_back` over the known-working profile. Codex save-back when switching away
must use the same evidence for divergent same-account copies: retain a working
native update, retain a working profile over a rejected native copy, and preserve
both on unknown results. This removes the path that would recreate the bug at
the next account switch.

Hold the existing native lock through repair and spawn, following one documented
lock order with managed login locks. Snapshot candidates around provider work,
read refreshed bytes only after it finishes, and recheck identity and contents
before copying. A concurrent change invalidates the observation; re-resolve at
most once, then report unavailable without overwriting the newly observed copy.
Retain the actual displaced file, including refreshed native bytes.
Do not claim this makes uncooperative native writers take Loopflow locks: general
provider refresh coordination remains outside this hotfix.

For same-account replacement, extract only the existing directory-descriptor
exchange syscall primitive into `platform` and retain its Task-file caller. Stage
the verified credential privately on the target filesystem, sync it, then exchange
it with the target. Keep the displaced inode in private recovery storage even
after success: a native client may still write through an open descriptor. Do
not let temporary-file cleanup unlink it. Read back both sides; if the displaced
version differs from the rejected version or the installed version changed,
report a concurrent update and do not spawn on stale evidence or automatically
roll back over another write. Retain both versions for recovery. An unsupported
exchange leaves the target unchanged and reports a retryable installation
failure, never falls back to destructive rename. No global recovery scanner or
new selectable credential source is introduced. Existing unrelated credential
writes need not migrate to this primitive.

Bound the whole resolution to 60 seconds, retain the existing 15-second request
timeouts, and probe at most two homes with one explicit refresh each. A changed
credential retry consumes the same deadline. Drop/timeout must terminate the
owned probe process group. No background monitor, retry loop, browser, or daemon
restart is introduced. A working preferred credential never probes the alternate.

## Alternatives and failure boundary

- Always choose stored: reproduces the opposite failure when native has the valid
  refresh. File timestamps and JWT expiry also cannot prove server acceptance.
- Always refresh native and stop: already fails to establish usable access in
  the supplied case and still hides the stored copy.
- Change CODEX_HOME to the working profile: changes shared history/configuration
  placement and can make a resume appear empty. Rejected.
- Inject external tokens into every launch: introduces another auth lifecycle and
  harness-specific refresh handling. Rejected for this hotfix.
- Copy on every failure: risks destroying valid updates during an outage.
  Rejected. Recovery requires affirmative alternate success and target rejection.

Success is an ordinary status/launch/resume working without another sign-in.
The dangerous failure is a green status followed by a launch on the old credential,
or a delayed native refresh being lost during repair. The acceptance scenario must
cross both boundaries and test concurrent replacement, not only the resolver.

## Scope and deletions

`provider_account.rs`, `subscription.rs`, associated auth error handling if shared,
account status and reset consumers, `docs/subscriptions.md`, and regression tests.

`ops/task/file_save.rs` caller without changing Task-file behavior.

No Swift DTO change is planned.

Delete — do not maintain:

- Codex's unconditional native-by-identity branch in `credential_home`; retain
  the existing Claude semantics under their existing owner.
- Codex's divergent-copy same-login early exits in `activate` and unsafe
  identity-only overwrite in `save_back`; keep identical-copy fast paths and
  different-account switching behavior.
- The test assertion that an active identity alone determines the probe home
  (`the_active_account_is_probed_in_the_native_home`); replace it with observable
  accepted/rejected/unknown cases. Keep the rotated-native preservation test,
  adapting its provider fixture to prove that rotation is usable.
- The one-home `subscription::poll_codex` wrapper; managed callers now resolve
  through `codex_access`, while `codex_usage` remains the raw observation owner.
- The private syscall implementation in `ops/task/file_save.rs` moves to the
  shared platform primitive; do not retain two platform-specific implementations.
- The separate Codex window-validation traversal; the fallible window parser
  owns both validation and conversion, retaining absent limits as unknown.

These deletion targets are removed in the current diff; no predecessor path
remains to cut over.

Forbidden: another routing policy, account choice changes, clearing a home,
credential output, automatic logout/relogin, history reconstruction, daemon
termination, a status-only fix, a second durable credential-choice record, or
claiming installed success from fixtures. This task intentionally permits bounded
recovery between the two existing copies of one account; it adds no compatibility
path or third live credential store. Kept displaced bytes are preservation only,
not another candidate catalog.

Preserve LOO-625's scoped Wave configuration, LOO-312's onboarding decisions, and
LOO-661's Claude persistence/diagnostics. LOO-325's general refresh coordination
and LOO-540's account-command redesign remain unselected. The Infrastructure
objective is reliable work with bounded truthful recovery; the chapter has no
numeric target for this repair. Root owns release/install and cross-Machine proof.
