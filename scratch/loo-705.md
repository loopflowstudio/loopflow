# LOO-705: long-lived lf processes move onto the installed lf

Status: accepted for implementation (headless choice, 2026-11-02; see
`scratch/questions.md` for the assumptions Jack can overturn).

## The one judgement

Every launch of Loopflow work runs through **the entry**: `resolve_lf_binary()`
gives the install gate (`~/.lf-machine/install/gates/1/lf`, which re-execs the
selected artifact), the Desktop helper for app-started work, or `LF_BIN` in a
private Home. A long-lived lf is **superseded** when the entry no longer
dispatches to the build it runs: `installation::superseded(executable)`, the
one function behind the owner ending, the `lf resume` takeover and the
inventory `lf monitor rollover`, `lf doctor` and the post-promote report read.
Viewers judge nothing; they follow the owner's word. Same build means the same file after symlinks, or the same
bytes at two paths (Desktop's bundled lf and the installed CLI artifact). No
store read, no version numbers, no probe of the other process; an entry nobody
can resolve is not superseded.

Replacement from durable state, never negotiation: Jack rejected stable
cross-version APIs and old-peer support (wave memory, LOO-401). The durable
state is the Session's saved provider conversation; everything else is
reconstructible by resuming it.

## Three places, one operation

1. **The owner ends itself at a safe boundary.** `transport/lifetime.rs`
   already ends an owner whose executable file was removed or replaced once
   its Sessions wait for a person. Superseded joins removed and replaced. The
   owner sends its attached viewers `Moved { notice, successor }` where
   `successor` is the entry, then ends as before (agent stopped, exit
   recorded, `lf resume` reopens from provider history). Every change sends
   the successor: removed, replaced and superseded are three ways of noticing
   that a launch through the entry no longer runs this build, and the viewer's
   next move is the same for all three (third concept review, 2026-11-02;
   built the same day). One notice:
   "This Session's lf was {change}; reopening it as `lf resume <id>`", so the
   hint survives when the follow itself fails. A turn in progress finishes
   first, so nothing is cut off.
2. **Viewers follow.** A viewer told a `successor` re-runs its own invocation
   through it (`<entry> session resume <id>`), so a terminal, cmux pane or
   Desktop pane showing a Session lands on the installed lf without anyone
   typing. The viewer judges nothing itself; the owner already did.
3. **`lf resume` takes over.** Opening a Session whose running owner is not
   the build the entry launches now (canonical path differs and content
   differs) ends the owner the way the lifetime policy does and resumes the
   saved conversation through the entry. The takeover happens at the same
   boundary the owner uses: a superseded owner whose Sessions wait for a
   person is ended. One mid-turn that answers its socket is attached to
   instead, so the person watches the turn end, the owner ends itself and the
   viewer follows; one mid-turn that does not answer cannot be watched and
   cannot be trusted to report idle, so it is ended and the cut turn reported
   (concept review, 2026-11-02; implemented the same day). Same
   build: attach as today, whatever build the viewer itself is; an owner that
   does not answer its socket is still taken over (#1790). This moves the
   0.15.0 owners that predate the policy.

`lf monitor rollover` is (3) applied to every superseded owner: idle ones
move; a busy one that answers stays until its turn ends; a busy one that does
not answer is ended and reported, since its "turn in progress" is a claim it
can no longer prove (the 31 Oct 28 owners). Its "a terminal is attached" rule
goes: viewers follow.
Graph runners keep running; each step already launches through the entry.
`lf install` reports what still runs the previous lf and that it moves as it
goes idle or when resumed.

## Protocol note

`Response::Moved` gains `successor: Option<PathBuf>`. Serde reads a missing
`Option` field as `None`, so a 0.15.1 viewer attached to a newer owner prints
the notice and leaves; a newer viewer on an older owner sees no successor and
leaves the same way. New variants would break older viewers' parsing (the
`moved` variant did exactly that to 0.15.0); fields on existing variants do not.

## Inventory: where a long-lived lf gets its binary

Every launch goes through `resolve_lf_binary()`: Session owners
(`human_session::serve_locked`), Graph steps (`graph.rs`), agent-facing
`LF_BIN`/hook executables (`context_block`, `harness/context`), prepared Session
commands (`open.rs`) and `lf install`'s own relaunch. The function returns
`LF_BIN` only in a private Home, the app bundle's lf inside Desktop, else the
install gate. So on the main Machine no owner runs a development build; a
development viewer attaches to the installed owner. Long-lived kinds: Session
owner (ends at idle when superseded), Graph runner (never stopped; its next step
launches through the entry), Desktop helper (its own entry; a replaced bundle is
"replaced"), monitors and crons (fresh invocations through the entry).

## Prior decision this revisits

LOO-502 (Jack Heart, 2026-10-17) removed executable pinning, compatibility
probing and replacement viewers, accepting that existing processes fail
naturally and are retried. This Task (Jack, 2026-11-02) asks that `lf resume`
and idle owners move without hand intervention, so viewers now follow through
the entry. Pinning and probing stay removed.

## Concept review (2026-11-02, headless)

What a person does, the concepts they meet, and the APIs behind them, on one
screen: `scratch/concept-review.html`.

**Actions.** `lf install`; `lf resume <id>` (or a pane that shows a Session);
`lf monitor rollover`. **Concepts.** The entry (what a launch runs); an owner
is *superseded* when its entry no longer runs its build; a superseded owner
*ends at idle* and `lf resume` *takes it over*; viewers *follow* the entry.
**APIs.** `installation::superseded`/`launch_target`, `lifetime::Change`,
`human_session::attaches`/`end_owner`/`answering`, `Response::Moved.successor`,
`rollover::inventory`/`owner_disposition`.

Second pass (after realign, 2026-11-02): one direction, recorded in (3)
above. `lf resume` ended a superseded owner whatever it was doing and told the
person the turn was cut off, while the owner itself and rollover move only at
the idle boundary. "At a safe boundary" is the Task's accepted outcome, so the
takeover keeps it: watch a busy owner that answers, end one that cannot be
watched, and rollover answers the same way. No new concept; `answering` and
`owner_waits_for_person` already exist, and the "cut off" message survives
only for an owner nobody can watch. The design text also said a viewer runs
`<entry> session resume <id>`; it replays its own invocation, which keeps
flags and works for `lf resume <task>` and Desktop's prepared commands. The
rename class is out of scope above.

The first pass's three implement findings are done: the owner and the takeover
call `installation::superseded` (`entry_target` and `same_build` are private
to it) and the viewer's `follow` reruns the invocation without judging again
(compress 2026-11-02: its own check only made the "reopening" notice false for
Desktop's bundled viewer, whose entry is the bundle); the successor now comes
with every change, not only supersession (implement after the third review);
`follow` notes that a renamed command survives replay only as a Clap alias. The lifetime test's
next build now differs in bytes, since a byte-identical reinstall supersedes
nothing.

## Concept review, third pass (2026-11-02, headless)

Reviewed the accepted design against the branch after the second pass's
direction landed (`attaches` watches a busy owner that answers; rollover moves
a non-answering busy one with `turn_cut_off`). Those match the design.

**One direction the accepted outcome implies.** The Task says one path handles
every kind of version change, "app bundle" among them, and `lf resume` lands
you on the current lf with no hand work. The branch has two paths: a
*superseded* owner's viewers follow the entry; a *removed* or *replaced*
owner's viewers get a hint to type `lf resume <id>` and leave. The first pass
reasoned "nothing follows them", but the entry exists whatever became of the
owner's own file: Dev.app rebuilt (LOO-693's class) is *replaced* and its
entry is the rebuilt helper; a rebuilt `LF_BIN` build in a private Home is
*replaced* and its entry is the new file; an install artifact deleted under a
gate-launched owner is *removed* and the gate dispatches the next one. In each
case the person's next action is identical, so the distinction teaches nothing.
Only when the entry *is* the dead file (a worktree build viewing itself) does
the follow fail, and it fails loudly with the notice already printed. So:
`lifetime.rs` sends `successor = resolve_lf_binary().ok()` for every `Change`
and one notice; `Change` stays as the word in the log and notice. Deletes the
`(None, Some)`/`(None, None)` arms and the `then(Superseded)` conditional.
Settled by the accepted outcome; it iterates to implement, then realign.

**Known limits added at the end.** A Graph runner has the owner's store limit;
a pre-policy busy owner needs a second `lf resume`.

### Unresolved product choice (recorded, not blocking)

Unchanged from the second pass. Jack wrote "perhaps always, and at a minimum
when necessary". The branch does
the minimum: a superseded owner nobody views **ends** at idle and comes back on
`lf resume`; viewed Sessions come back live because their viewer follows;
`lf monitor rollover` moves idle ones live right now. If "always" is wanted,
rollover folds into `lf install` and stops being a thing to learn (the race
noted in `scratch/questions.md` still needs rollover to resume Sessions that
ended for supersession). Stakes are low: nothing pushes input to an idle
owner, so an ended Session and an idle one answer a comment identically on
their next turn; the difference is process presence, list state and provider
start-up on the next open. Default `end_detached_after` already ends unviewed
owners after 24h.

### Known limit, kept

An owner whose store a newer lf has advanced past its reader floor knows it is
superseded (`entry_target` reads files) but cannot read whether it is idle, so
it keeps judging and never ends on its own; `lf resume` and rollover still move
it from the new lf. Staged migrations give old readers ~30 days, so this needs
an owner older than that. The deeper fix, if the Oct 30 class recurs: the owner
judges idleness from the harness signals it writes itself (`fact_writer`)
instead of reading them back through `owner_waits_for_person`; the Graph
ancestry half of that predicate is the part that still needs the store.

### Known limits, same class

- A Graph runner is a long-lived lf on the old build too. Its steps launch
  through the entry, so the Task's proof ("the Graph takes its next step on
  the new lf") holds, but the runner's own store reads between steps fail if a
  migration advances past its floor; it dies with the step unrecorded. Same
  staged-migration window as the owner. GraphProcess already records the
  compiled graph and each step row, so a successor runner could reconstruct
  the cursor without new state if this class recurs; not scheduled.
- An owner from before this policy (the Oct 28 0.15.0 trees) mid-turn and
  answering is watched by `lf resume`, but never ends itself when the turn
  settles, so the pane stays on it. The next `lf resume` finds it idle and
  takes it over. One-time, transitional; rollover moves them in bulk.
