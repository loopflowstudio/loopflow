## Surviving design

Generated-output lifetime is independent of Task completion and source disposal.
Discovery follows Git ignore decisions and registered worktrees, including those
under ignored containers. Batched ignore queries avoid tracked-content filters.
Unregistered repositories hidden in ignored data trees remain a coverage limit.
SwiftPM package source is separate from architecture output; Cargo profiles can
be reclaimed separately. Only measured eligible candidates reach fresh checks.

One shared recovery lock, 30-minute run budget, bounded inspection and nonzero
partial-failure receipts make unattended failures visible. Installation copies
five files into a versioned machine directory, uses a clean environment and the
hourly :17 calendar job, and restores prior configuration/job on bootstrap failure.
The schedule never depends on a Task checkout. Native manual worktree pruning
retains its existing owner and tests.

Private usage history is bounded to 168 samples / 4 MiB / 256 roots and two minutes
per observation. Least recently attempted roots go first; growth compares the last
known measurement and its timestamp. Unknown measurements stay null. Retention and
content-type labels are independent; overlapping roots and APFS allocation cannot
be summed as exclusive physical use.

Native caps apply even with abundant space: uv 8 GiB per cache, sccache 10 GiB LRU,
Docker engine build cache 8 GiB. Native locks, recent/in-use records and reservations
can defer those limits. Registry-backed Docker images need 24h age and no container
reference; volumes, containers, unpublished images and remote/custom builders stay.

Package exclusion: `pyproject.toml` disables packaging; package CI archives only
`lf`; app bundling copies only `lf`; Swift resources name only Swift folders.
No product path enables this utility.

## Concept review — 2026-11-04

Outcome: nothing to change in the accepted model; no open product choice for
LOO-722. Jack Heart's accepted policies settle the rebuild cost, eligible owner
teardown, evidence retention, native caps and machine-only installation. The
existing README and disk-cleanup skill describe that experience accurately;
leave their guidance unchanged. No new implementation direction is proposed.

The interaction is preview → explicit machine install → hourly cleanup → inspect
the receipt and growth history. Its concepts map directly to the implementation:
`Candidate` names a disposable unit, `Activity` supplies current owner evidence,
outcome markers determine disposable-evidence retention, private configuration
holds reservations and caps, and receipts describe observations. `_reason` derives
eligibility; `_stop_owners` and `_clean` perform verified teardown and removal;
`_record_usage` retains bounded comparisons; `_schedule` installs the same runner.
No Task-completion state, persistent candidate lifecycle or second scheduled
cleaner is needed. Accounting labels describe content; they never grant deletion.

Normal path: an ignored, inactive build loses eligible output while source stays;
its next build recreates that output. Failure: an owner cannot be verified or
survives teardown, so the directory stays and the run reports failure. Recovery:
the next invocation obtains the released lock and rediscovers current eligibility,
without replaying a saved deletion list. If a process dies before writing its
receipt, timestamps and invocation evidence prevent an older receipt from being
presented as success. Source, durable history, saved evidence and reservations
survive every path; installed bytes and private policy survive checkout removal.

The consequential counterexample remains concurrent generation: cleanup can
remove eligible allocation and exit zero while free space falls. Therefore a
successful cycle is not the laptop outcome. Retain separate allocation, physical
free-space, shortfall and last-known growth observations; unknown coverage stays
unknown. The remaining proof is successive comparable scheduled observations
and prevention at recurring generators, not broader deletion authority. Unmarked
demo history remains protected while LOO-725 resolves its separate runtime model.

Review page: `scratch/concept-review.html`. Code, tests, schedule and installed
bytes are unchanged by this review; existing acceptance remains applicable.
