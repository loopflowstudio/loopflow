## What exists

The stable `scripts/disk-cleanup.sh` entry point launches a stdlib Python runner.
It shares verification recovery's nonblocking flock and resource-policy 64/32 GiB
thresholds. Generated-output retention falls from four hours to one hour below
64 GiB and fifteen minutes below 32 GiB; recovery restores normal retention.
Ignored, untracked roots anywhere below the source directory are measured and
sorted largest first, using the nearest owning checkout for Git checks. Discovery
skips symlinks, Git metadata and generated roots, with a 30-second/100,000-entry
bound and a visible partial failure. Cargo debug/release profiles can be reclaimed
separately when the whole target is retained. Global Xcode DerivedData contributes
project Build/Index.noindex directories and whole ModuleCache.noindex,
SDKStatCaches.noindex and CompilationCache.noindex directories; adjacent package
source survives repeated cycles even without Git metadata. Embedded Git checkouts
retain a candidate.

Open output and builders inside a checkout retain output; idle shell cwd alone
does not. Tracked content, symlink roots/ancestors, recent output, account history,
SQLite state and the newest regular backup per database remain protected.
Inspection runs again before removal. Direct builds newly racing that inspection
remain unsupported, as in the existing resource-recovery contract.

Candidate inspection has a 30-second limit, children at most two minutes, and
work a 30-minute budget. Timed-out child groups are killed and reaped; locks
release on death. Public `~/.local/bin/lf` owns native pruning with inherited LF
attribution stripped. Generated-output cleanup precedes native maintenance.
The receipt records candidate decisions, removed allocation, free-space delta,
shortfall and failures. Failed removals get no allocation credit. Log failures
allow independent reclamation but produce nonzero status; reconciliation moved
the final log write before receipt construction so its failure is included too.

Launchd installation targets the main checkout, uses a clean environment, runs
hourly at minute 17, preserves running jobs and restores the prior job after
bootstrap failure. Only the old marked cron entry is removed. Dry-run inventories
without deletion or native maintenance and preserves log history.

### Experience and model

Jack Heart's accepted outcome is an hourly mechanical cleanup that preserves
source, history and live output, reclaims idle generated output even in unfinished
work, and explains incomplete reclamation. Installation coherence stays in
LOO-723; upgrade-hook errors stay in LOO-724.

The interaction needs three concepts: a schedule, a disposable output candidate,
and an observation of a cleanup run. Task completion continues to authorize
native source/worktree pruning; it is not the lifecycle of generated output.
Pressure and eligibility are derived from current measurements, never durable
candidate states or a second Task lifecycle.

| Action | Concept | Existing branch API and ownership |
| --- | --- | --- |
| Preview reclaimable output | Measured candidate | `scripts/disk-cleanup.sh --dry-run` → `Candidate`, `_inventory`, `_reason`; no deletion or native maintenance |
| Reclaim now or hourly | Same cleanup operation | `scripts/disk-cleanup.sh [run]` → `Cleaner.run`; shared resource lock, fresh inspection, bounded subprocesses |
| Enable or remove scheduling | One launchd job | `scripts/disk-cleanup.sh install/uninstall` → `_schedule`; main-checkout path, clean environment, existing-job preservation |
| Explain what happened | Timestamped observation | JSON receipt plus text/removal logs; removed allocation, actual free-space delta, retained reasons, shortfall and failures |

The receipt is a replaceable observation, not a resumable workflow. A preview also
writes it; a skipped lock acquisition does not. Read `dry_run`, timestamps and
the actual invocation exit before attributing it to a scheduled cleanup. A failed
receipt write can leave the earlier receipt in place. Recovery needs fresh
inventory, not a saved deletion queue. Source/history and removal evidence must
survive; candidate eligibility deliberately changes on the next inspection.

### Proposed documentation clarification

Keep the current command examples and preservation guidance. Add this explanation
to the usage docs when the policy decision is settled:

> Read the receipt's `dry_run` and timestamps before using it as evidence for a
> scheduled run. Exit zero means the inspected cleanup completed; a positive
> `target_shortfall_bytes` still means free space is below the target. Retained
> output stays protected even when the target cannot be reached.

Add to the disk-cleanup skill's reporting guidance:

> Report remaining target shortfall separately from failures. Identify previews
> as previews. If the receipt is missing or predates this invocation, report the
> invocation's exit and log evidence without attributing the older receipt to it.

These clarify accepted measured/visible behavior using existing fields. They
require no new persistent records, CLI commands or cleanup owner. They remain
proposed text; this review does not edit implementation or installed instructions.

### Normal path, failure and recovery

- Normal: at 50 GiB free, an ignored debug profile idle for two hours is eligible
  under the draft one-hour tier, even beside a held release binary and unpublished
  source. Reaching 64 GiB restores four-hour retention for subsequent eligible
  candidates. Source and the held binary remain. The receipt distinguishes
  removed allocation from free-space change.
- Failure: activity inspection becomes unavailable or a child times out. Unknown
  activity stops deletion; child failure is visible and independent work can
  continue within the budget. Partial removal receives no allocation credit.
  Missing receipt output must not turn an older successful receipt into evidence
  of this invocation's success.
- Recovery: the process releases its kernel lock on exit/death; the next hourly
  invocation inventories again. A partially removed generated root is measured
  afresh. A failed launchd bootstrap restores the previous job where possible;
  an active job is left running. Installed-cycle proof remains delivery work.

Counterexample to accepting the draft unexamined: under 32 GiB free, returning
to a checkout after a twenty-minute pause can require a full rebuild. Repeated
rebuilds could recreate pressure faster than cleanup relieves it. Preservation
fixtures prove neither acceptable rebuild cost nor sustained capacity. Conversely,
requiring 24 hours for every recurring deletion could retain nearly all outputs
in daily use and fail Jack's requested improvement. Neither alternative is
established by the one-time sweep's substantial reclamation.
