## Design

Keep the existing receipt-backed promotion as the activation owner. On macOS an
existing release app makes the installation app-inclusive, even with CLI-only
requested. CLI-only remains useful on app-free Machines. The shell installer and
Rust stream installer acquire the complete signed bundle; direct partial promotion
adopts an existing matching bundle or refuses the new switch with the full-install
remedy. Never splice a new helper into an older signed bundle.

Freshness requires the public entry to resolve to the bundled helper, matching
candidate identity and successful store preflight, plus the release app's metadata
and executables. Equal marketing versions alone prove nothing. Scheduled installs
use exactly the same decision. Explicit install completes its own receipt-backed
promotion instead of returning success after requesting an asynchronous app update.
Sparkle's explicit bundled adoption continues through that same promotion owner.
Do not opportunistically adopt an arbitrary old app before choosing the stream.

Only the Desktop executable is quiesced/reopened for bundle replacement. Session
owners and Graphs keep their running images; existing idle rollover owns retirement.
Retain renamed bundles while processes still execute them, including during cleanup
and recovery. Preserve signed bundles, retained rollback bytes and receipt recovery.
No schema change, no helper routing fallback, no private-dev selection change.

Outcome: **design changed; next implement direction**, with no unresolved product

The consequential mismatch is two definitions of the installed app.
`install.rs::installed_app` follows the public CLI link, then the configured
location. `published.rs::{installs_app,applications_dir,install_release,promote_build}`
and `release/install.sh` choose the environment/default location before promotion.
`schedule_plist` carries `LF_INSTALL_DIR`, but not `LF_APPLICATIONS_DIR`.
For example, a public CLI pointing into `/Volumes/Tools/Loopflow.app` can be
updated by a schedule that supplies `/Applications/Loopflow.app` as an explicit
target. `include_installed_app` then cannot preserve the original location because
the artifacts already name a target. The old app can remain beside the new
selection. With CLI-only and no default app, acquisition instead omits the bundle
and raw promotion refuses the differing custom helper. This is a source-path
counterexample, not a claimed installed reproduction.

Implemented experience:

```sh
LF_APPLICATIONS_DIR=/Volumes/Tools lf install --preview  # initial destination
lf install                                              # update that installation
# The existing schedule updates the same bundle without the first command's env.
```

public `lf` entry when no destination is explicitly supplied. A custom app location
survives ordinary and scheduled updates. `LF_APPLICATIONS_DIR` still supplies an
explicit destination; `/Applications` is the default for initial setup.” Keep the
already-clear pairing, CLI-only and running-image guidance unchanged.

release freshness, main acquisition, promotion arguments and downloaded installer

the public link identifies the bundle. CLI-only cannot omit an existing linked
