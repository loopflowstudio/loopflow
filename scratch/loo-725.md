## Current implementation

- `PendingInput` retains queued bytes and suppresses writable-PTY polling until
  a 100 ms retry deadline. Retention attempts never wait on the store mutex or
  SQLite writer lock; other writers keep their original busy timeout. Changed
  failures log once; recovery resumes record-before-delivery. Poll deadlines round
  up to milliseconds.
- `owner_retention` replaces the boolean-only judgment across retirement,
  resume and rollover. Named facts distinguish native input, Graph, headless
  Run, live turn and missing Session. The watcher also reports output/store
  retention, reuses its connection and limits policy work to the two-second
  poll regardless of activity. Ending-confirmation errors share deduplication.
- Host-security pressure stops later verification suites and retains `not_run`
  receipts. Ordinary product failures still allow independent suites to run.
- `demo.md` requires a complete copied runtime in a private root outside build
  output, with private `LF_HOME` and copied `LF_BIN` for launches, child commands
  and teardown. It records exact owners and retains the root/history until
  verified teardown. These are lifecycle instructions; configured proof remains.

## Demo cleanup decision — open, 2026-11-04

The experience is to return to the same editable conversation after a rebuild,
then finish the demo without broken owners or lost history. Session identity
persists; its live owner holds the editor and pending requests. `PendingInput`
is transport machinery, not a new public conversation state.

| Action | Current API and required result |
| --- | --- |
| Type while storage is busy | `PendingInput` → `try_record_owner_input` → PTY: queue until retention commits; keep control responsive. |
| Detach, rebuild, return | `lf resume SESSION` and `owner_retention`: preserve the same editor/request and valid private runtime/store. |
| Finish the demo | Existing Session/process stop controls: confirm verified owners exited before reclaiming eligible runtime; preserve history. |
| Resume after teardown | `lf resume SESSION` in its private Machine: reopen the same saved history without replay; this cannot recreate a dead editor. |

`demo.md` puts the private Machine, repository and provider history inside the
runtime root. LOO-722's `scripts/disk_cleanup.py` selects whole roots under
`.lf-machine/demos` marked `.disposable-coding-demo` with
`disposable runtime; evidence stored elsewhere`. Marking this layout would delete
history; leaving it unmarked supplies no automatic reclamation. Directory placement,
idle owners, viewer closure, age and socket failure establish no eligibility.

**Demo/review must choose two parts of completion:**

1. Keep durable Machine/provider history at stable paths outside disposable
   runtime, or retain the complete unmarked fixture until explicit teardown.
   Neither choice permits deleting history.
2. Settle editable drafts/requests before completion, or permit an explicit
   demo-completion action declaring that input disposable. Until disposition,
   unresolved input retains its owner and files.

Jack Heart's stop-before-delete policy applies after eligibility. LOO-722 comment
`2693d72d` rejects drafts silently retaining eligible output forever; `9ad44189`
preserves history and assigns artifact windows. Neither defines completion of a
history-bearing demo. November 4 readback found no later LOO-725 disposition.
The safe interim assumption keeps complete unmarked fixtures intact; it is not
Jack's acceptance of indefinite retention.

If separation is selected, change demo instructions to create stable durable
Machine, repository and provider-history paths before launch, copy runtime
separately, record input disposition at completion, mark only eligible runtime,
and record same-Session reopening after teardown. This proposal grants no archival

Preservation counterexamples: killing an owner loses its editor/request even
with copied history; screenshots are not resumable history; moving Machine/provider

The configured walkthrough must cover typing, detach/rebuild/resume, the chosen
completion action, private launch/child/teardown routing, interrupted cleanup,
