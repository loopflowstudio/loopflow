LOO-822: five open choices

Reading live Session state and usage from provider transcripts. Read on November 10, 2026, while the second implement pass (67d35407) was running. That pass has already picked an answer to each of these; every section says which, so you can leave it or redirect it.

  1. Does history's Turn grow, or do readers return runs?
  2. Where do a raw conversation's rows go when it has no Session?
  3. Does this Task call the exit read, or only ship it?
  4. What cost does a Claude turn read from a transcript carry?
  5. Do raw conversations show in plain lf session list?
  6. Answering

What the five have in common

Two comments set the frame. From LOO-732: "Whatever reads transcripts must keep producing those same per-turn facts in the store, for bare and raw conversations too, since provider transcripts expire." From the LOO-819 plan: "the read at exit is what writes a bare run its per-turn usage and completion rows; without it the run costs the Task nothing on paper."

Said later the same day, in the Task conversation: "i dont think its true that we need to maintain more history than raw transcripts. its possible that we will want to, but its also true well likely want to expire our own data, or maybe send it elsewhere"

That moves the question underneath 2, 3 and 4. They all assume the store must hold a row for every turn before the transcript goes. If the transcript is the record for as long as the provider keeps it, the choice becomes who reads it:

This Task writes rows

  • LOO-732 keeps reading session_events only.
  • Needs the exit read, the rule that matches transcript runs against live rows, and somewhere for a raw conversation's rows.
  • The rows outlive the transcript, until lf's own expiry is decided (a backlog Task: "Decide how long captured Session history is kept").

Cost reads through the reader

  • LOO-732 asks the same per-harness reader for a conversation's runs, as lf session list does.
  • No exit read, no matching rule, no Session needed for raw conversations. Questions 2 and 3 mostly go away.
  • A PR's cost is answerable only while its transcripts exist. Keeping longer, or sending elsewhere, becomes one later decision in one place.

The pass in flight is building the first. Question 1 is about code shape and 5 about what a person sees; neither depends on this.

1. Does history's Turn grow, or do readers return runs?

The LOO-614 reader gives lf history show and search a Turn: it opens at every request, including ones lf or the harness injected. A live turn is something else: one agent run, from the request that woke the agent until it hands back (Claude to end_turn, Codex task_started to task_complete). One run can hold several Turns, for instance when input is queued mid-run. Usage, model and end time belong to the run.

Turn is on the wire: server_schema.json and Swift's RegistryQuery mirror it.

A. Turn gains end, model and usage

  • One type for history and live.
  • A wire change: Rust DTO, schema, fixtures, Swift.
  • A run spanning three requests has one usage figure and three Turns to put it on. Something has to say which one carries it.

B. Readers return runs

  • Turn stays as it is; nothing on the wire moves.
  • Two concepts in one module, with the relation between them to explain.
  • Matches what the providers record: usage per run.

The pass in flight is building B, in a looser form: claude.rs and codex.rs each return a Transcript { turns, runs } from one read. Run is internal (pub(crate)) with id, state, start, end, model, usage, the provider's receipt, duration_ms and errors. Runs sit beside turns; they don't contain them. The wire still carries SessionTurn for live readings and the unchanged Turn for history.

What to decide: whether "one reader, two lists" satisfies "Extend that reader; a second one beside it is the wrong shape", or whether you want a single type.

2. Where do a raw conversation's rows go when it has no Session?

A raw conversation is a plain claude or codex lf never launched. docs/sessions.md says: "Listing it creates no Session." Every session_events row belongs to a Session. The constraint asks for per-turn rows for raw conversations too. Those three can't all hold.

The same doc says a raw conversation open in a Task's checkout counts toward that Task. Today that is true only while lf can still read the transcript.

A. Observing creates a Session

  • Rows land while the transcript exists; nothing is lost.
  • A read becomes a write. Either lf session list or the server's watch creates Sessions for things nobody asked lf to manage.
  • The Session list grows with every plain claude run on the Machine, unless creation is narrowed (for example, only in a Task's checkout).
  • "Listing it creates no Session" changes in the docs.

B. Rows wait for adoption

  • A raw conversation becomes a Session the first time you resume it; its rows are written then, from whatever transcript is left.
  • Never resumed means never recorded. Once the provider deletes the transcript, the run cost the Task nothing on paper.
  • Reads stay reads. No change to what the Session list holds.

The pass in flight is on B by construction: transcript::facts::record takes a Session and writes only for one. Whether it runs when a raw conversation is adopted wasn't checked; the only caller seen so far is the owner's exit (question 3).

What to decide: how much a raw conversation's cost matters. If raw runs in a Task checkout are rare next to bare ones, B loses little. If they must show in cost per PR, something has to write while the transcript exists, and that something needs a Session or a place for rows without one.

3. Does this Task call the exit read, or only ship it?

The plan says the read at exit writes a bare run its rows. But "Bare launches go direct" is a later piece of the LOO-819 plan. Today a bare launch still runs under an owner with hooks, and the hooks already record its turns from the live stream. So right now the exit read has nothing missing to fill, except turns a recording gap dropped.

A. Call it on today's owner exit

  • The function runs in the product now, on every managed and bare exit.
  • It must not double-count turns hooks already wrote, so it carries a matching rule against live rows.
  • It also backfills turns lost to a recording gap, which nothing does today.
  • There is something to demo: kill the store mid-turn, exit, see the row.

B. Ship the function; "go direct" calls it

  • No overlap with live rows, so no matching rule yet.
  • Nothing calls it until the later piece lands. Tests cover it; the product doesn't.
  • The matching rule gets written anyway when managed Sessions start reading transcripts at turn boundaries.

The pass in flight is building A. harness/native_exit.rs settle now calls record_transcript_turns, best-effort (a failure logs a warning and the exit proceeds). The matching rule is in facts.rs: skip a run whose id the store already has, or whose time span falls inside a recorded completion, with a 2-second allowance. That time rule exists because live recording folds input queued mid-turn into one completion, where the transcript shows several runs.

What to decide: whether a time-window match against live rows is acceptable on every exit now. Its failure modes are a turn counted twice or a turn skipped, and both land in LOO-732's numbers.

4. What cost does a Claude turn read from a transcript carry?

Read on this Machine on November 10 (Claude 2.1.322, Codex 0.167.0):

Per-turn cost_usd and duration_api_ms exist only in Claude's live result. The transcript has a cost-state row with totals in 25 of the 60 newest transcripts (last row in 24; one resumed transcript had six, mid-file). Not established: whether it totals the process or the conversation, when Claude writes it, and why 35 had none.

LOO-732's direction since November 5 changes what this costs: "Unit is subscription quota, not dollars." Its prototype spreads an account's used quota over turns by a weight. For Codex the weight is computed from tokens. For Claude it is the cost_usd difference between a Session's consecutive usage rows, which are cumulative. Two consequences for rows read from a transcript: one with no cost weighs nothing in the quota figure, and a per-run row among cumulative ones looks like a counter reset. A token weight for Claude, as Codex already has, would work from a transcript for both providers and needs no cost at all.

LOO-732's standing decision is "cost is provider-authored and frozen, no price table", which rules out computing cost from tokens. Its measured coverage today is Claude cost_usd on 5,091 of 5,192 turns, all from the live stream. Once bare launches drop their hooks, every bare Claude run, which the plan assumes is mostly a Task agent's subagents, has no live stream.

A. Last turn carries the cost-state total

  • A bare run's dollars reach the Task when the row exists.
  • The figure is a total on a per-turn row; anything summing cost_usd per turn stays right only if exactly one row carries it.
  • Rests on three unknowns above. A resumed conversation with a conversation-wide total would count earlier spend twice.
  • About 4 in 10 transcripts had the row.

B. Cost stays absent

  • Rows are honest: tokens and model, no dollars, marked "source":"transcript".
  • Cost per PR undercounts every bare Claude run once hooks go. LOO-732 can show "tokens without cost" rather than a wrong sum.
  • Leaves room to add cost later from a better source without rewriting rows.

The pass in flight is building B. From facts.rs: "A transcript gives no cost: Claude's cost-state row is a total, not a turn's. Rows from here carry "source":"transcript" and no cost_usd."

What to decide: whether B's undercount is acceptable until someone establishes what cost-state totals. That check is small (one fresh conversation, one resumed, compare against the live result) and could be its own Task or part of LOO-732.

5. Do raw conversations show in plain lf session list?

Finding raw conversations means walking the process table for claude and codex with no lf or provider ancestor, then reading each transcript's tail.

$ lf session list
session_21fe…   active    Repository  Agent platform craft   turn running 2m14s
0199a213-81c0…  active    raw claude  ~/src/app              turn running 41s
session_675c…   detached  LOO-472     CI under five          last turn ended 3m ago · 41.2k in (38.0k cached) · 1.1k out

A. By default

  • "Every conversation on the Machine" is true of the plain command.
  • Rows that aren't Sessions sit among Sessions: no actions, no open_argv, a provider id where a Session id goes. Scripts reading --json meet a second row kind.
  • A provider started by another app (Paseo, Codex Desktop) lists as raw too.
  • Every list pays for the process walk, though the server caches it when running.

B. Behind a flag

  • The default list stays Sessions only; nothing existing changes.
  • A plain claude in a Task's checkout stays invisible unless you ask, which is the gap this Task set out to close.
  • Desktop needs its own answer either way.

The pass in flight has A, from the docs step: raw rows list for their checkout, marked raw, creating no Session. scratch/questions.md records them joining only an unfiltered, unpaged list, while docs/sessions.md also promises --task and --available. Those two disagree and one will need fixing.

This one interacts with question 2. If observing creates a Session (2A), raw rows become ordinary Session rows and most of this question disappears.

Answering

If the pass in flight has all five where you want them, nothing is needed: it is building 1B (side by side), 2B, 3A, 4B, 5A. To change any, a comment reaches the running step and later ones:

lf comment LOO-822 '1: … 2: … 3: … 4: … 5: …'

Or answer in the Task conversation and it gets written into scratch/loo-822.md under Open.

The two with the widest reach are 2 and 4. Both decide how much of a Task's spend survives once bare launches lose their hooks, and both are where the pass in flight chose the option that records less.
