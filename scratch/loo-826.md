# LOO-826: observers become server registrations

Stacked on LOO-821 (`session.boundary`, PR #1879), merged at 838e8828c.

## Design (built, November 11)

- **Boundary answers.** `session.boundary` answers `update` beside `steers`
  at every non-`stop` moment (`harness::task_updates::claim`, shared with the wake). The
  read is `harness::task_updates::read`: compared against the last recorded
  update, baseline on the first. A cached quiet revision avoids rebuilding
  history until Task facts change. The hook prints it after the steers.
- **Idle waking** (steered; findings in `questions.md`). Derived from the
  store, no server memory (`SqliteStore::idle_conversations`): managed
  Sessions on a live AgentProcess whose last native turn yielded
  (`session_activity`), reached by Codex's `processes.endpoint` or the Claude
  inbox key a managed boundary saved in `processes.inbox` (migration
  `agent_process_inbox`; the hook sends only the key path). `<pid>.json`
  beside the key names the socket and must still name the conversation. One
  server thread waits on `store::changes`, the `task_updates` revision and the
  newest steer `seq`; the first reading wakes too, so news recorded while no
  server ran arrives at start. Each idle conversation with news gets the pending steer batch (rendered into the Session's `cwd`,
  confirmed once sent) plus the Task update in one message, then
  `record_woken` marks it in a turn until its Stop. A turn end (`after_stop`)
  wakes its own Session. Claude: cross-session inbox; only managed launches
  set `crossSessionInbound: accept` (`native_args(…, managed)`). Codex:
  `turn/start` with `toolOutput` `loopflow_wake`.
- **One comment, one delivery.** `task_undirected_comments` drops comments
  with a `comment:<id>` steer, so Task updates carry runs, steps and
  non-direction comments; direction arrives once, as a steer.
- **Codex observation.** `after_stop` reads the thread's turns
  (`recover_history`). lf sends the first turn on the app-server before the
  client starts (`codex_connection::start_turn`). The app-server carries the
  launch's `LF_CONTEXT_DELIVERY`, and the hook prefers a thread's own binding,
  so `/new` and `/fork` threads reach lf's hooks. A client lf waits on checks
  its attachment every 2 s and stops when a mover replaces it.

Settled by the design: steers wake (question 1 (a) in `questions.md`).

## Concept review 3 direction (November 11): built

  `task_updates::read` before connecting; emits and claims after. Emitting

## Bare conversations

An interactive bare Claude or Codex launch keeps its turn hooks (LOO-821, while
an owner holds it), so its prompt boundary asks the server and
`task_updates::read` finds its Task through `session_membership`. It hears Task
updates at its next turn and is never woken (`idle_conversations` requires
`is_managed`); `a_bare_conversation_is_not_woken_and_hears_the_update_at_its_next_prompt`
in `wake`'s tests covers it. A headless bare run asks no server and hears
nothing. When interactive bare hooks go with the owner (questions.md, LOO-821
"Kept as built"), bare conversations lose this; that Task's design says so.
