# LOO-826: observers become server registrations

Stacked on LOO-821 (`session.boundary`, PR #1879), merged at 838e8828c.

## Design (built, November 11)

- **Boundary answers.** `session.boundary` answers `update` beside `steers`
  at every non-`stop` moment (`harness::task_updates::claim`, shared with the wake). The
  read is `harness::task_updates::read`: stateless, compared against the last
  recorded update, baseline on the first. The hook prints it after the steers.
- **Idle waking** (steered; findings in `questions.md`). Managed boundaries
  register the Session in server memory (`server/wake.rs`): Claude by the
  `inbox` paths the hook sends, Codex by the recorded app-server endpoint.
  Stop marks it idle. One server thread waits on `store::changes`, the
  `task_updates` revision and the newest steer `seq`, and wakes idle
  registrations with news: the pending steer batch (rendered as a hook would,
  `boundary::wake_steers`, confirmed once sent) plus the Task update, in one
  message. A turn end (`after_stop`) wakes its own Session. Claude:
  cross-session inbox; only managed launches set `crossSessionInbound: accept`
  (`native_args(…, managed)`). Codex: `turn/start` with `toolOutput`
  `loopflow_wake`.
- **One comment, one delivery.** `task_undirected_comments` drops comments
  with a `comment:<id>` steer, so Task updates carry runs, steps and
  non-direction comments; direction arrives once, as a steer.
- **Codex observation.** `after_stop` reads the thread's turns
  (`recover_history`). lf sends the first turn on the app-server before the
  client starts (`codex_connection::start_turn`). The app-server carries the
  launch's `LF_CONTEXT_DELIVERY`, and the hook prefers a thread's own binding,
  so `/new` and `/fork` threads reach lf's hooks. A client lf waits on checks
  its attachment every 2 s and stops when a mover replaces it.

## Next implement direction (concept review 2, November 11)

Registrations are server memory, so every server restart (`lf install`,
`refresh_after_promotion`) forgets every idle conversation until someone types
in it. The observers this replaces outlived a restart, and the steer asks for
waking "as today". Everything a registration holds is already recorded or
recordable, so make it derived state and delete the map:

- Who: managed Sessions (`work_source`) with a live AgentProcess.
- Idle: the recorded turn state (`session_activity`, written by
  `record_native_turn`); Claude also publishes `status: idle|busy` in
  `<config>/sessions/<pid>.json` (seen on this Machine, claude 2.1.322).
- Reach: Codex's `processes.endpoint` (already read by
  `session_connection`); Claude's inbox key path saved on its AgentProcess at
  the first managed boundary. The key path names the config dir and pid, so
  `<pid>.json` gives `messagingSocketPath` and `status`; no new secret is
  stored. Endpoint column or a new one is the implementer's call.
- A sent wake records the conversation as in a turn, so the next revision
  doesn't start a second Codex turn on it.

Then `wake::register`, `Registration`, `REGISTRATIONS` and the `idle` flag
go; the watcher reads candidates from the store on each revision. Test: a
server restarted between Stop and a Task comment still wakes the conversation.
`docs/sessions.md` keeps "If the server is down … next turn" only for
updates that land while it is down.

Settled by the design: steers wake (question 1 (a) in `questions.md`).
