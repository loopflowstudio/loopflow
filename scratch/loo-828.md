# LOO-828: identity in the context block, child-agent guidance

## Built

- Start and compact context blocks open with `This Session: <id>` and, when the
  Session has exactly one Task, `This Session's Task: <identifier> "<title>"`.
  Tool boundaries stay steers-only. The hook (`lf::commands::context::session_identity`)
  renders the lines into the steer prefix from the `LF_PROVIDER_CONTEXT` adapter
  every native launch installs; a store read failure drops only the Task line.
- Docs: `LOOPFLOW.md` rename line and `work` `--session` line point at the
  context block; `work` gains `## Child agents`; `docs/agent-api.md` gains
  `## Run a child agent`; `docs/work.md` updated. Prompt goldens regenerated.

## Settled

- Placement: `work` guidance, not `LOOPFLOW.md`. Jack, LOO-821 conversation:
  "there is supposed to be a whole set of lf docs on task and work orchestration
  that you get if youre doing the work model" / "but you dont get if you are
  doing \"bare lf\"".
- "I think we should encourage using lf for subagents, but not forbid local
  subagents" and "using lf graphs and skills specifically, and/or writing new
  skills into .lf/skills as necessary" are both in `## Child agents`.
- Directing an `lf -b` child: no way today, running or finished. QA run:
  `lf -b resume <id> --message` on a finished `lf -b :` child fails with
  "is a Run (finished); `lf resume` takes only Sessions". Docs now say to start
  another child whose brief carries the first one's result.
- Task conversation: "lg2m ship it".

## Concept review (2026-11-11)

The two pieces line up with the work as it is now: a Session's identity is
something lf knows and shows at start, and running a child is `lf` work that
loads with the `work` guidance. Every command the guidance names exists in the
installed `lf` (`lf task steer`, `lf task wait`, `lf session list --interactive`,
`lf -b resume --message`). No change in direction; nothing to add before ship.

QA found `lf -b resume` refuses headless children, so the continuation
lookup is gone from the docs; printing the child's ID on exit no longer matters
for them.

## Open

- PR #1879 (LOO-821) decides which launches keep which hooks. If a launch keeps
  the context hook but loses `LF_PROVIDER_CONTEXT`, it loses the identity line.
- Continuing a headless child would need `lf resume` to accept finished Runs
  (refused since #1767). Product call, not this PR.
- Pre-existing: `lf __context-block` exits 1 with "file is not a database" when
  the store is unreadable (installed lf does the same), so the hook fails the
  turn instead of recording a gap.
- Bare `lf <skill>` in a Task checkout: does it get the `work` guidance, and
  should it follow LOO-821's managed rule?
- `LOOPFLOW.md` now names only the context block as the ID source. A launch
  that shows no identity line (no context hook, or no `LF_PROVIDER_CONTEXT`)
  leaves the rename instruction with nothing to read; `LF_AGENT_CALLER` still
  holds the ID. Whether the line mentions it as a fallback is open.
