Next experiment

Best next measurement: isolate the real Session event-recording API on its retained connection, with the same event rate and output/receipt checks, and profile preparation separately from execution. Compare ordinary preparation with reuse of the same prepared INSERT before considering schema changes. The active profile points to repeated trigger compilation; the present fixture writes directly, so it cannot establish a production-writer speedup. That new workload needs its own frozen baseline and alternating A/B runs.

Use this exact observer harness for a smaller alternating A/B experiment that makes an already-selected native Turn context read-only while retaining provider fencing and selection writes. The target is the unconditional write transaction, not TaskUpdates’ 8-step revision check. Keep a change only if its CPU improvement clears these ranges and delivery/retry/lifetime outputs hold. Do not use the 25.2% VM reduction as a promised CPU win.

For a radical reduction in installed CPU, the next separate baseline should exercise the server’s actual status/activity subscriptions with unrelated active Sessions, plus duplicate observer admission and cancellation/churn. The current settled-loop costs do not attribute the installed server’s reported 258% snapshot. Startup/catch-up CPU in the raw receipts includes late Task binding and initial delivery, so it is not a production startup benchmark. No shared-observer architecture is justified by this baseline alone.
