A terminal in your pocket, execution on your Machine

Architecture research for Jack Heart · 2026-11-03 · No Task selected · Checkout 2bc29a72e0

Recommended architecture: a native Swift terminal connects over host-installed Tailscale to a private Loopflow Machine service. The service runs independently of Desktop and exposes existing Rust operations and Session attachments. Execution remains in separate owners. A future public hub receives webhooks and can become an explicitly authorized client of that same Machine boundary.

Jack selected native Swift, a terminal as the core experience, host Tailscale and no custom relay. Jack requested automatic setup and architectural room for an optional hub, without building hub features now. HTTPS/WSS, the pairing protocol, service packaging and the precise screen design below remain recommendations to validate.

The server question, answered

The proposed server belongs to a Machine: one OS account and Loopflow data directory. It can run on the Mac used for Desktop or on a remote host without Desktop. Two accounts on one computer can be two Machines. A network address is a route to that authority, not its identity. Current Machine contract

Today, Desktop calls Rust through a local library and launches CLI operations. Its own Unix socket automates the GUI and dies with the app. Detached Session owners already retain execution; remote CLI commands already run through SSH. There is no general network Machine API in this checkout. Local query adapter, Desktop socket, Session transport

This restores a responsibility of lfd. Standalone hosting, launchd, mobile pairing and a thin command adapter have all existed before. The earlier deletions show maintenance and ownership difficulties alongside sustained product intent. The difference to prove this time is that the network frontend can disappear without changing the identity or lifetime of running work. Naming it “thin” proves nothing. Historical evidence

1. Give each component a clear owner

Component Owns Boundary to preserve
iPhone / iPad Terminal presentation, navigation, local selection and scroll position, paired credential An attachment does not create a new provider conversation.
Desktop / CLI Local interaction and device-specific layout Desktop need not run for phone access; local clients can keep current Rust paths initially.
Machine service — proposed Authentication, protocol connections and command admission Calls existing operations; no parallel Task or Graph engine. Durable receipts belong in Machine-owned storage.
Existing Rust operations and store Local records and execution facts; provider synchronization Planning intent keeps its configured provider/journal authority.
Session owners and Graph runners Their actual execution, provider identity, PTYs and retained output Separate supervision from the network frontend must be proved.
Optional hub — future Verified event inbox, trigger configuration, dispatch receipts May request authorized work; does not become the Machine database or terminal relay.

The hub can begin as an inbox, then gain an explicit execution grant. It dispatches an existing Loopflow operation to one named Machine; that Machine's Graph runner chooses the steps. Event refresh may fan out. Execution must not. Current Task claims deliberately tolerate disagreement and preserve local work; they are not a distributed lock. Offline status does not authorize another Machine to take over. Authority research, ownership implementation

For a future deployment, the Machine initiates an outbound authenticated connection to the public hub. Webhook events and scoped requests travel back over that connection. Direct phone traffic still uses Tailscale. This avoids requiring the hub to join each tailnet. Paseo provides a useful precedent for separating enrollment from execution permission; Loopflow should retain its own Graph model. Paseo security

2. Define survival before installation

What happens Proposed behavior Qualification
Phone disconnects or backgrounds Work continues; phone later reattaches iOS background networking is not an always-on connection.
Desktop quits Installed service and execution continue Desktop-provided tools may become unavailable.
Machine service restarts Connections drop; execution continues Not yet proved under either installed supervisor.
Service or app updates Negotiate compatible protocols; retain busy owners Executables, schema reader floors and owner versions all matter.
Mac user logs out Personal LaunchAgent stops Unattended hosting is a separate install mode.
Host sleeps Execution suspends; network requests can time out Tailscale does not make a sleeping host available.
Host reboots Old processes are gone; reconcile saved history Resuming a conversation must not replay an interrupted submission.

The important discovery: today's owners call setsid(), but that does not escape a systemd service's cgroup. A naïve Linux service restart would kill its supposedly detached children. Independent execution units are one candidate solution. macOS requires a separate launchd/logout/update experiment. Lifecycle research, systemd process termination

Personal Mac hosting can use a user LaunchAgent managed through SMAppService. Standalone installation can use the same implementation without a Desktop UI. Linux user services with lingering are a practical always-on option. A Mac that must recover before login needs both a compatible Loopflow installation and an appropriate Tailscale variant; ordinary Mac Tailscale GUI variants do not run before login. Apple registration, Tailscale variants

Credential access, PATH and browser/computer tools must be tested under the installed service account. A healthy listener does not prove an agent can authenticate or use a tool supplied by a closed application. Existing detached-session expiry and owner rollover policies remain relevant; this design does not promise immortal processes.

3. Share the Session, keep presentation local

Open to observe. Choose “Use here” to take control. Opening a phone, rotating it or showing its keyboard must not resize Desktop's TUI. Loopflow's existing wire already distinguishes input control from geometry/color ownership and supports passive observation. One PTY still has one canonical geometry. A passive phone pans or scales that screen; taking geometry causes the program to reflow for everyone. Shared-session research

Keep tabs, split ratios, font size, zoom, search and scroll position on each device. Reconnection must not steal control from a device that took over more recently. Input accepted before takeover may execute; takeover cannot retract bytes already delivered.

There must also be one terminal-query responder. Current code uses the headless owner when no input controller exists and the controlling renderer otherwise, even though geometry can belong elsewhere. Prefer a stable host responder if its emulation coverage is sufficient; otherwise make responder election explicit. Two renderers must never both answer a device query or replay old responses. Output processing

Native Swift provides the existing open-Task list. Tapping a Task opens its Session terminal, with usable, editable input. No intermediate Task details, changes or checks screen is required. A separate native composer is outside the minimum scope. Input claims and geometry still require a protocol decision.

4. Three recovery contracts, not one

Stream Current foundation Remote contract to establish
Work state Watches emit complete changed readings Fresh authoritative snapshot plus ordered updates; label cached data. Current store revisions are not an event replay log.
Terminal output Per-viewer byte resume: 60 seconds, 1 MiB spool Resume only within the same stream generation and bounds; otherwise install a fresh screen snapshot.
Semantic commands Existing operation-specific behavior Durable request identity, acceptance/result lookup and explicit outcome-unknown state.

Terminal snapshots currently omit images and bound retained history. A fresh screen is not a complete activity transcript. An interrupted socket says nothing definitive about whether a command ran. Transport contract

For semantic actions such as starting work, persist request identity and reconcile it to the accepted Process/Session. Reusing a request ID with different content must fail. Acceptance deduplication still does not guarantee exactly-once arbitrary external side effects; crashes before or after dispatch need recoverable admission and outcome reconciliation.

Never automatically resend raw keys, paste or Enter after uncertainty. Terminal input has no general operation result to query. Preserve the last screen visibly as stale, reacquire attachment and control, then let the person decide what to type. Backpressure must disconnect a slow viewer without blocking execution or Desktop. Recovery research

5. Choose the application contract before the carrier

Use two logical surfaces: typed Work operations/subscriptions and Session attachment/control/output. Reuse existing Rust operations; do not publish arbitrary CLI argv as the permanent application contract. The typed write surface still needs an inventory of missing mobile operations. A generic argv adapter already existed in lfd's history.

Recommended first transport experiment: HTTPS/WSS through host Tailscale Serve. It fits native app networking and ordinary Mac Tailscale installations. Compare the same operations over SSH before making the transport commitment. SSH can carry an application protocol and connect to a persistent server; it does not imply a serverless design. WezTerm multiplexing

Handshake on Machine identity, API major/minor or equivalent compatibility range, and capabilities before attachment. Negotiate supported operations rather than relying on matching app build numbers. The phone, gateway and still-running owners can be three versions. Define that policy before the first independent mobile release. Exact compatibility duration remains open. Protocol research

Rex's control/data separation, bootstrap and sequenced events, explicit ownership and scoped terminal connection tickets are the closest API reference. Borrow the contract patterns; retain Loopflow identities and behavior. Public documentation does not prove a complete reusable terminal wire implementation or hands-on iOS experience. Rex API

6. Automatic setup with explicit trust

Enable phone access → scan once → reconnect automatically. The host detects its installed Tailscale variant, signed-in state, available private Serve endpoint and running Machine. The phone validates the actual connection; host readiness alone cannot prove phone reachability.

Proposed QR: endpoint, expected Machine ID, protocol version and a short-lived single-use pairing ticket. Exchange it for a revocable per-phone credential stored in Keychain. No tailnet admin key, provider credential or permanent bearer credential in the QR. Revoking access closes active streams as well as rejecting future requests.

Tailscale controls network reachability; application pairing controls access to a particular Machine. Serve's identity headers are useful context but do not isolate a loopback backend from other local OS users. Require application authentication there too. Prefer a dedicated private Serve port, preserve unrelated routes, and never enable Funnel for phone access. Serve/Funnel exposure applies to a whole port. Trust/setup research, Serve, Funnel

Automatic setup cannot silently complete SSO, grant VPN consent, change organizational policy or wake a host. Tailscale offers iOS Shortcuts device discovery, but that does not establish a direct in-process enumeration API for Loopflow. QR handoff keeps setup independent of that question. Ordinary SSH still needs server/key setup; Tailscale SSH server support excludes the usual Mac GUI variants. Shortcuts, Tailscale SSH

7. Make the terminal excellent on an actual phone

Keep terminal rendering independent of transport. The host owns the PTY; the Swift app receives bytes and sends input. Existing Loopflow GhosttyKit is macOS-only. Upstream libghostty-vt building for iOS does not itself supply UIKit input and Metal rendering, and its API remains in development. Swift manifest, Ghostty library status

Start a device spike with Lakr233/libghostty-spm: it offers host-managed I/O, native wrappers and UIKit input. Compare Termini's smaller custom-transport controller; study Rootshell and gterm for complete mobile interaction. Use SwiftTerm as an accessibility/input benchmark. These are candidates, not a measured ranking. Native-mobile research

Prove IME marked text, dictation, multiline paste, hardware keys, selection, VoiceOver, keyboard resizing and hidden-surface power behavior. Rendering a demo is insufficient. A phone file path is not a remote file attachment; defer transfer or implement it explicitly. Preserve renderer reply suppression during replay.

The MVP remains useful entirely in the foreground. Background completion alerts require a separate APNs delivery design, possibly deployed beside the future hub. No background socket promise is implied. The selected prototype opens existing Tasks directly into editable Session terminals. Wave navigation, shells and other pane types are outside the MVP. The HTML simulates behavior and does not establish native-device quality. Selected MVP prototype

Prove these boundaries first

  1. Two clients, one Session. Phone observes, takes control, opens its keyboard and returns control. One provider, one geometry, one query responder.
  2. Kill the frontend during work. Same provider and Graph continue under real launchd and systemd. Reconnect to the same identities.
  3. Lose the reply after submission. Semantic command lookup finds its original acceptance. Raw input is never silently replayed. Reconnect beyond terminal retention gets a fresh screen.
  4. Clean-host pairing. Ordinary Mac Tailscale variants and Linux; existing Serve routes remain intact. Test cellular access, logout, certificate renewal and revocation.
  5. Update with a busy owner. Mobile/gateway/owner version skew and schema floors remain explicit. No forced duplicate conversation.
  6. Paper-test the future hub. Duplicate event, offline Machine, changed owner and lost receipt. Fixed execution recipient and ordinary transfer preserve authority. Build no hub feature to run this exercise.

Decisions still open

  1. First carrier to prototype: a. HTTPS/WSS + Serve (recommended); b. SSH carrying the same application operations. Host Tailscale is already selected.
  2. Initial hosting promise: a. personal Mac while logged in plus always-on Linux; b. also unattended Mac before login, requiring separate packaging and credential proof.
  3. Session input handoff and geometry when the phone opens a Task viewed on Desktop. Existing open Tasks → editable Session is selected.
  4. First-release alerts: a. foreground only; b. background push, with a separately scoped provider service. The future webhook hub remains optional either way.
