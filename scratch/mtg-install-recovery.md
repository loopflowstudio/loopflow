## Causal chain

1. **Why did previously working MTG commands/hooks fail?** They executed 0.14.3 against a database migrated to 0.14.4. This is directly visible in MTG-135/137 errors and the pre-restart process environments. The new binary could read the database; the old one could not.
2. **Why did installing the new binary not update those calls?** Provider launches inherit an immutable `LF_BIN`; hook declarations also retain executable paths. Released `os_process::resolve_lf_binary` prioritizes that variable, and `installation::dispatch_default_cli` honors it unconditionally. Reattachment alone can preserve a live provider's original environment. Actual native exit/relaunch refreshed the MTG clients.
3. **Why could promotion succeed with those older clients open?** Candidate preflight validates the candidate schema and retained Flow definitions. Its `executable_compatibility` field means executable Flow references, not compatibility of every running executable. In `lf/commands/install.rs`, `PromotionPreviewWire.active_runs` is an intentionally empty legacy field (`[String; 0]`); the source explicitly says promotion no longer decides from live Run state. The observed receipt says compatible/references=8 and active_runs=[], which must not be read as proof that no old clients were running. This explains the coverage gap; it does not establish that the right repair is to refuse every upgrade while a client exists.
4. **Why did even the new CLI initially fail in Manabot?** PR #1578 (commit `463c5803a2`) introduced Machine-scoped Git locators. Both `repository/location.rs::reconnect_current` and `store/sqlite/repositories.rs::ensure_repository_in` reject a retained repository without one. The existing Manabot database mapping was already at the new address, but its Git directory had not been enrolled. Supported enrollment immediately restored reads. The directory move is historical context, not proof that a fresh move caused today's failure.
5. **Why did acceptance miss this?** LOO-495 explicitly retained installed acceptance after release; its notes said 0.14.4 was published but not installed because active clients remained. Its tests covered new/enrolled repository relocation and rejected uncertain identity; they did not establish that upgrading this existing locatorless checkout preserved ordinary reads. LOO-502's implementation initially deferred real released-binary upgrade/live-provider acceptance too. Unit success and Flow compilation were insufficient evidence for the mixed-version, already-running installation.

## Prevention and remaining proof

- **LOO-502, already running:** new commands/hooks should resolve through the installed compatible entry before reading the shared store, while preserving explicit compatible development/private-home selection and caller/Session identity. Stable hooks remove future immutable-path pinning. Pre-fix native clients still need the verified same-Session relaunch; an already-running old process cannot acquire new compiled migrations. Require a real old-release → new-release test with an open Session, hooks, nested commands and retained history/pending steers. Changing immutable files underneath live processes is not the repair.
- **LOO-495, same unfinished outcome:** complete upgrade acceptance for existing registered repositories with no locator. Adapt using established identity and Git evidence rather than requiring routine manual enrollment. Preserve distinct clones, reused paths, symlink aliases and unknown/offline locations; do not blindly bind every matching remote. A real populated released-store fixture must survive install and ordinary CLI/Desktop reads without manual bind.
- **Proportional installation coverage:** prove the entire upgrade sequence with existing clients and preexisting repository metadata. An empty `active_runs` legacy field must never serve as liveness evidence. Preserve data, never weaken unknown-migration validation, and avoid duplicate execution or replaying effects. Whether running Flow processes need an explicit compatible handoff remains an acceptance question, not solved merely by changing hooks.
- **MTG-117:** retain the existing unresolved-exit evidence separately; determine whether a supported reconciliation can recover that legacy reservation without inventing an observed exit. Do not attribute it to this installation without further evidence.

The current repair restores access by supported enrollment and same-conversation native relaunch. It does not install the pending LOO-502 source changes or establish seamless future upgrades.
