Felt-performance metrics

A proposal for what to measure on Desktop and the phone, what exists today, and what to change. Written 2026-11-11.

What "fast" means here

A wait starts at the person's input (or the process starting) and ends when the thing they wanted is on screen and takes input. Three rules follow, taken from how the two frameworks studied measure themselves:

  • End at a named, usable point, not at "the model changed". Desktop's signposts end when a view observes a change; its own benchmark README says that does "not prove completed layout or on-screen presentation". Usable is: the result is drawn, and nothing the person needs is still outstanding.
  • Log wall time beside CPU time. A main thread blocked on the socket looks like a fast frame unless both are recorded (rune measured 263 ms wall against 3 ms CPU for one such case).
  • Gate on counts, report on times. Counts (rows built, readings applied, frames drawn at rest) do not flake; times go in a per-commit report with medians. Exact's rule: a count "cannot flake the way a timer does".

What is wrong with the current setup

  • Nothing reads the numbers. Desktop has signposts, a launch journal, a vitals heartbeat and a 16-scenario opt-in test suite. CI runs one pytest that checks the benchmark script's checkout handling, not a timing. A person has to run the scripts.
  • Two documented endpoints are never written. usable is marked only by tests, so timings.py's 1000 ms budget column is empty; cold_start begins and never ends.
  • The endpoints are proxies. Most intervals end "after commit", which the code itself calls "a scheduling proxy, not a render or compositor completion fence".
  • The phone had no timing code. It now logs four waits (commit ios: time the waits a person feels…); they end when bytes are handed to the terminal, one frame short of drawn.
  • The October 7 retirement still stands — "retires arbitrary numeric performance targets, soak requirements and deeper optimization while the product surface changes". This proposal reports numbers; it does not bring back acceptance gates.

Principles worth taking from rune and Exact

Both get their speed from doing less per update, not from a faster renderer. The parts that depend on owning the renderer (glyph atlases, instance buffers, precompiled shaders) do not transfer; libghostty already does the equivalent for the terminal.

Next steps, in order

  1. Close the two dead endpoints on Desktop: mark usable in production and end cold_start; emit hierarchy_interaction for filter and repository changes. Small, and it makes the existing reports true.
  2. One report, both apps. A script that reads the studio.loopflow perf log lines from a run (Desktop, Simulator or phone) and prints the table above with medians over 7 runs after one warm-up, wall and CPU side by side.
  3. A driver agents can use. An env-gated listener in each app with tree, tap, type, screenshot and settle, where settle waits on the same outstanding-work ledger that defines usable. This replaces OCR'd bitmaps and my coordinate clicking in the Simulator.
  4. Frame pacing. A display-link histogram during scripted scrolls, on a real phone and a real display; the Simulator's deadlines are not trustworthy.
  5. Then optimise, starting with whichever wait the report shows is furthest from its target. The phone's first live load (about 10 s) is the obvious first suspect: the Machine answers the same read in 2.8 s from the command line.

Open questions

  • Are the targets right? They are borrowed (rune: first frame p50 ≤ 150 ms, event → frame p95 ≤ 16.7 ms, key → photon p95 ≤ 35 ms; Exact: cold start to interactive 100 ms p50) and loosened where a network hop is unavoidable.
  • Should any count become a blocking check, given numeric acceptance was retired on October 7?
  • Where should the per-commit report live so that someone reads it?
