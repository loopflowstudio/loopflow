# LOO-1081 · Run a Task on Modal

**Done when** a Linear-backed Task runs its Graph on a fresh Modal Machine with the caller’s portable settings and a usable harness. The sandbox uses a small idle floor and quotes and caps cover peak compute. Giving it back requires no manual Git commit or SQLite edit. Collected history, transcripts and recorded usage remain available in work-scoped CLI and Desktop reports after abrupt loss. Lost sandboxes settle without a force flag and disappear from default live Machine listings.

LOO-1083 owns the server-routed Task workspace across CLI, Desktop and Mobile. LOO-1084 owns cross-Machine steering and status. The Task scope steer says “Do NOT build §4 in LOO-1081,” referring to the earlier remote-workspace section.

## 1. Built · Modal admission and container install

- Modal defaults to a `0.125` physical core and `128 MiB` request with burst ceilings. `--reserved` pins the request to the ceiling. The pinned 1.6.2 SDK sends `125/4000` millicores and `128/16384` MiB for 8 vCPU / 16 GiB burst and `4000/4000` and `16384/16384` when reserved. Both quote the $0.95184/h ceiling. New Modal declarations store the sizing mode, older ones default to burst on admission, and historical rentals without a recorded mode keep their original hardware and cost.
- `cargo test -p loopflow --test integration machine_commands::modal_ondemand_list_records_the_sizing_mode_before_any_rental -- --exact` passed on the synced checkout with the declaration fix. The CLI round trip reported both `burst` and `reserved` before any rental started.
- Jack Heart’s billing steer: “Billing data point: actual Modal dashboard usage was $1.65 vs ~$1.78 from lf fixed uptime math ($0.95184/h across modal-1..6), confirming lf currently sends --vcpus/--memory-gb as a full request floor rather than burst-only limits.”
- The caller resolves the matching Linux build before remote GitHub login. Release archives are checksum-verified, packaged dev builds carry the package run ID, and clean source builds can look up their commit. `LF_RENT_LINUX_BIN` installs a private executable and a non-login SSH wrapper targeting `~/.lf-dev`. The first live Modal trial hit `sudo: The "no new privileges" flag is set, which prevents sudo from running as root.` Docker had root. The rootless retry served over SSH in 53.9s. [Live QA](qa.html)
- The shared SSH environment includes both rental install directories. The non-login SSH environment fixture passed for Daytona’s root account and the other providers’ lf account.
- Without a systemd user bus, installation starts the selected CLI’s detached server and safely replaces superseded servers. Missing cron leaves updates unscheduled. Promotion can inspect a v0.15.1 store before migration.

## 4. Abrupt loss and recovery

Jack Heart: “we need some way to capture session history / usage data for analytics for sandboxes that we lose acces to”

### Built · Collection and transcript search

- The caller’s server copies changed Sessions and open transcripts over SSH while the sandbox runs, including when provider API credentials are absent. A clean return revisits the whole rental window for late writes. Copies live in `machine_records` and `<home>/machines/<origin>/runs`. Live QA saw copies arrive within about a minute. After provider-side termination, `lf session list`, the transcript by ID, and usage by ID could still read the records. Automatic settlement worked. [Live QA](qa.html)
- The preceding implementation pass landed transcript search in `4185bb97ed`. `lf session history search` reads copies beside local results, uses origin input time, matches Task, Project and Wave, and returns an optional `SessionOrigin`. It preserves local hit order and spends the remaining limit on copied hits. The offline CLI fixture `machine_commands::a_lost_rentals_transcript_and_usage_survive_on_its_collecting_machine` passed at that commit, including exclusion from a later window. `cargo fmt --all` and `cargo clippy --all-targets -- -D warnings` also passed then.
- In a synthetic search fixture with 10,000 Tasks and 100,000 each of copied turns and transcript rows, `EXPLAIN QUERY PLAN` used `machine_record_input_time`, `machine_record_input_task` and `machine_record_session` before and after `ANALYZE`. Warm indexed SQL after `ANALYZE` took 0.17 ms for 100 windowed rows and 0.07 ms for ten rows on one Task, excluding CLI startup and text matching.

### Built · Work-scoped usage and Desktop history

- Provider turns without captured inputs share the local history selection, recent row budget, and usage reducer. Copied turns carry their origin in the Rust and Swift history DTO. The Session drill-down totals distinct native turns across Machines. A local transcript replay can lack the dispatch attribution recorded on the rental. Select that recorded dispatch before applying Work and time filters.
- The offline loss fixture passed on the final Rust build. CLI Task, Wave, Project, day and weekly usage and the Desktop `session.usage` request reported the rental turn. A local continuation and a replay of the rental turn totaled two streams, 36 input tokens, 10 output tokens and $0.25. A one-row history budget kept the unfinished rental turn. Rust `dto_fixtures::session_input_history_retains_distinct_native_results_and_unknown_process` and Swift `swift test --package-path swift --filter sessionInputHistoryFixture` passed. `lf server describe --json` matched the checked-in schema. `cargo fmt --all` and `cargo clippy --all-targets -- -D warnings` passed. After merging main's #1973 (`9827ba6a5e`, which rewrote the Session inventory's Task and Wave filters), the offline loss fixture passed again.
- `store::query_plan_lifecycle_tests::session_history_reads_plan_by_window` passed. Measured the pending-input SQL with 10,000 Tasks, 100,000 copied turns and 100,000 copied transcript rows. Before and after `ANALYZE`, the time, completion, Task and Session reads used their respective indexes. The completion arm needed `INDEXED BY machine_record_turn_end` to avoid visiting every copied turn on a fresh store. After `ANALYZE`, a 50-row recent selection took 1.40 ms, a ten-row Task drill took 0.33 ms and the Session’s turn selection took 0.06 ms (median of four warm SQL reads, excluding CLI startup).
- Copied captured inputs join the same selection. `pending_inputs` finds each from its capture, manifest or turns on the origin (window or Task), drops it when this Machine records the same artifact key, and keeps the lowest origin among copies (`machine_record_capture_key`). Its end, latest time, Work and eligibility come from the copied Session, manifest, terminal receipt and turns, and it ranks with local rows before decoding. `read_history_input` reads its observations from the copy (`read_history` takes an origin) and its scoped turns through `COLLECTED_TURNS`. Local replays of a copied captured turn no longer count twice. Revision triggers now cover copied Sessions, events, history and turns.
- The offline loss fixture passed with a rental input whose two turns ran before and after the Session joined the Task: Task, Wave and Project usage count 11 input tokens, `--days 1` counts 24, the Desktop `session.usage` read matches, and with a local continuation the Task shows three rows. `store::query_plan_lifecycle_tests::` and `sqlite::revisions::` passed; `cargo fmt --all` and `cargo clippy --all-targets -- -D warnings` passed.
- Measured on a synthetic store with 10,000 copied Sessions, each with one capture, ten observations and ten turns: every copied read used an index. After `ANALYZE`, a ten-day, 50-row recent selection over 1,728 copied Sessions took about 270 ms against about 130 ms with the capture arm disabled; the Task drill took 0.43 ms. That window is far denser than real rentals produce; nothing was tuned further.

### Built · Failed starts on any stopped Session

Live QA steered a stopped repository Session without Codex login. A held terminal exited with the login error while `lf session list` stayed at `unknown`. [Live QA](qa.html)

- `ops::recovery::launch_failure` takes a Session ID (its recorded harness, else its skill's resolution) and is the one readiness check for Task recovery, steer wakeup (`server/wake.rs::start_stopped`) and `human_session::restart_provider`. `TaskConversation.provider` is gone; each caller passes the ID and the check reads the Session row.
- Steer wakeup records `start_failure` instead of spawning an unavailable harness, records a held start's error, and clears it on a held start. A person's start (including a steer's resume) still clears it via `record_persons_start`. A steer is read once; a later steer tries again.
- `session_ending` shows `start_failure` for every stopped interactive Session except a finished Task's conversation, whose failure is history. A non-Task Session reads `could not start: <why>; \`lf resume <id>\` opens it`, and a held-start error on one that had run reads `… · last start failed: <why>` (previously dropped when no left-reason applied).
- `restart_provider` refuses with `Session <id> was not restarted: <why>` before stopping anything, so `lf machine forward --task|--session` fails over SSH before printing "Resuming".
- Tests: `server::wake::tests::a_denied_wakeup_shows_its_start_failure_until_a_later_steer_starts_it` (status line through `human_session::listed`), `ops::human_session::tests::a_restart_without_a_usable_login_leaves_the_running_provider_alone` (fake `codex login status` exiting 1), `…::a_stopped_session_that_is_not_a_tasks_says_why_its_start_failed`. All 36 `ops::human_session::tests::`, `server::wake::tests::` and `server::recovery::tests::` pass; fmt and clippy pass.
- Not covered here: a provider that starts in the held terminal and then exits with a login error still records nothing beyond its exit; the readiness check is what prevents the QA case.
- Live on Modal (QA run 2): a steer to a codex Session without login logged `stopped Session not started` and carried `could not start: codex has no usable login…` on the rental. `lf session list` never printed `status_line`; it now prints it under any Session with an outlook. [Live QA](qa.html)

### 4.1 Built · Settle a lost rental before SSH and omit ended routes by default

Live QA saw `lf machine end` suggest `--force` before background settlement caught up, and saw the ended route in `lf machine list`. [Live QA](qa.html)

- `rental::recovery::end` runs `refresh` before any SSH: a sandbox the provider no longer has settles at its ceiling estimate, releases held Tasks and prints `<label> was already gone (ended; ceiling estimate $…)`. A live sandbox goes through `give_back` unchanged, so unreachable SSH still refuses without `--force`. `refresh` rereads the rental first, so a background settlement between the command's read and its refresh keeps its recorded cost and asks the provider nothing.
- `lf machine list` and unlabeled `lf machine status` skip Machines whose rental ended. A label, `lf ondemand list`, and copied-history labels still resolve them. Desktop's `machine.list` read (`machines()`) is unfiltered because its status read shows `ended_rental`.
- Tests: `rental::recovery::tests::ending_a_sandbox_its_provider_already_ended_settles_without_ssh_or_force`, `…::ending_after_background_settlement_keeps_what_it_recorded`, `…::ending_a_running_sandbox_ssh_cannot_reach_still_asks_for_force`, and CLI `machine_commands::ending_a_rental_its_provider_terminated_settles_and_leaves_the_default_listings`. The lost-rental fixture's final `machine end` now has a provider answering "still running", so it still covers an ordinary give-back. `documented_commands::`, fmt and clippy passed. `docs/ops.md` describes it.
- Live on Modal (QA run 2): `lf machine end modal-1` in the same second as `terminate()` printed `modal-1 was already gone (ended; ceiling estimate $0.072974)` without `--force`; transcript, usage and search read the copy. Empty default listings now print `No Machines.`, and `machine status <label>` shows the ended time on the local clock. [Live QA](qa.html)

### 4.2 Built · Desktop Telemetry, `--context` and copied `lf session list` read the origin

Concept review pass 2 ([Concept Review](concept-review.html)) found three readers of collected history that assumed every row ran locally. No DTO, schema or migration change.

- `store::sessions::conversation_inputs` sets a copied row's `repo` to this Machine's checkout (`SqliteStore::work_repository_path`) when its Task or Wave lives here, checking the row's Work and then its provider turns' (a captured input whose Session joined the Task later carries the Task only on its turns). `worktree` stays the origin's path; bare rental runs keep the origin's `repo`.
- Desktop Telemetry: `[SessionHistory].localCodebases` builds the picker from `origin == nil` rows; `shown(in:)` filters only with more than one codebase and keeps collected rows whose `repo` no local codebase holds.
- `session_record::history_record_dir` resolves a collected input's capture under `machines/<origin>/runs`; `context_usage::step_context` and `lf session history show` (instructions, manifest) use it. The store's `history_turn_context` and `history_silences` take a `SessionHistory` and read a copied input's turn contexts and `--weekly` silences from its origin's copies (on `machine_record_session`), so `step_context` and `context_cost` never branch on origin. Silences without evidence times are skipped locally and on copies (the fixture's hand-written silence had none).
- `CopiedSession.start_failure` is read from the copied row; `lf session list` prints `  could not start: <why>` under an unfinished copied Session.
- Tests: the offline loss fixture now asserts local `repo` on every scoped row, a gap-free `--context` step for the copied input (first/peak request tokens 13), and the `could not start` line under `from mini`; it passed. Swift `TelemetryCodebaseTests` passed. `documented_commands::` and `cargo clippy --all-targets -- -D warnings` passed.
- `lf session history show <id>` on a copy sends `--context`, `--instructions` and `--input` to the input views, which find a copied capture by key (`machine_record_capture_key`). `--final` says the copy keeps no final answer and points at `--transcript`. An input summary's conversation and provider transitions still read local rows only. The offline loss fixture checks that `show --context` matches the usage step.
