Task Flows without a Task worker

Jack Heart asked for the Task-worker machinery to be deleted and headless work routed through the ordinary launch. This PR deletes the worker's internals (claims, generations, restart, retry, the Ready/Complete handshake, automatic scheduling) and keeps one Task-specific launch command. Waiting, Task primary selection, workflow files and Desktop's all-Flow views are not in it.

2 · A Flow's process dies or a step fails

What “live” means

What completion waits for

A caller never waits on its own process lineage or on the Flow whose step it is. A Flow marked current blocks only if its execution is unsettled; a review Session whose Flow ended blocks nothing.

Mismatch. The failed slow Flow stays Current in task status and flow list --sessions, beside the line saying its process exited and two Exec rows reading failed. Only a finished Flow changes state. Jack set status presentation aside as outside this Task; the state value is also what execution_blockers filters on, so it is more than display.
Not shown. A driver killed mid-step. No slow provider-free step was available; the failed step stands in for it. The unit test a_dead_flow_is_history_while_a_live_driver_holds_completion (ops/task.rs) covers the lock held and released.
