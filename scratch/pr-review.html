The open workspace follows the store

PR #1452 · LOO-382 · base bee8dcc49 → head 2b96c6f0d · published head equals the local branch; no unpublished changes · 38 files, +4,601 −270

Jack Heart asked that a Task created anywhere appear in the open Desktop window without a refresh, and that the same hold for renames, completion, Session changes and Flow progress. Before this branch Desktop learned about changes by starting lf every 2 to 30 seconds. On this branch each window keeps one lf process open; the store counts displayed changes, and that process re-reads and sends only the parts a commit could have changed.

Delivered: the store counters, the reader, and Desktop's cutover with five timer loops deleted. Not delivered: the 1 s and 500 ms targets (measured 2.3 s and 0.56 s), and the Task's first acceptance line, which collides with an earlier decision. Both are in Open decisions.

1 · A commit elsewhere reaches the window

The command Desktop runs can be run by hand. This is a captured run of the branch's debug binary in an empty throwaway Home, with stdin held open. A second shell commits one row with sqlite3, then the first sends a refresh.

Three things are visible. The insert moved planning from 0 to 1 and one planning frame followed. The failed reading arrived as unavailable with a null body, not as an empty list. And frame 8 carries answers: 7: it was read after the request was handled. The heartbeat counts are discussed in Stop 4.

The line on the wire

Each body is the type the matching one-shot command already prints (lf roadmap --all --json, lf session list --json, and so on), so Swift keeps its decoders and the saved launch workspace from LOO-376 keeps working.

The loop that produces it

One loop reads the parts in turn. Sessions come first in Part::ALL, but a Session commit that lands while planning is being read waits for it: about 2 s on a copy of Jack's store. That is the difference between the 0.2 s and 2.1–2.3 s Session samples in the plan.

2 · What counts as a change

The store keeps four counters. A trigger on each displayed table adds one inside the writer's own transaction, so every writer is counted, including older installed lf binaries and sqlite3, and a rolled-back write counts nothing.

Transcript lines were 164,192 of 168,336 Session events in a day on Jack's Home. Counting them would re-read every part for ten hours a day, so the trigger skips the evidence types no summary reader selects, plus usage.

The predicate has already been wrong once. Its first version skipped every :events.jsonl: row and silenced about 1,270 displayed rows a day. If it skips too much, a row stops updating and the 1 s re-check cannot catch it, because it reads the same counters. A test walks each fact session list shows; Work activity and a Wave's Session history have no such test.

Token totals lag by design of the predicate, not by decision. Usage rows move nothing, so totals refresh at the next displayed change or the five-minute clock.

How a new table is kept from being forgotten

A store test lists every table and fails unless it has all three triggers or appears in NEVER_DISPLAYED (revisions.rs lines 53–129). It checks that triggers exist, not that each is assigned the right counter.

3 · Desktop applies a frame

PodiumModel remains the window's single owner of what is shown. Every frame passes the same four questions before it changes anything: is it newer, is it from this Home, does it answer the last local write, and is it for what the window shows now.

A local write and an explicit refresh use the same request. The number it returns becomes a floor; frames below it were read before the write.

Two guards now protect the same reads. sessionsGeneration and roadmapGeneration still guard the one-shot paths, which run when no reader is open: session fixtures and about sixty call sites in four test suites. With a reader open, the floors do the work. The plan lists the one-shot bodies as still to delete.

A frame from another Home is applied after dropping the old Home's content, where the design said it would be ignored. The reader exits when the Home changes, so one reader never sends two Homes.

4 · Failure and recovery

The reader is a foreground child of the window. When it ends, the window keeps its rows, marks them unavailable, and reopens the reader after 1 s, doubling to 30 s. A new reader numbers frames from one and reads the store as it is, so every floor resets.

Inside the reader, a store file that exists and cannot be opened is reported, not treated as absent. This was found on a Home copy at another schema, which read as an empty workspace.

A failing part is re-read about every second with no backoff. In the captured run the planning count went from 2 to 5 in the two seconds between heartbeats while the reading kept failing. No frames are sent, because the failure text is unchanged. On a small store that is free. On Jack's store a planning reading takes about 2 s on the one loop, so a persistent failure would likely keep the loop busy and delay Session rows; that consequence is inferred from source and not measured.

What else catches up

A missed filesystem event is covered by re-reading the four counters every second. Waking the Mac sends refresh (PodiumView, rescanWorkspace). SQLite removing and recreating its log file is handled by re-arming the watch (StoreChanges::wait); that case is tested on the waiter, not through the binary, because a running reader holds the log open.

5 · The read made cheap enough to run on change

A stream that delivered a 20 s old answer would not help. Most of roadmap --all's time went to loading every Exec a checkout ever ran, per Task, to answer a question that only concerns unfinished execution. The completion gate now starts from the unfinished Execs (109 on Jack's store) and asks which belong to the Task.

With Git answers reused inside the watch process (layout for ten minutes, checkout contents for one), a planning reading on a copy of Jack's store went from about 7.5 s to about 2 s. The target was 300 ms.

Open decisions

  1. A Task with no started work does not reach the left outline. LOO-382 asks that a new Task appear in the left pane “without an execution-start prerequisite”. On 2026-09-25 Jack Heart accepted an outline of started Tasks only. The stream delivers the Task; the outline filters it. Nothing was changed. Jack has not chosen. Counterexample: lf task create --wave product --title "Reactive demo" with no --run. The row appears in Product's Task list and not in the outline until a Run or Session exists.
  2. The latency targets are missed. Rendered, on a copy of Jack's store, debug builds, 3 samples: a Task change 2.3 s warm against 1 s; a Session row 0.55–0.6 s against 0.5 s. Jack decided a miss ships with numbers and a follow-up Task. The follow-up Task is not filed.
  3. Failed readings retry every second (Stop 4). New in this walkthrough; not in the plan.
  4. Git-only changes show later than before. A dirty checkout used to show within the 15 s poll. Now checkout contents are re-read at most once a minute and only when planning is read, which without a commit is every five minutes. Nobody chose this.
  5. Polling is not entirely gone. A window runs two readers, because monitor active --watch was not folded in. The Task-files comparison still starts lf every 10 s while shown; each start writes an Exec, which moves execs and re-runs planning in the watch.
  6. The shared store changed without Infrastructure's review. One table, three triggers on each of 25 displayed tables (75 in all), and three indexes. The session_events trigger parses each inserted payload as JSON; its cost on large transcript lines is unmeasured.
