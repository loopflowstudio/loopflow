The open workspace follows the store and the checkouts

PR #1452 · LOO-382 · base 1af81fe03 → head 410cffecb · published head equals the local branch; no unpublished changes · 71 files, +6,796 −617

Jack Heart asked that a change made anywhere appear in the open Desktop window without a refresh. Each window keeps one lf process open. The store counts displayed changes, the process watches Task checkouts on disk, and it re-reads and sends only the parts that could have changed. After the first walkthrough Jack asked that reading the current Waves and Tasks be simple and fast, so the read behind the list was rebuilt as well.

Delivered since the last walkthrough: a planning read that went from about 2 s to about 0.2 s, a first reading recorded at 1.1–2.3 s where it was 6.5–7.1 s (4.65 s in this page's own run, at load 33), checkout changes within seconds, token totals within about 10 s, a failing part that backs off, and the working-set rule moved from Swift to Rust. Dropped with measurements: one reader per window, and exempting read-only commands. Both are in Open decisions.

2 · What counts as a change

The store keeps five counters. Triggers on each displayed table add one inside the writer's own transaction, so every writer is counted, including older binaries and sqlite3, and a rolled-back write counts nothing.

Which counters a part follows is one function, and whether a due part is read now is another.

The Session-event condition has been wrong once. Its first version silenced about 1,270 displayed rows a day. If it skips too much, a row stops updating and nothing catches it, because the periodic re-check reads the same counters. A test walks each fact session list shows; Work activity and Wave history have no such test.

Any lf command still re-runs planning in every open window. Each command records an Exec, which moves execs. Ten lf session list calls caused 20–22 planning readings of about 0.2 s each, with no frame sent. See Open decisions.

3 · Checkouts on disk

A dirty file or a new commit is not a store commit. The reader watches each existing Task checkout and, for a linked worktree, its Git metadata directory.

The reader keeps Git's answers. When a checkout changes it asks the same questions again and compares.

macOS only. Elsewhere no watch starts and the five-minute clock still stands. The reader's CPU while a checkout is building is unmeasured.

4 · Desktop applies a frame

PodiumModel remains the window's single owner of what is shown. Every frame is asked four things before it changes anything: is it newer, is it from this Home, does it answer the last local write, and is it for what the window shows now. This is unchanged since the first walkthrough.

Two guards still protect the same reads. The generation counters guard the one-shot paths, which run when no reader is open: fixtures and about sixty test call sites. The plan lists those bodies as still to delete.

5 · Failure and recovery

A captured run in an empty throwaway Home. A hand-inserted Wave row is deliberately incomplete, so planning cannot be read. Heartbeats are shown here because they count readings.

The failure arrives as unavailable, not as an empty list. Planning is then read three more times in the next ten seconds, at widening gaps, and not again in the six seconds after that. In the first walkthrough's run it was read about every second.

On the Desktop side, a reader that ends leaves the rows in place, marked unavailable, and is reopened after 1 s, doubling to 30 s.

6 · The read made fast

Sampled on the store copy, 83% of a warm planning reading was one query: the completion gate asking, once per Task, which unfinished Execs belong to it. One statement now answers that for every Task.

The same value carries the other things a reading asks once. Before the per-Task details run, Git is asked about up to eight existing checkouts at a time, so the details find the answers waiting.

The pinned index is load-bearing. Without INDEXED BY and CROSS JOIN the bundled SQLite scans the whole Exec table: 350 ms against 23 ms, measured in-process. The system sqlite3 chose the fast plan unaided, so the slow plan does not show up there.

The rule is met for Exec membership only. The gate still runs a few statements per unfinished Task, about 40 ms of a 200 ms reading. Left alone by Jack's rule for this round: not a clear win against rewriting the code that decides lf task complete.

7 · The working set

Whether a finished Task still belongs in the outline was decided in Swift from three separate fields. Rust now derives it once and sends it.

A required field on the wire. A workspace saved by an earlier build lacks it, so the first launch after upgrading should show no saved planning until the reader answers. Expected from the decoder rule; not exercised.

Open decisions

  1. One reader per window was dropped. Jack listed it among the performance taboos to remove. The separate active-Session reader starts in 0.23 s, idles at 0.2% of a core and holds 25 MB, and starts only when the Monitor is first opened. Folding it in means rewriting its start, retry and Home-change handling in Swift. The copy has no run receipts, so its idle cost on Jack's Home is higher than measured.
  2. Read-only commands still re-run planning (Stop 2). The fix as planned cannot be written in a trigger: an insert does not know the command only reads, and Desktop's remaining reads run inside the Task checkout, where a live process is a real completion blocker. It needs a change to Infrastructure's Exec model.
  3. The reader idles at 1.6% of a core and 37 MB, against a 1% target. Unprofiled; the two-second process observation is the likely cost.
  4. The shared store changed without Infrastructure's review: one table, 76 triggers and three indexes. The Session-event triggers parse each inserted payload as JSON; the cost on large transcript lines is unmeasured.
  5. No derived state is stored. Jack said he wanted it in the database, then that SQLite reads should not be a problem. The branch computes each reading fresh. Recorded as an unconfirmed reading of his answer.
  6. LOO-382's first acceptance line is unmet by decision. A Task that has not started stays out of the outline.
