One provider home, several stored logins

Loopflow conversations now live in Codex’s and Claude’s ordinary home, so the provider’s own CLI sees them. One command changes which stored account that home is signed in as. A Codex engine closes when the interface that owns it exits, unless another interface took the conversation over first.

PR #1416 · base a278d6bc1 · published head a79921045. The switch command’s new spelling, lf account <provider> use <email>, and the collapse of account routes to two kinds are unpublished working-tree changes and are marked where shown. Not built: moving running agents (“everyone now”).

1A launch names no home and no credential

A route is how one launch reaches one account, and there are two. Shared is new and the default. Isolated is the previous behavior, now reached with --isolate, isolate: true, replaying a recorded run, or an account lent over lf ssh. The published head still has four variants; collapsing them is an unpublished working-tree change.

All five launch sites call launch_as. The returned lock is held until the child has spawned, so a concurrent switch cannot swap the login mid-launch. Nothing records the launch as a running shared agent; that record is what “everyone now” still needs.

An account lent over lf ssh used to be a third way in: the target exported the origin’s access token as CLAUDE_CODE_OAUTH_TOKEN or CODEX_ACCESS_TOKEN. It is now an isolated home like any other. The origin sends the login with its refresh token blanked, and the target writes it into a home for that account.

This changes what the SSH target holds. The token used to exist only in the environment; it is now a file under the target’s ~/.lf/accounts, readable by that user until the token expires, and nothing removes it when the session ends. It cannot be renewed from the target. Both providers were probed with synthetic logins and accept an empty refresh token; no real SSH session was run.

No terminal transcript here: a real launch spends a real account. The Codex fixture ran it against a synthetic provider and observed that the engine received neither CODEX_HOME nor a credential variable, and that plain Codex listed and resumed the conversation. See Evidence.

2Switching saves the old login before installing the new one

Two stored accounts, and a login in ~/.codex that Loopflow has never seen. The middle of the run rewrites work@’s login the way Codex does when it refreshes a token, then switches away and back.

The rotated token survived the round trip, and the unknown login was kept as a third account that automatic routing will not spend:

Nothing stores “the active account”. It is whichever stored account the login in the provider’s home identifies, which is why the already-active case returns before taking the lock. The login is installed before the log row is written, so a failed log write reports an error after the switch has already happened.

The provider comes before the verb only for use. connect, set, disconnect and redeem-reset still take it after. To allow this, the blanket parser rule that forbade arguments before any subcommand became the hand-written check above.

3Reopening follows how the conversation was started

recorded is Some(false) for a shared conversation, Some(true) for an isolated one, and None for a new one, which takes the launch’s mode. Rows from before this change default to isolated, so old conversations open where they were captured.

connect, history, rename, bind and complete accept a provider ID through this lookup. Only connect will create a Session for a conversation plain Codex or Claude started; the others report it as not found until then. A shared conversation started under one account and continued under another is assumed to work within one workspace and is unverified across workspaces or plans.

4Quitting closes the Codex process; history stays

Jack Heart chose this on 2026-10-03: close by default on ordinary exit. Three things have separate lifetimes: the saved conversation, the lf process currently driving it (the driver), and the Codex app-server process holding it in memory. SessionDriver already existed on the base and names the second and third.

The first check is the whole policy: an interface that is no longer the driver cannot close anything. The last statement clears the socket address and keeps the thread ID, which is what lets a later resume start from history.

While this process is alive, plain Codex is refused with “already has an active writer”. Closing it is what makes codex resume work straight after a batch run. The cost is that an exit during a tool call can interrupt it, and nothing rolls back what the tool already did.

What shutdown refuses to kill

Before signaling, the close asks the engine which conversations it has loaded. Codex’s own subagents count as part of this one. A separately started conversation makes the close fail and leaves the engine running. Releasing one conversation from an engine that serves several is unresolved.

5Taking over moves control first

claim_session_driver is called with replace_provider = false: the driver generation advances, the provider generation and process do not. The former driver’s later call to finish_session_driver then fails its first check.

If…Then
The new interface claims before the old one exitsThe old exit is refused as stale. The engine and its turn keep running.
The old interface exits firstThe engine is closed and its address cleared. The claim fails, finds no address, and falls through to resuming from saved history.
The new interface later exitsIt is the current driver, so it closes the engine.

Open decisions

QuestionWhere it stands
Moving running agents to the new account (“everyone now”)Not built; the switch log already allows everyone_now. Interrupting a turn moves sooner but risks a tool running twice; waiting for the turn to end delays the move. The research on what an interrupted session feels like has not been done.
Should the other account verbs also put the provider first?Jack named lf account codex use …. The other four verbs were left as they are, so the namespace is currently mixed.
A lent login left on the SSH targetWritten to disk and not removed at session end. Deleting it when the SSH session exits would break a second session to the same target that is using the same account. Not decided.
SSH from an origin with no stored accountsUnchanged: lf ssh still exports the origin’s own token as an environment variable in that case. The plan drops environment tokens; this path still uses one.
A login Loopflow has never seenKept as a new account marked explicit_only, as the transcript shows. An implementation choice awaiting confirmation.
A Wave-level isolation defaultRepository and Home isolate: true work, with --shared to override. Whether a Wave needs its own is open.
An isolated launch on the active accountIt runs on the stored copy of a login whose other copy is in the native home. If Codex rotates refresh tokens the two could invalidate each other. Unproven either way.
