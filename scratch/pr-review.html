The goal was to read and write the Program Status protocol (OSC 7501). This PR delivers reading: a program in any Loopflow pane can say it is working, blocked, done or failed, the app shows that, and for a Session the same report decides Waiting. Writing reports from lf is not here, and the PR says why.

What a report is

Review note. A pane can hold several records (the protocol's id hierarchy). What you see is one: the newest blocked, else error, else working, else done, else idle. The message is stored as reported and stripped of invisible formatting only when drawn. Rust mirrors the type in rust/loopflow/src/program_status.rs and enforces the spec's limits there.

Reports decide Waiting

Review note. Two things to judge. First, the app runs one lf session observe-status process per observed Session pane and feeds it snapshots on standard input; it is a new public subcommand that only the app is meant to call. Second, Waiting from reports exists only while Desktop is observing that terminal. A Session running in a plain terminal, or on another machine, still uses the old inference. The relay in LOO-415 is where reading without the app would go.

Stored state

Review note. Reports live on the existing session_activity row; no new table. The comment on line 6 means Sessions lose their current inferred Waiting reading at upgrade until a fresh one arrives.

Why writing is missing

The Flow ended as blocked on this question for you: should LOO-398 take on ownership of terminal output, or defer lf's own reports until the transparent relay (LOO-415) provides that owner? The worker removed its unsafe emitter and unused scaffolding from the diff.
