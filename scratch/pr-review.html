The experience

From Jack's words: you work in Desktop with one open primary Task conversation. Work runs in the background. At certain points the Task comes back to you; you look, and you say where it goes next: back for another pass, or on toward landing. You and the conversation have the same direct control over that choice. Nothing you do there ends the conversation. The graph is fixed when the Task takes it up; to change the graph you start over on a new one.

The builtin feature definition, as built. A loop back is just a way out that returns to the same stage.

One interaction: the demo loop

built When everything succeeds

This already matches the experience: choosing a way out is the whole interaction, and the reason travels to the Flow as Task direction.

built When something stops

The most consequential mismatch. A stage means “waiting on you”. But today “at demo” also means “the last thing failed” and “the landing is still settling”. Because position is computed and nothing can set it, the Workflow cannot tell these apart and nobody can correct it. Following it through four layers

proposed Jack asked for “the core data model at the center of this, what is the data model ↔ db API, db ↔ cli, db ↔ swiftui”.

LayerSurfaceRule
ModelWorkflow definition (stages, edges). Workflow: graph + position. Move: who, what, from, to, note.Position is at a stage, or on an edge with the process running it. Running or stopped is read from that process.
Model ↔ databaseRead · take up · choose an edge · arrive · set a stage.Choosing is one transaction and only legal from the edge's own stage, so two choosers cannot both leave. Only the process that ran an edge can arrive from it.
Database ↔ CLIRead: lf task status ISSUE --json. Write: lf task run, lf task move.The CLI calls the store; no other code writes these tables. Who made a move comes from the calling conversation, else the person.
CLI ↔ SwiftUIDesktop reads the same JSON and runs the same two commands.Desktop never opens the database. Its Swift types mirror the JSON with no defaults and are checked against one shared fixture.
There is no database ↔ SwiftUI layer, by design. Desktop's one reader runs lf … --json. That rule predates this work and it is what keeps buttons and the conversation on the same API.

built What the tables are today

The proposal keeps one row per Task that is updated in place (graph, position) and turns the second table into the history of moves.

Distinctions you must learn today, and whether they earn it

  • Three spellings, two meanings. lf task run X pursue moves the Workflow. lf --task X run pursue and lf run pursue in the worktree run the same Flow and do not. The difference is real (ad hoc work should not move the Task) but nothing in the words says which is which.
  • A way out is named by the Flow it runs. At demo you say pursue to mean “send it back” and ship to mean “land it”. Two ways out of one stage cannot run the same Flow. end is a special word for the one edge that runs nothing. Naming edges for the decision (revise, land) would read as the choice you are making.
  • “Workflow” and “Flow” share a catalog and a namespace. lf flow list shows both; feature is a workflow definition and lf run feature fails; a repository file .lf/flows/feature.yaml hides the builtin definition.
  • Three kinds of “done”. The Workflow is at end, the Task is still ready, and a “PR 1: working” slot remains. Deferred to LOO-385.
  • Waiting does not cover your primary conversation. Deferred to LOO-384.
  • Four process words. Exec, Flow run (FlowExec), Session and Run all appear in status. You need two: the Flow run and the conversation.

Choices that change what the product is

  1. Does a stopped edge hold the Task on the edge, or return it to the stage? The pass is building “holds, shown as stopped”, so retry and go-back are both visible. Returning is simpler and is what is built.
  2. Who tells the conversation an edge finished? Today only its own background tool, or reading status. A Desktop button's edge finishes unnoticed by the conversation. The alternatives are Desktop speaking into your session, which you ruled out, or the conversation being the only thing that ever starts an edge.
  3. Buttons, the conversation, or both? Both call the same two commands, so this can stay open. It decides whether Desktop must manage background processes at all.
  4. Are ways out named for the decision or the Flow? See friction above. Not in the pass.
  5. One verb or two? Choosing-and-running is lf task run, confirmed by Jack. Setting a stage needs a name; the pass is using lf task move.

What would invalidate the proposal

A stored position that disagrees with the world: the Workflow says “on revise” while no process exists. The rule that covers it is that running or stopped is never stored, only read from the process, and anyone may then choose or set. If a case appears where the stored stage itself must be recomputed from evidence, derived position was right and this should be reversed.
