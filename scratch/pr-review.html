01 / completion

End is completion, with or without a PR

Placement now belongs to the Task, so checkout creation no longer invents a PR. The shared read replaces the old PR array and active selection with pr: Option<TaskPr>; publication creates its one current PR.

task complete and task move … end share the dispatcher and workflow_set → task_end → reach_end. The operation explains refusals and handles planning writeback; this store transaction rechecks delivery before moving to end.

There is no separate “at end but incomplete” state. An open PR, unconfirmed filing or unresolved legacy obligation leaves the Task before end. A no-PR Task needs no disposition unless it already has filing or conversion obligations. Retained files and Sessions do not block completion.

The shared CLI entry and the visible Desktop result

The page consumes the shared optional PR and follow-through facts. It shows pending, ready to complete, or done with links; a recorded “none” reason remains readable. These are delivery labels alongside Workflow state.

Completion is local Workflow truth. Linear writeback and checkout cleanup retain their own retry paths; a failure there does not create a second completion flag. The alias and checkout-aware Flow launch are the earlier slice in this same PR.

Migration removes serial authority while retaining historical PRs

The migration preserves old PR IDs for landing and stack references, and converts legacy keep-open scope into evidence requiring a decision. Only one current PR is permitted. Historical rows are read-only; they are not a second live delivery chain. pr next, land --next, and land -c are removed.

Task owns placement; the PR API retains a validated mirror of branch/base/parent fields. The draft's remaining triggers enforce that relationship. Released-frontier installation still needs capable Docker CI.

Inspected public CLI coverage includes retained no-PR research and completion inside a Flow after merge and disposition. The base already supplied Workflow-derived state and completion/cleanup separation; this PR changes the delivery conditions and removes PR-placeholder dependence.

02 / post-merge trigger

The landing Flow runs the finishing skill

October 8 correction: Jack Heart requested self-contained waited landing. A real CLI fixture now runs Task → Flow → waited land → simulated CI repair → merge → follow-through without a watcher. Waiting controllers no longer block their own repair; unrelated live work still does. A watcher reports a busy checkout without marking the delivery failed.

The command waits for merge evidence. The skill decides which accepted obligations need another Task, records that decision through the API, and completes the source. Reconciliation can settle an already-recorded disposition; it never invents that judgment or launches the skill.

The operational limit: this adds no permanent completion watcher. If a driver dies or a PR merges manually, finishing waits for the next Task/Wave operation. A due date also creates no wakeup: without installed schedule coverage or an ongoing operation, “check tomorrow” is recorded work awaiting a pass.

CI repair and repeated landing

Waited landing and the optional repository watcher share one CI incident reservation. The repair skill repairs, publishes and re-arms. Admission recognizes the calling command’s recorded waiting Flow drivers and Task carrier; it still refuses unrelated live work and unresolved provider turns.

Jack also requested harmless retries after merge. Bare land and waited land now share this verified-merge success path. They report whether the Task is complete, preserve finishing notes and edits, and skip sync, cleanup, publication and re-arming. Failed or ambiguous observations remain failures.

The CI-repair skill ends after lf arm; it does not file follow-ups or complete the Task. If repair outlives the finishing driver, the next Task/Wave operation still owns follow-through.

The wait loop and stopped-delivery recovery instructions

Implementation defaults are 15-second observations for at most 30 minutes. The ordinary process handler owns interruption; timeout returns held and retains the request. Waited landing admits its own CI repair. A held command keeps exit 3 through the Flow and stops automatic retries. Ordinary failure still retries the whole Flow, up to three attempts while its Task runner survives; LOO-435 owns retry from the failed step. After merge, the operator follows this instruction:

finish-delivery contains only follow-through. It is a fresh Flow after liveness inspection, not a continuation controller.

Recorded fixture coverage retains one PR/request and checkout through interruption, retry, merge and reconcile. Timeout expiry, live provider execution and automatic schedule coverage are not established by that test.

03 / durable follow-through

A retry finds the same follow-up

The receipt separates the immutable filing request from the confirmed link. The saved key names an obligation, the UUID identifies its issue, and the saved Project survives chapter rotation. The confirmed due date follows Linear's current value.

This public operation owns the sequence: check merge, reuse or reserve the intent, confirm the issue and relation, then record the link. --finish reconfirms every intent before recording a reason; --none is the zero-filing path.

A caller-visible choice: --key defaults to follow-up. A second obligation needs a different stable key. Reusing a key with a new title, date or destination deliberately returns to the original request; it does not edit that child or create another one.

The transaction boundary and failed confirmation

Reservation serializes competing writers and returns the original request for an existing key. Once an intent exists, --none cannot discard it; every saved intent must have a confirmed matching link before finish. Completion rechecks the resulting facts in the transaction shown in stop 1.

The resolved() projection requires a reason, no conversion obligation, and one matching key/issue link for every intent. Linear's native relation supplies navigation; the source's receipt supplies direction. Neither relation makes the child block its completed parent.

The inspected operation fixture loses mutation responses and readbacks, rotates the chapter, edits/moves the created issue, changes then removes its due date, and ends with exactly one provider issue and relation. It also confirms completion is repeatable. That is simulated-provider evidence, not a live Linear filing.

04 / dependent work

The child receives only its own design

Existing stack sync already carries parent changes through squash merge. This PR adds an explicit --design handoff while keeping scratch isolation. The caller selects a child-specific file; the command transfers its bytes without interpreting a multi-step plan.

The applied receipt makes the handoff one-time: even deletion of the child's note is preserved on retry. A different input at an occupied destination fails with both contents retained. Parent code can keep syncing; later design decisions need a deliberate child update.

Inspected handoff fixtures cover two distinct child designs, exact content and provenance, repeated handoff after a parent commit, edited/deleted child notes, and occupied-path conflicts. Existing stack tests supply parent-update and squash behavior. A single complete stacked-task demo remains unshown.

Placement resolves before Process admission, and task run starts its Flow child in the target checkout. The caller retains its own history. Task status and Flow inventory share association rules; registration now records Started and the Flow together before any step runs.
