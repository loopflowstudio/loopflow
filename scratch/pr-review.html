1. Research ends without manufacturing a PR

Checkout used to imply a working PR slot, with an active selector over a serial list. Placement now belongs to Task; the shared read exposes pr: Option<TaskPr>. A research Task can keep its files after completion. A second PR requires a separate Task.

Illustrative CLI sequence, expected from pinned source; not a captured run. Bracketed lines describe state, not literal output.

$ lf task move RESEARCH end
[Workflow arrives at end and requests completion; no PR is created.]
$ lf task status RESEARCH --json
[status: done; pr: null; retained checkout and Process evidence remain visible.]

TaskSnapshot is a projection, not a second stored Task. Status, completion_pending, execution and work remain separate fields; Desktop consumes the same contract. The optional checkout comes from LOO-406. This branch removes the PR list and moves branch/base ownership out of its placeholder.

Stacking and historical data

Dependent PRs use separate stacked Tasks. lf checkout CHILD --stack-on PARENT --design PATH transfers a prepared child-specific plan; existing stack sync handles parent updates and squash merge. 2. End is a trigger, not a definition of Done

task complete saves planning status without moving Workflow or stopping Processes. Arrival at end commits first, then tries that operation. A failed completion retains the arrival and an exact request to retry; a later reopening supersedes it.

Illustrative CLI sequence, expected from pinned source; not a captured run. Bracketed lines describe state, not literal output.

$ lf task complete SOURCE
[If merge or required filing is missing: completion refuses; the request remains pending.]
$ lf task follow-up SOURCE --none 'No accepted obligation remains'
Follow-through recorded; complete with `lf task complete SOURCE`
$ lf task complete SOURCE
[Status becomes done. Workflow position and running Processes are unchanged.]
$ lf task reopen SOURCE --reason 'Further work is needed'
[Planning reopens; Workflow and the existing PR are retained.]

The transaction gates ordinary completion on authoritative merge and a resolved disposition, then queues local status delivery. It never writes Workflow or Process state. Cleanup is separate and retains live work and unpublished artifacts.

Linear can independently mark a Task Done before filing. That is respected as planning state, while unresolved delivery remains visible and finishable. The early-Done branch above is why “Done” alone cannot be treated as proof that follow-through was filed.

3. A usable follow-up exists before Linear export

Filing pins one local child, its destination and payload under an obligation key. Retrying the key uses that child even after chapter rotation. Finishing confirms local links; optional Linear creation and relation export can remain pending without blocking the child or its source.

Illustrative CLI sequence, expected from pinned source; not a captured run. Bracketed lines describe state, not literal output.

$ lf task follow-up SOURCE --key installed-check --title 'Verify installed release' --notes 'Run the accepted scenario on the released version and record the result' --due 2026-10-10
[Prints the linked local Task identifier and asks for --finish.]
$ lf task follow-up SOURCE --finish 'Installed verification has its own Task'
Follow-through recorded; complete with `lf task complete SOURCE`
$ lf task complete SOURCE
[Source completes. Child remains usable even while Linear export is pending.]

The same-key branch precedes current-Project admission: a retry recovers its original child. New scope after a resolved disposition is refused. A completed Task may file only when merged delivery is still unresolved; filing does not reopen it.

API entry, linking, and historical uncertainty

task_follow_up checks the optional PR has merged, reuses a matching intent key, and invokes link_intent. The reservation creates the child through common local planning; the link records its current local identity and URL. Historical provider payload fields remain for conversion; they are not a second current planning authority.

Old creation receipts lack a send boundary. Jack chose to keep the local Task usable while export remains uncertain; absence at Linear does not trigger a speculative duplicate create. This is settled policy, not a question awaiting approval.

4. Ship owns its wait and CI repair

land --wait-and-fix observes its own PR and admits CI repair without Desktop. Once merge is observed, the Flow runs follow-through. The skill judges accepted obligations and calls the completion API. Bare land still returns after requesting merge.

The 30-minute timeout and 15-second poll are implementation defaults. A hold returns exit 3 with merge intent retained; interruption is 130. Ordinary failures remain errors. Already-merged landing succeeds without republishing or clearing new notes. The Task runner still retries whole failed Flows; failed-step retry belongs to LOO-435.

Illustrative CLI sequence, expected from pinned source; not a captured run. Bracketed lines describe state, not literal output.

$ lf land --wait-and-fix
[Waits for this PR; repairs admitted CI failures; returns after verified merge.]
# If the ship driver stopped and no associated Flow is still live:
$ lf --task SOURCE run finish-delivery
[Runs follow-through only; does not repeat gate or re-arm the PR.]
# If filing already finished and only completion failed:
$ lf task complete SOURCE

There is no new permanent post-merge daemon. A live ship Flow owns its finish; otherwise a later Task or Wave operation starts the finishing Flow. A due follow-up returns on its Wave’s next operation. Filing installs no timer and a date alone never authorizes execution.
