1 · Moving a Task along its workflow

A Task is at an edge's to stage only when the process that ran the edge succeeded. A failed or stopped edge leaves it where it was. While the newest edge's process is alive, the Task is on that edge.

Fits the decisions. Jack: “One where there there is a start and a land node and then in between are human sessions, and the edges are lf flows”; a Task helper may prepare, then “go into the lf run flow”. Nothing approves or completes a stage: the only move is running an edge. A plain lf run is tracked as a Flow run and does not move the Task.
Differs from what Jack described. He said the outer record is the mutable one, and that it could be replaced or taken over. What is built is two append-only tables (task_workflows, task_workflow_traversals) with position derived. “Replace” exists as taking up another workflow by name; there is no take-over command. This was the open question in scratch/task-workflow.md and ran on the agent's default.
Unguarded. A second lf task run while an edge is running is allowed and chooses among the edges leaving the running edge's starting stage. Desktop disables its buttons in that state; lf does not.

2 · A Task that ends without a PR

Jack's question, partly answered. “I am pretty confident we want 0 PR tasks; not sure we need multi-PR tasks.” A workflow needs no landing edge, and several PRs would be a loop through one; the workflow never counts PRs. But the Task still carries a “PR 1: working” slot, as the last line shows, and reaching end does not complete it. Both belong to Task completion (LOO-367), which this PR leaves alone.

3 · The loop syntax

Before, the same loop was a five-line step: id: decide, name: loop-decide, repeat: from: implement.

4 · Steers on a repeated step

Jack's concern. “This seems potentially bad as that was specifically added to address some runaway token counts.” The saving is back without telling a step about its Flow. The memory is per driver process, so the first run of each node in a new Flow still receives every steer.

5 · Waiting and a Task's primary conversation

Limit to know before relying on it. Waiting is only known for a conversation whose stream lf owns: every headless Run, and Codex. A native claude or opencode terminal never shows Waiting. Reading Claude's transcript file would fix that and may be excluded by Jack's stream-json-only rule; it is an open question in scratch/questions.md.

Choices the slices made that Jack has not reviewed

All are listed in scratch/questions.md, one section per slice. The ones that change what you would see:

  • feature and code are workflows only. lf run feature fails and names lf task run. A repository's own .lf/flows/feature.yaml still wins.
  • Operators and a waiting Task. The operate skills now say a Task at a stage waits on a person, and only a stopped or failed edge is rerun. Jack's earlier “a defined Flow with steps left proceeds without asking” has no mechanism now that resume is gone.
  • Desktop. A Flow run whose driver was killed draws as running forever. Start is one button per edge leaving the waiting stage. Edit opens the file in the system's default application, not the Task file pane.
  • Session wire shape. attention is "waiting" or null; Session kind and the agent_sessions.kind column are gone.
  • lf wave update-plan --flow NAME does not check that NAME loads.
  • Still standing from the last review: structured output is gone for every provider, and any lf command can be a cmd: step.
