01

A conversation can gain a Task without gaining a checkout

Binding an existing conversation admits its planning issue, then attaches the conversation to that Task. It does not allocate a checkout, PR or Flow.

The first new boundary is optional placement: a path and slug exist together, or neither exists. A missing retained checkout remains different from never having allocated one.

Admission still needs valid Project and Wave ownership for a new row. An already registered Task returns directly. Project availability and optional chapter resets belong to LOO-366.

Before: binding required an already registered Task. Now: binding can admit the issue. Preview remains observational.

Admission ownership, race handling, and preview
02

An unrelated Wave refresh no longer invalidates the Task operation

After an issue mutation, confirmation reads that issue by stable identity. A successful edit no longer waits for the whole Wave snapshot to refresh.

Ownership and outcome checks remain: a moved issue or an unconfirmed completion still produces an error. This narrows the required evidence; it does not make provider evidence optional.

Planning-only completion already existed in the base. Its summary marker and retry behavior are retained; this diff changes the confirmation dependency.

Creation uses the same narrower confirmation; planning completion retains its summary marker
03

An explicit Flow uses the same driver with or without a Task

lf flow start ordinary and lf --task ISSUE flow start ordinary enter the same Flow runner. Attribution adds the selected context and directory.

The exact branch matters: the explicit-template route applies when placement, directive, reason and retry options are absent. Bare Task startup can instead resume or select its managed Flow. Taskless startup requires a template.

Managed startup now admits without allocation unless placement flags request it. The captured Flow owns its directory, so continuation does not need to invent a Task checkout.

Finishing a Flow leaves the Task open. Task completion no longer silently ends its managed Flow. Managed planning is checked before launching new work, rather than before consuming every saved result.

Saved results, launch validation, and cwd migration
04

“Complete Task” records an outcome through the shared operation

Representative scenario: a research conversation is bound to an unplaced Task. Jack enters “Measured startup” in Desktop and presses Complete Task.

  1. Desktop requires a nonempty outcome and sends the same CLI command used by an agent.
  2. The Rust operation finds the registered Task. An unregistered planning issue uses the pre-existing planning completion path instead.
  3. For a registered Task, the retained-work and delivery gate must pass before the outcome is appended and the Task is completed.
  4. Desktop refreshes on success and displays an operation error on failure.

The supplied outcome is a Task progress event. The terminal event says “Task completed.” Task state and the terminal event share a transaction; the supplied summary is appended before it.

This scenario explains the source path; it is not a newly observed Desktop interaction.

State change, CLI result, and Desktop refresh
05

The working conversation can finish the Task and keep talking

An agent-issued completion can exempt its own current conversation from unfinished-work checks. The relationship must match the stored provider generation and exact driver parent. Merely sharing the checkout grants no exemption.

The allowance is restricted to ordinary conversations and to completion. A pending review is not the requesting conversation. Unknown or live independent execution still blocks.

Done does not mean deleted. Cleanup runs the stricter retained-work check. A conversation still using a checkout, or an unfinished managed Flow, keeps it in place. Cleanup can be retried after that work settles.

Accepted intent: Jack Heart confirmed on October 2 that the working conversation may complete its Task before its own turn ends. The broader experience remains under review.

How the exception is confined and independent execution remains protected
06

Choosing delivery later preserves identity—and its promises still bind

First checkout allocation updates the admitted Task in place and inserts its first PR in the same transaction. The Task id and its bound conversation remain.

Once delivery exists, completion still refuses an open or publishing PR. An unpublished PR is also a promise, even if it has no commits, unless it is the narrowly defined empty successor after landed work.

Independent unfinished Flows block completion. Missing checkout or uncertain follow-up evidence remains a refusal, rather than an empty-work assumption. These protections build on LOO-355 delivery and LOO-358 membership.

The retained unpublished-PR distinction
07

Desktop shows independent Flows beside the managed selection

The Task pane draws independent Flow members from the shared Task-work snapshot. Each card shows saved progress and offers Resume or Retry for that exact Flow id.

Managed controls continue to use the managed selection. The new outcome entry is placed in the Flow pane even for a Task that uses no Flow.

Product judgment remains open: does placing Task completion inside the Flow pane make purpose and execution clear enough? This is a review question about the implemented placement, not an agreed redesign.
