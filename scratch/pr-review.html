01 / Create and retry

A Task exists before work starts

The full durable ID is a UUID-backed TaskId. The visible lf- alias uses a unique prefix of at least 12 characters. Linear identity and checkout placement are independently optional; neither supplies the local Task’s identity.

Retry the original command with the same --creation-id and original input. A changed title in the stored Task does not invalidate that retry; changing the creation request does. Omitting the flag mints a new ID, even for the same title. The CLI prints the ID before attempting creation, so callers must retain it.

Compared with the base, TaskPlan.id: LinearIssueId becomes an optional mapping, and provider observation time becomes optional. The existing owning Task.id stays durable; Task.worktree is now optional too. UUIDv4 generation is reused, not introduced here.

The transaction stores the original request separately from editable Task fields. It returns the current Task on replay; no second Task, checkout, or provider issue is allocated.

Between the CLI and SQLite: Wave selection and creation after rotation

With no selected Wave, explicit creation chooses personal:inbox. An existing shared Wave continues down the Linear path. On retry after rotation, the saved creation Project supplies the original request comparison; it does not move the Task back.

Proof for identity and fields

02 / Personal planning

The store holds the private definitions

A personal Wave’s goal, memory and custom workflow are rows, not new repository files. Its Project still uses the existing content shape for KRs, targets and workflow; Tasks expose the familiar title, notes, rank and assignee fields.

Planning authority belongs to the Wave’s personal-plan association, not to whether a Task happens to have a Linear ID. Adding an external mapping alone cannot silently change who owns edits. Personal storage is local to this machine; this PR supplies neither replication nor protection against losing its store.

Desktop edit: save succeeds before the sheet closes

The editor holds unsaved text and errors. The model delegates persistence to the Rust project operation. A failed save keeps the editor open; the headless interaction test checks that invalid text does not replace the saved definition.

Headless workflow and comment interactions use scripted queries and the shared DTO fixture. The private-definition CLI fixture checks that Wave and workflow repository files are not created. No rendered native-app acceptance is claimed.

03 / Work and delivery

Placement changes; Task identity does not

The store commits the path, first PR and initialization event together before checkout setup finishes. A failed setup therefore leaves an allocation to repair. Local planning removes the Linear prerequisite; it retains the existing Workflow, Process and PR authorities.

Publication and auto-merge requests remain intermediate states. The completion gate requires settled delivery, and cleanup happens after the completion transaction. Provider-free planning does not mean remote-free PR delivery.

Delivery evidence and preserved execution authority

The delivery test uses a local bare remote and a GitHub stub. It observes “not done” after publish and after land -c, then injects merge evidence and reconciles. This proves command composition under the fixture, not a real GitHub merge.

Public local Task execution and no-remote failure exercises existing execution. The native-session admission check now consults Task deletion independently of an optional Linear ID; it retains captured Session/Process ownership. The migration/adoption proof preserves existing shared Task and execution history, including retained deletion evidence.

04 / Rotation and recovery

Retry the plan that was already applied

Local rotation changes selected Projects and explicitly moved Task membership in one SQLite transaction. It records the original request. A repeated request recognizes its settled result; a changed request or selection is refused instead of replaying an old move onto newer work.

A chapter containing both personal and shared Waves is not one distributed transaction. Local rotation commits first; Linear work follows. If a provider step fails, keep the same chapter plan and retry. The local receipt prevents replay while the provider transition finishes.

Partial-failure proof

mixed_rotation_retry_preserves_settled_personal_work_after_provider_failure injects provider failure, changes the already-settled personal plan, then retries the original mixed rotation. The recorded matrix covered ten failure points. This is fixture evidence, not configured startup-team continuity.
