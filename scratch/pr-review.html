The open workspace follows the store

PR #1452 · LOO-382 · base c41895363 (main) → published head b81180102 · the local branch is one commit ahead (a2db1a8ba), which changes only the plan and Product memory · 56 files, +5,813 −420; 49 files, +4,462 −420 outside scratch/

Jack Heart asked that a Task created anywhere appear in the open Desktop window without a refresh, and that the same hold for renames, completion, Session changes and Flow progress. Before this branch Desktop learned about changes by starting lf every 2 to 30 seconds. On this branch each window keeps one lf process open; the store counts displayed changes, and that process re-reads and sends only the parts a commit could have changed.

Delivered: the store counters, the reader, Desktop's cutover with five timer loops deleted, and a planning reading that went from seconds to about a quarter of a second. Not delivered: a re-measurement of the window after that speed-up, and the Task's first acceptance line, which collides with an earlier decision. Both are in Open decisions, with Jack's stated wish for derived state in the database, which the branch does not build.

1 · A commit elsewhere reaches the window

The command Desktop runs can be run by hand. This is a captured run in an empty throwaway Home, with stdin held open. A second process commits one row with sqlite3; nine seconds later the first sends a refresh. The left column is seconds since start.

Three things are visible. The insert moved planning from 0 to 1 and a planning frame followed 0.11 s later. The failed reading arrived as unavailable with a null body, not as an empty list. And frame 12 carries answers: 7: it was read after the request was handled. The heartbeat counts show the retry slowing down, discussed in Stop 4.

The line on the wire

Each body is the type the matching one-shot command already prints (lf roadmap --all --json, lf session list --json, and so on), so Swift keeps its decoders and the saved launch workspace from LOO-376 keeps working.

The loop that produces it

One loop reads the parts in turn. A Session commit that lands while planning is being read waits for it. That wait was about 2 s when this page was first written and is about 0.2 s now, because the planning reading itself got faster (Stop 5). The loop is unchanged; the wait grows again if the reading does.

2 · What counts as a change

The store keeps four counters. A trigger on each displayed table adds one inside the writer's own transaction, so every writer is counted, including older installed lf binaries and sqlite3, and a rolled-back write counts nothing.

Transcript lines were 164,192 of 168,336 Session events in a day on Jack's Home. Counting them would re-read every part for ten hours a day, so the trigger skips the evidence types no summary reader selects, plus usage.

The predicate has already been wrong once. Its first version skipped every :events.jsonl: row and silenced about 1,270 displayed rows a day. If it skips too much, a row stops updating and the 1 s re-check cannot catch it, because it reads the same counters. A test walks each fact session list shows; Work activity and a Wave's Session history have no such test.

Token totals lag by design of the predicate, not by decision. Usage rows move nothing, so totals refresh at the next displayed change or the five-minute clock.

How a new table is kept from being forgotten

A store test lists every table and fails unless it has all three triggers or appears in NEVER_DISPLAYED (rust/loopflow/src/store/sqlite/revisions.rs). It checks that triggers exist, not that each is assigned the right counter.

3 · Desktop applies a frame

PodiumModel remains the window's single owner of what is shown. Every frame passes the same four questions before it changes anything: is it newer, is it from this Home, does it answer the last local write, and is it for what the window shows now.

A local write and an explicit refresh use the same request. The number it returns becomes a floor; frames below it were read before the write.

Two guards now protect the same reads. sessionsGeneration and roadmapGeneration still guard the one-shot paths, which run when no reader is open: session fixtures and about sixty call sites in four test suites. With a reader open, the floors do the work. The plan lists the one-shot bodies as still to delete.

A frame from another Home is applied after dropping the old Home's content, where the design said it would be ignored. The reader exits when the Home changes, so one reader never sends two Homes.

4 · Failure and recovery

The reader is a foreground child of the window. When it ends, the window keeps its rows, marks them unavailable, and reopens the reader after 1 s, doubling to 30 s. A new reader numbers frames from one and reads the store as it is, so every floor resets.

Inside the reader, a store file that exists and cannot be opened is reported, not treated as absent. This was found on a Home copy at another schema, which read as an empty workspace. A part whose reading fails is read again without waiting for a change, each time after twice the wait.

The transcript in Stop 1 shows the backoff. After the failed reading at 5.1 s the planning count reaches 4 by 8.6 s and stays there through 12.6 s: retries after about 1, 2 and 4 seconds, each rounded up to the loop's one-second check. No frames are sent for them, because the failure text is unchanged.

Backoff applies only to the idle retry. In due, a changed counter or a request still reads the part at once. A part that fails while agents commit is read as often as a healthy one. The 60 s cap is a guess, and none of this was run against a failing copy of Jack's store.

What else catches up

A missed filesystem event is covered by re-reading the four counters every second. Waking the Mac sends refresh. SQLite removing and recreating its log file is handled by re-arming the watch (StoreChanges::wait); that case is tested on the waiter, not through the binary, because a running reader holds the log open.

5 · The planning read made cheap enough to run on change

A stream that delivered a 20 s old answer would not help. Sampling the reader on a copy of Jack's store put 83% of a planning reading in one statement: which unfinished Execs belong to this Task, asked once per unfinished Task. It is now asked once per reading, for all Tasks.

The index and join order are pinned by hand. INDEXED BY and CROSS JOIN are there because the bundled SQLite otherwise scans every Exec: 350 ms against 23 ms. The statement fails outright if the execs_unfinished index is ever dropped or renamed.

The plan's rule is met for Exec membership only. The rule was a fixed number of statements per reading, never one per Task. task_open_work still calls members per Task, which walks that Task's Sessions including finished ones, and the gate then reads each Session's driver, row and pending turn. That is about 30 ms of a reading on 140 Tasks. It was left because the reading fits its budget and the remaining reads are the same completion rule lf task complete uses. Nothing bounds it as Tasks grow.

6 · Which finished Tasks stay in the outline

A finished Task stays visible while it still has started work nobody settled. Rust now decides that and sends it as a required field on the Task's condition; Swift's copy of the rule is deleted.

Half the rule moved. “Has open Sessions” and “started” stay in Swift, because they join Session rows the window already holds. Moving them means Rust joining Sessions into the planning part.

This function is also where the Task's first acceptance line fails. guard started else { return false } keeps a Task with no Run out of the outline. See Open decisions, 1.

The field is required, with no default. Workspace text saved by an earlier build lacks it, so the first launch after upgrading should show no saved planning until the reader answers. That follows from LOO-376's rule that saved text goes through the live decoder; it was not exercised.

Open decisions

  1. A Task with no started work does not reach the left outline. LOO-382 asks that a new Task appear in the left pane “without an execution-start prerequisite”. On 2026-09-25 Jack Heart accepted an outline of started Tasks only. The stream delivers the Task; the outline filters it (Stop 6). Counterexample: lf task create --wave product --title "Reactive demo" with no --run appears in Product's Task list and not in the outline until a Run or Session exists. Nothing was changed. Jack has not chosen.
  2. No derived state is stored. After the first walkthrough Jack said which Waves and Tasks are current should be very simple and fast, that “i think we want it in the db”, and that “this db's only purpose really is to serve this UX.” The branch instead keeps the wire and Swift types, reads in bulk, and stores nothing derived, on the measurement that one per-Task statement was the cost. That choice was made without Jack's confirmation. Stored display rows remain the next step when a bulk reading stops fitting; how they would relate to the execution authority the store also holds is not worked out.
  3. The window has not been re-measured. The last rendered run predates Stop 5: debug builds, 3 samples, a Task change 2.3 s against 1 s and a Session row 0.55–0.6 s against 0.5 s. The reader alone now answers in 0.3 s and 0.13 s. Whether the targets are met on screen is unknown until the benchmark is rerun; the 20-sample release run is still owed. Jack decided a miss ships with numbers and a follow-up Task. None is filed, and it is not yet known whether one is needed.
  4. A first reading still takes 4.2–4.6 s. About 1.7 s is Git asked about 32 existing checkouts one after another. A launch shows saved text first, so this is the wait for the first refresh, not the first frame. Asking Git about the checkouts at once was not built.
  5. Git-only changes show later than before. A dirty checkout used to show within the 15 s poll. Now checkout contents are re-read at most once a minute and only when planning is read, which without a commit is every five minutes. Nobody chose this.
  6. Polling is not entirely gone. A window runs two readers, because monitor active --watch was not folded in. The Task-files comparison still starts lf every 10 s while shown; each start writes an Exec, which moves execs and re-runs planning in the watch.
  7. The shared store changed without Infrastructure's review. One table, three triggers on each of 25 displayed tables (75 in all), and three indexes, two of them widened in the later slices to cover the bulk read. The session_events trigger parses each inserted payload as JSON; its cost on large transcript lines is unmeasured.
