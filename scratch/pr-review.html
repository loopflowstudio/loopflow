01 / Task

A save succeeds before Linear answers

TaskId already existed. The changes are optional Linear mapping, a local write revision, optional observation age, and Task.worktree: Option<PathBuf>. TaskPlan remains a nested subset of Task: state, rank and assignee still appear through PmItem. No model consolidation is claimed.

The input now accepts rank and nullable assignee as well as title/notes. The common store writer checks the expected local revision and saves fields with their receipts in one transaction. An invalid title or stale revision leaves the prior value intact; re-reading and reapplying the edit uses the current revision. A successful return promises a local save, not a completed provider write.

Creation identity is generated here; uncertainty stays with that identity

This replaces the rejected public creation-token option. Separate explicit creates produce separate IDs even for identical titles. Automatic export retains the saved ID. If a create reply is lost, export observes that exact identity before doing anything further; an attempted create with no confirmed result remains uncertain rather than minting another issue.

02 / Project

Plan edits and Task order become local mutations

KRs, targets and the default Workflow retain their existing shape. The Project’s provider link becomes optional, and its mutation API returns the locally saved plan with synchronization evidence.

The outer Project identity and Wave membership remain. PmProject now also projects locally authored data; prompt_context still encodes the content from which KRs and targets are parsed. planning reads both the saved Project and its receipts. This changes what success means without inventing a second kind of Project.

One reorder changes the list

Moving a Task changes other Tasks’ displayed ranks too. This PR removes scalar Task-rank delivery and gives the Project one task_order receipt containing the list, its provider baseline and attempted moves. Partial delivery is compared with those recorded intermediate lists, so Loopflow’s own move does not masquerade as a competing Linear edit.

Inspect the Project ordering writer and its provider delivery. New members survive; ambiguous omissions defer delivery. A competing observed Linear order wins while the losing local list is retained. Equal sort keys need intermediate moves; unrepresentable intervals remain visibly pending.

03 / Wave

Editing a file stops being editing the active Wave

The Wave identity type is unchanged. Its goal, memory and reusable Workflow definitions now belong to stored rows keyed by WaveId. Repository files become import sources.

The function signature stays the same while its persistence contract changes. Reads use stored documents too. Changing an already-imported GOAL.md or MEMORY.md file does not replace the active saved content. Missing stored definitions direct the caller to lf wave ensure; ordinary reads do not silently provision.

Import fills missing records and preserves existing edits

Source files remain intact, stored edits survive repeated import and renamed addresses retain identity. This is local preservation, not cross-machine backup. LOO-412 owns Git-ref synchronization; execution records remain local.

04 / Delivery and visibility

Reconnect without another turn or manual refresh

Previously these operations depended on provider-first writes and narrower acquisition paths. The new foreground lifetime independently acquires planning/comments and delivers saved effects. Repository and Wave views now keep that lifetime even when no Task is selected.

Task selection changes the view, not the synchronization owner. Removing the repository or closing the connection drops the lifetime. No resident service is introduced, so a closed CLI/Desktop connection does not promise ongoing propagation.

Independent incoming and outgoing loops

Acquisition waits 15 seconds after an attempt; delivery waits one second. These are scheduling intervals, not latency guarantees. A pending field write does not prevent comment/state acquisition. Publication and execution completion are not granted by this observer.

Saved, uncertain, or superseded

CLI and Desktop now consume the same receipt-derived status instead of a completion-only pending flag. Creation without a Linear mapping is included. When Linear is disconnected, pending delivery is hidden while retained conflict history remains available.

Swift’s text formatter mirrors the CLI formatter. Their DTO and view fixtures are authored; final runtime proof remains outstanding.

Example: local title A → B saves offline. If Linear still has A, B remains pending; if Linear has independently changed it to C, C wins and B is retained as the losing edit. A later local save must survive an earlier write’s acknowledgement. Importing completion changes planning evidence without moving a captured Workflow, stopping a Process or cleaning a checkout.
