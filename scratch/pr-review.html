1 · Running an edge

The WHERE clause is the rule: the update only lands if the Task still stands at the edge's own node and, if it is on a stopped edge, on that same run. Two callers choosing at once cannot both leave. An edge that runs nothing moves straight to its target.

Fits the decisions. Jack: “live states in the LFDB”; “the graph is fixed upfront when it's loaded and never mutated” (a trigger refuses any update of graph); each edge is “a unique step (flow/skill)”, so an edge is named by what it runs.

2 · One run, several Flow execs

Fits the decisions. Jack: “lf task run should … also have some amount of retry”; “run is one conceptual attempt, exec is one lf invocation”. The count of three, retrying with no pause, and not retrying a Flow that ended blocked or was interrupted are the agent's.
Changed from the last review. A stopped edge now holds the Task on the edge. Before, a failure returned it silently to its node.

3 · Setting a node, and the history

Unguarded on purpose. lf task move accepts any node from a node or from an edge, and stops nothing that is running. It is the correction tool for hand work and late merges. Desktop shows the position but not this history.

4 · A Task's state

Fits the decisions. Jack: “no separate Task is ready state; that is derived from where it is in the graph”; “active”; “abandoned/deleted bool should still stay”. tasks.work_state is dropped by the draft migration. When Linear calls an active Task complete, end is refused without --force, which Jack preferred to a separate clear command.
Existing Tasks. On an existing Home every done Task is placed at the end of an empty graph named unplanned. Every started, unfinished Task has no Workflow and reads not ready until its next lf task run. Jack allowed either treatment; this is the agent's pick.
