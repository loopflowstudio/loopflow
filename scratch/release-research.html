Release research: minors from main and release streams

None of the projects studied pairs a minor release with a patch. They either cut from main or promote a build that already ran on a faster stream. For loopflow the hard part isn't streams. It's the reader floor: one store is shared by the CLI, Desktop and every stream on a machine, so a fast stream that raises the floor leaves stable unable to open it.

What broke v0.15.0

Today's minor (release.rs:766) cuts from patch_commit. It skips the prepare hooks (:1902), refuses NeedsIntegration (:2088), requires the merged tree to equal prepared_tree (:1235), and refuses any draft migration (:1258). #1751 hit two of those guards. 635d99fee has no tag, and wave_setup.sql is still a draft.

The interrupted implement step left an uncommitted diff (−307/+25) that removes all of that pairing. With it, minors cut from main, run prepare, and base their notes on the previous .0. Not yet updated: the tests at release_tests.rs:1321-1456 and the docs that call a minor "the same product snapshot".

The floor across streams

There are three positions, each with a cost:

  • Older reads newer (Codex, Zed). Migrations are additive only, and a breaking change gets a new file. There's no floor at all. Loopflow chose a floor on purpose.
  • Older refuses newer (Rex, loopflow today). This is safe. But if dev or beta raises the floor, stable on that machine can't open the store. Rex reduces the pain by saying which side to update.
  • A store per stream (Zed, VS Code Insiders). No machine gets stranded, but Tasks split by stream. That's probably wrong here, because the store is the work model.
Proposed reading, not decided: let any stream ship additive migrations, but only a minor promoted to stable may raise the floor. That would give "minor" a meaning again that doesn't depend on pairing.

Desktop updates

Today lf install is the only updater, for both the CLI and /Applications/Loopflow.app. That already keeps the two in lockstep. There's no Sparkle, no in-app check, and an app that's already running isn't restarted. Ghostty's pattern is two separate appcasts chosen by a setting (Sparkle's own channels can't leave the default channel), a staged appcast that's promoted only after every asset returns 200, and a monotonic CFBundleVersion.
