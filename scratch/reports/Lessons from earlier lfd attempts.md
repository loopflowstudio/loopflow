# Share complete operations, preserve one owner

The history supports Jack Heart's concern about multiple code paths, with a qualification: **earlier lfd versions already shared engine code**. The strongest demonstrated defect appeared in orchestration surrounding a shared executor. Later, shared operations still had multiple possible lifecycle owners. A Machine service is therefore defensible when it exposes complete existing operations and removes replaced delivery paths. It does not become safe merely by importing the same Rust crate. Neither deletion proves a finished thin server or complete mobile workflow was tried and rejected; both accompanied broader changes in product scope.

## The first daemon sought the same consolidation

January's Python lfd explicitly centralized spawning, monitoring, Session tracking and SQLite writes, replacing multiple pollers and giving Swift a socket connection. launchd allowed it to survive app restarts. The Rust migration quickly combined control protocols, scheduling, run orchestration and webhook handling. Centralization was the original intent, rather than a lesson discovered only now. ([Original daemon](https://github.com/loopflowstudio/loopflow/commit/6ea523cf27ebd57e59f21e1b6fa72c4f8ad97c54), [Rust migration](https://github.com/loopflowstudio/loopflow/commit/d99b430532d41f2a02ec02f73e556c992cbb6ea4))

**PR #304 supplies the clearest concrete example of semantic drift.** HTTP run and continue handlers called the same executor, but failure updated both Run and Wave in one path and only Run in the other. Extracting shared spawning/finalization repaired the mismatch. By June, CLI and REST also shared `ops::land`, while HTTP separately resolved worktrees, selected options, synchronized PR/run state and emitted events. Those wrappers were substantial behavior, although not every difference is evidence of a bug. The useful unit of sharing is the complete operation, including its defaults, state transitions and cleanup. ([Failure repair](https://github.com/loopflowstudio/loopflow/commit/d96f6a2eb90c5669455cba40510d7d2773d87182), [June HTTP orchestration](https://github.com/loopflowstudio/loopflow/blob/7099cacb1de24e6dfaeb56e3657c1ec01ad8410b/rust/loopflow/src/lfd/http/routes/waves.rs#L1215))

Other defects survive even perfect command sharing. Restarting lfd lost in-memory Docker ownership, leaving running containers invisible, disrupting output and accumulating orphans; #331 persisted container identity and added recovery. #513 bounded output retention, closed writers and removed obsolete reconciliation locks. These are concrete durability and resource-lifetime repairs. A service with independent Session owners addresses a different failure boundary, but must demonstrate that independence under its actual supervisor. ([Restart recovery](https://github.com/loopflowstudio/loopflow/commit/f7af78c0740deebedb678ec656fca67d39cdf96c), [Resource repairs](https://github.com/loopflowstudio/loopflow/commit/a40a8dc9070861db1f305da51fe6b3eaf56d85e2))

## CLI delegation arrived, but its cutover stayed unfinished

July 6's #825 implemented a real state-free argv adapter: validate with the CLI's Clap tree, launch the resolved `lf` without a shell, return status/stdout/stderr. It was not an interactive terminal transport. Immediately before deletion, older mutation handlers still performed git/worktree operations and state writes, with an explicit TODO to convert them to exec or remove them. Swift used new local CLI queries while clients without a runner retained REST reads. **The surviving code demonstrates an incomplete replacement, not failure of a completed single-path design.** ([Exec implementation](https://github.com/loopflowstudio/loopflow/blob/93960b439d3dab0466f8150f47745b18e5fef670/rust/loopflow/src/lfd/lf_exec.rs), [Remaining handlers](https://github.com/loopflowstudio/loopflow/blob/be285d5d401fe150ac2f9bdfa884b5dbcc7f6366/rust/loopflow/src/lfd/http/routes/waves.rs#L29), [Swift split](https://github.com/loopflowstudio/loopflow/blob/93960b439d3dab0466f8150f47745b18e5fef670/swift/LoopflowCore/Services/RegistryQuery.swift#L1))

The #825 PR body is stale: it describes an additive change without Swift edits, whereas the landed commit includes Swift changes and substantial deletion. July 14's #872 then removed lfd during a broader model/runtime cutover and retained a resident Wave server. Its description calls the iOS shell non-functional; that is a contemporary judgment, not evidence that a complete editable mobile terminal had been demonstrated and rejected. Source and landed changes must outrank proposal text. ([Landed #825](https://github.com/loopflowstudio/loopflow/commit/93960b439d3dab0466f8150f47745b18e5fef670), [First removal](https://github.com/loopflowstudio/loopflow/pull/872))

## The second daemon shared functions but multiplied ownership

The July 16 replacement began with three routes: health, status and signed Linear webhook ingress. It durably recorded deliveries before acknowledgment and reused existing domain ingestion. It soon acquired worktree pruning and Home supervision. #1161 subsequently removed Desktop's separate tmux startup/polling path in favor of `lf start`, demonstrating the value of consolidation within this generation too. ([Narrow ingress](https://github.com/loopflowstudio/loopflow/pull/1012), [Home supervision](https://github.com/loopflowstudio/loopflow/pull/1119), [Startup consolidation](https://github.com/loopflowstudio/loopflow/pull/1161))

By September, CLI and daemon could invoke the same landing supervisor under Local or Home claims. Fencing prevented uncontrolled double execution; fallback, heartbeat and stale-claim recovery still had to coordinate two potential owners. The retained inventory also found launchd/systemd installation alongside tmux fallback startup, and two webhook receivers sharing processing but offering different durability guarantees. **Sharing an algorithm did not select its lifecycle authority.** ([Local landing](https://github.com/loopflowstudio/loopflow/blob/42ed461d1ee718fb3f791750454d4eb99a3afd79/rust/loopflow/src/ops/pr_landing.rs#L897), [Home recovery](https://github.com/loopflowstudio/loopflow/blob/42ed461d1ee718fb3f791750454d4eb99a3afd79/rust/loopflow/src/lfd/mod.rs#L306), [Contemporaneous inventory](https://github.com/loopflowstudio/loopflow/blob/42ed461d1ee718fb3f791750454d4eb99a3afd79/scratch/cutover/cut-i-lfd-research.md))

Some multiple paths were appropriate. Polling and webhooks reused reconciliation and comment identity while observing different delivery sources. September's deletion deliberately sacrificed resident/listener/webhook features to reduce scope and ship planning and delivery. No inspected evidence establishes a particular outage as its cause or ranks duplication as the largest measured problem. The justified historical claim is narrower: repeated consolidation repairs and overlapping ownership added maintenance obligations. ([Shared observations](https://github.com/loopflowstudio/loopflow/pull/1275), [Second removal](https://github.com/loopflowstudio/loopflow/pull/1360))

## Today's service must preserve sharing already present

Current Desktop FFI already calls shared Rust reads, writes and subscriptions; its watches reuse `lf watch` machinery. Other commands use CLI subprocesses. Moving these behind a socket changes availability and failure boundaries, rather than introducing engine sharing for the first time. Desktop's create/start command already owns Task creation, workflow launch and primary conversation admission. A service should delegate that whole command instead of reconstructing its sequence. ([Current Desktop adapter](https://github.com/loopflowstudio/loopflow/blob/2bc29a72e0c3479dff528a4232e8d9d18268a0b2/swift/LoopflowMac/Services/RegistryQueryLocal.swift#L12), [Shared reads](https://github.com/loopflowstudio/loopflow/blob/2bc29a72e0c3479dff528a4232e8d9d18268a0b2/rust/loopflow/src/lf/commands/read.rs#L349), [Create/start](https://github.com/loopflowstudio/loopflow/blob/2bc29a72e0c3479dff528a4232e8d9d18268a0b2/rust/loopflow/src/lf/commands/task_create.rs#L1))

The architectural inference is to permit CLI and socket adapters while assigning resolution, defaults, writes, attribution and recovery to one complete operation. CLI need not depend on the service. Native subscriptions should call existing readers. Authentication, framing and buffering belong at transport boundaries; Task orchestration and durable business receipts do not belong exclusively in the gateway. A received partial-success receipt already preserves a created Task after launch failure, but cannot resolve a reply lost after external creation. Recoverable request identity must reach shared command admission.

The proposed proof is behavioral: compare CLI and socket Task results, state and attribution; compare initial/change/error/cancel watch behavior; lose a create reply, restart and recover one Task or report unknown; fail a remote route without local mutation. Restart the installed service during an agent Session and verify the same owner/provider survives. Exercise concurrent startup, helper replacement and bounded slow-client cleanup. These checks target observed historical weaknesses while exposing new socket/version boundaries. Finish the Work cutover and delete migrated FFI glue; preserve renderer FFI and existing runtime owners.

## The optional hub needs a delivery boundary

A future hub can own public delivery acknowledgment, durable ingress and retransmission while the Machine owns domain admission and execution. Polling must remain another producer of the same observations, rather than a rival implementation. That leaves useful eventual hub functionality without making private development depend on it. The sharper design question is therefore where an operation becomes authoritative and recoverable—before adding another always-running place that can perform it.
