# Give Desktop and mobile one backend

Research for Jack Heart · November 3, 2026

**Loopflow Desktop does not currently install the proposed Machine server.** It starts an app-owned automation socket; Work reads, writes and subscriptions cross a C binding into Rust, while other commands invoke `lf`. Jack Heart's proposal to move those Work operations onto a socket provides a stronger reason for automatic service setup: Desktop itself would require the backend. Recommend automatically registering and connecting to a same-user local service, with remote Tailscale access enabled separately. Rex provides concrete precedent for that separation, and Paseo demonstrates a shared local/remote protocol. Installation, registration and update details remain proposed, not approved implementation. ([Current Desktop server](../../swift/LoopflowMac/DesktopServer.swift), [local Work adapter](../../swift/LoopflowMac/Services/RegistryQueryLocal.swift))

## Rex demonstrates a separate Mac server

Read-only inspection found Rex Beta 0.1.0 build 1696 running a separate **user launchd LaunchAgent**. Its executable came from a versioned Application Support installation, distinct from the bundled server helper and main app process. This verifies an actual supervised server, rather than merely an advertised architecture. It does not establish first-launch registration, automatic startup after login, survival after app quit, or uninstall behavior. The job's reported source plist was absent when checked, and neither the app layout nor launchctl metadata proves `SMAppService` usage. No active service was disturbed. ([Sanitized local observations](<../research_notes/Machine service installation and lifecycle/rex.md#local-observation>))

Rex's public Mac documentation says local communication uses a Unix socket and begins without network or Tailscale listeners. Settings separately exposes server status, API compatibility, uptime, the local socket and remote serving readiness. That is a useful product pattern: ordinary local use works immediately; remote access has its own setup and diagnostics. Loopflow should borrow the separation and visibility without claiming Rex's unverified login or upgrade behavior. ([Rex privacy](https://www.superlogical.com/rex/docs/reference/privacy), [Mac settings](https://www.superlogical.com/rex/docs/reference/mac-settings))

Rex's Linux/FreeBSD contract is more explicit. Personal servers start on demand, while the login frontend delegates to account servers that can outlive it. Shared-server restarts end Sessions; account and personal servers can retain their running version until work drains. These are valuable examples of documented boundaries, **not evidence of identical macOS behavior**. Installed version and running version deserve separate presentation in Loopflow, especially when busy Session owners retain an older executable. ([Server modes](https://www.superlogical.com/rex/docs/linux/server-modes), [upgrading](https://www.superlogical.com/rex/docs/linux/upgrading))

## Borrow protocol contracts rather than another domain model

Rex's server API exposes method discovery, schemas, validation errors and version information. Attach/bootstrap associates a snapshot with an event sequence, and overloaded consumers disconnect rather than silently miss updates. Separate data connections use expiring tickets. Client-native actions are routed to a named client instead of pretending the server can focus an absent window. These patterns address the hard parts of a shared backend: coherent startup, bounded traffic, compatibility and explicit authority. Public documentation does not specify enough detail to promise a wire-compatible Rex implementation. ([API guide](https://www.superlogical.com/rex/docs/automate/server-api), [API reference](https://www.superlogical.com/rex/docs/reference/api))

For Loopflow, the existing typed query facade and DTOs can remain while their transport changes. The service should use the same Rust `Read` and `Subscription` implementation, execute typed command requests through `lf`, and bridge existing Session-owner sockets for terminal traffic. The C binding for Ghostty rendering remains a different responsibility. Window focus, menus and visible pane arrangement remain in Desktop's own automation interface. **If the Work cutover is selected, delete the migrated FFI route** rather than keep a permanent direct-call fallback that can diverge from mobile. ([Swift query facade](../../swift/Loopflow/Services/RegistryQuery.swift), [FFI adapter](../../swift/LoopflowMac/Services/LoopflowLibrary.swift), [Rust reads](../../rust/loopflow/src/lf/commands/read.rs))

Local and remote clients can share operations without sharing authentication. Rex explicitly warns that forwarding Tailscale Serve into an ordinary trusted Unix listener identifies the proxy's local account instead of the remote caller. Loopflow needs distinct local-peer and remote-admission boundaries, even when both reach the same methods. The phone's credential and expected Machine identity must survive proxying; tailnet reachability cannot impersonate the desktop user. ([Rex remote access](https://www.superlogical.com/rex/docs/linux/remote-access))

## Comparable tools expose the lifetime choices

Paseo bundles and automatically starts its daemon. Its current Desktop defaults set `keepRunningAfterQuit` to false: quitting stops the owned daemon unless that setting is enabled. Stopping for ordinary quit closes terminals; update or version-mismatch replacement can preserve them on supported platforms. Its detached worker enables continuity, but shutdown policy still decides whether to use it. The examined paths do not establish launchd registration or login persistence. ([Desktop defaults](https://github.com/getpaseo/paseo/blob/main/packages/desktop/src/settings/desktop-settings.ts), [quit lifecycle](https://github.com/getpaseo/paseo/blob/main/packages/desktop/src/daemon/quit-lifecycle.ts), [daemon manager](https://github.com/getpaseo/paseo/blob/main/packages/desktop/src/daemon/daemon-manager.ts))

Paseo also carries WebSockets over local Unix sockets or pipes while retaining windows, dialogs, notifications and editor launching in Desktop. That supports Loopflow's proposed shared protocol without moving every native responsibility into the service. WezTerm's mux bootstrap supplies another example of automatic server startup without proving startup at login. Happy's newer runtime instead drains and resumes checkpoints during updates; that is recovery of its own harness, not preservation of arbitrary vendor CLI PTYs. These mechanisms should be compared by the state they preserve, not grouped under “background daemon.” ([Paseo local transport](https://github.com/getpaseo/paseo/blob/main/packages/desktop/src/daemon/local-transport.ts), [Desktop bootstrap](https://github.com/getpaseo/paseo/blob/main/packages/desktop/src/main.ts), [WezTerm](https://wezterm.org/multiplexing.html), [Happy updates](https://happy.engineering/updates/))

## Make launchd automatic without hiding its boundaries

Apple's `SMAppService` supports registering a bundled per-user LaunchAgent, bootstrapping it immediately and at subsequent logins. Ordinary background registration can be automatic with system notification and user control; it does not justify an additional routine Loopflow permission prompt. If macOS has disabled the item, show that state and its repair path rather than repeatedly registering around the choice. A personal LaunchAgent is a logged-in-user service: it does not promise availability after logout or before login. Sleep makes the host unavailable; reboot destroys live processes. ([Registration](https://developer.apple.com/documentation/servicemanagement/smappservice/register()), [Apple background-item guidance](https://developer.apple.com/videos/play/wwdc2022/10096/), [launchd lifecycle](https://developer.apple.com/library/archive/documentation/MacOSX/Conceptual/BPSystemStartup/Chapters/CreatingLaunchdJobs.html))

The installed Apple SDK requires re-registration when the agent plist or executable changes and recommends unregistering first for executable replacement. **Unregister terminates the helper.** Therefore, service update must reconnect clients while independently owned Session processes continue; `setsid()` alone is not proof against installed supervisor cleanup. An update test with active work matters more than another successful first launch. The exact behavior must also be proved under Linux systemd, whose cgroup boundary differs. ([Apple SDK evidence](<../research_notes/Machine service installation and lifecycle/apple-loopflow.md>), [runtime research](../research-runtime-lifecycle.md))

One installation authority should reconcile the selected signed bundle, registered helper and public `lf` entry. Desktop and CLI must not install competing servers. A bundle-relative helper fits `SMAppService`; Apple's GUI-less signed bundle example provides a standalone distribution option. Whether Loopflow keeps the helper in the promoted Desktop app or a separately installed signed container remains open, because that choice changes updates and removal. Removing registration should not erase Work or credentials, and deleting Desktop must not silently masquerade as a supported standalone installation. ([Apple standalone package sample](https://developer.apple.com/documentation/servicemanagement/updating-your-app-package-installer-to-use-the-new-service-management-api), [Loopflow installation authority](../../rust/loopflow/src/installation.rs))

The decisive next proof is a local Desktop client using the proposed protocol while the service restarts and an existing Session keeps running. Add the phone only after that same contract handles readiness, subscription replacement and stale input authority. This makes mobile an additional client of a proven boundary and exposes the lifetime failure modes before they become remote troubleshooting problems.
