# Second-generation lfd: shared operations, overlapping owners

Research question: does the July–September 2026 daemon support Jack's hypothesis that multiple code paths were the main problem, and that a shared engine changes the architectural choice?

## Takeaway

The evidence supports the concern about multiple paths, with an important refinement: the second lfd already reused substantial domain logic. Its later problems were also about **multiple ways to start, keep alive, claim, discover, and recover the same work**. Sharing an engine reduced duplicated business rules; it did not automatically give each operation one lifecycle owner.

This history does not establish that a daemon was inherently wrong. The second daemon began with a useful, bounded capability, then accumulated other useful responsibilities. Its removal explicitly sacrificed those capabilities to reduce product and maintenance scope. Persistent returns to a server are evidence of continuing demand; the expanding ownership arrangements show why satisfying that demand was difficult.

## What changed, and why?

1. **July 16: durable webhook ingress.** [PR #1012](https://github.com/loopflowstudio/loopflow/pull/1012), merged as `48f02ffd5bfafa775ef7b37a83eef5f6a7de8955`, introduced three routes: health, status, and Linear webhook. Verified deliveries entered a durable inbox before acknowledgment, with delivery deduplication and recovery of pending deliveries after restart. Domain processing called existing `webhook::ingest_event`; delivery identity and semantic idempotency were deliberately separate. A per-user launchd/systemd installation made it available continuously. It was explicitly not a general remote API.

2. **July 17: disk recovery.** [PR #1043](https://github.com/loopflowstudio/loopflow/pull/1043), `d833bd08c5e114dcf98812edf243adcb3096c0d5`, added periodic worktree cleanup and signed GitHub merge/delete events. The stated problem was concrete: multi-GiB incremental build state in short-lived worktrees. Automatic pruning was conservative; manual pruning intentionally had broader behavior. The daemon became an attractive home for a second background responsibility almost immediately.

3. **July 20: Home supervisor.** [PR #1119](https://github.com/loopflowstudio/loopflow/pull/1119), `9f91fc5d637d948eddfb39dd8788edac87e0bece`, made commands machine-local and SSH an explicit remote boundary. lfd acquired an in-process WaveHost that reconciled assigned Waves and authenticated local start/stop operations. This was part of clarifying authority and credential boundaries, not merely adding another executor. The PR reports that its live remote-machine probe timed out; its automated test results are not proof of that remote installation working.

4. **July 21: unify startup and make success truthful.** [PR #1161](https://github.com/loopflowstudio/loopflow/pull/1161), `cc3f7a44fb54f3bbc1f9e17b478c38a57667379f`, changed `lf start` to return success only when the Home daemon and listeners were reachable and durable observations drained. It added startup serialization, receipts, shared in-flight starts, per-Wave results, and rollback of failed registration/placement changes. Most relevant to Jack's hypothesis: **Mac Wave Chat switched to `lf start`, removing its separate tmux launch/poll path.** This is explicit evidence that consolidating a UI path into the CLI mattered.

5. **August 22: durable landing supervision.** [PR #1231](https://github.com/loopflowstudio/loopflow/pull/1231), `3441ee5d43c777f07affa1b7b599ab0186aed4ce`, introduced a watched landing lifecycle with generation-fenced claims, heartbeats, CI repair, and Home recovery. It removed the Task runner's separate CI-repair flow. Again, unification was already an objective; durable recovery subsequently required coordinating local and daemon placements of the shared supervisor.

6. **September 24: one authored steering record.** [PR #1275](https://github.com/loopflowstudio/loopflow/pull/1275), `7160f3637b590988cd2304a186d5c80941c44b65`, made Linear comments the authoritative authored direction and the advancing Task worker its consumer. It removed several older steering surfaces. Polling and webhook ingestion converged on shared reconciliation/deduplication machinery. They did not become literally identical call stacks: issue-edit webhooks called `reconcile_linear_observation`, while comment webhooks used shared comment rendering/revision identity and the store's `apply_linear_comment` path.

7. **September 27–30: inventory, then deliberate removal.** The [retained September 27 inventory](https://github.com/loopflowstudio/loopflow/blob/42ed461d1ee718fb3f791750454d4eb99a3afd79/scratch/cutover/cut-i-lfd-research.md) explicitly says the first daemon's generic CLI/client split was gone: Swift called `lf`, and lfd had no generic remote command API. It identifies the remaining issue as “same-operation-two-owners.” [PR #1360](https://github.com/loopflowstudio/loopflow/pull/1360), `3dc89bc9a062148a884e36db8f9528842e833d13`, then removed resident Waves, listeners, lfd, webhooks, and chat surfaces to ship planning and delivery with less maintenance. It removed roughly 35,000 lines. The actual PR changed no database tables or migrations, despite a more aggressive migration proposal in the [deletion brief](https://github.com/loopflowstudio/loopflow/blob/42ed461d1ee718fb3f791750454d4eb99a3afd79/scratch/cutover/cut-i-delete-listeners.md).

## Where was the engine shared, and what still duplicated?

**Desktop command execution was substantially consolidated.** The retained inventory traces Mac startup to `lf start --json`, then Home startup/control, then WaveHost spawning `lf __resident`. Mac stop used `lf stop`. This was not Swift and lfd independently implementing Task execution. But the resulting chain still crossed several process owners: system keeper, daemon, Wave supervisor, resident process, plus detached processes started through tmux.

**Landing used one algorithm with two potential placements.** In [ops/pr_landing.rs](https://github.com/loopflowstudio/loopflow/blob/42ed461d1ee718fb3f791750454d4eb99a3afd79/rust/loopflow/src/ops/pr_landing.rs#L897), `watch_armed` tried an lfd claim and then entered `wait_for_landing`; the latter could acquire a `LandingPlacement::Local` claim and invoke `supervise_pr_landing`. In [lfd/mod.rs](https://github.com/loopflowstudio/loopflow/blob/42ed461d1ee718fb3f791750454d4eb99a3afd79/rust/loopflow/src/lfd/mod.rs#L306), daemon recovery acquired `LandingPlacement::Home` claims and invoked the same operation. Fencing prevented this from being uncontrolled double execution. Nevertheless, two owners, stale-claim recovery, and fallback semantics remained necessary to understand.

**Polling plus webhooks can be a sound pair.** [Polling](https://github.com/loopflowstudio/loopflow/blob/42ed461d1ee718fb3f791750454d4eb99a3afd79/rust/loopflow/src/ops/linear_observe.rs#L102) and [webhook ingestion](https://github.com/loopflowstudio/loopflow/blob/42ed461d1ee718fb3f791750454d4eb99a3afd79/rust/loopflow/src/webhook.rs#L229) reused domain reconciliation and comment identity. Having two observation sources is not itself evidence of duplicate business logic. A more concerning duplication was the separate `lf pm webhook serve` receiver: the inventory found the same signature/parser/ingest operations but no durable inbox, on a different port. Shared functions did not make the receivers equivalent in acknowledgment or crash-recovery guarantees.

**Daemon lifecycle had two installation/start arrangements.** The inventory records `lfd install` for launchd/systemd, and `lfd::ensure` using a tmux fallback with startup attempt IDs, receipts, and a startup socket. The installer had to stop both. `lf install` managed an existing keeper but did not register it. This is a concrete example of extra orchestration paths outside the shared business engine.

**Always-running attracted more ownership.** Wave reconciliation, landing recovery, webhook inboxes, pruning, orphan cleanup, and prompt-log maintenance all accrued to the same server. Some operations already had foreground, worker, or cron paths. The inventory also found overlap between resident cron firing and installed `lf cron` schedules. Its absence-of-callers findings for certain endpoints are repository-search evidence, not proof that nobody used them externally.

## Implications for the proposed Machine service

These are architectural inferences from the history, not historical facts or established performance results.

- **Define one semantic operation and one lifecycle authority separately.** Desktop Unix sockets and mobile connections over host Tailscale may be different transports into the same API. Neither adapter should redefine Task behavior, Session ownership, or retention. Sharing Rust code is necessary but does not decide who can launch or recover a process.
- **Delegating commands to `lf` fits the strongest consolidation in this history.** The service can perform admission, launch the canonical command, and expose its durable results. Avoid adding equivalent service-native Task workflows merely to reduce subprocess overhead. Conversely, shared in-process read subscriptions are reasonable: expose the existing reader/projection engine without a second independent polling implementation in each client.
- **Make installation and startup one policy.** Automatic Desktop installation through launchd can help, provided Desktop, CLI startup, update, and uninstall converge on that same arrangement. The old keeper-plus-tmux fallback is the specific pattern to avoid recreating accidentally. Remote hosts will need their platform's equivalent, with the same ownership contract.
- **Separate transport availability from Session survival.** A service reconnect should not create another Session owner. Retained shells or agent Sessions need an explicit owner, attachment contract, cleanup policy, and failure behavior independent of which UI is connected. A shared engine alone does not establish these properties.
- **Do not assign every background job to the Machine service merely because it stays running.** Subscription multiplexing, command admission, and terminal attachment directly support the agreed mobile experience. Wave residency, scheduling, landing, and cleanup each need a separate reason and an explicit owner before being added.
- **Leave a clean future hub boundary.** A public webhook receiver can retain delivery acknowledgment/deduplication/retry responsibilities, then submit authenticated domain observations to the private Machine authority. Domain idempotency must remain beneath ingress so optional webhook delivery and polling can coexist. This history does not establish whether the future hub needs its own database, queue, or deployment; it establishes which guarantees cannot live only in one transport adapter.

## Evidence limits

The cited PR descriptions report intent and validation, not independent production telemetry. No inspected PR discussion established a particular outage as the reason for deletion. The September inventory is contemporaneous architectural analysis, spot-checked here against landing and Linear source; its entire call graph was not re-audited. Claims about orphan/leak frequency or operational reliability would require incident logs or usage evidence. The removal was explicitly a scope cut and lost real background features, so it cannot be described as a behavior-preserving simplification.
