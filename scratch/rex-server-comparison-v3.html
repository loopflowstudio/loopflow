LOO-593 · PR #1813 at 77ab719b1 against Rex Beta build 1696, API revision 8 (server built October 30, 2026) · November 6, 2026 · supersedes the November 5 comparison

Loopflow's server now matches Rex where a phone needs it, and differs where Loopflow's model does.

Since the last comparison the protocol gained what Rex had and Loopflow lacked: a published schema, attachment by a durable handle, and requests that fail alone. Rex is unchanged. Three Rex choices are still ahead of Loopflow and worth copying in some form: reconnect identity, a ticket for the byte connection, and remote access the server manages itself.

Where Rex is still ahead, and what to take

  • Reconnect identity. Rex's client keeps its id and resumes within 60 s. Loopflow's phone loses every watch on a drop and pays a full reading for each. Loopflow does not need Rex's event log to fix that: a watch that resumes from the last checkpoint the client saw is the same benefit with readings. Filed as eee944.
  • A ticket for the byte connection. Rex never lets a data connection in without a single-use, expiring ticket issued on an authenticated control connection. Locally Loopflow does not need one, since the socket is same-user. Remotely it does, and LOO-718 is already building that ticket; it is now steered to issue it for session.attach.
  • Remote access the server owns. Rex joins the tailnet itself and lets the person choose who on it gets in. LOO-718 relies on the host's Tailscale. That is simpler, but Loopflow then cannot say who connected or refuse a tailnet member. Worth deciding before the phone ships, not after.
  • Examples beside the schema. Rex publishes a request and response example and validation notes for every method. Loopflow already has a fixture for most operations; attaching them to describe as examples would cost little.

Where Loopflow differs on purpose

  • Readings, not events. A client replaces a projection rather than applying a reducer. The terminal stream already owns a byte cursor. Rex's events need its seq bookkeeping; Loopflow's readings need nothing, and measured fine: 63 clients with a watch each read in 23 ms median.
  • One connection for terminal input and output. Rex sends terminal input through control methods. Loopflow passes bytes both ways to the owner, so lf is never between the keyboard and the provider except as a pass-through.
  • Cancellation. Loopflow has cancel {id} for a request or a watch; Rex closes the connection.
  • One revision. Rex speaks nine and translates. Loopflow speaks one, and now fails an unknown operation per request, so a newer client loses one request, not its connection.
  • A Session is a conversation. Rex's session is a workspace of panes; Loopflow's is the provider conversation that survives owner changes. Both call attaching session.attach; a client written against one should not assume the other's meaning.

For the three cases. The phone has what it needs to start except remote admission and checkpoint resume. Desktop gets nothing new from Rex. An agent shed is not limited by this server at all, since agents call lf directly; its open question is Rex's: whether the server, not the host, should own the remote door.
