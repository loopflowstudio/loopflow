Keep the independent execution owners. Rex provides a useful model for the client protocol around them: discoverable methods, structured results and explicit version negotiation. Those choices are independent of whether the server owns running programs. This comparison proposes no implementation change or shipping approval.

The system boundary

Desktop ── framed Unix connections ── lf server
                                      ├─ shared Rust reads / writes / watches

                                                     └─ provider / PTY
CLI ────── shared Rust operations + direct owner access

Rex, as documented by the installed server
App / CLI / Lua ── control WebSocket ── Rex server
                                       ├─ sessions / layouts / blocks
App ───────────── data WebSocket ──────└─ terminal / program
Native client actions ← request routed to the named app

The nouns differ. A Rex session groups windows and blocks. A Loopflow Session is a durable agent conversation; Work and native arrangement live elsewhere. Equating the two would import layout and process-lifetime responsibilities into the wrong Loopflow object. Rex can route native actions to a specific client; that is compatible with keeping our Desktop automation app-owned. Sources: Rex method reference, Loopflow boundary.

Restart behavior makes the lifetime distinction concrete. Rex's Linux personal and account servers retain their old executable while sessions remain; restarting a shared server ends its programs. Its login server is an ingress exception: restarting it preserves independent account servers. Our access server can be replaced while existing execution owners continue. The same-build composed replacement test passed; final rendered continuity, released-version upgrade and Linux replacement remain unproved. Sources: Rex upgrades, Loopflow proof limits.

The wire, side by side

Layer clarification — November 5: Jack Heart asked about within-computer requests. A Unix socket is a local transport; WebSocket supplies a handshake and message protocol above a stream. WebSocket can run over a Unix socket, as Rex's local endpoint does. Persistence is a third choice: our one-operation connections are an implementation decision, not a Unix-socket limitation. The table compares current stacks, not mutually exclusive technologies.

Rex details below come from the installed server's own protocol specification, retrieved over its existing Unix socket. They describe that build, not a claim that every released Rex version behaves identically.

Complete Work readings let Loopflow clients replace a projection without writing event reducers. Rex's sequence contract supports finer updates, with more client ordering rules. The comparison supplies no workload evidence that warrants replacing our watch model.

Similar machinery, different contracts

Both terminal streams combine an initial screen with subsequent output and nonce-tagged APC events. Both use byte positions for stream recovery. Rex's documented initial data uses Ghostty's snapshot format; Loopflow's live attachment uses Ghostty's VT formatter, while ended-screen files use Ghostty snapshots. Shared Ghostty foundations therefore do not make the wire formats interchangeable.

Neither design promises exactly-once mutations after a lost response. An operation may have completed; inspect state before retrying. Request correlation IDs do not solve duplicate creation. This remains a shared-command admission question for mobile, rather than a reason to add a gateway response cache.

Rex block ownership arbitrates presentation such as terminal size and grants no additional rights. Loopflow separates size/color ownership from exclusive input control. Our reconnect policy must retain that distinction; importing the name “owner” alone would obscure it. Sources: installed Rex session.own_block schema and validation notes; Loopflow viewer stream.

What the comparison suggests

1. Keep execution independent of client access. That boundary protects live providers and Graphs during access-server updates. Rex's login/account split also demonstrates that an ingress process need not own the programs it reaches.

2. Make the mobile API discoverable and return domain values. A rename should return its identity/result directly, with diagnostics alongside it. Today our inputs are typed, but many results retain the CLI stdout/stderr shape and require a second decode. Derive schemas and results from the existing shared operations; avoid another method catalogue or mutation implementation. Preserve ordinary CLI formatting at its adapter. This is a proposed improvement, not accepted scope.

3. Decide compatibility before treating the phone protocol as stable. Desktop and its selected local helper can update together. A phone and its host may not. Rex's revision negotiation makes that difference explicit. A small supported version window may suffice for Loopflow; copying eight compatibility layers is not implied. Keep executable selection an installation concern.

4. Choose framing and connection lifetime without moving ownership. A persistent connection can carry requests and subscriptions with either framing choice. WebSocket over Unix locally and WSS remotely could share message handling while retaining local peer credentials and separate remote authentication. This adds HTTP/WebSocket machinery locally; library support for Unix streams must be checked in each client. Keeping custom local framing is smaller at that boundary, but leaves two framing implementations. Neither the comparison nor the saved latency measurements establishes a performance winner. Protocol reuse is a separate reason to consider the change. Sources: WebSocket specification, WebSocket over Unix example API, Unix socket semantics.

Rex currently derives remote admission from the connection's identity, commonly Tailscale, and documents broader authentication as planned. It specifically warns that forwarding the ordinary trusted Unix listener misidentifies remote callers. LOO-593 supplies local access; LOO-718 owns remote admission and iOS. Its pairing design and combined integration need their own review. Sources: Rex remote access, LOO-718 handoff.

Questions for the next design pass

These are comparison choices, not new acceptance gates for the published PR.

  1. Protocol scope: a) preserve custom local framing and improve the shared operation contract first; b) use WebSocket framing over Unix locally and the network remotely. Assess client-library fit and removed code before choosing; both preserve the local Unix transport. Jack has not selected either approach.
  2. Result contract: a) expose typed domain results and generated discovery; b) retain CLI-shaped replies and decode them in each client. a is the larger API simplification suggested by Rex.
