# Wave Area Summaries

## Problem

When a wave step runs, it gets context about the area it's changing (diff, area READMEs, scratch docs). But it gets nothing about the rest of the codebase. An agent implementing a feature in `src/api/` knows nothing about `src/engine/` unless it reads files ad hoc.

This wastes agent turns on discovery. Worse, it leads to designs that duplicate existing patterns or miss important constraints. The agent doesn't know what it doesn't know.

Summaries fix this: pre-generated, cached descriptions of codebase areas that get injected into every step's context automatically. The agent starts with a mental model of the whole codebase, not just its corner.

## Approach

**Summaries are files on disk, generated by running the builtin `summarize` step, loaded by `gather_context()` at prompt assembly time.** No new database tables. No webhook infrastructure. Three pieces:

### 1. Storage: `.lf/summaries/`

Summaries live in `.lf/summaries/{path_hash}.md` with YAML frontmatter tracking provenance:

```yaml
---
path: src/engine/
source_hash: a1b2c3d4
tokens: 4200
generated_at: 2026-02-08T21:36:00Z
model: gemini
---
# src/engine/

Core prompt assembly engine. Key types: `PromptComponents`, `GatherContextOpts`...
```

- `path_hash` = hex-encoded SHA-256 of the normalized area path (avoids filesystem issues with slashes)
- `source_hash` = SHA-256 of concatenated file contents in the area (for staleness detection)
- `.lf/summaries/` added to `.gitignore` (like `.lf/log/`)

### 2. Generation: `lf summarize`

The builtin `summarize` step already exists at `builtins/ops/summarize.md`. Extend it to accept area paths and write output to `.lf/summaries/`.

Generation flow:
1. Enumerate source files in the area path (respecting `.gitignore` and config `exclude`)
2. Compute `source_hash` from file contents
3. Check if `.lf/summaries/{path_hash}.md` exists with matching `source_hash` — skip if fresh
4. Count tokens of all source content
5. If total tokens < 50,000: preload all content into the prompt
6. If total tokens >= 50,000: pass file paths, let the agent read what it needs
7. Run the summarize step with a token budget (from `SummaryConfig.tokens` or `config.summary_tokens`, default 10,000)
8. Write the agent's output to `.lf/summaries/{path_hash}.md` with frontmatter

CLI interface:

```bash
# Summarize all configured areas
lf summarize

# Summarize a specific path
lf summarize src/engine/

# Force regeneration (ignore cache)
lf summarize --force
```

### 3. Loading: `gather_context()` integration

In `gather_context()`, replace `summaries: Vec::new()` with actual loading:

```rust
// Load summaries for configured areas
let summaries = load_summaries(repo_root, &config.summaries, config.summary_tokens);
```

`load_summaries()`:
1. Read `config.summaries` (the existing `Vec<SummaryConfig>`)
2. For each configured path, look for `.lf/summaries/{path_hash}.md`
3. If found, parse frontmatter, return as `Document { path, content, category: "summaries" }`
4. If missing, skip silently (summaries are supplementary, never block execution)

The existing `trim_context_with_breakdown()` already handles summaries correctly — drops them before docs, after area_docs.

## Alternatives considered

| Approach | Tradeoff | Why not |
|----------|----------|---------|
| Store summaries in SQLite | Requires lfd running for CLI usage; couples generation to daemon | Summaries are per-repo artifacts, not daemon state. Files work everywhere. |
| Generate on-the-fly during `gather_context()` | Blocks step execution with a full agent invocation | Summaries should be pre-generated. A 30-second agent call before every step is unacceptable. |
| GitHub webhooks trigger regeneration | Requires webhook infra, external connectivity | Over-engineered for Phase 1. Manual `lf summarize` + optional loop stimulus is sufficient. |
| Use the LLM's own file-reading to discover codebase | Status quo | Wastes agent turns on discovery. Summaries give the agent a head start. |
| Store in `.lf/cache/` or a central cache dir | Adds another directory convention | `.lf/summaries/` is descriptive. One dir per concern. |

## Key decisions

**Files on disk, not database.** Summaries are repo-local artifacts. They should work with `lf` CLI without `lfd` running. SQLite is for daemon state (waves, runs, agents). File-based cache is simpler and portable.

**50k token preload threshold.** Below 50k tokens, we preload all source content into the summarize prompt — the agent sees everything and produces better summaries. Above 50k, we pass paths and let the agent read selectively. This matches the 75k default context budget (50k source + overhead for the step prompt and directions).

**Default model: gemini.** The existing `SummaryConfig` defaults `model` to `"gemini"`. Summaries are a cost-optimization target — they run frequently, produce reference material, and don't need the strongest model. Gemini CLI is fast and cheap for this.

**No automatic regeneration in Phase 1.** Users run `lf summarize` manually or add it to a flow. A future `lf summarize --watch` or a stimulus-driven wave can automate this, but that's Phase 2 infrastructure. Manual is fine for now.

**Staleness via content hash, not timestamps.** A file's mtime can change without content changing (checkout, touch). Content hashing is deterministic and correct. We hash file contents, not metadata.

> Wave principle followed: "Self-extending: Missing features become builtin steps, not code." Summarize is a step. The cache is just files. The only new code is file I/O in `gather_context()` and a CLI entry point.

## Scope

**In scope:**
- `.lf/summaries/` directory with frontmatter-bearing markdown files
- `load_summaries()` function in `prompt.rs` to read cached summaries
- `lf summarize` CLI command that runs the summarize step per configured area
- Content-hash-based staleness check
- Preload vs. path-only decision based on 50k token threshold
- `.lf/summaries/` added to `.gitignore` via `ensure_gitignore_entry`

**Out of scope:**
- Webhook-triggered regeneration (Phase 2)
- Branch-specific summaries (use main's summary for now)
- Recursive bin-packing or chunk splitting
- Summary storage in SQLite/lfd
- Automatic regeneration on file change

## Done when

```bash
# Configure summaries in .lf/config.yaml
cat .lf/config.yaml
# summaries:
#   - path: src/engine/
#     tokens: 5000
#   - path: src/lfd/
#     tokens: 5000

# Generate summaries
lf summarize

# Verify files created
ls .lf/summaries/
# <hash1>.md  <hash2>.md

# Verify summary loaded into prompt
lf gate --dry-run 2>&1 | grep -q "lf:summaries"

# Verify staleness detection (no-op when fresh)
lf summarize  # "src/engine/ — up to date"

# Verify regeneration on change
echo "// new" >> src/engine/prompt.rs
lf summarize  # "src/engine/ — regenerating..."
```

Tests:
- `load_summaries()` returns documents from `.lf/summaries/` files
- `load_summaries()` returns empty vec when no summaries exist
- Content hash matches/mismatches detected correctly
- Preload decision respects 50k threshold
- `ensure_gitignore_entry` adds `.lf/summaries/`
- Integration: summaries appear in formatted prompt output
