# 02: Path Validation

Prevent directory traversal in any identifier that touches the filesystem: wave IDs, run IDs, worktree paths, and the file APIs coming in remote/08.

Path traversal is consistently one of the most common vulnerability classes in self-hosted services that map user input to filesystem operations (Gitea, Woodpecker CI, and most CI/CD runners with artifact storage). CWE-22 (Path Traversal) applies directly.

## What exists today

- **Wave IDs and run IDs** are UUIDs generated by lfd — safe by construction today. But the store trait accepts `&str`, and nothing validates the format at the API boundary.
- **Worktree paths** are derived from branch names via `git worktree add`. Branch names can contain `/` and other path-significant characters. The worktree directory is a sibling inside the repo volume.
- **Log file paths** in `OutputHub` use wave/run IDs to construct file paths under `~/.lf/logs/`. No explicit path containment check.
- **Phase 08 file APIs** (`GET /v0/waves/{id}/files?path=`, `GET /v0/waves/{id}/file?path=`) accept user-supplied paths. The design doc specifies a 1MB cap but no traversal protection.

## What exists after this

A shared `path_within_root` function validates all filesystem paths against their expected root. All identifiers that become path components are validated at the API boundary.

## Security boundary for this phase

This phase prevents:

- User-controlled path input from escaping the intended filesystem root.
- ID/path values from being interpreted as parent traversal or alternate roots.

This phase does not prevent:

- A compromised process with direct host filesystem access outside lfd APIs.
- Cross-worktree access that occurs purely inside agent runtime mounts (covered in Phase 03).

## Implementation

### `path_within_root` utility

Add to a shared location (e.g., `src/engine/fs.rs` or `src/lfd/security.rs`):

```rust
/// Resolve `candidate` within `root` and verify it stays inside.
/// Returns the canonical path on success.
/// Rejects `..`, null bytes, and symlink escapes.
pub fn path_within_root(root: &Path, candidate: &str) -> Result<PathBuf> {
    if candidate.contains('\0') {
        return Err(anyhow!("null byte in path"));
    }

    let root_canonical = root.canonicalize()
        .with_context(|| format!("root does not exist: {}", root.display()))?;

    let joined = root.join(candidate);
    let canonical = joined.canonicalize()
        .with_context(|| format!("path does not exist: {}", joined.display()))?;

    if !canonical.starts_with(&root_canonical) {
        return Err(anyhow!("path escapes root: {}", candidate));
    }

    Ok(canonical)
}
```

For cases where the file doesn't exist yet (writes), use a parent-check variant that canonicalizes the parent directory and validates the final component separately.

### ID validation at API boundary

Add a validation function for identifiers used as path components:

```rust
/// Validate that an ID is safe to use as a filesystem path component.
/// Allows alphanumeric, hyphens, underscores. Rejects empty, `.`, `..`,
/// slashes, null bytes, and control characters.
pub fn validate_safe_id(id: &str) -> Result<()> { ... }
```

Call this in axum extractors or at the top of route handlers for `:wave_id`, `:run_id`, and any future path-bearing parameters.

### Apply to existing surfaces

| Surface | Root | Validation |
|---------|------|-----------|
| `OutputHub` log paths | `~/.lf/logs/` | `path_within_root` on constructed log path |
| Worktree directory names | Repo volume root | `validate_safe_id` on branch name component |
| Store file paths (SQLite) | `~/.lf/` | `path_within_root` on DB path from config |
| Git hook handler paths | Working directory | `path_within_root` on any path params |

### Apply to Phase 08 file APIs (when built)

The `GET /v0/waves/{id}/files?path=` and `GET /v0/waves/{id}/file?path=` endpoints must call `path_within_root(worktree_root, path)` before any filesystem access. This should be noted in the remote/08 design doc.

### Symlink handling

`canonicalize()` follows symlinks, so a symlink inside the worktree pointing outside it will be caught by the prefix check. This is the correct behavior — agents shouldn't be able to create symlinks that escape the worktree.

For the shared repo volume (where multiple worktrees are siblings), `path_within_root` with the specific worktree as root prevents cross-worktree access through the file API. Agent containers access the full volume at runtime (a Phase 03 concern), but the API layer validates against the individual worktree.
