One settings catalogue

Draft for Jack Heart · LOO-714 / infrastructure · 2026-11-03

Build one executable definition of every LF-owned setting, so its accepted values, supported locations, editing path and explanation agree across CLI, files, DB and Desktop. This develops the existing settings-portability-review.md audit. It is a design for review, separate from the running choice-before-fallback implementation. No catalogue implementation or synchronization is approved by this draft.

Jack Heart clarified the design goal on November 3: close the coverage gaps, not merely catalogue today's exceptions. For every supported setting, implement consistent access through appropriate surfaces or document a real domain/lifecycle constraint. Existing missing support is not its own justification.

Writer policy remains open. Jack tentatively prefers lf set to mean a DB override, but is also considering limiting it to account/machine choices, with ordinary preferences file-backed. Paseo research in paseo-settings-reference.md informs that decision. The catalogue must not silently settle it by making storage depend on whichever writer happened to exist before.

Jack's request: “designing a single settings catalog and explaining and clarifying what exists today versus what would need to change.” Preserve the accepted agent rule: choice before fallback, then source > scope > target. No built-in skill recommendations or per-skill accounts.

“Current” means the working branch, including the active revision, not the installed release. The revision now carries default_agent and authored candidate keys; its full validation is ongoing. These observations do not claim shipped behavior.

What one definition says

A definition describes a setting, not a configured value. Sources continue to hold declarations; resolution continues to produce values for a particular context.

Definition field Example: docs Example: agent
Value and validation List of path/glob strings Harness/model string with existing validation
Default Empty list No authored choice; application fallback is separately identified
Applicability Launch settings at general/skill/occurrence targets Same targets; LF-owned metadata only
Combination Append; explicit empty list clears prior contributions Choice/fallback resolution group with default_agent
Persistence binding Files or DB preferences according to the requested source Same
Lifecycle New context assembly New launch; resume has an explicit continuity operation
Portability/dependencies Relative repo paths portable; absolute paths need local mapping Declaration portable; selected harness/model must be available
Description Additional documents included in context Agent to use for applicable work

Applicability is a rule over source × scope × target, not three independent checkbox lists whose cross-product accidentally permits invalid combinations. For example, session presentation is personal-global; account routes allow personal global/repo/Wave scope but no skill target.

Dynamic paths are declared patterns with typed selectors: release.targets.<name> and its supported fields, or a validated context-budget category. skills and graphs are target selectors around a setting, not independent setting definitions. Planning remains a tagged unit; a generic editor cannot splice together fields from different planning providers.

Ownership and data flow

Use Rust as the authority. For core Config fields, a small declarative field list can emit the typed fields, defaults and descriptors together. Retain existing domain types/codecs; derive value schemas from them rather than hand-writing a parallel string/bool/list schema. Settings owned elsewhere register descriptors bound to their existing typed domain operations. Export the catalogue as a typed DTO for Desktop/help/editor consumers. No separately maintained Swift key list or external schema file becomes another authority.

The exact macro spelling is implementation detail. The requirement is that adding a Config preference also requires its policy definition, while internal fields such as retained source layers never become public settings. Type validators and default constructors remain single-owned even when reused by domain code.

Four concepts are sufficient:

  • Definition: key/pattern, typed codec/default, applicability, resolution policy, adapter, lifecycle, portability and description.
  • Address: setting plus scope and optional skill/graph-occurrence target.
  • Declaration: address, authored value and source locator. Choice versus fallback comes from the declaration key's definition, not a UI guess.
  • Resolution: effective value, each declaration's contribution/status, comparison reason and source diagnostics. This extends current EffectiveSetting/candidates.

Core operations, names illustrative:

describe_settings(filter) -> definitions
parse_setting(address, input, source) -> validated declaration
write_setting(declaration) / unset_setting(address, source) -> adapter result
resolve_settings(context, declarations) -> values + explanation

The resolver owns both the decision and its explanation. Reasons identify the actual comparison: explicit choice, higher source, narrower scope, more specific target, additive contribution or clearing. A reset can clear earlier items while later declarations append; there need not be one winning list declaration.

Read each source as present, absent or unavailable. The existing fallback on an unreadable DB can remain usable, but inspection reports incomplete evidence. Bootstrap readers request only sources available at that stage; listing settings, loading a theme and reporting a store-version problem must not require a working DB.

Domain settings remain domain settings

Account routes expose their ordered preference and existing read/write operation, not credentials. Machine/session selection exposes its existing operation, including movement/copy semantics; generic writes must not bypass those effects. Theme keeps its draft/Apply/Cancel behavior and file writer. Installation settings retain bootstrap access. Portfolio remains a managed collection.

The catalogue advertises whether an entry supports generic assignment or needs a domain action. Close missing appropriate CLI/file/DB/UI access; an adapter that only labels a current omission does not fulfill Jack's direction. Unsupported source/target combinations need an actual domain or lifecycle reason and the supported action. Which surfaces write files versus DB awaits the writer decision. Native provider configuration is identified as delegated, not reimplemented. Unknown LF keys are diagnosed after dispatching all known owners; native skill frontmatter and recognized non-setting structure are not treated as unknown LF keys.

Paseo reference: lessons for the writer contract

Paseo's daemon CLI and settings patches write the same config.json; its project API writes paseo.json. Its schema supports validation and editor-schema generation, but lifecycle/mutable-field lists remain separate. Client-local remembered model choices are another launch input, not daemon configuration. Evidence and limits: Paseo settings reference.

For LF, a write result should identify the saved declaration and report whether it applies now, to the next launch, requires an explicit lifecycle action, or is shadowed by another declaration. Persist only requested intent; never serialize a resolved view back into a preference source. Include UI-carried choices in launch provenance rather than letting them become an invisible precedence tier.

This strengthens the file-editor alternative without deciding it. “Close gaps” requires common semantic access through appropriate interfaces, not automatically a DB copy of every preference. Generic file edits can remain source-explicit if lf set keeps its tentative DB-only meaning.

Consequences for the LF design


Two coherent storage choices remain:


    

  1. General DB overrides. lf set always writes the DB layer; personal files
remain a lower-authority declaration source. Close appropriate CLI/UI/file/DB
gaps, and always explain the destination and any shadowing.
    2. 

  2. Ordinary preferences in files. CLI/UI become editors of the same personal
config. Repository files keep shared intent; DB retains registrations, routing
and execution state. lf set could be restricted to the DB-backed domain choices,
with an explicit config-edit operation for ordinary preferences. Existing
scope_settings values would need migration, not silent abandonment.
    3. 



Paseo makes option 2 more credible: file ownership does not require hand editing
or giving up a settings UI. It does not settle LF's richer precedence policy, nor
show that accounts/machines are the only legitimate DB settings. Storage remains
an LF design decision, not a consequence of building a catalogue.


For either option, adopt the useful contracts: one typed definition used by input
surfaces; preserve authored intent when writing; report saved versus effective;
make client-local remembered selections visible in launch provenance. LF's catalogue
should additionally own applicability and lifecycle policy, avoiding Paseo's
remaining parallel lists.


Jack accepted closing coverage gaps. That goal means every appropriate read/write
surface reaches the common semantics. It does not by itself mean every preference
must have a DB copy. No LF storage migration or writer-policy change is accepted.

Delivery shape and acceptance


Additive series. Keystone: replace scattered catalogue policy and wire discovery,
validation, writers and explanation to it in one coherent PR. Include all existing
LF-owned settings and close appropriate access gaps, with correct adapter
capabilities. The implementation inventory must identify each gap, its new entry
points or justified restriction, and its behavioral proof. No new storage layer
is required by the catalogue itself. If the writer decision removes ordinary DB
preferences, their migration becomes a separate explicit cutover requirement.


Internal sequence: (1) co-locate definitions and cut over validation/eligibility,
removing the old lists; (2) bind special owners and CLI adapters; (3) expose catalogue
and resolver explanations through shared DTOs and inspection. These are internal
slices, not separately maintained old/new implementations.


Later outcomes: generated config-editor schema/completion; historical launch
snapshots; cross-machine comparison and profile distribution. Catalogue metadata
prepares them but does not implement synchronization, credential distribution or
new history persistence. Preserve source and strength when exporting declarations;
a resolved snapshot is not a portable preference profile.


Headless acceptance proves:
