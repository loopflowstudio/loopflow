1. What was built

Every reviewable skill (explore, ship-review, design, research, demo) now runs as an ordinary headless Graph worker on its own configured agent and model, followed by a standalone - break marker. Instead of stopping before an interactive: step and asking your Task conversation to switch hats and run the skill on its own model, the worker finishes first, parks at - break, and wakes the Task's primary conversation — or starts it in a held terminal if you quit it — with the summary, scratch/ artifact links, recommended continuation, and numbered questions already waiting.

2. How it works

Compiling - break and translating legacy interactive:

- break compiles to ConcreteStep::Breakpoint and gets an automatic name (after-<prev>, or break at step 0, deduplicated with #2). Legacy interactive: <skill> compiles into the same worker-then-breakpoint pair so existing Graphs keep working until LOO-1100 removes the reader. Inside a loop, the backward edge moves from the deciding skill to its trailing breakpoint so the worker's verdict is held for review.

Legacy interactive: <skill> compiles as the skill worker followed by an unnamed breakpoint. When a loop ends in skill + break, the backward edge attaches to the breakpoint so the worker's verdict pauses for review.

Stopping at a breakpoint and waking the primary conversation

In the Graph runner, hitting ConcreteStep::Breakpoint checks continue_at_breakpoint (returns true under -b or auto: on unless the verdict is blocked, else false). When it stops, execute builds the handoff from the preceding worker's answer or verdict, resolves any scratch/ paths to real files on disk, and records the arrival atomically via arrive_task_graph — which also queues the task update that wakes the primary conversation (or starts it held if stopped).

Auto/batch runs settle straight through non-blocked breakpoints; interactive runs park and return StoppedAt. A blocked verdict on a breakpoint still parks at the breakpoint name with the blocker attached. Stores BreakpointArrival on task_graphs and writes the handoff text in one transaction. Embeds the exact --at-arrival <carrier> command so stale clicks or replies can't advance a later review. Prefers the deciding skill's verdict summary, then falls back to the preceding worker's recorded final answer or command outcome.

Continuing from a breakpoint

continue_from_breakpoint validates --at-arrival, applies any --decision advance|iterate override on loop breakpoints, carries --reason as a one-step handoff (or loop iteration direction), clears cursor.producer, and advances the cursor without losing enclosing XOR routes or loop pass counts.

Refuses --decision on non-loop breakpoints like after-explore. Iterating without a prior verdict requires --reason so the next loop pass knows what to change.

3. Key data structures and APIs

One additive SQLite column on task_graphs carries the parked visit, mirrored across Rust DTOs, CLI flags, and Swift models:

Additive column storing serialized BreakpointArrival JSON while parked; NULL once continued. id is the Graph carrier's LfProcessId (unique per arrival); cursor preserves exact XOR path, loop counts, and pending verdict. TaskGraphPosition::Breakpoint replaces overloaded At waits and surfaces arrival + blocked directly on the wire. task.run accepts at_arrival, decision, and reason over the server protocol and CLI alike. SelectionState::Breakpoint is set only on open Active Tasks so breakpoints float first in Now and stay distinct from LOO-1078's shelved Paused.

4. Trade-offs and invariants going forward

  • Plain Continue accepts the worker's recommended loop verdict. If ship-review or research recommends iterate, plain lf task run (or Desktop's Continue) iterates; if it recommends advance, it advances. Overriding uses --decision advance|iterate on that arrival (--at-arrival) rather than --from, which resets loop counts.
  • Blocked breakpoints hide Desktop's plain Continue button. Even under auto: on, a blocked verdict parks with blocked: true, sets actions.recommended = no_action, and tells you to answer in the conversation with --at-arrival / --decision rather than offering a button that errors.
  • Sidebar drag order stays intact when "Sort by status" is off. Tasks at a breakpoint float first in Now and when Sort by status is on, but manual sidebar drag order is untouched when sorting by status is off.
  • Workflow bar shows breakpoints as separate items; "Start from…" lists runnable stages. Breakpoints render beside their step (explore · 👤 after-explore · plan · …) matching lf graph show; Start from… lists real stages so picking ship-review runs a fresh review instead of jumping to an empty producerless stop.
  • Initial-step review Graphs (feature, redesign, research, or leading - break). On task create --graph feature --run, setup.rs spawns lf task run (running explore headless first) and immediately starts Turn 1 of the primary conversation. Turn 1 reports explore moving and goes idle; after-explore wakes it once explore finishes (immediately on Claude/Codex/OpenCode/Pi; on next turn in agy until LOO-1098). A literal leading - break compiles as break and parks immediately on step 0, though its handoff still uses the generic "Present the result, links…" phrasing.
  • Two skill modes only. Builtin skills have direct interactive use (lf <skill>) and headless Graph worker mode (propose a default plan of action that continues if nobody intervenes). No third "headless-before-breakpoint" mode exists.
  • Sync onto origin/main adopts #2036, #2047, #2048, and #2049. Resolving the 57 conflicts means: dropping edits to deleted verify.md / kickoff-demo.yaml; keeping SelectionState::Breakpoint distinct from #2036's Paused; preserving #2048's review-page skill rules (lf page build / lf page open) on ship-review/explore/qa/demo; and re-verifying DTO fixtures and Rust/Swift suites on the merged head.
  • Untested live surfaces: real Desktop GUI click-through (covered by headless Swift tests), Codex as worker/primary (weekly quota exhausted during QA), and a live blocked worker verdict (unit-tested only). No auth, credential, telemetry, or deployment paths changed.
