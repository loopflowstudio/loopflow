# Linear and Asana Tracker Research (LOO-938)

Research date: 2026-11-18. Scope: vendor API capabilities, limits, and community patterns for `scratch/plan-design.md` and `rust/loopflow-execution/src/{linear,asana,ops}`.

---

## Findings that change the design

1. **Linear manual order is workspace-global on the `Issue`, not per-Project; Asana manual order is per-Project.**
   `scratch/plan-design.md` marks Linear's manual-order field unverified and treats backlog order as *"the Project's order"*. In Linear's GraphQL API, `Issue.sortOrder: Float!` (and `Issue.prioritySortOrder: Float!`) is writable via `issueUpdate`—`rust/loopflow-execution/src/linear/actions.rs` already writes both—but `sortOrder` lives on `Issue`, not on a Project membership join. Reordering issues in a Linear Project mutates their manual order across the **entire workspace** (Team board/list, Cycles, and Custom Views sorted manually) ([Linear Display Options](https://linear.app/docs/display-options), date not shown; [Linear GraphQL Schema](https://raw.githubusercontent.com/linear/linear/master/packages/sdk/src/schema.graphql), retrieved 2026-11-18). Also, `linear/actions.rs` currently sorts and writes `(prioritySortOrder, sortOrder)`, which reorders views sorted by **Priority**, not views sorted by **Manual** (`sortOrder` alone). Meanwhile, Asana's `POST /tasks/{task_gid}/addProject` (`insert_before` / `insert_after`) reorders tasks strictly inside one project without touching other projects ([Asana Add a project to a task](https://developers.asana.com/reference/addprojectfortask), updated 2026-05-27), which `asana/actions.rs` currently retires as `Unsupported`.

2. **Neither tracker has a clean, uniform primitive for shared Loopflow-only metadata without UI clutter—and `loopflow://task/<id>` on Linear has three problems.**
   `scratch/plan-design.md` proposes one `loopflow://task/<id>` attachment per Linear issue carrying API-only `metadata`, *"shown to everyone as a link"*.
   - **Visibility**: Every Linear `Attachment` renders a link card on the issue for all teammates, including the 50% not on Loopflow. Attaching `loopflow://task/<id>` to issues that have no external artifact violates *"doesn't get in the way"*.
   - **Scheme**: Linear's schema requires `http://` or `https://` on `AgentSessionExternalUrlInput.url` and groups API/OAuth `attachmentSources` *"by URL domain"*; whether `attachmentCreate` accepts custom URI schemes such as `loopflow://` is **unconfirmed** in Linear's public docs and schema ([Linear Attachments](https://linear.app/developers/attachments), date not shown; [Linear GraphQL Schema](https://raw.githubusercontent.com/linear/linear/master/packages/sdk/src/schema.graphql), retrieved 2026-11-18).
   - **Metadata UI exposure and replacement**: `Attachment.metadata` (`JSONObject`) is **not** purely API-only—keys `title`, `messages`, and `attributes` render a rich modal in Linear UI, `{key__since}` / `{key__relativeTimestamp}` format into `subtitle`, and Linear notes *"we're also considering exposing it in the UI"*. Worse, `attachmentCreate` and `attachmentUpdate` **replace the entire `metadata` object** on write (no partial key merge).
   - **Asana asymmetry**: Asana's `external` field (`external.gid` ≤ 1,024 chars, `external.data` ≤ 32,768 chars) is **100% invisible in the Asana UI**, requires OAuth, is isolated to the Loopflow OAuth app, and is readable/writable by **all users of that same OAuth app** who can view the task ([Asana Custom external data](https://developers.asana.com/docs/custom-external-data), updated 2025-09-11). Linear has no invisible API-only equivalent.

3. **Private per-person claimed-task order has no Linear mapping and only a workspace-wide Asana mapping (`user_task_list`).**
   Linear has no per-user issue order in its API; dragging issues in *My Issues* when sorted manually mutates the shared global `Issue.sortOrder` ([Linear My issues](https://linear.app/docs/my-issues), date not shown; [Linear Display Options](https://linear.app/docs/display-options), date not shown). Asana's *My Tasks* (`user_task_list`) is private per user and supports section/task ordering via `/sections/{section_gid}/addTask` (`insert_before` / `insert_after`), exclusively accessible to that list's owner ([Asana Forum: My Tasks API changes](https://forum.asana.com/t/upcoming-changes-coming-to-my-tasks-in-asana-and-the-api-breaking-changes/109717), 2021-02-09), but spans all workspace tasks. Keeping claimed-task order local to Loopflow (synced across a user's Machines via Git + hub) is the right call for both trackers.

4. **Neither a Linear `Initiative` nor an Asana `Portfolio` can hold Tasks directly—Waves must be able to link directly to a `Project`.**
   - In Linear, `Issue.project` points to at most one `Project`; `Initiative` holds only `Project`s (via `InitiativeToProject`) and `subInitiatives`, never `Issue`s, and Initiatives can be disabled per workspace ([Linear Initiatives](https://linear.app/docs/initiatives), date not shown; [Linear GraphQL Schema](https://raw.githubusercontent.com/linear/linear/master/packages/sdk/src/schema.graphql), retrieved 2026-11-18).
   - In Asana, `Portfolio` holds only `Project`s and nested `Portfolio`s, and **both `Portfolio` and `Goal` require Asana Advanced tier** (`402 Payment Required` on Personal and Starter plans) ([Asana Pricing](https://asana.com/pricing), retrieved 2026-11-18; [Asana Get a goal](https://developers.asana.com/reference/getgoal), updated 2026-05-27).
   - Requiring an Initiative or Portfolio blocks single-team adopters and Starter-tier Asana workspaces.

5. **Four behaviors in Loopflow's current tracker code will break or disturb coworkers in a shared 100-person workspace:**
   - `LinearClient::claim_team` / `validate_team_claim` (`rust/loopflow-execution/src/linear/mod.rs:239,666-755`) mutates the Linear Team's `description` (`<!-- loopflow-repository: ... -->`) via `teamUpdate` and refuses to share one Linear Team across multiple repositories.
   - `validate_project_ownership` (`linear/mod.rs:41-73`, `ops/linear.rs:856-900`) rejects any Linear Project that belongs to `0` or `>1` Initiatives or `>1` Teams, whereas multi-team Projects (`ENG` + `DESIGN`) are standard in Linear ([Linear Projects](https://linear.app/docs/projects), date not shown).
   - `LinearClient::team_changes` (`linear/team_changes.rs:45-52`) and `check_scope` (`ops/tracker_events.rs:208-239`) poll and ingest **every open issue in the entire Linear Team** into local SQLite `tasks`, regardless of Project or assignee.
   - `AsanaClient::changes` (`asana/mod.rs:327-344`) runs `PUT /tasks/{gid}` with `{"external": {"gid": ...}}` on **every open task in the repository project** that lacks an `external.gid`, writing to coworkers' unclaimed tasks during background reads.

6. **Polling traps without webhooks: unassignment blind spots on Linear, and `GET /tasks` filter limits vs `GET /events` on Asana.**
   - If Loopflow polls Linear only for `assignee: { isMe: { eq: true } }`, it will never observe a coworker unassigning or reassigning an issue away from the Loopflow user. Delta queries must filter `or: [{ assignee: { isMe: { eq: true } } }, { id: { in: $trackedIssueIds } }]`, paired with a separate comment query because `CommentFilter.issue` filters by current issue state.
   - On Asana, `GET /tasks` cannot combine `project` and `assignee` (`You must specify a project or tag if you do not specify assignee and workspace`), and `/workspaces/{workspace_gid}/tasks/search` requires Starter+/Premium (`402` on Free), is capped at **60 req/min**, has unstable pagination, and lags **10–60 seconds** behind writes ([Asana Get multiple tasks](https://developers.asana.com/reference/gettasks), updated 2026-05-27; [Asana Search tasks](https://developers.asana.com/reference/searchtasksforworkspace), updated 2026-05-27). For ongoing sync without webhooks, Asana's `GET /events?resource={project_gid}&sync={token}` is far cheaper than Loopflow's current N+1 `modified_since` + `/stories` loop ([Asana Events](https://developers.asana.com/reference/events), updated 2025-09-13).

## 1. Attaching structured integration data to an issue or task

### Linear

- **Vendor recommendation & established integrations**
  Linear recommends **`Attachment`** records (`attachmentCreate` / `attachmentUpdate`) keyed by a unique `url` per `issueId` for stateless integration links and structured `metadata` ([Linear Attachments](https://linear.app/developers/attachments), date not shown). Linear's own first-party integrations use dedicated link mutations (`attachmentLinkGitHubPR`, `attachmentLinkGitHubIssue`, `attachmentLinkSlack`, `attachmentLinkZendesk`, `attachmentLinkIntercom`, `attachmentLinkJiraIssue`, `attachmentLinkFront`, `attachmentLinkSalesforce`, `attachmentLinkDiscord`) or `attachmentLinkURL` ([Linear GraphQL Schema](https://raw.githubusercontent.com/linear/linear/master/packages/sdk/src/schema.graphql), retrieved 2026-11-18). In addition, `issueCreate`, `commentCreate`, `projectCreate`, `issueRelationCreate`, and `initiativeToProjectCreate` all accept a caller-supplied UUIDv4 `id: String` for idempotent creation.

- **Native integration attachment (`Attachment`)**
  - **Mutations & queries**: `attachmentCreate(input: AttachmentCreateInput!)`, `attachmentUpdate(id: String!, input: AttachmentUpdateInput!)`, `attachmentDelete(id: String!)`, `attachmentLinkURL(...)`, `attachment(id: String!)` (accepts UUID or URL), `attachments(filter: AttachmentFilter)`, and `attachmentsForURL(url: String!)` ([Linear Attachments](https://linear.app/developers/attachments), date not shown; [Linear GraphQL Schema](https://raw.githubusercontent.com/linear/linear/master/packages/sdk/src/schema.graphql), retrieved 2026-11-18).
  - **URL as idempotent key**: `Attachment.url: String!` is unique per issue. Calling `attachmentCreate` with an `issueId` and `url` already present on that issue updates the existing attachment in place rather than duplicating it ([Linear Attachments](https://linear.app/developers/attachments), date not shown). Note: Loopflow's `linear/actions.rs` currently calls `attachmentLinkURL` (which does not accept `subtitle` or `metadata`) followed by `attachmentUpdate`; `attachmentCreate` sets `title`, `subtitle`, `url`, `iconUrl`, and `metadata` in a single request.
  - **URI scheme**: Every documented example uses `http://` or `https://`, and `Query.attachmentSources` groups API/OAuth attachments *"by URL domain"*. Acceptance of non-HTTP custom schemes (`loopflow://task/<id>`) is **unconfirmed**; using an `https://` URL (or omitting the attachment unless linking a real URL like a GitHub PR) avoids scheme rejection.
  - **How it shows in UI**: Always visible in the issue's Links/Resources section to every user who can view the issue, displaying the OAuth app's icon (or `iconUrl`, PNG/JPG ≤ 1 MB, 20×20 px recommended), `title` (≤ 2,048 chars), and `subtitle` (≤ 2,048 chars, supporting `{key__since}` and `{key__relativeTimestamp}` ISO date interpolation from `metadata`). If `metadata` contains `title: string`, `messages: { subject?, body?, timestamp? }[]` (keep body < 10,000 chars), or `attributes: { name, value }[]`, clicking the attachment opens a **rich modal** inside Linear. Arbitrary other top-level string/number keys in `metadata: JSONObject` are not rendered today, though Linear notes it is *"considering exposing it in the UI"*. Both `attachmentCreate` (on upsert) and `attachmentUpdate` **replace the entire `metadata` object** (`title` is also required on `AttachmentUpdateInput`) ([Linear Attachments](https://linear.app/developers/attachments), date not shown; [Linear GraphQL Schema](https://raw.githubusercontent.com/linear/linear/master/packages/sdk/src/schema.graphql), retrieved 2026-11-18).

- **Custom fields & issue properties**
  Linear has **no user-defined custom fields** (`CustomField` does not exist in `schema.graphql`). Issues have fixed built-in properties: `stateId`, `priority` (`0`..`4`), `estimate` (`Float`, `0`..`64`), `dueDate` (`TimelessDate`), `assigneeId`, `delegateId` (for `actor=app` agent users), `cycleId`, `projectId`, `projectMilestoneId`, `parentId`, `labelIds`, `releaseIds`, and `slaType` ([Linear GraphQL Schema](https://raw.githubusercontent.com/linear/linear/master/packages/sdk/src/schema.graphql), retrieved 2026-11-18). Projects and Initiatives have `EntityExternalLink` (`entityExternalLinkCreate`) and `Document` (`documentCreate`).

- **App UI surfaces**
  Linear's Agent Platform (`AgentSession`, `AgentActivity` via `agentActivityCreate` with `actor=app`) renders structured `plan` steps (`1..100` entries, each `1..10,000` chars), `externalUrls`, thoughts, actions, and elicitations in an issue thread ([Linear Agents](https://linear.app/developers/agents), date not shown; [Linear GraphQL Schema](https://raw.githubusercontent.com/linear/linear/master/packages/sdk/src/schema.graphql), retrieved 2026-11-18). Requires workspace-admin installation (`actor=app`).

- **Labels & label groups**
  `IssueLabel` (`issueLabelCreate`, `issueLabelUpdate`) supports workspace labels (`teamId: null`) and team-scoped labels (`teamId`), plus one level of label groups (`isGroup: true`, `parentId`). Groups cannot be applied directly to issues; `groupType: LabelGroupType` is `singleSelect` (default—at most one child label per issue) or `multiSelect` (added 2026-10-22). `name` is 1–80 chars (no emoji); `description` is ≤ 255 chars ([Linear GraphQL Schema](https://raw.githubusercontent.com/linear/linear/master/packages/sdk/src/schema.graphql), retrieved 2026-11-18; [Linear Changelog](https://linear.app/changelog), 2026-10-22). Visible to all workspace/team viewers; clutters team label pickers if created per Wave.

- **Hidden markers in descriptions or comments**
  `Issue.description` and `Comment.body` store Markdown. HTML comments (`<!-- loopflow-... -->`) are hidden in rendered Markdown, and Linear's 2026-11-12 changelog notes that API description patches preserve formatting of unchanged content ([Linear Changelog](https://linear.app/changelog), 2026-11-12). However, `IssueUpdateInput.description` replaces the entire description (`Issue.documentContent` backs collaborative ProseMirror editing), so any human editing near the bottom of an issue description can accidentally delete or corrupt a hidden HTML comment, and `IssueUpdateInput` has no optimistic-concurrency revision guard.

- **Size limits, visibility, and webhooks**
  - **Size limits**: `Attachment.title` ≤ 2,048 chars; `Attachment.subtitle` ≤ 2,048 chars; `Attachment.iconUrl` file ≤ 1 MB; `Attachment.metadata.messages[].body` recommended < 10,000 chars; maximum total byte size of `Attachment.metadata`, `Issue.description`, and `Comment.body` is **unconfirmed** in public docs (`AgentActivityCreateInput` documents 250,000 chars for activity bodies) ([Linear Attachments](https://linear.app/developers/attachments), date not shown; [Linear GraphQL Schema](https://raw.githubusercontent.com/linear/linear/master/packages/sdk/src/schema.graphql), retrieved 2026-11-18).
  - **Visibility to non-users**: Attachments, labels, descriptions, and comments are visible to all Linear members with team/issue access; only arbitrary non-reserved keys inside `Attachment.metadata` are hidden from the UI (and readable via GraphQL by any authenticated workspace user/integration).
  - **Webhooks**: Data-change webhooks fire on `Issue`, `Attachment` (`Issue attachments`), `Comment`, and `IssueLabel` (`create`, `update`, `remove`, with `updatedFrom` carrying prior values) ([Linear Webhooks](https://linear.app/developers/webhooks), date not shown). Whether mutating an `Attachment` advances its parent `Issue.updatedAt` when polling `issues(filter: { updatedAt })` is **unconfirmed**; `attachments(filter: { updatedAt })` has its own `updatedAt` filter in the schema.

### Asana

- **Vendor recommendation & established integrations**
  For app-private or structured integration state, Asana recommends **Custom External Data** (`external.gid` and `external.data`) on tasks ([Asana Custom external data](https://developers.asana.com/docs/custom-external-data), updated 2025-09-11). For team-visible structured columns, Asana recommends **Custom Fields** (`custom_fields`); for interactive cards linked to third-party URLs (Jira, GitHub, Figma, Zendesk), Asana provides **App Components** (Widgets + URL Attachments) ([Asana Custom fields guide](https://developers.asana.com/docs/custom-fields-guide), updated 2026-04-20; [Asana App components on tasks](https://developers.asana.com/docs/app-components-on-tasks), updated 2025-09-12).

- **Native integration data (`external` field on Task)**
  - **Fields & addressing**: `Task.external` holds `{ "gid": string, "data": string }`, written via `POST /tasks` or `PUT /tasks/{task_gid}` (or `PUT /tasks/external:{custom_gid}`). Once `external.gid` is set, any task endpoint accepting `{task_gid}` accepts `external:{custom_gid}` (note: `GET /tasks/{gid}/stories` in Loopflow's `asana/mod.rs:350` requires the native numeric `gid`) ([Asana Custom external data](https://developers.asana.com/docs/custom-external-data), updated 2025-09-11; [Asana Update a task](https://developers.asana.com/reference/updatetask), updated 2026-05-27).
  - **Authentication & who can read/write**: **Requires OAuth** (unavailable to Personal Access Tokens). Scoped strictly to the **OAuth application**: invisible in the Asana UI and invisible to all other OAuth apps, **but visible and writable to every Asana user of the same OAuth app** who can view the task. Asana explicitly warns not to store private single-user secrets in `external.data` because teammates using the same OAuth app can read it—which makes `external.data` ideal for shared Loopflow-only task metadata ([Asana Custom external data](https://developers.asana.com/docs/custom-external-data), updated 2025-09-11). Opt-in on reads via `opt_fields=external,external.data`.
  - **Note on Projects**: `external` is documented for **tasks**, not projects (Loopflow currently appends `Loopflow ID: <uuid>` to Asana project `html_notes`).

- **Custom fields & task properties**
  - **Types (`resource_subtype`)**: `text` (≤ 1,024 chars; also supports rich text via `html_custom_fields`), `number` (precision `0`..`6`), `enum` (1–500 `enum_options`, options cannot be deleted—only `enabled: false`), `multi_enum`, `date` (`YYYY-MM-DD` or ISO `date_time`), `people` (user GIDs), and `reference` (links to `task`, `project`, `portfolio`, `goal`, `team`, or `record`). Read-only subtypes: `formula` (`is_formula_field: true`) and `custom_id` (`id_prefix != null`, auto-assigned human ticket IDs like `ENG-123`!) ([Asana Custom fields guide](https://developers.asana.com/docs/custom-fields-guide), updated 2026-04-20; [Asana Update a task](https://developers.asana.com/reference/updatetask), updated 2026-05-27).
  - **Plan tier & container limits**: Custom fields require a **paid plan (Asana Starter or above)**; Personal (free, ≤ 2 users) workspaces lack custom fields ([Asana Pricing](https://asana.com/pricing), retrieved 2026-11-18; [Asana Custom fields guide](https://developers.asana.com/docs/custom-fields-guide), updated 2026-04-20). Asana's OpenAPI specification notes a limit of **20 custom fields per project or portfolio** (`PortfolioCompact` description in [Asana Get a portfolio](https://developers.asana.com/reference/getportfolio), updated 2026-05-27; whether higher enterprise limits exist in the web product is **unconfirmed**).
  - **Scope, visibility & permissions**: Can be workspace-wide (`POST /custom_fields`, `is_global_to_workspace: true`) or local to one project/portfolio (`POST /projects/{project_gid}/addCustomFieldSetting` passing an inline `custom_field` object). Visible in the Asana UI to project/workspace viewers unless `privacy_setting: "private"`. Users can **lock** custom fields (`403 Forbidden` when non-lockers edit metadata) or set `default_access_level` (`admin`, `editor`, `user`), and `owned_by_app: true` is **allow-listed** (`403 Forbidden` for non-allow-listed apps). Moving a task out of all projects carrying a custom field sets `enabled: false` on its value (read-only until cleared with `null` or re-homed) ([Asana Custom fields guide](https://developers.asana.com/docs/custom-fields-guide), updated 2026-04-20; [Asana Add a custom field to a project](https://developers.asana.com/reference/addcustomfieldsettingforproject), updated 2026-05-27).

- **App components**
  Asana's App Components (`Entry point`, `Modal form` with 0–20 fields, `Lookup`, and `Widget` cards triggered by `POST /attachments` with `resource_subtype: "external"`, `url`, and `connect_to_app: true`) require **hosting an HTTPS app server** (`Widget metadata URL`, CORS-enabled) that Asana calls live whenever a user opens a task, plus per-project app installation ([Asana App components on tasks](https://developers.asana.com/docs/app-components-on-tasks), updated 2025-09-12; [Asana Upload an attachment](https://developers.asana.com/reference/createattachmentforobject), updated 2026-05-27). Incompatible with a serverless CLI/desktop architecture.

- **Tags**
  `Tag` objects (`POST /tags`, `POST /tasks/{task_gid}/addTag`, `removeTag`) are workspace-global labels with `name`, `color`, and `notes`. Visible to everyone in the workspace, provide no ordering, cannot be grouped, fan-out tag queries hurt Asana's cost rate-limiter, and Asana explicitly warns: *"it is possible that we will simplify them in the future so it is not encouraged to rely too heavily on it"* ([Asana Tags](https://developers.asana.com/reference/tags), updated 2025-11-12; [Asana Rate limits](https://developers.asana.com/docs/rate-limits), updated 2026-07-03).

- **Hidden markers in descriptions or comments**
  Asana **cannot store hidden HTML comments (`<!-- ... -->`)** in `html_notes` or story `html_text`. Writing rich text requires strict valid XML using only Asana's supported tag allowlist (`<body>`, `<strong>`, `<em>`, `<code>`, `<pre>`, `<a>`, `<ul>`, `<ol>`, `<li>`, `<blockquote>`, `<h1>`, `<h2>`, `<hr/>`, `<table>`, `<img>`, `<object>`); unsupported markup returns `400 Bad Request` ([Asana Rich text](https://developers.asana.com/docs/rich-text), updated 2026-09-16). Any marker in `notes` or `stories` must be visible text (which is why `rust/loopflow-execution/src/ops/tracker.rs:294` strips `<!-- loopflow-... -->` and `asana/mod.rs:37` writes a visible `Loopflow ID: <uuid>` footer on projects).

- **Size limits, visibility, and webhooks**
  - **Size limits**: `external.gid` ≤ **1,024 chars**; `external.data` ≤ **32,768 chars** (prose says `32,768`, parameter table on the same page has a typo `32,786`—treat `32,768` as the cap) ([Asana Custom external data](https://developers.asana.com/docs/custom-external-data), updated 2025-09-11); `text` custom field ≤ **1,024 chars**; `enum` options ≤ **500** ([Asana Custom fields guide](https://developers.asana.com/docs/custom-fields-guide), updated 2026-04-20); file attachments ≤ **100 MB** ([Asana Upload an attachment](https://developers.asana.com/reference/createattachmentforobject), updated 2026-05-27). Maximum length of `notes` / `html_notes` is **unconfirmed** in Asana's API reference.
  - **Visibility to non-users**: `external` is completely hidden from non-Loopflow users and the Asana UI; custom fields, tags, attachments, descriptions, and stories are visible to all project/task viewers.
  - **Webhooks & `modified_at`**: Custom field changes advance `Task.modified_at` and emit `task` `changed` events (`change.field: "custom_fields"`). Asana's `modified_at` specification lists `completed`, `name`, `due_date`, `description`, `attachments`, `items`, `schedule_status`, `assignee`, `custom_fields`, stories, and trashing—it does **not** list `external` ([Asana Update a task](https://developers.asana.com/reference/updatetask), updated 2026-05-27). Whether updating *only* `external.data` / `external.gid` advances `modified_at` or fires a `task` `changed` webhook/event is **unconfirmed** in Asana's docs.

## 2. Manual order

### Linear

- **Order fields & mutations**
  Linear exposes floating-point rank keys (`Float`, lower values appear first; Linear adjusts neighbors on collision), all writable via `issueCreate` and `issueUpdate` ([Linear GraphQL Schema](https://raw.githubusercontent.com/linear/linear/master/packages/sdk/src/schema.graphql), retrieved 2026-11-18):
  - `Issue.sortOrder: Float!` — *"The issue's position in manually sorted lists, with lower values first."* On `IssueCreateInput`, `preserveSortOrderOnCreate: Boolean` (default `false`) must be set to `true` to keep a supplied `sortOrder` instead of placing the new issue first in its status. (`Issue.boardOrder` is `@deprecated(reason: "Will be removed in near future, please use sortOrder instead")`). Note: as of 2026-11-05, changing an issue's cycle or status in a manually ordered list no longer alters its `sortOrder` ([Linear Changelog](https://linear.app/changelog), 2026-11-05).
  - `Issue.prioritySortOrder: Float!` — *"The issue's position within its priority group, with lower values first. This order is separate from `sortOrder`, which is used for other manually sorted lists."* Used as tiebreaker when a view is ordered by **Priority** (`PrioritySort.usePrioritySortOrderTiebreaker: Boolean = true`).
  - `Issue.subIssueSortOrder: Float` — *"The issue's position among its parent's direct sub-issues, with lower values first. Null for top-level issues. This order is independent of the issue's position in team lists."*
  - **Project & Initiative order**: `Project.sortOrder: Float!` and `Project.prioritySortOrder: Float!` order projects in workspace/team views (`projectCreate` / `projectUpdate`); `InitiativeToProject.sortOrder` (input `Float`, output numeric `String!`, via `initiativeToProjectCreate` / `initiativeToProjectUpdate`) orders projects **per Initiative**; `Favorite.sortOrder: Float!` orders a user's personal sidebar favorites ([Linear GraphQL Schema](https://raw.githubusercontent.com/linear/linear/master/packages/sdk/src/schema.graphql), retrieved 2026-11-18).

- **Scope of order & effect on other people's views**
  - **Issue `sortOrder` is workspace-global on the `Issue` record.** There is **no** per-Project, per-Team-view, or per-Custom-View `sortOrder` join table for issues. Linear's documentation states explicitly: *"Manual ordering is default for board views and can be selected in most list views... Manual ordering is unique in that it will update the manual order for everyone in the workspace."* ([Linear Display Options](https://linear.app/docs/display-options), date not shown).
  - **View preferences (`ViewPreferences`)**: Each view has `organizationViewPreferences` (workspace default) and `userViewPreferences` (personal override) controlling *which* sort mode (`Manual`, `Priority`, `Status`, `Last updated`, etc.) and grouping (`Status`, `Assignee`, `Priority`, `None`, etc.) a user sees, but anyone viewing **any** surface in `Manual` sort reads and mutates the same `Issue.sortOrder`, and anyone in `Priority` sort reads and mutates `(Issue.priority, Issue.prioritySortOrder)` ([Linear Display Options](https://linear.app/docs/display-options), date not shown; [Linear GraphQL Schema](https://raw.githubusercontent.com/linear/linear/master/packages/sdk/src/schema.graphql), retrieved 2026-11-18).
  - **Bug in Loopflow's existing `linear/actions.rs`**: `list_issue_nodes` (`linear/mod.rs:1114-1119`) sorts by `(priority_sort_order, sort_order)` without `priority` (`0..4`), and `move_input` (`linear/actions.rs:769-789`) mutates `prioritySortOrder` whenever neighbors differ. That neither matches Linear's **Manual** order (`sort: [{ manual: { order: Ascending } }]` → `sortOrder` only) nor Linear's **Priority** order (`priority` first, then `prioritySortOrder`)!

- **Mapping to Loopflow's two required orders**
  - **Shared backlog order**: Maps to `Issue.sortOrder` (via `issueUpdate(id, input: { sortOrder })` and reading with `sort: [{ manual: { order: Ascending } }]`). Caveat: team members viewing the Project in *Manual* order see the exact order; team members viewing the Project in *Priority* or *Status* order will only see it if they switch Display Options to *Manual*, and reordering in the Project also reorders those issues relative to each other on the Team's board/backlog.
  - **Private per-person order of claimed tasks**: **No mapping in Linear.** *My Issues* uses *Focus* grouping by default, and manual drag-and-drop in *My Issues* writes the global `Issue.sortOrder` ([Linear My issues](https://linear.app/docs/my-issues), date not shown). Loopflow must keep claimed-task order in its own store (synced across the user's Machines via Git + hub).

### Asana

- **Order fields & endpoints**
  Asana does not expose numeric rank floats. Ordering is relational per container and returned in array order ([Asana Get tasks from a project](https://developers.asana.com/reference/gettasksforproject), updated 2026-05-27; [Asana Add a project to a task](https://developers.asana.com/reference/addprojectfortask), updated 2026-05-27; [Asana Add task to section](https://developers.asana.com/reference/addtaskforsection), updated 2026-05-27):
  - **Project & Section order**:
    - Read: `GET /projects/{project_gid}/tasks` returns tasks *"ordered by their priority within the project"*, and `opt_fields=memberships.project.gid,memberships.section.gid` identifies each task's section. `GET /sections/{section_gid}/tasks` returns tasks in one section.
    - Write: `POST /tasks/{task_gid}/addProject` reorders a task even when it is **already in the project**. Body parameters (`TaskAddProjectRequest`): `project` (required), optional `section`, and **at most one** of `insert_before` (task GID, or `null` with `section` for end of section) or `insert_after` (task GID, or `null` with `section` for beginning of section). Anchor tasks must belong to the same `section` if `section` is specified.
    - Alternative section write: `POST /sections/{section_gid}/addTask` (`task`, optional `insert_before` or `insert_after`; defaults to top of section, removes task from other sections of that project).
    - Reordering sections themselves: `POST /projects/{project_gid}/sections/insert` (`section`, `before_section` or `after_section`) ([Asana Move or Insert sections](https://developers.asana.com/reference/insertsectionforproject), retrieved 2026-11-18).
  - **Subtask order**: `POST /tasks/{task_gid}/setParent` accepts `parent` plus `insert_before` or `insert_after` ([Asana Set the parent of a task](https://developers.asana.com/reference/setparentfortask), retrieved 2026-11-18).
  - **Portfolio item order**: `POST /portfolios/{portfolio_gid}/addItem` accepts `item` plus `insert_before` or `insert_after` ([Asana Add a portfolio item](https://developers.asana.com/reference/additemforportfolio), updated 2026-05-27).

- **Scope of order & effect on other people's views**
  - **Project task order is strictly per-project (and per-section within that project).** Because an Asana task can be multi-homed in up to **20 projects** (`addProject`), reordering a task in Project A changes what everyone viewing Project A (with default "None" sort) sees, and **never** changes its position in Project B or in any assignee's *My Tasks* ([Asana Add a project to a task](https://developers.asana.com/reference/addprojectfortask), updated 2026-05-27). Note: if a project uses sections (List headers or Board columns), moving task X before task Y when Y is in a different section moves X into Y's section!
  - **"My Tasks" (`user_task_list`) order is strictly per-user.** Each user has one `user_task_list` per workspace (`GET /users/me/user_task_list?workspace={workspace_gid}`). Since Asana's My Tasks v2 migration (`new_user_task_lists`; `assignee_status` is deprecated and ignored on writes), a `user_task_list` has real column-sections (`GET /projects/{user_task_list_gid}/sections`), ordered left-to-right/top-to-bottom via `GET /user_task_lists/{user_task_list_gid}/tasks`, and tasks are reordered within/across its sections using `POST /sections/{section_gid}/addTask` (`insert_before` / `insert_after`). Asana enforces that **only the owner of the `user_task_list` can read or write task order/sections in their My Tasks** ([Asana Get tasks from a user task list](https://developers.asana.com/reference/gettasksforusertasklist), updated 2026-05-27; [Asana Add custom field to project note on user_task_lists](https://developers.asana.com/reference/addcustomfieldsettingforproject), updated 2026-05-27; [Asana Forum: My Tasks API changes](https://forum.asana.com/t/upcoming-changes-coming-to-my-tasks-in-asana-and-the-api-breaking-changes/109717), 2021-02-09). Note: moving a task in `addProject` / `addTask` does **not** advance `Task.modified_at` ([Asana Update a task](https://developers.asana.com/reference/updatetask), updated 2026-05-27).

- **Mapping to Loopflow's two required orders**
  - **Shared backlog order**: Maps cleanly to `POST /tasks/{task_gid}/addProject` with `project`, `section` (matching the anchor task's `memberships.section.gid` so section grouping isn't scrambled), and `insert_before` / `insert_after`.
  - **Private per-person order of claimed tasks**: *Could* technically map to the user's `user_task_list` sections/order, **but** `user_task_list` mixes tasks from every project across the entire company workspace and users often have personal auto-promotion rules (Today / Upcoming / Later). Keeping claimed-task order in Loopflow's own store (Git + hub) avoids rearranging the user's non-Loopflow *My Tasks* sections and preserves parity with Linear.

## 3. Working inside a project you do not own

### Linear

- **Efficient queries for "assigned to me" and "unassigned" in one Project**
  `project(id: $projectId) { issues(first: 100, after: $after, filter: $filter, sort: [{ manual: { order: Ascending } }]) { nodes { ... } pageInfo { hasNextPage endCursor } } }` (page size `first` accepts `1..250`, default `50`) ([Linear Filtering](https://linear.app/developers/filtering), date not shown; [Linear GraphQL Schema](https://raw.githubusercontent.com/linear/linear/master/packages/sdk/src/schema.graphql), retrieved 2026-11-18):
  - **Assigned to me in this Project**:
    `filter: { assignee: { isMe: { eq: true } }, state: { type: { nin: ["completed", "canceled"] } } }`
    (Or across multiple linked Projects in one call: `viewer { assignedIssues(first: 100, filter: { project: { id: { in: $projectIds } } }) { ... } }`).
  - **Unassigned in this Project (on-demand backlog read)**:
    `filter: { assignee: { null: true }, state: { type: { nin: ["completed", "canceled"] } } }`.
  - **Complexity tip**: Never nest multi-connection children (like `project { initiatives(first: 50) teams(first: 50) }` or `comments(first: 50)`) inside an issue list query. Linear calculates complexity from requested `first` multipliers before execution: `100` issues × `50` comments = `5,000+` points per page ([Linear Rate limiting](https://linear.app/developers/rate-limiting), date not shown).

- **Assigning as the claim & what happens on reassignment**
  - **Claiming**: `issueUpdate(id: $issueId, input: { assigneeId: $viewerId })`. Note: Linear GraphQL `issueUpdate` has **no** check-and-set / precondition on current `assigneeId`—if two people assign concurrently, last write wins on Linear; Loopflow should read `issue.assignee` immediately before claiming (or verify the mutation response) and yield if a non-Loopflow user already holds it. Also note Linear separates human `assignee` from agent `delegate` (`delegateId` is for `actor=app` OAuth agents) ([Linear Agents](https://linear.app/developers/agents), date not shown).
  - **Reassignment**: Setting `assigneeId` automatically subscribes the new assignee to notifications, leaves the previous assignee subscribed unless unsubscribed, records an `IssueHistory` entry (`fromAssignee` / `toAssignee`), advances `Issue.updatedAt`, and fires an `Issue` `update` webhook (`updatedFrom.assigneeId`) ([Linear GraphQL Schema](https://raw.githubusercontent.com/linear/linear/master/packages/sdk/src/schema.graphql), retrieved 2026-11-18; [Linear Webhooks](https://linear.app/developers/webhooks), date not shown). When a coworker reassigns or unassigns an issue in Linear, `Issue.assignee` becomes `null` or another `User.id`; Loopflow only sees this without webhooks if it keeps polling `id: { in: $liveClaimedIssueIds }`!

- **Rate limits & GraphQL complexity limits**
  Source: [Linear Rate limiting](https://linear.app/developers/rate-limiting) (date not shown; retrieved 2026-11-18), [Linear Pricing](https://linear.app/pricing) (date not shown; retrieved 2026-11-18), and [Linear Changelog](https://linear.app/changelog) (2026-11-05 & 2026-11-12).
  - **Algorithm & HTTP status**: Leaky bucket (`LIMIT_AMOUNT / LIMIT_PERIOD` constant refill). Returns HTTP **`429`** (changed from `400` on 2026-11-05) with GraphQL error `extensions.code == "RATELIMITED"` and `Retry-After` (seconds), plus `X-RateLimit-Requests-{Limit,Remaining,Reset}`, `X-Complexity`, `X-RateLimit-Complexity-{Limit,Remaining,Reset}`, and endpoint-specific `X-RateLimit-Endpoint-{Name,Requests-Limit,Requests-Remaining,Requests-Reset}` (`Reset` in UTC epoch ms).
  - **Unit of quota**: **Per authenticated `User` (or `actor=app` App User) per 1-hour window**—shared across **all** API keys or user-actor OAuth tokens belonging to that user on that workspace! If one user runs 5 Machines + other Linear tools, all 5 Machines draw from that user's single hourly bucket.
  - **Standard base limits (Free & Basic plans)**:
    - **Personal API key**: **2,500 requests / hour / user** and **3,000,000 complexity points / hour / user**.
    - **OAuth App**: **5,000 requests / hour / user (or app user)** and **2,000,000 complexity points / hour / user** *(note: OAuth gets 2× the request cap of an API key, but 2M vs 3M complexity points)*.
    - **Unauthenticated**: **600 requests / hour / IP** and **100,000 complexity points / hour / IP**.
  - **Workspace plan multipliers**:
    - **Free / Basic**: `1×` standard limits.
    - **Business**: **`2×`** standard limits (OAuth: **10,000 req/hr**, **4,000,000 pts/hr** per user).
    - **Enterprise**: **`5×`** standard limits (OAuth: **25,000 req/hr**, **10,000,000 pts/hr** per user).
    - **Dynamic scaling**: Workspace-level `actor=app` OAuth apps receive additional dynamic scaling based on paid seat count.
  - **Single-query complexity ceiling**: **10,000 points** maximum per query (always rejected above 10,000, regardless of plan). Formula: **0.1 pt** per scalar property + **1 pt** per object, multiplied by connection page argument (`first`/`last`, or **50** if omitted), rounded up to the nearest integer.
  - **Endpoint-specific limits**: E.g., creating comments on a single issue is capped at **200 / minute** (2026-11-05 changelog); OAuth token endpoint is also rate-limited (`429 temporarily_unavailable` + `Retry-After`, 2026-11-12 changelog).

### Asana

- **Efficient queries for "assigned to me" and "unassigned" in one Project**
  Asana has a major REST filtering constraint: **`GET /tasks` does NOT support combining `project` and `assignee` in one query** (`You must specify a project or tag if you do not specify assignee and workspace`) ([Asana Get multiple tasks](https://developers.asana.com/reference/gettasks), updated 2026-05-27; [Asana FAQ](https://developers.asana.com/docs/faq), updated 2026-03-11). The viable patterns are:
  1. **Project task scan (`GET /projects/{project_gid}/tasks?completed_since=now&limit=100&opt_fields=gid,name,assignee.gid,completed,modified_at,external,memberships.section.gid`)**:
     Strongly consistent (read-your-writes), works on **all tiers including Free/Personal**, preserves exact manual project order, and returns both "assigned to me" (`assignee.gid == me`) and "unassigned" (`assignee == null`) in **1 call per 100 open tasks** (e.g., 5 requests for a 500-task project) without disturbing any task ([Asana Get tasks from a project](https://developers.asana.com/reference/gettasksforproject), updated 2026-05-27).
  2. **User's incomplete tasks across workspace (`GET /tasks?assignee=me&workspace={workspace_gid}&completed_since=now&limit=100&opt_fields=...,memberships.project.gid`)**:
     Strongly consistent, works on all tiers, scales with **one person's** open tasks (typically < 100, i.e., **1 request**), filtered client-side to `memberships.project.gid == project_gid`! Cannot answer "unassigned in this project" (use #1 on demand when the user views the backlog).
  3. **Workspace Search API (`GET /workspaces/{workspace_gid}/tasks/search?projects.any={project_gid}&assignee.any=me&completed=false&limit=100`, or `assignee.any=null` for unassigned)**:
     Server-side intersection, **but** fails with **`402 Payment Required`** for non-Premium/Personal users, is capped at **60 req/min**, has **no cursor pagination** (results are unstable; must manually window by `created_at.after`), does **not** return manual project order, and has **10–60 seconds eventual consistency lag** ([Asana Search tasks](https://developers.asana.com/reference/searchtasksforworkspace), updated 2026-05-27). Avoid for core sync; use #2 for "my slice" and #1 for on-demand backlog + order reads!

- **Assigning as the claim & what happens on reassignment**
  - **Claiming**: `PUT /tasks/{task_gid}` with `{"data": {"assignee": "me"}}` (or user `gid`). Like Linear, Asana `PUT /tasks/{task_gid}` has **no** conditional ETag/If-Match precondition on `assignee`—last write wins, so read `GET /tasks/{task_gid}?opt_fields=assignee.gid` before claiming an unassigned task. Write `external: {"gid": task_uuid}` **only** at the moment the task is created by Loopflow or claimed (`lf task claim`), never during read sweeps!
  - **Reassignment**: Updating `assignee` advances `Task.modified_at`, places the task in the new assignee's `user_task_list` ("Recently assigned" section), generates an assignment story, and emits a `task` `changed` event (`change.field: "assignee"`, `new_value: { gid, resource_type: "user" }` or `null`). The previous assignee typically remains in `Task.followers` unless removed ([Asana Events](https://developers.asana.com/reference/events), updated 2025-09-13; [Asana Update a task](https://developers.asana.com/reference/updatetask), updated 2026-05-27).

- **Rate limits, unit, concurrency, and cost limits**
  Source: [Asana Rate limits](https://developers.asana.com/docs/rate-limits) (updated 2026-07-03).
  - **Unit of quota**: **Per authorization token**! With OAuth, **each Loopflow user gets their own independent bucket** (`1,500 req/min` on paid domains), so 50 Loopflow users in a 100-person company get `50 × 1,500 = 75,000 req/min` aggregate capacity rather than sharing one token. **Critical penalty**: requests rejected with `429` **still count against your per-minute quota**, so retrying before `Retry-After` actively starves recovery!
  - **Standard request volume limits (per token, 1-minute window)**:
    - **Free (Personal) domain**: **150 requests / minute / token**.
    - **Paid (Starter, Advanced, Enterprise, Enterprise+) domain**: **1,500 requests / minute / token**.
  - **Search API limit**: **60 requests / minute / token** on `/workspaces/{workspace_gid}/tasks/search` (separate lower cap).
  - **Concurrent request limits (per token, in-flight simultaneously, independent for reads vs writes)**:
    - **`GET`**: **50 concurrent requests**.
    - **`POST`, `PUT`, `PATCH`, `DELETE`**: **15 concurrent requests**.
  - **Computational cost limit**: Dynamic per-minute graph-traversal quota per token (penalizes wide `opt_fields` like `followers,custom_fields,subtasks,likes` across large pages; mitigated by requesting minimal `opt_fields`).
  - **Heavyweight async job limit**: **5 concurrent jobs / user** (duplication, template instantiation, exports—shared with actions the user triggers in the Asana web UI).
  - **Batch API (`POST /batch`)**: Up to 10 actions per HTTP call; reduces concurrency/round-trips, **but each inner action still counts as 1 request** against the 150 / 1,500 per-minute volume limit.

## 4. Knowing something changed without a public server

### Linear

- **Polling strategies (no public server)**
  - **No public sync/delta token endpoint**: Although Linear's own web/desktop client uses an internal sync engine (mutations return `lastSyncId: Float!`), the GraphQL schema explicitly marks `lastSyncId`: *"Synchronization cursor used by Linear clients. External integrations can ignore this field."* There is no public `syncBootstrap` or delta endpoint in `Query`, and `Subscription` types are not documented for third-party clients ([Linear GraphQL Schema](https://raw.githubusercontent.com/linear/linear/master/packages/sdk/src/schema.graphql), retrieved 2026-11-18). Linear's rate-limit guide states *"Avoid polling"*, and when polling is unavoidable recommends sorting by `updatedAt` with tight filters ([Linear Rate limiting](https://linear.app/developers/rate-limiting), date not shown; [Linear Pagination](https://linear.app/developers/pagination), date not shown).
  - **Recommended slice-scoped `updatedAt` poll**:
    Instead of `linear/team_changes.rs` polling the whole Team, poll only the user's slice + known live `trackedIds` (issues currently claimed/stored locally and not terminal):
    1. `issues(first: 50, orderBy: updatedAt, filter: { updatedAt: { gte: $since, lte: $through }, or: [{ and: [{ project: { id: { in: $waveProjectIds } } }, { assignee: { isMe: { eq: true } } }, { state: { type: { nin: ["completed", "canceled"] } } }] }, { id: { in: $liveTrackedIssueIds } }] })`
    2. `comments(first: 50, orderBy: updatedAt, filter: { updatedAt: { gte: $since, lte: $through }, issue: { id: { in: $liveTrackedIssueIds } } })`
  - **Edge cases to handle when polling `updatedAt`**:
    - *Unassignment / deletion / archive*: Including `{ id: { in: $liveTrackedIssueIds } }` (with `includeArchived: true` or checking missing/archived issues) catches a coworker reassigning an issue away, completing/canceling it, or trashing/archiving it (`archivedAt != null`, `trashed == true`).
    - *`updatedAt` housekeeping caveat*: Linear's schema notes on `updatedAt`: *"When the resource was last meaningfully updated, in UTC. Some background or housekeeping changes do not advance this timestamp."* Whether `sortOrder`-only edits advance `Issue.updatedAt` is **unconfirmed**; backlog order should be read fresh when viewing/reordering the backlog rather than assumed current from `updatedAt` deltas.

- **What webhooks would add (with a hub or relay)**
  - Subscribing to `Issue`, `Comment`, `Attachment`, and `Project` pushes `create` / `update` / `remove` JSON payloads with `actor` and `updatedFrom` within seconds, eliminating idle polling complexity burn ([Linear Webhooks](https://linear.app/developers/webhooks), date not shown).
  - **Catch for decentralized teams**: Creating/reading Linear webhooks via `webhookCreate` **requires Workspace Admin permissions** (or an OAuth app authorized at workspace level with `admin` scope, or OAuth app-level webhook configuration), requires a public non-localhost HTTPS URL responding within **5 seconds** (3 retries at 1m, 1h, 6h before auto-disable), and as of **2026-10-08** Linear enforces a hard quota of **30 webhooks per team** and **50 webhooks per workspace** ([Linear Webhooks](https://linear.app/developers/webhooks), date not shown; [Linear Changelog](https://linear.app/changelog), 2026-10-08). Individual non-admin engineers cannot register personal webhooks on their team's Linear; only a shared Loopflow OAuth app relay or an admin-configured hub could.

### Asana

- **Polling strategies (no public server)**
  1. **Events API (`GET /events?resource={project_gid}&sync={sync_token}`)** — **Vendor-recommended serverless poll**:
     - Asana explicitly recommends `GET /events` when you do not run a public webhook server: *"For most simple integrations, events provide much of the same benefits while using a significantly simpler implementation which does not require maintaining an internet-accessible server... In general, requesting events on a resource is faster and subject to higher rate limits than requesting the resource itself."* ([Asana Webhooks guide](https://developers.asana.com/docs/webhooks-guide), updated 2026-03-23; [Asana Events](https://developers.asana.com/reference/events), updated 2025-09-13).
     - **How it works**: First call without `sync` returns `412 Precondition Failed` + a fresh `sync` token. Subsequent calls pass `sync={token}` and return all events since that token plus the next `sync` token. Events on a `project` **bubble up** changes to tasks in that project, subtasks, and stories/comments (`comment_added`, `assignee` changed, task `added`/`removed`/`deleted`).
     - **Limits & fallback**: Sync tokens **expire after 24 hours** (or sooner under load), returning `412 Precondition Failed`. Delivery is **at-most-once** (average latency < 1 minute; rare dropped events possible), and each active `/events` stream counts toward the **1,000 webhooks/streams per resource** limit ([Asana Events](https://developers.asana.com/reference/events), updated 2025-09-13; [Asana Webhooks guide](https://developers.asana.com/docs/webhooks-guide), updated 2026-03-23). Therefore, pair `GET /events` (every 15–30s while active) with a `modified_since` catch-up scan on `412` or startup!
  2. **`modified_since` polling (`GET /tasks?assignee=me&workspace={gid}&modified_since={iso}` + exact reads on `$liveTrackedTaskGids`)**:
     - Strongly consistent and catches edits, assignments, completions, and comment additions (stories advance `Task.modified_at`).
     - **Caveat**: Moving a task between projects/sections or reordering it does **not** advance `Task.modified_at` ([Asana Update a task](https://developers.asana.com/reference/updatetask), updated 2026-05-27), and unassigning a task removes it from `assignee=me`—so any task in `$liveTrackedTaskGids` not returned by `assignee=me` must be checked by GID or via the project's `/events` stream.
  3. **Search API (`modified_at.after`)**: Inferior for sync polling (60 req/min cap, `402` on Free, 10–60s indexing lag) ([Asana Search tasks](https://developers.asana.com/reference/searchtasksforworkspace), updated 2026-05-27).

- **What webhooks would add (with a hub or relay)**
  - Unlike Linear, **any Asana user with read access to a project or task** can create a webhook (`POST /webhooks` with `webhooks:write`)—no workspace admin required! Limits are **1,000 webhooks per resource** and **10,000 webhooks per token** ([Asana Webhooks guide](https://developers.asana.com/docs/webhooks-guide), updated 2026-03-23).
  - However, Asana webhooks share the exact same underlying infrastructure, < 1 min average (~10 min tail) timing, compact-only payloads (still require a follow-up `GET` to read full state), and **at-most-once** delivery as `GET /events`, while adding an interactive `X-Hook-Secret` creation handshake and 8-hour heartbeat requirement (deleted after 24h of missed heartbeats). Notice also that higher-level webhooks (`team`, `portfolio`, `goal`, `workspace`) **do not propagate task, subtask, or story events**—task webhooks must be registered per `project` or per `task` ([Asana Webhooks guide](https://developers.asana.com/docs/webhooks-guide), updated 2026-03-23). Without a public server, `GET /events` on each linked `project` gives ~95% of webhook ergonomics.

- **Design fit for Asana**:
  - **Map a Wave directly to an Asana `Project`** (and stop auto-creating a parallel "repository project" when linking to an existing team's Asana project!).
  - `Project` is the **only** Asana container available on Personal and Starter plans, the **only** container with manual task ordering (`addProject`), the **only** container where task and comment events bubble up to `GET /events`, and `ProjectBrief` + `StatusUpdate` map cleanly to Wave `GOAL.md` / status updates.
  - `Portfolio` (for grouping sequential Wave Projects) and `Goal` + `GoalMetric` (for numeric KRs / metric targets) should be strictly optional enrichments when the workspace is on Asana Advanced+, never required to run a Wave.

## 6. Community techniques: storing state and staying out of a team's way

1. **Linear first-party integrations (GitHub, Sentry, Zendesk, Intercom, Slack, Jira)**
   - **Link attachments instead of description edits**: Sentry, Zendesk, Intercom, Front, Salesforce, Slack, and GitHub all attach one URL-keyed `Attachment` per external ticket/PR/thread (`attachmentCreate` / `attachmentLink*`) carrying external IDs and conversation previews in `Attachment.metadata` + status in `Attachment.subtitle`, leaving `Issue.description` untouched ([Linear Attachments](https://linear.app/developers/attachments), date not shown; [Linear Sentry](https://linear.app/docs/sentry), date not shown; [Linear Zendesk](https://linear.app/docs/zendesk), date not shown; [Linear Intercom](https://linear.app/docs/intercom), date not shown). When duplicate Linear issues are merged, Linear automatically migrates attachments to the canonical issue (`Attachment.originalIssue`) and updates linked Zendesk/Slack threads.
   - **Thread isolation for noisy sync**: Slack thread sync (`attachmentLinkSlack(syncToCommentThread: true)`) binds external chat replies into **one dedicated root `Comment` thread** (`Comment.externalThread: SyncedExternalThread`) instead of flooding top-level issue comments ([Linear Slack](https://linear.app/docs/slack), date not shown; [Linear GraphQL Schema](https://raw.githubusercontent.com/linear/linear/master/packages/sdk/src/schema.graphql), retrieved 2026-11-18).
   - **Non-destructive label & deletion rules**: Linear's Jira sync **never deletes** the remote issue when one side is deleted, and **only maps labels that already exist in Linear** rather than auto-creating foreign labels in the team's taxonomy ([Linear Jira](https://linear.app/docs/jira), date not shown).

2. **SyncLinear (`calcom/synclinear.com` — open-source two-way Linear ↔ GitHub Issues sync)**
   - **Opt-in scope gate**: Syncs **only** Linear issues that carry an explicit `"Public"` label (`publicLabelId`) and GitHub issues carrying `"linear"`, leaving the rest of the team's Linear backlog untouched ([`linear.handler.ts`](https://github.com/calcom/synclinear.com/blob/main/utils/webhook/linear.handler.ts), archived 2026-04-20).
   - **Zero-UI-noise echo prevention via deterministic UUID suffix**: When creating a Linear issue or comment from GitHub, SyncLinear passes a caller-generated UUIDv4 whose last 8 hex digits are `"decafbad"` (`generateLinearUUID()` in [`utils/linear.ts`](https://github.com/calcom/synclinear.com/blob/main/utils/linear.ts) and [`utils/constants.ts`](https://github.com/calcom/synclinear.com/blob/main/utils/constants.ts)). When Linear's webhook echoes that creation back, `data.id.includes("decafbad")` drops it immediately with zero text markers in Linear!
   - **Asymmetric link storage**: On Linear, SyncLinear calls `attachmentCreate` with the GitHub Issue URL (clean UI card, no Linear description footer); on GitHub (which has no attachment object), it appends a `<sub>` link footer on the issue body and `<!-- From <user> on Linear. LinearCommentId:<uuid>: -->` on comments so comment edits round-trip ([`utils/index.ts`](https://github.com/calcom/synclinear.com/blob/main/utils/index.ts), [`utils/github.ts`](https://github.com/calcom/synclinear.com/blob/main/utils/github.ts)). It also skips creating missing labels in Linear *"to avoid cluttering Linear"* ([`github.handler.ts`](https://github.com/calcom/synclinear.com/blob/main/utils/webhook/github.handler.ts)).

3. **`git-bug` (`git-bug/git-bug` — distributed offline-first bug tracker in Git refs)**
   - **Git-ref operation log + Lamport clocks**: Stores each entity as an operation log in Git refs (`refs/bugs/<id>`) ordered by Lamport logical clocks (`create-clock-<n>`, `edit-clock-<n>` as zero-byte Git tree entries) with deterministic hash tiebreaking—very close to `scratch/plan-design.md`'s `(counter, machine id)` stamped refs ([`doc/design/data-model.md`](https://github.com/git-bug/git-bug/blob/trunk/doc/design/data-model.md), retrieved 2026-11-18).
   - **Zero remote tracker pollution**: `git-bug`'s bridges (GitHub, GitLab, Jira) write **no hidden markers, attachments, or custom fields** onto the remote tracker at all! Instead, `git-bug` stores remote tracker IDs and URLs (`github-id`, `github-url`, `origin`) as **immutable metadata on the Git-side `Operation`**, maps each author to their own API token (`getClientForIdentity`) so exports act as the real author, and skips operations authored by teammates whose token isn't present ([`bridge/github/export.go`](https://github.com/git-bug/git-bug/blob/trunk/bridge/github/export.go), [`bridge/github/import.go`](https://github.com/git-bug/git-bug/blob/trunk/bridge/github/import.go), retrieved 2026-11-18).

4. **Sentry (`getsentry/sentry`) & `bugwarrior` (`GothenburgBitFactory/bugwarrior`)**
   - **Sentry Linear integration**: Installs once per workspace with `actor=app`, stores workspace/issue-link state in Sentry's own `ExternalIssue` table + a single Linear `Attachment` per linked Sentry group, and serializes OAuth refresh token rotation behind a 30-second reuse lock so concurrent workers don't invalidate rotating grants ([`src/sentry/integrations/linear/client.py`](https://github.com/getsentry/sentry/blob/master/src/sentry/integrations/linear/client.py), [`integration.py`](https://github.com/getsentry/sentry/blob/master/src/sentry/integrations/linear/integration.py), retrieved 2026-11-18; Loopflow already implements a similar file lock in `ops/linear.rs:321`).
   - **`bugwarrior`**: Personal CLI pull-tracker used by individual developers inside large company trackers; queries strictly `assignee.email == me` + active `state.type in ["backlog", "unstarted", "started"]` with `first: 250` cursor pagination and stores mapping keys (`linearurl`, `linearidentifier`) locally as Taskwarrior UDAs without ever writing back to unassigned team issues ([`bugwarrior/services/linear.py`](https://github.com/GothenburgBitFactory/bugwarrior/blob/develop/bugwarrior/services/linear.py), retrieved 2026-11-18).

## What `scratch/plan-design.md` gets wrong or has not decided

1. **Wrong — "Backlog order is the Project's order" on Linear (lines 123–128):**
   Linear has no per-Project issue order. Writing `Issue.sortOrder` reorders those issues in **every** manually sorted view in the workspace (Team board, Team backlog, Cycles, Custom Views). Moreover, Loopflow's existing `linear/actions.rs` writes `prioritySortOrder` alongside `sortOrder`, which scrambles Priority-sorted views rather than cleanly updating Manual order (`sortOrder`). *Decision needed*: write `sortOrder` alone (matching Linear's Manual sort) and accept that Team-board manual order moves too, or don't write order to Linear unless explicitly requested.

2. **Wrong / risky — "One `loopflow://task/<id>` attachment per issue, shown to everyone as a link" with API-only `metadata` (lines 132–136):**
   - `loopflow://` as an `AttachmentCreateInput.url` scheme is **unconfirmed** (Linear expects domain-bearing URLs for `attachmentSources` and requires `http(s)://` on agent links).
   - Every attachment is visible to non-Loopflow teammates as a link card, which violates *"Me using Loopflow to sort of interact with my team's Linear doesn't get in the way"* if created on issues that have no real external URL.
   - `Attachment.metadata` is **full-replacement on update** (concurrent writers clobber keys unless read-modify-written) and Linear warns `metadata` may be surfaced in the UI later (`title`, `messages`, `attributes` already are).
   - Meanwhile, the design overlooks that **Asana already has a true UI-invisible, OAuth-app-shared 32 KB store (`external.data`)** while Linear does not. Luckily, nothing in the current design actually *needs* shared Loopflow-only per-task fields yet—drop the `loopflow://` attachment until a real shared field exists.

3. **Undecided (Open item, line 214) — "Does a Wave link to a Project, an Initiative or either":**
   The research resolves this: **an Initiative (Linear) or Portfolio (Asana) cannot hold Tasks directly**, Initiatives may be disabled in Linear, and Portfolios/Goals return `402 Payment Required` on Asana Personal/Starter. To work inside a team's existing tracker without reorganizing their workspace, **linking a Wave directly to one `Project` must be supported on both Linear and Asana** (with `Initiative` optional on Linear when a Wave spans multiple Projects).

4. **Undecided (Open item, lines 212–213) — Non-user reassigns or closes an issue while its Graph runs:**
   - First, Loopflow won't even **notice** an unassignment unless its delta query explicitly includes `id: { in: $liveClaimedIds }` alongside `assignee == me` (because once unassigned, `assignee == me` stops matching!).
   - Second, neither Linear `issueUpdate` nor Asana `PUT /tasks/{gid}` has server-side compare-and-swap on `assignee`. Stopping the local Graph run and keeping the worktree/branch (matching Rule 4's losing-claim behavior on line 47: *"stops its run, keeping the work"*) avoids fighting a human teammate over ticket state or posting unsolicited bot comments into a 50%-non-Loopflow team's issue.

5. **Contradictions with existing `rust/loopflow-execution` code not yet listed in "What is deleted" / "Changes" (lines 142–163):**
   To ship Slice 4 (*"Your slice of a Linear Project"*) and Asana parity, four existing code paths must change:
   - Remove `LinearClient::claim_team` / `validate_team_claim`'s `<!-- loopflow-repository: ... -->` mutation on `Team.description` (`linear/mod.rs:666-755`) so multiple repos and non-admin adopters can share an existing Linear Team without editing Team settings.
   - Relax `validate_project_ownership` (`linear/mod.rs:41-73`, `ops/linear.rs:856-900`) so multi-team Projects (`project.team_ids.len() > 1`) and Projects in `0` or `>1` Initiatives are accepted.
   - Replace `LinearClient::team_changes` (`linear/team_changes.rs`) + `check_scope` (`ops/tracker_events.rs:208-239`) so unmapped Team issues are **not** auto-ingested into `tasks`.
   - Stop `AsanaClient::changes` (`asana/mod.rs:336-343`) from writing `PUT /tasks/{gid}` `{"external": {"gid": ...}}` onto unassigned/coworker tasks during read polls, and remove the mandatory shadow "repository project" when a Wave links directly to an existing Asana `Project`.
