# Upgrade audit, 2026-11-05

For Jack Heart. Read-only; anchors are this worktree at 3b07e13404 unless a commit is named. Builds on `scratch/upgrade-incident-2026-11-04.md` and the memory notes it cites.

Jack's two rules, used as the test for every option below:

1. A version rising is about features for people. Store-compatibility markers are plumbing; they never end a Session or ask a person to act.
2. A conversation keeps working when lf's store breaks. The store records the conversation; the conversation never depends on it.

## 1. How an upgrade flows today

`lf install` on this Mac, `stream: dev` (`~/.lf/config.yaml:5`), run by hand or by `com.loopflow.refresh` at 09:00 and at login (`~/Library/LaunchAgents/com.loopflow.refresh.plist`; written by `install/published.rs:681-703`, `:854-858`).

1. `published.rs:55-77 install()` picks the stream, finishes any interrupted switch, and for `dev` calls `main_build` (`:290-330`), which downloads the newest green-main package and runs the *candidate* as `lf install promote --cli-target …` (`promote_build`, `:337-353`). The parent never opens the store for writing and dispatches before journal emission, so no Process row (`bin/lf.rs:2010-2016`, since #1074 on 2026-07-17).
2. The candidate takes the promotion lock (`install.rs:2729`), reads a preview of the store (`read_binary_preview`, `classify_compatibility` `:258-320`), and decides (`decide()` `:185-240`). `AheadPending` with every pending migration merged is `PromoteAndMigrate`; `raised_reader_floor` is computed (`:278-290`) and never read by `decide`. `render_human` prints only under `preview_only` (`:2756`; `#1649`: "Newcomers see only the outcome"). So a floor-raising dev install prints nothing before acting.
3. Validation runs the migrations on an APFS clone (`#1824`), then the real store is advanced under the migration lock: `apply_sqlite_with_backup` (`migrations.rs:429-456`) clones `loopflow.db` to `<db>.backup-<version>-<16hex>`, applies the pending tail in one exclusive transaction, and prunes backups to 1. The commit is the moment every other process's world changes.
4. Desktop is stopped and restarted (`quiesce_app_processes` `install.rs:1844-1870`, SIGTERM then SIGKILL at 5 s; `#1815`). Nothing else is touched: "preserve running Session helpers, Graphs".
5. `settle_switch` (`:2494-2507`) prunes the backup to 0 ("The settled release opens the store, so nothing restores its pre-migration clone") and removes superseded binaries no live process executes (`:2515-2560`).
6. Only now `report_after_promote` (`rollover.rs:601-620`) inventories live processes and prints "still running the previous lf … each ends as its Session goes idle".

What the 177 old processes meet, from the commit on:

- Every reopen of the store runs the floor check (`sqlite.rs:569-640`: `validate_sqlite_schema` `:611`, `pending_shared_migration` `:612` → `admitted_newer_floor` `migrations.rs:1183-1215`). A build that does not know the newest floor gets `this store needs an lf that knows task_session_promotion … run lf install`. Long-lived processes reopen constantly (telemetry writes in `lf.log` at 20:02:56).
- SQL that names a dropped column fails at once: `route='local'` in `sqlite.rs:266@ac8e088f5`, the Task lookup in `task_work.rs:560@ac8e088f5`.
- The Codex relay lives inside the Session owner (`util.rs:992-1020 serve_codex_native` → `CodexConnection`). While idle it polls `updates.pending` every second and returns `Err` on any store error but `InvalidAuthority` (`codex_connection.rs:463-471`, `:491-500`). The relay task ends, the client websocket closes, the Codex TUI shows "Reconnecting". Every reconnect enters `serve_with_input`, which reads the store *before* `accept_async` (`:410-420`, `:438`), so each retry fails in handshake until the 2-minute timeout. 317 relay failures across 20 Sessions, 20:02:55 to 20:07:50.
- A Claude Session is the exec'd provider: `exec_native` (`agent_process.rs:152-185`) records the launch, then `command.exec()`; the owner *is* `claude`. No lf code sits between the keyboard and the provider. Store writes happen in short-lived hook processes (`task_updates::watch` `task_updates.rs:223-241` opens the store per hook; `claude_updates.rs:20-33`) and once at exit (`native_exit.rs:48`). A failing hook fails a hook process; the conversation never notices. That is the whole reason Claude survived and Codex did not.
- A Graph runner's next step is a fresh `lf` launch through the entry, so it runs on the new build; the runner itself keeps old code and fails where it reads the store (`rollover.rs:423-431`).
- `lf monitor rollover` (`#1799`) decides eligibility by reading the owner's state from the store, so an owner that cannot open the store is "keeps its lf until it exits" (`rollover.rs:393-396`). On 10-30 it moved 0 of 31; on 11-04, 29 of 134.

Fifteen manage skew after it exists; two (classifier, floor) decide who is locked out; none prevents a destructive commit under live readers, and none keeps lf out of the conversation's data path. The stated policy matches the code: "Installation does not restart existing processes or wait for their exit; they may continue or fail naturally" (`docs/architecture/machines.md:373-379`); Jack removed executable pinning after #1587, "accepting natural failure and retry", and "compatibility probing and installer-triggered restart are deleted" (`.lf/wave/infrastructure/MEMORY.md:952-984`). Natural failure is the design. What the design did not say is that the failure would land in the conversation.

## 3. Why the class recurs

Two structural facts. The rest are consequences.

**A. One file, commit-time truth, process-lifetime code.** `~/.lf/loopflow.db` is opened directly by every build on the Machine; a migration is true for everyone the instant it commits; a binary is fixed for the life of its process, and Jack runs processes for days. Every row in the incident table (10-19 through 11-04) is this fact. The floor, the classifier, rollover, fallbacks, the clone, the preview: all of them exist to manage the gap this fact opens, and each one has been patched after a skew event. Candidate "one shared store with commit-time schema change and process-lifetime binaries": **holds**, and is the root.

**B. lf sits in the conversation's data path, and reads the store there.** For Codex, the relay is inside the Session owner and polls the store every second with store errors fatal (`codex_connection.rs:491-500`); reconnect reads the store before accepting (`:410-420`). For every harness, the owner opens the store to settle the exit (`native_exit.rs:48`). Claude survived 20:02 because its conversation path contains no lf code at all (`exec_native`). Same commit, same floor, same processes; the harness that depended on the store died and the one that only recorded to it lived. Candidate "conversations depend on the store instead of only recording to it": **holds**, and is the fact Jack's rule 2 names directly.

The other candidates, against the evidence:

- "The floor conflates schema-differs with old-SQL-breaks": **true but secondary**. `is_additive` is a structural diff; `wave_removal` and `task_session_promotion` raised the floor and broke no SQL. Fixing the semantics would have spared 09:16 and left 20:02 untouched, because at 20:02 old SQL did break. A floor with perfect semantics still ends Sessions when a drop lands; it is the drop, not the floor's precision, that matters.
- "Release version marks features while compatibility is tracked separately, so users see neither": **holds in the form Jack means**. Nothing couples version and floor. The floor reaches release notes only through a hand-written `release/unreleased/BREAKING.md` line (`release.rs:2761-2790`, `:2586-2594`), written once ever (#1760, by hand). Today `release/unreleased/` holds only DECISIONS.md while the installed build's reader catalog ends `0.15.0.001_release, wave_removal, settings_authority, task_session_promotion`: three floor raises since v0.15.1 with no version change and no note. So rule 1 is already the de-facto state; the version carries no compatibility meaning. What people see instead is the floor itself: `this store needs an lf that knows task_session_promotion`. A slug, invisible until it is lethal. Under rule 1 the message has to disappear, which means the concept has to.
- "Install owns promotion but nothing owns the live process population": **holds as a description, not as a cause**. `decide()` sees no processes; `report_after_promote` runs after the commit; Jack ruled on 2026-11-02 (LOO-693) that install does no rollover and "I have LF processes running 24/7". Owning the population is a *way out* of A; it is not why A hurts.

## 4. What fundamentally needs to change

Three options evaluated, plus the LOO-705 exec-forward sketch folded into (c).

### (a) One long-lived store owner; binaries never open the store directly

`lf server` from #1813 is this seed: Desktop already routes Work through a local server there. Extend: every lf process talks to the server; only the server opens `loopflow.db`.

- Demo: Jack runs `lf install` with 20 Sessions open; `lf server status` shows the server restarted on the new build; every Session keeps talking.
- Deletes: nothing in §2 by itself. The floor moves from SQL to the server's startup. Old clients still speak an old RPC to a new server: skew moves from SQL (which SQLite tolerates for additive change) to a protocol lf would have to version, the thing Jack has said not to build yet. Rule 2 is met only if clients also tolerate the server being down, which is option (b)'s work anyway.
- Live processes: unchanged; they reconnect to a restarted server. Busy owners still carry old client code.
- Cost: highest. A new process to supervise (launchd, crash loops, syspolicyd class), a wire protocol with a compat story, and Desktop's FFI deletion (#1813) as prerequisite.
- Open question: whether Jack wants a daemon on every Machine at all; 2026-09-27 deleted lfd and the residents.

### (b) The store only records; destructive change is always staged; the floor is deleted

Two halves, each independently valuable.

*Conversations never depend on the store.* Every lf process in a conversation's path treats a store error as a recording gap: log it, keep passing bytes, retry recording later. Concretely: the relay's `update_clock` arm and `history.outbound` stop returning `Err` on store errors; `serve_with_input` stops reading the store before `accept_async`; the owner's exit settle is already tolerant on main (`transport.rs:1236-1245` writes "Loopflow could not record this exit" and continues). Task updates become best-effort reads, as they already are for Claude.

*Destructive change is staged, so no reader is ever locked out.* Jack's 10-27 rule, finally in the repo: a migration is additive, or it is a dated contract that drops what an expand migration merged ≥30 days earlier left behind. A build therefore never meets a store missing something it reads unless its process is older than 30 days, and then (first half) it logs and continues; `lf resume` moves it. With that, the floor has no job:

- Deletes: `reader_floor` semantics (`admitted_newer_floor`, `newer_store_floor`, `store_reader_floor`, `raised_reader_floor`, `reader_catalog`, `can_open`, `release_opens_store`, `Compatibility::Behind`, `binary_opens_store` in rollover, the "needs an lf that knows" message, `-- breaks:`, the floor line in release notes); `validate_schema_within`'s byte-identical rule for triggers/indexes/views; the `copies/` directory; hotfix dirs; `prune_migration_backups(.., 0)` at settle. The `reader_floor` column stays as immutable ledger history (shipped records), unread.
- Keeps: the ledger, checksums, immutability of merged migrations, the validation snapshot, the promotion lock, streams, scheduled refresh, Desktop promotion, rollover as an operator tool, the one remaining refusal (a binary *newer* than the store, `unapplied_message` `sqlite.rs:612`), which only ever hits a fresh process and names `lf install`.
- `is_additive` moves to `check_migrations.py` as the staging rule: a slug on this branch must be additive against origin/main's schema, or be a contract whose expand slug merged ≥30 days ago by `git log origin/main` date and whose data it drops was exported (3fcb3f is the template). A CHECK-only rebuild is additive for readers; the check says so. This is a CI measurement, the kind Jack has accepted; no runtime guard, no refusal to install.
- Live processes: untouched. Old code runs against a superset schema for 30 days. Old writers leave new columns NULL; MIGRATIONS.md:104-110 already demands new code read that.
- Rule 1: the version carries no compatibility meaning because nothing does; release notes lose the "lf < X" line. Rule 2: by construction.
- Demo: Jack opens a Codex Session and a Claude Session, runs `lf install` for a build carrying an expand migration and, separately, a contract migration past its date. Both Sessions keep accepting input through both installs; `lf.log` shows the recording gaps; `lf resume` on the Codex Session afterwards lands on the new build with history intact. Then he runs `lf install` for a candidate with a non-staged `DROP COLUMN`: CI red on the PR is the only place it can fail.
- Cost: medium. Mostly deletion in `migrations.rs`/`install.rs`/`rollover.rs`/`published.rs`; the relay change (e46a80, running); the CI rule (843f5c, running, partly); MIGRATIONS.md rewrite.
- Open question: whether validation of a newer store should be deleted outright or reduced to "the columns this build's SQL names exist". Deleting it means an old build learns of a missing column from SQLite, once, in a recorded error; that is the first half's contract, so deletion is consistent. Second: 30 days is a number Jack picked; the check needs it in one place.

### (c) Install moves the live population, so skew lasts seconds

Rollover during install (`#1799` plus exec-forward at idle boundaries from LOO-705: a long-lived lf re-execs into the installed lf between turns/steps and on attach, keeping identity, PTY and saved provider conversation).

- Demo: `lf install`; within one idle boundary every Session and runner shows the new build in `lf monitor rollover --dry-run`.
- Deletes: rollover's eligibility list and most per-surface skew wording (LOO-705's inventory). Not the floor: between the commit and the re-exec the old process must survive the store error, so (b)'s first half is a prerequisite, and the floor still fires on any process that is busy.
- Live processes: idle ones move within a boundary; the 22 "held by native input" and anything mid-turn keep old code for as long as they are busy, which can be hours. Exec-forward of the Codex relay must carry the client's socket through `exec` (fds survive; the websocket state does not, so the client reconnects once).
- Cost: medium-high and new mechanism. It also runs against the 2026-11-02 decision "no process rollover at install", the standing "I have LF processes running 24/7", and the earlier deletion of "installer-triggered restart" after #1587 (`MEMORY.md:952-984`); it is enforcement by process management, the class Jack has rejected. Today's rollover is the opposite of a move: it kills the owner and starts a fresh resume (`human_session.rs:1210-1227`, `restore.rs:58-93`), never touching a drafted owner.
- Open question: whether Jack wants install to touch processes at all. If yes, exec-forward is the right shape and (b) is still needed underneath it; if no, (c) is off the table.

### (d) What the code suggests beyond the brief

Nothing better than (b). One observation worth recording: the Claude path already *is* rule 2. The design principle to write down is the one `exec_native` embodies: lf is never in the byte path between a person and their provider except as a pass-through that keeps passing when the store is gone. Codex has a relay because the app-server protocol needs a socket; the relay can obey the same principle.

## 5. The three mysteries

**10-30: an additive install broke 0.15.0 readers.** Solved; LOO-693 recorded it. v0.15.0 (acd37dde71) predates slug ids (#1755, 10-29). Its `admitted_newer_floor` ran `MigrationId::parse_version(version).ok_or_else(incompatible)` on each unknown tail row; `parse_version("ship_stop")` is `None`, so it never reached the floor and returned `RECREATE_MESSAGE` "incompatible Loopflow database; delete loopflow.db and rerun the command" (`v0.15.0:migrations.rs:130-131`, `:1280`, `:1347`). The floor stayed at `0.15.0.001_release`; additivity was irrelevant. A reader-format change shipped inside a release cycle is the same class as A, with the id format instead of a column. Main's `incompatible` now says keep the file (`migrations.rs:1515-1530`). Under (b) this class cannot recur: nothing an old reader does with an unknown row decides whether it opens.

**Quitting an old lf hangs the terminal.** Narrowed, not solved. The viewer puts the tty in raw mode (`cfmakeraw`, `transport.rs:1604-1614`), so Ctrl-C and Ctrl-D are bytes, not signals, until `restore` (`:1543-1555`), which runs after the owner's `NativeEnded`/exit reply (`:1215-1230`). On main, a failed exit settle is caught and still replies (`:1236-1245`). On the build that was running (`ac8e088f5`), five quits recorded `no such column: route` as the Process error, so the write failed fast, not by the 15 s busy timeout (`sqlite.rs:78`). What is unknown is where that build's owner stopped before replying; its code path for a settle error is not main's. The structural fix is independent of the answer: a viewer that owns the tty needs a path back to cooked mode that does not wait on the store (restore on owner EOF, which `finish_client` should already produce), and under (b) the settle never errors on skew.

**No Process row for the 19:57 `lf install`.** By design, since #1074 (2026-07-17): `lf self install` dispatches before home routing and journal emission because a candidate that does not know the frontier must reach preflight, not die in trace capture (`bin/lf.rs:2010-2016`; the later arm is `unreachable!` `:3034-3037`). The riskiest command on the Machine is unrecorded on purpose. Why the 09:15 `lf self install --dev` has a row is unknown; it went through the same arm, so the row came from elsewhere (an agent-issued-command observer, or a branch build). Check that row's argv and `parent_lf_process_id`. Under (b) install can record itself after the store is readable again, as a plain Process; nothing about the candidate's frontier blocks a write once the migration has committed.

## 6. Recommendation

Path (b), in this order, each a landable PR with its own demo:

1. **e46a80 as scoped** (any conversation keeps working when the store breaks, all harnesses, quit and resume). It is (b)'s first half and the only change that protects Sessions on builds from today forward. Fits exactly. Two additions to its brief: `serve_with_input` must not read the store before `accept_async`, and the viewer must return the tty to cooked mode on owner EOF regardless of settle.
2. **Delete the floor** (new Task, infrastructure Wave): remove the §2 "Deleted" column, relax or delete `validate_schema_within`, keep the clone while `rollover::inventory()` reports any process on an older build (`lf doctor` already reads that inventory, `doctor.rs:142-172`), print that inventory on every `lf install` before promoting (visibility, not a gate), record install as a Process after the commit, remove `copies/` and the hotfix dirs, rewrite MIGRATIONS.md's "Older lf keeps opening…" section, delete the `BREAKING.md` plumbing in `release.rs`, and fix `docs/ops.md:106` ("Loopflow keeps no scheduler") and `monitor.rs:26`. With old builds able to open the store again, `lf self install rollback` and the retained `lf-<sha>` binaries become a real rollback path for the first time since 10-19. Demo as in §4(b).
3. **843f5c, re-scoped.** Of its four outcomes: the staging rule in MIGRATIONS.md/AGENTS.md/`check_migrations.py` fits and is the CI half of (b); "every install shows running processes before commit" fits and should move into step 2 or stay here. "Floor rises only when old SQL breaks" and "shows floor rise" are patches to the thing step 2 deletes; drop them, or the Task lands semantics for a check that is removed a week later. "Floor-raising install keeps its backup" becomes "an install keeps its backup while an older build runs". Tell the running step now, before it writes floor code.
4. **3fcb3f** (cutover exports login emails) is unrelated to upgrade architecture and should land: it repairs a shipped contract's export and is the template for the rule that a contract migration exports what it drops (`settings_authority` dropped `tasks.agent` with no export; the only copy is a hand-made 10-28 backup).

Two things on the table that cut against this and need a decision from Jack before 09:00 runs again: `#1808` (unarmed auto-revert of #1803) deletes `wave_removal.sql`, which this store has applied; `#1819` (unarmed auto-revert of #1815) restores the CLI-only install behind 09:16. Neither has auto-merge; both should be closed.

Not recommended now: (a), because it moves skew from SQL, where SQLite tolerates additive change for free, to a protocol lf would have to version; and (c), because it is process management, the class Jack has declined three times, and it still needs (b) underneath it. Exec-forward at idle boundaries stays a good shape for *getting features sooner* once (b) makes skew harmless; it is not compatibility machinery and should not be built as such.
