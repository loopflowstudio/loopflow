# W2-127 — Release-scoped database migrations

## Where we actually start

There is no migration sequence to namespace. `rust/loopflow/src/store/migrations.rs`
carries exactly one file, `migrations/001_initial.sql`, and the rule today is:

- fresh db → run the baseline, stamp `schema_migrations` with `001_initial`;
- any other db → compare live tables/columns against the baseline SQL and, on any
  difference, return *"incompatible Loopflow database; delete loopflow.db"*.

A schema change is made by **editing the baseline**, which silently invalidates
every existing database. That is the real defect behind this task. Release-scoped
ids are the naming half; the forward-migration chain is the half that makes shipped
databases survive an upgrade at all.

## Decision

Migration identity is `{major}.{minor}.{ordinal:03}_{name}`, flat in one directory:

```
rust/loopflow/src/store/migrations/
  0.10.001_initial.sql          # today's baseline, renamed, byte-identical
  0.11.001_add_thing.sql        # next minor's first migration
  0.11.002_add_other.sql
```

- **Namespace = package `major.minor`.** Patch releases append into the same
  namespace (0.10.1 and 0.10.7 both write `0.10.NNN`).
- **Ordinal is three digits, local to the namespace.** `0.11.001` and `0.12.001`
  are distinct; order is the numeric tuple `(major, minor, ordinal)`, never a
  string sort (`0.9` vs `0.10` would invert).
- **The recorded `schema_migrations.version` is the file stem** — `0.10.001_initial`.
  Renaming a shipped file is therefore a schema break, which is the point:
  identity is immutable after release.
- **Flat, not a directory per release.** Git cannot hold an empty directory, so
  per-release dirs would force `.gitkeep` scaffolding at every minor bump for no
  gain. Nothing to scaffold means nothing to forget.

Layout, parsing, ordering, and the canonical version string live in exactly one
place: a `MigrationId` type in `migrations.rs`. Nothing else formats or parses an id.

## Build

**1. `migrations.rs` becomes a real runner.**

```rust
struct MigrationId { major: u32, minor: u32, ordinal: u32 }   // Ord by tuple
struct Migration { id: MigrationId, name: &'static str, sql: &'static str }
const MIGRATIONS: &[Migration] = &[ /* include_str! each file, in order */ ];
const ACTIVE: (u32, u32) = /* parsed from env!("CARGO_PKG_VERSION") */;
```

`apply(conn, &[Migration])` — takes the slice, so tests drive synthetic sets
without any factory or trait — does, inside the existing `BEGIN EXCLUSIVE`:

1. create `schema_migrations` if absent;
2. **adopt the legacy stamp**: if applied rows are exactly `["001_initial"]`,
   rewrite that row to `0.10.001_initial`. Same file, same bytes, same schema —
   an in-place rename of the identity, no data touched. This is the "carry
   existing databases forward" requirement, and it is a code step rather than a
   SQL migration because it edits bookkeeping, not product schema;
3. apply every migration whose id is not yet in `schema_migrations`, in id order,
   stamping each;
4. an applied id the binary does not know → *"database was written by a newer
   Loopflow; upgrade lf"* (today this misreports as "delete loopflow.db");
5. `validate_baseline` generalises: build the expected schema by applying the full
   migration set to a fresh in-memory db and compare product tables/columns, so a
   db that drifted from *the chain* (not just the baseline) still gets the recreate
   message.

`latest_version_sqlite` returns the highest applied id — a release-scoped string.

**2. Set validation** (`validate_set`, pure): strictly increasing ids, no
duplicates, no id ahead of the active `major.minor`, ordinal gaps allowed but a
repeat rejected. Called from a unit test over `MIGRATIONS` and reused by the
verify script's Rust-side counterpart. Malformed sets are a programmer error, so
the test is the enforcement, not a runtime cost on every store open.

**3. `scripts/check_migrations.py`** — release/CI verification. Fails when:

- a filename does not parse, or ids collide, or ordering regresses;
- any migration sits in a namespace **ahead of** the version in the root
  `Cargo.toml` (wrong namespace);
- a migration that existed at the last release tag (`git describe --tags`) is
  edited, renamed, or deleted — compared byte-for-byte against
  `git show <last_tag>:<path>`. This is the immutability gate, and it needs no
  checksum manifest, which would only be a file people regenerate on autopilot;
- `Cargo.toml` and `pyproject.toml` versions disagree (the namespace has to come
  from one number).

"A schema change with no forward migration" reduces to the same gate: schema
exists *only* inside migration files, so the only way to change it without a new
migration is to edit a shipped one — which the tag comparison already rejects. No
second check; a separate one would be theater.

Wired into `ci.yml` as its own fast job (alongside `scratch-clear`) and therefore
into the weekly release, which gates on the same verification.

**4. `scripts/new_migration.py <name>`** — reads the active namespace from
`Cargo.toml`, picks the next free ordinal, writes the empty `.sql`, and prints the
`include_str!` line to paste. This is the "namespace selection" half of the bump
integration; the bump script itself needs no change, because a minor bump starts a
new namespace implicitly and `check_migrations.py` proves it.

**5. Fixtures** (Rust tests in `migrations.rs`, synthetic sets via the slice):
fresh db; legacy `001_initial` db adopted then upgraded; two migrations in one
minor; a `0.10` → `0.11` boundary applying only the missing tail; re-open applying
nothing twice; unknown-future-id db rejected with the upgrade message.

**6. Docs** — `rust/loopflow/src/store/MIGRATIONS.md`, next to the SQL, stating the
convention and the one rule that matters: *never edit a shipped migration; add a
forward one.*

## Assumptions

- Baseline lands in `0.10` because every shipped database today came from a 0.10.x
  binary, so `0.10.001_initial` is a true statement about those databases.
- `validate_run_events_schema` and `migrate_plaintext_provider_tokens` in
  `sqlite.rs` stay as they are; folding them into the chain is a separate task.
