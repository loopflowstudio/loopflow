# W2-131 — Wave Chat consumes the shared roadmap

## Intent

Make the empty/default Wave Chat pane the machine-wide roadmap. The Mac reads
the `RoadmapSnapshot` shipped by W2-144 through `RegistryQuery.roadmap()`; it
does not aggregate `lf status`, derive its own sections, or introduce another
work/status DTO.

## Shape

- `RoadmapView` renders `RoadmapSnapshot.waves` as Wave → Project → Task.
  Project and Task section labels come from the wire unchanged.
- A repo rail selection filters the one machine-wide snapshot locally. The
  query remains one `lf roadmap --json` read.
- `WorkEvidence.unavailable` renders its per-Wave reason. A failed refresh
  keeps the last successful snapshot visible and adds the query error; it never
  replaces known work with an empty state.
- Wave controls open an already-live Wave Chat or start the Wave through the
  existing launcher before opening it.
- Task controls are selected only from the shared runtime evidence:
  unstarted → `lf task run`, live → attach / interrupt, dormant non-terminal →
  `lf task resume`, terminal → no mutating action. Workspace and PR links use
  the references already carried by the roadmap DTO.
- Task attach reuses the existing Task workspace sheet and embeds
  `lf task attach`; file/diff/shell behavior stays on the existing
  `lf task changes|diff|file` paths.

## Done when

- With no Wave selected, the Mac shows all registered Waves and their durable
  Projects/Tasks even when no Wave process is running.
- A Wave whose plan is unreadable remains visible with the exact evidence
  reason, and a later whole-query failure leaves the previous roadmap visible.
- Start, attach, interrupt, resume, open-worktree, and open-chat actions route
  through existing lifecycle commands/handles.
- Swift DTO/query tests, launcher command tests, package tests, the
  multiplatform boundary check, and the macOS build-for-testing pass.
