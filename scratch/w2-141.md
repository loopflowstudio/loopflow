# W2-141 — Unified Now + Available work views

Research and product design. Not an implementation task: the build lands as the
follow-on Tasks in §9, chiefly W2-131.

---

## 0. The finding that reframes the task

`lf status <wave> --json` **already returns the whole join**. Wave → Projects
(definition, KRs, Project Session runtime) → Tasks (PM item, Task Session
runtime, worktree, branch, PR, next-move owner) → plus `attention` and `runs`,
each wrapped in `Evidence` so "looked and found nothing" stays distinct from
"could not look" (`rust/loopflow/src/lf/commands/waves.rs:85-155`). The PM↔Session
join is already written, by id, at `waves.rs:643-646`.

So the question is **not** "what data do we need". It is: *what view do we build
over data we already have, and what is the smallest contract change that makes it
machine-wide and truthful?*

Only two things are missing:

1. **No machine-wide work read.** `lf ls` returns waves plus `active_tasks` /
   `active_projects` counts. Everything below the wave needs one `lf status <wave>`
   per wave.
2. **Liveness is silently broken**, so "Now" would lie. §2.

Everything else is a view.

## 1. Empirical shape of the real data (2026-07-14)

Measured, not assumed. Product wave: 7 Projects, 26 Tasks.

| PM `completed` | Session state | n | Meaning |
|---|---|---|---|
| open | *none* | **18** | Available. The bulk. |
| open | `running` | **1** | Genuinely Now. |
| open | `submitted` | 2 | In review. **No live process.** PRs #877, #878. |
| open | `failed` | 1 | Attention. W2-133. |
| done | `merged` | 1 | Clean completion. W2-130, PR #882. |
| done | *none* | **3** | **Ambiguous.** W2-87, W2-126, W2-114. |

Across both waves (`product`, `infrastructure`): 13 Projects, ~40 Tasks, and
**exactly two live tmux processes on the machine** (`lf-task-W2-141`,
`lf-task-W2-142`).

Three numbers drive the design:

- **1 of 26** rows is truly live. A Now-only view is nearly empty.
- **18 of 26** are available. A roadmap-only view buries the live row.
- **5 sessions claim an active process; 2 exist.** Ghosts outnumber reality.

That last one is not a rounding error. It is the product problem.

## 2. The truthfulness bug (dogfooded, confirmed)

`lf status product` reports the `product-performance` Project Session as
`status: "running", process_alive: false` — and does **not** raise it in
`attention`, though the documented rule 2 is exactly *"the Session's record claims
a live process the machine cannot find"* (`waves.rs:383-389`).

Root cause, confirmed:

```rust
// rust/loopflow/src/ops/util.rs:3
pub fn command_exists(name: &str) -> bool {
    Command::new(name).arg("--version") ...   // tmux only accepts -V
}
```

```
$ tmux --version
tmux: unknown option -- -
exit=1
$ tmux -V
tmux 3.6a          # exit=0
```

`Liveness::probe(command_exists("tmux"))` therefore always yields
`Liveness::Unknowable` (`waves.rs:361-381`), and `is_gone()` short-circuits to
`false` **on every machine**. Attention rule 2 has never fired and cannot fire.

Meanwhile `process_alive` is *correct* — computed by `tmux_session_exists()`,
which uses `has-session` (`engine/process.rs:90-101`). Two liveness paths in one
snapshot disagree: one sees the process, the other believes tmux isn't installed.

Do **not** "fix" `command_exists` itself — its other five callers all probe `gh`,
which does accept `--version` (`ops/pr.rs:234`, `ops/release.rs:151…337`).

### 2.1 The near-miss already in the Swift tree

`RegistryQuery.backlog(wave:)` computes availability as `!completed` over
`lf pm show --json --no-sync` (`swift/Loopflow/Services/RegistryQuery.swift:105-113`).
`lf pm show` carries **no Session data**, so that is half a predicate. Its own
docstring names the missing half and pushes it onto the caller:

> *"Active runs remain a separate registry query; callers subtract running task
> ids/titles to render backlog."*

`backlog()` has **no production callers** — one test, nothing else. So this is not
a shipped bug; it is evidence, and it is the thesis in miniature:

*Availability is not a PM property.* It is the **absence of a Session**. Compute
it from the planning store alone and you must reconcile against runs afterward —
*by title matching*, per that docstring — which is exactly the join that rots.
§8 makes the predicate `!completed && runtime == None` and sources both halves
from one read, where the join is already done by id in Rust.

Delete `backlog()` and `BacklogItem` when `lf work` lands.

## 3. Comparative research

Sources are primary (vendor docs, changelogs, source). Where a UI detail is
undocumented it is marked *unverified* rather than guessed — that turned out to
cover a lot of the prior art, and the absences are themselves a finding.

### 3.1 The status-category pattern — three products converged independently

The strongest signal in the whole survey. **Split the status *name* from the
status *category*.** Teams get unlimited names; the machine reasons only over a
fixed, ordered category set.

| Product | Categories |
|---|---|
| Linear | Backlog, Unstarted, Started, Completed, Canceled ([docs](https://linear.app/docs/configuring-workflows)) |
| Jira | To Do, In Progress, Done — *"this can't be customized"* ([docs](https://support.atlassian.com/jira-cloud-administration/docs/what-is-a-workflow-status/)) |
| Shortcut | Backlog, Unstarted, Started, Done ([docs](https://help.shortcut.com/hc/en-us/articles/205268889)) |

Linear's rule: *"Teams can reorder statuses within each status category, but the
categories themselves stay in a fixed order."* Everything downstream — the Active
view, cycle rollover, auto-add, rollups — keys off the **category**, never the
name. GitHub Projects is the counter-example: its Status is a bare single-select
with **no category abstraction**, so a renamed column silently breaks every
downstream assumption and two projects holding the same issue hold two
independent Status values.

*Applies directly:* Loopflow's `TaskSessionStatus` has nine names and no
category. Three surfaces (CLI, Mac, iOS) would each re-implement the same 9-arm
match. §8.1 puts the category on the wire.

### 3.2 "Active" is not "in flight" — Linear

Linear's team-level split is **All Issues / Active / Backlog**, and *an "active"
status is one in the **Unstarted or Started** categories* ([custom views](https://linear.app/docs/custom-views)).
So Active = Todo **+** In Progress **+** In Review. **The eligible pool and the
running pool live in the same view**, deliberately — because "what should I pick
up" and "what's already moving" are asked in the same breath.

This is a direct argument against a hard Now|Available split screen, and it
killed my first concept (§6, Concept A).

Promotion between the pools is a keystroke, not a form: **⌘⇧A** → Active,
**⌘⇧B** → Backlog. Eligibility changes must be as cheap as reading.

Linear also **infers the plan from the execution**: cycles can *"auto-add any
Started or Completed issues that do not have a cycle assigned into the current
cycle."* If someone started it, it is this cycle's work; arguing otherwise is
theater.

### 3.3 Status should be attention-shaped, not execution-shaped

The clearest fork in the agent products.

| Product | Vocabulary |
|---|---|
| **Cursor** | `running / finished / error / cancelled` ([SDK](https://cursor.com/docs/sdk/typescript)) |
| **Devin** | `working / blocked / waiting_for_user / waiting_for_approval / finished`, **with a reason on suspension** (`inactivity`, `usage_limit_exceeded`, …) ([v3 API](https://docs.devin.ai/api-reference/v3/sessions/post-organizations-sessions)) |
| **Copilot** | `queued, in progress, completed, failed, **idle waiting for user**, timed out, cancelled` ([changelog](https://github.blog/changelog/2026-03-05-discover-and-manage-agent-activity-with-new-session-filters/)) |
| **Linear AgentSession** | `pending, active, **awaitingInput**, error, complete, **stale**` ([docs](https://linear.app/developers/agent-interaction)) |
| **OpenCode** | `idle / busy / retry` — the whole vocabulary ([schema](https://github.com/sst/opencode/blob/dev/packages/schema/src/session-status-event.ts)) |

Cursor's model has **no "needs review" state at all** — review is a *place* you
navigate to, not a state that comes to you. Fine for one agent; hostile at eight.

Loopflow is already on the right side of this: `Waiting`, `Blocked`, `Submitted`
exist, and `next_move.owner` (`Human/Wave/Project/Task/Review/Ci/External`) is a
genuine attention axis. The design should key presentation on **`next_move.owner`,
not raw status**.

### 3.4 Linear's AgentSession derives state; it never trusts a stored field

The precise fix for §2's ghosts, already shipped by someone else:

> *"Session state is tracked automatically based on the last emitted activity."*
> *"If you receive a `created` event, you are expected to send an activity or
> update your external URL within 10 seconds to avoid the session being marked as
> **unresponsive**."*

The agent **never sets its own state**. It emits activity; the platform derives
the state, and silence past a threshold is itself a state (`stale`). Loopflow
does the opposite — the session process writes its status into SQLite, so when
the process dies the status is frozen at whatever it last claimed, forever. That
is precisely the ghost. **Derive liveness at read time; never trust the stored
status alone.** This is what W2-139 exists to do.

Also: *"Assigning an issue to an agent triggers delegation — the agent acts on
the issue, but the human teammate remains responsible for its completion."*
Delegated issues **still appear in My Issues**. Accountability does not transfer
to a process.

### 3.5 Claude Code's agent view — the closest existing thing to the target

*"One screen for all your background sessions: what's running, what needs your
input, and what's done."* Cross-project by default. ([docs](https://code.claude.com/docs/en/agent-view))

```
Pinned
  ✽ clawd walk cycle     Drawing the walk-cycle sprite frames        3m
Ready for review
  ∙ jump physics         Opened PR with collision fix         #2048  2h
Needs input
  ✻ power-up design      double jump or wall climb?                  1m
Working
  ✽ collision detection  Adding swept-AABB checks                    2m
Completed
  ✻ title screen         result: menu, options, credits done         9m
```

Two ideas worth taking whole:

**(a) Three orthogonal encodings in one row, no legend.**
- **color** = task state (`Working / Needs input / Idle / Completed / Failed / Stopped`)
- **shape** = *process liveness* (`✻`/`✽` alive · `∙` exited · `✢` sleeping between loop iterations)
- **link color** = PR state (yellow waiting on checks · green passed · purple merged · grey draft)

Three independent facts about one row, rendered on independent visual channels.
Loopflow's row carries exactly three analogous facts: PM completion, Session
status, and process liveness — plus the PR. Same shape.

**(b) "A dead process is not a dead task."** The `∙` glyph means *"the process
has exited. You can still peek, reply, or attach, and Claude restarts from where
it left off."* The row **outlives the process** — which is the only way a list
survives a laptop lid closing. Loopflow's ghosts are not an error state to be
cleaned up; they are `Stopped` rows that remain attachable and resumable.

Note what this view is **not**: it has no hierarchy. It is flat and grouped by
*attention*, not by project. That is a deliberate shape difference from a
roadmap, and §5.2 takes it seriously.

### 3.6 Obsidian — views are stored predicates; the store is the files

The vendor states the whole "no second database" thesis in one sentence
([Bases syntax](https://obsidian.md/help/bases/syntax)):

> **"By default a base includes every file in the vault. There is no `from` or
> `source` like in SQL or Dataview. The `filters` section lets you define
> conditions to narrow down the dataset."**

A `.base` file has five keys — `filters, formulas, properties, summaries, views`
— and **zero rows**. It holds only the *question*. Delete every `.base` and you
lose no data; delete the notes and the base renders nothing. That asymmetry *is*
the definition of derived. Writes land in the source note, so there is no
reconciliation problem — there is nothing to reconcile.

And the counter-case, which is the warning: **Dataview keeps a second index.** Its
maintainer, verbatim — *"Dataview essentially stores an in-memory cache of all of
the useful metadata in the vault"* — and in the same breath the cost: it *cannot*
search file contents, because that would mean scanning thousands of files. Large
vaults don't render until indexing completes ([#1064](https://github.com/blacksmithgu/obsidian-dataview/issues/1064)).
Bases avoided this by having no source clause — and the two fields that *do* need
a reverse index (`file.backlinks`, `file.properties`) carry a documented
*"Does not automatically refresh results when the vault is changed"* warning.
**A second index buys speed, constrains the query language, and then goes stale.**

### 3.7 The board metaphor is losing, empirically

The worktree-board category is consolidating hard:

| Tool | Status (Jul 2026) |
|---|---|
| **Conductor** | Alive, healthiest — and it is **not a board** |
| **Sculptor** | Alive, research preview |
| **Vibe Kanban** | **Sunsetting** — the only true kanban board ([post](https://www.vibekanban.com/blog/shutdown)) |
| **Crystal** | Deprecated |
| **Terragon** | Shut down |

Conductor — the survivor — landed on a **status-grouped sidebar**: *"Workspaces
are now organized by status: backlog, in progress, in review, and done"*
([0.35.0](https://www.conductor.build/changelog/0.35.0-workspace-status)). A list,
not lanes.

And Vibe Kanban's own docs contain the epitaph: *"You can manually drag tasks
between columns, but **this won't trigger any functionality**."* A board that is
not a control surface is a lie. **Loopflow should not build a kanban.**

### 3.8 Task vs attempt — and a constraint this exposes in Loopflow

Vibe Kanban's one genuinely good idea: a **task** (durable intent) is distinct
from an **attempt** (one agent run: profile + variant + base branch). One task,
many attempts. "Try this three ways" is trivial; Conductor conflates the two into
"workspace" and that is exactly where it gets awkward.

*Applies uncomfortably:* Loopflow has the right nouns — Task (Linear issue) vs
Task Session (one run) — but **`task_sessions.issue_id` is `UNIQUE`**
(`store/migrations/0.10.001_initial.sql:243-244`). **One Task can have exactly one
Session, ever.** A merged or abandoned Task can never be re-run, and a terminal
Session cannot be succeeded. That is not a view problem, but the view will make
it visible: the roadmap will show terminal rows with no legal action. It is the
same bootstrap deadlock the wave already hit on W2-140. Flag it there; do not
solve it here.

### 3.9 Conductor — the no-resident answer

> *"you can commit, rename branches, push to `origin`, open a PR, or merge from
> the Conductor UI **or the terminal**."* ([git-worktrees](https://www.conductor.build/docs/concepts/git-worktrees))

**An idle worktree is just a checkout.** The tool is a view over git, not a
wrapper around it. Archiving — deleting the directory — is the only destructive
act. This is exactly the posture for Loopflow's no-resident state: with every
process dead, the worktrees, branches, and PRs are all still there and still
work. Nothing about the roadmap depends on a process existing.

### 3.10 Other patterns worth taking

- **The resume list and the running list are the same list.** OpenCode's session
  dialog renders a live spinner in the gutter of any `busy`/`retry` session — one
  surface, one query, one glyph of difference ([source](https://github.com/sst/opencode/blob/dev/packages/tui/src/component/dialog-session-list.tsx)).
- **Make the artifact the progress bar.** GitHub didn't invent an agent-status
  widget; "in progress" literally means *there is a draft PR with commits landing
  in it*. Loopflow already has `pull_request` on the session and `lf task diff`.
- **Every artifact links back to the reasoning that made it.** Copilot puts a
  session-log URL in **every commit message**. Loopflow has `lf trace <run>` and
  the auditability project wants exactly this.
- **Reverse lookup from artifact to work.** Claude Code's session picker lets you
  **paste a PR URL** to find the session that created it. Loopflow stores
  `pr_number`/`pr_url` on the Task Session — this is nearly free.
- **Notify only when you're not looking.** OpenCode fires desktop notifications
  *only when the terminal is blurred*, with distinct sounds for `question`,
  `permission`, `error`, `done` ([tui docs](https://opencode.ai/docs/tui/#attention)).
- **Intake lives outside every view.** Linear excludes Triage issues from all
  views by default, so untriaged work cannot inflate your counts or your
  conscience ([triage](https://linear.app/docs/triage)).

### 3.11 Anti-patterns — the failure modes to design against

1. **Hiding work by inference, then hiding it again by filter.** OmniFocus stacks
   a *computed* availability model (Active ∧ ¬Blocked ∧ ¬Deferred ∧ project not
   On Hold) **and** a per-view Availability filter, with different semantics.
   Result: years of forum threads where deferred actions appear greyed in some
   views, vanish from others, and empty projects leak into "Available"
   ([1](https://discourse.omnigroup.com/t/deferred-actions-in-available-perspective/54599),
   [2](https://discourse.omnigroup.com/t/stop-empty-projects-from-appearing-in-my-available-perspective/6691)).
   **If you compute eligibility, show ineligible work greyed with the reason
   attached. One hiding mechanism, never two.**
2. **A denormalized read model presented as truth.** GitHub Projects' board is
   eventually consistent with its issues — with a documented **5-hour** tail
   during the March 2026 incident ([thread](https://github.com/orgs/community/discussions/188489)).
   Loopflow's PM snapshot **is** a denormalized read model of Linear. It must
   always show its `synced_at`.
3. **Completion signalled by side-effect, not by word.** In Codex web, "done" is
   inferred from *diff stats appearing* on the row; a task with no diff is
   indistinguishable-by-badge from one still thinking.
4. **An eligible pool with no dependency model.** Things 3 has no blocking
   computation, so a 20-step project dumps 20 items into "Anytime." The pool
   becomes noise. *Loopflow's 18 available items are already most of the list.*
5. **A deferral bucket with no review cadence.** Things' Someday removes items
   from every eligible view and offers nothing to bring them back.
   Someday-as-graveyard isn't user error; it's the designed exit.
6. **Backlog bloat is terminal, and it arrives as an error message.** Jira ships
   the literal string **"Your board has too many issues"** and an Atlassian KB
   article titled *"Backlog is slow to load."* The conceptual failure precedes
   the technical one, but the technical one arrives.
7. **Fully autonomous eligibility management is unproven.** Height's AI pruned
   stale backlog items and triaged without prompting — the boldest version of
   this idea shipped — and the company **shut down 24 Sep 2025**. Not causal
   evidence, but the only natural experiment available. It argues for machine
   *suggestion* over machine *decision*.
8. **The prior art's entity models drift fast.** Cursor 3 *removed* cloud agents
   from the editor and deprecated its worktree/best-of-n UI; Claude Code's
   `/bashes` is gone; Copilot's "coding agent" is now "cloud agent". Any design
   citing the 2025 shape of these products is citing a dead model.

### 3.12 The dissent worth holding open

Basecamp deletes the concept entirely ([Shape Up ch. 7](https://basecamp.com/shapeup/2.1-chapter-07)):

> **"Backlogs are a big weight we don't need to carry.** Dozens and eventually
> hundreds of tasks pile up that we all know we'll never have time for… The time
> spent constantly reviewing, grooming and organizing old ideas prevents everyone
> from moving forward on the timely projects that really matter right now."
> *"Really important ideas will come back to you."*

Loopflow's own `loop/README` once said "no backlog", and the wave resolved that
in Linear's favor — with the explicit note that what it bought ("the open runs
ARE the wave's open tasks") is now gone. **18 of 26 product tasks are available
and unstarted.** That is not yet Jira, but it is the direction of travel, and this
design makes the pile *more* visible, not less. Linear's own answer is decay, not
discipline — auto-close and auto-archive on staleness. Worth a future decision;
out of scope here.

## 4. Information architecture

### 4.1 The row carries two truths, never one

**PM completion and Session runtime are orthogonal axes. Never collapse them into
one status word.** (This is the task statement's own demand, and §3.1's category
pattern is how to make it machine-readable.)

Every work row renders a pair, plus liveness:

```
plan:     open | done                    (Linear `completed`)
session:  none | created | starting | running | waiting | blocked
        | submitted | failed | merged | abandoned
liveness: alive | exited | unknowable    (derived, never stored — §3.4)
```

The cross product lands in six cells in the real data, and three are only legible
as a pair:

| plan × session | Row language | Real rows |
|---|---|---|
| open × none | **Available** | 18 |
| open × running (alive) | **Working** · elapsed · provider | 1 |
| open × running (exited) | **Stopped** · record says running | 3 today |
| open × submitted | **Ready for review** · PR #877 | 2 |
| open × failed | **Failed** · reason | 1 |
| open × waiting/blocked | **Needs input** | 0 today |
| done × merged | **Done** · PR #882 | 1 |
| done × none | **Closed outside Loopflow** | 3 |
| open × merged | **Merged — not closed in Linear** | 0 (nudge) |

`done × none` (W2-87, W2-126, W2-114) is the ambiguous combination the Task names.
It is neither an error nor a contradiction: it is work completed by a human, or
superseded, that never ran a Session. The view says exactly that. It must never
render identically to a merged Session — the provenance differs, and hiding that
is how a ledger starts lying.

Per §3.11.1: an ineligible row is **greyed with its reason attached**, never
hidden twice.

### 4.2 One query. Two shapes.

There is exactly **one tree** — `Wave → Project → Task` — sourced from the PM
snapshot, complete, and renderable with **zero processes running**. Session state
is an *overlay*, never a parallel list.

But the research is clear that a lens must be allowed to change the **shape**,
not merely filter the tree (§3.5). Claude Code's Now surface is *flat and grouped
by attention*; a roadmap is *hierarchical and grouped by bet*. Forcing both into
one outline serves neither.

- **Now** — **flat**, cross-wave, grouped by attention:
  `Ready for review → Needs input → Working → Stopped → Failed`.
  Ordered by age within each group. This is `attention` (`waves.rs:392-446`) plus
  the live rows. Rows carry wave/project as *context*, not as structure.
- **Available** — **flat or grouped by project**, `!completed && runtime == None`,
  ordered by PM `rank`.
- **Roadmap** — **the tree**. Everything, including completed. This is where KRs
  live and where a Project's bet is legible.

Same query, three projections. Per §3.6, the lenses hold only the *question*;
the store holds the answer.

### 4.3 Attention is a sort, not a fourth view

`attention` already computes who is waiting on whom, with an owner and an age.
It is not a separate surface — it is the **grouping of the Now lens** and the
**badge on a collapsed Wave row**. Present it via `next_move.owner`, not raw
status (§3.3).

## 5. Three view concepts

Evaluated against the real 2-wave / 13-project / 40-task / 2-live-process data.

### Concept A — Split screen: Now over Available

Two stacked sections; roadmap on a third tab.

*Against real data:* the Now section has **one row** and reads as broken. The
Available section is 18 rows with no project context, so the `wave-chat` and
`loopflow-api` bets are invisible — you cannot tell which KR a task serves. And
because the two sections come from different predicates, `submitted` (not live,
not available) belongs to neither and **vanishes**.

*Against the research:* Linear deliberately merged these pools — Active =
Unstarted + Started (§3.2). The split is the Jira ancestor, but it is a
*within-team* split; promoted to all-Wave it loses the tree and strands the
middle states.

**Rejected.**

### Concept B — Attention inbox

Primary surface is `attention`, newest-waiting first. Roadmap behind a key.

*Against real data:* 4 rows — two PRs awaiting review, one failed task, one
boundary-violating project. An excellent *morning* surface; it is what a human
actually does next. But the full all-Wave roadmap is not legible from it, 18
available items are invisible, and it **degrades to empty when everything is
healthy** — precisely the moment you want to pick up new work.

**Rejected as the primary surface; adopted as the shape of the Now lens** (§3.5
shows Claude Code arriving at exactly this grouping).

### Concept C — One store, two shapes (recommended)

One durable `Wave → Project → Task` tree from the PM snapshot. Now is a flat,
attention-grouped projection; Roadmap is the tree; Available is the tree's
unstarted rows by rank. Every row carries plan × session × liveness (§4.1).

*Against real data:* the tree is 13 project rows; each Project collapses to
`wave-chat · 0/6 KRs · 1 working · 2 in review · 1 available`, so 40 tasks
compress to 13 lines until opened. The one working task is found by the Now lens
*or* by its loud overlay in the tree. `done × none` renders honestly. Kill every
process and the tree is identical minus the chips.

**Recommended.** It is the only concept where *"useful with no Wave process
running"* is a structural property rather than an empty-state special case — and
the only one that satisfies both halves of the task (live operational context
**and** the full filed roadmap) without a second model.

## 6. Recommended design

### 6.1 Now — flat, attention-grouped, cross-wave

```
NOW                                        2 alive · 4 need you
──────────────────────────────────────────────────────────────
Ready for review
  ∙ W2-129  Make Wave Chat human-first        #878  product   2h
  ∙ W2-132  Measure slow token streaming      #877  product   1h
Working
  ✽ W2-141  Research Now + Available views    claude · loopflow.w2-141   2h
  ✽ W2-142  Recover the v0.11.0 release       codex  · loopflow.w2-142   2h
Stopped        (record says running — process is gone)
  ∙ product-performance   Project Session · since 19:23
  ∙ technical-architecture Project Session · since 19:20
Failed
  ∙ W2-133  lf status audit snapshot   provider turn failed    product   1h
```

Shape = liveness (`✽` alive, `∙` exited), exactly as §3.5. **A stopped row is not
an error** — it is attachable and resumable, and it says why it is stopped.

### 6.2 Roadmap — the tree, always available

```
▾ product                                       idle · no resident
  ▾ wave-chat          0/6 KRs   ✽1 working · ∙2 review · ○1 available
      W2-141  Research unified Now + Available   ✽ working  2h
      W2-131  Show the all-wave roadmap          ○ available
      W2-129  Make Wave Chat human-first         ∙ review  #878
      W2-87   Native chat UX                     ✓ closed outside Loopflow
  ▸ loopflow-api       0/5 KRs   ⚠ abandoned · ○8 available
  ▸ mac-surface-ux     0/5 KRs   ○5 available
▸ infrastructure                                idle · no resident
                                        synced 2h ago from Linear
```

Density follows Linear's list rows: one line per task — identifier, title, one
status chip. A second line appears **only for live rows** (provider + worktree).
Projects collapse to KR proof + a session census. Waves collapse to residency +
an attention count. `synced_at` is always on screen (§3.11.2).

### 6.3 The verbs — all of which already exist

| Journey | Offered on | Existing command |
|---|---|---|
| browse | the tree | `lf ls`, `lf status <wave>` |
| filter | Now / Available / Roadmap | client-side over one read |
| **launch** ("spin this up") | rows where `session == none` | `lf task run <id>` |
| **attach** | any row with a Session | `lf task attach <id>` |
| **steer** | a live row | `lf task steer` / `follow-up` / `interrupt` |
| **review** | a `submitted` row | `lf task diff <id>`, PR url |
| **worktree jump** | any row with a Session | `runtime.worktree` → open |
| resume | a stopped / failed row | `lf task resume <id>` |
| abandon | any non-terminal row | `lf task abandon <id>` |

**Zero new verbs.** And note the identity: launch is offered exactly where
`session == none`, which is the same predicate that defines Available. *Launch
and availability are the same fact.*

Per §3.8, a terminal Session (`merged`/`abandoned`) currently has **no legal
action** — `issue_id` is UNIQUE, so it cannot be re-run. The view must grey those
rows with that reason rather than offering a button that will fail.

### 6.4 No-resident behavior

The tree comes from the PM snapshot in SQLite — a cache that is **always
present**, written by every PM mutation and by `lf pm sync`. Therefore:

- **No wave server running** → tree renders in full; only the chips are absent.
  Per §3.9, an idle worktree is just a checkout: branches, PRs and `lf task diff`
  all still work.
- **Linear unreachable** → tree renders from cache with `synced 6h ago`.
  **Never an empty roadmap.**
- **Store unreadable** → `Evidence::Unavailable { reason }`. The view says *why*;
  it does not show zero rows. The wrapper already exists (`waves.rs:101-127`), and
  W2-131 makes the same demand: *"Never turn sync, auth, or store failure into a
  false empty roadmap."*

The empty state that matters is not "no data" — it is **"no data *yet*" vs "could
not look"**, and those must never render the same. (Nobody in the prior art
documents their empty state; §3.11 found it *unverified* across Cursor, Devin,
Copilot and Codex. Uncontested ground.)

## 7. What this design refuses

- **No kanban board.** The board metaphor is losing empirically (§3.7), and a
  board that isn't a control surface is a lie.
- **No second store.** Lenses are predicates, not tables (§3.6).
- **No autonomous backlog pruning.** Height bet the company on it and died
  (§3.11.7). Machine *suggestion*, human *decision*.
- **No new status vocabulary.** Reuse `TaskSessionStatus` + `next_move.owner`;
  add only the derived category (§8.1) and the derived liveness.

## 8. The minimal data contract

**No second database. No new planning model. One new read command, one derived
field.**

### 8.1 Rust / CLI

```
lf work --json [--wave <name>] [--lens now|available|all]
```

A thin envelope over the **existing** per-wave snapshot — reusing
`ProjectDetailSnapshot` / `TaskDetailSnapshot` / `AttentionItem` verbatim:

```rust
pub struct WorkSnapshot {
    pub waves: Vec<WaveWorkSnapshot>,
    pub liveness: Liveness,          // Observable | Unknowable — must be on the wire
}

pub struct WaveWorkSnapshot {
    pub wave: WaveSnapshot,                       // existing
    pub projects: Vec<ProjectDetailSnapshot>,     // existing, unchanged
    pub attention: Evidence<Vec<AttentionItem>>,  // existing
    pub synced_at: i64,                           // PM staleness — always rendered
}
```

Implementation is `snapshot_projects()` looped over `store.list_waves(None)`, with
**one** batched `tmux list-sessions` for the whole call rather than `has-session`
per Session — the wave's own performance rule, and what W2-139 already specifies.

**The one genuinely new field — a status category** (§3.1). Derive it in Rust so
three surfaces don't each write the same 9-arm match:

```rust
pub enum WorkCategory {   // on TaskDetailSnapshot, derived, never stored
    Available,     // !completed && no session
    Working,       // session active && process alive
    Stopped,       // session claims active && process gone   <- the ghost, named
    NeedsInput,    // waiting | blocked  (next_move.owner == Human)
    InReview,      // submitted
    Failed,
    Done,          // completed && merged
    ClosedOutside, // completed && no session   <- the ambiguous cell, named
}
```

`liveness` must be on the wire: a client that cannot distinguish *"process gone"*
from *"cannot tell"* will invent a finding — which is exactly the bug in §2.

### 8.2 Swift

`RegistryQuery.work()` → `lf work --json` → `WorkSnapshot`. It **replaces** the
current N-subprocess fan-out (`WavesView.buildWavePlanCache` spawns one
`lf pm show` per wave, `WavesView.swift:584-620`) with a single spawn — so this is
a performance *win*, not a new cost.

`WaveProjectWork` / `WaveTaskWork` (`swift/Loopflow/Models/WaveWorkMap.swift:13-40`)
already mirror the per-wave shape, and `runtime` is already `Optional` — the
Available predicate decodes today. The new type is one array wrapper above them.

### 8.3 Explicitly not adding

- **No `now`/`available` field on the wire.** They are client-side predicates
  over `runtime == None`. Persisting a lens is how you grow a second planning
  model that drifts from Linear (§3.6).
- **No PR polling.** `pull_request` on the Task Session is the only PR truth and
  is already there. (`lf pr` has no `--json`; the view does not need it.)
- **No worktree scan.** `runtime.worktree` is authoritative; `lf wt list` is a
  different, repo-scoped concern.
