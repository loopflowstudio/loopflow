# W2-141 — Unified Now + Available work views

Research and product design. Not an implementation task: the build lands as the
follow-on Tasks in §8, chiefly W2-131.

---

## 0. The finding that reframes the task

`lf status <wave> --json` **already returns the whole join**. Wave → Projects
(definition, KRs, Project Session runtime) → Tasks (PM item, Task Session
runtime, worktree, branch, PR, next-move owner) → plus `attention` and `runs`,
each wrapped in `Evidence` so "looked and found nothing" stays distinct from
"could not look" (`rust/loopflow/src/lf/commands/waves.rs:85-155`).

So the question is **not** "what data do we need". It is: *what view do we build
over data we already have, and what is the smallest contract change that makes it
machine-wide and truthful?*

Two things are missing, and only two:

1. **No machine-wide work read.** `lf ls` returns waves plus `active_tasks` /
   `active_projects` counts. Everything below the wave requires one
   `lf status <wave>` per wave. There is no all-Wave query.
2. **Liveness is silently broken**, so "Now" would lie. See §2.

Everything else in the deliverable is a view over `lf status`.

## 1. Empirical shape of the real data (2026-07-14)

Measured, not assumed. Product wave: 7 Projects, 26 Tasks.

| PM `completed` | Session state | n | What it means |
|---|---|---|---|
| open | *none* | **18** | Available work. The bulk. |
| open | `running` | **1** | Genuinely Now. |
| open | `submitted` | 2 | In review. **No live process.** PRs #877, #878. |
| open | `failed` | 1 | Attention. W2-133. |
| done | `merged` | 1 | Clean completion. W2-130, PR #882. |
| done | *none* | **3** | **Ambiguous.** W2-87, W2-126, W2-114. |

Across both waves (`product`, `infrastructure`): 13 Projects, ~40 Tasks, and
**exactly two live tmux processes on the machine** (`lf-task-W2-141`,
`lf-task-W2-142`).

Three numbers drive the whole design:

- **1 of 26** rows is truly live. A Now-only view is nearly empty.
- **18 of 26** are available. A roadmap-only view buries the live row.
- **5 sessions claim an active process; 2 exist.** Ghosts outnumber reality.

That last one is not a rounding error. It is the product problem.

## 2. The truthfulness bug (dogfooded, confirmed, one line)

`lf status product` reports the `product-performance` Project Session as
`status: "running", process_alive: false` — and does **not** raise it in
`attention`, even though the documented rule 2 is exactly *"the Session's record
claims a live process the machine cannot find"* (`waves.rs:383-389`).

Root cause, confirmed:

```rust
// rust/loopflow/src/ops/util.rs:3
pub fn command_exists(name: &str) -> bool {
    Command::new(name).arg("--version") ...   // tmux only accepts -V
}
```

```
$ tmux --version
tmux: unknown option -- -
exit=1
```

`Liveness::probe(command_exists("tmux"))` therefore always yields
`Liveness::Unknowable` (`waves.rs:361-381`), and `is_gone()` short-circuits to
`false` on every machine. **Attention rule 2 has never fired and cannot fire.**

Meanwhile `process_alive` itself is *correct* — it is computed by
`tmux_session_exists()`, which uses `has-session` and works fine
(`engine/process.rs:90-101`). So the two liveness paths in the same snapshot
disagree: one can see the process, the other believes tmux does not exist.

Consequence for this design: **a Now view built naively on today's `lf status`
renders three ghost "running" rows.** Truthful liveness is a hard prerequisite,
not a nice-to-have. It is the upstream cause W2-139 already names ("A dead
Session still reads Running... it is the status field that every launch gate then
trusts"). The one-line fix (`--version` → `-V`) is filed separately in §8 as
W2-14x-A because it is independently shippable today and W2-139 is larger.

## 4. Information architecture

### 4.1 The row carries two truths, never one

The single most important rule, and the one the task statement asks for
explicitly: **PM completion and Session runtime are orthogonal axes. Never
collapse them into one status word.**

Every work row renders a pair:

```
plan:    open | done                    (Linear `completed`)
session: none | created | starting | running | waiting | blocked
       | submitted | failed | merged | abandoned      (Task Session status)
```

The cross product is not decorative — the real data lands in six of its cells
(§1), and three of them are only legible as a pair:

| plan × session | Language on the row | Real rows |
|---|---|---|
| open × none | **Available** | 18 |
| open × running | **Running** (+ elapsed, provider) | 1 |
| open × submitted | **In review** · PR #877 | 2 |
| open × failed | **Failed** · reason | 1 |
| done × merged | **Done** · PR #882 | 1 |
| done × none | **Closed outside Loopflow** | 3 |
| open × merged | **Merged — not closed in Linear** | 0 (would nudge) |
| *claims running, no process* | **Stopped** · record says running | 3 today (§2) |

`done × none` (W2-87, W2-126, W2-114) is the ambiguous combination the Task
statement names. It is not an error and not a contradiction: it is a task
completed by a human, or superseded, without ever running a Session. The view
says so in those words. It must never render as "Done ✓" identically to a merged
Session — the provenance differs, and hiding that is how the ledger starts
lying.

### 4.2 One hierarchy, three lenses

There is exactly **one tree**: `Wave → Project → Task`, sourced from the PM
snapshot, complete, and renderable with **zero processes running**. Session state
is an *overlay* on the tree's rows, never a parallel list.

- **Now** — a lens: rows where a Session exists and is non-terminal.
- **Available** — a lens: rows where `!completed && session == none`, ordered by
  `rank`.
- **Roadmap** — no lens: the whole tree, including completed.

Lenses are filters over one query result, not three queries against three
models. This is the property that makes the no-resident case fall out for free:
turn every process off and the tree is unchanged; only the overlay is empty.

### 4.3 Attention is a sort, not a fourth view

`attention` already computes "what is waiting on somebody" with an `owner` and an
age (`waves.rs:392-446`). It is not a separate surface — it is the **default
ordering** of the Now lens, and the source of the badge on a collapsed Wave row.

## 5. Three view concepts

Each evaluated against the real 2-wave / 13-project / 40-task / 2-live-process
data, not a hypothetical.

### Concept A — Split screen: Now over Available

Two stacked sections on one all-Wave screen. Top: every live Session. Bottom:
every unstarted item by rank. Roadmap is a third tab.

*Against real data:* the Now section has **one row**. It reads as broken. The
Available section is 18 rows with no project context, so `wave-chat` KRs and
`loopflow-api` KRs are invisible — you cannot tell which bet a task serves. And
because the two sections are built from different predicates, `submitted` (no
process, but not available either) belongs to neither and vanishes.

*Verdict:* rejected. The split is the ancestor pattern (Jira board vs backlog;
Linear's Active/Backlog tabs) but it is a *within-project* split. Promoted to the
all-Wave level it loses the tree and strands the middle states.

### Concept B — Attention inbox

Primary surface is `attention`: everything whose next move is owned by someone
other than itself, newest-waiting first. Roadmap behind a key.

*Against real data:* 4 rows — two PRs awaiting review, one failed task, one
boundary-violating project. That is a genuinely excellent *morning* surface and
it is exactly what a human does next. But it does not satisfy the Task's core
ask: the full all-Wave roadmap is not legible from it, and 18 available items are
invisible. It also degrades to empty when everything is healthy — which is the
moment you most want to pick up new work.

*Verdict:* rejected as the primary surface; **adopted as the default sort of the
Now lens** and as the Wave-row badge.

### Concept C — One tree, live overlay (recommended)

The durable `Wave → Project → Task` tree is always the surface. Every row shows
the plan/session pair from §4.1. Now / Available / Roadmap are saved filters over
it. Attention orders it.

*Against real data:* the tree is 13 project rows; Projects collapse to a
one-line summary (`wave-chat · 0/6 KRs · 1 running, 2 in review, 1 available`),
so 40 tasks compress to 13 lines until you open one. The single running task is
found by the Now filter *or* by its loud overlay chip in the tree — both work.
`done × none` renders honestly. With every process dead, the tree is identical
minus the chips.

*Verdict:* **recommended.** It is the only one of the three where "useful with no
Wave process running" is a structural property rather than an empty-state
special case.

## 6. Recommended design

### 6.1 The surface

```
WAVES                        product · infrastructure · [all]
─────────────────────────────────────────────────────────────
  Now (1)   Available (18)   Roadmap (40)        ⚠ 4 need you
─────────────────────────────────────────────────────────────
▾ product                                    idle · no resident
  ▾ wave-chat            0/6 KRs   ● 1 running  ◐ 2 review
      W2-141  Research unified Now + Available    ● running 2h
                                    claude · loopflow.w2-141
      W2-131  Show the all-wave roadmap          ○ available
      W2-129  Make Wave Chat human-first         ◐ in review #878
      W2-87   Native chat UX                     ✓ closed outside
  ▸ product-performance   0/3 KRs   ⚠ stopped (record says running)
  ▸ loopflow-api          0/5 KRs   ⚠ abandoned · 8 available
  ▸ mac-surface-ux        0/5 KRs   ○ 5 available
▸ infrastructure                             idle · no resident
```

Density rules, taken from Linear's list rows: one line per task; identifier,
title, and one status chip; the second line appears only for live rows and
carries provider + worktree. A Project collapses to KR proof plus a session
census. A Wave collapses to residency plus an attention count.

### 6.2 The verbs — all of which already exist

Every action the Task asks for is an existing `lf` verb. The view is a launcher
over the CLI, not a new runtime.

| Journey | Affordance | Existing command |
|---|---|---|
| browse | the tree | `lf ls`, `lf status <wave>` |
| filter | Now / Available / Roadmap lens | client-side over one read |
| **launch** ("spin this up") | on an `available` row | `lf task run <id>` |
| **attach** | on a `running` row | `lf task attach <id>` |
| **steer** | on a `running` row | `lf task steer` / `follow-up` / `interrupt` |
| **review** | on a `submitted` row | `lf task diff <id>`, PR url |
| **worktree jump** | on any row with a Session | `runtime.worktree` → open |
| resume | on a stopped/failed row | `lf task resume <id>` |
| abandon | on any live row | `lf task abandon <id>` |

Two consequences worth stating plainly: **zero new verbs**, and **the launch
affordance is only ever offered on rows where `session == none`** — which is the
same predicate that defines Available. Launch and availability are the same fact.

### 6.3 No-resident behavior

The tree comes from the PM snapshot in SQLite, which is a *cache that is always
present*. It is written by every PM mutation and by `lf pm sync`. Therefore:

- No wave server running → tree renders in full. Only chips are absent.
- Linear unreachable → tree renders from the cached snapshot, with a
  "synced 6h ago" staleness marker. **Never an empty roadmap.**
- Store unreadable → `Evidence::Unavailable { reason }` — the view says *why*, it
  does not show zero rows. The `Evidence` wrapper already exists for exactly this
  (`waves.rs:101-127`) and W2-131's description makes the same demand: "Never
  turn sync, auth, or store failure into a false empty roadmap."

The empty state that matters is not "no data". It is "no data *yet*" vs "could
not look" — and those must never render the same.

## 7. The minimal data contract

**No second database. No new planning model. One new read command.**

### 7.1 Rust / CLI

The gap from §0 is machine-wide scope. Add one command that is `lf status` fanned
across the registry:

```
lf work --json [--wave <name>] [--lens now|available|all]
```

returning a new wire DTO that is a thin envelope over the *existing* per-wave
snapshot — reusing `ProjectDetailSnapshot` / `TaskDetailSnapshot` / `AttentionItem`
verbatim, not re-modelling them:

```rust
pub struct WorkSnapshot {
    pub waves: Vec<WaveWorkSnapshot>,   // one per registered wave
    pub liveness: Liveness,             // Observable | Unknowable — see §2
}

pub struct WaveWorkSnapshot {
    pub wave: WaveSnapshot,             // existing
    pub projects: Vec<ProjectDetailSnapshot>,  // existing, unchanged
    pub attention: Evidence<Vec<AttentionItem>>, // existing
    pub synced_at: i64,                 // PM snapshot staleness
}
```

Implementation is `snapshot_projects()` in a loop over `store.list_waves(None)`,
with **one** batched `tmux list-sessions` for the whole call rather than
`has-session` per Session — the wave's own performance rule, and what W2-139
already specifies.

`liveness` must be on the wire. A client that cannot distinguish "process gone"
from "cannot tell" will invent a finding, which is precisely the bug in §2.

### 7.2 Swift

`RegistryQuery.work()` → `lf work --json` → `WorkSnapshot`. It replaces the
current N-subprocess fan-out (`WavesView.buildWavePlanCache` spawns one `lf pm
show` per wave, `WavesView.swift:584-620`) with a single spawn — so this is a
performance *win*, not a new cost.

`WaveWorkMap` and friends (`swift/Loopflow/Models/WaveWorkMap.swift`) already
mirror the per-wave shape. The new type is one array wrapper above them.

### 7.3 What we are explicitly not adding

- No `Now`/`Available` field on the wire. They are **client-side predicates over
  `runtime == None`**. Persisting a lens is how you get a second planning model
  that drifts from Linear.
- No PR polling. `pull_request` on the Task Session is the only PR truth, and it
  is already there. (`lf pr` has no `--json` today; the view does not need it.)
- No worktree scan. `runtime.worktree` is authoritative; `lf wt list` is a
  different, repo-scoped concern.

## 8. Sequenced follow-on tasks

Ordered by dependency. Each is independently shippable.

1. **Fix the liveness probe** (one line, ship today).
   `command_exists("tmux")` → `tmux -V`, or replace with a batched
   `tmux list-sessions`. Without it, attention rule 2 is dead code and every Now
   view shows ghosts. *Small; unblocks everything below.*

2. **W2-139 — Session reads tell the truth** (already filed).
   Batched liveness probe; terminal Sessions render as terminal rather than being
   filtered out of view. The Now lens is only as honest as this.

3. **`lf work --json`** — the machine-wide read (§7.1). Reuses
   `snapshot_projects`; adds no model. *This is the whole backend of the feature.*

4. **W2-131 — all-Wave roadmap + launch/attach from chat** (already filed).
   Consumes `lf work`. Renders the tree, the three lenses, the plan×session pair,
   and wires the existing verbs. Chat and Mac share the contract.

5. **Mac surface** — `RegistryQuery.work()` and the tree view; retires the
   per-wave `pm show` fan-out.

6. **Ambiguity language** — the `done × none` and `open × merged` cells (§4.1),
   plus the "close it in Linear" nudge. Small, and the thing that keeps the two
   truths from collapsing back into one.

This Task ships only this document. Items 1 and 3 are new; 2 and 4 exist.
