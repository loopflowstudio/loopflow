# W2-142 — Recover and validate the v0.11.0 release

## What happened

`v0.11.0` was tagged at `c0b00ff20` and dispatched (run 29363619549). The four
`build-native` jobs passed; `build-dmg` died in 1m07s:

```
FileNotFoundError: swift/.build/release/Loopflow
```

The Mac app product was renamed `Loopflow` → `LoopflowMac`, but the DMG packager
still copied the retired path. `release` and `publish-crates` are gated on
`build-dmg`, so **nothing published**: no GitHub release (`gh release view
v0.11.0` → not found), no crate, no DMG in R2. The failure is total, not partial
— re-entry has nothing to clean up.

The packaging bug is already fixed on `main` (#884, `249360d3d`): read
`CFBundleExecutable` from `Info.plist`, copy `LoopflowMac` under that name.

## Why a re-dispatch still fails

`release.yml` checks out `ref: ${{ env.RELEASE_TAG }}` in every job. The tag is
immutable and predates #884, so a re-dispatch of `v0.11.0` checks out the broken
`scripts/release-loopflow.py` and fails identically. The release is wedged: the
fix exists, and the workflow cannot reach it.

## The fix: tagged source, current tooling

On `workflow_dispatch`, `build-dmg` checks out the default branch into
`.release-tooling/` and overwrites `scripts/` with it. Application source
(`rust/`, `swift/`, `python/`, `RELEASE_NOTES.md`) still comes from the tag;
only the packaging tooling floats to `main`.

That line is the policy, and it is the honest one: `scripts/` is how we build a
release, not what we release. A tag pins *what ships*; it should not pin the
build script that failed to ship it. A tag-push release is unaffected (`if:
github.event_name == 'workflow_dispatch'`), and since every real release is
dispatched from a tag freshly cut off `main`, the two trees are normally
identical — the copy only bites on a *re-run*, which is exactly when it should.

`00fa125fc` on `jack-heart/w2-127-release-recovery` prepared this, copying the
single file `scripts/release-loopflow.py`. Widen it to the whole directory:
`release-loopflow.py` imports `bundle_version.py` from the same tree, so a
one-file copy can pair a new script with an old helper. Today only
`release-loopflow.py` differs (`git diff --stat v0.11.0..main -- scripts/`), so
the widened copy is a no-op *now* and closes the skew class *later*.

No other re-entry hazard: `build-native` re-uploads artifacts, the `release` job
creates a release that does not exist yet, `publish-crates` already tolerates
"already uploaded", and the R2 upload overwrites by key.

## Build target

One commit on `jack-heart/w2-142`, one PR to `main`:

- `.github/workflows/release.yml` — the two `workflow_dispatch`-gated steps in
  `build-dmg` (checkout `main` → `.release-tooling`, `cp -R` its `scripts/` over
  the tagged one).

Nothing else. The migration behavior this task validates is already shipped and
unit-tested (`a_legacy_baseline_database_is_adopted_and_upgraded_without_data_loss`
in `store/migrations.rs`); W2-127 landed it. This task proves it in the
*released artifact*, and only writes product code if that proof fails.

## Verification target

1. **Land** the recovery PR to `main`.
2. **Dispatch** `gh workflow run release.yml -f tag=v0.11.0` from `main` and
   watch it to completion. Done when `gh release view v0.11.0` lists the four
   `lf-*.tar.gz`, `Loopflow.dmg`, and `install.sh`.
3. **Validate the released `lf` binary** (downloaded from that release, not a
   local build) against two databases, each seeded with a wave + a task so data
   loss is observable:
   - **pre-namespace**: `schema_migrations` stamped `001_initial`, built with a
     pre-namespace release (`v0.9.12`).
   - **v0.10 release-scoped**: stamped `0.10.001_initial` +
     `0.10.002_session_execution_context`, built with `v0.10.1`.

   For each: run the released `lf` against a copy, then assert the seeded rows
   survive and `schema_migrations` reads `0.10.001_initial` first (the legacy
   stamp *adopted*, not re-run — same bytes, no data moved).

A failure at step 3 is a product bug and belongs in this PR before it merges; a
failure at step 2 that is not the packaging path is a new red signal and gets
reported, not papered over.
