# W2-78 — Bootstrap the maintained Mac mini cron host

## Problem

The infrastructure wave wants a maintained host (mini-heart, the Mac mini) that
runs `lf` on a schedule: a daily health check that surfaces the first red signal
before a human notices. The runtime is explicit — launchd invokes top-level `lf`
commands; no lfd daemon, no resident wave listener required. Secrets come from
Doppler. The schedules must be **repo-owned**: declared in the repo, installed by
one idempotent command, not hand-typed per host.

## What exists

- **`lf cron add/list/remove`** (`ops/cron.rs`) — installs launchd plists that run
  `lf <flow> --wave <wave>` daily at 03:00. Imperative only: one flow per call, a
  fixed time, and **nothing reads the repo's declared schedule**.
- **`crons:` frontmatter** in `wave/<wave>/GOAL.md` (`WaveCronDef { flow, schedule }`,
  6-field cron expression) — consumed *only* by the resident `lf wave` listener
  (`flowloop/wave.rs`), which needs a live process. The launchd path ignores it.
- **`telemetry-daily` flow** (`.lf/flows/telemetry-daily.yaml` → `op: doctor`);
  `lf doctor` exits non-zero on any failed check, so a cron can gate on it.
- **`lf ssh`** — bounded (W2-153): `BatchMode=yes`, `ConnectTimeout=10`; an
  unreachable host fails fast, credential-free, host-named.

## The gap

Two schedulers, one declaration format, but only the resident listener reads it.
On a launchd host the operator would hand-run `lf cron add` per flow and lose the
declared schedule. The repo-owned declaration (`crons:`) is dead config for the
launchd path.

## Design

**One declaration, two schedulers.** Reuse `crons:` frontmatter as the single
repo-owned schedule source. Add `lf cron sync --wave <wave>` that reconciles the
host's launchd jobs to match the wave's declared crons.

1. **`sync_crons(dir, wave, declared, working_dir, lf_path, launchctl) -> CronSyncResult`**
   (`ops/cron.rs`): install/replace a launchd job per declared cron; prune launchd
   jobs *for this wave* whose flow is no longer declared. Idempotent. Returns
   `{ installed, removed, skipped }`.
2. **Honor the declared time.** Replace the fixed 03:00 with `Schedule::DailyAt { hour, minute }`
   derived from the cron expression via a deterministic classifier
   (`daily_time_of`): parse with the `cron` crate, take two consecutive fires from a
   fixed anchor, require exactly 24h apart, emit `DailyAt{hour,minute}`. A non-daily
   expression is **skipped with a reason**, never silently mismapped. `parse_schedule("daily")`
   → `DailyAt{3,0}` (unchanged default for `lf cron add`).
3. **CLI** `lf cron sync --wave <wave>`: read `crons:` via `read_wave_config`,
   reconcile, print the summary.
4. **Repo-owned schedule content:** add one real cron to
   `wave/infrastructure/GOAL.md` — `flow: telemetry-daily`, a daily time — so the
   host has a real health check to run and the feature has a live demo.
5. **`release/CRON_HOST.md`** — the maintained-host contract: names mini-heart
   (host, tailnet IP, role) so the host is a discoverable committed fact (not a
   SaaS-console-only fact), lists prerequisites (lf, Doppler), the bootstrap
   command, where failures land, and the known limitations below.
6. **`scripts/bootstrap-cron-host.sh <host> [wave]`** — bounded reachability/auth
   probe (`lf ssh <host> -- lf --version`), Doppler presence check, `lf cron sync`,
   then `lf cron list` to prove it. Idempotent, no secrets, no values printed.

## Failure surfacing (v0)

launchd writes each job's stdout+stderr to `<repo>/.lf/logs/cron.<wave>.<flow>.log`;
`lf doctor` exits non-zero on failure. That is the v0 surface — a red run leaves a
non-zero exit and a log. Turning a red cron log into an attention item / focused
fix PR is the wave's separate "Release feedback loop" item, not this task.

## Known limitations (documented, not hidden)

- **Timezone:** launchd `StartCalendarInterval` is host-local; the resident
  listener reads the same expression as UTC. The declared HH:MM is applied as
  host-local on the launchd host. Acceptable for a daily health check; documented
  in `CRON_HOST.md`. Not worth a tz-normalization layer at v0.
- **Schedule expressiveness:** only fixed daily times translate to launchd at v0.
  Sub-daily / weekly / multi-time expressions are reported as skipped. The resident
  listener still honors the full expression; the launchd host is daily-only for now.

## External blocker (evidence)

mini-heart is **unreachable** from this worktree right now:
- `lf ssh mini-heart -- echo ok` → `ssh: connect to host mini-heart port 22: Operation timed out`
- `ssh -o BatchMode=yes -o ConnectTimeout=10 jack@100.96.227.95 echo ok` → same timeout
- no `mini-heart` alias in `~/.ssh/config`; local `tailscale` CLI is the known-broken shim

So the *provisioning* half (run the bootstrap against the host, prove a nightly
run from the host) cannot complete here. The *repo-committable* half — the
`lf cron sync` feature, the declared schedule, the host doc, the bootstrap script —
is unblocked, verified locally, and makes provisioning a single command the moment
mini-heart answers on the tailnet.

## Verify

- Unit: `daily_time_of` extracts HH:MM and rejects non-daily; `sync_crons` installs
  declared and prunes undeclared.
- Local run: `lf cron sync --wave infrastructure` on this Mac installs the
  telemetry-daily job at the declared time (`lf cron list`, inspect the plist), then
  `sync` against an empty declaration prunes it — leaving the Mac clean.
