# W2-88 — Wave home as an explicit inherited SSH target

## What we're building

A Wave carries an **explicit execution home**: either `local` (this machine) or
one SSH target (e.g. the Mac mini). The home is authored on the Wave, inherited
by Project and Task launches, and used to route top-level `lf` commands to that
host. It is not an lfd daemon, not an environment-selected role, not a new
Concerto protocol. Credentials keep riding the existing `lf ssh` + Doppler
surfaces.

Finish line: one remote-home Wave routes a top-level `lf` command onto the Mac
mini (via the existing SSH credential-forwarding transport) while a local Wave
stays local, unaffected, and both are distinguishable in `lf status` data.

## Why the pieces land where they do

The transport already exists. `lf ssh <host> -- <cmd>` (`lf/commands/ssh.rs`)
resolves local credentials (gh, Claude OAuth, PM/Linear token, named Doppler
secrets), forwards them as a stdin preamble that never touches argv/logs, `cd`s
into `$HOME/<repo>`, and execs over `ssh <host> bash -s`. This Task adds *no new
credential path* — routing reuses this machinery.

Home is **authored policy**, so it lives in `GOAL.md` frontmatter, not the
registry row. `wave/registry.rs` is explicit: the registry "stores no
launch-policy cache; authored Wave policy remains in GOAL.md." Home sits beside
`agent`, `paused`, `pm`, `crons` in `WaveConfig` — a human edits it, it is
file-first, and `snapshot_wave` already reads `GOAL.md` for `paused`, so status
gets home for free.

Inheritance is **pinning**, matching the doctrine already in
`ChildExecutionContext` ("whoever happened to type the command chose the child's
execution context" is the exact anti-pattern that struct exists to kill). Home
is resolved once at Session creation and pinned, exactly like `lf_bin`/`db_path`,
then forwarded to the child as an env var. A child never re-derives its home
from a `GOAL.md` that could have changed underneath it.

Routing keys on the **resolved Wave identity**, not a string parsed from a
branch or path — "without string-derived identity." The router resolves the Wave
the same way `resolve_status_wave` does (ambient `LF_WAVE_ID` / registry), then
reads that Wave's authored home. The target host is authored config, never
munged out of a name.

## Scope boundary (what this Task does NOT do)

The remote home is a **compute surface for routed commands**, not where the
resident lives. The Wave's resident loop, chat, memory, `.wave-endpoint`, and
`lf status` stay **local** — they assume a co-located filesystem and loopback
HTTP (`wave_context.rs` reads `http://{addr}/conversation`), and relocating them
is Concerto/transport territory the directive excludes. Status must stay local
anyway: a local operator has to *see* both waves to compare them; if `lf status`
forwarded to the remote, the two waves stop being comparable.

We also do NOT relocate the Task/Project tmux runner onto the remote host. That
needs a remote worktree + remote registry + Concerto-grade transport. What
inherits is the *routing decision*: a Task launched under a remote-home Wave
pins the home, so the shipping commands it runs (`lf commit`, `lf pr open`)
route to the Mac mini. The runner process itself stays where it was launched.

## Design

### 1. `WaveHome` — the typed home (new `engine/wave_home.rs`)

```rust
#[derive(Debug, Clone, PartialEq, Eq)]
pub enum WaveHome {
    Local,
    Ssh { host: String, repo: Option<String> },
}
```

Single input funnel, Postel-style (mirrors `WorktreeName::parse`):
- `parse(&str) -> Option<WaveHome>`; `Display` round-trips.
- Authored forms in `GOAL.md`: `home: local` (default when absent) or
  `home: ssh://<host>` or `home: ssh://<host>/<repo>`. A plain string keeps the
  frontmatter hand-editable; no nested tagged-enum YAML.
- `host` validated non-empty, no whitespace; `repo` defaults to
  `ssh::DEFAULT_REPO`.

`WaveConfig` gains `pub home: Option<String>` (raw authored string;
`read_wave_config` already tolerates unknown/missing fields). A helper
`WaveConfig::home() -> WaveHome` parses it, defaulting to `Local`.

### 2. Routing — the intercept in `bin/lf.rs`

A `route_to_home(&cli, &args) -> Option<Result<()>>` guard, called **before**
the big `match &cli.command`, returns `Some(result)` when it handled the command
remotely and `None` to fall through to local dispatch.

Routing set (deliberately minimal, a named `const`): the repo/PR/release/PM
operations that must run where the wave's work lives —
`pr`, `commit`, `rebase`, `release`, `pm`. Everything else (wave/resident/stop,
status/ls/runs/trace/tokens/usage, chat/radio/memory, auth/doctor/context,
ssh, skill/flow/inline runs, the `__task`/`__project` runners) stays local.
Extending the set later is a one-line change; start small and demoable.

Decision procedure:
1. If the command is not in the routing set → `None` (local).
2. Resolve the home: `LF_WAVE_HOME` env (pinned/inherited) first, else resolve
   the ambient/explicit Wave and read its `GOAL.md` home, else `Local`.
3. If home is `Local` → `None`.
4. If `LF_HOME_ROUTED` is set → `None` (loop-break: we are already on the home
   host after a forward; never re-forward to ourselves).
5. Else forward: reconstruct the original `lf` argv (drop `argv[0]`), and run it
   on `host` via the ssh transport, setting `LF_HOME_ROUTED=1` in the remote
   preamble. Propagate the remote exit code.

The loop-break uses an env sentinel exported by the forwarder, not a hostname
comparison — no FQDN/short-name/tailscale guessing.

`ssh.rs` change: the human `lf ssh` stays untouched. Add a thin
`ssh::run_routed(host, repo, argv)` (or an `extra_env` param on `run`) that
reuses `build_preamble`/`run_ssh` and additionally exports `LF_HOME_ROUTED=1`.
`build_preamble` already single-quote-escapes everything; the marker is a fixed
literal.

### 3. Inheritance — pin home onto the child

Extend `ChildExecutionContext` (`child_session.rs`) with `home: WaveHome`,
persisted as its round-tripping string. `0.10.002` stores the context as
**discrete columns** (`lf_bin`/`db_path`/`lf_home` on both `task_sessions` and
`project_sessions`), so this needs an additive migration
`_session_execution_home.sql`: `ALTER TABLE {task,project}_sessions ADD COLUMN
home TEXT`. Nullable, mirroring `0.10.002` — a Session created before this
migration has no pinned home and reads back as `Local` (the safe default), which
is exactly the pre-existing behavior.

- `pinned_execution_context()` (`engine/process.rs`) resolves the owning Wave's
  home from its `GOAL.md` and stores it on the context.
- The Project/Task launch env assembly (`ops/project.rs` ~L459, `ops/task.rs`
  ~L621) adds `("LF_WAVE_HOME", <pinned home string>)` beside the existing
  `LF_WAVE_ID`/`LF_HOME`/`LF_DB_PATH`. The child's routed commands then read
  `LF_WAVE_HOME` first (step 2 above), inheriting the home the Session was born
  with even if `GOAL.md` later changes.

### 4. Status — distinguish local vs remote (`lf/commands/waves.rs`)

`WaveSnapshot` (wire DTO, no defaults) gains:

```rust
pub home: WaveHomeDto,   // { kind: "local" } | { kind: "ssh", host, repo }
```

`snapshot_wave` already reads `read_wave_config` for `paused`; it reads `home`
from the same config and projects the typed DTO. `WaveHomeDto` is a tagged enum
(`#[serde(tag = "kind")]`) so both languages mirror it cleanly; add it to the
`tests/fixtures/dto/` round-trip fixture. `print_status`/`ls` render a short
`home` line (`local` or `mini-heart`).

A remote-home wave will show `live: false` locally (its resident, if any, is not
on this machine) — acceptable and correct: `home` is the distinguishing field,
liveness of a remote resident is out of scope.

## Demo / verification target

Unit-testable (no live host needed):
- `WaveHome::parse`/`Display` round-trips: `local`, `ssh://mini-heart`,
  `ssh://mini-heart/src/loopflow`; rejects empty host.
- Router: a `pr`/`commit`/`rebase`/`release`/`pm` command in a wave whose
  `GOAL.md` says `home: ssh://mini-heart` produces a forward to `mini-heart`
  with the reconstructed argv and `LF_HOME_ROUTED=1`; the same command with
  `home: local` or absent, or with `LF_HOME_ROUTED=1` already set, runs locally.
- A non-routed command (`status`, `wave`) never forwards, even under a remote
  home.
- `ChildExecutionContext` round-trips with a pinned `Ssh` home; the Task/Project
  launch env includes `LF_WAVE_HOME`.
- `WaveSnapshot` JSON carries `home` for both a local and an `ssh` wave; DTO
  fixture round-trips.

Live demo (the finish line):
- Create/author two waves: one `home: local`, one `home: ssh://<mac-mini>`.
- `lf status <remote-wave>` and `lf status <local-wave>` show distinct homes.
- In the remote-home wave, `lf pr open` (or a harmless routed `lf pm status`)
  executes on the Mac mini via the forwarded transport; the local wave's
  identical command runs locally and is unaffected.
- Where no Mac mini is handy, substitute `home: ssh://localhost` to prove the
  hop end-to-end without a second box.
