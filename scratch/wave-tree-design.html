One tree of Waves

What Loopflow feels like from a solo founder's first day to a few people inside a large company, when all work is one kind of thing that nests.

Draft for comparison, 2026-11-20. Written without reading the parallel draft. Anything marked proposed is this document's choice and has not been said by anyone; the rest restates what is recorded in scratch/said.md. Tracker facts are from scratch/hierarchy-research.md.

The whole model in one screen

A Wave is a piece of work. It can hold other Waves, to any depth. There is no second kind.

Any Wave may have any of these, and none is required:

  • A thread: the conversation you use to drive it. It never changes as the work grows, and it hears when a Wave directly under it stops, fails or lands.
  • A runner: at most one, with a checkout and its PRs over time, one current.
  • Goal, memory and settings.
  • Connections to things outside: one tracker item (a Linear team, initiative, project or issue), a chat channel, docs or folders.

Four rules cover the rest.

  1. The tree is Loopflow's. Changing it changes nothing outside, and it need not match Linear's or Slack's shape.
  2. What a Wave lacks, it finds by going up. Chat to post in, where to file, settings, memory. If nothing up to the root has it, the action fails and says so.
  3. A Wave is personal until you publish it. Publishing shares that one Wave. Others see it under the nearest shared Wave above it.
  4. Nothing outside is created unless you ask. Connecting attaches to what exists. Making a Linear project or issue is always a deliberate step.

Waves live with the plan, published live like the tracker, and are not files in the repository. proposed A Wave's goal and memory are docs connected to it; when the tracker is Linear, the goal sits in Linear where teammates already read.

lf wave create store --parent infrastructure     # personal, connected to nothing
lf wave move store --parent product              # tree only
lf wave connect store linear:project/store-rework
lf wave connect infrastructure slack:#infra
lf wave publish store                            # this one becomes shared
lf wave show store                               # what it has, and what it gets from above
lf wave close store                              # what's worth keeping moves up

The same seven commands serve all four stages below. What changes from stage to stage is only what is connected and who a Wave is published to.

1. A solo founder, from day one to a company that runs itself

Day one

You run lf init in an empty repository. There is one Wave: the repository. You open its thread and say what you're building.

It files the first three pieces of work under itself and starts them. Each has a runner and will end in a PR. You have connected nothing, and nothing asked you to.

acme
  sign-up flow            running · implement
  billing skeleton        running · design
  landing page            needs you · review

Week two: work fans out

Billing turns out to be five things. In billing's thread you say "split this up." Five Waves appear under it. Billing's thread is unchanged; it now tells you when one of the five stops or lands. Its own first PR merges and billing stays open, because work is still under it.

You never decided that billing was "a project now". It held work, so it holds work.

Month two: areas appear

The top level has thirty things in it. You tell the root thread "group these." It proposes product, infrastructure and growth, creates them and moves Waves under them. Each new Wave gets a goal and starts collecting memory. Nothing was committed and no PR was opened to do it.

Month six: you zoom

Each level's thread knows only the level under it, so each level is a summary of the one below.

  • At the root: "Infrastructure has one thing waiting on you. Growth shipped four PRs. Product is blocked on pricing." You answer the pricing question there.
  • In infrastructure: the eight Waves under it and which are stuck.
  • In one stuck Wave: its diff and its runner's question.

You can step in at any level and the levels above and below keep working. A Wave with a cadence wakes on its own, reads what's under it, and files or starts what its goal calls for; settings and budget come from above unless it sets its own.

When you want the outside world

You connect a Discord channel to the root. Every Wave can now reach you there, because each one finds that channel by going up. Later you connect a separate channel to growth, and only growth's Waves move to it.

2. Five people, a big codebase, Linear and Slack already in use

Setting up is one request

One person runs lf init and says: "Set us up from our Linear and Slack." The agent reads the Linear teams and active projects and the Slack channel list, then shows the tree it would make:

acme                         linear: workspace     slack: #eng
  platform                   linear: team PLAT     slack: #platform
    store rework             linear: project
    perf                     linear: project
  app                        linear: team APP      slack: #app
    onboarding v2            linear: project       doc: Onboarding v2 brief

She edits it by talking ("perf belongs under app"), then says go. The agent runs create, connect and publish. There is no importer: the commands are good enough that an agent does the mapping, and keeps it up when Linear changes.

Nothing was created in Linear or Slack. Every connection points at something that already existed.

The other four join

They install Loopflow and the shared tree is there, the way the plan is. No pull, no PR to review.

Doing work: where people and agents meet

The meeting point is a Linear issue. Dana takes PLAT-212, "Drop members marked leaving", and starts a thread on it. A Wave now exists under store rework, connected to that issue. Its status and PR link update in Linear exactly as if she'd done it by hand.

It grows into four pieces. Those four are personal Waves under hers.

Dana sees

store rework
  PLAT-212 drop leaving members
    stage the column drop
    backfill
    remove the readers
    drop the column

Linear and her teammates see

store rework
  PLAT-212 drop leaving members
    four PRs, linked to PLAT-212

If one of the four is something a teammate should pick up, she publishes it and asks for a Linear issue for it. It appears under PLAT-212 as a sub-issue. The other three stay hers.

What the team shares

  • Memory. What an agent learns in platform is read by everyone's agents working under platform, the moment it's saved. It no longer waits inside a code PR.
  • Settings and Graphs. App runs the feature Graph and platform runs code, set once on each Wave.
  • The plan doc. The onboarding brief is a Google Doc connected to its Wave. People edit it in a meeting; the Waves under it read the latest at their next step.
  • Where to talk. A Wave's updates go to the nearest connected channel above it.

What the team doesn't share

Runners. Each Wave has at most one, and it belongs to the person who started it. Nobody drives someone else's agent. Handing work over means a new Wave, or a Linear issue someone else takes.

The repo-level agent

The root Wave has a thread too. Asked "what should we do about flaky CI?", it can file Linear issues, unassigned, in the project found by going up. A person takes one, and that is the meeting point again.

3. One person inside a large organisation

The test for this stage: someone who has never heard of Loopflow can't tell you're using it.

Starting

You run lf init in your clone of a repository you don't own. proposed Nothing is written into the repository: no .lf/ to commit, no ref pushed. Your Waves, settings, Graphs and skills live on your Machine.

Bringing the context in

You tell your root thread: "I'm on the Payments team. Set me up." It builds a small personal tree and connects it to what you can already read:

payments (personal)          linear: team PAY      slack: #payments (read)
  ledger migration           linear: project       doc: Ledger migration RFC
  on-call                    slack: #pay-oncall (read)
  my scratch

Connections on a personal Wave are personal too. Connecting to the PAY team changes nothing in Linear; it tells your agents where your work sits and what to read.

Working

You take PAY-4821 the normal way and start a thread on it. Your agent has the RFC, the project's other issues and the channel history as context, found by going up. It fans out into six personal Waves. Each one's PR is an ordinary PR from your account, linked to PAY-4821.

What "doesn't gum up the works" means concretely

  • No sub-issues appear in the team's backlog. In Linear a sub-issue shows in team views like any issue, so fan-out stays in Loopflow.
  • Nothing is posted for you. proposed A channel connected to a personal Wave is read-only by default; an agent that wants to post writes a draft and shows you.
  • The repository has no Loopflow files.
  • Linear writes are the ones you'd make yourself: status, assignee and PR link on issues you own.

4. A few of you inside that organisation

Two teammates start using Loopflow too. The same test holds for everyone else: it looks like three people collaborating normally.

Sharing between the three of you

You publish ledger migration to the three of you. proposed Publishing names who it is for: a group you set up once, and the place its plan travels.

lf group create payments-lf --members dana,eli --carrier git:<a small repo the three of you can push to>
lf wave publish ledger-migration --to payments-lf

From then on the three of you share, for that Wave and what is published under it:

  • its goal and memory,
  • its settings,
  • its Graphs and skills, which travel with the Wave instead of being committed to the organisation's repository, proposed
  • who is working on what under it, and where each piece stands.

Each of you still has personal Waves under it that the other two never see.

What everyone else sees

Linear issues with assignees, PRs with reviewers, messages in #payments. When Eli's agent needs something from you, it files a Linear issue assigned to you or drafts a message for Eli to send. Coordination between you travels through the tools the whole team reads, so nobody outside the three is missing half the conversation.

Growing from three to the whole team

Add people to the group. If the team adopts Loopflow outright, the group's carrier becomes the team repository's own and this is stage 2. The tree, the Waves and their history are the same ones.

What this asks of the product

  • Task and Wave become one kind. PR #1986 is the first slice under the old names: a parent link, a thread that hears about what's under it, staying open after merge, reopening after close.
  • Waves leave the repository and travel with the plan. In this repository 54 of the last month's 55 commits under .lf/wave/ were memory edits riding in code PRs.
  • The doc store (LOO-997) holds goals, memory and plans, so it comes early.
  • Everything Loopflow needs can live outside the repository, for stages 3 and 4: settings, Graphs and skills.
  • Sharing has an audience smaller than "everyone with the repository", for stage 4.
  • Turning a Wave into a Linear project flattens its sub-issues in Linear. Loopflow's tree keeps the shape; Linear's does not.

Questions

  1. The word in the UI and CLI for a Wave with a runner that is meant to end: a. Task, as a word for that case only. b. Everything is a Wave.
  2. A new Wave under one connected to a Linear project: a. starts unconnected; you ask for an issue. b. gets a Linear issue by default when it has a runner. c. a setting on the Wave above.
    Stage 2 reads better with b; stage 3 needs a.
  3. Who a published Wave is shared with: a. everyone on the repository's plan, always. b. a named group, as in stage 4. c. a at first, b later.
  4. Graphs and skills: a. stay repository content; stages 3 and 4 keep them on each Machine. b. can also travel with a Wave.
  5. An agent reads and writes memory: a. as files Loopflow places in the checkout, untracked, saved back. b. only through lf and what's given at launch.
  6. When the tracker is Linear, a shared Wave's goal lives: a. in Linear, on the project. b. on the plan, linked from Linear.
  7. Posting to a channel connected to a personal Wave: a. drafts only. b. posts as you. c. a setting.
  8. A Wave's thread hears about: a. the level directly under it. b. everything under it. c. the level under it, plus anything deeper that needs a person.
  9. Closing a Wave with personal Waves under it: a. closes the ones with nothing unmerged and names the rest, as #1986 does. b. closes all. c. asks.
  10. Does #1986 land as built, with the fusion as later work?
