The Work model

2026-10-10 · LOO-412 · source at c8fe4628affc13ac0553c14cd5bec5e5896369a1

Jack Heart requested a map of the major data structures before choosing better language than “Planning.” This describes the current branch, including inherited types. Naming suggestions at the end are proposals; no rename is selected here. The current design owns implementation scope.

The model in one screen

Work is the existing umbrella. Its three named scopes are Wave, Project and Task. Comments, success criteria, workflow definitions and execution records attach to that model; they are not additional Work scopes.

Repository
└── Wave                       Long-lived objective and responsibility
    ├── Goal and memory        Authored documents in the repository
    ├── Metric contracts       What to measure and what evidence means
    ├── Selected Project ──┐   Explicit selection, independent of naming
    └── Projects           │   Concrete bodies of work, including past work
        ├── Content        ◀── Summary, KRs, metric targets, workflow choice
        └── Tasks              Concrete outcomes, descriptions and disposition
            └── Comments       Discussion and direction

On each Machine separately:
  Task → checkout and PR records
       → captured Workflow and its position/history
       → associated Sessions and Processes

There are three ways these things travel:

Data Where it lives / how it travels
Goal, memory, metric and workflow definitions, source code Ordinary repository files and Git history.
Shared Work fields and Task comments Local SQLite records, exchanged through the configured Linear or Git-ref transport.
Execution and machine-local bookkeeping Local SQLite/filesystem records. This Task's Work exchange does not copy them.

The distinction is by field and responsibility, not by serializing whole Rust objects. In particular, Task combines shared descriptive content with local checkout and delivery information. Copying its entire struct would cross the intended boundary.

“Planning” currently names parts of all of the following: descriptions of work, completed work, provider observations, pending changes, and synchronization. There is no single Planning domain object that owns all of them.

1. Identity and scope

Type Meaning Important boundary
WorkRef Wave(WaveId), Project(ProjectId) or Task(TaskId). A reference to a scope of work. Contains identity, not the object's content or authority to run it.
WaveId, ProjectId, TaskId Durable Loopflow identities. Names, issue identifiers and filesystem paths are separate.
LinearIssueId, LinearProjectId Optional mappings to Linear objects. A Work object can exist before it has a provider mapping.
WaveLocator A Wave's local canonical repository and readable slug. A mutable address, not its durable identity.
CanonicalRepo The local repository path, normalized across its worktrees. Machine-local; a path on the laptop is not a path on the worker.
RepoId Repository identity derived from its remote provider/owner/repository. Separate from checkout location.
MachineId, Machine One registered Machine, its route, optional label and saved repository. A connection record, not another Work scope.
Placement A WorkRef, a MachineId and placement time. Not part of the shared-field schema in this slice. It does not implement distributed first-start scheduling.

New Linear-backed Tasks derive their Loopflow ID from the issue ID. Locally created Tasks retain their ID across provider creation; Git exchange carries authored IDs. Existing mappings retain their IDs, including two Machines' different legacy IDs for the same issue. Display text such as LOO-412 is a selector, not the universal primary key.

Sources: durable identities and WorkRef, WaveId, repository identities, provider IDs.

2. Wave — the long-lived workstream

Wave is the durable identity and lifecycle record. Its important fields are id, name, repo, parent_wave_id, creation/promotion/retirement times and supersession information. Its slug is derived from its name.

The broader Wave concept spans several representations:

Representation Content
Wave Identity, hierarchy, repository association and lifecycle.
GOAL.md body Objective, responsibility and bounds.
MEMORY.md Curated decisions, evidence and unresolved work.
WaveConfig Goal frontmatter: ID, context budgets, agent defaults, per-skill agents, crons, PM binding and chat binding.
WaveCronDef Flow name and schedule. Installing/running that schedule is a separate operation.
WavePmConfig Mapping to a Linear Initiative; repository configuration owns the Team.
WaveChatConfig Local chat or a specific Discord guild/channel binding.
waves.current_project_id The selected Project in SQLite. It is not a field on the Rust Wave struct.

The current shared-field writer exchanges the Wave's name, parent and selected Project. It does not exchange the entire Wave row, goal frontmatter, memory or installed cron jobs. The documents travel with the source repository.

Sources: Wave, Wave configuration, shared fields.

3. Project — a body of work and its success criteria

Project joins durable identity to its Wave and descriptive content:

Project
  id, wave_id
  plan: ProjectPlan
  iteration
  abandon_intent
  created_at, updated_at

iteration is documented as recording Project judgment passes. Current-source inspection found storage, reload and preservation tests, but no production path advancing it. It appears to be retained state from an earlier model, not an active Project behavior. A Project has no checkout or PR of its own, and does not own another permanent goal, memory or cadence.

There are three overlapping Project representations:

Type Important fields Role
ProjectPlan name, slug, summary, workflow, status, prompt_context, optional Linear ID and observation time Payload carried inside durable Project. Includes rendered context and provider metadata as well as authored content.
ProjectContent krs, metric_targets, workflow Structured content parsed from/rendered into the Project description.
PmProject ID/revision, name/slug/summary, KRs, targets, workflow, status, Initiative IDs and Team IDs Provider-shaped view also used to return local Project data.

ProjectStatus has Backlog, Planned, Started, Paused, Completed and Canceled. Those are Project lifecycle categories, separate from whether a Process is running or the Project is selected for a Wave.

Chapter is not another durable object or table. Chapter terminology names a planning convention across Projects; it still appears in names such as ChapterMetricTarget. Explicit Project selection is its own stored fact.

Sources: Project, ProjectPlan, ProjectContent, PmProject and ProjectStatus.

Success criteria and measurement

Type Meaning
PmKr A key result: text and an explicit holds judgment. Completing Tasks does not itself establish that judgment.
ChapterMetricTarget A Project's target for a named metric: metric_id plus MetricTarget. The name says Chapter; the containing object is Project content.
MetricTarget A numeric threshold: AtLeast { value } or AtMost { value }.
MetricIdentity Wave identity plus metric identity. The instrument belongs to the long-lived Wave.
MetricContractDefinition / MetricContract Authored and validated measurement definition: instrument, unit, window, freshness policy, description and stage. The validated contract has a content revision.
MetricObservation Either measured evidence with value/window/completeness, or explicit unavailability with a reason. Tied to a contract revision and instrument.
MetricReadingDto A displayed reading joining contract, optional current target, freshness and evidence.
MetricEvidenceDto Untargeted, Met, Missed, Unknown or Unavailable.
MetricPortfolioDto A collection of readings plus contract problems.

The contract says what a measurement means; the Project target says what this body of work aims to achieve; the observation records measured evidence. They have different lifetimes. The shared Work schema includes Project targets and KRs; it does not replicate the metric observation store.

Sources: Project criteria, metric definitions, evidence and readings.

4. Task — a concrete outcome, with local work attached

Task contains id, wave_id, project_id and a TaskPlan. It also carries local worktree path, workspace slug, branch/base/parent-PR information, agent choice, abandonment intent, timestamps and delivery/observation state.

TaskPlan is much narrower than the complete shared Task record:

TaskPlan
  identifier, title, description
  linear_id?
  revision                  Local optimistic-write counter
  pm_snapshot_synced_at?     Provider observation time

Assignee, ordering, due date and disposition are stored/read elsewhere. Thus “the Task's plan” does not currently mean “all the fields that synchronize.”

Type Role
NewTask Creation input: retained Task ID, Project ID, title, description and optional due date. Retaining the ID lets a retry remain the same creation.
TaskPlan Descriptive payload inside Task, plus local revision and provider metadata.
PmItem Broad Task/issue view: identity, identifier, title (name), description, rank, assignee, due date, state/completion, Project/Team membership, URL and branch name.
PmItemUpdate A partial content update. For assignee, omission preserves and explicit null clears.
PmTaskRecord A PmItem, optional PmProject, and the time these facts were observed. Requires no checkout or running work.

PmItem is not exclusively a Linear response. The local SQLite reader constructs it too, using the external ID when mapped and the local ID otherwise. Its generic name Item and provider-looking prefix hide its role as a central Task read model.

Sources: Task, TaskPlan and NewTask, PmItem, PmTaskRecord, local read projection.

Completion is shared; execution is local

There are several different state questions:

Type / field Question answered
Disposition What is the shared Task state, is it completed, and when? Groups planning_state, planning_completed and planning_completed_at into one edit.
TaskState What is this Task's overall local presentation? NotReady, Ready, Active, Done, Abandoned. Combines durable disposition with Workflow readiness.
WorkStatus Is this Work open (Ready), done or abandoned? Coarser than Task readiness.
WorkflowPosition Where is this Machine's captured Workflow: at a node or on an edge?
TaskExecutionState What does observed local Flow activity show: Idle, Starting, Running, Stalled, Blocked, Unknown?
PlanningState Are retained facts available, invalid, removed, absent or unavailable? This is availability of knowledge, not Task progress.

An imported completion can change the shared disposition and the Task's presented status without moving its Workflow, terminating a Process, cleaning its checkout or claiming that its local run succeeded. “Task done” and “Process exited” remain different facts.

Sources: Disposition, TaskState and WorkStatus, Workflow position, execution reading, fact availability.

5. Comments, direction and follow-up work

Type Meaning Shared or local?
TaskComment Comment ID, body, author and creation time. Content is exchanged.
TaskCommentAuthor Person { name? } or Integration. Attribution is part of comment content.
TaskComments Saved thread plus pending deliveries, retained conflicts and refresh errors. A local reading that combines shared content with local delivery evidence.
IssueComment Provider comment with author ID/name, creation time and revision. Provider observation used to construct the local thread and recognize direction.
IssueObservation Issue title, description, revision and comments from one provider read. Acquisition input, not another Work object.
Steer, SteerComment, Author Direction derived from Work comments/events, with attribution. A derived view; Steer is not an independently synchronized object with its own lifecycle.
FollowThroughIntent Exact retained filing input for follow-up work: stable issue/relation identities, target Project/Team, title, notes and due date. Local effect/recovery history.
FollowThroughLink Confirmed identity and display details of the filed follow-up. Local filing evidence; the resulting Task is ordinary shared Work.
FollowThrough Projection of intents, links, remaining conversion and explicit disposition from Task events. Local history/read model.

Saving a follow-up Task and saving the evidence that one Machine filed it are different writes. Other Machines acquire the resulting Work record; they do not inherit the first Machine's provider request as something to retry.

TaskEvent / TaskEventKind and ProjectEvent / ProjectEventKind retain local history. They include direction and operational decisions as well as progress. This exchange does not replicate those entire event streams.

Sources: Task comments, provider observations, Steer and Author, follow-through, Task events, Project events.

6. The single typed writer defines the shared boundary

PlanningEdit is the main internal write API. Each variant has a concrete value type, such as TaskTitle(Option<String>) or Krs(Vec<PmKr>). It defines which fields can be changed through the common writer and represented in Git exchange.

Object kind Fields in the current common schema
Wave Name, parent Wave, selected Project.
Project Wave, external ID, slug, name, summary, status, order, Initiative/Team associations, workflow selection, KRs, metric targets.
Task Project, external ID, identifier, title, description, order, assignee, due date, deletion time, URL, branch name, Team, grouped disposition.
Comment Task identity and grouped body/author/creation time.

The table describes the common field vocabulary, not a promise that Linear has a native writable counterpart for every field. Its adapter and repository definitions still own provider-specific mappings.

WriteOrigin distinguishes Local from Import. Both use the same field writer inside the caller's transaction. Local writes capture mutations with the record change; imports apply retained mutations without creating an echo change. Callers continue to own their transaction and local effect receipts.

This is one typed field-writing boundary, not one process designated to write for all Machines. Every Machine can make local edits and use its selected transport.

The schema deliberately has no Workflow position, Session turn, Process ownership, checkout path, Machine assignment or provider-attempt receipt. It does include a Task's descriptive branch name; that does not place or reset a checkout.

Source: PlanningEdit, grouped values and WriteOrigin.

7. Observations, changes and transport — three different layers

What was read

Type Meaning
PmSnapshot Current collection of Project and Task views.
PmSnapshotRow One Wave's snapshot plus provider, Initiative and acquisition time.
PmTaskObservation Optional Task facts plus their PlanningState availability.
PmWave Provider Wave/Initiative view: ID, name and summary. Not the durable local Wave.

Presence, freshness and execution eligibility are separate. An old observation does not become newly acquired just because it was copied. Missing data is not automatically deletion. None of these read models grants control of another Machine's Processes.

Sources: provider-shaped views, observation wrappers.

What needs to reach Linear

Type Meaning
PlanningChange A pending field edit: ID, field, local value and optional provider baseline.
PlanningSyncStatus Whether connected and a list of delivery readings. Despite its broad name, the fields/text describe Linear delivery.
PlanningSyncChange / PlanningSyncState Local versus Linear values, error and Pending, Uncertain or AdoptedLinear state.
PlanningExport Retained input for creating a local Project/Task in Linear, including model/input and stable effect identities. Not the Git exchange document.
PmWritebackState / PmWritebackOperation Current or pending completion/reopening/cancellation delivery.

These are local obligations and evidence. A failed network read can leave a request uncertain; another Machine must not treat that receipt as its own authority to repeat the request.

Sources: pending changes and status, creation export, lifecycle writeback.

What travels through the Git ref

Type Meaning
PlanningKind Wave, Project, Task, Comment: the exchange's record kinds. Unlike WorkRef, it includes subordinate comments.
PlanningObject Kind plus object ID: address of a record in the exchange.
PlanningMutation Object, field, JSON value, logical clock and causal parent change IDs. The writer validates the value's type.
PlanningSnapshot Map of immutable change IDs to mutations. It is a retained change journal, unlike PmSnapshot's current entity collection.
PlanningDestination Pinned Git endpoint and custom ref. A destination, not another Machine or controller.
PlanningRevision / PlanningDocument Git revision identity and document bytes at that revision.
PlanningPublication Confirmed, Pending or Unconfirmed remote publication evidence.
PlanningGit Transport implementation for reading/publishing the document without using the source branch/index/worktree.

Causality takes precedence over clocks. Concurrent field values use a deterministic clock/identity ordering, retaining losing values for inspection. That produces a chosen value; it does not prove that every combined edit is semantically valid. Projection into local Work records can still fail and retain a conflict.

Sources: exchange types and merge, Git transport types.

What “peer” means in this branch

PeerPlanningStatus reports a Git destination's local synchronization state: selected records, fetched/imported/published revisions, pending local changes, errors and conflicts. It is not a connection to one worker Machine.

PeerPlanningRecord and PeerPlanningValue expose retained objects, references, candidate values and provenance for recovery. PeerProjectionConflict explains why an object could not be applied. These readings are not executable restore instructions.

The SQL names preserve the same terminology:

Table group Responsibility
planning_peer_changes, planning_peer_observed Immutable mutations and accepted causal heads.
planning_user Personal ref key.
planning_destinations, planning_active, planning_members Saved destinations, active selection and record ownership.
planning_peer_imports, planning_peer_conflicts Import evidence and projection failures.

These are local storage/transport machinery, not new user-facing entities.

Sources: peer status types, schema draft.

Configuration and the exchange owner

PlanningConfig selects Git { remote, shared? } or Linear {}. Omitting shared selects the user's ref. Repository configuration replaces the personal selection as one value. Existing Linear Team configuration selects Linear when there is no explicit transport setting.

The PlanningSync runtime owns exchange during foreground command/Session lifetimes. It is operating machinery, not a shared record or a permanent master. In Linear mode, each Machine connects independently and outages buffer locally; there is no fallback Git transport for those changes.

Sources: configuration, foreground exchange.

9. What CLI and Desktop readers receive

TaskStatus explicitly separates planning, its availability/staleness/error, sync, and optional execution. A Task can be readable before it has local execution attached.

TaskDetailSnapshot joins the descriptive Task view with optional runtime, direction, next move, conditions/actions, workflow name, latest Flow, execution, run controls, PR and follow-through. It is a display projection, not another writer or source of execution authority.

WorkFrame is the committed-reading stream envelope. WorkContent distinguishes parts including Planning, PeerPlanning, Sessions, Task, Wave and activity. Here PlanningPart means roadmap plus Wave listings, while PeerPlanningPart means Git synchronization receipts. Neither is the Git exchange document.

Sources: TaskStatus, TaskDetailSnapshot, Work stream.

10. Naming choices worth discussing

The clearest existing product nouns are Work, Wave, Project, Task, Comment, Workflow, Session and Process. The main naming problem is the infrastructure around them: “Planning” is used for content, observation, exchange and delivery.

A useful vocabulary would distinguish Work records, Work sync and execution. Work records include outcomes and discussion, so the phrase still fits after a Task is completed. Work as the broader product concept can still encompass its associated execution.

These are candidate directions, not a bulk rename prescription:

Current name Candidate direction Why / limitation
PlanningConfig WorkSyncConfig Chooses how shared Work data is exchanged.
PlanningEdit WorkEdit Typed edits to Work records and their subordinate comments.
PlanningObject, PlanningKind WorkRecordRef, WorkRecordKind Makes clear these are exchange records; keep distinct from the three-scope WorkRef.
PlanningMutation, PlanningSnapshot WorkChange, WorkJournal “Journal” describes retained mutations better than “snapshot.”
PlanningDestination, PlanningGit WorkSyncDestination, GitWorkSync Describes the route and transport directly.
PeerPlanningStatus GitWorkSyncStatus Says what it observes; does not imply a Machine peer.
PlanningState RecordAvailability Its variants describe known/invalid/removed/missing facts, not progress.
PlanningSyncStatus LinearSyncStatus Already exposes Linear values and Linear-specific states.
PlanningExport LinearCreation or LinearCreationInput Captures one provider creation effect, not a generic export.
PlanningPart RoadmapPart Exactly the broad Work listing this stream part carries.
PmKr, ChapterMetricTarget ProjectKR, MetricTarget Jack selected these names during review; they supersede the earlier KeyResult / ProjectMetricTarget suggestions.
TaskPlan, ProjectPlan Remove the wrappers; fields belong on their domain objects Jack selected flattening Task content into Task. The analogous Project restructuring is proposed below. Preserve local write revisions and provider observation evidence separately.
PmItem, PmProject Separate domain views from provider observations, or name them as domain views Local readers already use these. Calling everything Linear… would misdescribe local/Git mode.

Two distinctions should survive any rename:

  1. A record's content versus knowledge about it. Title, completion and comments are content. Revision, acquisition time, invalidation and delivery uncertainty describe what this Machine knows or has attempted.
  2. Shared disposition versus local execution. A completed Task is a shared outcome. Its Workflow position, conversation and Process results remain local.

The next naming decision is whether Work records / Work sync expresses that boundary well enough. The code inventory supports it, but Jack has not approved those replacement names. No model, wire format, command or configuration was changed while preparing this document.

11. Review direction from Jack Heart

One cron list — proposed 2026-10-10

Jack proposed replacing Wave-owned cron declarations with one list of scheduled commands. Commands can carry ordinary --wave or --task selectors; the UI can filter by that scope when requested. The schedule need not become a child of a Wave just to run in its context.

Illustrative definition, not implemented configuration:

crons:
  - id: infrastructure-telemetry
    schedule: '0 0 9 * * *'
    command: [lf, --wave, infrastructure, run, telemetry-daily]

This would replace WaveCronDef and the Wave-only declaration/reconciliation path. Current CronSpec also separates wave, flow and target_kind; an ordinary command would remove that second command vocabulary. Scope filtering should use the normal command parser, not substring matching.

The single definition list and installed execution are different concerns: installing the same repository on two Machines must not silently duplicate a schedule. Existing Machine ownership, schedule identity, due accounting and receipts must survive moving declarations. A failed command keeps its failed receipt; editing its Wave selector must not erase history or imply successful recovery. Where the list is authored and how its execution Machine is selected remain open. This discussion authorizes no schedule activation or change.

Source: current cron spec, reconciliation and receipts.

Remove PM as an umbrella — requested direction 2026-10-10

Jack questioned PM as a separate concept and proposed naming Linear explicitly where that is what the code means. The code supports that distinction:

Current type Proposed treatment
WavePmConfig WaveLinearConfig or a simple Linear Initiative binding. Its useful current field is the Initiative ID; provider and Wave-level Team are retained migration sentinels.
PmConfig LinearConfig with the repository Team binding. Provider selection belongs in transport configuration, not repeated here.
PmWritebackState, PmWritebackOperation Use Linear delivery terminology because these describe provider writeback.
PmKr, PmItem, PmProject, PmTaskRecord Use domain names for shared Work content/readings. They also serve local and Git-backed work, so a mechanical Pm → Linear rename would be inaccurate.

Proposed configuration vocabulary: linear.initiative in Wave definitions and linear.team in repository configuration, with Git/Linear selection remaining on the sync configuration. Exact type and configuration names are not yet selected. The intended reduction is to keep Work concepts in the domain and Linear concepts at the integration boundary, removing the extra PM vocabulary.

These notes revise the naming discussion, not the current-source inventory above. Implementation remains unchanged.

Criteria names — selected 2026-10-10

Jack Heart selected PmKr → ProjectKR and directed that Chapter terminology leave low-level types, with MetricTarget sufficient for the target concept. The earlier KeyResult and ProjectMetricTarget suggestions are superseded. Currently ChapterMetricTarget contains a metric ID and an existing MetricTarget threshold enum. The redesign must resolve that name collision: the named metric target becomes MetricTarget; its at-least/at-most comparison can be a small Threshold enum. That inner name is proposed, not selected by Jack.

12. One Project record — proposed redesign

Jack Heart requested a natural redesign of ProjectPlan, ProjectContent and PmProject now that local Work records and selectable synchronization are the model. The proposal is one domain Project, usable without Linear:

// Domain sketch, not implemented code or a final storage schema.
struct Project {
    id: ProjectId,
    wave_id: WaveId,
    name: String,
    summary: String,
    description: String,
    status: ProjectStatus,
    workflow: Option<String>,
    krs: Vec<ProjectKR>,
    metric_targets: Vec<MetricTarget>,
    // Existing ordering and timestamps remain where their behavior requires them.
}

The description is authored prose. KRs, targets and workflow selection are typed fields with one stored representation. Prompt context and Linear description sections are rendered from them when needed. Currently the SQLite writer stores rendered KRs/targets inside project_prompt_context and readers parse that text back into fields; the redesign removes that internal render/parse round trip.

Current representation Proposed disposition
Project.plan: ProjectPlan Flatten its domain fields into Project; delete the wrapper. Keep Linear identity/freshness out of the domain payload.
ProjectContent Put its fields directly on Project. A private Linear Markdown parser may return a temporary parsed value, but it is not a second domain record or storage owner.
PmProject Local reads return Project. Actual Linear responses become an integration-local LinearProject shape, translated through the common typed writer.
prompt_context Derive prompt text from authored prose and structured fields. Preserve existing prose and criteria during conversion.
iteration Remove from the live model after confirming no remaining consumer. Preserve historical events and stored evidence during migration; do not invent a new counter meaning.
Linear ID, provider revision, acquisition time, Initiative/Team associations Keep explicit Linear binding/observation data keyed to ProjectId, outside the shared domain shape. Retain unrelated provider associations when updating Linear.
Pending edits, uncertain creations, errors, abandonment attempts Keep their existing local effect/history ownership; no new generic Project state machine.

This gives one path: read a Project, change it through the typed writer, commit locally, then exchange through the selected transport. Both Git import and Linear acquisition update that same Project. Read models may join it with sync status for display without becoming another writable Project representation.

The ordinary case is a local Project with KRs and no provider mapping. In a Linear outage, its edits stay saved and pending. On recovery, the adapter uses retained baselines and exact creation identities; replacing the domain types must not discard the evidence needed to resolve uncertain writes. A changed external description must preserve unrelated prose when extracting/updating managed criteria. Missing fields in a partial response are not permission to clear them.

The proposed removal of iteration follows a source search for reads, writes and ProjectEventKind::IterationCompleted: only persistence/preservation was found, with no production increment/emission. The original type comment explains its historical intent, not a current user requirement.

Next proof before implementation: one Project read/edit path in Git and Linear modes, plus a populated-store conversion preserving IDs, prose, KRs, targets, workflow selection, provider associations, pending effects and historical events. No Task execution records move or change. This proposal is not yet an approved schema or implementation scope.

13. Task content belongs on Task — selected 2026-10-10

Jack Heart agreed to remove TaskPlan and put identifier, title and description directly on Task. There is no separately named Task plan or brief in the proposed model. This supersedes the earlier tentative TaskBrief direction.

Task
  id, project_id, wave_id
  identifier, title, description
  …other Task fields

Removing the wrapper must preserve its local optimistic-write revision, Linear mapping and provider acquisition time. Their deletion is not implied by the content flattening. The proposed boundary, matching the Project redesign, keeps provider identity and observation metadata with the Linear integration and write revision with local persistence. Exact representation remains to be implemented.

This does not make the whole Task struct portable. Checkout, captured Workflow, Sessions, Processes and execution controls remain local; the typed writer still defines the shared fields. Source code has not yet changed.

14. Follow-ups as ordinary Tasks and comments — proposed 2026-10-10

Jack Heart questioned explicit FollowThroughIntent, FollowThroughLink and FollowThrough models, suggesting a comment instead. The simpler experience: create an ordinary Task when concrete work remains, then comment on the source Task with its link and the reason. A note that needs no Task stays a comment. Neither case needs a separate follow-through lifecycle or a mandatory “none” declaration.

The current types do more than display links: CompletionGate and the store's completion settlement require resolved follow-through, and cleanup consults that gate. Replacing the model therefore includes removing those special requirements, its --finish/--none ritual and dedicated UI status. Existing merge, process and checkout preservation rules remain separate. Comments do not authorize cleanup.

Task creation and comment delivery retain their ordinary stable identities and pending/uncertain receipts. If a follow-up Task saves but its linking comment fails, the Task survives and only the comment needs retry; a missing comment must not cause duplicate creation. This reliability belongs to the normal operations, not another domain model for follow-ups.

Retain historical follow-through events and unresolved provider effects during conversion. Existing filed Tasks and their identities survive; obsolete lifecycle requirements must not be recreated by parsing comments. This is a proposed reduction, with no implementation change yet.

Sources: current filing operation, completion gate, completion settlement, cleanup.

15. One comment model — selected 2026-10-10

Jack Heart accepted one domain TaskComment. TaskComments remains the thread reading with delivery status; it is not another comment entity. If a separate Linear response shape is needed for deserialization, use private LinearComment inside the adapter. Rename and confine IssueObservation to an internal LinearIssueObservation; ordinary Work readers do not depend on it.

Linear response → TaskComment → stored thread / UI

Keep provider comment/author IDs and revisions in the integration's observation metadata. They remain necessary to preserve identity, recognize incoming direction and reject stale observations; removing the extra domain vocabulary must not lose those facts. The adapter translates through the common writer. This is accepted design direction; source types have not yet changed.
