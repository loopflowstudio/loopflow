One Work model

Accepted design · LOO-412 · October 10, 2026

Jack Heart requested a deeper reduction of the Pm* and Planning* types. This proposal starts from one principle: a Project is a Project and a Task is a Task, whether saved offline, read from Linear, or received through Git. Transport changes how records arrive; it should not create another hierarchy of work.

Jack Heart accepted this structural direction on October 10. Finish the existing passes in the pursuit design, then take the queued deletion audit. Implementation owns the exact WorkEdit shape; the sketch below is illustrative. This adds no concurrent writer or automatic Flow restart. The original diagnosis is pinned to c8fe4628a; the audit covers the newer merged source.

1. Where the extra models came from

The current code describes the same Project through three overlapping shapes:

Project.plan: ProjectPlan       durable identity + a partial payload
ProjectContent                 workflow + KRs + metric targets
PmProject                      full provider-shaped view, also used locally

The follow-up audit also found persistent duplication: pm_projects and pm_items hold provider-shaped records, then accepted values are projected into Work rows. Ordinary local readers reconstruct PM-shaped views from those Work rows again. Remove that round trip while retaining concrete observations for foreign, unmapped, partial and stale provider facts; those facts must not silently acquire Work ownership.

The strongest example is the local content path. KRs and targets are rendered into project_prompt_context; readers parse that prose back into ProjectContent, then construct PmProject. The workflow name also exists as its own column. Ordinary local work is going through a provider-description encoding even when no provider is involved.

The Task side has the same split: Task.plan: TaskPlan contains title/description, while PmItem carries a broader field set and can use a provider ID or a local ID. Git exchange adds another object address (PlanningKind + PlanningObject) and a parallel field vocabulary.

Those transport records have useful jobs. They should describe changes to Work, rather than becoming another set of Work objects.

Sources: Project, plan payloads, local content reader, local Project/Task projections, exchange schema.

2. The proposed center

One domain model, with a single durable identity for each local object:

Wave
  id, name, parent?, selected_project?
  goal and memory references

Project
  id, wave_id
  name, summary, description, status
  workflow?, krs: [ProjectKR], metric_targets: [MetricTarget]

Task
  id, project_id
  identifier, title, description
  disposition, assignee?, due_date?, order

TaskComment
  id, task_id
  body, author, created_at

This is a conceptual field sketch, not a migration-ready schema. Existing timestamps, deletion evidence and necessary fields still need disposition. A Task's Wave can be derived from its Project; if retained for efficient reads, ownership writes must validate it.

A comment belongs to a Task. It does not become a fourth top-level Work scope. Tasks belong to Projects; Projects belong to Waves. Provider IDs never replace these domain IDs in ordinary read results.

Attach local activity to this Work rather than making Work carry all of it. Checkout placement, captured Workflow, Sessions, Processes and PR delivery records remain local records keyed to the Task. A Task's workflow preference is different from the captured Workflow and its current position.

                     one local Work store
                              │
               Wave → Project → Task → Comments
                              │
                   associated local activity
                   Workflow / Sessions / Processes
                              │
                       never replicated

        selected transport exchanges shared Work fields
                   Git ref     OR     Linear

There is no PmWave → PmProject → PmItem domain tree alongside this tree, and no separately writable “Planning Project.” An adapter may deserialize a provider response without giving that shape a second lifecycle or public API.

4. One read path and one edit vocabulary

The public operations should be recognizable from the objects being changed:

// Illustrative API, not a new generic repository framework.
store.project(project_id) -> Option<Project>
store.task(task_id) -> Option<Task>
store.task_comments(task_id) -> Vec<TaskComment>

store.apply(edit) -> Result<...>

Typed edits identify their own owner. There is no need for each caller to provide a kind, an untyped object ID, a field string and a JSON value independently:

// Examples, not the complete edit enum.
enum WorkEdit {
    ProjectName { project: ProjectId, name: String },
    ProjectKrs { project: ProjectId, krs: Vec<ProjectKR> },
    TaskTitle { task: TaskId, title: String },
    TaskDisposition { task: TaskId, disposition: TaskDisposition },
    TaskComment { task: TaskId, comment: TaskComment },
}

Creation, deletion and relationship changes must use the same typed boundary, with their existing transactional rules. SQL remains the one owner. The writer validates ownership, updates the row and records the needed local change/effect evidence atomically.

Both transports translate their inputs to these edits. The origin still matters: applying an observed remote value must not manufacture a new locally authored edit or inherit someone else's delivery attempt.

For Git, an immutable change envelope retains change ID, typed edit, causal parents and clock. Derive the conflict address from the edit. In particular, comments need their own comment ID in that address; two different comments must not compete for one generic Task “comment” slot.

This retains the real distributed requirement while deleting kind + object + field as a separately maintained domain vocabulary. Exact serialization, conflict keys and conversion of retained journal entries need proof before replacing the current format.

UI snapshots can join Work with sync status or local activity. They are disposable read projections, with no independent write path. A smaller list DTO is fine when it avoids loading large data; it should not redefine the Project.

5. Keep transport evidence beside Work

“Fewer types” cannot mean losing information about an uncertain write or stale response. The useful split is between Work content and evidence about exchanging that content.

Belongs on Work Belongs to an integration or local operation
Task title, description, comments, disposition Linear object/comment IDs, author IDs and provider revisions
Project KRs, targets, workflow preference Provider acquisition time and retained invalidation/removal evidence
Wave parent and Project selection Pending/uncertain delivery and exact creation identity
Stable domain identities and relationships Git destination, fetched/imported/published revisions, causal history

A Linear binding is keyed to the existing Work identity. It is not another Project that owns Tasks. A Git journal entry describes an edit to existing Work; it is not another object that needs its own domain placement and lifecycle.

Keep two concrete transport implementations behind the existing configuration choice. Linear needs provider baselines, revision ordering and readback of uncertain effects. Git needs causal reconciliation and publication readback. A universal synchronization state machine would add machinery without removing either requirement.

The reduction is in the shared domain and write vocabulary. Transport receipts can stay specialized and local. Reuse the existing creation/comment-delivery owners rather than inventing a new universal outbox just to make the types look symmetrical.

PlanningSyncStatus is already Linear-specific: expose it as Linear delivery evidence when relevant. PeerPlanningStatus describes a Git destination, not a Machine peer. If the UI needs one sync-status field, a tagged Linear/Git reading can wrap the concrete results; that wrapper owns no data.

PlanningState describes fact availability. Keep that information at the read boundary; it must not compete with Task disposition or observed execution status. Introduce a shared Read<T> wrapper only if real callers need the same shape—not as a prerequisite for this redesign.

Sources: Linear change evidence, creation recovery, Git publication, fact availability.

6. Walk the behavior through the smaller model

A worker files a follow-up while disconnected

  1. It creates an ordinary Task locally using a retained creation ID.
  2. It saves a comment on the source Task linking to that stable Task identity.
  3. Both writes are durable even if the configured transport is down.
  4. Reconnection delivers the pending changes. A provider issue identifier can be displayed once its mapping is known; the domain Task ID remains unchanged.
  5. If creation succeeded but the response was lost, the existing receipt owns readback. If only the comment failed, retrying that comment does not recreate the Task.

There is no follow-through object to resolve and no --none declaration when nothing remains. Pending effects remain visible through normal operation status.

Linear changes a Project description

The Linear adapter observes a specific provider revision and separates authored prose from the supported KRs/targets/workflow representation. It updates the same local Project through typed edits, preserving pending local changes and unrelated provider content according to the existing reconciliation rules.

Local readers do not reparse Linear-flavored Markdown to rediscover the Project. Prompt text is rendered from the Project. An incomplete response cannot clear fields it did not observe.

A remote Task is completed

The receiving Machine applies shared disposition. Its local captured Workflow position, Sessions, Processes and checkout stay untouched. “The work is done” remains independent from “this local process exited.” No transport receipt grants cleanup authority.

A Git merge contains competing edits

Git's journal keeps both edits and their causes. Deterministic conflict selection remains available, with losing values inspectable. If an otherwise chosen edit violates Work ownership, the import keeps the evidence and surfaces that projection failure. A failed projection cannot become an accepted ancestor for the next local edit.

This behavior requires a journal and import evidence. It does not require a second Project/Task hierarchy.

7. Implement in the order that deletes the most duplication

First, make ordinary local Work independent of provider-shaped types. Flatten Project/Task payloads, store structured criteria directly, and have local reads return the domain objects. Move actual Linear response types behind the adapter. This is the largest conceptual reduction and overlaps the approved pursuit.

Then make the writer the sole field vocabulary. Have local operations, Linear acquisition and Git import use the same typed edits. Derive Git conflict addresses and serialized edit validation from those types; delete the redundant exchange schema only after retained journal conversion is proved.

Then simplify projections and names. Roadmap readers query Work. Recovery readers inspect changes and receipts. Remove unused iteration, obsolete follow-through lifecycle and duplicate reader/patch types. Rename the remaining transport-specific structures according to their actual job.

For each cut, preserve domain IDs, provider mappings, authored text, criteria, selected Project, pending/uncertain effects and historical evidence. Existing legacy Task IDs do not get unified by a naming cleanup. Released SQL stays immutable; the Task owns one final migration draft.

Useful proof is behavioral: a Project edited offline and through Linear is read as the same Project; a Git-imported Task can be edited through the ordinary writer; reconnect never repeats creation; comments retain authorship; imported completion leaves local execution unchanged. Test the released frontier with populated records, plus transport failures at actual operation boundaries.

Implementation responsibilities

  • Choose the precise shared WorkEdit shape and derive its conflict address, including subordinate comments. Jack delegated this detail; it is not an outstanding approval.
  • Establish which Git documents already exist, and prove retained documents convert without losing causal or routing history.
  • Choose the smallest concrete Linear observation storage that preserves required evidence without reproducing a writable Work hierarchy. The deletion audit names conditional table removals and their proof.

The proposal does not add a provider framework, universal effect lifecycle, new Work scope, or distributed execution ownership. It aims to leave one model that ordinary operations use directly.
